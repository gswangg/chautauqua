### Finding 1 (OPEN ITEM) — `/admin` 404s on a literal fresh-clone Quickstart, for organizer and reviewer

Reproduced both via Playwright (browser console shows `Failed to load
resource: the server responded with a status of 404`) and via a raw `curl`
POST `/login` (CSRF cookie + form-encoded credentials) followed by `curl -b
cookies /admin`, which returns bare `HTTP/1.1 404 Not Found` with an empty
body — not a redirect, not an app error page, nothing.

Root cause (read-only inspection, not fixed — out of this task's scope):
`wrangler.jsonc` configures the `ASSETS` binding as `"directory": "public"`
with `"run_worker_first": ["/admin", "/admin/*"]`. `src/routes/root.tsx`
serves the admin SPA shell via `fetchAsset(c, "/admin/index.html")`, i.e.
`env.ASSETS.fetch(...)` against `public/admin/index.html`. That file is
produced by `npm run build` (`vite build --config app/vite.config.ts`),
which writes into `public/admin/` — a path listed in `.gitignore` and never
generated by anything in the Quickstart. `package.json` has no `predev`,
`postinstall`, or wrangler `build` hook that runs `vite build` before `npm
run dev`. Confirmed: `public/admin/` does not exist anywhere in the fresh
clone at any point in the literal Quickstart sequence.

Effect: an evaluator following the README's Quickstart literally
(`npm i && npm run db:migrate && npm run seed && npm run dev`) can log in
as organizer or reviewer, but the entire admin console (`/admin` and
`/admin/*`) 404s — J1, J3-J6, J8-J9, J11-J12 (everything living in "Admin
→ ...") are unreachable. `/login` and `/portal` are unaffected — they are
server-rendered by the worker itself, not served from the `vite`-built
bundle.

This is a stage-1 scope violation per SPEC section 0/8 as read by this
task: the documented zero-setup path does not, in fact, produce a working
admin console. (Not fixed here — task w2-g is read-only verification;
flagging per DEC-257 instructions.)

the confirmation email body, is:


not a relative href and not `http://localhost:8787/claim/<token>`. Per this
task's own instructions this is an OPEN ITEM — I did **not** fetch it (no

Read-only root-cause note: `wrangler.jsonc` has
`"routes": [{"pattern": "chautauqua.cc", "custom_domain": true}]`, and
`src/routes/public/submit.tsx:540` computes `const origin = new
URL(c.req.url).origin;` directly — the exact `req.url`-origin pattern
DEC-252 identified as broken under `wrangler dev` with a `custom_domain`
route. There is no `src/server/origin.ts` / `resolveBaseUrl` helper
anywhere in this codebase at this SHA (`grep -rln resolveBaseUrl src/`
finds nothing); DEC-252's prescribed fix was never implemented. The same
raw `new URL(c.req.url).origin` pattern also appears in
`src/routes/comms.ts:264` (notification-send origin) — a second surface
likely affected the same way, not independently verified here (out of
task scope to explore further).
