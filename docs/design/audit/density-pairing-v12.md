# Status/state density-pairing audit (DEC-730 wave-87 amendment, B8)

Generated by reading the population `app/src/status-density-pairing.scan.test.ts`
enumerates. **Wave-99 amendment (task v12m-w2-b, DEC-808):** the population
used to be `app/src/**/*.css` only — a green zero measured over half the
campaign's 53 phone frames, since the other 17 are SSR (public site, CFP,
portal, auth, docs) and their sheets were never read. The scan now enumerates
a DERIVED population with two halves:

1. **App half** — every `app/src/**/*.css` file (`readdirSync`, recursive,
   unchanged from before this wave).
2. **SSR half** — every module under `src/` that exports a top-level
   `` export const `SOMETHING`_CSS = `...` `` template literal, found via
   `test/helpers/ssr-css-sources.ts`'s `ssrCssSources()` — the same
   derived-population helper `no-fitted-geometry.scan.test.ts` already uses.
   This is deliberately **not** a `src/**/*.css.ts` filename glob: that glob
   is the exact shape that silently drops `src/views/theme.ts` (no `.css.ts`
   suffix, ~600 lines, loaded by every SSR surface) from a scan — the field
   guide records this exact failure mode twice already (DEC-393 wave-95,
   DEC-808 wave-96) for other probes.

Both halves are parsed by the same rule walker: `chq-*` classes whose name
carries a `-status-`/`-state-` segment, grouped by the stem up to and
including that segment. A member enters a family only if it is named
`dense`/`roomy` (DEC-730's own density vocabulary) or declares at least one
visual-identity property (`color`/`background(-color)`/`border*`/
`border-radius`) — pure layout wrappers sharing a stem by naming accident are
excluded, since they render no status themselves.

later only strengthens the tripwire, never weakens it.

### SSR half in detail

Grepping the 16 SSR `*_CSS` modules for a bare `.chq-...-status-...` or
`.chq-...-state-...` class (the exact shape the scan's stem-splitter
matches) finds exactly two candidates, both in `src/routes/portal/portal.css.ts`:

| selector | declarations | enters a family? |
|---|---|---|
| `.chq-portal-status-row` | `margin-top: 8px` | no — no identity property, not named dense/roomy |
| `.chq-portal-status-badge` | `display:block; font-size:11px; font-weight:800; letter-spacing:0.09em; text-transform:uppercase` | no — `font-weight`/`font-size`/`letter-spacing`/`text-transform` are not in the identity-property list (`color`/`background(-color)`/`border*`/`border-radius`); the badge carries no colour of its own (it composes `.chq-flag` in markup per the file's own DEC-729 comment) |

No other `chq-*-status-*`/`chq-*-state-*` class exists anywhere in the 16 SSR
modules (`.chq-auth-status` and `.chq-home-state` both fail the "member after
the stem word" check — the stem word is the last segment, so there is no
member name left to classify).

**Result: the SSR half contributes zero families, therefore zero
divergences.** `DIVERGENCE_CEILING` stays at `0` — re-measured over the full
(app + SSR) population, not just re-affirmed from the app-only measurement.

**Owner if this ever changes:** if a future SSR page (most plausibly
`portal.css.ts`, which already carries the naming) adds a colour/background/
border to a status class, or authors a `dense`/`roomy` pair for one, the
divergence (if any) belongs to whichever lane owns that route file at the
time — grep `git log --oneline -1 -- <file>` for the last touching branch/
commit before assigning.

### chq-speakers-status — cluster: speakers (`speakers.css`) — REFERENCE IMPLEMENTATION — owner: speakers lane

The only family that actually realises DEC-730's two-axis split: colour/
weight live on six MEANING modifiers, geometry lives on two orthogonal
DENSITY modifiers, combined on the same element via multiple classes.

| member | axis | color | font-weight | geometry |
|---|---|---|---|---|
| complete | meaning | `--chq-muted` | 600 | (none — dense/roomy applied separately) |
| pending | meaning | `--chq-ink` | 800 | " |
| overdue | meaning | `--chq-on-ink` (bg `--chq-ink`) | 800 | " |
| invited | meaning | `--chq-ink-2` | 700 | " |
| none | meaning | `--chq-muted` | 600 | " |

Check 1 (density axis carries no colour/weight) passes: neither `dense` nor
`roomy` declares `color`/`font-weight`/`background`. No other divergence.

### chq-content-status — cluster: content (`content.css`) — owner: content lane

| member | color | font-weight | geometry | density |
|---|---|---|---|---|
| muted | `--chq-muted` | 600 | none | dense |
| band | (none) | (none) | `min-height:79px; padding:10px var(--chq-pub-main-pad-x); border-top/bottom; background` | roomy |
| band-label | `--chq-muted` | 700 | none | dense |

No `dense`/`roomy`-named pair exists here — `band` (a chrome container, not a
status chip) happens to classify roomy by the same min-height+padding rule
DEC-730 uses for a real control; `muted` and `band-label` are two different
MEANING slots (flag text vs. caption) that share this stem's name, not a
density pair of each other, so the scan's colour-identity check (scoped to
the `dense`/`roomy` axis only) never compares them and correctly does not
flag `band-label`'s 700 against `muted`'s 600. Whether `band-label` and
`muted` *should* agree on weight is a content.css design question for its
owning lane, not a density-pairing defect this scan's population covers.

`.chq-content-status-band` is re-targeted inside `@media (max-width:700px)`
(content.css:1253) to `min-height:0`, but `band` classifies ROOMY (not
dense), so Check 2 does not apply to it.

## Summary

Outside `chq-speakers-status`, no family in either half of the population
authors an explicit `dense`/`roomy` pair — every other status/state token is
a single, un-paired dense chip. That is not a divergence under the checks
this scan enforces (nothing differs because nothing else exists to differ
from), but it does mean DEC-730/B8's density-pairing pattern is not yet
load-bearing anywhere except speakers.css. Should any of
`chq-content-status-muted`, `chq-review-plan-status-open/opens`,
`chq-settings-public-pages-state-live/muted`, `chq-submissions-status-label`,
`chq-comms-compose-status-cell`, `chq-comms-status-pill-count`, or the SSR
`chq-portal-status-row/badge` pair ever need to render on a phone row as a
real tap target, its owning lane (named per-section above, or the portal
lane for the SSR pair) should add the matching `-roomy` (or
architecturally, adopt the speakers.css two-class pattern) rather than
inflating the existing single class past the 20px dense register.

**DIVERGENCE_CEILING = 0**, measured over the full derived population
(app + SSR) as of this wave. The ceiling is a two-sided pin
(`toBe(divergences.length)` in the test) — it can only move when the
measured count actually changes, in either direction.
