# Status/state density-pairing audit (DEC-730 wave-87 amendment, B8)

Generated by reading the population `app/src/status-density-pairing.scan.test.ts`
enumerates (DEC-808 idiom: every `app/src/**/*.css` file, `chq-*` classes
whose name carries a `-status-`/`-state-` segment, grouped by the stem up to
and including that segment). A member enters a family only if it is named
`dense`/`roomy` (DEC-730's own density vocabulary) or declares at least one
visual-identity property (`color`/`background(-color)`/`border*`/
`border-radius`) — pure layout wrappers sharing a stem by naming accident
(`.chq-comms-status-filter`, `-pills`, `-search`, `.chq-content-status-band-info`,
`-band-actions`, `-band-copy`) are excluded, since they render no status
themselves.

**Result at the time this scan was written: zero divergences** against the
two checks the scan enforces (density-axis colour/weight leakage; a dense
member re-targeted from a `max-width:700px` block with anything beyond
`display:none`). Nothing needed fixing in `app/src/components/*.css` because
no status/state family lives there.

The families below are recorded for the lanes that own each file, in case a
future edit reintroduces the exact "bordered Pending box came back on three
phone frames" shape B8 names.

## chq-content-status — cluster: content (`content.css`)

| member | color | font-weight | geometry | density |
|---|---|---|---|---|
| muted | `--chq-muted` | 600 | none | dense |
| band | (none) | (none) | `min-height:79px; padding:10px var(--chq-pub-main-pad-x); border-top/bottom; background` | roomy |
| band-label | `--chq-muted` | 700 | none | dense |

No `dense`/`roomy`-named pair exists here — `band` (a chrome container, not a
status chip) happens to classify roomy by the same min-height+padding rule
DEC-730 uses for a real control; `muted` and `band-label` are two different
MEANING slots (flag text vs. caption) that share this stem's name, not a
density pair of each other, so the scan's colour-identity check (scoped to
the `dense`/`roomy` axis only) never compares them and correctly does not
flag `band-label`'s 700 against `muted`'s 600. Whether `band-label` and
`muted` *should* agree on weight is a content.css design question for its
owning lane, not a density-pairing defect this scan's population covers.

`.chq-content-status-band` is re-targeted inside `@media (max-width:700px)`
(content.css:1253) to `min-height:0`, but `band` classifies ROOMY (not
dense), so Check 2 does not apply to it.

## Summary

Outside `chq-speakers-status`, no family in the current tree authors an
explicit `dense`/`roomy` pair — every other status/state token is a single,
un-paired dense chip. That is not a divergence under the checks this scan
enforces (nothing differs because nothing else exists to differ from), but
it does mean DEC-730/B8's density-pairing pattern is not yet load-bearing
anywhere except speakers.css. Should any of `chq-content-status-muted`,
`chq-review-plan-status-open/opens`, `chq-settings-public-pages-state-live/
muted`, `chq-submissions-status-label`, `chq-comms-compose-status-cell`, or
`chq-comms-status-pill-count` ever need to render on a phone row as a real
tap target, its owning lane should add the matching `-roomy` (or
architecturally, adopt the speakers.css two-class pattern) rather than
inflating the existing single class past the 20px dense register.
