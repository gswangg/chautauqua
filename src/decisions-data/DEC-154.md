## Amendment (wave 158): the SPA's sign-out lands on the URL the server's redirect names — a hardcoded post-logout path silently destroys the confirmation the ruling requires

DESIGN-RULINGS.md item 24 is a 'RESTYLE — must fix' and is only half-built. The server half is correct and pinned: src/routes/auth-login.tsx`c.redirect("/login?signed-out=1", 302)` is the redirect it returns, `src/routes/auth-helpers.ts`'s `loginStatusLine` is the single owner that turns `?signed-out=1` into 'You have been signed out.', and `test/auth.test.ts` plus `test/logout-get.test.ts` both assert the redirect target. The SPA half throws it away: app/src/lib/api.ts`signOut()` POSTs to `/logout`, receives the 302, and then calls `window.location.assign('/login')` with a hardcoded path — discarding the query the server just chose. Every organizer who signs out from the admin SPA lands on a bare sign-in card and never sees the confirmation line, which is the one visible thing item 24 asks for; the passing tests cover the server redirect and the status-line helper, so nothing catches the drop. RULED: a client that follows a server redirect navigates to the URL the SERVER named, never to a path the client re-invents. `signOut()` navigates to `res.url` when the fetch followed the redirect (the browser exposes the final URL there), falling back to `/login?signed-out=1` — the literal the server and `loginStatusLine` already agree on — so the confirmation survives either path. The generalisation is the point and is what makes this a ruling rather than a one-line fix: wherever the SPA hardcodes a destination that a server handler also computes, the server's value wins, because a second copy of a destination is a second vocabulary with a delay fuse (DEC-613).
