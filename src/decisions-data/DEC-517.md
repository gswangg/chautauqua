# DEC-517: ONE `isEpochMs` predicate home, and a CFP form / evaluation plan may never be saved with its close date before its open date

## Amendment (wave 153): A write door refuses everything its own read door refuses — non-finite numbers included

DEC-517's own clause, quoted verbatim in src/routes/review/shared.ts ("Mirrors the CFP form door (forms.ts) exactly, per DEC-517's whole point: refuse identically on both surfaces"), was written about two WRITE surfaces refusing alike. It says nothing about the write/read seam, and that seam is where the product is actually breakable. Measured on main 495f0a7a: parseScale (shared.ts:71) admits ±Infinity because `typeof Infinity === "number"` and `1 >= Infinity` is false; parseCriteriaList's rating weight (:132) admits it because `Infinity <= 0` is false. JSON.stringify persists both as `null`, and the read door parsePlanScale (src/domain/evaluation/plan-json.ts:65-72) and assertCriterionShape (:96) both demand Number.isFinite and throw PlanJsonError — uncaught, a 500 — on EVERY subsequent read of that row, including reviewerCanAccessSubmissionFile in src/server/repo/files-authz.ts, which takes every reviewer file download in the event down with it, and requireOwnedPlan→toPlanRecord, which removes the DELETE recovery path. RULED: a door that writes into a JSON column must refuse every value its own read door refuses; where the two are written in different files the write door cites the read door's predicate by name. The boundary is DERIVED, not assumed — parseRounds/parseMaxEvaluations already go through Number.isInteger and parseEpochMs/round-meta opensAt/closesAt through isDayLabelMs/isEpochMs, all finite-safe, so exactly two doors move. A value JSON.stringify turns into `null` is a poison pill, and the only honest place to refuse it is where it enters.
