# DEC-865: Reviewer assignment resolves the user through the ORG_USER_ROLES vocabulary that already exists — a speaker-portal account is not an org user anywhere, including the review routes

DEC-865 already rules that the org user directory is organizer/reviewer only, and `src/server/repo/users.ts:143` implements it — the lookup is scoped `and(id, orgId, inArray(role, ORG_USER_ROLES))`. `src/server/repo/review/users.ts:118`'s `requireOrgUser` is a SECOND copy of the same resolution that validates `orgId` alone and never looks at `role`. It has exactly one caller, `POST /api/v1/plans/:id/reviewers` (`src/routes/review/plans-reviewers.ts:118`), so the blast radius is bounded and the fix is safe: any same-org user id is accepted today, including a speaker-portal account, which writes a `plan_reviewer` row that permanently inflates the plan's assigned/expected denominator, mails reviewer reminders to someone `requireReviewerOrOrganizer` will always refuse, and cannot be satisfied by any action that account can take. This is the field guide's recurring shape — a rule implemented once and missing from its sibling module — and the remedy is not a new check but reuse of the existing exported `ORG_USER_ROLES` constant so there is one vocabulary and it cannot drift. The refusal stays `not_found`, matching the sibling, so role membership is never leaked across orgs by the shape of the error.
