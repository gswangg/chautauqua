# DEC-865: Reviewer assignment resolves the user through the ORG_USER_ROLES vocabulary that already exists — a speaker-portal account is not an org user anywhere, including the review routes

DEC-865 already rules that the org user directory is organizer/reviewer only, and `src/server/repo/users.ts:139` implements it — the lookup is scoped `and(id, orgId, inArray(role, ORG_USER_ROLES))`. `src/server/repo/review/users.ts`'s `requireOrgUser` is a SECOND copy of the same resolution that validates `orgId` alone and never looks at `role`. It has exactly one caller, `POST /api/v1/plans/:id/reviewers` (`src/routes/review/plans-reviewers.ts:118`), so the blast radius is bounded and the fix is safe: any same-org user id is accepted today, including a speaker-portal account, which writes a `plan_reviewer` row that permanently inflates the plan's assigned/expected denominator, mails reviewer reminders to someone `requireReviewerOrOrganizer` will always refuse, and cannot be satisfied by any action that account can take. This is the field guide's recurring shape — a rule implemented once and missing from its sibling module — and the remedy is not a new check but reuse of the existing exported `ORG_USER_ROLES` constant so there is one vocabulary and it cannot drift. The refusal stays `not_found`, matching the sibling, so role membership is never leaked across orgs by the shape of the error.

## Amendment (wave 131)

The gap this decision describes was still open in code: `src/server/repo/review/users.ts`'s `requireOrgUser` was a second copy of the org-user resolution that validated `orgId` alone and never filtered on `role`, while its sibling `src/server/repo/users.ts` (`getOrgUserById`) already resolved the same question through `ORG_USER_ROLES`. `requireOrgUser` had exactly one caller, `POST /api/v1/plans/:id/reviewers` (`src/routes/review/plans-reviewers.ts:118`), so the blast radius was bounded. It now imports the existing exported `ORG_USER_ROLES` constant from `src/server/repo/users.ts` and adds `inArray(schema.user.role, ORG_USER_ROLES)` to its WHERE, so a same-org row outside that vocabulary resolves not-found exactly like a missing or cross-org id — no second vocabulary, no leak of role membership through the error shape. Verified with an in-memory-SQLite probe: assigning an `organizer` or `reviewer` succeeds, and assigning a same-org user whose role is a speaker-portal role is refused `not_found` and writes no `plan_reviewer` row.
