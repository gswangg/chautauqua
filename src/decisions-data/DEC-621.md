# DEC-621: The Comms phone landing's draft card renders from a real persisted draft: a frame element wired to a literal null is dead code, not an implementation

docs/design/audit/comms-v12.md finding 1 asked the planner to choose, and the tree makes the choice urgent: app/src/pages/Comms.tsx:303 renders <PhoneDraftCard draft={null} /> unconditionally, so the CENTRE element of the Comms 390 frame (Chautauqua Comms.dc.html:188-193 -- eyebrow, subject, recipient count, "Read the draft") has never rendered once in the shipped app, while PhoneDraftCard.tsx and its unit test both pass against a fabricated prop. That is the DEC-967 wave-57 tautology in component form: a test with a population the product never produces. The alternative -- deleting the card -- loses the frame, and the frame is the authority. RULED: the draft becomes real from the state the wizard already holds. One single-purpose module owns a per-event localStorage record carrying exactly what the frame draws (template name, resolved subject, recipient count, updatedAt); ComposeWizard writes it on step ADVANCE (never on keystroke, so this is not the silent pre-fill DEC-967's wave-54 amendment bans) and clears it on a successful send; Comms.tsx reads it on mount and renders the card from it, rendering nothing when absent. Nothing is fabricated: the frame's "reviewer feedback merged" provenance clause has no source in the app and is NOT invented -- the card renders the recipient count alone. A malformed record throws rather than degrading to a default (fail loudly). DEC-621's chooser deletion is unchanged and is not reopened.

## Amendment (wave 98): a phone head band's count line is phone-only, derived from data already on the page, never a second fetch

Comms.dc.html:290 draws `5 saved` as a third line inside the Templates drill head, and :339 draws `57 sends · 4 in the last 7 days` in the History drill head, while the DESKTOP pins for both surfaces (Comms.dc.html:227-229) draw no count line at all — so this is new phone-only copy, not an existing element to relocate, and TemplatesTab's existing `Saved · N` in `.chq-section-head` stays exactly where it is at every width. The same rule settles History's richer clause: `4 in the last 7 days` is computed from the send rows the tab has ALREADY fetched (the pager's current page plus the total it is handed), never a second request and never a new endpoint — the head band is a projection of the page's own state. The frame's `5` and `57` are sample data (DEC-650 wave-82: a frame carries two kinds of number; geometry and copy bind, the counts inside placeholder content do not), so what binds is the LINE's presence, position (directly under the H1, inside the head band), register (13px, muted) and grammar.

## Amendment (wave 109): The comms phone landing is an entrance, never a dead end

`phoneEntered` (Comms.tsx`useState(() => isTab(rawTab))` — this amendment has since landed) initialised `false` unconditionally, and comms.css hides the head, the tab strip and all three tab bodies at <=700px until it flips. The landing's only control is `PhoneDraftCard`, which renders nothing when `draftRecord` is null (Comms.tsx:321). So a phone with no localStorage draft is shown a title, a rhythm line and a read-only Recent sends list, and offers ZERO controls -- compose, templates and history are all unreachable -- while `/comms?tab=templates` silently shows the landing instead of the tab the URL asked for, despite DEC-710 making `?tab=` the bookmarkable contract. RULING, two clauses. (a) The URL wins: when `searchParams.get('tab')` is a recognised tab, the visitor named a screen and the landing is skipped. (b) The landing always carries a route into the three tabs. The frame (Comms.dc.html:188-193) draws the draft card as the one CTA when a draft exists; when none does, that same slot carries the equivalent entry and the Recent sends head carries the two remaining tab entries. Labels come from the existing tab strip's own vocabulary -- no new copy is invented -- and the geometry is the frame's card (bordered, 6px radius, #FAF8F2, 44px floor). DEC-919 governs: re-line, never remove.


## Amendment (wave 125: a Comms `?tab=` drill stands the landing head and tab strip down at 390 through the Contacts MARKUP gate, not a second CSS suppression)

At 390 a Templates or Send-history drill prints `<h1 class=\"chq-page-title\">Comms</h1>` (Comms.tsx:249) and the tab strip (:263) above the drill's own `.chq-phone-head chq-phone-head-drill` band — two heads on a screen the frames draw with one. Comms already adopted the shared drill vocabulary (DEC-576 wave-7), so the band is right; what is missing is the stand-down. Contacts solved this identically, at two sites, with ContactsApp.tsx`{!(isPhone && panel !== 'directory') && (` under `useIsPhone()`, and DEC-576 wave-120 (b) ruled that gate the idiom precisely because it is markup: desktop renders byte-identically with no new selector, no `display:none` that leaves an off-screen control tabbable (the DEC-919 trap), and nothing for a cascade-order accident to lose. The alternative — a CSS suppression in comms.css — would be a second copy of a mechanism the tree already owns, which is the DEC-613 delay fuse. One idiom, applied a second time, is not duplication; a second mechanism for one behaviour is.

## Amendment (wave 25): the compose-draft record is session-scoped -- sign-out clears it, because a frame element that renders another person's data is worse than one wired to null

DEC-621 made the Comms 390 frame's 'Draft in progress' card real by persisting a per-event localStorage record. The key is `chq.composeDraft.<eventId>` with no user or org scoping, and app/src/lib/api.ts's signOut() only POSTs /logout and navigates -- nothing in the SPA removes the record. On a shared browser (including the seeded demo personas an eval judge drives) the next organizer's Comms phone landing renders the PREVIOUS user's subject line and recipient count as their own draft. That is a strictly worse failure than the `draft={null}` stub DEC-621 was written to kill: the frame element now renders, and renders a lie about who wrote it. It is also the same line DEC-967's wave-54 amendment draws against silent pre-fill of state the visitor did not act to create. RULED: composeDraft.ts owns a clearAllComposeDrafts() that removes every `chq.composeDraft.` key, and signOut() calls it before navigating. The fail-loudly throw on a malformed record is unchanged and not reopened.

## Amendment (wave 33): a persisted compose draft this module cannot read is EVICTED and reported, never fatal — the write side stays loud

`readComposeDraft` throws on any JSON.parse or shape mismatch and `Comms.tsx:105` calls it unguarded in a mount effect, so one unreadable `chq.composeDraft.<eventId>` record sends the entire Comms page to `RouteErrorBoundary`. The only `removeItem` for that key is `clearComposeDraft`, reached only from a successful send — which the organizer can no longer reach, because the page that would send is the page that is crashing. /comms is bricked until localStorage is cleared by hand. The module's premise ("localStorage is OUR OWN writer, not an external boundary") is right about the SHAPE and wrong about the BOUNDARY: a versionless record that outlives deploys, other tabs and truncated writes is exactly the external-input boundary the house rule carves out. RULED: `assertValidDraft` stays loud on the WRITE side — a caller handing this module a malformed draft is still a bug and still throws. On the READ side a stored value that fails to parse or fails the shape check is removed and `null` is returned; nothing else is swallowed, and `readComposeDraft` still throws for a caller error (empty eventId). `writeComposeDraft` guards ONLY its `setItem` call, after the assert: a QuotaExceeded or Safari-private throw means the draft card cannot be recorded, which must never take the wizard down on "Next", and the key is removed so a half-written record can never be read back. This is eviction-plus-recovery, not a silent fallback: the state that could not be honoured is destroyed rather than papered over.
