# DEC-621: The Comms phone landing's draft card renders from a real persisted draft: a frame element wired to a literal null is dead code, not an implementation

docs/design/audit/comms-v12.md finding 1 asked the planner to choose, and the tree makes the choice urgent: app/src/pages/Comms.tsx:303 renders <PhoneDraftCard draft={null} /> unconditionally, so the CENTRE element of the Comms 390 frame (Chautauqua Comms.dc.html:188-193 -- eyebrow, subject, recipient count, "Read the draft") has never rendered once in the shipped app, while PhoneDraftCard.tsx and its unit test both pass against a fabricated prop. That is the DEC-967 wave-57 tautology in component form: a test with a population the product never produces. The alternative -- deleting the card -- loses the frame, and the frame is the authority. RULED: the draft becomes real from the state the wizard already holds. One single-purpose module owns a per-event localStorage record carrying exactly what the frame draws (template name, resolved subject, recipient count, updatedAt); ComposeWizard writes it on step ADVANCE (never on keystroke, so this is not the silent pre-fill DEC-967's wave-54 amendment bans) and clears it on a successful send; Comms.tsx reads it on mount and renders the card from it, rendering nothing when absent. Nothing is fabricated: the frame's "reviewer feedback merged" provenance clause has no source in the app and is NOT invented -- the card renders the recipient count alone. A malformed record throws rather than degrading to a default (fail loudly). DEC-621's chooser deletion is unchanged and is not reopened.

## Amendment (wave 98): a phone head band's count line is phone-only, derived from data already on the page, never a second fetch

Comms.dc.html:290 draws `5 saved` as a third line inside the Templates drill head, and :339 draws `57 sends · 4 in the last 7 days` in the History drill head, while the DESKTOP pins for both surfaces (Comms.dc.html:227-229) draw no count line at all — so this is new phone-only copy, not an existing element to relocate, and TemplatesTab's existing `Saved · N` in `.chq-section-head` stays exactly where it is at every width. The same rule settles History's richer clause: `4 in the last 7 days` is computed from the send rows the tab has ALREADY fetched (the pager's current page plus the total it is handed), never a second request and never a new endpoint — the head band is a projection of the page's own state. The frame's `5` and `57` are sample data (DEC-650 wave-82: a frame carries two kinds of number; geometry and copy bind, the counts inside placeholder content do not), so what binds is the LINE's presence, position (directly under the H1, inside the head band), register (13px, muted) and grammar.

## Amendment (wave 109): The comms phone landing is an entrance, never a dead end

`phoneEntered` (Comms.tsx:59) initialises `false` unconditionally, and comms.css hides the head, the tab strip and all three tab bodies at <=700px until it flips. The landing's only control is `PhoneDraftCard`, which renders nothing when `draftRecord` is null (Comms.tsx:321). So a phone with no localStorage draft is shown a title, a rhythm line and a read-only Recent sends list, and offers ZERO controls -- compose, templates and history are all unreachable -- while `/comms?tab=templates` silently shows the landing instead of the tab the URL asked for, despite DEC-710 making `?tab=` the bookmarkable contract. RULING, two clauses. (a) The URL wins: when `searchParams.get('tab')` is a recognised tab, the visitor named a screen and the landing is skipped. (b) The landing always carries a route into the three tabs. The frame (Comms.dc.html:188-193) draws the draft card as the one CTA when a draft exists; when none does, that same slot carries the equivalent entry and the Recent sends head carries the two remaining tab entries. Labels come from the existing tab strip's own vocabulary -- no new copy is invented -- and the geometry is the frame's card (bordered, 6px radius, #FAF8F2, 44px floor). DEC-919 governs: re-line, never remove.
