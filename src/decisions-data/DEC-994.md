# DEC-994: A credential-recovery reset revokes bearer API tokens, not only cookie sessions

`deleteApiTokensForUser` (src/server/repo/users.ts:205) has exactly ONE call site in the tree — `src/routes/api/users.ts:187`, the ORGANIZER-triggered reset — and that call site's own comment states the reason: a `chq_` token keeps full organizer authority, and its CSRF exemption, after a reset that only cleared cookie sessions. The two paths a compromised user actually takes — `src/routes/auth-reset.tsx` (forgot-password, anonymous browser that only proved inbox control) and `src/routes/account.tsx` (self password change) — both call `issueSessionRevokingAll` and nothing else, so an attacker who minted a token from a stolen session keeps organizer access through exactly the doors recovery exists for, and `DELETE /api/v1/tokens/:id` cannot clean it up without the session the reset just destroyed. This is the DEC-027 class the field guide names (CSRF-EXEMPT WITHOUT SESSION IS BEARER-REACHABLE). Ruling: a credential-recovery act revokes every credential the lost credential could have minted. Both paths call `deleteApiTokensForUser` alongside `issueSessionRevokingAll`; the self-service password change is included because DEC-994's own stated premise for revoking all sessions there (`every other device/browser is signed out`) is false while a bearer token survives.
