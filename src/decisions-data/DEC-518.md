# DEC-518: A cross-file manifest is DERIVED in a test, never hand-mirrored — including the test that guards a manifest

## Amendment (wave 91): a ledger keyed by file path is RE-DERIVED when a module is split or renamed — the new path is the population member, and the old path's row is stale, never both

test/spa-count-source-ledger.scan.test.ts fails in both directions at once: useTracksRoomsPanel.ts is a population member with no row, and TracksRoomsPanel.tsx is a row citing a file no longer in the population. DEC-518 already says a cross-file manifest is derived, never hand-mirrored; what it did not say is what happens at a rename. Stating it makes the two-sided failure self-explaining and keeps a future refactor from 'fixing' the scan by adding the new row while leaving the old one, which passes the population→ledger direction and fails the other.

## Amendment (wave 102): a test-only fixture module is not dead code — it earns a rule-shaped ENTRY_OR_ALLOWED entry, in a named shape, not a per-file exception

module-reachability.scan.test.ts is red on `app/src/pages/settings/TracksRoomsPanel.render-helpers.ts`, unreachable from any entry point and absent from ENTRY_OR_ALLOWED. Both directions of the ledger are satisfied in the same edit, so the no-drift assertion goes green with it. The house rule is no dead code, not no test infrastructure.

The reason names what the file IS, never a wave, branch or schedule.

## Amendment (wave 108, mandate D21, v12m-w4-t): a failed background revalidation keeps the stale rows AND raises the page's error banner; reconciliation REPLACES the payload wholesale and never merges

app/src/spa-fetch-swallow-honesty.scan.test.ts's KNOWN_SWALLOWS ledger currently holds exactly 25 entries against a `toBeLessThanOrEqual(25)` tripwire — it is FULL. So no task in this subtree may add a non-surfacing `.catch(` anywhere under app/src: every catch these tasks write must name a `set*Error*`-shaped setter or rethrow. That constraint and the honest design coincide. RULED: the hook owns exactly one catch, and it calls `setError(err instanceof ApiError ? err.message : failureMessage)` — surfacing, so it needs no ledger row. On that failure `data` is left EXACTLY as it was: the previously rendered rows stay on screen and the page's existing error banner appears above them. Stale data plus a visible statement that the refresh failed is honest; stale data with nothing said is the lie, and blanking rows the user was reading to punish a network blip is the other failure mode. On SUCCESS the fresh payload REPLACES `data` wholesale — never a per-field or per-row merge, never a union of cached and fresh items — so a row deleted server-side cannot survive in the rendered list, and `error` is cleared. Two further ledger hazards each page task must check before committing: (a) removing an api* call from a page changes which call is "nearest preceding" for a LATER non-surfacing catch in the same file, which can both strand a ledger row as stale and create an unledgered offender — verified safe for all three target files at main (ContactsApp.tsx's two loadEventsOnce catches at :169/:187 precede every api* call in the file and keep their "(no preceding api call found)" context; OnboardingGrid.tsx's and SubmissionsTable.tsx's ledgered catches each immediately follow their own call), but it must be re-checked, not assumed; (b) the scan's API_CALL_RE does not recognise `apiGetCached`/`apiListCached`, so those two names are added to the alternation AHEAD of `apiGet`/`apiList` (longest-first, or the regex matches the short prefix and stops).

## Amendment (wave 117): A refetch is a keyed read: its resolve is discarded unless the key it was issued for is still the key on screen

app/src/lib/useCachedRead.ts guards its path effect with a `cancelled` flag (:54-68) but `runRead` (:29-43) writes setData/setError with no guard at all, and `refetch()` (:72-75) calls it. OnboardingGrid.tsx awaits gridRead.refetch() after every mutation (:790/:819/:837/:857/:872) while gridPath is keyed on event + filters + page (:366-369), so a filter, page or event change landing during an in-flight refetch writes the OLD key's payload into the NEW view -- silently, with optimisticOverride already cleared, and with no error to show. The guarded effect and the unguarded refetch are two halves of one contract that disagree. RULED: cancellation is a property of the READ, not of the effect that happens to own it. runRead takes the key it was issued for plus a generation token; a resolve or reject writes nothing unless both still match the live path and the live generation. Every path change, mutation-version bump and unmount advances the generation. The rule is stated once in the hook, so no caller has to remember it.

## Amendment (wave 118): an exemption reason may not name a lane in ANY naming, nor describe work in progress — and the blessed-deviations document is inside that rule's population

`test/exemption-reason-is-a-principle.scan.test.ts` exists to stop "an exemption reason may never be a branch name," but its `BRANCH_NAME_RE` is `/task-w\d+-[a-z]/` — the PREVIOUS naming. Every branch in this campaign is `v12m-wN-x`, so the rule the scan enforces has been unenforceable against current work for the whole campaign. It has already been evaded: `docs/design/DEVIATIONS.md:267` blesses deferring the Portal task-list dock and justifies it with "v12m-w15-b is doing exactly that" — a live branch, in the tree's highest-precedence deviation document, as the reason a gap stays open. The document is also outside the scan's population (test files only), so nothing checks it. Both halves are the same defect: an instrument whose predicate and whose population were each fixed to a moment in time. RULED: (1) the branch pattern covers the lane-naming shapes the repo actually uses; (2) the schedule-shaped list gains the progressive/future work-in-flight constructions ("is doing", "is building", "will land") that carry the same meaning with the token filed off; (3) `DEVIATIONS.md`'s deferral sections are a reason population by construction and join the scan. A lane name stays legal ONLY as the authorship of a landed ruling — a line that also cites the `DEC-NNN` it landed under — because that is a fact about the past, not a promise about the future.

## Amendment (wave 126): a keyed read clears its error when the key changes

`app/src/lib/useCachedRead.ts`'s path effect seeds `data` from the cache on a path change but never calls `setError(null)`, so a failed read's message survives onto the NEXT key. Because `loading` is derived as `data === undefined && error === null`, the new key does not even render a skeleton — it renders the previous key's failure banner as though it described the new object. This is exactly the discipline `useCurrentEvent.ts:103` implements for the same shape, and `spa-error-clear.scan.test.ts` cannot see it because the state lives in a hook with no `role="alert"` nearby — so the defect leaks into every page migrated to `useCachedGet`/`useCachedList`. The error-clear rule is a property of the KEY changing, not of a component rendering an alert.
