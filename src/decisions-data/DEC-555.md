# DEC-555: The itinerary picker MERGES localStorage with the checkboxes actually rendered; a day-filtered or row-capped render can never delete a pick

The saved-itinerary picker's localStorage-backed selection set is merged against the rows the current render actually shows, never replaced wholesale — a day filter or a row cap must not silently drop a pick the organiser made on a different view.

## Amendment (wave 148): the /schedule overlaps panel speaks one sentence per SESSION naming its time range and every session it covers, not one line per pair

`Chautauqua Public and Portal.dc.html:847` draws 'Evaluating Agents runs 10:00–12:00, over both Taming 40-Minute CI and Your AI Pair Programmer.' — one sentence covering a session and all of its clashes. `src/routes/public/agenda-itinerary-script.tsx` composed one line per pair, deduped by a sorted pair key; as built by this ruling's wave-148 amendment it now composes `item.title + ' overlaps ' + joined + '.'` (and the richer `' runs '` range form when the item carries one). The frame's form is strictly more informative and every input is already in the script's own saved-item shape (`startMin`/`endMin` are parsed at :99-100 from the row's `data-start-min`/`data-end-min`). Ruling: group by the covering session, print its clock range through the SAME formatter the day rows already use (never a second clock helper — DEC-522's day-label hazard is a live one in this file), and join the covered titles as 'both X and Y' for two, a comma list ending in 'and' for three or more. The per-row inline `Overlaps <title>` chip at :112 is a different affordance in a different place and is untouched; the panel heading's '1 overlap' / 'N overlaps' count keeps counting PAIRS, so the heading and the sentences are allowed to disagree in number and the sentence count is not asserted against it.


## Amendment (wave 29): the itinerary change handler is ONE serialized write path — a read-modify-write spread across an event handler is not atomic against its own reads

docs/mobile-campaign.md gained a Cut-4 triage section at main b2157a6e2 naming one REAL item: on the public /schedule itinerary view the per-session Remove control toggles visually but the removal does not persist, diagnosed as the shared localStorage handler's read-modify-write racing a concurrent write/reload. The handler in src/routes/public/agenda-itinerary-script.tsx does re-read `localStorage.getItem(key)` inside the change listener, but the mutation is spread across four steps (mirror the checkbox set, derive currentIds() from live DOM state, merge, setItem) with `allRenderedIds` captured once at IIFE init from a static NodeList — so the write is a function of DOM state read at three different moments, not of one snapshot. RULED: (a) the handler routes every mutation through ONE serialized write function that takes the changed (value, checked) pair, re-reads storage, computes the next list, writes it, and returns it — no other code path calls setItem on the itinerary key; (b) the derived view (updateLink, applyScheduleView) is driven from the RETURN VALUE of that write, never from a second DOM read afterwards; (c) the root cause is re-derived against the tree before the fix lands (DEC-903) — the mandate's diagnosis is a claim, and the failing case must be reproduced in a test before it is repaired; (d) no UI change, and DEC-555's merge rule (a day-filtered or row-capped render never deletes a pick) is preserved by construction.

## Amendment (wave 29, task w29-c receipt): the mandate's "read-modify-write race" is not what reproduces — the real defect is a SECOND embedded-dependency gap (EMB-10/11's own class), and it disables the Remove listener entirely

DEC-903: verified against the tree, not paraphrased. A plain single-tab synchronous remove-then-reload and a rapid toggle-toggle-reload (test/itinerary-script-persistence.test.ts) do NOT reproduce a failure against the pre-fix handler — the merge/mirror math is correct for that case, since a single JS event loop has no true concurrency between the handler's own reads. The REAL, reproduced root cause: `applyScheduleView()`'s overlaps sentence calls `__chqClock` (the embedded copy of `src/domain/clock.ts`'s `clockHMM`), and `clockHMM`'s own source text calls `assertValidMinute` as a free identifier — a private, unexported module-level function. `.toString()` embedding (the idiom this file already documents for `mergeItinerarySelection`/`MAX_ITINERARY_IDS`, EMB-10/11) carries only a function's SOURCE TEXT, never a closed-over dependency, so `assertValidMinute` was never emitted into the IIFE. The FIRST time a visitor has two time-overlapping saved sessions — an ordinary state; it's the entire reason the wave-148 overlaps panel exists — the initial `applyScheduleView()` call at page load throws `ReferenceError: assertValidMinute is not defined` synchronously, BEFORE `document.addEventListener('change', ...)` (the IIFE's last line) ever runs. The checkbox still flips visually on click (native browser behavior needs no JS), but with no listener ever registered, nothing is ever written to localStorage — this is the observed "toggles visually but does not persist" shape. Reproduced in `test/itinerary-script-persistence.test.ts`'s "overlapping saved sessions crash init and silently disable Remove entirely (w29-c root cause)" describe block; fails pre-fix with the exact `ReferenceError`, passes post-fix.

Fix: `assertValidMinute` is exported from `src/domain/clock.ts` and embedded into the IIFE under its own name, same idiom as every other helper. Separately (defense in depth, and to satisfy this ruling's (a)/(b) literally): `src/lib/itinerary.ts` gained `applyItineraryToggle`, the ONE serialized write function ruled above — it takes one storage snapshot, one DOM-checkbox-state snapshot, and the changed `(value, checked)` pair, and returns both the next persisted id list AND the checkbox states every view must redraw from (resolving each box's checked state to agree with what `mergeItinerarySelection`'s `MAX_ITINERARY_IDS` cap actually kept — closing a second, real, cap-triggered divergence between the raw DOM and storage, covered by the "cap divergence" test in the same file). `agenda-itinerary-script.tsx`'s change handler now reads storage exactly once, calls `applyItineraryToggle` exactly once, and `applyScheduleView` takes `ids` as a parameter instead of re-deriving it via a second `currentIds()` DOM read — no other code path calls `setItem` on the itinerary key.

## Amendment (wave 34): the persistence listener is registered before the first paint, and a parsed store is proved to be an array

src/routes/public/agenda-itinerary-script.tsx runs the checkbox sync, updateLink(stored) and applyScheduleView(stored) BEFORE binding the change listener that persists Remove. Any throw in those first-paint passes reproduces the shipped Cut-4 MAJOR symptom exactly (docs/mobile-campaign.md: "Remove toggles visually but the removal does not persist"). Commit 01d815c5c removed one instance of the throw (the missing assertValidMinute embed) but not the failure MODE — the ordering is still the bug. RULED: the handler that makes an act durable is registered before any code that could throw, because a page that cannot render is recoverable while a page that silently discards writes is not. Compounding it, JSON.parse(localStorage.getItem(key)) is never proved to be an array before stored.indexOf is called, and currentIds() is dead code the wave-29 rewrite left behind. A localStorage read is an external-input boundary, so Array.isArray guarding it is the sanctioned catch, not a defensive fallback.
