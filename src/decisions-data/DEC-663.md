# DEC-663: The phone import pager ends in the dry run, and the frame's existing-contact count renders only from the plan that produced it

docs/design/audit/contacts-v12.md findings 2 and 3 have been open since wave 1 and both are decisions, not fixes. Finding 3: the v12 "Import CSV · 390" frame draws only mid-pagination (column 2 of 5) and never shows what happens after the last column, so the landed pager clamps and leaves the organiser to find the shared modal footer -- a one-column-per-screen flow whose last screen is a dead end. Finding 2: the frame's literal "9 rows match an existing contact by email · those get updated" can only come from the server's dry run (plan.updated), which does not exist at that step, so the lane substituted the same-file dedupe count -- a different number under the frame's sentence, which is the kind of near-miss DEC-663 was written against ("A CSV import is PLANNED before it is applied: one dry run names, per row, what it will do"). RULED: (a) the last column's primary becomes the entry to the plan -- it reads "Review N rows" and runs the same runPreview() the desktop Review step runs, so Next column / Skip is a path INTO the dry run rather than a cul-de-sac; (b) the existing-contact note renders only from the dry-run plan's own updated count and renders NOTHING before that plan exists -- a number with no plan behind it is worse than a missing line; the same-file dedupe count returns to where it is true, beneath the column grid. The two-stacked-docks half of finding 1 stays with the shell lane and is not addressed here.
