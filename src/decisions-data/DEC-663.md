## Amendment (wave 115): an import-merge FILLS a blank email and never replaces a non-blank one — the offered address is reported, and picking a side stays with the merge tool

Judge-filed: "merging the speakers.csv row overwrote Marcus Okafor's stored email with the imported value." That is not a coding accident — DEC-663's own wave-64 amendment ruled it ("the CSV row's email REPLACES the target's stored email (that is the whole point — same person, new address)") and `applyImportRows` implemented it literally, forcing the row's normalized address onto the merged commit row. Wave 64 was wrong on its own terms, twice. FIRST: `describeImportOverwrites` (src/domain/contacts-parts/duplicates.ts) types `ImportPlanOverwrite.field` over firstName/lastName/company/title/phone/bio and structurally cannot carry `email`, so the ONE field the merge disposition destroys is the one field DEC-663's dry run cannot name — and DEC-663 exists precisely because "the organizer is asked to commit before being shown the consequence". Every other clobbered identity field (name, company, title) is legal because the plan renders it struck-through old → new before an irreversible commit (wave-27 amendment); email had no such receipt. SECOND: DEC-456/DEC-479 cascade a changed contact email onto the linked `user` login row, and BOTH other write paths run it — `patchContact` and `mergeContacts` (src/server/repo/contacts/merge.ts:639-646). The import merge has no cascade at all, so the ruled overwrite silently desynced a speaker's sign-in address from their CRM record.

RULED, reversing wave 64's email clause and nothing else: a merge line FILLS a blank stored email and NEVER replaces a non-blank one. When the file's address differs from a stored non-blank one, the stored address stands and the offered one is REPORTED — `ImportResult.emailConflicts` carries `{ line, contactId, kept, offered }`, the review step says "Merging keeps the stored address" before the commit, and the summary names each conflict afterwards. The commit response carries the field only when there are conflicts, exactly as `addedToEvent` appears only for a roster-scoped import. Wave 64's other four clauses are untouched: a merged line still does not create, still re-derives its target against the candidate set, still counts as `updated`, and its address still ROUTES later same-address rows in the same file to the same contact (routing is this run's lookup, not a column). Changing which address a person answers to is a pick-a-side act, and this product already owns exactly one surface for it: the Duplicates/merge tool, whose `planMerge` (DEC-167) already rules this precedence with `fill(primary.email, duplicate.email)` and whose preview names both records and their vintages (DEC-992). Two merge surfaces with opposite email precedence is one vocabulary too many, and the one that cannot preview the loss is the one that yields.

## Amendment (wave 135): A dry run plans the SAME inputs the real run applies -- a preview that cannot see mergeLines is a preview of a different import

src/routes/api/contacts/import.ts:265 calls planImportRows(db, orgId, rows) while the real run at :270 calls applyImportRows(db, orgId, rows, { skipLines, mergeLines }). planImportRows has no mergeLines parameter at all, so every merge row previews as action:'create' -- the organiser is shown 'this will create a new contact' for a line that will in fact overwrite firstName, lastName, phone, company, title, bio, notes and customFields on an existing person, and `overwrites` is computed only on the email-matched update branch (src/server/repo/contacts/import.ts:792) so none of those eight columns is disclosed. This is the still-open root of the cut-2 MAJOR the mandate records as 'the copy and the behavior must agree': wave-115 taught the plan to promise the stored email is preserved, which made the preview MORE trustworthy about the one column it can see and no more honest about the other eight. DEC-663's existing invariant (never applyImportRows on a dry run) is untouched -- the fix is that the planner receives the same disposition inputs, resolves a merge line to its update, and reports its overwrites through the struck-through old-to-new idiom that already exists.

## Amendment (wave 136): a CSV import run is one address space — a merge line may not fill an org-scoped email that an earlier line in the same file just minted

applyImportRows (src/server/repo/contacts/import.ts) validates every merge line in a PRE-PASS (~:300-410) whose email-collision guard reads `byEmail`, a map populated only from the DB pre-pass at ~:279. The apply loop that follows (~:418+) walks rows in file order and keeps `byEmail` current for both creates (~:504) and merge fills (~:485) — but by then the merge lines have already been blessed. So a plain create line for ada@x.com followed, later in the SAME file, by a merge line that fills ada@x.com onto a blank-email target passes every check and commits two contacts sharing one org-scoped address. The contact table carries only the non-unique contact_email_idx, so the database refuses nothing, and every email-keyed identity path afterwards — lookupContactIdsByEmail, findAccountUserId, claim links, duplicate detection — silently picks one of the two. The guard belongs where the map is true, not where it is stale: the collision decision moves into the apply loop, immediately before the fill, and refuses through the SAME ApiError shape and mergeLines field vocabulary the pre-pass already speaks (one vocabulary, DEC-613). The pre-pass check stays — it still catches DB collisions before any write, and catching a fault earlier is not the same as catching it correctly.

## Amendment (wave 22): The CSV merge-FILL path is a login-identity write and owes both halves of DEC-456, not just the org-scoped contact check

DEC-456 makes a contact's email a LOGIN identity: `src/server/repo/contacts/crud.ts`'s `patchContact` refuses a new address already owned by a different `user` row and then cascades the accepted address onto the contact's own linked `user` row, so login identity never drifts from the CRM record. ## Amendment (wave 25): (orgId, lower(email)) identity is enforced on every WRITE path, not only on create -- patchContact owes the same 409 POST /contacts already gives

src/routes/api/contacts/crud.ts:186-193 refuses a create that collides with an existing contact's email in the same org, on the stated rule that identity within an org is (orgId, lower(email)) on every find-or-create path. src/server/repo/contacts/crud.ts's patchContact (:141) consults only schema.user -- login accounts -- and never another contact row, so editing an email in the drawer mints a duplicate-identity contact with no unique index to stop it. Downstream that is not cosmetic: findContactByEmail (src/server/repo/submit.ts:180) binds repeat CFP submitters and co-presenters to whichever row is older, and DEC-663's own 'never overwrite a non-blank email' import policy becomes bypassable by hand. A rule enforced on one of two write paths is a rule with a hole, which is the shape DEC-663's wave-22 merge-FILL amendment already closed on the import side. RULED: patchContact performs the sibling-contact check and throws the SAME ApiError('conflict', ...) the create path throws, reusing its message string so the refusal vocabulary keeps one source.

## Amendment (wave 30): CSV import mapping is keyed by column INDEX, not header name -- two columns sharing a header are two distinct sources and the injectivity rule must see both

src/domain/contacts-parts/import.ts:132 keys the mapping by CSV column NAME. `validateImportMapping` (:74) is documented as "the ONE place the injectivity rule lives ... never silently drops", but it cannot see a collision that happened before it ran: two columns named `Email` (primary/secondary -- routine in CRM exports) collapse to one key, `mapImportRow`'s left-to-right assignment keeps the rightmost, and when that column is blank the row returns `{}` and is counted as "no email, skipped" with no receipt naming the discarded column. That is exactly the silent-drop DEC-663's own text forbids, one layer below where the rule is enforced. Ruling: the mapping key is the column's zero-based INDEX; the header name is display only. A duplicate header is either refused at validateImportMapping with both column positions named, or disclosed on the completion receipt the same way DEC-663's emailConflicts rows are -- never resolved by last-write-wins.
