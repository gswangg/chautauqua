# DEC-996: The admin-390 tap-floor roster classifies every sighting as EXEMPT or CANDIDATE; a bare count over a mixed population is not a measurement

ADMIN_MOBILE_INTERACTIVE_OFFENDERS_CEILING = 77 is the campaign's Tier 2 44px-floor number, and docs/design/audit/admin-mobile-tap-floor-390-v12.md — the machine-written roster scripts/render-sweep.ts emits — lists all 77 as undifferentiated lines. Reading it on 32436e11b: ~74 are `input.chq-check*` sightings whose operable target is the documented `.chq-check-hit` label wrapper (app/src/styles.css's own tap-floor-exempt comment), 2 are `a.chq-wordmark` on /dev/mailbox (DEC-382 operator chrome, exempted in src/views/theme.ts), and 1 is `a.chq-overview-link-inline` (DEC-393 wave-106's inline-in-prose ruling, pinned by overview-phone-floor.test.ts). Every one of the 77 is already adjudicated somewhere in the tree, and the roster says none of it — so a reviewer reads 77 open tap-floor defects where the honest number is 0, and a genuinely NEW offender would land in that same undifferentiated list and be invisible. This is DEC-903's own ruling generalised: a classification row is re-classified in place so the roster's arithmetic and its measured total both stay honest. RULED: the pure formatter gains a classification argument — an exempt-token set supplied by its caller, never read from disk inside the formatter, so purity holds — labels each line EXEMPT (naming the receipt that reaches it) or CANDIDATE, and prints `Measured total: N (exempt: X, candidate defects: Y)`. The exempt set is DERIVED by the scan test from the tree's own `tap-floor-exempt` / `chq-check-hit` receipts, never hand-listed, and a vacuity control proves an unreceipted selector classifies CANDIDATE.
