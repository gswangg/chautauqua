# DEC-065: Amendment: the destructive file path inherits the read path's dangling-authoritative-link refusal verbatim — one grader, not two

src/server/repo/files-authz.ts`if (!fileRow.taskAssignmentId)` is the gate on the reverse `task_assignment.file_id` fallback, and its DEC-065 wave-10 comment states why: a file whose own `taskAssignmentId` names a deleted/reassigned assignment must NOT borrow the reverse link, because that link is not guaranteed to resolve the same assignment and silently borrowing it would grant access under a different speaker's `assignmentContactId`. `src/server/repo/files-versions-delete.ts:132` gates the identical fallback on `if (!assignmentRow)` — the exact re-resolution the read path bans — while its own comment claims parity (`the SAME links, in the SAME order`). So the DESTRUCTIVE door resolves its entire authz check (orgId, eventId, assignmentContactId) from an unrelated assignment in precisely the case the read door refuses. This is the field guide's second-copy-of-a-vocabulary trap (DEC-613): the fix is not to re-type the condition but to make both doors read one exported resolver, so a future amendment cannot move one without the other.
