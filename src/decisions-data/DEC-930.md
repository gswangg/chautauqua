# DEC-930: A speaker has ONE event-scoped detail page at /admin/speakers/:contactId, served by ONE bounded GET

## Amendment (wave 115): a headshot IS a file object — it takes a Files row like any other, and every Files row names its uploader and its timestamp

Filed by a judge in ALL FIVE eval runs, which makes it the highest-yield open defect in the speaker-management rubric. A portal-uploaded headshot reached the organizer's record as an avatar plus a bare "Download" and appeared NOWHERE in the record's Files table — no filename, no uploader, no timestamp — while a task upload sitting in the same section showed its filename and size. The rule this breaks was already written. DEC-894 ruled, for the Contacts drawer, that the surface "prints the stored file's filename and upload date beside the image: an uploaded file with no metadata reads as decoration, not as a record" — and GET /contacts/:id still computes a `headshotFile { filename, uploadedAt }` per request to honour it. The speaker record is the one headshot surface that never got the rule, which is why five separate judges read the same page and filed the same complaint. The asymmetry was never a storage limit: `setContactHeadshot` (src/server/repo/profile.ts) inserts a real `schema.file` row carrying `filename`, `sizeBytes`, `uploadedByContactId` and `createdAt`, and `fetchHeadshotRoots` (src/server/repo/files-library-list.ts) already reads exactly those columns to list headshots in the ADMIN Files library. The speaker record was simply the one surface that reduced a file to a thumbnail. `getSpeakerDetail` projected `contact.headshotFileId` as a bare id and joined no file row at all.

RULED, in three parts. (1) The payload carries `headshotFile: SpeakerDetailFile | null` — one single-row read scoped to `kind = 'headshot'` (HEADSHOT_KIND, the same predicate `getHeadshotServeScope` applies, so this can never widen into a general file-by-id read), skipped entirely when the contact has no headshot. DEC-930's bounded-GET contract is preserved: the query count stays independent of how many sessions or tasks the contact has. (2) `SpeakerDetailFile` gains `uploadedAt` and `uploaderName` for EVERY file the section lists, not just the headshot — "list the headshot like any file row" is only meaningful if the other rows carry the same facts, and `createdAt`/`uploadedByContactId` were already on the join. Names resolve through ONE chunked lookup (DEC-078) over the DISTINCT uploader ids other than the speaker themselves, who is resolved from the contact row already in hand. `uploaderName` is null — rendered as a dash — when the file row records no uploader; only the HEADSHOT falls back to the owning speaker's name, because ownership makes that true there and nowhere else, which is the same rule files-library-list.ts already applies. (3) The row keeps the frame's FOUR cells (docs/design/Chautauqua Speakers.dc.html:391-396 draws tag / name / when / Download, and DEC-982 makes a shared row grid a contract on cell count): the uploader and timestamp fold into the name cell as a subline, the same file-cell-with-subline anatomy the admin Files library uses. The headshot downloads through `/headshots/:id` and a task upload through `/files/:id` — the split `FilesLibrary`'s own `downloadHref` already makes.

NO version history is invented. `setContactHeadshot` never sets `previousFileId`, so a headshot is structurally a single-file chain: a new upload is an unlinked row and the old one simply stops being referenced by `contact.headshotFileId` (which is also why `/headshots/:id` cannot serve a superseded id at all). The row states the `versionNo` the file row stores and nothing more — this is the same fact DEC-669 relies on when it keeps headshots out of the deliverable chain query.

The bare Download beside the avatar is DELETED rather than left as a second door: the Files row carries the same link with the three facts the bare link never had, and `chq-speaker-detail-headshot-download` goes out of the tree and out of docs/design/audit/phone-tap-floor-links.md's population with it. The portrait stays a portrait.

### A note the wire-field ledger used to hold

`ContactDetail.headshotFile` (GET /contacts/:id, src/routes/api/contacts/crud.ts) has had no SPA reader since G13 A20 removed the drawer's 238px HEADSHOT row, and test/wire-field-reader.scan.test.ts carried a ledger row saying so: the field stays on the wire because DEC-894 is a standing decision about that endpoint's PAYLOAD while A20 is a ruling about what the drawer DRAWS, and a design ruling does not by itself repeal an API contract. That row is deleted here, not because the reasoning changed but because the scan can no longer measure it: `hasReader` matches field names across all of app/src, and SpeakerDetailPage.tsx now reads a `headshotFile` of its own. The reasoning is recorded here so deleting the row loses nothing.

## Amendment (wave 118): the speaker-detail reminder captions are derived, from the ONE email_log reader the task view already owns

The v12 speakers redesign is named in the campaign goal as needing to be frame-complete, and `docs/design/Chautauqua Speakers.dc.html:804-809` draws the speaker-detail Tasks rows with a remind ordinal (`Remind · never sent` / `Remind · sent once` / `Remind · 3rd time`) and a due caption that carries tense (`Was due 1 Apr` vs `Due 10 Apr`). The app renders `Remind · last 4 Aug` and a bare date, and `SpeakerDetailPage.tsx:526-531` justifies dropping the header's drawn `Reminded 3× · last 4 Aug` with "the × count is not derivable (see taskRemindLabel)". That premise is FALSE in this tree: `src/server/repo/tasks/task-view.ts`'s `countRemindSends` derives exactly this count out of `email_log`, correlated per (task, contact) and bounded by the assignment's own created/completed window, matching on the shared `REMINDER_SUBJECT_PREFIX` — one grouped query, no schema change. A comment that books a frame divergence as impossible while the neighbouring module does the thing is the "caption the code contradicts" pattern. RULED: the count is derived for the speaker-detail surface from that SAME reader lifted to a shared home (DEC-613 — one vocabulary, never a second copy in speaker-detail.ts), the rows and the header render the frame's copy verbatim, and the false comment is deleted rather than re-worded. The due caption takes its tense from the date against now, not from status, exactly as the frame's own rows do (a complete task with a future date reads "Due 25 Apr"). DEVIATIONS §6 defers the speaker-detail header RESTRUCTURE (04/07 frames); it does not defer a caption the Speakers frame draws and the page already renders.
