## Amendment (wave 47): a wall-clock sleep is not a synchronization primitive, and a config comment's timing premise is a measurement that decays

test/reminders-portal-link-batched.test.ts:218 waits `await new Promise((r) => setTimeout(r, 50))` and then asserts `issued.length === N` — the claim being proved is an ORDERING one (all N claim-token puts are issued before any resolves, which a sequential loop could never do), but the instrument that decides it is a fixed 50ms budget for twelve real crypto.subtle mints. It passes in 64ms standalone and fails at 127ms inside the 1417-file tier: the assertion measures host load, not the code under test. It is the only one of the five load-flaky fast-tier files that is not a timeout, and its neighbours in the round-trip-depth family use setTimeout legitimately (fake IO latency, not synchronization), so a blanket scan would over-fire. RULED: (a) the sleep becomes a bounded condition wait on `issued.length === N` that reports the observed count on failure — the ordering claim survives intact, because a sequential implementation can never reach a second issued put while the first is blocked, so it still times out and still fails; (b) vitest.fast.config.ts's comment stops asserting "stay well under 60s" and records the measured tier size and duration WITH the sha they were taken at, because an undated timing claim is the shape that made an unbounded worker count look safe for six waves.
