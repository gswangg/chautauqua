# DEC-027: Bearer API tokens: chq_ prefix + sha256 lookup in sessionLoader, CSRF-exempt, cookie-only minting; export endpoints per entity

## Amendment (wave 20): A claim-token mint is a credential mint — the four organizer routes that mint 30-day portal claim links gain `requireCookieSession`, and the scan's primitive list learns the mint's name

DEC-027's wave-38 amendment closes bearer-token privilege escalation by placing `requireCookieSession` immediately after the role guard on every credential-bearing route, precisely because `csrfJson` deliberately exempts bearer clients (src/server/middleware.ts:267-285), so a missing session check there is a full escalation rather than a CSRF gap. A `/claim/<token>` link IS a credential — possession of it is the entire authentication, as this codebase already states in its own UNAUTHENTICATED_DOORS justification for src/routes/auth-claim.tsx ('the auth is possession of an unguessable KV claim token, not a session'). Four organizer routes mint one with only `requireOrganizer, csrfJson`: src/routes/comms/portal-invites.ts:26, src/routes/comms/send.ts:37, src/routes/api/contacts/bulk-email.ts:167 and src/routes/content-notes.ts:53. Combined with the equally unguarded `PATCH /api/v1/contacts/:id` email write, a bearer token can repoint a speaker's address and have a working login mailed to it. Both scans miss all four because their populations are literal-matched on names no mint site actually uses — `test/credential-route-cookie-session.scan.test.ts`'s CAPABILITY_MARKERS reads only the route's REGISTRATION text (an indirect mint deeper in the handler is invisible to it) and CREDENTIAL_PRIMITIVES lists only password/session literals. RULED: the mint gets a NAME so the literal can be true (`mintPortalLinks`, a thin named export over the existing `resolvePortalLinks(..., true)` path — one implementation, never a copy), the four routes gain the guard, and CREDENTIAL_PRIMITIVES gains `mintPortalLinks(`, `createClaimToken(` and `applyMintedPortalLinks(`. src/routes/public/submit-post.tsx:512 then joins the population and is EXEMPT as a fourth UNAUTHENTICATED_DOOR with its justification written into the record as that list requires: it is the public CFP submit door, running with no `c.var.auth` at all, minting the submitter's own claim on their own just-created submission — the same no-session model the three existing doors carry.

## Amendment (wave 10): The claim-token mint guard's population is DERIVED from the tree, and POST /events/:eventId/onboarding/remind is the one route that never got it

src/server/middleware.ts's DEC-027 wave-18 comment claims requireCookieSession sits on "every route that reaches createClaimToken" and then hand-lists four files: comms/portal-invites.ts, content-notes.ts, comms/send.ts, api/contacts/bulk-email.ts. Verified against the tree: src/routes/tasks.ts's `taskRoutes.post("/events/:eventId/onboarding/remind", requireOrganizer, csrfJson, ...)` carries only the role guard, and it reaches remindNow -> sendReminderEmails(..., mintClaimTokens=true) -> resolvePortalLinks(..., true) -> createClaimToken. Because csrfJson short-circuits on auth.viaBearer, a bearer API token can mint and MAIL fresh /claim/<token> interactive-login credentials — the exact escalation the comment says is closed. RULED: (a) the guard goes on that route, immediately after requireOrganizer, per the assembler contract; (b) the preview twin stays unguarded — previewRemindNow resolves with mintClaimTokens:false and mints nothing; (c) the hand-list is retired. A HAND-LISTED POPULATION IS NOT A POPULATION (DEC-180): the enumeration becomes a test that walks src/routes/** for modules transitively reaching a mint and asserts the guard, with src/routes/public/submit-post.tsx excluded on a stated principle (an unauthenticated public route has no session to require), never an allowlist entry.
