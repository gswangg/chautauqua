# DEC-909: A form field states its own optionality and its own budget — one renderer, one grammar, no asterisks

## Amendment (wave 111): the live character counter is a LONG-TEXT affordance; maxlength is validation, the counter is presentation

The counter was gated on `field.kind === "text" || field.kind === "long_text"`, so a one-line Title, a name, a company all rendered `12 / 200` beside their label. The pack draws exactly THREE counters in its entire 158-frame extent, and all three are the same string on the same field: `412 / 1,200` on Abstract, at `docs/design/Chautauqua Public and Portal.dc.html:614` (Portal · Edit your session · 390), `:1037` (CFP 390) and `:1399` (Portal edit · desktop). No frame puts a counter on a short text field, a date or an email. Ruling: the counter renders for `long_text` only — landed, and `src/views/form-render.tsx:169` now reads `field.kind === "long_text" ? resolvedTextCap(field) : undefined`. `resolvedTextCap`'s `maxlength` stays on both kinds — that is the validation contract and it is untouched; this is the grammar half of DEC-909, and DEC-909's own words already say "a long-text field with a maximum carries a live counter". The inline sync script keeps its single code path.

## Amendment (wave 128): a roster add is a contact act: the session title is optional, and a typed title that matches an existing session references it

`RosterPanel.tsx` puts `sessionTitle` in `FIELD_ORDER` and marks it required, and the POST comment at :175 records the current rule (DEC-810: the server never invents a session title; adding to an event requires naming the session here). The cost of that rule: an organiser adding a known speaker must invent a session, and 'Add <name> to this event' minting a brand-new session from the typed title even when an identical one exists is the same defect downstream. RULED, two clauses landing together. (a) The session title is OPTIONAL on a roster add — the roster is every participant of an accepted submission with ACTIVE as the predicate (DEC-829), and adding a person to an event is a participation fact, not a scheduling one; the field states its own optionality through the one renderer DEC-909 mandates, no asterisk, no second grammar. (b) When a title IS typed, an exact match against this event's existing sessions REFERENCES that session; only an unmatched title mints a new one — a title that already exists is a reference the organiser is making, not a coincidence, and minting a duplicate silently is the write-side twin of the disclosure defect DEC-936 rules on this same wave. The 'never invents a session title' half of the old rule is preserved by both clauses; the server still never invents one, and now also never duplicates one.
