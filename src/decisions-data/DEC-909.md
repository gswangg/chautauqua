# DEC-909: A form field states its own optionality and its own budget — one renderer, one grammar, no asterisks

## Amendment (wave 111): the live character counter is a LONG-TEXT affordance; maxlength is validation, the counter is presentation

The counter was gated on `field.kind === "text" || field.kind === "long_text"`, so a one-line Title, a name, a company all rendered `12 / 200` beside their label. The pack draws exactly THREE counters in its entire 158-frame extent, and all three are the same string on the same field: `412 / 1,200` on Abstract, at `docs/design/Chautauqua Public and Portal.dc.html:614` (Portal · Edit your session · 390), `:1037` (CFP 390) and `:1399` (Portal edit · desktop). No frame puts a counter on a short text field, a date or an email. Ruling: the counter renders for `long_text` only — landed, and `src/views/form-render.tsx`field.kind === "long_text" ? resolvedTextCap(field) : undefined` (line number has since shifted; the expression is unchanged). `resolvedTextCap`'s `maxlength` stays on both kinds — that is the validation contract and it is untouched; this is the grammar half of DEC-909, and DEC-909's own words already say "a long-text field with a maximum carries a live counter". The inline sync script keeps its single code path.

## Amendment (wave 128): a roster add is a contact act: the session title is optional, and a typed title that matches an existing session references it

`RosterPanel.tsx` puts `sessionTitle` in `FIELD_ORDER` and marks it required, and the POST comment at :175 records the current rule (DEC-810: the server never invents a session title; adding to an event requires naming the session here). The cost of that rule: an organiser adding a known speaker must invent a session, and 'Add <name> to this event' minting a brand-new session from the typed title even when an identical one exists is the same defect downstream. RULED, two clauses landing together. (a) The session title is OPTIONAL on a roster add — the roster is every participant of an accepted submission with ACTIVE as the predicate (DEC-829), and adding a person to an event is a participation fact, not a scheduling one; the field states its own optionality through the one renderer DEC-909 mandates, no asterisk, no second grammar. (b) When a title IS typed, an exact match against this event's existing sessions REFERENCES that session; only an unmatched title mints a new one — a title that already exists is a reference the organiser is making, not a coincidence, and minting a duplicate silently is the write-side twin of the disclosure defect DEC-936 rules on this same wave. The 'never invents a session title' half of the old rule is preserved by both clauses; the server still never invents one, and now also never duplicates one.

## Amendment (wave 134): a field-builder row's grammar includes its hint, not just its label and its optionality

DEC-909's "one renderer, one grammar" covers required/optional marking, but the field-builder's own Label row was silently missing the hint register `FormRow` already exposes (`help`). `FieldModal.tsx`'s Label `FormRow` now carries `help="What the submitter reads"` (`docs/design/Chautauqua Submissions.dc.html:681`), matching the register every other row in the modal uses rather than inventing a second hint mechanism. The Help-text row's own placeholder is corrected to the frame's example (`Beginner, intermediate or advanced`, `:685`) — the prior placeholder (`Shown beneath the field, e.g. 300 words max`) described the field's PURPOSE where the frame's is an EXAMPLE VALUE; the label already carries "Help text · optional" via the `optional` prop, so the purpose is not lost. Neither change touches `resolvedTextCap`, `maxlength`, or the long-text counter grammar from the wave-111 amendment.

## Amendment (wave 18): clauses (a) and (b) bind EVERY door that adds a contact to an event, and a wire field error the form cannot render is surfaced at the top of the form, never dropped

DEC-909's wave-128 amendment ruled the session title OPTIONAL on a roster add (clause a) and ruled that a typed title exactly matching an existing session REFERENCES it rather than minting a duplicate (clause b) — and named the second door explicitly: "'Add <name> to this event' minting a brand-new session from the typed title even when an identical one exists is the same defect downstream." Both clauses landed on `POST /contacts` only. `src/routes/api/contacts/crud.ts`'s `POST /contacts/:id/add-to-event` still calls `repo.pushContactToEvent`, bypassing `findSubmissionByExactTitle` entirely, and still 400s a blank `title` with `{title:"required"}` — while `app/src/pages/contacts/DuplicateEmailNotice.tsx` forwards RosterPanel's now-optional `sessionTitle` straight into it, so the duplicate-email recovery button fails on a field the form labels optional and names no field the organiser can fix. A ruling applied to one of two doors is not applied. Separately, `app/src/pages/speakers/RosterPanel.tsx` routes every non-empty `err.fields` into `setFieldErrors`, whose `FIELD_ORDER` covers seven keys; `src/server/repo/participants.ts`'s participant-cap refusal throws `ApiError('invalid', …, { submissionId })`, a key no `FormRow` renders, so the organiser sees nothing at all after the contact has already been created — a silent partial write, the exact failure mode the fail-loudly principle forbids. RULED, three clauses. (a) EVERY DOOR: clauses (a) and (b) of the wave-128 amendment are properties of adding a contact to an event, not of one route; every such door resolves an exact title match before minting and accepts a blank title. (b) ONE PREDICATE: the doors share `attachOrCreateRosterSession`, never a second copy of the match-then-mint logic (DEC-613/DEC-180). (c) NOTHING SWALLOWED: a form partitions a refusal's `fields` into keys it renders and keys it does not; unrenderable keys are surfaced through the form's existing top-of-form error line with their messages intact — never a bare count, never discarded because no anchor exists for them.

## Amendment (wave 22): The wave-18 amendment's three clauses are built on BOTH sides of the wire, including the client-side title requirement the modal still enforces

DEC-909's wave-18 amendment already RULED three clauses — (a) EVERY DOOR, (b) ONE PREDICATE, (c) NOTHING SWALLOWED — and none of them is built on main `27e4ae3b1`: src/routes/api/contacts/crud.ts still calls repo.pushContactToEvent (bypassing findSubmissionByExactTitle) and still 400s a blank title with {title:"required"}, while repo.attachOrCreateRosterSession has existed and been exported through src/server/repo/contacts.ts the whole time. A ruling is not a receipt of build. This amendment adds the half the wave-18 text left implicit and which is the reason the recovery path is a dead end in practice: the CLIENT doors must stop enforcing what the server no longer requires. AddToEventModal.tsx refuses an empty title locally ('Enter a session title.') before any request leaves the browser, so fixing only the route would leave one of the two doors still unreachable; RosterPanel.tsx's FIELD_ORDER-filtered errorSummaryProblems silently discards any wire key it has no FormRow for (the participant-cap refusal's `submissionId`), which is clause (c)'s exact subject. RULED: the client halves land with the server half in one lane — AddToEventModal drops its local title requirement and labels the field optional through the ONE FormRow renderer DEC-909 mandates (no asterisk, no second grammar), and RosterPanel partitions err.fields into rendered keys and unrenderable keys, routing the latter into its existing top-of-form error line with their messages intact.
