# DEC-929: Deleting an evaluation plan freezes server-side once any evaluation exists, through the same predicate the criteria freeze uses

DESIGN-RULINGS ruling A9 is explicit: 'Delete plan: RESTYLE, one line: a tertiary link in the plan editor footer, disabled once any review has landed (same freeze rule as criteria), with the same "Start a new wave" alternative.' Verified on main: the freeze exists ONLY in the SPA (`app/src/pages/review/PlanEditor.tsx`), while `src/routes/review/plans-crud.ts`'s `DELETE /api/v1/plans/:id` calls `repo.deletePlan` with no guard, and `deletePlan` unconditionally deletes every `evaluation` row for the plan. A bearer-token organizer is CSRF-exempt, so the SPA's disabled attribute is the only thing standing between a direct call and a destroyed wave of submitted reviews — the precise outcome the criteria/scale freeze twenty lines above (DEC-123, `plans-crud.ts:180`) was written to prevent. The house invariant is authz and visibility on every route, server-side; a rule that lives only in a disabled button is not a rule. The predicate must be `repo.planHasEvaluations` — the SAME one the criteria guard calls — never a second count query, because two predicates for one freeze is DEC-613's two-vocabularies trap and would let the button and the route disagree about what 'a review has landed' means. The refusal is a 409 whose message names the alternative the ruling names, so the organiser is not left at a dead end. The read-only `delete-preview` endpoint is untouched: naming a blast radius is not performing it.

## Amendment (wave 131)

Closed server-side: `DELETE /api/v1/plans/:id` in `src/routes/review/plans-crud.ts` now calls `repo.planHasEvaluations` (the identical predicate the DEC-123 criteria guard above it calls, never a second count query) before `repo.deletePlan`, and refuses with a 409 naming ruling A9's own alternative -- start a new wave (`POST /api/v1/plans/:id/waves`, DEC-709) -- rather than deleting. `app/src/pages/review/PlanEditor.tsx`'s disabled affordance is untouched; it remains the UI hint, and this amendment is the enforcement it was hinting at. `GET /api/v1/plans/:id/delete-preview` is unchanged.

## Amendment (wave 34): DESIGN-RULINGS A9's delete freeze is keyed on a LANDED review, never on a draft row — and a refusal may not name a door that does not exist

DESIGN-RULINGS.md's Review item 9 rules Delete plan "disabled once **any review has landed**". src/routes/review/plans-crud.ts's DELETE guards on repo.planHasEvaluations, which has no submittedAt filter — while its sibling countSubmittedEvaluationsForPlan in the same file explicitly excludes drafts for the identical "evaluations exist" question. Consequence verified against the tree: one reviewer pressing Save draft permanently bricks the plan — criteria/scale PATCH 409s, DELETE 409s ("start a new wave instead"), and POST /plans/:id/waves 400s ("no submitted evaluations yet ... edit this plan's criteria in place"), two of the three refusals pointing at each other. The criteria refusal's only named escape, "delete the evaluations first", has no endpoint anywhere: the only delete(schema.evaluation) call sites are deletePlan's own cascade and submission-delete. RULED: (a) the DELETE freeze keys on submitted evaluations — a plan holding only unsubmitted drafts stays deletable and its cascade removes them; (b) DEC-123's criteria/scale freeze KEEPS planHasEvaluations, because a draft already holds scores against the criteria shape and a shape change would orphan it; (c) refusal copy names only exits that exist. No evaluation-delete endpoint is added — a door invented to satisfy a sentence is worse than the sentence.
