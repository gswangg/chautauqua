# DEC-660: `POST /api/v1/submissions/:id/files` gets the per-submission cap every sibling mint door already has

Every sibling minting door in the tree carries a named cap enforced pre-write (`MAX_API_TOKENS_PER_ORG`, `MAX_SAVED_VIEWS_PER_EVENT`, `MAX_PARTICIPANTS_PER_SUBMISSION`, `MAX_PLAN_CRITERIA`, and `MAX_EMAIL_TEMPLATES_PER_EVENT` — the wave-25 repair this census's own ratchet comment records). `src/routes/files.ts:167` enforces per-file type and size but no count, while its own reader src/server/repo/files-versions-read.ts`if (rows.length > MAX_SUBMISSION_FILE_SCAN)` throws `ApiError('invalid')` past `MAX_SUBMISSION_FILE_SCAN = 1000` — so an active-participant speaker can permanently 400 `GET /api/v1/submissions/:id/files` and every Content view built on it, with only a one-at-a-time delete door to recover. A writer with no cap feeding a reader with a hard cap is a self-inflicted denial door. Ruling: a named `MAX_FILE_VERSIONS_PER_SUBMISSION` constant lives beside the other upload constants, is strictly below `MAX_SUBMISSION_FILE_SCAN`, and is enforced pre-write with an `ApiError('invalid')` naming the cap. The reader's own limit is left alone — one authority, and the writer is the side that must yield.
