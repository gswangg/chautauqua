# DEC-265: Participant API responses carry the contact's name and email server-side: an optimistically appended row must render identically to a reloaded one

## Amendment (wave 110): an optimistic rollback reverts the one write that failed, never the snapshot it started from

app/src/pages/speakers/OnboardingGrid.tsx captures `previous` (the whole grid) before a cell flip and, on failure, calls `setGrid(previous)`. A slow failure therefore silently un-does every concurrent write that succeeded in the meantime, or replays a previous page/filter's rows over the current view -- while the banner names only the one row that failed. That is precisely the state DESIGN-RULINGS.md:283 error rule 11 forbids: the user is told what broke and not told what was reverted underneath them. RULED: rollback is a functional update that restores ONLY the failed assignment's cell (or the failed participant's inviteStatus) from the value captured before that flip. Concurrent successes and a page/filter change survive it. The banner's claim about what survived becomes true by construction rather than by luck of timing.

## Amendment (wave 126): an optimistic overlay is released by SERVER TRUTH, never by the write's own resolution — and never left standing after it

Two mirror defects, both live and both on the landed v12 work. (a) SubmissionsTable.tsx deleted the `statusOverrides` entry the instant `apiPost` resolved, while `submissions.data` still held the pre-write payload (the SWR refetch is asynchronous and DEC-700 wave-121 deliberately leaves `data` untouched on a bump) — so every SUCCESSFUL triage or bulk accept visibly reverted to the old status for one round trip, indistinguishable from a failed write and exactly the "turns a rollback into a flicker" state the rulings forbid; the release is now keyed on server truth instead (SubmissionsTable.tsx`standing on success -- the reconciliation effect above releases each`). (b) `OnboardingGrid.tsx`'s `applyCellStatus` (:598) and `applyInviteStatus` (:696) never clear `optimisticOverride` on success, and `grid = optimisticOverride ?? gridRead.data` (:382), so after the first cell toggle the whole roster is pinned to a pre-write snapshot: the server-computed column-head aggregate ("7 of 12 done", declared EVENT-WIDE and never counted from rows) and the counts panel silently stop updating — a Tier-0 fidelity break on the v12 speakers redesign. Every other write handler in that file already does `setOptimisticOverride(null); await gridRead.refetch()`. Release on server truth, not on the promise resolving.

## Amendment (wave 138): an optimistic override is cleared by the write that SUCCEEDS, not only by the write that fails

`app/src/pages/speakers/OnboardingGrid.tsx` renders `grid = optimisticOverride ?? gridRead.data` (:425), and `optimisticOverride` is cleared on a `gridPath` change (:423) and by six other writes (:696, :835, :864, :882, :902, :917). `applyCellStatus`'s success path (the `await apiPatch` at ~:640, then `setPendingFailure(...)`) never clears it, and `applyInviteStatus` (:721) has the identical omission. After one cell toggle the override — a client-side snapshot with the cell flipped and every OTHER field frozen at its pre-write value — permanently masks the post-mutation refetch. The visible consequence is squarely a Tier-0 speakers-redesign fidelity row from the mandate: the B8-ruled column head `taskDoneLabel` ('7 of 12 done' / 'All N done', :80-87) reads `task.assigned`/`task.complete` from the frozen snapshot, so the aggregate the v12 frame draws stops moving after the first toggle, as does the counts panel, until the organiser changes filters or reloads. RULED: an optimistic override is a bridge across ONE in-flight request; the request's resolution ends it in both directions. The success path clears the override so the refetch becomes visible; the failure path keeps its existing per-cell rewrite (a whole-grid snapshot would clobber concurrent successes) and then clears once the rewrite is reconciled. Pinned by a test that toggles a cell, resolves the PATCH, serves a refetch whose column aggregate differs, and asserts the rendered column head shows the SERVER's number.

## Amendment (wave 25): an optimistic override is retired per-write, never wholesale -- the success path owes the same per-cell discipline the failure path already keeps

DEC-265's wave-110 amendment ruled that a rollback rewrites only the failed assignment's cell because 'a whole-grid snapshot would clobber every concurrent success'. app/src/pages/speakers/OnboardingGrid.tsx honours that on failure and violates it on success: after `await gridRead.refetch()` it calls `setOptimisticOverride(null)`, discarding every OTHER in-flight cell's optimistic flip. Because `grid = optimisticOverride ?? gridRead.data`, a second cell toggled while the first PATCH is in flight visibly snaps back to its pre-click status until its own PATCH resolves; and the failure branch's `current ? ... : current` guard then silently no-ops, since a concurrent success has already nulled `current`. The surrounding comment claims the wave-110 guarantee is 'preserved verbatim' -- it is preserved in one branch of two. RULED: the write that succeeds retires only its own cell from the override (writing the refetched server value), and the override drops to null only when nothing in it still differs from the refetched data. Tier 0 applies: this is the landed v12 speakers redesign, audited before anything is built on top of it.
