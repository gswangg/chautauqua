# DEC-367: An exemption is a grammar, not a punctuation mark — repair `topLevelRulesWithExemption`'s exempt flag and re-seed the ceiling it blinded

app/src/phone-tap-target-scan/core.ts`m[0].trimStart().startsWith('/*')` set the `exempt` flag from the match prefix alone (the file's own header now names it as the predicate this ruling replaced). The optional exemption group `(?:\/\*\s*tap-floor-exempt:[^*]*\*\/\s*)?` is allowed to NOT match, after which the selector group `([^{}]+)` happily swallows any brace-free block comment — so `m[0]` still starts with `/*` and the rule is marked exempt. I proved it on a clean archive: `/* just a normal design comment */\n.chq-x { padding: 0; }` returns `exempt: true`. In a tree where nearly every rule carries a frame-citation comment this exempts a large fraction of the 44px population from FOUR ratchets at once (base tap-target scan, undeclared-height lens, SSR scan, anchor-floor). Measured on a clean archive of main with the one-line repair `const exempt = /\/\*\s*tap-floor-exempt:/.test(m[0] ?? '')`: `UNDECLARED_HEIGHT_OFFENDERS_CEILING` goes 15 -> 28 live offenders, and the base scan's `every sub-44px control has a >=44px phone override or a named exemption` assertion goes from GREEN to 2 offenders. Three of the four 44px defects an independent lens measured live at 390 (`.chq-review-editor-title-input` ~36px, `.chq-speakers-phone-roster-link` 58x21, `.chq-check` 18x18) were invisible for exactly this reason. RULED: an exemption is recognised only by its literal grammar `/* tap-floor-exempt: <reason> */` immediately above the rule; the repair lands with a positive control (an ordinary comment does NOT exempt), a negative control (a real exemption DOES, and does not leak onto the NEXT rule), and both controls live in a new file so they do not contend with the drain lanes. Because this is a PREDICATE REPAIR and not a regression (DEC-989 clause c), `UNDECLARED_HEIGHT_OFFENDERS_CEILING` is RE-SEEDED upward to the value measured under the repaired predicate, in the repairing commit, with a header that names the blind line it replaces.

## Amendment (wave 138): a fixed `width` below the floor is the THIRD evasion mode of the 44px ruling — horizontal padding cannot reach the floor while an explicit width survives

DESIGN-RULINGS:189 names two evasion modes (a shared token that cannot satisfy a dense grid and a 390 card at once; a hardcoded sub-44 `min-height` on a phone token) and states the width mechanism as 'plus horizontal padding — without padding the hit box is only as wide as the text'. `button.chq-pub-search-submit[type=submit]` declares `width:40px; height:40px` at `src/routes/public/css/chrome.css.ts:155`, and its phone override adds `min-height:44px; display:inline-flex; align-items:center; justify-content:center; padding: 0 8px` — every clause the ruling names, and the control still measures 40px wide, because the base `width:40px` survives and border-box makes the padding inert. Every scan in the campaign grades the HEIGHT dimension only, so this reads floored to all of them. The mirror case is `.chq-portal-footer-profile` (declared with `src/routes/portal/portal.css.ts`padding-inline: 8px;` at the time of filing, before the `min-width:44px` repair landed alongside it), which took that floor and no padding at all and measured 39px wide. Both were filed by independent reviewers and both are live. RULED: a phone override that floors a control which declares an explicit sub-floor `width` must also reset it (`width:auto; min-width:44px`), and a phone override on a shrink-wrapped inline-flex anchor must declare non-zero horizontal padding — the padding clause of the ruling is a requirement, not a suggestion. The live population of the width shape is exactly one rule today, so it is pinned by a targeted receipt rather than a new ratchet; a second sighting promotes it to a scan.

## Amendment (wave 151): the live 390 pass's control population is DERIVED from interactivity, never a selector hand-list

scripts/render-sweep.ts is the only gate in this repo that measures REAL rendered geometry in a real browser at 390x844, and its admin pass is blocking (ADMIN_MOBILE_PASS_BLOCKING = true). It grades exactly six selectors: `.chq-tabbar a`, `.chq-tabbar button`, `.chq-btn`, `.chq-input`, `.chq-select`, `header nav a`. Everything else on every admin page at 390 is invisible to it. That is why a `.chq-participation-menu-trigger` can render at 95x19px — a clickable dropdown less than half the ruled floor — on a live admin page while ANCHOR_FLOOR_OFFENDERS_CEILING, SSR_TAP_FLOOR_OFFENDERS_CEILING, SSR_UNFLOORED_TOKENS_CEILING and UNDECLARED_HEIGHT_OFFENDERS_CEILING all read 0. The static scans are token-keyed and can only reach what a CSS token declares; the live gate is the one instrument that could catch what a token never declared, and it was pointed at a named handful. A HAND-LISTED POPULATION IS NOT A POPULATION (DEC-180/DEC-808) applies with full force to a selector list. RULED: the admin 390 pass grades every element the DOM itself calls interactive — a[href], button, input (excluding type=hidden), select, textarea, summary, the interactive ARIA roles, and any element with a non-negative tabindex — keeping the existing offsetParent visibility filter. Because this widens the population, the pass seeds a NAMED two-sided ratchet for its offender count in the same commit rather than flipping the gate red on landing: a widening re-seeds where it widens, which is a repair and not a raise (DEC-976 wave-138, DEC-393 wave-139's own precedent). Every exemption names a property of the ELEMENT that makes it correct — the `inline-in-prose` disposition DEC-393 wave-142 already defines — never a schedule note.

## Amendment (wave-16 r5): a control's REST ink is never a state token, and a token substitution that is not byte-equal may not be written as an exact resolution

Two failures of one comment block on the Contacts 390 rule chip. (1) `.chq-contacts-filter-rule-chip` rests at `var(--chq-brand-hover)` and its only text child, `.chq-contacts-filter-rule-chip-edit`, takes `color: inherit` — so the B8 hover state landed for that label (`--chq-brand-hover`) resolves to the value it already had, and hovering the chip's label changes nothing but an underline. app/src/interaction-states.scan.test.ts scans transition properties, easing and reduced-motion; it never compares a state's VALUE against the value it inherits, so a whole B8 leg was dead in a rule that passes every guard. (2) The same rule's receipt books `#EFF1E4 -> --chq-surface-sunk` and `#2E3A16 -> --chq-brand-hover` beside two claims that really are exact (`#4E5C31 -> --chq-brand`, `radius 4px -> --chq-r-ctl`), and the sibling dismiss rule books `#5E6B47 -> --chq-muted` the same way; `--chq-surface-sunk` is #EFEBDF, `--chq-brand-hover` is #3C471F and `--chq-muted` is #565A4B — none of the three is the frame's value. app/src/palette.scan.test.ts strips block comments before it looks for hex literals, so it is blind to a receipt that overstates its own fidelity. RULED, two parts. (a) A control's rest ink resolves to a REST token; the chip's frame ink #2E3A16 takes `var(--chq-brand)` (#4E5C31, exactly the border the frame draws on the same chip), which restores a strictly monotone ladder rest -> `--chq-brand-hover` -> `--chq-brand-active`. Rejected: minting a third olive (DEC-383/palette closure forbids the literal), and spending `--chq-brand-active` at rest, which just moves the no-op from the hover leg to the active leg. (b) A `#HEX -> --token` receipt says `exactly` only when the two are byte-equal; otherwise it states the residual in the same breath, the way this same block's micro-caption comment already does when it records that the trio's tracking is 0.11em against the frame's 0.12em. The optical residual — the app draws the chip's label and its border in one olive where the frame draws the label a step darker — is recorded in DEVIATIONS §3 rather than left as a silent divergence.
