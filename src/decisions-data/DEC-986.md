# DEC-986: The phone CFP wizard validates before it advances, and conditional visibility un-requires every control in a group

Two independent defects made the phone CFP silently unsubmittable, on the product's primary public conversion path. (1) cfp.css.ts:272 hides `.chq-cfp-step-talk` with display:none on step 2 while its controls keep `required`; cfp-steps-script.tsx's Next handler ran no validation (type=button by design) and "Submit this talk" carried no formnovalidate, so a speaker who advances with an empty required talk field taps Submit and the browser aborts on a non-focusable invalid control — no message, no server hit, no recovery. (2) form-render.tsx's visibility script called a SINGULAR `wrap.querySelector` to un-require a hidden field, but Format and Audience render as N radios each carrying `required` and the same data-field-id, so radios 2..N stayed required inside a display:none wrap — the same dead end by a different route.

RULING, LANDED ON MAIN in wave 109 — receipts: src/routes/public/cfp-steps-script.tsx:77 `if (!control.checkValidity()) return control;` guards the advance, :87 `invalid.reportValidity()` raises the browser's own bubble on the first invalid step-1 control, :91 `setStep('2')` runs only when nothing is invalid, and src/views/form-render.tsx:283 `wrap.querySelectorAll` un-requires every control sharing the hidden field's id. Executable pins: test/cfp-phone-steps.test.ts drives the emitted script in a real jsdom document (empty step 1 → stays on step 1 and fires `invalid` at the first control; complete step 1 → advances), and test/form-render-rules.test.ts asserts all N radios of a hidden group lose `required`. (This paragraph previously read "not yet landed": DEC-976's wave-106 amendment had corrected it from a false "Fixed" narrative, and the implementation it pointed at lived only on the in-flight branches v12m-w10-h and v12m-w11-a, which never merged.) The ruling as written: (1) must be closed by calling reportValidity() on the step-1 section in the Next handler and refusing to advance when it fails — that converts a silent dead end into the browser's ordinary validation stop and leaves step 2's Submit safe because step 1 was already validated; (2) must be closed with querySelectorAll + forEach in place of the singular querySelector. Neither is a frame change; both are what the frame's two-step flow means.

## Amendment (wave 93): a control that is display:none must not be constraint-validatable

Verified on main 32d33500 (line since drifted to :272 as of 114b4d2c; DEC-976 wave-106 amendment corrected the citation, the ruling itself is unchanged): cfp.css.ts:272 `[data-chq-cfp-step="2"] .chq-cfp-step-talk { display: none; }` hides step 1 while its controls keep `required` (Track radios carry `required` on all N, submit-views.tsx:202-204, inside the .chq-cfp-step-talk section at :587); submit-views.tsx:658's "Submit this talk" has no `formnovalidate` (only Save draft at :665 does); cfp-steps-script.tsx's Next handler calls setStep('2') with no validation. The browser therefore aborts submission on a non-focusable invalid control with no message, no focus and no server hit — a silent dead end on the primary public conversion path. jsdom never runs constraint validation, so the entire suite is structurally blind to this class. RULING: (1) a step transition must un-require every control it is about to hide and restore the original `required` when the step is shown again — the toggle is part of hiding, not a separate concern; (2) "Next" must run checkValidity() over the outgoing step's controls and reportValidity() on the first invalid one BEFORE advancing, so the message lands on a visible field; (3) the guard is authored in the step script, not by adding `formnovalidate` to the real Submit — suppressing validation on the primary action would let an empty required talk field reach the server. Find defects of this class by reading which elements can be display:none while required, never by adding a test.
