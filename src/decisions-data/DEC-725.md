# DEC-725: removeParticipantRow stamps its submission before the delete — the one participant writer that skipped the touch-on-write contract

src/server/repo/submissions/touch.ts states its contract in its own header: touchSubmissions must be called BEFORE (or as part of the same logical operation as) any delete of a row the stamp represents, precisely because an EXISTS-over-dependents predicate cannot see a DELETE. Verified: participants.ts calls touchSubmissions at five write sites (:135, :266, :287, :335, :376) and removeParticipantRow (:435) calls it at none; its only caller, src/routes/api/submissions.ts's participant DELETE, does not either. Consequence: removing a co-presenter leaves the removed name live in the customer's Airtable Speakers cell indefinitely (src/sync/airtable.ts's gt(submission.updatedAt, lookbackMark) never re-selects it) and never resurfaces the session on repo/overview.ts's desc(submission.updatedAt) worklist — the same defect class DEC-981 closed for declines. RULED: the touch lands inside removeParticipantRow (not the route) so every future caller inherits it, and A SILENT FALLBACK HAS SIBLINGS IN OTHER FILES (DEC-843) is answered with a derived scan over participants.ts rather than a fixed row, reading the one legitimate exemption from its own in-code comment instead of an allowlist.

## Amendment (wave 17): the sessionboard `participants` entity import is the last participant writer that skips the touch-on-write contract

DEC-725 closed `removeParticipantRow` (it now calls `touchSubmissions` before the delete) and DEC-981 closed the decline path, but `src/server/repo/import/sessionboard.ts`'s `participants` branch still inserts rows (chunked flush) and updates them (`flushParticipantUpdates`) without ever stamping the owning submissions: the file imports only `touchSubmissionsForContacts`/`touchSubmissionsForTracks`, and neither reaches a submission whose participant SET changed. `src/server/repo/submissions/touch.ts` states the contract's reason plainly — an EXISTS-over-dependents predicate cannot see a dependent write, so the watermark must be stamped by the writer. The consequence is the one the contract predicts: `src/sync/airtable.ts`'s `gt(submission.updatedAt, lookbackMark)` never re-selects the submission, so a bulk-imported co-presenter never reaches the customer's Airtable `Speakers` cell, and `repo/overview.ts`'s `desc(submission.updatedAt)` worklist never resurfaces the session. RULED: every participant writer stamps, including the import path; the population is the set of statements that INSERT, UPDATE or DELETE `schema.participant`, derived by grepping that table name, never a hand-listed set of functions (DEC-180).

## Amendment (wave 22): An exemption is only as good as its PREMISE: insertActiveParticipants' 'one caller' claim is false, so the exemption is deleted rather than re-argued

src/server/repo/participants.ts's touch-on-write exemption comment reads 'this function's one caller (pushContactsToEvent) always calls it in the same request that just createSubmission'd submissionId — that INSERT already stamped updatedAt to `now` moments earlier, so there is no stale stamp to correct here.' src/server/repo/contacts/push.ts's attachOrCreateRosterSession is a SECOND caller, and it is the one the premise excludes by construction: it attaches a participant to a PRE-EXISTING submission found by findSubmissionByExactTitle, which was stamped whenever it was last written and never by this call. The consequence is exactly the one submissions/touch.ts's header predicts and that DEC-725's wave-17 amendment already ruled against ('every participant writer stamps, including the import path'): src/sync/airtable.ts's `gt(submission.updatedAt, mark)` never re-selects the session, so a roster add that JOINS an existing session never reaches the customer's Airtable Speakers cell, and repo/overview.ts's `desc(submission.updatedAt)` worklist never resurfaces it. test/touch-on-write-population.scan.test.ts passes because it reads the exemption from the comment rather than from an allowlist — the right mechanism (DEC-180/DEC-808), reading a claim that has since become untrue. RULED: insertActiveParticipants calls touchSubmissions for the submission id it just wrote; the in-code exemption comment is DELETED, not rewritten, and the scan's exemption branch keeps its synthetic positive control so the mechanism survives with zero live consumers. The scan additionally asserts the participants.ts population has no live exemption — a scan whose one real exemption disappears must say so, not silently keep a door open for the next writer.
