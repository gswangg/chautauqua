# DEC-727: A test that touches `window` is jsdom/SLOW — composeDraft.test.ts leaves the fast tier

app/src/pages/comms/composeDraft.test.ts is 12 of the fast tier's 41 failures, all `ReferenceError: window is not defined` at composeDraft.ts:57, and test/test-tiers.test.ts independently reports it as the one file the fast config wrongly selects. That is one defect reported twice, not two. The tier predicate is DERIVED, never hand-listed, so the repair is to make the derivation true: pin the file to jsdom in vitest.config.ts's environmentMatchGlobs and add the matching exclude line in vitest.fast.config.ts, exactly as the six existing entries there do. Fixing composeDraft.ts to guard `typeof window` would be the wrong repair — it is a localStorage contract module and the house rule is to fail loudly, not to defend against an environment the tier system is supposed to supply.


## Amendment (wave 115): a gate whose measured runtime sits at its undeclared timeout is a coin flip, and it teaches the train to discount reds

`test/public-cacheability-enumeration.test.ts` FAILED in the fast tier ("Test timed out in 5000ms", measured 5316ms) and PASSED in the full suite on the identical tree — the same commit, two verdicts. That is worse than a red: a gate that reports a defect that is not there is how a merge train learns to land batches over failing ratchets, which is precisely what happened to the desktop ledger this wave. Cause: `buildApp()` re-parses `src/index.ts`'s mounts and rebuilds the Hono app from scratch, is called three times in the file, and no `it` in it declares a timeout. RULED: a fixture that costs seconds is built once and shared, and any test still measuring above half the default timeout declares its own explicitly. Amortising the fixture is preferred over raising the limit — raising a timeout hides the cost, sharing it removes it — and the file's "never silently narrow" guard on the mount list must stay reachable exactly once rather than being dropped along with the repetition.

## Amendment (wave 17): a whole-corpus scan is a first-class member of DEC-069 wave-25's per-test timeout population, and its receipt is measured loaded AND unloaded

The fast tier ran 1374 files and reported 11 red; four of those reds (`app/src/css-contract.scan.test.ts` 6040ms, `test/files-library.test.ts` 5687ms, `test/fixed-table-column-hack.scan.test.ts` 5267ms, `test/anonymous-route-probe.test.ts` 6035ms) were pure 5000ms timeouts — two of them PASSED when re-run alone. A ratchet red and a load-dependent flake are indistinguishable in a summary, which is exactly how a planner inherits a wrong red set. The obvious fix is banned and correctly so: `test/suite-timeout-policy.scan.test.ts` (DEC-069 wave-25) forbids a config-level `testTimeout` in both vitest configs, because a global raise disarms hang detection for ~16,880 tests to rescue a handful of slow probes. RULED: the remedy is the per-test one that policy already names — `it(name, fn, ms)` with the receipt comment `// DEC-069 wave-25: measured <N>ms at <sha> (default 5000)` — and the population that earns it is not limited to `*-probe.test.ts`: any test whose body walks a whole corpus (every `.css` under `app/src`, every test file, every frame) belongs to it. The measured receipt records the SOLO duration, since a test whose solo time already exceeds half the default is load-dependent by construction; that threshold, not a hand-picked list, is what selects the population.


## Amendment (wave 47): no fast-tier test may spend its 5000ms per-test budget on a module-graph load — the import is a hook, not the first assertion's cost

MEASURED at main f572ee4cc: `npm run test:fast` = 1417 files / 18,633 tests, 11 files / 14 tests RED (386s). FIVE of the eleven are product tests, not instruments, and all five pass standalone: test/portal-session-card-clauses.test.ts, test/portal-submission-detail-round-trip-depth.test.ts, test/review-remind-laggards.test.ts, test/review-remind-recusal.test.ts and test/reminders-portal-link-batched.test.ts run 14/14 green in 3.6s together. Four of them fail under load at 5008/5014/5005/5008ms — the default testTimeout, to the millisecond — and every one has the same shape: a helper containing `await import("../src/routes/...")` is called from inside the FIRST `it()`, so loading the whole portal/review route module graph (~2.5s standalone) is billed against that one test's budget and crosses 5s the moment vitest's uncapped fast-tier worker count saturates the host. vitest.fast.config.ts's own justification for leaving workers uncapped — "to stay well under 60s" — is 6.4x false against the measured 386s, so the premise that made the choice safe no longer holds. Raising testTimeout would hide the growth curve (DEC-976 wave-45); capping workers would slow an already 6.5-minute tier. RULED: the module-graph load moves into a `beforeAll` (vi.mock hoisting is unaffected), so the per-test budget covers only the request under test; the config's timing premise is replaced by the measured figure stamped with its sha. This is the campaign's critical path, not hygiene: the exit predicate's `--suite-verified-sha` cannot be issued over a tier that flakes, and w43-e's `--frames-verified-sha` compounds the same requirement one tier over.
