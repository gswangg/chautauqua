# DEC-024: D21 amendment: URL-keying IS event scoping, and that claim is proven by a ledger scan rather than assumed — no cached read may be event-varying without carrying the event id in its path

The D19 cross-event switch (DEC-728 wave-108, landing this wave as v12m-w4-s) means a URL eventId can repoint the whole app mid-session, so a cache that served event A's payload under event B would be a correctness bug, not a staleness one. Keying on the full URL already handles it for the endpoints in play — every event-scoped read in this SPA carries the id in the PATH (`/events/${eventId}/submissions`, `/events/${eventId}/onboarding`), while the contacts reads (`/contacts?…`, `/contacts/stats`, `/segments`) are org-scoped and do not vary by event at all. But "already handles it" is an assumption a future adoption can break silently, so it is pinned: a scan derives every string/template literal passed to `apiGetCached`/`apiListCached`/`useCachedGet`/`useCachedList` anywhere under app/src and asserts each one either contains the substring `/events/${` or appears in an ORG_SCOPED_CACHED_READS ledger in the scan file with a one-line written reason — the DEC-808 derive-never-hand-list idiom, with a non-vacuity assertion that the derived population is non-empty and a negative control proving the check can fail. Deliberately chosen so that NOTHING in this subtree edits app/src/lib/useCurrentEvent.ts: that file is v12m-w4-s's to change for the switch banner, and event scoping here is a property of the KEY, not of the current-event hook.
