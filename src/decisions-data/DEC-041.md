# DEC-041: Speaker submission editing: portal edit sub-app with server-side edit lock

J2/CFP-06 requires speakers to edit their submission until close date, with accepted speakers editing indefinitely (swyx) — no surface implements this and no wave-4 task owns it. Design: new sub-app src/routes/portal/edit.tsx (GET+POST /portal/submissions/:id/edit) behind speakerGate, repo src/server/repo/portal-edit.ts scoping every query by auth.contactId via the participant join, and pure src/domain/edit-lock.ts: canEditSubmission(status, closeDate, now) = status==='accepted' || !isFormClosed(closeDate, now), enforced on POST (fail loudly), never CSS-hidden. Edits re-validate through validateAnswers + conditional visibility; DEC-016 locked fields sync submission.title/description columns; tracks editable only while the window is open; file-kind answers read-only in v1. Separate file keeps the in-flight w4-b portal work conflict-free.

## Amendment (wave 38): the edit lock belongs to the SUBMISSION, not the portal route, and no write is gated by a read predicate

SPEC §5 states the invariant unconditionally — form.close_date past ⇒ unaccepted speaker edits locked, server-side — and src/routes/portal/edit.tsx:345/425 enforces it with canEditSubmission. The deliverable API does not: src/routes/files.ts:85-100 authzSubmissionWrite gates on participant membership alone, so a declined speaker, or one whose CFP window has closed, keeps uploading and replacing files (POST /submissions/:id/files) and posting comments. Worse, the comment WRITE (src/routes/files.ts:528) was, at the time of this ruling, gated by authzFileRead — a read predicate protecting a write, the same inverted trust direction wave 37 found in the participant paths. Ruling: the lock is canEditSubmission(status, form.closeDate, now, event.timezone) for speakers on every deliverable write; organizers are never locked; reads keep their own, looser predicate under a helper named for reading. This preserves the clarification "accepted speakers keep editing" because canEditSubmission returns true for accepted regardless of close date.

## Amendment (wave 46): the DESTRUCTIVE speaker write obeys the same edit-lock as the constructive ones, and the lock becomes ONE function with every submission-scoped speaker write as its reader

canEditSubmission has exactly three write readers today: src/routes/files.ts:113 (authzSubmissionWrite — upload/replace), :403 (authzFileWrite — comment) and src/routes/portal/edit.tsx. DELETE /api/v1/files/:fileId (src/routes/files.ts:444) is a fourth speaker write and it does not consult the predicate at all — it checks uploader identity, isLatestInChain and contentStatus === pending, but not submission status / form close date. The result inverts the intent: past the CFP close date a speaker on a still-pending submission may not upload a new version and may not comment, but MAY permanently delete the latest version of a deliverable. The least reversible action is the least guarded one. Decision: the check is extracted to one pure guard over an already-loaded scope — `assertSpeakerSubmissionUnlocked({ status, formCloseDate, timezone })`, throwing ApiError("forbidden", "This submission can no longer be edited") — and all three existing readers plus the DELETE route call THAT function; the DELETE route's scope query grows the three columns rather than paying a second round trip. Deletion is not a category the DEC-713 rules exempt from DEC-041; DEC-713's per-version rules are additive to the edit lock, not a replacement for it.

## Amendment (findings wave 6): the close-date lock binds every status EXCEPT accepted — and canUploadDeliverables is deleted as its duplicate

src/domain/edit-lock.ts `status` was, before this amendment restored it, discarded (`void status`) so an accepted speaker was locked out of their own talk the moment the call closed. Three independent authorities say the opposite and none say what the code does: docs/clarifications.md:39 (highest precedence — "Accepted speakers can keep editing their submission; close-date edit locks exist in most tools 'but we dont really use that'"), SPEC.md:297-298 verbatim ("form.close_date past => new submissions rejected and (unaccepted) speaker edits locked, server-side. Accepted speakers keep editing per swyx"), and the vendored frame pack — docs/design/Chautauqua Public and Portal.dc.html:597-620 draws the portal's "Edit your session" screen editing Title and Abstract with the consequence line "Edits are live on the public pages straight away" and only Session length disabled as "set by the organisers"; a session is on the public pages only after acceptance, so that frame IS the post-acceptance editor. The in-code justification (a CFP-16 rubric FAIL) is ranked 4th by docs/README.md, below both clarifications and the brief, and clarifications.md:47-52 says the eval kit "is NOT the final list" — it is self-check tooling. So CFP-16 is a deliberate, recorded forfeit, not a defect. Consequence: canEditSubmission regains `status === "accepted" ||`, which makes canUploadDeliverables (edit-lock.ts:30-37) character-for-character the same rule under a second name; two names for one rule is exactly the drift the house forbids, so it is deleted and its callers in src/routes/files.ts move to canEditSubmission. canEditTracks is untouched — tracks drive reviewer and agenda assignment already settled by acceptance, and SPEC only exempts the submission's own text.

## Amendment (wave 117): A read-only answer is rendered read-only: the portal edit form stops offering a file picker whose bytes it will drop

src/routes/portal/edit.tsx:92-102 deliberately never reads a file part and carries the stored answer over, and :242-248 prints the current filename as "(read-only)". Yet :204/:228 render every field through FormFieldsSection, and src/views/form-render.tsx:116-126 has no read-only variant for kind:"file" -- so the speaker gets a live <input type=file>, picks a replacement deck, presses "Save changes", and receives a 302 success (:569) with the file silently discarded. The comment at :195-200 already names the gap and adds enctype defensively, which is a fix for the wrong half: the form does not need to accept the upload, it needs to stop asking for one. This is the fail-loudly principle inverted -- a control that cannot succeed is offered anyway, and the failure is rendered as success. RULED: FieldControl gains a read-only file rendition that shows the stored filename (or the no-file state) as a readout with no input, used wherever the surface declares file answers read-only; the separate "(read-only)" paragraph block at :242-248 is retired in the same commit rather than left as a second copy of the same fact beside the field it describes. Where a re-upload is genuinely wanted it is a separate, named action -- never an input the submit handler ignores.

## Amendment (wave 148): the portal edit page's Session length is a read-only row sourced from the submission's own format answer, and is omitted when not derivable

`Chautauqua Public and Portal.dc.html:620` (390) and `:1405` (desktop) both draw a 'Session length' block reading 'Talk, 30 min · set by the organisers', and `src/domain/edit-lock.ts:9` already names it ('only Session length disabled') — the row is anticipated by the lock rules and simply never built. This wave's amendment already ruled that a read-only answer renders read-only; this applies that rule to a field the form does not currently carry. Source of truth: the submission's own `session_format`-role answer through `sessionFormatLabel` (`src/lib/session-vocabulary.ts`) — the SAME derivation DEC-895 trusts for unplaced-row durations, never a second parse and never the scheduled slot's `durationMin` (a placement fact, not the session's declared shape). When the answer is absent or carries no parseable '(N min)', the whole row is omitted rather than shown empty or defaulted: the same 'never a fabricated default' rule applied one surface over. The trailing '· set by the organisers' is static prose stating who owns the value, which the edit lock makes true.
