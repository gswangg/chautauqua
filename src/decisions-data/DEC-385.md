# DEC-385: One phone switch (max-width: 700px) and one set of phone metrics for every stylesheet in the product

## Amendment (wave 7): a single-direction stylesheet's phone block is its LAST top-level construct, and a shadowed phone declaration is repaired by APPENDING, never by reordering

DEC-385 made the product single-direction (narrow overrides wide via max-width only) but never said WHERE the narrow block may sit. Measured on main by brace-matched parse: app/src/styles.css declares its first @media (max-width:700px) at :381, ABOVE the base rules it means to override, so 12 equal-specificity desktop declarations later in the same file win at every phone width — .chq-page-title renders 36px not the pinned 27px, .chq-main padding 26/16/34 not 16, .chq-steps 4 columns not 1fr, .chq-rail sticky/column not static/row. Same exposure in review.css (2), contacts-panels.css (3) and src/routes/public/css/rail.css.ts (1); no other sheet in the tree has it. Media queries add no specificity, so source order alone decides — which is why every phone gate in the tree (phone-page-scaffold, phone-tap-target, phone-block-visibility) reads green: they scan CSS text per-layer and cannot model source order. RULING: a phone override is authoritative only when its block is the file's final top-level construct; a sheet with a shadowed declaration is repaired by appending a terminal max-width block that re-states the shadowed declarations verbatim. Reordering or deleting the desktop rules is FORBIDDEN — 37 live worktrees hold hunks in these files and a reorder turns every one of them into a conflict that drops work. The fix is additive by construction.

## Amendment (wave 91): a single-direction sheet declares EXACTLY ONE terminal max-width block; consolidation is by MOVE in source order, never by appending a further block

DEC-385's wave-7 amendment already says the phone block is a sheet's LAST top-level construct, but 'last' is satisfied by appending a second block, which is what happened: settings.css now has four (:1170, :1517, :1677, :1863) and portal.css.ts two (:666, :834), and both sheets' own tests (settings-phone-frames.test.ts:29, portal-phone-frames.test.ts:220) demand exactly one and are RED — settings-phone-frames.test.ts does not even collect. review.css has the same shape (:2207 carrying a comment that it 'must stay the LAST block', then :2271 appended after it). The move must preserve relative order so the only cascade change is the intended one: phone rules that were losing to later top-level rules now win. app/src/styles.css is exempt this wave — its terminal block at :2360 already exists and the shell is a separate lane.

## Amendment (wave 92): one terminal max-width block per sheet, duplicate repairs deleted, and the cascade ratchet drops to 20

Three symptoms, one rule going unenforced. (a) review.css carries ELEVEN max-width:700px blocks, two of which (:2561 and :2577) are byte-equivalent terminal repairs of the same two selectors landed independently by two lanes, while the comment at :2204 still claims its block "must stay the LAST" though three blocks follow it. (b) portal.css.ts has two, and its own test demands one. (c) SHADOWED_CEILING = 22 in test/phone-cascade-order.scan.test.ts against 20 measured — a two-sided ratchet, so a sheet that got FIXED keeps the suite red until the ceiling moves, and the test's own text says only a merge-train step may move it. Planner-authorized the drop to exactly 20 as a merge-train step. Consolidation is by DELETING the redundant duplicate and correcting the stale comment — never by reordering rules, since source order is the whole mechanism.

## Amendment (wave 93): a two-sided cascade ratchet is re-measured and re-set by the lane that last touched a sheet

test/phone-cascade-order.scan.test.ts declares SHADOWED_CEILING=20 and measures 19 on main 32d33500, so the suite is red one wave after the identical 22-vs-20 failure was closed — because a different lane fixed a different sheet. A two-sided ratchet whose repair step belongs to nobody is a permanent red. RULING: the ceiling is authorised to move to exactly the number measured on the tree at the end of the lane that owns the last sheet change in a wave; this wave that lane is v12m-w11-b, which also consolidates src/routes/portal/portal.css.ts's two `@media (max-width: 700px)` blocks into one terminal block (test/portal-phone-frames.test.ts:222 pins exactly 1; the file has 2, at :678 and :923), so w11-b must set SHADOWED_CEILING to the value measured AFTER its own consolidation, not before. Consolidation moves rules DOWN in source order only — a terminal block can only win more, never less — so it is always shadow-neutral or shadow-reducing. Every other CSS lane this wave appends at true EOF (DEC-989 wave-90) and may therefore also lower the count; the merge train re-measures once for the batch.
