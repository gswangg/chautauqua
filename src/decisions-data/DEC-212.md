# DEC-212: Amendment (wave 34): completeness is a NUMERIC test, not a presence test — one function decides both the guard and the arithmetic

## Amendment (wave 34): completeness is a NUMERIC test, not a presence test — one function decides both the guard and the arithmetic

src/domain/evaluation/scores-json.ts's header declares numericScoresFor "the ONLY function in this module allowed to refuse a string, because it is the function that hands scores to something that multiplies them". Two of the three arithmetic sites obey (src/routes/review/shared.ts:522, src/server/repo/exports/evaluations.ts:295). The third, src/routes/review/evaluations.ts:66-75, builds a presence-only `complete` guard and then casts `r.scores as Record<string, number>` into computeWeightedScore — whose own guard (src/domain/evaluation/scoring.ts:55) THROWS on a non-finite value. So a dropdown-shaped string stored under a rating criterion 500s the whole organiser read, breaking the promise its own comment at :63-65 makes ("a read must never throw computeWeightedScore's invariant"). A guard that does not test the property the arithmetic requires is not a guard. RULED: add numericScoresOrNull(scores, criteria): EvaluationScores | null to scores-json.ts — null when the criteria list is empty or any criterion is absent/non-number/non-finite, the numeric record otherwise, never throwing — and let the ONE function decide both completeness and the projection. numericScoresFor keeps its throw unchanged: the reads adjacent to a write must still refuse loudly; only this unbounded historical list degrades, and it degrades to the same `score: null` an incomplete review already produces. The display projection (`scores` on the response) stays untouched — the module header already rules that tolerance belongs to the display reader, never to the arithmetic.
