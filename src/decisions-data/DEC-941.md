# DEC-941: An irreversible delete in the SPA goes through ConfirmDialog with a BODY, and the exemptions are a NAMED list

## Amendment (wave 91): when a panel splits into a hook and a view, the delete guard resolves through the PAIR — the hook owning apiDelete is guarded by the sibling view that renders its ConfirmDialog

app/src/pages/settings/tracksRooms/useTracksRoomsPanel.ts now owns the apiDelete calls while TracksRoomsPanel.tsx renders the ConfirmDialog, so delete-confirm.scan.test.ts's per-FILE rule ('every apiDelete call site imports ConfirmDialog') reports a false unguarded site and a second failure for a pendingX gate whose setter now lives across the split. The rule's intent is that no irreversible delete reaches the API without a confirm; a hook/view split does not weaken that. The scan must follow the module graph for the hook→view pair rather than being satisfied by an allow-list entry, because an allow-list entry would exempt the real guarantee too. Deciding this once here stops the next extraction re-opening it.

## Amendment (wave 97): An irreversible act at 390 keeps the control that decides its direction: Merge's dock carries the frame's two verbs and re-lines Swap rather than dropping it

`Chautauqua Contacts.dc.html:522` ("Merge · 390") draws a dock at `:536` with `Merge them` (`flex:1`, olive, 48px) and `Not a duplicate` (bordered, 48px, `padding:0 16px`); the desktop twin at `:356` draws three controls — `Merge into Marcus Okafor` (`:392`), `Swap which is kept` (`:393`) and `Not a duplicate` (`:394`). `MergePage.tsx:342-379` renders all three inline in the body at every width with the desktop's long primary label. RULED two ways. The primary's copy is width-dependent because the frame says so and because a `flex:1` centred button cannot hold a person's full name at 390: `Merge them` on phone, `Merge into <name>` on desktop, one button, one handler. And `Swap which is kept` RE-LINES above the dock rather than disappearing — the frame's two-control footer is a footer, not an inventory, and a merge is irreversible, so the one control that decides WHICH record survives is exactly the control DEC-941's arming doctrine forbids removing from the screen where the act is committed. DEC-919's "re-line, never remove" and DEC-941's "a confirm with no arming is the mirror of a delete with no confirm" agree here.

## Amendment (wave 107): a confirm names a scope and the handler must clear exactly that scope — and an unsaved add draft arms the confirm

The mandate filed "Ruling needed (from the tracks/rooms refusal fix, bbcf8b06)": discardDirtyAndClose clears row errors but not the add forms' field errors. Reading the code rather than the report found the smaller half and the larger half. discardDirtyAndClose (useTracksRoomsPanel.ts:135) resets trackDrafts/roomDrafts/trackRowErrors/roomRowErrors and calls closeEdit(), which only strips search params — so trackFieldErrors, newTrack and showAddTrack all survive the drill-in and a refusal re-renders over an empty field on the next visit. That is the filed symptom. The larger defect is that dirtyRowNames() names rows by their SAVED name, so a new track that has been typed but not added contributes nothing to the gate: an organiser with a half-written new row and no dirty rows gets NO confirm at all and loses it silently. That is the exact mirror of this DEC's own governing line — a confirm with no arming is the mirror of a delete with no confirm. RULED, two clauses that must land together. (a) Closing the drill-in retires the pass: one retireAddForms() reset, reusing the two toggles' own expressions rather than writing a third copy, called from closeEdit() so BOTH exits pass through it. (b) The arming gate counts an unsaved add draft, and the confirm body gains a clause naming it, built from the count-copy helpers the panel already imports. Widening (a) alone was rejected: the dialog's body says "{row names} have unsaved edits ... leaving now discards these edits", so a handler that also drops an add draft would make the confirm's own copy untrue in the other direction. The copy and the handler name the same scope, or neither is honest.

## Amendment (wave 132): Done-with-discard retires the WHOLE attempt -- every draft, every add form, every error state -- because that is what its confirm body promises

The mandate's open 'Ruling needed (from the tracks/rooms refusal fix, bbcf8b06)' is closed here. `handleDone` (useTracksRoomsPanel.ts:167) arms the discard confirm when EITHER a row is dirty OR an unsaved add draft exists, so the confirm's body speaks for both; `discardDirtyAndClose` (:175-189) then resets the row drafts and clears `trackRowErrors`/`roomRowErrors` but leaves `trackFieldErrors`/`roomFieldErrors` -- the ADD forms' own errors -- the panel-level `error`, and the add drafts themselves standing. The next drill-in therefore re-renders a refusal describing an attempt the organiser already walked away from: DEC-856's 'a component holding two error states owes each one its own clear' from the other side, and DEC-941's arming rule in mirror image -- a confirm that performs less than its body promises is the same lie as a delete with no confirm. RULED: discard retires every dirty row draft, both add forms (open/closed state and fields), both row-error maps, both add-form field-error maps, and the panel-level error. It does this by calling the EXISTING add-form retirement path rather than clearing state inline, because a second copy of a closing vocabulary is a trap with a delay fuse (DEC-613).

## Amendment (wave 134): the irreversible register is a WEIGHT, and a page's own arming field satisfies it exactly as a dialog's does

DESIGN-RULINGS.md ruling A8 drops the bulk-bar Delete from the submissions list and says that if bulk delete returns, "it needs a typed confirmation." It returned as its own page (`app/src/pages/submissions/DeleteSubmissionsPage.tsx`, DEC-886/DEC-921), cascading up to 1000 ids across files, comments, revisions, participants, answers, tracks, recusals, task responses, review assignments and agenda slots, fired straight off the primary with no typed phrase anywhere -- the divergence had been recorded nowhere. The page's own DEC-886 wave-2 comment is right that a stacked ConfirmDialog restating the page's own already-printed prose a second time would demote it; that answers WHERE the confirmation lives, it does not answer WHETHER the act is armed, and those are two different questions this DEC has always kept separate (the `weight` prop decides the second one independently of which component draws the body).

RULED: the NAMED irreversible population (a portal resource delete, a contact merge, a form field delete, and now bulk session delete) is satisfiable two ways -- by `ConfirmDialog`'s own `weight="irreversible"` typed-phrase gate, or by a page arming the same act in its own footer, when a stacked dialog would only restate prose the page already committed to render. Both paths MUST reuse the identical match rule (trim + case-insensitive compare), extracted to `app/src/lib/confirmPhrase.ts`'s `confirmPhraseMatches` so there is one comparator, not two independently-maintained copies of the same guarantee (DEC-613). `DeleteSubmissionsPage.tsx` arms its `Delete N sessions` primary with a labelled text input in its own footer (`chq-submissions-delete-arm-row`) whose value must match `"delete sessions"` (drawn from the page's own H1, stated in the label so it can be read and typed) before the primary enables; `busy` and `deleteCount === 0` keep gating the primary as before, and Cancel is never blocked by the arming, matching `ConfirmDialog`'s own irreversible weight exactly.

`ConfirmDialog.tsx`'s population note (formerly "the SPA's irreversible population today is exactly two callers -- ResourcesPanel.tsx and MergePage.tsx") was already false before this wave (`FormsPage.tsx` renders `weight="irreversible"` twice, for its two form-field deletes) and is corrected in place: the component's own callers are ResourcesPanel.tsx, FormsPage.tsx (x2), and MergePage.tsx; bulk session delete arms through its own page footer instead of an instance of this component, reusing its match semantics without rendering it.

## Amendment (wave 19): a destructive fold that cannot be rolled back reports exactly which pairs it completed

`src/server/repo/contacts/merge.ts`'s `mergeContacts` loops `mergeOnePair` once per merge id, and each pair performs roughly a dozen unbatched writes ending in an irreversible contact DELETE. Measured: `db.batch(` appears nowhere in `src/` (the only mention is `src/server/repo/submissions/status.ts`'s comment saying so), and unlike `updateSubmissionStatuses` — whose no-transaction posture is explicitly justified by idempotence — merge is destructive and non-idempotent. The function's own docstring claims "a refusal always means ZERO writes, never a write of contacts 1..k-1 followed by a 409 on contact k"; that is TRUE of `checkMergeConflicts`'s whole-operation preflight and FALSE of any runtime failure inside the fold, so the sentence currently reads as an absolute guarantee the code does not make, behind a dialog DESIGN-RULINGS classes as irreversible. RULED, per DEC-941's own mirror principle: the fold is not made atomic (no transaction primitive exists to make it so, and inventing a compensating-write path would add a second, untested destructive code path), it is made HONEST. A failure inside the loop is re-raised as an ApiError whose message names, by id, the pairs already folded and the pairs not yet attempted, so the organizer's next act is a retry of the remainder rather than a guess; and the docstring is corrected to scope its all-or-nothing claim to preflight refusals explicitly, naming the runtime-failure case it does not cover. A durable write is a point of no return; a caller that cannot see where the return was is worse off than one that can.

## Amendment (wave 20): `mergeContacts` is all-or-nothing only about its PREFLIGHT; a failure mid-loop must name every contact that already folded

src/server/repo/contacts/merge.ts`survivor = await mergeOnePair(db, keepId, mergeId);` loops that helper once per merge id, and each pair performs roughly a dozen unbatched destructive writes (contact update, participant folds/deletes, task-assignment dedupe, pipeline fold, seven FK repoints, user-email rewrite, contact delete). No D1 `batch()` or transaction exists anywhere in src/. Unlike `updateSubmissionStatuses`, whose no-transaction posture is explicitly justified by idempotence at src/server/repo/submissions/status.ts:518, a merge is destructive and non-idempotent: a failure on pair 2 of 3 returns an error to the organizer AFTER pair 1's contact has been irreversibly deleted, behind a dialog DESIGN-RULINGS classes as irreversible. The function's own docstring makes this worse by claiming 'a refusal always means ZERO writes, never a write of contacts 1..k-1 followed by a 409 on contact k' — true of the `checkMergeConflicts` preflight, false of any IO failure inside the loop. RULED (narrowest fix, no invented transaction layer): the docstring's all-or-nothing claim is scoped to the preflight path in words, and the loop makes the partial state VISIBLE — when a pair fails after at least one pair has folded, the error names how many of how many folded, which ids they were, and that they cannot be un-merged; when nothing has folded the original error is rethrown untouched so the preflight guarantee reads exactly as before. Making the partial state legible beats pretending atomicity the storage layer does not provide.

## Amendment (wave 22): A claim is released only by the caller that still holds it — the reminder mailer-failure restore takes a claim predicate, and `updatedAt` stays bumped

DEC-023's claim-before-send design closes the reminder double-send window by stamping `lastRemindedAt` BEFORE the mailer runs, under a conditional UPDATE whose RETURNING identifies exactly the rows this call won. Measured on main: `src/server/repo/tasks/reminders.ts`'s mailer-failure release restores the pre-claim value with `.where(inArray(schema.taskAssignment.id, chunk))` and NO predicate on the current stamp — so a cron tick whose send fails will overwrite a stamp written by a concurrent `remindNow` (which claims unconditionally, `claimCutoff: null`) that has already delivered, re-opening the exact window the claim exists to close. RULED (narrowest fix, no new locking layer): the release is conditioned on the row still carrying THIS call's claim value, so a release can only ever undo a claim the same call made. `updatedAt` is deliberately NOT restored: a write really did occur on that row, and un-bumping it would make the row lie about its own history — the claim/release pair is honest about the attempt even when the attempt failed. Consistent with this decision's ruling on `mergeContacts`: make partial state legible rather than pretend at atomicity the storage layer does not provide.

## Amendment (wave 7): One comparator implies one input policy — no field cap may defeat the trim the comparator performs

confirmPhrase.ts is declared the ONE comparator for typed-phrase arming and it trims both sides. DeleteSubmissionsPage.tsx:251 caps its arming input at `maxLength={DELETE_ARM_PHRASE.length}` (15) while the sibling caller ConfirmDialog.tsx sets none, so a leading space or padded paste clips the tail, trim() can never rescue it, and Delete stays permanently disabled. Two users of one comparator behaving differently on identical input is the exact trap DEC-613 names. RULED: the comparator's trim is part of the contract; a caller may not narrow the accepted input under it.

## Amendment (wave 23): A destructive confirm's title names the object it destroys — and the population is derived from the caller's own pending-row state, not asserted

This decision's wave-9 amendment already RULES 'the title names the object' from Chautauqua Settings.dc.html:1421 (`Delete "Speaker handbook 2027.pdf"?`), and justifies it with the sentence 'Every other ConfirmDialog caller already names its object in the title.' A ruling whose premise is a claim about a tree, dated, is not a built ruling. RULED, with a predicate instead of a claim: a ConfirmDialog whose act destroys or detaches exactly ONE named row, and whose caller ALREADY holds that row's own name/title in state (a `pendingDelete: SavedView`, `pendingRemove: ScheduleBreakRow`, `pendingUnassignReviewer: {displayName}`, a contact in props), MUST render `title={…}` naming it in the frame's shape. A confirm with no single named object — a bulk act, a whole-form change, a state toggle, a navigation discard — keeps its fixed title and is explicitly out of population; naming an object it does not have would be an invention. Where the body already repeats that name, the body drops it (one copy, DEC-613). confirmLabel is untouched: app/src/confirm-primary-object.scan.test.ts already governs primaries, and DEC-941's own wave-9 ruling AGAINST the frame's pronoun primary stands.

## Amendment (wave 38): a confirm whose own body says 'permanently delete' takes the irreversible weight — the weight is read off the consequence the dialog states, not off the caller's mood

DESIGN-RULINGS 'Confirm dialogs — one component, two weights' rules the weight by reversibility: irreversible deletes take the typed confirmation. app/src/pages/review/PlanEditor.tsx:2932 opens the plan-delete ConfirmDialog at the default reversible weight with no confirmPhrase/confirmNoun, while its own body reads 'This will permanently delete N submitted evaluation(s) and N draft evaluation(s), N reviewer assignment(s), and N recusal(s). This plan's results table and CSV export go with it.' Strictly less destructive acts in the same product all carry the typed gate — a portal resource, a contact merge, a saved embed — so the one dialog that names the largest blast radius is the one with the weakest gate. The DELETE door was relaxed at wave 34 from planHasEvaluations to countSubmittedEvaluationsForPlan (verified built), which is correct policy but widens exactly this exposure: a plan holding reviewers' in-progress DRAFT scores is now deletable, and one un-gated click destroys them. RULED: plan delete takes weight='irreversible' with confirmPhrase set to the plan name the dialog title already quotes (`Delete "<name>"?`) and a confirmNoun naming the plan, matching the event-delete idiom; the body copy is unchanged, since it already names the blast radius from real data as the ruling requires. This is a DESIGN-RULINGS-mandated behaviour change on an admin surface, not a desktop reflow — no geometry moves and the desktop pins stay green.
