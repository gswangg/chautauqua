# DEC-509: An evaluation plan's numeric fields are validated at the route on BOTH POST and PATCH; a bad value is a 400, never a silent coercion and never an uncast bind

An evaluation plan's numeric fields (maxEvaluations and its siblings) are validated at the route layer on both the create (POST) and update (PATCH) paths. A value that fails validation is refused with a 400 at the route; it is never silently coerced to a default, never NaN-coerced, and never bound uncast into the write. The read door and the write door agree on the same shape.

## Amendment (wave 30): a plan's JSON-column fields are validated at the route on BOTH POST and PATCH, by the same predicate the read door enforces -- never an uncast bind

DEC-509 already rules this for an evaluation plan's NUMERIC fields, and src/routes/review/plans-crud.ts's own comment claims the class is closed for maxEvaluations. It is not closed for `filters`. Verified on main: plans-crud.ts:230 (PATCH) and :96 (POST) both write `body.filters as { trackIds?: string[] } | null` with zero validation, while the read door src/domain/evaluation/plan-json.ts`parsePlanFilters` THROWS PlanJsonError on anything but `{trackIds: string[]}`. One `PATCH /api/v1/plans/:id {"filters":{"trackIds":"t1"}}` writes a filters_json that every later `toPlanRecord` (src/server/repo/review/plans.ts:74) rejects, so the plan, its results, its queue AND the repair PATCH all 500 forever. A write door laxer than its read door is a permanent brick, not a 400. This amendment extends DEC-509 from numeric fields to every JSON-column field on the plan record, and names the enforcement shape: the route calls the SAME parser the reader uses (or a shared validator it delegates to), never a second hand-rolled shape check that can drift from it.

## Amendment (wave 23): An unresolvable request PARAMETER is a refusal in the house envelope; only a data-corruption invariant may throw bare

src/server/repo/contacts/crud.ts's scanAndFilterContacts throws `new Error(`segment ${params.segmentId} not found for org ${orgId}`)` when findSegmentForOrg misses — a bare Error, so it escapes as a 500 `internal` instead of the house 400/404 envelope. The trigger is pure user input and it is reachable two ways: GET /api/v1/contacts?segmentId=… (the route's try/catch wraps only the query parser, not listContactsForOrg) and GET /api/v1/events/:id/export/contacts?segmentId=…. The repo layer's other ~145 bare Errors are correct and must stay: they assert invariants ('has no stored version_no — data corruption', 'previous_file_id cycle detected'), where fail-loudly is the house rule and a 500 is the honest answer. RULED: the distinction is the trigger, not the layer. A throw whose cause is a value that arrived in the request is an ApiError in the house envelope, naming the parameter and never echoing the caller's orgId back; a throw whose cause is stored state contradicting itself stays a bare Error. This decision also forbids the silent-coercion escape — an unknown segmentId must never be treated as 'no segment' and quietly return the unfiltered list.
