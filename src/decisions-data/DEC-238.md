# DEC-238: A skipped recipient the send report counts owes a comms-history row — the CRM bulk-email path adopts the same status:"skipped" write the comms send path already makes

DEC-238's contract is a structured `{sent, skipped, failed}` report rather than a 500, and `src/routes/comms/send.ts` treats the comms history as the record that must agree with it — it writes an explicit `status: "skipped"` `email_log` row per skipped recipient, with `bodyHtml: ""` and a comment explaining that no HTML render exists for a message that never reached the shell step. `src/routes/api/contacts/bulk-email.ts` returns `skipped: intraBatchSkipped + crossCallSkipped` and writes nothing, so the count appears in the response and vanishes: an organiser who opens the history a day later sees 21 rows for a send that reported 23 recipients and has no way to learn why two never went. DESIGN-RULINGS B1 rules on exactly this reader — 'a count of skips is not actionable; two names are' and 'being told "skipped" without knowing why reads as a failure' — which is only satisfiable if the skip is recorded per recipient somewhere durable. The route can do this honestly because it already renders every target BEFORE the dedupe split, so a skipped recipient's subject and body are in hand and need no second render pass and no second query. The write must go through the same `d1EmailLogWriter` and carry the same `batchId` the fan-out uses, so the history groups the whole send into one row. Minting is explicitly NOT extended: DEC-397's rule that a claim credential is minted only for recipients that ship stands unchanged — a skipped recipient gets a history row, never a token.


## Amendment (wave 131)

`src/routes/api/contacts/bulk-email.ts` now collects skipped recipients into one `skippedRendered` array (the same `RenderedRecipientEmail` records the sent path uses) instead of two bare counters (`intraBatchSkipped`, `crossCallSkipped`); the returned `skipped` count is `skippedRendered.length`, and one `status: "skipped"` `email_log` row is written per entry through `d1EmailLogWriter`, sharing the call's `batchId` — the response and the comms history are now structurally unable to disagree, mirroring `src/routes/comms/send.ts`'s wave-8 amendment. No second render pass or query was needed: bulk-email already renders every target before the dedupe split.

The invariant this establishes — **a reported `skipped` count owes a comms-history row** — is not yet honored by two other paths that return a `skipped` count and write nothing:

- `src/routes/review/plans-progress.ts`'s reviewer-laggard reminder send.
- `src/server/repo/tasks/reminders.ts`'s speaker task reminder send.

Both are recorded here, not fixed here, so the next wave that picks either one up starts from this record instead of rediscovering the gap.

## Amendment (wave 132): The reviewer-reminder path writes the comms-history row its own skipped count promises; the third path is blocked on a repo shape and is named, not silently skipped

src/routes/comms/send.ts`status: "skipped"` is written as an explicit `email_log` row per skipped recipient through `d1EmailLogWriter` carrying the fan-out's `batchId`. `src/routes/review/plans-progress.ts:465` returns `skipped: skipped.length` and writes nothing, so an organiser told two reviewers were skipped finds a history that has never heard of them -- the same broken invariant DEC-238 was written for, in a sibling module that missed it. The path can satisfy it honestly with no new query and no second render: `skipped` (:381) already holds the full laggard rows, and eventId/subject/name/batchId are all in hand. The per-laggard body must be hoisted into ONE local so the sent and skipped texts can never drift (DEC-238 wave-66's 'one variable, never two literals'), `contactId` stays null (DEC-191: reviewers are users, not contacts), and minting is untouched (DEC-397: a skipped recipient gets a history row, never a token). The FOURTH path, `src/server/repo/tasks/reminders.ts:620`, cannot take the same fix: `listRemindableContactIds` returns `skipped` as a COUNT, not a roster, so there is nothing to write a row per. That is recorded here as a repo-shape prerequisite so the next wave schedules it from a record rather than rediscovering it -- an unrecorded blocker and an unnoticed defect are indistinguishable to the next planner.

## Amendment (wave 133): the FOURTH send path — speaker task reminders — writes the email_log rows its skipped count promises, and its repo helper returns a roster rather than a number

DEC-238 wave-8 set the invariant that the comms history row must agree with the send report about skipped recipients, and it was implemented in exactly one place — src/routes/comms/send.ts`status: "skipped"`, written alongside `provider: "none"`, `bodyHtml: ""` and the UNMINTED rendered body. `v12m-w6-h` closes `src/routes/api/contacts/bulk-email.ts` and a wave-7 lane closes `src/routes/review/plans-progress.ts:424`. The fourth and last send path is the speaker task reminder, in `src/server/repo/tasks/reminders.ts`: `remindNow` returns `{ ...result, skipped: chosen.skipped, remaining: chosen.remaining }` (:620) where `chosen` comes from `listRemindableContactIds`/`planManualReminders`, whose contract is `{ contactIds: string[]; skipped: number; remaining: number }` (:191, :264) — a COUNT, with the contact identities discarded inside the dedupe aggregation. That is the repo-shape prerequisite, and it is the reason this path was deferred three waves running. RULED: `listRemindableContactIds` and its JS-side twin both return `skippedContactIds: string[]` alongside the count (the count stays, derived from the roster's length so the two can never disagree), and `remindNow` writes one `email_log` row per skipped contact with the same field discipline the sanctioned path uses. A skipped recipient is never minted a claim token, so the stored body is the un-substituted reminder text; where no rendered body exists for a skipped contact the row still lands with the reminder subject and an empty `bodyHtml`, because a history that omits the skip is the defect this invariant exists to prevent.
