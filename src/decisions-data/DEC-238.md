# DEC-238: A skipped recipient the send report counts owes a comms-history row — the CRM bulk-email path adopts the same status:"skipped" write the comms send path already makes

DEC-238's contract is a structured `{sent, skipped, failed}` report rather than a 500, and `src/routes/comms/send.ts` treats the comms history as the record that must agree with it — it writes an explicit `status: "skipped"` `email_log` row per skipped recipient, with `bodyHtml: ""` and a comment explaining that no HTML render exists for a message that never reached the shell step. `src/routes/api/contacts/bulk-email.ts` returns `skipped: intraBatchSkipped + crossCallSkipped` and writes nothing, so the count appears in the response and vanishes: an organiser who opens the history a day later sees 21 rows for a send that reported 23 recipients and has no way to learn why two never went. DESIGN-RULINGS B1 rules on exactly this reader — 'a count of skips is not actionable; two names are' and 'being told "skipped" without knowing why reads as a failure' — which is only satisfiable if the skip is recorded per recipient somewhere durable. The route can do this honestly because it already renders every target BEFORE the dedupe split, so a skipped recipient's subject and body are in hand and need no second render pass and no second query. The write must go through the same `d1EmailLogWriter` and carry the same `batchId` the fan-out uses, so the history groups the whole send into one row. Minting is explicitly NOT extended: DEC-397's rule that a claim credential is minted only for recipients that ship stands unchanged — a skipped recipient gets a history row, never a token.
