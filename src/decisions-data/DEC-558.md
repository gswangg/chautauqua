# DEC-558: The contacts sibling-email conflict `.limit(1)` takes a total order because its refusal message NAMES the row it found

src/server/repo/contacts/crud.ts's patch path selects any same-org contact holding the new email, excluding the contact being edited, with `.limit(1)` and no ordering — the one uncited offender against the DEC-558 ceiling of 0. The usual 'any row proves the predicate' argument does not apply here: the handler throws `${firstName} ${lastName} already uses this email`, so WHICH row the engine returns is user-visible copy that can differ between runs over the same data. Ruled: add an `.orderBy(schema.contact.id)` total order rather than a DEC-citation exemption — the cheapest fix that makes the refusal deterministic.
