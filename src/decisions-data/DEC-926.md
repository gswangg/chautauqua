# DEC-926: Amendment: deleting a form-task answer file clears the answer it is stored in — a repointed `file_id` is not a repointed `response_json`

`src/routes/portal/tasks.tsx:449` writes portal form-task file answers with `kind: "handout"` and stores the id inline as `answers[field.id] = fileId` in `task_assignment.response_json`. `handout` is in `FILE_KINDS`, so `getFileDeleteScope` (src/server/repo/files-versions-delete.ts:72) admits these rows into the deletable population — unlike the exactly-parallel CFP answer, which uses `kind: "attachment"` PRECISELY to stay out of it (src/server/repo/submit.ts:442, and the delete scope's own DEC-713 comment says so). `deleteFileVersion` repoints only `task_assignment.file_id`, never `response_json`, so DEC-926's rule (reopen the assignment rather than leave it pointed at a deleted row) silently fails: the assignment stays `complete` and `src/server/repo/tasks/response-detail.ts:97` degrades to rendering a raw file id. Ruling: the delete path clears the dangling id from `response_json` and reopens the assignment in the SAME statement set — a dangling id is never left behind, and the answer's absence is what reopens the task. Set-based, no read-then-write.
