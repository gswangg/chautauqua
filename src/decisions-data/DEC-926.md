# DEC-926: Amendment (wave 135): A repoint across a partial-unique link deletes the row before it re-links, never after
## Amendment (wave 135): A repoint across a partial-unique link deletes the row before it re-links, never after

deleteFileVersion repoints the successor onto the deleted row's parent (files-versions-delete.ts:232) and only then deletes the row (:265). For a chain v1 -> v2 -> v3, deleting the middle version sets v3.previous_file_id = v1 while v2.previous_file_id is still v1, so two live rows share a previousFileId and file_previous_file_id_unique (the partial UNIQUE from migrations/0043) rejects the UPDATE -- a hard 500 on a path only organizers can reach, which is exactly why every existing test misses it (the speaker rule isLatestInChain and every 2-version chain avoid the overlap by construction). The insert path already guards this same constraint (files-versions-write.ts:81), so the delete path is a plain omission rather than a disagreement about the invariant. The ordering rule is stated once here because it generalises: wherever a set-based repoint moves rows onto a key the row being removed still holds, the removal is the FIRST statement, and DEC-926's own repoint-or-reopen contract for task_assignment is unaffected by moving it.
