# DEC-013: D21 amendment: the SWR read cache lives INSIDE the one API client and is opt-in per call site — apiGetCached/apiListCached, keyed on the exact request URL

app/src/one-api-client.scan.test.ts pins app/src/lib/api.ts as the sole module in app/src containing a `fetch(` call against /api/v1 (and the scan is a raw-line grep — the token `fetch(` must not appear even in a COMMENT in any other file). So the cache Map, its writes and its eviction all live in api.ts and reuse the existing `request()` path; nothing is allowed to open a second read path beside it. The cache is OPT-IN, not automatic on every GET: apiGet today serves one-shot reads whose whole value is freshness (`/tasks/:id/delete-preview`, `/contacts/duplicates/check`, `/submissions/:id` header reads) — serving those from cache would be wrong, and an automatic cache would make every one of those call sites silently participate in a policy none of them asked for. Two new exported helpers, `apiGetCached<T>(path)` and `apiListCached<T>(path)`, delegate to the SAME `request()` and additionally write their successful payload into the cache; only 2xx payloads are ever written (an ApiError throws before the write). The key is the FULL request URL string `${API_PREFIX}${path}` — the identical string handed to fetch — so two paths differing in any segment or query param are two entries and can never share a payload. A synchronous, non-fetching `peekCachedRead<T>(path): T | undefined` is the read seam (it must contain no React, so a useState initializer can call it during render). Bound: a 32-entry least-recently-read eviction, so a page paginating through query strings cannot grow the Map without limit. NO TTL: the bump counter (DEC-700) is the ONE author of "is this entry still good" — a TTL would be a second author of that same fact, DEC-678's "a default is an invitation to guess" on the freshness question. `resetApiCacheForTests()` is exported as the test-only seam, mirroring useCurrentEvent.ts's existing resetEventsCacheForTests idiom. Note for the api-mutation-bump scan: both helpers issue GET only, so api-mutation-bump.scan.test.ts's issuesNonGetMutation never classifies them and EXEMPT_HELPERS stays exactly `['apiPostBlob','signOut']`.
