# DEC-700: D21 amendment: the mutation bump IS the cache's invalidation clock — bumpMutationVersion clears the whole read cache, wired once by subscription, never per-helper

Two candidate contracts were on the table: (A) per-entry version stamps, serving a payload written before a mutation and revalidating behind it; (B) any successful mutation drops every entry. (B) is ruled. Under (A) the stamp buys nothing the hook does not already get from putting useMutationVersion() in its effect deps (the DEC-700 idiom useNavExceptions.ts already uses), while adding a state whose only honest use would be a knob nobody renders — and it leaves open the case the mandate specifically warns about: a payload from BEFORE a write presented as the current answer. Under (B) that case cannot exist. The cost is bounded and small: the cache's win is revisit-without-a-write (Contacts → Speakers → Submissions → back), which is most navigation; a write resets it and it refills on the next read. WIRING, and this is the load-bearing half: the clear must NOT be a second line added beside each `bumpMutationVersion()` call — request() and apiUpload each call it separately today, and "remember to add the second line in both places" is precisely the drift api-mutation-bump.scan.test.ts was written to stop. Instead mutationSignal.ts exports its existing private `subscribe` as `subscribeToMutationVersion(cb: () => void): () => void`, and api.ts calls `subscribeToMutationVersion(clearReadCache)` ONCE at module scope. mutationSignal.ts must not import api.ts (api.ts already imports mutationSignal.ts — the reverse would be a cycle). Because api.ts's subscription is registered at module load, it sits ahead of every component's useSyncExternalStore subscriber in the insertion-ordered Set, so the cache is already empty by the time a mounted hook re-runs its effect on the version change. Every future mutating helper therefore invalidates the cache for free, because the scan already forces it to bump.

## Amendment (wave 121): A mutation bump invalidates the CACHE, never the RENDERED payload

DEC-700 already rules that the mutation bump IS the cache's invalidation clock, and app/src/lib/api.ts`subscribeToMutationVersion(clearReadCache)` wires it as the FIRST subscriber. But `useCachedRead.ts`'s effect runs on `[path, mutationVersion]` and unconditionally re-seeds `setData(peekCachedRead<T>(path))` — so by the time the effect runs after any successful POST/PATCH/PUT/DELETE the cache is empty and every mounted cached read blanks to `data=undefined, loading=true` for one full network round trip. I proved it by recording rendered frames on a clean archive of 17deea82 with a 20ms fetch: `["data=Ada loading=false", "data=undefined loading=true", "data=Ada Updated loading=false"]`. This contradicts the file's own comment app/src/lib/useCachedRead.ts`loading means "nothing to render", never "a request is in` ("a cached payload never shows a skeleton") and docs/mobile-campaign.md's D21 entry ("render last-known data on revisit (no skeleton when a cached payload exists), refetch in background, reconcile"). The pin that claims to guard it — useCachedRead.honesty.render.test.tsx, the `it()` whose comment reads "the still-mounted hook never blanks its rows or flips back to loading" — asserts synchronously after `await apiPost(...)`; with an instantly-resolving mock the effect's `setData(undefined)` and the refetch's `setData(fresh)` land in ONE React batch, so the blank frame is never rendered and the test is green over a defect that ships. RULED: the path-driven effect re-seeds `data` from the cache ONLY when `path` changed since the last run (tracked via a `prevEffectPathRef`); a bump-only run leaves the rendered payload untouched and revalidates behind it. And a render-honesty pin about a background revalidation asserts across a real FLUSH — a deferred resolution and recorded frames — never synchronously after an awaited mutation, because a mock that resolves in the caller's own batch cannot observe the frame it exists to forbid.

## Amendment (wave 144): a cached read carries the invalidation epoch it started under; a read resolving after the clock cleared must not repopulate

app/src/lib/api.ts's `apiGetCached`/`apiListCached` write `cacheSet(cacheKey(path), result)` AFTER their `await` with no check against the mutation clock, while `clearReadCache` is fired SYNCHRONOUSLY by `subscribeToMutationVersion`. A read already in flight when a mutation lands therefore repopulates the cache with pre-mutation data after the clear, and the next visit paints stale rows with no skeleton — the precise defeat of this decision's own invariant that "the mutation bump IS the cache's invalidation clock". The epoch rides the EXISTING subscription (the file's own comment forbids a second `clearReadCache` beside `bumpMutationVersion()`). Fail-loudly boundary: the in-flight request still RETURNS its result to its own caller — only the cache write is dropped — so nothing is invented and nothing is silently swallowed.
