# DEC-700: D21 amendment: the mutation bump IS the cache's invalidation clock — bumpMutationVersion clears the whole read cache, wired once by subscription, never per-helper

Two candidate contracts were on the table: (A) per-entry version stamps, serving a payload written before a mutation and revalidating behind it; (B) any successful mutation drops every entry. (B) is ruled. Under (A) the stamp buys nothing the hook does not already get from putting useMutationVersion() in its effect deps (the DEC-700 idiom useNavExceptions.ts already uses), while adding a state whose only honest use would be a knob nobody renders — and it leaves open the case the mandate specifically warns about: a payload from BEFORE a write presented as the current answer. Under (B) that case cannot exist. The cost is bounded and small: the cache's win is revisit-without-a-write (Contacts → Speakers → Submissions → back), which is most navigation; a write resets it and it refills on the next read. WIRING, and this is the load-bearing half: the clear must NOT be a second line added beside each `bumpMutationVersion()` call — request() and apiUpload each call it separately today, and "remember to add the second line in both places" is precisely the drift api-mutation-bump.scan.test.ts was written to stop. Instead mutationSignal.ts exports its existing private `subscribe` as `subscribeToMutationVersion(cb: () => void): () => void`, and api.ts calls `subscribeToMutationVersion(clearReadCache)` ONCE at module scope. mutationSignal.ts must not import api.ts (api.ts already imports mutationSignal.ts — the reverse would be a cycle). Because api.ts's subscription is registered at module load, it sits ahead of every component's useSyncExternalStore subscriber in the insertion-ordered Set, so the cache is already empty by the time a mounted hook re-runs its effect on the version change. Every future mutating helper therefore invalidates the cache for free, because the scan already forces it to bump.
