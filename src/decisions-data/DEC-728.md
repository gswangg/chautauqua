# DEC-728: Settings is a read-only summary with drill-in editing, and the drilled section is URL state

## Amendment (wave 99): The Settings 390 drill frames depict the DRILLED view; its row-level actions bind, its save model does not

docs/design/audit/settings-v12.md has carried an explicit design-gap request since wave 3: the Tracks-and-rooms (:347-390) and Your-data (:393-441) 390 frames draw each row as name + detail + a boxed 44px `Edit`/`Download`/`Revoke`, while the app's `SummarySection` drill (`?section=<key>&edit=1`, DEC-728) renders either a summary of pills or a list of live input rows. Two sub-questions were tangled together and both were deferred as one. RULED, split: (a) the frame's per-row `Edit` is SATISFIED by the app's always-editable drill rows — DEVIATIONS §6 already blessed the per-row dirty-reveal save model over the frame's page-footer model, and re-reading `Edit` as a demand to hide those rows behind a second tap would reverse a recorded user ruling; (b) the frame's per-row `Download` on the Exports list is NOT satisfied by `.chq-pill`, which fuses the name and the action into one element and can never present the frame's name-over-detail stack beside a separate boxed control. The pill strip is desktop's shape and stays; the 390 drill renders a phone-only export ROW list (name, detail, boxed 44px `Download`) under the DEC-919 phone-sibling rule. DEVIATIONS §5's "sweep should verdict" on the save model is therefore answered by §6's own recorded adjudication — it is closed, not open.


## Amendment (wave 108, USER RULING 2026-08-19 D19): a URL eventId that overwrites a DIFFERENT stored context announces itself and offers one click back

The mandate gained a user ruling during this planning pass. useCurrentEvent.ts writes the URL's eventId straight into localStorage and returns it, so following a link from one event silently repoints every other page at another — the one-event-at-a-time invariant is kept, but the switch is invisible. The user ruled the write-through stays (page and context move together, no transient or split-view state) and the switch becomes explicit: a banner naming both events with a one-click return. The pin the user specified is two-directional by construction — equal ids show no banner, differing ids show exactly one — which is what stops a later wave from either dropping the banner or firing it on every navigation.

## Amendment (wave 117): An unresolvable URL eventId is a bad address, not a switch: it never evicts the stored context and never heals to a third event

The 2026-08-19 user ruling requires every URL-driven cross-event switch to announce itself with a one-click return. app/src/lib/useCurrentEvent.ts honours that only when BOTH ids resolve in /events (:135): it writes the URL id to storage before any validation (:115), and when the URL id does NOT resolve, reconcileStoredEventId heals it to items[0] and persists that (:149-152). A stale, foreign or bookmarked ?eventId= therefore discards event A, lands the organiser on a third event, and shows no banner and no restore() -- the exact silent switch the ruling forbids, reached by the one path the ruling's implementation did not cover. RULED: (a) a URL eventId that does not resolve in the caller's own /events list is never persisted and never heals over a DIFFERENT stored id -- the prior stored context is restored to storage and to state, and the page announces once that the link is not available, naming the event it kept; (b) items[0] remains the fallback only when there was no prior stored context, or the prior stored id is itself unresolvable; (c) when the URL id resolves but the PRIOR id no longer does, the switch is still announced with the target's name and no Back link, because there is nothing left to return to. A banner that requires two names is a banner that goes silent exactly when the user is most lost.

## Amendment (wave 138): D19's pre-overwrite event context is captured ONCE per page load and shared, never re-derived per hook instance

The user's 2026-08-19 ruling requires that a URL eventId overwriting a different stored context announce itself ('Switched to <B> · Back to <A>' with a one-click return). `useCurrentEvent.ts` computes `priorStoredId` from `localStorage` inside each hook instance's own effect and then writes `localStorage[STORAGE_KEY] = fromUrl` in the same pass. `EventSwitchBanner` is its only mount point and is gated behind `useMe()`'s async `/me` round trip (`loading: true` on first commit), while `PhoneTabBar` -> `useNavExceptions` -> `useCurrentEvent` runs on the FIRST commit and performs the write. By the time the banner's own instance reads storage, `fromStorage === fromUrl`, `priorStoredId` is null, and `switchInfo` can never be set — the ruled banner is unreachable in the real app, and only the isolated hook test (which mounts one instance) ever sees it. RULED: the pre-overwrite stored id is read exactly once per document, at module scope, into a module-level constant every `useCurrentEvent` instance reads; `priorStoredId` derives from that constant, so the banner's reachability does not depend on which consumer mounts first. Pinned by a test that mounts a non-banner `useCurrentEvent` consumer first and still renders exactly one banner, plus the existing no-banner case (URL id equal to stored id).


## Amendment (wave 143): The pre-overwrite event snapshot is scoped to a NAVIGATION, not to a document

The wave-138 amendment froze (fromUrl, fromStorage) once per document to defeat a mount-order race: PhoneTabBar's useNavExceptions writes localStorage before EventSwitchBanner (gated behind useMe()) can read the pre-overwrite value, so priorStoredId was unreachable and the D19 ruled banner could never fire. That fix is correct and must be preserved, but it was scoped one level too wide. A document-scoped snapshot is blind to react-router client-side navigation, and three real links carry a new eventId across one: app/src/pages/speakers/RosterPanel.tsx twice ('/contacts?import=1&eventId=…') and app/src/pages/contacts/AddToEventModal.tsx ('View in Speakers'). On those paths the destination renders the PREVIOUS event's data, storage is never updated, and docs/mobile-campaign.md's D19 pin ('differing shows exactly one banner, and the return link restores the prior context') cannot fire at all. The same freeze makes two render tests red on main by leaking one it()'s null snapshot into the next. RULED: the snapshot is keyed on the navigation (location.search), so every hook instance on ONE navigation still shares one pre-overwrite pair -- the wave-138 mount-order guarantee verbatim -- while a new search captures fresh. getInitialStoredId() takes the same scoping, the resolve effect re-runs on search change rather than once, and both test-only reset seams clear the new keyed state.
