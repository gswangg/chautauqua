# DEC-397: A minted claim token is never part of a dedupe identity — the cross-call key is computed on the pre-mint body, normalized identically on both sides

Two fast-tier tests are RED on main 4babe7ac2 (test/contacts-bulk-email-skipped-log.route.test.ts expects {sent:0,skipped:1} and gets {sent:1,skipped:0}; test/contacts-bulk-email-preview-send-agreement.test.ts expects willSend 6/skipped 1 and gets 7/0). Root cause, traced this wave: DEC-936's wave-17 amendment correctly widened the cross-call (stage 2) identity to include the rendered BODY, and src/server/repo/comms.ts's loadRecentlySent keys both the wanted set and each email_log row with dedupeKey(email, subject, body). But src/routes/api/contacts/bulk-email.ts mints a fresh per-recipient claim URL through applyMintedPortalLinks AFTER the preflight render, so email_log.body_text stores a MINTED `{portal_link}` while the next call's dedupe check runs on the UNMINTED render. The two bodies can never be equal for any message spending `{portal_link}` — the window silently never matches, and the skipped-log test's own comment ("renders BYTE-IDENTICAL for every recipient") is falsified by the mint. RULED. The fix is NOT to drop the body term (that re-opens exactly the hole DEC-936 wave-17 closed, where a static subject plus per-submission vars in the body collapses a multi-session speaker). Instead src/domain/comms-dedupe.ts gains ONE exported normalizer that replaces any minted claim URL with a constant placeholder, and dedupeKey applies it to the body before hashing — so BOTH sides of the comparison (the caller's wanted key and loadRecentlySent's row key) normalize through the same single owner and can never re-derive the rule independently. This restates DEC-397's own "A MINT IS THE LAST THING A SEND DOES": the mint is downstream of identity, so identity must not read it. email_log keeps storing the real shipped body — log fidelity is not traded for dedupe stability.

## Amendment (wave 20)

IMPLEMENTED. src/domain/comms-dedupe.ts gained the ONE normalizer (normalizeMintedClaimLinks) called from inside dedupeKey and intraBatchKey — no second copy of the rule anywhere, so every caller (src/server/repo/comms.ts's loadRecentlySent on the row side, src/routes/api/contacts/bulk-email.ts's planBulkEmailSends and src/routes/comms/send.ts's/src/routes/comms/preview.ts's planComposeSends on the candidate side) inherits the same normalization for free — none of those four call sites needed their own edit. The normalizer replaces every `/claim/<token>` path segment (the shape src/server/repo/portal-link.ts mints via src/auth/claim.ts's newClaimToken, and the shape src/domain/compose.ts's fixed PREVIEW_CLAIM_TOKEN already has) with a constant placeholder, leaving the rest of the body — including a static subject's per-submission merge vars — compared verbatim. FAIL LOUDLY: a `/claim/` substring not immediately followed by a token-shaped segment throws rather than silently passing an unnormalized (and therefore permanently unmatchable) claim link through. email_log.body_text itself is NEVER normalized — only the value fed into dedupeKey/intraBatchKey is, so log fidelity is not traded for dedupe stability, exactly as ruled above. Restates the host ruling: the mint is downstream of identity, so identity must not read it.
