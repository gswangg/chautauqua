# DEC-144: Wave-154 amendment: the route manifest carries tab and panel sub-states, derived from the pages' own tab unions

`app/src/routeManifest.ts` has 64 rows and ZERO query-string entries (grepped: no `?tab=`, no panel key). Every tabbed or panelled admin surface is therefore visited by the desktop AND the 390 live pass only at its default tab. Consequences measured against the campaign's own record: the mandate counts NINE Settings width:390 frames (Chautauqua Settings.dc.html :275/:316/:347/:393/:444/:481/:510/:552/:578) and the gate renders at most one of them; `/admin/contacts?tab=pipeline` — the exact surface where meta-probe round 3 found a dock MISSING entirely — is never navigated to, which is why no gate caught it and a human probe had to.

RULED: the sub-state population must be derived from each page's own tab/panel key union (Comms.tsx's `isTab`, Contacts.tsx, Settings.tsx's panel union, ContentApp.tsx, the speakers tabs), never hand-listed, and `routeManifest.test.ts`'s parity check must FAIL when a new key has no row — a hand-listed population is not a population.

## Amendment (wave 27): a route population that stops at a page's DEFAULT query state has never visited the screens its query keys mint

`app/src/routeManifest.ts` is the population every live gate walks — render sweep, overflow probe, tap-floor pass, contrast pass. Waves 154-156 widened it with `?tab=`/`?view=`/`?section=` rows for Content, Comms, Contacts and Settings, which is real progress and is why the field guide's older "zero query sub-states" line is now stale. But I measured the current tree: `edit=1` appears ZERO times in the manifest while `searchParams.get('edit')` is read at TEN SPA sites, and Settings.tsx's own comment rules that "a settings section URL carrying `edit=1` ... is a SCREEN, not a scroll target — only that one panel mounts." So the Settings EDIT screens — seven sections, DESIGN-RULINGS B10's whole ruled surface, and the family DEVIATIONS §6's two deferrals sit inside — have never been visited by any live instrument at either width. Nine more query keys the SPA reads (`import`, `intent`, `keep`, `openContact`, `batch`, `history`, `templateId`, `embed`, `ids`, `page`) are in the same position, unmeasured. RULED: the admissible sub-states are DERIVED from the reader sites and their own closed value sets, never hand-listed, and the unvisited set is rostered under a two-sided ceiling before the manifest is widened — population first, instrument second. The manifest widening is deliberately NOT this wave's act: it would move the live sweep's measured population underneath the roster lane measuring it.

## Amendment (wave 28): the route manifest's sub-state population is derived from its PARAM READERS, and every `?…&edit=1` screen is a member

Wave-154 already ruled tab/panel sub-states into ROUTE_MANIFEST, derived from each page's own tab union. That derivation stopped at `tab`/`section`/`view`. Measured on main at f4629d5a: `searchParams.get('edit') === '1'` is read at ten SPA sites (Settings.tsx, the five settings panels with their own SECTION_KEY, useTracksRoomsPanel.ts, SubmissionDetailPage.tsx) while the string `edit=1` appears ZERO times in app/src/routeManifest.ts. Settings.tsx's own comment rules that URL a SCREEN and DESIGN-RULINGS B10 draws all five Settings edit views as their own desktop frames, so B10's entire edit surface has never been visited by the render sweep, the overflow probe, the tap-floor pass or the contrast pass at either width. RULED: a manifest sub-state population is completed from the READERS of the parameter, never from the fact that someone widened the manifest once; a reader with no row is a gap the parity test must name. The absence of a `public-pages` edit row is evidence the derivation is honest (B10's own DROP says that section has no edit view), not an oversight to patch by hand.

## Amendment (wave 6): the seven `?edit=1` route sub-states are documented in AUDIT.md, and ROUTE_SUBSTATE_UNVISITED_CEILING drops to its measured 3 in the same commit

app/src/routeManifest.ts declares seven sub-states docs/AUDIT.md never mentions (/admin/submissions/:id?edit=1 and six /admin/settings?section=…&edit=1 variants) and audit-claims flags every one. They are real, reachable, organiser-visible states, so the answer is documentation, not an EXCLUDED entry — an exclusion would assert the state does not exist. In the same tree the two-sided companion reports ROUTE_SUBSTATE_UNVISITED_CEILING = 10 stale against a measured 3: earlier waves closed seven gaps and never lowered the constant, which is exactly the stagnation licence the two-sided ratchet exists to prevent. Ruled: AUDIT.md gains a row per sub-state and the ceiling moves 10 → 3 in the same commit that documents them.

## Amendment (wave 23): The route manifest visits its last three derived sub-states; a sub-state no live gate visits is an ungraded screen

This decision's wave-154 amendment makes app/src/routeManifest.ts the exhaustive population every live gate walks — the desktop sweep, the mobile 390 sweep, the overflow probe, the tap-floor pass, the contrast pass. test/route-substate-coverage.scan.test.ts derives, from app/src/pages/** source, every closed-set `searchParams.get('<key>')` sub-state and diffs it against that manifest; ROUTE_SUBSTATE_UNVISITED_CEILING sits at 3 and the scan's own comment names the survivors: `/admin/settings?section=your-data&edit=1&intent=new`, `/admin/contacts?import=1`, and the submission-detail `?history=0` row. docs/design/audit/route-substate-coverage-v12.md states plainly that widening the manifest 'is next wave's act, once this roster exists' — the roster has existed for several waves and no wave has done it. RULED: the three rows land in ROUTE_MANIFEST using seed literals already present in that file (never invented ids), and the ceiling drops to the re-measured value in the same commit. This is the mandate's Tier 2 44px/overflow sweep completing its own population rather than measuring a subset and reporting zero: a screen the gate never opens cannot be conformant, only unexamined.
