# DEC-604 wave-46 amendment: the participant-cap pre-check counts the dispositions the apply path will PERFORM, never every parsed row

src/routes/api/contacts/import.ts's cap pre-check builds `toAddCount` by walking every parsed row's email, ignoring `skipLines` and `mergeLines` - both of which the same handler has already validated (:103-144) and both of which planImportRows and applyImportRows honour (src/server/repo/contacts/import.ts builds a skipLineSet and resolveMergeTargets from them). The consequence is a false refusal: an organiser who has already trimmed the roster with the per-row "Skip this row" control is still told the file would add N participants and exceed the cap, where N counts rows that will never be written. And because the check deliberately sits ABOVE the dryRun branch so the Review step sees the same verdict, the Review step shows the same false refusal - the honesty property the placement was chosen for is what propagates the error. DESIGN-RULINGS' error standard rules that a refusal offers the way out; here the way out has already been taken and the refusal does not notice. RULED: (a) the pre-check's population is the post-disposition population - a line in skipLines contributes nobody; (b) a line in mergeLines contributes its MERGE TARGET contactId, tested against the already-on-roster set, never the file email's own lookup, because merging is what the apply path will do with that line; (c) every other line is unchanged; (d) the check stays above the dryRun branch, so plan and commit keep agreeing by construction; (e) the refusal message and its named exit are unchanged - this amendment corrects who is counted, not what is said.


## Wave-55 amendment: the speaker portal's participant list shows every row the cap counts, each with its status; a declined co-presenter is drawn and actionless, never hidden

Verified live: getPortalParticipants filters on PORTAL_VISIBLE_INVITE_STATUSES while the MAX_PARTICIPANTS_PER_SUBMISSION count and the unique-index duplicate refusal both run over ALL participant rows — so a declined co-presenter is invisible on /portal/submissions/:id/edit yet re-adding them returns CO_PRESENTER_DUPLICATE_MESSAGE and still consumes one of six slots, with no in-portal remedy. DESIGN-RULINGS.md:301 rules the list "is what a speaker checks before typing, and putting it second invites duplicate entries" — a list that omits rows the refusal counts is the same defect the ruling names, one layer down. The fix is a list-only query, NOT a widening of PORTAL_VISIBLE_INVITE_STATUSES: that constant is an ACCESS predicate consumed by files-authz.ts and portal/resources.ts, and widening it would hand a declined contact read access (DEC-317). Visibility in a list and authority over a record are two facts and get two predicates.
