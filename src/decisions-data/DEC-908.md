## Amendment (wave 152): A fixture that predates a fail-loud invariant is a stale claim about the product, and is fixed by supplying the datum — never by softening the throw

test/portal-batched-scope.test.ts's third case fails on main with `listLatestDeliverables: file file-b1 has no stored version_no — data corruption`, thrown from src/server/repo/portal/sessions.ts:287. The throw is CORRECT and is the house rule working: DEC-818's identical guard in files-library-list.ts refuses a file row with no stored `version_no` rather than defaulting it, and src/db/schema/content.ts`versionNo: integer("version_no")` declares it nullable, so a null is genuinely reachable and genuinely means corruption. What is stale is the fixture: buildTwoOrgFixture's `file-b1` row was written before the guard landed and supplies no version_no, so a DEC-962 scoping test — whose subject is WHERE the ownership predicate runs, not what a deliverable contains — now dies on an unrelated invariant. RULING: when a fail-loud invariant lands and an older fixture trips it, the fixture is amended to satisfy the invariant and the assertions are widened to cover the new field; the throw is never relaxed, never try/caught, and never routed around with a nullable default, because that would convert a fail-loud guard into exactly the silent fallback CLAUDE.md forbids. Concretely here: the fixture's file rows gain a real `versionNo`, and the two positive cases that already assert `{ id: "file-b1", filename: "b-slides.pdf" }` extend to assert the resolved `versionNo` too — so the fixture repair leaves a pin behind instead of just restoring green.
