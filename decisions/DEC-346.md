# DEC-346: Plan-scoped submission loads shed `description`, and the reviewer queue's evaluation counts become SQL aggregates; queue PAGINATION stays deferred exactly as DEC-342 ordered it

src/server/repo/review.ts:344 and :355 select submission.description for EVERY submission in the event on both branches of listPlanFilteredSubmissions, which feeds /plans/:id/queue, /progress, /remind, /results and listAssignedSubmissions. No consumer reads it: grep for `description` across src/routes/review/** and src/domain/evaluation.ts returns nothing, and the queue route (src/routes/review/reviewer.ts:102-114) explicitly reshapes to submissionId/ref/title/ratingsCount/alreadyRatedByMe per DEC-239. Only getSubmissionSummaryInEvent (:461), a single-row lookup, legitimately carries description into the reviewer scorecard via `...summary`. So at 2,000 submissions the hottest reviewer-facing endpoints pull megabytes of abstract text out of D1 on every paint and throw it away. Separately, the queue loads every evaluation row of the current round (reviewer.ts:62) — JSON scores blobs included — to compute two numbers. DEC-342 laid out the fix order as (i) replace the whole-round load with a SQL GROUP BY count, (ii) drop description, (iii) only then paginate with Scorecard's traversal changed in the same commit. This decision authorises (i) and (ii) and explicitly keeps (iii) OUT OF SCOPE: buildReviewerQueue prioritises across the whole scoped set and app/src/pages/review/Scorecard.tsx:79 re-reads the queue to advance to the next unrated submission, so a slice would trade a measured non-problem for a real bug. Binding contract: split the type — PlanSubmissionRef { id, ref, title, trackIds } for the whole-set loaders (listPlanFilteredSubmissions, resolveReviewerSubmissions, listAssignedSubmissions), SubmissionSummary extends PlanSubmissionRef { description } for the single-row getSubmissionSummaryInEvent only; add countEvaluationsBySubmission(db, planId, round): Promise<Map<string, number>> and listSubmissionIdsRatedBy(db, planId, round, reviewerId): Promise<Set<string>> as grouped/filtered SQL, and have the queue route use them; listEvaluationsForPlan itself stays for /progress, /remind and /results. Queue ORDERING, the recusal partition and every wire key are unchanged — this is a load-shedding change with no observable behaviour difference, and any test that has to change is evidence the change went too far.

## Amendment (wave 57): a plan-scoped submission load is BOUNDED by a loud MAX_PLAN_SUBMISSION_SCAN refusal, and its track hydration is scoped to the matched set — never a second whole-event scan

`listPlanFilteredSubmissions` (src/server/repo/review/submissions.ts:47-119) runs TWO unbounded whole-event scans on every request to the plan detail, plan progress, plan remind and distribute-preview routes: an unlimited `select ... where submission.event_id = ?`, then an unlimited `submission_track join submission` over the WHOLE event which is then grouped against the matched set in JS. DEC-346 already shed `description` from this load; the row COUNT was never bounded and the track join was never narrowed. Every sibling whole-population read in the repo now refuses rather than truncates (MAX_CONTACT_DIRECTORY_SCAN, MAX_FILE_LIBRARY_SCAN, EXPORT_MAX_ROWS) — this one is the outlier, against SPEC §7's 2,000-submission scale target. The cap is a pathological-data guard set well above the scale target (20,000, mirroring MAX_FILE_LIBRARY_SCAN), not a functional limit; the track read becomes an id-scoped chunked query so its cost is proportional to the matched set, not the event.

## Amendment (wave 62): the plan-wide evaluation and recusal reads get the same ORDER BY + cap+1 + loud refusal their submission sibling already has, and the caller-less listEvaluationsForPlan is deleted rather than left standing

DEC-346's wave-57 amendment capped listPlanFilteredSubmissions at MAX_PLAN_SUBMISSION_SCAN + 1 and made it refuse loudly (src/server/repo/review/submissions.ts:93,105,107). Its two neighbours on the same request never got the rule: listEvaluationScoresForPlan (src/server/repo/review/evaluations.ts:53-59) and listRecusalsForPlan (src/server/repo/review/recusal.ts:122-124) have no LIMIT and no ORDER BY, and GET /api/v1/plans/:id/results calls all three in one handler (src/routes/review/shared.ts:335-362). At SPEC §0's 5,000-submission x 50-reviewer target that pulls an entire round's evaluation table into the isolate per request, against SPEC §7's "admin API reads p95 < 50 ms" — and perf-smoke already measures this exact endpoint (scripts/perf-smoke.ts:705), so the budget is enforced but the query is not. Every other family in the repo already obeys this (exports at EXPORT_MAX_ROWS + 1, agenda at MAX_AGENDA_SCAN + 1, reminders at MAX_REMINDER_SCAN + 1, public at MAX_PUBLIC_ROWS); the review repo is the only outlier. Evaluations are submissions x reviewers, so they need their OWN larger constant rather than borrowing the submission cap. Separately, listEvaluationsForPlan (evaluations.ts:36) has zero production callers in src/ — only a vi.fn mock in test/email-log-null-contact.test.ts:124 keeps it alive; house rule is delete the code, don't cap a corpse.


## Amendment (wave 66): every PLAN-WIDE read of schema.evaluation carries MAX_PLAN_EVALUATION_SCAN — the cap is a property of the population, not of the one function someone measured

Verified on main: listEvaluationScoresForPlan (src/server/repo/review/evaluations.ts:65-93) orders totally and takes `.limit(MAX_PLAN_EVALUATION_SCAN + 1)` with a loud, forward-pathed refusal over the cap. Its sibling listEvaluatedPairsForPlan (:255-272) has the SAME plan+round+submitted WHERE, returns one row per evaluated (reviewer, submission) pair, and has NO `.limit()` and NO refusal. It backs GET /api/v1/plans/:id/progress (src/routes/review/plans-progress.ts:61) and POST /api/v1/plans/:id/remind (:225), so at SPEC §0/§7s scale target (a 2,000-submission event) both routes materialize the whole plans evaluation table into the isolate before the DEC-461(e)-blessed JS slice at :132-134 ever runs — and the blessing at :132 is about slicing an ALREADY-BOUNDED array, which this one is not. The rest of the family is already correct and must stay untouched: countEvaluationsBySubmission is a `group by` aggregate, listSubmissionIdsRatedBy / listEvaluationScoresForReviewer are per-reviewer, listEvaluationsForSubmission is per-submission. RULING: listEvaluatedPairsForPlan takes a deterministic order and `.limit(MAX_PLAN_EVALUATION_SCAN + 1)` and throws the same ApiError("invalid", ...) shape as its sibling, naming the cap and the way out (narrow the plans track filter). A scan test owns the population going forward: every `.from(schema.evaluation)` select in src/server/repo/review/**.ts whose WHERE is plan-scoped but NOT reviewer- or submission-scoped must mention MAX_PLAN_EVALUATION_SCAN in the same function body — so the next sibling added to this file cannot ship uncapped, and the scan asserts it found more than one such function (a scan whose population is one file is a scan that proves nothing).

## Amendment (wave 18): two readers of the same rows carry the same bound, and a comment that claims a bound its callee does not have is a defect

isSubmissionInReviewerScope (src/server/repo/review/submissions.ts:396) reads a reviewer's plan_reviewer rows with a bare `.select()` — every column, no order, no LIMIT — while resolveReviewerSubmissions in the SAME file (:241-252) caps the identical read at MAX_REVIEWER_SCOPE_ROWS + 1 and refuses past it. The file's own header asserts "the two readers never disagree"; today past the cap the queue refuses while GET/PUT of a single submission still succeeds, and an unbounded scan sits on the review hot path SPEC §7 budgets at p95 < 50 ms. Separately, countEvaluationsBySubmission (evaluations.ts:168-190) has no LIMIT on its GROUP BY, and reviewer.ts:139-144 describes it as "restricted to this reviewer's already-scoped submission ids" — which its own DEC-449 contract explicitly denies. RULE: the per-submission scope check adopts the sibling's cap, ordering and literal refusal message; the grouped count adopts the MAX_PLAN_EVALUATION_SCAN ceiling already exported beside it (strictly larger than the submission cap, so it can only fire where the submission scan already refuses); DEC-449's one-round-trip shape is preserved — no id-list parameter, no chunking — and the false comment is rewritten to the real contract. A knob table that drifts by comment is prose, not a contract.

## Amendment (wave 22): a LIMIT after GROUP BY caps groups, not rows -- the grouped read declares the cap it can actually enforce

src/server/repo/review/evaluations.ts:186-193 applies `.limit(MAX_PLAN_EVALUATION_SCAN + 1)` AFTER `.groupBy(evaluation.submissionId)` and then refuses with "This plan would scan more than 50000 evaluations". The LIMIT bounds distinct submissions, not evaluation rows, and a plan's distinct submissions are already bounded by SPEC's 5,000-per-event ceiling -- so the guard is unreachable and its message is false. The ungrouped sibling `listEvaluationScoresForPlan` (:87) applies the same constant where it genuinely bounds rows and genuinely refuses, which means at scale the reviewer queue and the organiser results page disagree about which plan is too large. Ruling: the grouped read declares a GROUP cap sized to the submission population it actually returns (`MAX_PLAN_SUBMISSION_SCAN`, already exported from src/server/repo/review/submissions.ts) and refuses in the vocabulary of submissions; the row cap stays where it can fire. The comment at src/routes/review/reviewer.ts:143-147 -- which claims the counts query is "restricted to this reviewer's already-scoped submission ids" when `countEvaluationsBySubmission(db, planId, round)` takes no id list -- is corrected to state the DEC-449-blessed truth: a whole plan+round map, read only via `.get(id)` for ids in the reviewer's own scope, bounded by the group cap.

## Amendment (wave 74): a queue that empties for a reason names the reason — the reviewer envelope carries `cappedOut`

Once DEC-707's wave-74 amendment lands, a reviewer's queue can be legitimately empty while submissions remain in their scope, because other reviewers filled the cap first. An empty list with no sentence is indistinguishable from a broken assignment — it is the same defect class as the out-of-queue bare "Submission not found" this codebase already fixed by naming the reason. RULING: the queue envelope gains `cappedOut: number` — the count of submissions in this reviewer's own scope, not recused, that the cap filter removed (`scopedActionable.length - queueItems.length`, both arrays already in hand at `src/routes/review/reviewer.ts:235-242`; no new query, and the closed-plan early return at `:171` reports 0). The SPA's empty/short queue state states it in the reviewer's own words, and the PUT's existing 409 copy (`reviewer.ts:524`) is aligned to the same sentence so the two surfaces cannot contradict each other. This is a display/refusal-copy decision only: the cap predicate itself is unchanged and stays `needsMoreRatings`.
