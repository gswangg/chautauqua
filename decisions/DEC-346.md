# DEC-346: Plan-scoped submission loads shed `description`, and the reviewer queue's evaluation counts become SQL aggregates; queue PAGINATION stays deferred exactly as DEC-342 ordered it

src/server/repo/review.ts:344 and :355 select submission.description for EVERY submission in the event on both branches of listPlanFilteredSubmissions, which feeds /plans/:id/queue, /progress, /remind, /results and listAssignedSubmissions. No consumer reads it: grep for `description` across src/routes/review/** and src/domain/evaluation.ts returns nothing, and the queue route (src/routes/review/reviewer.ts:102-114) explicitly reshapes to submissionId/ref/title/ratingsCount/alreadyRatedByMe per DEC-239. Only getSubmissionSummaryInEvent (:461), a single-row lookup, legitimately carries description into the reviewer scorecard via `...summary`. So at 2,000 submissions the hottest reviewer-facing endpoints pull megabytes of abstract text out of D1 on every paint and throw it away. Separately, the queue loads every evaluation row of the current round (reviewer.ts:62) — JSON scores blobs included — to compute two numbers. DEC-342 laid out the fix order as (i) replace the whole-round load with a SQL GROUP BY count, (ii) drop description, (iii) only then paginate with Scorecard's traversal changed in the same commit. This decision authorises (i) and (ii) and explicitly keeps (iii) OUT OF SCOPE: buildReviewerQueue prioritises across the whole scoped set and app/src/pages/review/Scorecard.tsx:79 re-reads the queue to advance to the next unrated submission, so a slice would trade a measured non-problem for a real bug. Binding contract: split the type — PlanSubmissionRef { id, ref, title, trackIds } for the whole-set loaders (listPlanFilteredSubmissions, resolveReviewerSubmissions, listAssignedSubmissions), SubmissionSummary extends PlanSubmissionRef { description } for the single-row getSubmissionSummaryInEvent only; add countEvaluationsBySubmission(db, planId, round): Promise<Map<string, number>> and listSubmissionIdsRatedBy(db, planId, round, reviewerId): Promise<Set<string>> as grouped/filtered SQL, and have the queue route use them; listEvaluationsForPlan itself stays for /progress, /remind and /results. Queue ORDERING, the recusal partition and every wire key are unchanged — this is a load-shedding change with no observable behaviour difference, and any test that has to change is evidence the change went too far.

## Amendment (wave 57): a plan-scoped submission load is BOUNDED by a loud MAX_PLAN_SUBMISSION_SCAN refusal, and its track hydration is scoped to the matched set — never a second whole-event scan

`listPlanFilteredSubmissions` (src/server/repo/review/submissions.ts:47-119) runs TWO unbounded whole-event scans on every request to the plan detail, plan progress, plan remind and distribute-preview routes: an unlimited `select ... where submission.event_id = ?`, then an unlimited `submission_track join submission` over the WHOLE event which is then grouped against the matched set in JS. DEC-346 already shed `description` from this load; the row COUNT was never bounded and the track join was never narrowed. Every sibling whole-population read in the repo now refuses rather than truncates (MAX_CONTACT_DIRECTORY_SCAN, MAX_FILE_LIBRARY_SCAN, EXPORT_MAX_ROWS) — this one is the outlier, against SPEC §7's 2,000-submission scale target. The cap is a pathological-data guard set well above the scale target (20,000, mirroring MAX_FILE_LIBRARY_SCAN), not a functional limit; the track read becomes an id-scoped chunked query so its cost is proportional to the matched set, not the event.

## Amendment (wave 62): the plan-wide evaluation and recusal reads get the same ORDER BY + cap+1 + loud refusal their submission sibling already has, and the caller-less listEvaluationsForPlan is deleted rather than left standing

DEC-346's wave-57 amendment capped listPlanFilteredSubmissions at MAX_PLAN_SUBMISSION_SCAN + 1 and made it refuse loudly (src/server/repo/review/submissions.ts:93,105,107). Its two neighbours on the same request never got the rule: listEvaluationScoresForPlan (src/server/repo/review/evaluations.ts:53-59) and listRecusalsForPlan (src/server/repo/review/recusal.ts:122-124) have no LIMIT and no ORDER BY, and GET /api/v1/plans/:id/results calls all three in one handler (src/routes/review/shared.ts:335-362). At SPEC §0's 5,000-submission x 50-reviewer target that pulls an entire round's evaluation table into the isolate per request, against SPEC §7's "admin API reads p95 < 50 ms" — and perf-smoke already measures this exact endpoint (scripts/perf-smoke.ts:705), so the budget is enforced but the query is not. Every other family in the repo already obeys this (exports at EXPORT_MAX_ROWS + 1, agenda at MAX_AGENDA_SCAN + 1, reminders at MAX_REMINDER_SCAN + 1, public at MAX_PUBLIC_ROWS); the review repo is the only outlier. Evaluations are submissions x reviewers, so they need their OWN larger constant rather than borrowing the submission cap. Separately, listEvaluationsForPlan (evaluations.ts:36) has zero production callers in src/ — only a vi.fn mock in test/email-log-null-contact.test.ts:124 keeps it alive; house rule is delete the code, don't cap a corpse.
