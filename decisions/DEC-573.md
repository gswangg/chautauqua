# DEC-573: A file comment thread belongs to the version CHAIN, not to one file row; the comment list carries an envelope

listFileComments(db, fileId) selects on file_comment.file_id alone. A re-upload creates a new file row (previous_file_id → old), so every comment the producer wrote ("please use the event template") disappears the moment the speaker acts on it — confirmed server-side, and it is the exact opposite of J8's "comment thread per deliverable" plus "history complete". Comments are therefore read across the whole chain: resolve the chain (walk back via previous_file_id to the root, then forward through rows whose previous_file_id points at the current one — cycle-guarded, throwing on a missing row, as resolveTaskFileChainLatest already does), then read every comment on every file in it in one time order, each row tagged with the version it was written against. Writes still anchor on the latest file id, so the portal and the organiser surfaces keep landing in the same thread (DEC-244). While the read is being rewritten it also gains the product's ONE list shape ({items,total,page,perPage}) — it was flagged UNBOUNDED in the w20/w21 envelope enumerations and a thread is exactly the list that grows.
