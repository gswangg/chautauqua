# DEC-040: Form-answer file uploads: file rows kind 'attachment', answer = file id

J1 promises a file question type, but the public form posts without enctype and extractAnswers stringifies File objects, so file answers are silently broken. Design: the submit form posts multipart/form-data; file-kind answers upload only at final submit (KV drafts never persist file selections); each upload is validated with validateUpload (src/domain/files.ts allowlist + size caps, stated in the UI), stored via makeFileStore under a random key, and recorded as a file row with kind 'attachment', submissionId, and uploadedByContactId; the submission_answer value is the file.id string that forms/validate.ts already expects. Serving goes through the existing authenticated /files route — never a new unauthenticated path. 'attachment' joins presentation/poster/handout/headshot as the fifth file.kind.

## Amendment (wave 70): a form surface that RENDERS a file field must POST multipart and store a real file — the rule is per rendering surface, not per route

DEC-040's own opening sentence is "the public form posts without enctype and extractAnswers stringifies File objects, so file answers are silently broken" — and it fixed exactly one form. src/routes/portal/tasks/views.tsx:252 (TaskFormPage) posts without enctype while rendering FormFieldsSection, which emits <input type="file"> for a file-kind field (src/views/form-render.tsx:103). The browser urlencodes the FILENAME; tasks.tsx:342 coerces it with String(raw); validate.ts:155 accepts any non-empty string as a "file id"; tasks.tsx:367 marks the assignment complete. J6/clarifications name hotel-stay and flight-reimbursement forms as must-haves and they are exactly this task kind. Ruling: every surface that renders a FormFieldDef posts multipart/form-data and runs the same extractFileAnswers -> validateUpload -> putThenRecord -> insertFile pipeline the CFP runs; the answer is the minted file id, never a filename. On the portal task form the file row is submissionId:null, kind 'handout' (the same shape the file_request 'else' branch already uses), so it never joins a submission's deliverable-authz population. An EMPTY file part is silence, not a clear — a file input cannot be pre-populated, so a re-submit with no new selection carries the previously stored file id forward (this is the one deliberate exception to "submitted blank CLEARS"). FormTaskFieldKind widens to include 'file' and the comment claiming there is no upload path is deleted rather than left as a lie.


## Amendment (wave 6): a pipeline that mirrors the CFP submit path must mirror its ROLLBACK, not only its ordering

src/routes/portal/tasks.tsx:365-403 documents itself as mirroring the public CFP submit pipeline, and it copies the ordering faithfully — one putThenRecord per file field, answers written before validateAnswers so required checks see them. It does not copy the other half: src/routes/public/submit.tsx:573-580 explicitly rolls back both the R2 keys and the submission when validation fails, while the portal's 400 re-render (tasks.tsx:407-425) returns with every already-uploaded object and `file` row still committed. A multi-field form where one field fails therefore leaks an R2 object plus a DB row per attempt, permanently and invisibly, because the response the speaker sees is an error. Half a write is not a draft. Ruling: the portal form-task submit accumulates {r2Key, fileId} for every file it writes in the request and, on the 400 path only, deletes those R2 objects and file rows before rendering — the happy path is byte-identical, and the rollback is scoped to THIS request's writes (never to a carried-forward prior file id).

## Amendment (wave 78): replacing a file answer on a kind='form' task CHAINS the previous upload, never orphans it

src/routes/portal/tasks.tsx:411-427 writes every new form-field file with previousFileId: null and then overwrites answers[field.id] with the new id. The prior file row survives with its task_assignment_id grant and its R2 object, referenced by nothing and reachable through nothing — the wave-74 rollback block (:444-456) deliberately only cleans up files THIS request wrote, so it never touches it. That is the same act the /upload path already models correctly (DEC-922 chain-or-restart, :591-600) done wrong one route over. Ruling: a re-answered file field is a NEW VERSION of the same answer, not a new document — chain previousFileId onto the prior answer's file id whenever that file is a legitimate predecessor (submissionId null and the same kind, mirroring isValidVersionChain), and start a fresh chain rather than 400 when it is not. History complete beats storage reclaimed: we do not delete the superseded row, we make it reachable.
