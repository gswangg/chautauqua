# DEC-687: A function embedded in a page by .toString() carries no closure: every free identifier travels with it, and the emitted script is proved by EXECUTING it

Verified on main: src/lib/itinerary.ts:66-81 `mergeItinerarySelection` ends in `merged.slice(0, MAX_ITINERARY_IDS)`, referencing a module constant declared at :11 — and src/routes/public/agenda.tsx:281-283 embeds that function into the page as `var __chqMerge = (${mergeItinerarySelection.toString()});` without ever emitting `MAX_ITINERARY_IDS`. `.toString()` serializes a function's TEXT, never its scope, so the first change event throws ReferenceError inside `__chqMerge` before `localStorage.setItem(key, ...)` at :352 ever runs. Every pick is lost on reload while ScheduleContent (:368) tells the visitor "Your picks are saved in this browser and survive a reload" — the judge's EMB-10/11 CRITICAL, a data-loss path plus dishonest copy. Every existing test of this machinery tests the TypeScript functions, which is exactly why a two-year-old contract passed while the shipped script was dead on the first click. The rule: a server-emitted browser script is only proven by running the emitted TEXT, and any identifier the embedded function is free in must be emitted beside it in the same IIFE. The same rule covers the sibling `mirrorItineraryCheckboxes` embed and any future `.toString()` embed.
