# DEC-548: The public agenda is a bounded query like every other public list: ?day= filters in SQL, the scan carries LIMIT + a truthful COUNT, and its ORDER BY totally orders the row

getPublicAgenda (src/server/repo/public/agenda.ts:29-41) is the last public query with no .limit() — its sessions/speakers siblings are choked through boundedRowLimit/boundedWindow against MAX_PUBLIC_ROWS (src/server/repo/public/bounds.ts). Worse, the ?day= filter that DEC-489 added is applied in JavaScript AFTER the whole-event scan, in all three consumers (dispatch.tsx:93,98 and index.tsx:297), so asking for one day of a five-day event still pays a full slot scan plus ~4×ceil(N/90) hydration round trips on every cache miss — for /e/:slug/agenda, /e/:slug/schedule, /e/:slug/agenda.ics and /embed/:slug/agenda.json alike. SPEC §7 names oversized/unbounded reads a bug at the 2,000-row scale target, not a tuning opportunity. And the ORDER BY is (day, startMin) only, which does not totally order the selectDistinct tuple — the moment a LIMIT exists, an underdetermined sort makes the truncation point nondeterministic (the DEC-534 lesson). Decision: (a) `getPublicAgenda(db, event, params?: { day?: string | null })` returns `{ items, total }`: the day predicate moves into the WHERE, the scan gets `.limit(MAX_PUBLIC_ROWS)`, and `total` is the true unwindowed count of the same filtered join (counted over the selectDistinct as a subquery, so it is the count of rows the surface would render, not of join hits). (b) The ORDER BY totally orders the distinct tuple: day, startMin, submissionId, endMin, roomId. (c) A cap the UI cannot see LIES (standing rule), so the HTML agenda/schedule render an honest one-line notice whenever items.length < total, and the .json envelope reports the true `total` against `items.length` — DEC-484's whole purpose is letting a consumer detect truncation. (d) getPublicAgendaByIds is untouched: it is already id-scoped and chunked (DEC-310), and MAX_ITINERARY_IDS already bounds it.
