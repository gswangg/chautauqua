# DEC-283: 'Assign to all accepted' means all ACTIVE participants of accepted submissions -- DEC-278's invite gate applies to the task-creation expansion too

DEC-278 landed (status.ts:133 filters participants through isActiveParticipant so an 'invited' or 'declined' co-speaker is never auto-assigned onboarding tasks), but its twin path did not: listAcceptedContactIds (src/server/repo/tasks.ts:263-270) still returns every participant of every accepted submission with no invite filter, and it is the expansion target for createTask({assignToAllAccepted:true}) (:318-321). So the moment a producer adds one new event-wide task, the co-speaker who declined the invitation reappears on the who-owes-me-what grid owing a hotel form -- the exact falsehood DEC-278 was written to remove, reintroduced by a different door. One rule, one gate: ACTIVE_INVITE_STATUSES / isActiveParticipant (src/domain/acceptance.ts:80-84) is the sole definition of 'is a speaker on this session', and every roster expansion reads it. Filter in application code after selecting invite_status (mirroring status.ts:129-133) rather than in SQL, so the rule is testable against the repo layer's fakeDb harness, which cannot evaluate a WHERE clause; the row set is bounded by the participants of accepted submissions (hundreds at scale target), so there is no volume cost.
