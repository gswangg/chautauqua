# DEC-592: A public session's Format is the answer to one named form field, and an event without that field renders no Format row

EMB-01 and EMB-08 both require Format on public session cards and on the agenda drill-in, and the .json payload has no format key either. There is no format column in the former src/db/schema.ts (now split across src/db/schema/) — session format is a form answer, created by the seed as the literal id 'field_session_format'. Rather than sniff labels (hand-copied vocabularies drift) or add a migration, name the id once: SESSION_FORMAT_FIELD_ID in src/forms/types.ts, imported by scripts/seed.ts (killing its hand-copied literal) and by the public repo, which hydrates it in one batched query alongside tracks. When the event's default form has no such field the value is null and the surface renders nothing — never a labelled blank, per the copy rule against asserting what no endpoint stores.

## Amendment (findings wave 10): a form field's ROLE — not a global literal id — identifies session format and audience level

Verified on main: form_field.id is a GLOBAL primary key (src/db/schema/event.ts:58-85), yet SESSION_FORMAT_FIELD_ID='field_session_format' (src/forms/types.ts:93) and AUDIENCE_LEVEL_FIELD_ID='field_audience_level' (:101) are fixed literals created ONLY by scripts/seed.ts:478. createDefaultForm (src/server/repo/forms.ts:208-246) seeds locked fields only and createField mints a random id (:332), so the constant is unsatisfiable on any event created through J1 — a literal id can exist on exactly one event, forever. Consequence, all read off the tree: the public card/agenda format line and ?format= chips are permanently empty (src/server/repo/public/sessions.ts:85,479), the Home hub's format count is 0 (public/home.ts:141), the reviewer queue's format/audienceLevel are always null (review/submissions.ts:758), auto-schedule always falls back to defaultDurationMin (agenda/rows.ts:229), and POST /api/v1/events/:id/submissions {format} hard-400s 'This event's form has no session format field' (routes/api/submissions.ts:147-152) with no configurable path — while DESIGN-RULINGS A5 and A7 both require a format select. RULING: fix the IDENTITY, not each read site. Add a nullable column form_field.role with values 'session_format' | 'audience_level' (NULL for every other field); createDefaultForm mints both fields with ordinary ids and a role; role becomes the ONE matcher everywhere, expressed as an EXISTS join from submission_answer to form_field so it also works for the cross-event Home query that has no single form in scope. The literal constants are DELETED, not kept as fallbacks (house rule: no back-compat shims) — the seed carries a seed-local id and the same role. Deleting the field stays legal: DEC-592's original 'an event without that field renders no Format row' is unchanged, and the builder must never clear a role when a field is edited. No new index: the EXISTS join keys on form_field's primary key.

## Amendment (findings wave 12)

w10-a landed the mechanism — the form_field.role column (migrations/0038_form_field_role.sql), FORM_FIELD_ROLES in src/forms/types.ts:21, the role-keyed helpers in src/server/repo/form-roles.ts, role tags on both minting paths (scripts/seed.ts:479-480 and createDefaultForm at src/server/repo/forms.ts:234ff) — and explicitly deferred the read-site conversion to a lane that has not landed (three files still carry the literal TODO: forms/types.ts:20, server/repo/form-roles.ts:6, server/repo/forms.ts:236, and no task-w10-b ref exists in .git/refs/heads). The consequence is live on main: SESSION_FORMAT_FIELD_ID = "field_session_format" is a fixed global-PK literal that only the seed satisfies, so on any event created through J1 the public card's format line and ?format= chips are empty, the reviewer queue's format is null, auto-schedule falls back to the default duration, and POST /api/v1/events/:id/submissions {format} hard-400s "This event's form has no session format field".

RULING: every read site keys on role via answerFieldRoleCondition('session_format'|'audience_level') (a drop-in for eq(submissionAnswer.formFieldId, LITERAL)) and every write/resolve site via getEventFieldIdByRole / getFieldOptionsByRole; the FormFieldDef render layer matches on `role`, not on id. The literals stay exported as the ids the seed and createDefaultForm mint, and their "read sites resolve on this" comments are deleted, not amended. No migration, no schema change.

## Amendment (findings wave 13): a form_field role is a two-way door — the builder can grant and clear it, and a role-tagged field cannot be deleted out from under its readers

w10-b converted ~14 read sites to resolve session_format/audience_level by role and deleted the literal ids; createDefaultForm (src/server/repo/forms.ts:240-267) and scripts/seed.ts:481-482 now mint both role-tagged fields. But src/routes/api/forms.ts contains the string 'role' ZERO times: the field API neither accepts nor clears it. Those two fields are minted `locked:false` precisely so an organiser may rename or remove them — so DELETE /api/v1/fields/:fieldId will happily remove the only session_format-role field on an event, after which the public ?format= facet, the reviewer queue's format, auto-schedule's duration heuristic, the New-submission Format select and POST/PATCH submissions {format} are all permanently dead with NO path back: role has exactly one minting site and it only runs at form creation. A capability with one door in and no door back is not a configuration, it is a trap. RULING: PATCH /api/v1/fields/:fieldId accepts `role` (null | 'session_format' | 'audience_level'), enforcing (i) kind must be 'dropdown' and section 'session' for a field that carries or is being given a role, and a kind/section change is refused while a role is set, (ii) at most ONE field per (form, role) — a grant that would create a second is a 400 keyed `role` naming the field that already holds it. DELETE of a role-tagged field is refused with a 400 keyed `role` that names the consequence and the way forward ('clear its role first'), the same shape deleteTrack/deleteRoom already use for in-use rows. No migration, no schema change — the column exists (migrations/0038_form_field_role.sql).

## Amendment (wave 18): answerFieldRoleCondition is answer-set-scoped BY CONTRACT — the missing event join is deliberate (dismissal, no code change)

A reviewer-lens finding reads answerFieldRoleCondition (src/server/repo/form-roles.ts:16) as a leak because it carries no form.eventId/isDefault join, unlike its two siblings at :22 and :35. Verified against main and DISMISSED: all eight call sites hand it an answer set already narrowed to specific submission ids of one event (public/sessions.ts:478, agenda/rows.ts, overview.ts, portal/*, review/submissions.ts), a submission's answers reference its own form's fields, and DEC-592 already enforces at most one field per (form, role) at the write door (src/routes/api/forms.ts:286-293), so the per-submission result is single-valued. Scoping it to the event's DEFAULT form would be a regression, not a fix: a submission made through a non-default form would lose its format/audience label entirely on public cards, agenda, review and portal. The two siblings are default-form resolvers by design (they answer "what options does this event offer"), this one is an answer matcher ("what did THIS submission answer") — different questions, different scoping. Recorded so it is not re-filed.

## Amendment (wave 80): a role-tagged answer has ONE resolver, and any COUNT of role answers must count exactly what that resolver yields

Verified on main: the two-line ladder `const parsed: unknown = JSON.parse(r.valueJson); ... typeof parsed === "string" && parsed.length > 0 ? parsed : null` is copied byte-identically into seven places — overview.ts:552-555, review/submissions.ts:857-860 and :899-902, public/sessions.ts:485-488, portal/submissions.ts:71-74, portal/data.ts:357-358, agenda/rows.ts:318-321 — each building the same Map from the same role-filtered `submission_answer` query. This repo already ruled that answer-TO-TEXT gets one owner (DEC-561, src/domain/answer-text.ts); the role-answer path never got one. The duplication has already produced its first divergence, and it is written in SQL: public/home.ts:134 computes the hub's format count as `count(distinct submissionAnswer.valueJson)`, which counts stored `""` and non-string answers that all seven readers map to null — so the root page's "N formats" shape line can exceed the number of formats any session on that event actually shows. RULING: `src/server/repo/form-roles.ts` — which already owns `answerFieldRoleCondition`, the other half of this read — becomes the owner, exporting `roleAnswerLabel(valueJson)` and `roleAnswerMap(rows)`. All seven sites spend it; the hub aggregate is narrowed to count exactly the set `roleAnswerLabel` yields non-null for. This grammar is deliberately NOT `answerDisplayText`'s: a role answer is a stored label, never a Yes/No or a joined array, and the new scan must not collide with `answer-text-single-source.scan.test.ts`'s detector.
