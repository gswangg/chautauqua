# DEC-843: A list and the export beside it read status through ONE reader, and an unknown token is loud on both

VERIFIED, and it is DEC-649's own rule broken in both directions: src/server/repo/submissions/query.ts:47-52 silently drops unknown status tokens (?status=aproved returns EVERY status), while src/routes/api/exports.ts:86-91 validates each repeated token with isValidStatusLiteral and 400s; and the list route (src/routes/api/submissions.ts:141) reads c.req.query() — ONE value per key — while the export reads c.req.queries('status') — ALL values. So ?status=accepted&status=declined exports a different row set than the list it claims to mirror, and a typo silently widens the list to everything. Decision: one exported reader in query.ts, readStatusTokens(raw: string | string[] | undefined), accepts repeated params AND comma-separated tokens, trims, dedupes, and throws on any token outside SUBMISSION_STATUSES; parseListQuery takes that shape; both routes call it and both answer 400 "Unknown status '<token>'". Fail-loudly beats graceful degradation here because a filter that silently returns rows you did not ask for is a lie about what is on screen, and because DEC-649 makes the export the list's WHERE clause — two parsers guarantee they drift.

## Amendment (wave 38): loudness is a property of the FILTER, not of the `status` param

DEC-843 made an unknown `status` token throw so a typo can never silently widen a list, and DEC-881 gave `reuploaded` the same treatment. `contentStatus` did not get it: src/server/repo/submissions/query.ts:112-115 drops unrecognised tokens with .filter(), so ?contentStatus=aproved returns every content status — on the one filter that decides public visibility (SPEC J10 "only accepted + visible + content-approved"), across both the admin list and the CSV export that shares parseListQuery (src/routes/api/exports.ts:17). src/routes/files.ts:230-239 parseKinds has the same hole and a comment citing the pre-DEC-843 behaviour as precedent. A rule that names one parameter will be re-broken by the next parameter, so the ruling is the class plus an enumerating scan: every query-token parser under src/ throws on a token outside its vocabulary, and a scan names them all.
