# DEC-903: A drag handle drags — the field list joins the app's ONE drag contract, and a disabled row looks disabled

app/src/pages/forms/FieldList.tsx:143-159 renders a ⋮⋮ drag handle that is keyboard-only: ArrowUp/ArrowDown call onMove, and pointer drag does nothing at all, so the builder shows a drag affordance that is inert to the gesture it depicts. The app already owns a drag contract (app/src/pages/agenda/DayGrid.tsx sets the moved entity's id in text/plain on dragstart and reads it on drop; DEC-898 extends the same contract to the pipeline board) — a third surface inventing a third idiom is how vocabularies desync. Rule: field rows become drag sources and drop targets on that exact contract, and the drop calls the SAME onMove(field, delta) the keyboard path calls, so there is ONE reorder write path and one optimistic update; the keyboard path is KEPT (a drag-only list is unreachable for some organizers); locked/built-in rows are neither draggable nor drop targets. Separately, disabled Edit/Delete/handle currently render identical to enabled controls — a disabled control that looks live is a promise the row cannot keep — so forms.css gives the disabled state a visible treatment, and the builder's header row aligns to the same var(--chq-measure) column as the field list so Preview/Save stop floating over dead space.
