# DEC-725: The Airtable push is incremental from a stored watermark, and a rate-limited response backs off instead of throwing

runAirtableSync re-pushes the org's entire contact and submission tables with a fresh SyncedAt on every 15-minute tick. At SPEC §0 scale that is hundreds of sequential calls per tick, and — worse than the cost — it re-fires every 'record updated' automation on every row, the exact opposite of the customer's stated use in docs/clarifications.md ('automations that happen once a new row lands'). A 429 currently just throws, so a rate limit becomes a failed tick. The correction is the standard shape for a periodic one-way push: a watermark per org in KV, both selects filtered to rows changed since it, the tick's clock written back on success, and a bounded Retry-After backoff inside the batch loop. A missing watermark means a full push, which is exactly right for the first sync and for a restore, so the incremental path needs no separate bootstrap.

## Amendment (wave 57): the Airtable tick is incremental from a KV watermark with a bounded Retry-After backoff, and EVERY read in the tick carries the MAX_SYNC_ROWS refusal and a deterministic order

DEC-725 is a decision with no code: `src/sync/airtable.ts` still re-pushes the org's entire contact and submission tables with a fresh SyncedAt on every tick (re-firing the customer's 'new row lands' automations on every row — the opposite of docs/clarifications.md's stated use), and `upsertBatches` throws on any non-ok response, so a 429 is a failed tick. Reading the module also exposes two smaller inconsistencies one level down from work already done: the participant join carries an explicit orderBy precisely so an unchanged submission never re-upserts with a permuted Speakers string, but the submission_track join has NO orderBy (the Tracks cell can permute between runs and fire automations on a non-change), and neither join carries the MAX_SYNC_ROWS+1 refusal that the contact and submission reads do. One watermark key per org in KV; a missing watermark means a full push (right for first sync and for restore, so no separate bootstrap); the watermark advances only when the whole tick succeeded, so a failed push is retried rather than skipped. This is sync CODE, not stage-2 provisioning: no network in tests (fetch is already injected), no secrets, nothing deployed.

## Amendment (wave 63): submission.updated_at is the whole record's change stamp — every participant and track write touches its submission

DEC-725's incremental Airtable push selects submissions by `submission.updated_at > mark`, and DEC-981 requires that a declined co-presenter never appear in the customer's Speakers cell. Both are defeated by the same fact: participant writes (src/server/repo/participants.ts insert/visible/invite-status/remove, portal-edit's addCoPresenter) and submission_track writes bump only their own row's updated_at. So on any org with a watermark, adding a co-speaker, removing one, or declining one leaves the submission out of the next tick's `subs` set forever, and the customer's base keeps publishing the speaker DEC-981 was written to remove. The same lie is visible in-product: src/server/repo/overview.ts orders the producer's awaiting-approval worklist by `desc(submission.updated_at)`, so a session whose speaker list just changed does not move. An EXISTS-over-dependents predicate cannot fix it, because the destructive cases are DELETEs with nothing left to select. Rule: the submission is the sync/recency unit, so every writer of a table the submission's published shape is composed from touches the submission row's updated_at in the same operation, through one shared `touchSubmissions` helper (chunked, set-based, never a per-row update).


## Amendment (wave 27): an external Retry-After is clamped before it can pause the cron

DEC-725 bounds retry ATTEMPTS but never wait DURATION: `Number.isFinite(retryAfterSeconds) ? retryAfterSeconds * 1000 : ...` accepts 86400 (blocking handleScheduled for a day, killing the same tick that runs reminders) and accepts negatives as 'finite'. A third party's header is untrusted input like any other: parse it, require finite and >= 0, clamp to a module constant, and fall back to the existing exponential when it fails any of those.

## Amendment (wave 30): touch-on-write covers the DENORMALISED strings too — a contact or track rename bumps every submission whose pushed cell contains it

src/server/repo/submissions/touch.ts already exists and its own header names the rule: the incremental Airtable watermark (`gt(submission.updatedAt, mark)`) only re-pushes a submission whose row was touched, so every writer of a table the pushed shape is composed from owes it a touch. participant and submission_track writers comply; the CONTACT and TRACK name writers do not — src/server/repo/profile.ts's updateContactProfile, src/server/repo/portal-edit.ts's contact update (~:287), the organizer contact patch, src/server/repo/contacts/import.ts's flushContactUpdates and src/server/repo/events.ts's updateTrack all change the exact strings src/sync/airtable.ts:303-304 denormalises into the Speakers/Tracks cells, and none of them touches the submission. The customer's base then keeps the old name indefinitely — the failure mode touch.ts claims to have closed. The touch stays ON WRITE and set-based (never an EXISTS predicate in airtable.ts, which cannot see a delete), and the two new helpers resolve the dependent submission ids by subquery so a 200-row CSV rename is still one chunked UPDATE per chunk.

## Amendment (wave 33): a dependent stamp is bounded by a REAL change to the pushed string, at every writer that already holds the pre-write value

The wave-30/32 amendment correctly made contact and track renames re-stamp their dependent submissions, but the call sites fire on writes that changed nothing. flushContactUpdates (src/server/repo/contacts/import.ts:171-198) stamps every id in every chunk of an import's update set, so re-uploading an unchanged CSV bumps every dependent submission; updateTrack (src/server/repo/events.ts:337-365) stamps whenever `name` is merely PRESENT in the payload, so a colour-only PATCH that re-sends the same name stamps the whole track, even though it already holds the old name in `existing`; updateContactProfile (src/server/repo/profile.ts:125-145) stamps unconditionally, so a bio-only portal save fans out even though bio is not in the pushed Speakers cell. Both readers that touch.ts's own header names are harmed: the Airtable tick re-pushes byte-identical strings (against DEC-450's determinism rule), and — worse — src/server/repo/overview.ts:284 orders the producer's worklist `desc(submission.updatedAt)` with `limit(ROW_CAP)` where ROW_CAP is 5, so one bulk import EVICTS every genuinely-awaiting item from Overview's first screen. That is a direct hit on SPEC §2.3 'nothing falls through the cracks'. RULING: the stamp is fired only for ids whose pushed string actually changed, computed from values the writer already has in hand; a writer that would have to buy an extra read on a hot path (patchContact) keeps the unconditional stamp and says so in a comment, because its fan-out is bounded by one contact's own submissions. Precision, not suppression: a genuine rename must still stamp.

## Amendment (wave 32): the wave-30 contact/track-rename touch is a decision with no code — implement it, and fire it ONLY when a string the pushed record serializes actually changed

DEC-725's wave-30 amendment already ruled that contact and track name writers must touch their dependent submissions. Verified open at the file: src/server/repo/submissions/touch.ts still exports only touchSubmissions, its own header still scopes the contract to participant/submission_track writers, and none of the named writers (profile.ts updateContactProfile, contacts/crud.ts:126, contacts/import.ts:178/:379, portal-edit.ts:287, events.ts:346, import/sessionboard.ts:317/:357) calls it — so under gt(submission.updatedAt, mark) (src/sync/airtable.ts:217) the denormalised Speakers/Tracks strings built at :310-311 keep the old name in the customer's base indefinitely. New ruling this wave, because the stamp has a SECOND reader: src/server/repo/overview.ts orders the producer's awaiting-approval worklist by desc(submission.updatedAt), so a blanket touch on every contact write would let a headshot- or notes-only edit reorder the producer's worklist. The touch fires only when a string the pushed record actually serializes changed (contact.first_name/last_name, track.name), mirroring DEC-519's same-string room-rename/timezone no-op rule; and it resolves dependents by subquery in one chunked set-based UPDATE, never a read-then-loop, so a 200-row CSV rename stays one statement per chunk.

## Amendment (wave 6, sha d4584747): a watermark that will not parse is a fault — never a silent full push, never a silent zero-row tick that still advances the cursor

`src/sync/airtable.ts:199` does `new Date(storedMark)` with no validity check. A corrupt or non-ISO KV watermark yields an Invalid Date, `lookbackMark` becomes NaN-valued, the `gt(...)` predicates at `:214` and `:235` then match nothing, and `runAirtableSync` pushes zero rows while still advancing the watermark at `:342` — a permanently, silently dead one-way sync, in direct contradiction of the module's own contract at `:7-8` ("Sync failures throw (fail loudly) ... visible in the cron invocation log"). The same file already gets this right one screen earlier: DEC-725's own amendment clamps an untrusted external `Retry-After` at `:24-27` rather than trusting it. Ruling: the stored watermark is validated (a parseable ISO date) before use; an unparseable watermark throws, failing the sync loudly and visibly in the cron log, rather than silently degrading to a no-op that still advances the cursor. An ABSENT watermark stays a full push — that path is documented and correct for a first sync and a restore; the distinction is between no cursor and a broken one.
