# DEC-725: The Airtable push is incremental from a stored watermark, and a rate-limited response backs off instead of throwing

runAirtableSync re-pushes the org's entire contact and submission tables with a fresh SyncedAt on every 15-minute tick. At SPEC §0 scale that is hundreds of sequential calls per tick, and — worse than the cost — it re-fires every 'record updated' automation on every row, the exact opposite of the customer's stated use in docs/clarifications.md ('automations that happen once a new row lands'). A 429 currently just throws, so a rate limit becomes a failed tick. The correction is the standard shape for a periodic one-way push: a watermark per org in KV, both selects filtered to rows changed since it, the tick's clock written back on success, and a bounded Retry-After backoff inside the batch loop. A missing watermark means a full push, which is exactly right for the first sync and for a restore, so the incremental path needs no separate bootstrap.

## Amendment (wave 57): the Airtable tick is incremental from a KV watermark with a bounded Retry-After backoff, and EVERY read in the tick carries the MAX_SYNC_ROWS refusal and a deterministic order

DEC-725 is a decision with no code: `src/sync/airtable.ts` still re-pushes the org's entire contact and submission tables with a fresh SyncedAt on every tick (re-firing the customer's 'new row lands' automations on every row — the opposite of docs/clarifications.md's stated use), and `upsertBatches` throws on any non-ok response, so a 429 is a failed tick. Reading the module also exposes two smaller inconsistencies one level down from work already done: the participant join carries an explicit orderBy precisely so an unchanged submission never re-upserts with a permuted Speakers string, but the submission_track join has NO orderBy (the Tracks cell can permute between runs and fire automations on a non-change), and neither join carries the MAX_SYNC_ROWS+1 refusal that the contact and submission reads do. One watermark key per org in KV; a missing watermark means a full push (right for first sync and for restore, so no separate bootstrap); the watermark advances only when the whole tick succeeded, so a failed push is retried rather than skipped. This is sync CODE, not stage-2 provisioning: no network in tests (fetch is already injected), no secrets, nothing deployed.

## Amendment (wave 63): submission.updated_at is the whole record's change stamp — every participant and track write touches its submission

DEC-725's incremental Airtable push selects submissions by `submission.updated_at > mark`, and DEC-981 requires that a declined co-presenter never appear in the customer's Speakers cell. Both are defeated by the same fact: participant writes (src/server/repo/participants.ts insert/visible/invite-status/remove, portal-edit's addCoPresenter) and submission_track writes bump only their own row's updated_at. So on any org with a watermark, adding a co-speaker, removing one, or declining one leaves the submission out of the next tick's `subs` set forever, and the customer's base keeps publishing the speaker DEC-981 was written to remove. The same lie is visible in-product: src/server/repo/overview.ts orders the producer's awaiting-approval worklist by `desc(submission.updated_at)`, so a session whose speaker list just changed does not move. An EXISTS-over-dependents predicate cannot fix it, because the destructive cases are DELETEs with nothing left to select. Rule: the submission is the sync/recency unit, so every writer of a table the submission's published shape is composed from touches the submission row's updated_at in the same operation, through one shared `touchSubmissions` helper (chunked, set-based, never a per-row update).
