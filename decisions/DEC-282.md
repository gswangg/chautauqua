# DEC-282: Contact merge is total over every contact-referencing table: pipeline_entry/pipeline_activity carried, task_assignment deduped, twin login accounts refused, and a schema-derived tripwire keeps the list honest

Verified defect, not inherited. src/db/schema.ts has SEVEN columns referencing a contact (user.contact_id:38, participant.contact_id:244, task_assignment.contact_id:462, file.uploaded_by_contact_id:538, file_comment.author_contact_id:554, pipeline_entry.contact_id:655, email_log.contact_id:718) but buildMergeRepointOps (src/server/repo/contacts.ts:203-212) enumerates six and omits pipeline_entry -- so merging a duplicate who was enrolled in the CRM sourcing pipeline leaves an entry pointing at a row mergeContacts then deletes (:590), and listPipelineForOrg (src/server/repo/pipeline.ts:156-161) fails loudly by design: `throw new Error('pipeline_entry ... references missing contact ...')`. The whole J11 pipeline board 500s permanently after a documented, one-click producer action. Three sub-decisions, mine not the worker's: (1) pipeline_entry carries a uniqueIndex on (org_id, contact_id) (schema.ts:661) so a blind repoint would violate it -- when both contacts are enrolled, the kept entry survives, the merged entry's pipeline_activity rows are repointed onto it so history is complete, and the kept entry's stage becomes the further-along of the two by rank identified<contacted<interested<confirmed with 'declined' ranked below all of them, so a stale declined duplicate never buries an active lead. (2) task_assignment has NO unique index (schema.ts:477-481), so a blind repoint silently produces two cells for one speaker x one task in getOnboardingGrid (src/server/repo/tasks.ts:198 dedupes by assignmentId, which differs) -- dedupe before repointing, and completion wins so a finished task is never resurrected as pending. (3) If BOTH contacts have a `user` row the merge would create two accounts for one contact, a state getOnboardingGrid's comment (tasks.ts:195-197) explicitly assumes impossible -- refuse it up front with a structured conflict rather than corrupting the invariant. The enumeration is then locked by a tripwire in the family of test/schema-fk-indexes: derive every '*contact_id' column from the drizzle table configs and assert its table appears in an exported CONTACT_FK_TABLES, so the eighth table cannot be forgotten.
