# DEC-506: ONE likeContains, escape-only and never case-folding, paired with ESCAPE '\' at every LIKE call site including the unauthenticated public search boxes

Verified at file:line. The repo has TWO copies of likeContains -- src/server/repo/contacts/query.ts:47 and src/server/repo/submissions/query.ts:82, the latter's own comment declaring the duplication deliberate -- and THREE search call sites that use neither and escape nothing: src/server/repo/public/sessions.ts:59 (`%${q}%` through Drizzle like(), which emits no ESCAPE clause), src/server/repo/public/speakers.ts:51-56, and src/server/repo/email.ts:86-88. Consequence: an unauthenticated visitor hitting /e/:slug/speakers?q=%25 gets the entire roster returned as "matches", ?q=_ matches any single character, and a literal '_' or '%' in a name, company, or email subject can never be searched. The field guide's own w24 lesson is that two implementations of one invariant means one is wrong; here three sites have no implementation at all. The one home is a new pure module src/server/repo/like.ts exporting likeContains(raw: string): string, both duplicates DELETED (no re-export shims, house rule), every call site paired with `LIKE ${pattern} ESCAPE '\'` mirroring the proven clause ordering at src/server/repo/contacts/crud.ts:164. Second half of the decision: the canonical helper must NOT lowercase. SQLite's LIKE already folds ASCII case, so folding the pattern is redundant there, and folding only the pattern while the column stays unfolded strictly LOSES non-ASCII matches -- today likeContains('École') becomes an all-lowercase pattern that no longer matches the stored capitalized value, where an unfolded pattern would match exactly. Escaping is the helper's whole job; case handling belongs to the collation.
