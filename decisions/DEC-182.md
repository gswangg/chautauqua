# DEC-182: Bounded id-array validation helper applied to every bulk-ids JSON endpoint

A 5MB string element in POST /api/v1/events/:eventId/submissions/status ids reaches D1 and throws unhandled D1_ERROR SQLITE_TOOBIG as a 500 (src/routes/api/submissions.ts:331 checks only typeof string, and silently drops non-strings, violating fail-loudly). The same unbounded pattern exists at src/routes/tasks.ts:228 (contactIds), :296 (taskIds), src/routes/api/contacts.ts:541 (contactIds), and src/routes/files.ts:200 (fileIds — count-capped at 50 but not element-length-capped). One helper, one owner: export parseBoundedIdArray(value: unknown, field: string, opts?: { maxCount?: number }): string[] from src/server/http.ts next to ApiError. Rules: must be an array; ANY non-string element is a 400 'invalid' (no silent filtering); each element 1..64 chars (all newId()/seed ids are well under 64); default maxCount 1000, callers may pass tighter (files archive passes MAX_ARCHIVE_FILES). All five call sites switch to it.
