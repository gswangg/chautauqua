# DEC-182: Bounded id-array validation helper applied to every bulk-ids JSON endpoint

A 5MB string element in POST /api/v1/events/:eventId/submissions/status ids reaches D1 and throws unhandled D1_ERROR SQLITE_TOOBIG as a 500 (src/routes/api/submissions.ts:331 checks only typeof string, and silently drops non-strings, violating fail-loudly). The same unbounded pattern exists at src/routes/tasks.ts:228 (contactIds), :296 (taskIds), src/routes/api/contacts.ts:541 (contactIds), and src/routes/files.ts:200 (fileIds — count-capped at 50 but not element-length-capped). One helper, one owner: export parseBoundedIdArray(value: unknown, field: string, opts?: { maxCount?: number }): string[] from src/server/http.ts next to ApiError. Rules: must be an array; ANY non-string element is a 400 'invalid' (no silent filtering); each element 1..64 chars (all newId()/seed ids are well under 64); default maxCount 1000, callers may pass tighter (files archive passes MAX_ARCHIVE_FILES). All five call sites switch to it.

## Amendment (wave 30): a bulk id array is a SET — parseBoundedIdArray dedupes, and every downstream count is counted off the returned array

Verified on main: parseBoundedIdArray (src/server/http.ts:76) rejects non-arrays, over-cap counts and bad elements but never dedupes; requireFullMatch (src/routes/comms.ts:59) only detects MISSING ids; loadComposeSubmissions chunks at ID_CHUNK_SIZE=90 (src/lib/chunk.ts), so one id repeated across two chunks returns two rows, becomes two recipient rows through expandRecipients, mails the same speaker twice and over-reports `sent` — the same shape inflates `updated` on bulk status changes. All 16 call sites are set-semantics (bulk status, task assign, merge, compose, archive), which is why the coercion belongs at the ONE parse point rather than at each caller. Dedupe (first-occurrence order) rather than a 400: the field guide's house rule is already 'bulk ops set-based', a duplicate id is a harmless client artifact at a boundary, and silently doing the right thing beats failing a request whose intent is unambiguous. The cap check stays BEFORE the dedupe so 1000 copies of one id still 400s on count.
