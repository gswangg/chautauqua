# DEC-564: The notify pipeline is reproducible: recipients, reviewer-feedback numbering and reminder task lists each carry a declared order

J5's promise is a per-recipient preview a producer reads before sending, and J6's is a reminder whose preview is byte-identical to the send. Neither holds across two requests. `loadComposeSubmissions` (src/server/repo/comms.ts:153-206) reads submissions through chunked `inArray` with no ORDER BY and participants with no ORDER BY, then `expandRecipients` (src/domain/compose.ts:50-70) walks them in that order — so the preview dialog lists 40 decision emails in a different sequence each time it is opened, and the email_log rows land in a different order than the preview the producer approved. `listFeedbackComments`/`listFeedbackCommentsForSubmissions` (:210-247) order by `createdAt` alone, and `formatFeedback` numbers them "Reviewer 1/2/3" positionally — two evaluations submitted in the same millisecond (a decision meeting, a bulk import) can swap identities between the preview and the send, which is the one thing an anonymized feedback attachment must not do. And `buildReminderMessage` (repo/tasks/reminders.ts:95-102) renders `group.assignments` in raw row order, so DEC-441's "a preview draft is always byte-identical to what a send would produce" is true only within a single request. Decision: (a) loadComposeSubmissions selects `submission.seq` and `participant.order`, returns submissions ordered by `seq asc` and each submission's participants by `(participant.order asc, contact.id asc)` — applied as a JS sort over the accumulated chunks per DEC-562's stated fallback, since DEC-078 chunking dissolves a pure SQL order. (b) both feedback readers order by `(evaluation.createdAt asc, evaluation.id asc)`. (c) buildReminderMessage orders its task lines by `(dueDate asc with nulls last, taskTitle asc, assignmentId asc)` before rendering, so preview and send agree across requests and a speaker reads their most urgent task first. Nothing about the DEC-019 100-recipient cap changes: it still REJECTS rather than truncates, so no ordering decision here can silently choose who gets mail. The regression bar is byte-identity under shuffle: feed the same rows twice, once shuffled, and the rendered preview, the feedback numbering and the reminder text must be identical.
