# DEC-494: An event-clock string carries its event's timezone with it; the browser's zone is never a default

docs/verification-log/task-w21-d-walkthrough-stage1.md Finding 3 live-reproduced a three-hour lie: the Comms compose-preview calendar chip showed "May 12, 2027, 12:00 PM" for a session genuinely scheduled 09:00 Pacific, because app/src/pages/comms/icsChip.ts:13-14 formats with `toLocaleString(undefined, ...)` -- the viewer's machine zone. The .ics attachment itself is correct (UTC DTSTART/DTEND), so this is purely the human-readable string an organizer proofreads before hitting send, which is exactly the reader who must not be misled. DEC-424's rule ("dates via event-time.ts, the OWNING EVENT's tz") already governs the server; this extends it to the SPA with a type-level guarantee rather than a comment: `IcsChipInfo` gains a REQUIRED `timeZone: string` (IANA), the server fills it from `event.timezone` in src/routes/comms/compose-core.ts's `icsPreviewInfoFor`, and the chip names the zone in its rendered text so a distributed program committee reads an unambiguous time. A formatter that CAN be called without a zone will be called without a zone; the compiler is the enforcement, and the unit test proves independence from the ambient TZ. Scope is deliberately narrow: audit timestamps (email sentAt, token lastUsedAt, comment createdAt) stay in the viewer's local zone -- they describe when something happened to the viewer, not where the event's clock is.
