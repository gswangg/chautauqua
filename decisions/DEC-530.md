# DEC-530: Per-recipient account and feedback lookups inside a batch send are resolved by ONE batched query each; findAccountUserId's contact-id-OR-email rule stays single-sourced and is contract-tested against its batch twin in both directions

`buildRenderTargets` (`src/routes/comms/compose-core.ts`) loops the expanded recipient list and issues two awaits per recipient: `repo.listFeedbackComments(db, recipient.submissionId)` — re-run per co-speaker for the SAME submission — and `resolvePortalLink`, whose first act is `repo.findAccountUserId`. At the DEC-019 cap of 100 recipients that is up to 200 sequential D1 round trips inside one request, and it runs on POST /compose/preview as well as /send, so the per-recipient preview a producer clicks through in J5 pays the full waterfall. `src/routes/api/contacts/bulk-email.ts:98` has the identical shape for the CRM bulk send. SPEC §7 sets admin reads at p95 < 50 ms and writes at p95 < 100 ms and calls a route over budget a bug, not a tuning opportunity, and states the one-round-trip-per-view rule explicitly; DEC-333 already ruled that scale-shaped admin read defects are stage-1 product defects, not stage-2 perf work. Decision: (a) `src/server/repo/comms.ts` gains `listFeedbackCommentsForSubmissions(db, submissionIds): Promise<Map<string, string[]>>` and `findAccountUserIds(db, params: {contactId,email}[]): Promise<Map<string,string|null>>`, both chunked with `chunkIds`, both keyed so a caller cannot mis-associate a row; (b) the two loops call them once up front and read from the maps; (c) the standing house invariant that account identity is answered by contact_id OR email and NEVER email alone (DEC-456) stays owned by the singular `findAccountUserId` — the batch form must express the same OR predicate, and a test asserts the two agree on the four discriminating cases (contact-id hit only, email hit only, both, neither), because a batch query that quietly narrowed to email-only would silently mint claim links for contacts who already have logins; (d) claim-token minting stays per-recipient and unbatched — it is a KV write with real side effects and DEC-397's preview/send split depends on it staying exactly where it is.

## Amendment (wave 42): minting is a per-recipient read too — batch it

src/routes/comms/compose-core.ts awaits resolvePortalLink inside the per-recipient loop, and that call performs a KV write per claim token (src/server/repo/portal-link.ts:27). At the DEC-019 100-recipient cap that is up to 100 sequential KV round trips — precisely the serial per-recipient IO the adjacent DEC-530 comment (comms.ts:386-398) claims to have collapsed 'into 2' for the D1 reads. Same pattern at comms.ts:662 and content-notes.ts:125. A write inside a per-recipient loop is the same defect as a read inside one; the whole recipient set resolves through one batched call.

## Amendment (wave 44): batched portal-link resolution is the rule on EVERY per-recipient path — the last unconverted path makes the rule a lie

DEC-530's wave-42 amendment collapsed per-recipient KV minting into one batched `resolvePortalLinks` on both comms.ts send paths and states "the loop itself must contain no await on KV". src/routes/api/contacts/bulk-email.ts:92 still awaits `resolvePortalLink` per contact inside its loop, so the 100-recipient bulk send performs up to 100 sequential KV round trips. A predicate honoured on two paths and skipped on the third is worse than none: it makes the comment describing the rule false.

## Amendment (wave 46): task reminders are the LAST per-recipient KV path — after this the singular resolver has no callers and is deleted

The wave-44 amendment named src/routes/api/contacts/bulk-email.ts:92 as the last unconverted fan-out; that one landed (bulk-email.ts:93 now calls the batched resolvePortalLinks). Re-probing today found the rule is STILL a lie on a third file nobody named: src/server/repo/tasks/reminders.ts:188 (remindNow / organizer-triggered fan-out, mintClaimTokens=true — real KV writes) and :327 (the manual-reminder DRAFT/preview builder) both await the singular resolvePortalLink inside their per-group loop. At the capped group size that is up to N sequential KV round trips plus N sequential claim-token writes before the first email leaves. Decision: both loops hoist ONE resolvePortalLinks call above themselves, exactly as comms.ts/content-notes.ts/bulk-email.ts do; and because reminders.ts is then the only remaining consumer, the singular resolvePortalLink export is DELETED from src/server/repo/portal-link.ts rather than left as a convenience wrapper that invites a fourth serial loop (house rule: delete the old code, no compatibility shims). A rule honoured on four paths and skipped on the fifth is not a rule; the way to stop re-discovering this every second wave is to remove the API that makes the wrong thing easy.

## Amendment (wave 48): a version-chain walk is one query per DEPTH across all seeds, not one per link — the portal /tasks page resolves chains, comment threads and linked deliverables via batched frontier reads

`loadTasksPageData` (src/routes/portal/tasks.tsx:124-201) awaits inside two loops, and the functions it awaits are themselves per-link walks: `resolveTaskFileChainLatest` (files-versions.ts:78) and `listFileChainIds` (:120) issue one SELECT per chain link. A speaker with four file tasks of three versions each pays roughly forty sequential D1 round trips to render one portal page — the same serial-fan-out defect this DEC's KV amendments (wave 42/44/46) already eliminated on the mail side, now found on the D1 read side of the same portal surface. Ruling: chain resolution for ALL seed file ids on the page is batched into a frontier walk — at each depth, one chunked query over the current whole frontier (the file ids still needing a next-version lookup), advancing every chain one hop per round trip — so total query count is proportional to chain DEPTH plus a constant, independent of the number of tasks or file chains on the page. This is the same rule DEC-530 already imposed on the KV portal-link side, now applied to the D1 chain-walk side.

## Amendment (wave 53): 'the fan-out loop contains no await on KV/R2' becomes a scanned invariant with a two-directional ledger

This exact class has been rediscovered four times: wave 42 (comms.ts), wave 46 (content-notes.ts), and waves 50/51 (bulk-email.ts and tasks/reminders.ts, both missed by the wave-42 migration that declared the rule). All four are batched now and I re-verified each — bulk-email.ts:94 and reminders.ts:184/342 all call the batched `resolvePortalLinks` before their loops. Nothing prevents the fifth. Per the field guide's own rule (FOURTH WAVE OF SAME FINDING = BUILD THE SCAN), the invariant moves from memory into test/kv-r2-loop.scan.test.ts, shaped exactly like test/serial-write-scan.test.ts: innermost-enclosing loop attribution, chunk-helper exemption, and a ledger that fails in BOTH directions so a fixed site's excuse line cannot outlive it. The helper names it recognises are ENUMERATED from the KV/R2 modules' own `export async function` lines rather than hand-listed. `Promise.all(list.map(async ...))` is the correct shape and is deliberately not flagged.

Running the built scan (`test/kv-r2-loop.scan.test.ts`) against the four previously-fixed sites confirmed the class is closed there, but it found a fifth, real, previously-unlisted offender the memory-based re-litigation had never named: `src/routes/public/submit.tsx`'s CFP file-upload path awaited `fileStore.put`/`fileStore.delete` (R2, not KV) once per file-field inside two separate `for` loops (upload phase and error-rollback phase). Both were batched into `Promise.all(list.map(async ...))` rather than ledgered — per-field-count is small but there was no structural reason the puts/deletes needed to be serial, so batching (the preferred fix per this DEC's own precedent) was applied instead of adding an exception. `KNOWN_SERIAL_IO` in the new scan starts and stays EMPTY.

## Amendment (wave 26): a parallel fan-out owns its own cleanup — the R2 put phase rolls back the puts that DID succeed

DEC-530 made the submit-time R2 puts fan out with `Promise.all` instead of one await per field. On the single unauthenticated write path in the product, that fan-out sits OUTSIDE the try that guards the DB phase: `src/routes/public/submit-post.tsx:355` opens `const preparedFiles: {...}[] = await Promise.all(` and the guarded block does not begin until `:369` `try {`. `Promise.all` rejects on the first rejection while the other puts keep running to completion, so an N-file submission that fails on one put leaves the other N-1 objects in the bucket with no row referencing them and no cleanup — the rollback at `:392-406` only ever runs for DB-phase failures. The DB phase already got this right in wave 21 (DEC-713 ordering: commit the row delete, then best-effort delete every R2 key, always rethrow the original error). RULING: the upload phase mints every r2 key BEFORE any put (so the key set is known regardless of which promises settle), settles the puts without short-circuiting, and on any rejection best-effort deletes every minted key (an R2 delete of a key whose put failed is a harmless no-op) inside its own try/catch that logs, then rethrows the FIRST rejection unmasked. Symmetry with the DB-phase rollback is the rule: every phase that can partially apply cleans up what it applied.

## Amendment (wave 33): the compose render's four independent batch reads are one wave; MINT LATE is untouched

DEC-530 already collapsed the compose path's per-recipient lookups into batched reads — the right shape, issued in the wrong order. `buildRenderTargets` awaits `listFeedbackCommentsForSubmissions`, `findAccountUserIds`, `listOutstandingForEvent` and `loadIcsScheduleData` one after another though every one of them depends only on `expanded` and `event` (pure, already resolved), then `resolvePortalLinks` on `accountMap` — 5 serialized trips where 2 waves suffice, on the J5 preview an organizer runs before every send. RULING: the four independent batches issue as one Promise.all wave; `resolvePortalLinks` stays the dependent second wave. DEC-397's MINT LATE semantics are explicitly out of scope: the validating render still resolves links with `mintClaimTokens=false` and mints nothing, and the preview/send envelopes stay byte-identical. Minting is IO with a side effect; it never joins a read wave.

LANDED (wave 33, task w33-e): `buildRenderTargets` (`src/routes/comms/compose-core.ts`) now issues `listFeedbackCommentsForSubmissions`, `findAccountUserIds`, `listOutstandingForEvent` and `loadIcsScheduleData` as a single `Promise.all` wave (the non-feedback slot uses `Promise.resolve(new Map())` rather than branching around the wave, keeping the `feedback ? ... : new Map()` shape). `resolvePortalLinks` stays a dependent second wave, still called with `mintClaimTokens=false`. Proven behaviourally by `test/compose-preview-round-trip-depth.test.ts` (an instrumented fake `Db`/tracker pattern, not a source grep) plus a byte-identical pinned-target assertion for a two-recipient (with/without outstanding tasks) fixture.

## Amendment (wave 70): the SEND loop is a bounded fan-out pool too, not just the render's reads

The wave-33 amendment batched only compose's read side; every mail fan-out still pays one round trip per recipient at the SEND loop: comms/send.ts:197-245 (up to MAX_COMPOSE_RECIPIENTS = 100, each `mailer.send` writing its own `email_log` row), api/contacts/bulk-email.ts:282-296, comms/portal-invites.ts:88-109, review/plans-progress.ts:349-371, repo/tasks/reminders.ts:485. Five sites, one shape — DEC-155 (wave 68) already ruled a route's WRITE phase is a wave too, and this is that same ruling applied to `await mailer.send(`. RULING: each site's send loop runs through a bounded pool, `MAIL_FANOUT_CONCURRENCY = 6` (conservative against Workers' concurrent-subrequest behaviour and any provider-side burst limit), and returns SETTLED results in INPUT order, so each route's existing per-recipient try/catch accounting, its `failed[]` ordering and its response envelope reproduce byte-for-byte. Nothing above the loop moves into it — preflight, dedupe and the DEC-397 late mint all run against one consistent snapshot and stay there.
