# DEC-530: Per-recipient account and feedback lookups inside a batch send are resolved by ONE batched query each; findAccountUserId's contact-id-OR-email rule stays single-sourced and is contract-tested against its batch twin in both directions

`buildRenderTargets` (`src/routes/comms.ts:327-347`) loops the expanded recipient list and issues two awaits per recipient: `repo.listFeedbackComments(db, recipient.submissionId)` — re-run per co-speaker for the SAME submission — and `resolvePortalLink`, whose first act is `repo.findAccountUserId`. At the DEC-019 cap of 100 recipients that is up to 200 sequential D1 round trips inside one request, and it runs on POST /compose/preview as well as /send, so the per-recipient preview a producer clicks through in J5 pays the full waterfall. `src/routes/api/contacts/bulk-email.ts:98` has the identical shape for the CRM bulk send. SPEC §7 sets admin reads at p95 < 50 ms and writes at p95 < 100 ms and calls a route over budget a bug, not a tuning opportunity, and states the one-round-trip-per-view rule explicitly; DEC-333 already ruled that scale-shaped admin read defects are stage-1 product defects, not stage-2 perf work. Decision: (a) `src/server/repo/comms.ts` gains `listFeedbackCommentsForSubmissions(db, submissionIds): Promise<Map<string, string[]>>` and `findAccountUserIds(db, params: {contactId,email}[]): Promise<Map<string,string|null>>`, both chunked with `chunkIds`, both keyed so a caller cannot mis-associate a row; (b) the two loops call them once up front and read from the maps; (c) the standing house invariant that account identity is answered by contact_id OR email and NEVER email alone (DEC-456) stays owned by the singular `findAccountUserId` — the batch form must express the same OR predicate, and a test asserts the two agree on the four discriminating cases (contact-id hit only, email hit only, both, neither), because a batch query that quietly narrowed to email-only would silently mint claim links for contacts who already have logins; (d) claim-token minting stays per-recipient and unbatched — it is a KV write with real side effects and DEC-397's preview/send split depends on it staying exactly where it is.

## Amendment (wave 42): minting is a per-recipient read too — batch it

src/routes/comms.ts:435 awaits resolvePortalLink inside the per-recipient loop, and that call performs a KV write per claim token (src/server/repo/portal-link.ts:27). At the DEC-019 100-recipient cap that is up to 100 sequential KV round trips — precisely the serial per-recipient IO the adjacent DEC-530 comment (comms.ts:386-398) claims to have collapsed 'into 2' for the D1 reads. Same pattern at comms.ts:662 and content-notes.ts:125. A write inside a per-recipient loop is the same defect as a read inside one; the whole recipient set resolves through one batched call.

## Amendment (wave 44): batched portal-link resolution is the rule on EVERY per-recipient path — the last unconverted path makes the rule a lie

DEC-530's wave-42 amendment collapsed per-recipient KV minting into one batched `resolvePortalLinks` on both comms.ts send paths and states "the loop itself must contain no await on KV". src/routes/api/contacts/bulk-email.ts:92 still awaits `resolvePortalLink` per contact inside its loop, so the 100-recipient bulk send performs up to 100 sequential KV round trips. A predicate honoured on two paths and skipped on the third is worse than none: it makes the comment describing the rule false.
