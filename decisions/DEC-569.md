# DEC-569: participant.order is the producer's to set: a full-set reorder endpoint, or the column that now governs every rendered speaker list is dead

DEC-562 (wave 37) makes `(participant.order asc, contact.id asc)` the order every surface renders a session's speakers in — public card, J3 table, admin agenda, portal, compose recipients. But nothing writes `order` except the insert path: inviteParticipant computes MAX+1 (src/server/repo/participants.ts:81-89) and the two create paths correctly write 0 for a submission's first participant (src/server/repo/submit.ts:259, src/server/repo/submissions/create.ts:101). There is no writer at all for reordering — src/routes/api/submissions.ts:337-363 exposes only `visible`, while docs/sessionboard-reference/00-how-sessionboard-works.md:89 states plainly that 'Speakers can be drag-reordered for display order and toggled public/hidden'. Wave 37 already learned this shape from `position` on room/track: a column that governs what a human reads but has no writer is a dead column, and worse here, because DEC-562 just promoted it to the order of record. Decision: POST /api/v1/submissions/:id/participants/order, requireOrganizer + csrfJson, body `{ participantIds: string[] }` that MUST be the complete set of that submission's participant ids, each exactly once — anything else is ApiError('invalid', 'participantIds must list every participant on this submission exactly once', { participantIds: '<the specific mismatch>' }); no partial reorder, no silent ignore (fail loudly). Repo `setParticipantOrder(db, submissionId, participantIds): Promise<ParticipantRow[]>` in src/server/repo/participants.ts: one SELECT of the submission's participant ids, the full-set guard, then order = array index, returning the rows re-read in `(order asc, id asc)` in the existing ParticipantRow shape. Response `{ participants: ParticipantRow[] }` — a bounded mutation echo, deliberately NOT a paged list envelope (DEC-460 does not apply). Ownership is checked on the submission (getSubmissionOwnership + orgId compare) exactly as the sibling visibility PATCH does, and every listed participant must belong to that submission, so this endpoint can never touch another org's rows.
