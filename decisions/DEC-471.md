# DEC-471: Re-running DEC-466's own criterion found two more list reads it never named; `/api/v1/submissions/:id/files` and `/api/v1/files/:fileId/comments` get the DEC-013 envelope

DEC-466 declared the population criterion mechanical ("every `c.json({ items` site under src/routes") but its prose still named only three offenders. Re-running the criterion against main returns two sites DEC-466 never mentioned: `GET /api/v1/submissions/:id/files` (src/routes/files.ts:166) and `GET /api/v1/files/:fileId/comments` (src/routes/files.ts:309), both `return c.json({ items })` with no total, no page, no perPage and no LIMIT — flattened in JS from `listSubmissionFiles` (src/server/repo/files-versions.ts:160, unbounded SELECT ORDER BY createdAt desc) and `listFileComments` (src/server/repo/files-comments.ts:23, unbounded SELECT ORDER BY createdAt asc). This is not a theoretical gap: app/src/pages/content/DeliverableDetail.tsx:47 and :68 read both through `apiList<T>`, whose `ListEnvelope<T>` (app/src/lib/api.ts:32) declares `total: number` — so the SPA's type says `number` and the wire says `undefined`. A version history and a review comment thread are exactly the lists that grow forever under an active content-review workflow, which is what DEC-460 refused to exempt as "naturally small". Both are assembled in JS from an already-materialized array, so DEC-461(e)'s blessed exception applies verbatim: clampPage + listPerPage, slice the already-ordered array, report the FULL array length as `total`, never re-derive `total` from the slice, and add `id asc` as the final ORDER BY tiebreak in the two repo queries so page boundaries are deterministic. The durable point: DEC-466 wrote the right rule and then published a hand list next to it, and the hand list was short again — a criterion is only mechanical once its output is an artifact somebody re-ran (DEC-473).
