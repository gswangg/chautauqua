# DEC-747: Every Settings section is a read view with ONE action on its rule; the rail is SEVEN, and Import from Sessionboard is a row inside Your data

DEC-728 established the summary/drill-in pattern and w1-b landed SummarySection.tsx, but only EventSettingsPanel consumes it — Tracks and rooms, Public pages, Speaker portal, People, Exports and Tokens are still edit-everything forms, which is the mandate's single most divergent surface. docs/design/Chautauqua Settings.dc.html:103-233 fixes each section's read view exactly: Tracks and rooms = two columns of name + count with "Add" on the rule; Public pages and embeds = name · path · state · "Embed code" per row; Speaker portal = Welcome note / Speakers can edit (pills) / Onboarding tasks / Resources (name · detail · Replace, plus "Add a resource") / Access, with "Open as a speaker" on the rule; People and roles = name+email · role · scope · "Change" per row with "Invite someone" on the rule; Your data = Exports (four pills) / API tokens (name · mask · last used · Revoke + "New token") / API docs link. The pack has no eighth section, so "Import from Sessionboard" becomes a labelled row inside Your data that drills into the existing three-step panel, and the rail renders exactly seven entries in the pack's order. No control renders disabled (DEC-733) and no section dumps raw markdown — a wiki resource's read row names the page and its size, never its body.

## Amendment (wave 53): the tracks-and-rooms read view is a full-column block, not a value cell

`.chq-settings-tracks-rooms-grid` (settings.css:665) correctly declares `width:100%`, but it is hosted inside the `1fr` value cell of the `170px 1fr auto` `.chq-settings-row` grid, so 100% resolves to ~488px inside the 820 settings column and the two 227px sub-columns cramp while the section rules run past them. DEC-747 already recognised this row has no label (hence `.chq-settings-row-label:empty { display:none }` at :659) — the row was half-converted. The decision completes it: a labelless block row declares a single-column template and spans the full 820 measure, so the grid's width comes from the settings column rather than from a label gutter it does not use.

## Amendment (w1): the wiki-page editor states the grammar the portal applies, from one source

Verified at the file: src/routes/portal/tasks/views.tsx:501 renders a resource body through renderMarkdown, which per DEC-696 is escape-first with a closed allow-list — `##`/`###` only, paragraphs on blank lines, `-` lists, `**bold**`/`*italic*`, `[text](https-url)` with javascript: rejected, and every raw tag escaped. app/src/pages/settings/ResourcesPanel.tsx's two content textareas (add at :329, edit at :271) say nothing about any of this. An organizer writing `# Heading`, a `<br>`, or single-spaced lines gets something different in the speaker's portal and has no preview and no hint to learn from — the writer's control does not state the reader's rules. Ruling: the supported syntax gets ONE home beside renderMarkdown and the panel prints it; a test asserts every syntax the hint advertises actually survives renderMarkdown and that the hint advertises nothing renderMarkdown escapes, so the two can never drift.

## Amendment (findings wave 4): the portal EDIT view states what speakers may edit, from the same source as the read view

docs/design/Chautauqua Settings.dc.html:907-917 draws the 1600 "editing the speaker portal" screen with three sections — Welcome note, What speakers may edit (the pill set), Resources · 3 — and puts the organiser-only consequence directly under the pills. On main, PortalSettingsPanel.tsx renders the pills in the READ rows only; the edit branch drops them entirely and prints the consequence as a bare footer line, so the one screen that exists to answer "what can a speaker change" cannot answer it while you are changing it. Ruling: the edit form renders the SAME `SPEAKER_EDIT_FIELDS` array the read view uses (one source, never a second list) under a section head in the read view's rhythm, with the consequence sentence beneath that section rather than floating at the form foot. Resources stops being a raw `.chq-settings-row` and becomes a titled section like every other block on the screen.

## Amendment (findings wave 7) — Settings' "Open the portal" row gets a real read-only preview at GET /portal/preview; a row action that its own role cannot reach is not an action

DEC-747 says every Settings section is a read view with ONE action on its rule. The Speaker-portal section's action is `Open as a speaker` -> `/portal` (app/src/pages/settings/PortalSettingsPanel.tsx:212), but `speakerGate` (src/routes/portal/shared.tsx:52-71) redirects every non-speaker session to `/admin`, so the ONE action an organizer has on that section bounces them back to the admin shell in a new tab. DESIGN-RULINGS A22 blesses the row on the condition that it "must say it is a read-only impersonation of the portal, or it reads as a login-as" — the capability it names does not exist at all, which is worse than the wording defect the ruling anticipated, and swyx's "blindly copying the screens/forms but they dont work will not be in the spirit of the competition" (docs/clarifications.md:55) rules directly on it. RULING: build the smallest honest version of the capability the frame draws (docs/design/Chautauqua Settings.dc.html:175). `GET /portal/preview` is organizer-only and renders the portal chrome a speaker sees — event branding, welcome message, resources — and NOTHING speaker-scoped: no submissions, no task assignments, no files, no mutating control. It is a preview of the producer's own configuration, not an impersonation, so it needs no consent story and leaks no speaker's data (SPEC §6 object-level ownership). Non-organizers get the same 404 card the portal gate already renders for an unknown path, never a redirect, so the route is invisible to the roles it is not for. The Settings row keeps the frame's link text and gains the read-only clause A22 requires.

## Amendment (wave 58): the invite flow names the act it performs, and the reset names what it ends

DESIGN-RULINGS:358-366 rules that `POST /api/v1/users` creates the account IMMEDIATELY — there is no invitation and no pending state — so the primary must read 'Create the account', not 'Send invitation'. Verified the panel today: `PeopleRolesPanel.tsx:217` says 'Invite someone', :226-228 reveals the password as a bare `<code>` with no Copy control, and nothing states the email_log.event_id gap, the role consequences, the duplicate escape route, or the two reset facts. Ruling: the created screen carries the one-time password in monospace at 20px with a Copy control that reports success or failure (never a silent clipboard failure), plus 'Closing this dialog is the last time you see it — after that only a reset can replace it.' The panel states honestly that an org with no events gets a working account and NO welcome email, because `email_log.event_id` is NOT NULL. A rejected duplicate offers 'Open <name>'s row' rather than making the organiser retype. A reset states that sessions end everywhere and that resetting sends no email. NO pending-invitation state is designed or built — the schema has no such row and a greyed 'Invited' row would describe a status that cannot resolve.

## Amendment (wave 67): the invite flow is a dialog, not an inline strip

Frames 09--18/19/20 draw "Invite someone" and the created/reveal screen as a dialog; on main it was still an inline strip inside the People section body (`PeopleRolesPanel.tsx`, pre-wave-67). The wave-58 amendment's COPY contract (the 'Create the account' primary, the reveal-once one-time-password screen, the honest email-gap sentence, the DEC-238 welcome-notice vocabulary, and the 409 duplicate escape route) was already correct and is unchanged by this ruling — only the FORM FACTOR moves. RULING: "Invite someone" opens the shared `ModalFrame` (DEC-651) built the same way `UploadRejectedModal` is (`role="dialog"`, `useEscapeKey`, scrim-click-to-close). The created/reveal screen is the SAME dialog's second step — its body swaps from the invite form to the reveal block rather than opening a second dialog or rendering a sibling element — so the one-time password is still shown on exactly one screen and closing the dialog (Done, the frame's Close, Escape, or a scrim click) is still the last time it is seen; all four close paths clear the revealed password identically. The reset-password reveal (frame 09--24) is a distinct per-row affordance and keeps its original inline site and copy verbatim; the reveal markup itself is extracted into one `PasswordRevealBlock` component so the invite (dialog) and reset (inline) paths render from a single source and cannot drift apart.

## Amendment (wave 60): a preview must name what it is not showing, and must offer the way back

Read in full at src/routes/portal/preview.tsx: the route renders the read-only banner, the welcome message and the resources section (with DEC-988's showResources-off explanation and DEC-919's empty state), and nothing else. Frame 10--24 mandates three further clauses that are absent: a 'Not shown here' section naming what a real speaker sees and this page deliberately does not (their submissions, their tasks, their files), the honest sentence that seeing a real speaker's portal would require being them, and resource rows whose Download affordance is present-but-DISABLED so the preview shows the speaker's own control rather than silently omitting it; there is also no route back to Settings, so the organiser's only exit is the browser's Back button. RULING: all four land in preview.tsx against the frame's copy; the disabled Download is rendered disabled (this is the one sanctioned disabled control on the surface — the thing it names EXISTS for the speaker, so DEC-733's absent-not-disabled rule does not apply), and the Settings return link is a plain link, never a mutating control, preserving the route's no-mutation invariant.
