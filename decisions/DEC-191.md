# DEC-191: email_log.contact_id is a real contact id or NULL — never a user id; RenderedEmail/EmailLogEntry.contactId widen to string | null

src/routes/api/users.ts:86 (org-user welcome) and src/routes/review.ts:472 (reviewer reminders) write user ids into email_log.contact_id as a documented stand-in. That silently corrupts the per-contact contract: per-contact history (src/server/repo/contacts.ts filters emailLog.contactId = contactId) and contact-merge repointing can never see or reattribute these rows, and the pseudo-FK violates the fail-loudly/honest-data house rule. The column is already nullable (src/db/schema.ts:673, no .notNull()), so no migration: widen RenderedEmail.contactId and EmailLogEntry.contactId in src/mail/types.ts to string | null, pass null at both user-recipient call sites, and make all readers/writers null-safe (dev-sink, d1EmailLogWriter, /dev/mailbox, email-log API, exports). Contact-recipient sends are unaffected (string assignable to string | null).
