# DEC-360: Wave-23 gate lanes are log-only: each owns exactly one new file (its own verification log) and never patches product code; a red gate is an OPEN ITEM with file:line for wave 24

Six gate lanes run concurrently over the same tree. If any of them is allowed to fix what it finds, they collide on product files and the merge agent has to reconcile fixes against evidence written about a tree that no longer exists. DEC-284 already established this shape for a mechanical gate lane ("it edits exactly one file, its own log; ... a red result is reported with file:line and failing test names for the next wave to schedule, never patched in-lane where it would collide with the in-flight defect branches"), and DEC-315 established that a FAIL yields a narrow fix wave over the cited file:line only. Binding for wave 23: the ONLY path a gate lane may create or modify is its own docs/verification-log/task-w23-{a..f}-c3-*.md. It must not touch src/, app/, test/, scripts/, migrations/, decisions/, field-guide/, src/decisions.ts, or the shared docs/verification-log.md ledger (six lanes appending to one ledger is a guaranteed six-way conflict for zero benefit — the per-lane files ARE the record, as task-w21-a/b/c did). Each log carries the verbatim headings FROZEN SHA, OPEN ITEMS: N, RESULT: PASS|FAIL, RECHECK SHA, POST-S DELTA. Under DEC-329, a failing probe may have its FETCH narrowed to match a legitimately-changed shape, but an ASSERTION may never be weakened to make a gate green.
