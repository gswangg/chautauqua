# DEC-532: Conditional-field visibility resolves to a FIXED POINT: a field gated on a hidden field is itself hidden, because a hidden field has no answer

`isVisible` (src/forms/visibility.ts:7) takes only (field, answers) and reads the RAW submitted answer map, so it can never know whether the field its rule points at is itself hidden. Chain: Format(dropdown) -> "Workshop length" (rule: Format=Workshop) -> "Projector?" (rule: Workshop length=3 hours). A speaker who switches Format from Workshop to Talk and resubmits gets: "Workshop length" correctly hidden and stripped (validate.ts:44-54, DEC-501), but "Projector?" still evaluates VISIBLE because answers["Workshop length"] is still "3 hours" in the raw map. Two live consequences, both on the public CFP that J2 says must not gate on invisible questions: (a) if the grandchild is required, validateAnswers emits `required` for a question the speaker cannot see, and the submit button is a dead end with no reachable error field; (b) if it is optional, its stale answer survives DEC-501's cleanup and is served to reviewers (review/submissions.ts sessionAnswers), the organizer detail, and every export as current -- exactly the failure DEC-501 was written to kill, one level deeper. DEC-501 fixed depth 1 and stopped. Decision: (a) `src/forms/visibility.ts` gains `resolveHiddenFieldIds(fields, answers): Set<string>`, a MONOTONE fixed point -- repeat until stable: a field is hidden when `!isVisible(field, effectiveAnswers)` where effectiveAnswers omits every currently-hidden field's key, or when its `rule.fieldId` names an id absent from `fields`. Fields only ever move visible->hidden, so it terminates in at most `fields.length` passes and a rule CYCLE resolves deterministically to hidden-on-both (an unsatisfiable rule is not an exception -- an organizer misconfiguration must still render the form). (b) `isVisible` stays exactly as it is and stays the ONE single-field predicate; resolveHiddenFieldIds is its only new caller. (c) `makeVisibilityPredicate(fields, answers)` returns a closure with the existing `(field, answers) => boolean` shape so `src/views/form-render.tsx`'s prop type is UNCHANGED and the three render sites are a one-line swap. (d) Every render site builds the predicate from the FULL field list, never the per-section slice, because a session field can gate a speaker field.

## Amendment (wave 43): the public form's conditional-field script is a MIRROR of the server predicate, never a second authority

resolveHiddenFieldIds runs at render (submit-views.tsx:246) and again at submit (submit.tsx:354), but the public CFP page ships no client behaviour, so a field ruled 'show when Format eq Workshop' is decided once at GET against an empty answer map and can never appear as the visitor answers — the builder's conditional feature is unreachable in the only place it matters. Amendment: rule-bearing fields are always emitted, hidden via the `hidden` attribute, carrying their rule as data-chq-rule-* attributes; a small inline script (the precedent public pages already use in shell.tsx/agenda.tsx) toggles `hidden` on change. The server predicate stays the ONLY authority — hidden answers are still dropped server-side (DEC-132/DEC-973), so a tampered client can neither reveal a field's answer into the record nor block a submit.

## Closure note (wave 43, w43-e): the mandate above already lagged the tree by the time it was worked

By the time this task ran, `src/views/form-render.tsx`'s `FieldRulesScript` (added earlier the same wave by DEC-973's "Hide dependents of a hidden trigger structurally" commit) already emitted `<script>` toggling every rule-bearing field's wrapper on `change`/`input`/`DOMContentLoaded`, computing the DEC-532/DEC-973 transitive fixed point in the browser via the shared `RULE_MATCH_JS` twin (src/forms/rule-match.ts), and `submit-views.tsx:408` was already calling it. So the *functional* gap this amendment describes (a rule-gated field frozen at GET, unreachable as the visitor answers) was closed before this task started — proven by the fixed-point toggle test already in test/form-render-rules.test.ts, which runs the actual emitted script against a fake `document`. The one real gap found on inspection: `FieldRulesScript`'s rule filter (`fields.filter(f => f.rule)`) had no DEC-625 locked-field guard, unlike `resolveHiddenFieldIds`'s two guarded branches — a locked field's rule, if one ever reached the renderer despite the API-side block (src/routes/api/forms.ts:226), would have been surfaced to the browser's toggler. Fixed by mirroring the same `lockedFieldName(f.id) === null` guard client-side. The wire format stayed the pre-existing JSON-blob-plus-inline-style mechanism (not the `hidden`-attribute/data-chq-rule-* shape this amendment's text describes) since that mechanism was already shipped, tested, and functionally equivalent — see test/submit-conditional-field-behavior.test.ts and test/submit-hidden-text-field-answer.test.ts for wave-43 coverage of the present-but-hidden markup, the locked-field guard, and the server-drops-a-hidden-text-answer path.
