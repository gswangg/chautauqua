# DEC-244: Portal deliverable panel mechanics (implements DEC-242)

Completed file_request assignments must not collapse to plain text (prod finding, CNT-05/D). Concrete contract so portal and organizer Content stay ONE system: (1) /portal/tasks renders, for each completed file_request assignment, an inline panel with the deliverable's current filename + uploaded time; (2) new GET /portal/tasks/:assignmentId/file serves the CHAIN-LATEST version (follow previous_file_id forward from the assignment's completion file via the files repo, so organizer-side replacements are honored) with Content-Disposition attachment, authz identical to the upload route (assertOwnAssignmentOr403 + org scope) — do NOT reuse the organizer /files route; (3) Replace is a plain re-post to the existing POST /portal/tasks/:assignmentId/upload, which already accepts complete assignments and chains previous_file_id per DEC-240; (4) comment thread reuses the file_comment table anchored to the chain-latest file id (same anchor rule as organizer DeliverableDetail, which shows comments[latest.id]); speaker posts via new POST /portal/tasks/:assignmentId/comments (csrfForm) inserting authorContactId=speaker contact AND authorUserId=speaker user, body trimmed, non-empty, capped at 4000 chars, redirect back to /portal/tasks. One thread, two surfaces.

## Amendment (wave 56)

A portal form POST re-renders its own page on refusal, and the comment cap is named where it is typed.

src/routes/portal/tasks.tsx:134-137 states the house pattern in its own words: the tasks-page loader was factored out 'so a failed upload can re-render the SAME page inline (with an on-screen field error attached to the offending row) instead of the request falling through to the global JSON error handler'. The sibling POST /portal/tasks/:assignmentId/comments (tasks.tsx:651-682) does exactly what that comment forbids: it throws ApiError for an empty or over-cap body, so a speaker who writes past MAX_COMMENT_BODY_LENGTH (4000, declared at tasks.tsx:126) gets a raw JSON error and loses everything they typed — against the error standard's 'say what was kept' and 'count against limits'. The textarea itself (src/routes/portal/tasks/views.tsx:94) carries no maxlength and no line naming the cap, so the limit is invisible until it is enforced. Ruling: MAX_COMMENT_BODY_LENGTH moves to pure core (src/domain/files.ts, which views.tsx already imports for the upload vocabulary) so the form and the validator read ONE constant; the textarea declares it and says so in a quiet helper line; the comments POST re-renders the tasks page inline with the error on the offending row and the typed text still in the box, exactly like the upload path.

## Amendment (wave 58): one thread, one cap — every writer into a file_comment body enforces MAX_COMMENT_BODY_LENGTH, and the control that collects the text declares it

Verified on main: src/domain/files.ts:278-284 declares MAX_COMMENT_BODY_LENGTH = 4000 with the explicit reasoning that 'long-text form answers cap at 20000, but a deliverable reply thread is capped much tighter', and the portal reply enforces it (src/routes/portal/tasks.tsx:697) with a textarea + help text that declare it (src/routes/portal/tasks/views.tsx:118-121). The other TWO writers into the same file_comment row do not: src/routes/files.ts:519 (POST /api/v1/files/:fileId/comments — reachable by speakers as well as organizers, via authzFileWrite) and src/routes/content-notes.ts:67 (POST /submissions/:id/content-note, whose own comment says it writes 'the same row /files/:fileId/comments POST writes') both cap at MAX_LONG_TEXT_LENGTH = 20000. One column, one thread, two caps, five times apart — and the tighter one is the documented rule. Meanwhile the organizer's composer (app/src/pages/content/CommentThread.tsx:71) declares no cap at all, so the only way to learn the limit is to hit it. RULING: MAX_COMMENT_BODY_LENGTH is the cap for a file_comment body at every writer; MAX_LONG_TEXT_LENGTH governs form answers, not this thread. The admin composer declares the cap by importing it through the DEC-660 named crossing (app/src/lib/file-caps.ts) and states it in help text the way the portal does, and the refusal names the control's own label and counts the overage rather than printing a bare 'Max N'.

## Amendment (wave 28): a walkthrough check CREATES the state it asserts — an assertion inherited across a fixture change is a guess, and the deliverable panel is proven by uploading twice

task-w26-f's runtime receipt (docs/verification-log.md:3587-3621, docs/verification-log/task-w26-f-walkthrough-73f380f2.md) recorded the single J1-J12 failure at this tip: the DEC-244 deliverable panel row 'is missing version 2', scripts/walkthrough/speaker.ts:805. Diagnosed at main ceda66f2, it is the INSTRUMENT that is wrong, not the product. The assertion's own justification comment (speaker.ts:799-804) claims scripts/seed.ts's DEC-739 loop pre-completes this task at version_no=1 so the walkthrough's upload is a REPLACE landing at version 2 — but the assignment under test belongs to an ad hoc task the walkthrough itself CREATES at runtime (`Walkthrough ad hoc file task ${Date.now()}`, speaker.ts:719-742) and then assigns, which no seed-time loop can have pre-completed; seed's pre-completed file_request task is the separate seeded 'Upload your slide deck' (scripts/seed.ts, deliverableTaskId). The premise died when DEC-009's wave-59 amendment moved 'Finalize bio + headshot' from file_request to general kind and the lane was re-pointed at an ad hoc task while the assertion and its comment were carried over unchanged. This is the fourth instance of the identical shape (task-w9-d OPEN ITEMS 1-4: a walkthrough assertion outliving what it measured). RULING: the check uploads TWICE against the assignment it created — first upload asserts the panel at `version 1` with the Version-history row `v1` marked Current, second upload to the same /portal/tasks/:assignmentId/upload endpoint (the REPLACE path DEC-240/DEC-244 actually specify) asserts `version 2`, the new filename in the flat block, and BOTH `v1` and `v2` rows in the Version-history section with Current on v2. The coverage the old assertion intended is then genuinely exercised rather than inherited. The stale justification comment is DELETED, not softened. GENERAL RULE for every walkthrough lane: an assertion may depend only on state the same lane created, or on a seed literal it re-reads in the same run — never on a seed loop's assumed coverage of a row created at runtime.
