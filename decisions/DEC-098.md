# DEC-098: On-screen claim links only for contacts created in the same submit request; pre-existing contacts get the claim link by email only (amends DEC-014)

DEC-014 renders /claim/<token> on the confirmation page whenever the contact lacks a user row, but submit.tsx matches contacts by unverified submitter-typed email — so anyone typing an imported CRM contact's email mints an on-screen takeover link to that contact's entire portal (violates SPEC §6 object ownership / J7 absolute scoping). Ruling: the claim token is still always created and always emailed (dev sink locally, viewable at /dev/mailbox per DEC-005) whenever no user exists, but the confirmation page renders the claim URL ONLY when the contact row was created by this very request (nothing pre-existing to steal; email "ownership" is proven by the submitter having just supplied all the data). For a pre-existing contact without a user, the page says a password-setup link was emailed and links /login; existing-user behavior (link /login) is unchanged. Evaluability is preserved: eval and walkthrough flows submit fresh emails (producer.ts:416, scale.ts:372), so their on-screen claim path is untouched, and the emailed link is inspectable at /dev/mailbox with no inbox.

## Amendment (wave 2): the public CFP form gets NO "create an account" CTA — do not build it

An eval-coverage line asks for a visible "Create an account" CTA on /submit. The design authority (docs/design/README.md, "the password CTA has three states") explicitly rules it out: submitting needs no account, there is no public signup route, the only safe account path is the emailed claim link governed by DEC-098's three states on the CONFIRMATION, and a signup affordance beside Submit competes with the one action that matters. Ruling: never build it; the rubric line is answered by the confirmation's password CTA. Recorded so no future wave spends a lane on it.
