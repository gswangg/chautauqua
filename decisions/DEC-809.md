# DEC-809: A saved view re-saved under its own name is one view, and the directory headline states every figure it computes

The CRM P3 batch reports that saving a segment under an existing name creates a second identical segment — two rows with one name is a directory of ghosts, and the organiser's only repair is to delete the one they cannot tell apart. Separately VERIFIED src/server/repo/contacts/stats.ts computes eventCount and returningSpeakers, app/src/pages/contacts/types.ts declares them, and ContactsApp.tsx:195 renders only total/speakerCount/duplicateCount — the two figures that actually answer 'how deep is our speaker bench' are computed on every page load and shown to nobody. Decision: POST of a segment whose name already exists in this org UPDATES that segment's rules (a re-save is a save, not a twin) and the response says which id it wrote; deleting a saved view asks first, because a view is somebody's saved work. The directory headline states returning speakers and event reach alongside the counts already there, each with a word naming what it is — a number the API computes and the UI hides is a fact the product refuses to say. A database-level unique index on (orgId, name) is deliberately deferred: existing rows may already collide, and a dedupe migration is its own piece of work.
