# DEC-815: A settings section is a read-only summary until you ask to change it

VERIFIED DEC-728 built SummarySection and only three of the seven rail sections adopted it (EventSettingsPanel, CallForPapersPanel, TracksRoomsPanel). PublicPagesPanel, PortalSettingsPanel, PeopleRolesPanel and YourDataPanel still render live forms on landing, so /admin/settings teaches two grammars at once — four editable forms stacked under three summaries. Half an adopted pattern is worse than none, because the reader cannot tell which sections are safe to scan. Decision: all seven sections render label:value rows with ONE tertiary action on the section rule ('Change' / 'Edit the form' / 'Replace'), and the form appears only under ?section=<key>&edit=1 (DEC-728's URL state, so a form stays bookmarkable and Back leaves it). Adoption is proved by ENUMERATION, never a hand list: a test walks Settings.tsx's own SECTIONS array, renders each panel, and asserts a summary with no form control before the edit param is set — so a section added later cannot quietly opt out.

## Amendment (wave 44): a Settings section is named by its frame name, and that same string is its region label

The v6 frames name the sections "Public pages" and "Event"; the app renders "Public pages and embeds" (app/src/pages/Settings.tsx:47, PublicPagesPanel.tsx:155) and "EVENT SETTINGS". The heading text and the aria-label are the same string in this codebase's SummarySection idiom, so the rename is one edit per panel and the render tests assert on it — which is exactly why they must move together rather than drifting into a visible name and a different accessible name.
