# DEC-815: A settings section is a read-only summary until you ask to change it

VERIFIED DEC-728 built SummarySection and only three of the seven rail sections adopted it (EventSettingsPanel, CallForPapersPanel, TracksRoomsPanel). PublicPagesPanel, PortalSettingsPanel, PeopleRolesPanel and YourDataPanel still render live forms on landing, so /admin/settings teaches two grammars at once — four editable forms stacked under three summaries. Half an adopted pattern is worse than none, because the reader cannot tell which sections are safe to scan. Decision: all seven sections render label:value rows with ONE tertiary action on the section rule ('Change' / 'Edit the form' / 'Replace'), and the form appears only under ?section=<key>&edit=1 (DEC-728's URL state, so a form stays bookmarkable and Back leaves it). Adoption is proved by ENUMERATION, never a hand list: a test walks Settings.tsx's own SECTIONS array, renders each panel, and asserts a summary with no form control before the edit param is set — so a section added later cannot quietly opt out.

## Amendment (wave 44): a Settings section is named by its frame name, and that same string is its region label

The v6 frames name the sections "Public pages" and "Event"; the app renders "Public pages and embeds" (app/src/pages/Settings.tsx:47, PublicPagesPanel.tsx:155) and "EVENT SETTINGS". The heading text and the aria-label are the same string in this codebase's SummarySection idiom, so the rename is one edit per panel and the render tests assert on it — which is exactly why they must move together rather than drifting into a visible name and a different accessible name.

## Amendment (wave 4): a settings read view LISTS what it summarises; Change is for WRITING only

Gate-4 files "read views show lists" as a MAJOR for the third gate. Waves 1-2 landed it for People/roles, Public pages and Tracks-and-rooms, but `Your data` still reads "Submissions CSV, Contacts CSV, Schedule ICS, Everything JSON + more" and "Create and manage bearer API tokens for this event" (YourDataPanel.tsx:105-116), and `Speaker portal` still reads "Wiki pages and files speakers can access from their portal" (PortalSettingsPanel.tsx:166). A summary that DESCRIBES a list forces an organiser into write mode to read a fact — the drill exists for editing, not for looking. Ruling: every settings summary row whose value is a set renders the real rows at rest (exports as their real links, tokens as name/created/last-used, resources as their real titles), with creation/deletion controls still living only behind Change.

## Amendment (wave 41): a combined export fails per KIND, not per BUNDLE

YourDataPanel's 'Everything JSON' awaits six per-kind exports in a loop (app/src/pages/settings/YourDataPanel.tsx:87-108); the first kind that refuses (over-cap, per DEC-027 above) aborts the loop, downloads nothing, and shows one message that does not say which kind failed. That is the house boundary rule inverted — the swarm already ruled that a boundary fails per RECIPIENT, not per REQUEST (mail), and that a truncated read must disclose rather than vanish (DEC-468). Ruling: the bundle collects every kind independently, downloads what succeeded, and names each skipped kind with the server's own reason, so the largest customer still leaves with their data instead of an error.

## Amendment (findings wave 4): a settings edit section head carries its count and its add action; the form footer owns the only filled primary

docs/design/Chautauqua Settings.dc.html:819-841 draws the tracks-and-rooms edit screen with `Tracks · 3` / `Rooms · 4` over a 2px rule and a right-flushed TERTIARY link `Add a track` / `Add a room`; the full-width dashed add bar only appears in the 390 frame, so it is phone grammar. On main TracksRoomsPanel.tsx:553 renders `Add track` as `chq-btn chq-btn-primary`, giving one screen two olive primaries whose scopes differ (add one row vs save the form) — the same defect DESIGN-RULINGS A1 rejected on the content worklist. Ruling: in a settings edit view the section head owns the add affordance as a tertiary action beside its `LABEL · N`, and the form footer's Save is the view's only filled primary.
