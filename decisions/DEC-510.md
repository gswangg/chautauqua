# DEC-510: Event start/end dates are strict ISO YYYY-MM-DD, validated at the API boundary, with ONE isIsoDate home

Verified at file:line. src/routes/api/events.ts validates startDate/endDate only as non-empty strings (requireString, :208-209 and :284-285) plus an ORDER check (isDateOrderValid, src/routes/api/validators.ts:32-37) built on `Date.parse`, which happily accepts `'August 5, 2026'`, `'2026-8-5'`, and any other locale form. Nothing downstream tolerates that: `computeDays` (the former src/server/repo/agenda.ts:29-33 (now split across src/server/repo/agenda/)) builds `new Date(`${startDate}T00:00:00Z`)` and throws `computeDays: invalid date range`, 500ing the producer's agenda; `isDayWithinEventRange` (:45-46) compares raw strings, so `'2026-08-06' >= 'August 5, 2026'` is false and src/routes/agenda.ts:74 rejects every legitimate slot write as 'Slot day is outside the event date range' while the public agenda silently drops every placement. The failure is loud in the wrong place — an internal helper — because the boundary that owns external input never checked format. The codebase already knows the rule: src/routes/public/query.ts:36 carries `DAY_RE = /^\d{4}-\d{2}-\d{2}$/` on the read path. Decision: one exported `isIsoDate` in src/routes/api/validators.ts (regex AND a calendar round-trip so 2026-02-30 and 2026-13-01 fail), applied to both dates in POST and PATCH before the order check, and DAY_RE deleted in favour of that single home — two implementations of one invariant means one is wrong (w24 lesson). Scope note: only the two event date columns are in scope; task due dates are already ms-epoch numbers and validated.
