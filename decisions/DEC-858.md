# DEC-858: Two names differing only by case are the same name at an irreversible merge; and a skip control belongs on every row it can skip

VERIFIED, two Contacts affordance defects that both break the standing rule that a control must tell the truth about what it can do. (a) MergePage.tsx:129-132 computes namesCollide by comparing `${first} ${last}` raw and case-SENSITIVELY, while the column headers render CSS-uppercased — so 'PARKER anders' and 'Parker Anders' produce two headers reading PARKER ANDERS with no disambiguator, at the one screen in the product whose action cannot be undone. The duplicate DETECTOR that put those two records on screen together already normalizes (src/domain/contacts.ts:56-61 `normalizedName`, lowercased + whitespace-collapsed) — the merge screen just doesn't use it, because it is a private function. Decision: export it as the one name-identity rule and consume it in MergePage, the same way app/src already imports PARTICIPANT_ROLE_OPTIONS straight out of src/domain. (b) ImportWizard.tsx:330-375 heads a column 'Skip this row' and captions 'N row(s) marked to skip', but renders the checkbox only when `decorated` (the row has an overwrite or a possible duplicate) — so on a clean import there is a promised column with no controls in it, which is precisely what the CRM grader reported. Skipping is possible on EVERY row; the checkbox renders on every row, and the decorated detail list stays conditional. The affordance rule is 'controls render only when their action is possible', not 'only when the row is interesting'.
