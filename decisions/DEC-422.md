# DEC-422: Free-text caps and the public rate limiter extend to the two write paths DEC-417's scope does not reach

DEC-417 is scoped to 'every admin JSON mutation route'. Two write paths outside that set take unbounded client free text on this tree. (1) POST /submit/:eventSlug/save-draft (src/routes/public/submit.tsx:465-508) is fully public and has NO rate limit at all — unlike POST /submit/:eventSlug in the same file, which has carried the DEC-057/DEC-072 scoped limiter since — and writes extractAnswers' output straight into KV via saveDraft, so an unauthenticated caller buys unmetered KV writes and can push a value past KV's size ceiling into an uncaught 500. SPEC §6 says 'Rate limits on auth + public submission'; a draft save is a public submission write. (2) POST /portal/profile (src/routes/portal/profile.tsx:252-287) writes firstName/lastName/title/company/bio and four social links to `contact` with no length check whatsoever — the identical D1 SQLITE_TOOBIG 500 DEC-417 names, on a speaker-authenticated route DEC-417 will not touch. Rule, stated once: the caps are the ones ALREADY exported from src/forms/validate.ts (MAX_TEXT_LENGTH for single-line values, MAX_LONG_TEXT_LENGTH for bio/long text) so the portal, the public form and the admin API agree on what 'too long' means and no lane invents a third vocabulary; an SSR form post reports oversize by re-rendering ITS OWN page with an error naming the field at HTTP 400 (never a JSON error envelope, never a 500, never a silent truncation); and save-draft takes the same checkAndIncrementScopedLimit the real submit uses, under its own scope, so a draft flood cannot bypass the submit budget.

## Amendment (wave 57): a server-side text cap lives in pure core and the control that collects the text declares it — a cap declared inside a route can never reach the client

src/routes/tasks.ts:81 declares MAX_INSTRUCTIONS_LENGTH=2000 inside a route module, which by DEC-002's purity rule the SPA can never import; the New-task Instructions textarea therefore accepts unlimited typing and only learns the cap by being refused after submit. The two caps that ARE already pure core (MAX_CRITERION_GUIDANCE_LENGTH in src/domain/evaluation.ts:147, PIPELINE_RATIONALE_MAX_LEN in src/domain/pipeline-fit.ts:19) are equally invisible: neither the plan-editor guidance input nor either pipeline rationale input declares maxLength. The rule: every server-enforced text length lives in src/domain/*, and every control that collects that text declares the same constant by import — never a re-typed number (w54's shape: A CONSTANT DECLARED IN A ROUTE CANNOT CROSS TO THE CLIENT, SO THE CLIENT WILL RETYPE IT). A scan keeps route modules out of the cap-declaring business.

## Amendment (wave 59): a BATCH cap (recipients, rules, rounds, bytes) is pure core on the same terms as a text cap — a route module cannot declare one

DEC-422's wave-57 amendment ruled that a server-enforced text length lives in src/domain/* and the control that collects the text declares it by import, and backed it with test/text-cap-declaration.scan.test.ts. That scan is keyed on the NAMES `*_LENGTH`/`*_MAX_LEN`, so the same class of cap under a `MAX_*` name is unguarded, and four of them sit in route modules the SPA can never import (DEC-002 purity): src/routes/api/contacts/segments.ts:25 MAX_SEGMENT_RULES=20 — whose own comment says it is "deliberately local to this file … to avoid a merge collision within the same wave", a stated reason that expired dozens of waves ago (w55's shape: a defect with a timer); src/routes/review/shared.ts:175 MAX_PLAN_ROUNDS=10; src/routes/api/contacts/import.ts:29 MAX_IMPORT_CSV_BYTES=5,000,000; and src/routes/api/contacts/bulk-email.ts:25 MAX_BULK_EMAIL_RECIPIENTS=100, which is a second literal for the SAME DEC-019 100-recipient batch cap the client already imports from src/domain/compose.ts as MAX_COMPOSE_RECIPIENTS — two constants that agree today only because nobody has moved either. RULING: every product cap on a batch — how many recipients, how many rules, how many rounds, how many bytes — lives in src/domain/*, is declared exactly once, and the control that collects toward it declares the same constant by import. The bulk-email route stops declaring a private twin and imports the one recipient cap. A sibling scan bans `const MAX_… = <number>` anywhere under src/routes/** (.ts AND .tsx), with a named, non-expiring allowlist for the one genuine route-shape bound (validators.ts's MAX_EPOCH_MS: a JSON-field ceiling no control collects toward).

## Amendment (wave 61): one contact field, one cap, whichever role is typing; and one overage grammar for the refusal

contact.firstName/lastName/title/company are bounded at MAX_NAME_LENGTH=200 by the CRM (src/routes/api/contacts/crud.ts:103-113, 273-297) and at MAX_TEXT_LENGTH=2,000 by the speaker portal (src/routes/portal/profile.tsx:182-194, 317-325, in both the input maxLength and the server check). J7's headline promise is 'one record, two views': a speaker sets a 500-character company on their own profile, it lands on the producer's record, and then the producer's contact drawer cannot save ANY edit to that contact — the whole record is PATCHed and 400s on `company: Max 200` with no way forward. bio correctly agrees (MAX_LONG_TEXT_LENGTH both sides) and the four social links correctly agree (MAX_TEXT_LENGTH both sides), which is exactly why the four that disagree are drift, not design. The CRM wins the number (200 is the human cap for a name/title/company). Separately, the two sides speak different refusal languages for the same failure: the portal names the overage ('Company is 34 characters over the limit. Nothing else was saved.'), the CRM says 'Max 200' — the recorded error-and-validation standard requires counting against the limit. One exported helper in src/domain/count-copy.ts produces the overage phrase for both.

## Amendment (wave 67): landed

MAX_FORM_FIELDS moved to src/domain/form-copy.ts, MAX_BREAKS_PER_EVENT to src/domain/schedule.ts, MAX_PARTICIPANTS_PER_SUBMISSION to src/domain/participant-roles.ts -- each declared exactly once, with every former importer (src/routes/api/forms.ts, src/routes/api/breaks.ts, src/server/repo/breaks.ts's own read-side check) switched to import the pure-core constant directly rather than through a repo re-export. src/server/repo/portal-edit.ts's addCoPresenter refusal now reads "This submission already has {count} of the maximum {MAX_PARTICIPANTS_PER_SUBMISSION} participants allowed", naming the real row count already read instead of a hard-typed "(5)" -- so a submission that already carries an organiser-invited participant is told the truth about its remaining co-presenter headroom rather than a number that assumes zero organiser-invited rows.

test/batch-cap-declaration.scan.test.ts's population widened to src/server/repo/** alongside src/routes/**, with a categorical exemption for the six query-bound name suffixes above (each excused by shape, not by file) plus three named, live allowlist entries with their own reasons: validators.ts's MAX_EPOCH_MS (a wire-format value bound, not a batch cap), contacts/history.ts's MAX_CONTACT_HISTORY_SUBMISSIONS/MAX_CONTACT_HISTORY_EMAILS (bounded-scan slices, same shape as the _SCAN/_ROWS suffix class but pre-dating the suffix convention), and public/bounds.ts's MAX_PUBLIC_PAGE (an anti-scrape pagination-depth bound, not a control-collected cap).

The two disclosed caps cross the app/ -> src/ boundary through a new app/src/lib/batch-caps.ts (same crossing-module discipline as merge-fields.ts/file-caps.ts -- never a raw ../../../src/domain import from a page, except BreaksPanel.tsx's pre-existing OPTIONAL_SUFFIX import, left untouched as out of this task's scope). FormsPage.tsx prints "N of MAX_FORM_FIELDS questions" beside Add-a-question; BreaksPanel.tsx prints "Up to MAX_BREAKS_PER_EVENT breaks per event" beside its add-break button (a static per-event ceiling, not a live per-event count, since the panel only holds the selected day's breaks).

## Amendment (w1): ONE over-cap refusal grammar; `Max ${N}` is banned and no module may regex-parse a sibling's error prose

Verified at the file: the repo has FIVE grammars for one event. (1) `Max ${N}` — a bare number with no unit and no separator ('Max 2000', 'Max 20000') at ~35 sites across 18 modules (routes/tasks.ts:218,227,301,310; comms/templates.ts:45,47,49,75,80; comms/compose-core.ts:135,140; api/portal-config.ts x7; api/events.ts:137; api/forms.ts:172; api/tokens.ts:81; api/submissions.ts:122; api/pipeline.ts:67,309; api/contacts/{import,bulk-email,segments,crud}.ts; api/import.ts:48,80; review/plans-crud.ts:67,69,115,118; review/reviewer.ts:411; server/repo/portal-edit.ts:474,476; server/http.ts:100,134; domain/files.ts:186,468; domain/evaluation.ts:273). (2) `Too long (max ${cap} characters)` (validate.ts:104). (3) `Too long by 1,234 characters — keep it to 5,000 characters or fewer` (files.ts:540-541, content-notes.ts:72-73). (4) `212 characters typed — 12 over the 200-character limit` (submit-messages.ts:24). (5) `Too long (max 2,000 characters)` (tasks.ts:99). Meanwhile the ONE helper this decision already created — overBudgetBy in src/domain/count-copy.ts — has exactly TWO callers. A component that exists and isn't called is a rule that isn't enforced. Worst of all, submit-messages.ts:11 recovers the number by regex-matching validate.ts's English (`/^Too long \(max (\d+) characters\)$/`): the moment the validator adopts the separator the design standard demands, that regex silently stops matching and the public CFP falls back to the raw string. The V9 error standard requires 'count against limits'. Ruling: one src/domain/cap-copy.ts built on overBudgetBy/countOf, every refusal routed through it, the regex deleted, and a scan that bans both the bare `Max ${` literal and any regex matching another module's prose.

## Amendment: a request-body collection must declare a CARDINALITY bound in pure core; a cap that exists only in the SPA is not a cap (wave 2)

DEC-422's scans police WHERE a cap is declared (test/batch-cap-declaration.scan.test.ts, test/text-cap-declaration.scan.test.ts). Neither can see a collection with no cap at all, and neither walks app/src. Verified: src/forms/builder.ts caps each dropdown option at MAX_NAME_LENGTH but never bounds how MANY options a field carries; validateRuleReference does not type- or length-check rule.value for a text trigger and never bounds the 'in' array; src/routes/review/shared.ts's parseCriteriaList bounds nothing about list length, criterion id length, or a dropdown criterion's option count/length; src/server/repo/views.ts's isValidSavedViewConfig accepts q/columns/trackId of any size; src/routes/api/contacts/crud.ts bounds each customFields value but not the key count or key length. ## Amendment (findings wave 10): the per-event saved-view cap counts the caller's OWN views, never other organisers' shared ones

MAX_SAVED_VIEWS_PER_EVENT documents itself as 'max saved views ... one organiser may create per event' (src/domain/saved-views.ts:15-17), but the POST enforces it against countSavedViews(db, eventId, auth.userId) (src/routes/api/views.ts:84), whose predicate is DEC-904's visibleToViewer — `shared = 1 OR createdBy = me` (src/server/repo/views.ts:96-127). Once 50 shared views exist on an event, an organiser with zero of their own can never create one, and cannot delete anyone else's to make room because the DELETE gate correctly refuses non-authors (routes/api/views.ts:112-119). That is an unrecoverable lockout produced by a colleague's work, and it contradicts the constant's own contract. RULING: the cap predicate is authorship, not visibility. countSavedViews keeps DEC-904's visibleToViewer predicate — it is the true `total` for a paged, visibility-scoped list and must not change — and a SEPARATE countSavedViewsCreatedBy(db, eventId, createdByUserId) counts only rows the caller authored (legacy createdBy = null rows are org-owned, not anyone's, and are excluded). The refusal copy names the author scope ('You already have the maximum of N saved views on this event.') so the cap message matches the cap it enforces.

## Amendment (wave 54): the draft cap loop bounds every value SHAPE, not just strings — an array answer is bounded by count and by per-entry length before saveDraft, never truncated

DEC-422 exists because save-draft is an otherwise-unmetered anonymous KV write path, and its stated rule (src/routes/public/submit-draft.tsx:73-75) is to reject any answer over its field-kind cap before it ever reaches saveDraft. The loop at :76-97 inspects only `typeof value === "string"`, and the reserved `__trackIds` key is written AFTER it (:127) from extractTrackIds (submit-body.ts:75-80), which does a Set-dedupe and no bounding at all — so an unauthenticated POST bounded only by the 100 MB body ceiling lands an arbitrarily large array in a 30-day KV record, 60 times an hour per IP. This is a SIZE ruling and deliberately does not reopen task-w49-h's ruling that MEMBERSHIP validation is not owed on the draft path (a draft is the submitter's own scratch value, validated for real by validateTrackChoice at final submit): that lane answered whether the values must be legal, never whether there may be unboundedly many of them. Bound by count (MAX_SUBMISSION_TRACK_IDS) and per-entry length (MAX_TEXT_LENGTH); refuse loudly with the surface's own re-render, never truncate, never persist a refused draft.

## Amendment (wave 77): two doors that write one table spend ONE named cap, and an inline numeric argument is the same second copy as a const

VERIFIED at main. "How many people may one task write name" has four independent authors and two different answers. src/routes/tasks.ts:316 (create) passes a bare inline `{ maxCount: 200 }`; src/routes/tasks.ts:487 (assign) passes nothing and silently takes DEFAULT_BOUNDED_ID_ARRAY_MAX = 1000 (src/server/http.ts:71) — two doors onto the same task_assignment write, five-fold apart. The SPA writes the number three more times as a bare literal: app/src/pages/speakers/OnboardingGrid.tsx:346 (`perPage=200`), :350 (`res.total > 200`) and app/src/pages/speakers/TaskModal.tsx:362 (the ceiling copy, "200 this picker can list"), because MAX_PER_PAGE (src/lib/pagination.ts:10) is declared without `export` and the SPA cannot reach it. test/batch-cap-declaration.scan.test.ts cannot see any of this: its fingerprint is `const MAX_[A-Z0-9_]* = <number>`, a DECLARATION SHAPE, so a cap spent as an inline argument or a JSX literal walks straight past the guard that exists to catch it. RULING: the ceiling is not a page size that happens to be reused — it is its own fact, MAX_TASK_ASSIGNEES, declared in pure core (src/domain/task-kinds.ts, already the task vocabulary's home) and spent by BOTH route doors, by the picker's fetch, by its truncation test and by its ceiling copy, crossing the app/ boundary through exactly one re-export module in the DEC-660 style. Because the picker can only ever fetch what the pagination clamp allows, a test pins the invariant that clampPerPage(MAX_TASK_ASSIGNEES) === MAX_TASK_ASSIGNEES — the ceiling must be one the picker can actually reach, not a number that silently truncates.

## Amendment (wave 77): landed, and the scan's blind spot is now stated rather than widened

MAX_TASK_ASSIGNEES=200 lives in src/domain/task-kinds.ts (the task vocabulary's existing home) with prose naming it as the largest assignee set one task write may name, not a page size that happens to match. Both parseBoundedIdArray call sites in src/routes/tasks.ts (create at the contactIds-subset check, assign at the assign handler) now pass `{ maxCount: MAX_TASK_ASSIGNEES }` — no bare number survives at either door, and a route test (test/task-assignees-max-cap.test.ts) proves both refuse at the same count with the same shaped 400. The app/ -> src/ crossing is app/src/lib/batch-caps.ts (the existing DEC-422 crossing module for per-event/per-form batch caps — this is a batch cap, not a vocabulary, so it belongs beside MAX_FORM_FIELDS/MAX_BREAKS_PER_EVENT/etc rather than in domain-caps.ts's unrelated crossing). OnboardingGrid.tsx's subset-picker fetch (`perPage=${MAX_TASK_ASSIGNEES}`, `res.total > MAX_TASK_ASSIGNEES`) and TaskModal.tsx's ceiling copy now read the constant instead of retyping 200.

GAP, stated rather than closed here: test/batch-cap-declaration.scan.test.ts's fingerprint is a DECLARATION SHAPE (`const MAX_[A-Z0-9_]* = <number>` in src/routes/** or src/server/repo/**). It can only ever catch a cap that is DECLARED without export in the wrong module — it was never built to catch a cap that IS correctly declared in pure core but then SPENT as a bare inline argument (`{ maxCount: 200 }`) or a JSX literal at the call site, which is exactly how this defect survived. Widening that scan's fingerprint to also flag inline numeric literals passed to known cap-shaped parameters (maxCount, perPage, etc.) is a distinct, larger change — out of this lane's scope — and is left as an open gap for a future wave rather than attempted here.

## Amendment (wave 82): a Choice criterion's options are bounded 2..6 by the control AND by the server, from one declared pair

The design ruling is explicit that a scoring criterion is the opposite case from a CFP field: two to six short strings whose order is the order reviewers see, with the bound enforced BY THE CONTROL rather than asserted in prose. Today `MAX_CRITERION_OPTIONS = 20` (`src/domain/evaluation/criteria.ts:50`) and the only floor is non-empty (`src/routes/review/shared.ts:136`). Ruling: `MIN_CRITERION_OPTIONS = 2` and `MAX_CRITERION_OPTIONS = 6`, both declared in the pure core and spent by BOTH doors — the SPA's rows control (Remove disabled at two, Add-an-option hidden at six, counter "3 of 6") and the server's refusal. No seeded or fixture plan exceeds three options, so no migration and no compatibility branch (house rule). The comma-separated single input at `PlanEditor.tsx:1771-1797` is replaced by rows, deliberately diverging from FieldModal's textarea, which keeps it because 40 pasted options is a real case there.

## Amendment (wave 2): a Choice criterion carries 2 to 6 options — the ruling's prose bound binds, and a lone option is refused server-side

The v12 DESIGN-RULINGS §'Review criteria — Scale or Choice' states the 2-6 bound twice and then makes it a control behaviour ('Remove disabled at two — the bound enforced by the control rather than asserted in prose'). Today src/domain/evaluation/criteria.ts:50 declares MAX_CRITERION_OPTIONS = 20 and src/routes/review/shared.ts:136 refuses only the EMPTY array, so a one-option Choice criterion — a radio row with a single answer, which records nothing — is legal on the wire. This is the mirror of DEC-746's lesson: a bound the UI enforces and the server does not is a promise with an expiry date, and w82-f is building that control right now. Distinguish carefully from the DEC-650 wave-82 lesson: 'a frame carries two kinds of number' — the FieldModal's '3 of 40' was placeholder content inside a drawing and did not bind; 2-6 is a sentence in the ruling and a stated control behaviour, so it does. MIN_CRITERION_OPTIONS = 2 is declared beside the max, both single-sourced, both enforced in the one parser.
