# DEC-552: An upsert over a UNIQUE index is ONE atomic statement — the five surviving SELECT-then-INSERT-or-UPDATE pairs become INSERT ... ON CONFLICT

src/db/schema.ts declares eleven uniqueIndexes, and exactly one write path in the product respects them atomically: upsertSubmissionAnswers (src/server/repo/submit.ts:306, DEC-541). Five others still read first and write second, over columns the schema has already made unique: upsertSlot (repo/agenda.ts:388-421, schedule_slot_submission_id_idx at schema.ts:432), upsertEvaluation (repo/review/evaluations.ts:179-219, evaluation_plan_submission_reviewer_round_idx at :350), upsertPortalSettings (repo/portal-config.ts:102-133, portal_settings_event_id_idx at :505), createRecusal (repo/review/recusal.ts:33-51, review_recusal_plan_submission_user_idx at :376) and enrollContact (repo/pipeline.ts:196-227 behind a route-level pre-check at routes/api/pipeline.ts:93-94, pipeline_entry_org_id_contact_id_idx at :669). Every one of these is on a path SPEC §7 names as high-frequency and concurrent: drag-drop placement, reviewer ratings, status pills — with "5-15 team members working concurrently". Two racing requests both read "absent" and both INSERT; the loser gets a raw SQLite UNIQUE violation, i.e. a 500 and an optimistic-UI rollback, on an operation that is semantically idempotent. This is the standing rule the field guide already carries ("a uniqueIndex makes read-then-write loops an atomic ON CONFLICT DO UPDATE"; "two implementations of one invariant means one is wrong — atomic SQL beats read-then-write"), applied to every remaining site rather than the one that got caught.

Decision: (a) each of the five becomes a single INSERT whose ON CONFLICT target is the exact column list of its declared uniqueIndex, referenced through the schema objects so a schema change breaks the compile rather than the behavior. (b) Value-merge semantics are preserved without a read: a single-row upsert sets literal values, and upsertPortalSettings's partial-patch merge becomes "insert defaults, on conflict SET only the keys the caller actually supplied" — which is what mergePortalSettingsInput(existing, input) computes anyway. (c) Where the caller distinguishes created-vs-existed (createRecusal's 201/200, enrollContact's duplicate 400), the distinction is derived from the atomic statement's own .returning() result, and the now-redundant route-level pre-check is DELETED rather than left in place — a losing duplicate is not kept (no-backwards-compat rule). (d) The regression bar is statement-shaped, not state-shaped: a fake-db harness (modelled on test/portal-edit-answer-upsert.test.ts) asserts ZERO selects against the target table before the write and exactly one write statement, and asserts the ON CONFLICT target equals the uniqueIndex's columns read from src/db/schema.ts.
