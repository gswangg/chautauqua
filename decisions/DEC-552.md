# DEC-552: An upsert over a UNIQUE index is ONE atomic statement — the five surviving SELECT-then-INSERT-or-UPDATE pairs become INSERT ... ON CONFLICT

the former src/db/schema.ts (now split across src/db/schema/) declares eleven uniqueIndexes, and exactly one write path in the product respects them atomically: upsertSubmissionAnswers (src/server/repo/submit.ts:306, DEC-541). Five others still read first and write second, over columns the schema has already made unique: upsertSlot (repo/agenda.ts:388-421, schedule_slot_submission_id_idx at schema.ts:432), upsertEvaluation (repo/review/evaluations.ts:179-219, evaluation_plan_submission_reviewer_round_idx at :350), upsertPortalSettings (repo/portal-config.ts:102-133, portal_settings_event_id_idx at :505), createRecusal (repo/review/recusal.ts:33-51, review_recusal_plan_submission_user_idx at :376) and enrollContact (repo/pipeline.ts:196-227 behind a route-level pre-check at routes/api/pipeline.ts:93-94, pipeline_entry_org_id_contact_id_idx at :669). Every one of these is on a path SPEC §7 names as high-frequency and concurrent: drag-drop placement, reviewer ratings, status pills — with "5-15 team members working concurrently". Two racing requests both read "absent" and both INSERT; the loser gets a raw SQLite UNIQUE violation, i.e. a 500 and an optimistic-UI rollback, on an operation that is semantically idempotent. This is the standing rule the field guide already carries ("a uniqueIndex makes read-then-write loops an atomic ON CONFLICT DO UPDATE"; "two implementations of one invariant means one is wrong — atomic SQL beats read-then-write"), applied to every remaining site rather than the one that got caught.

Decision: (a) each of the five becomes a single INSERT whose ON CONFLICT target is the exact column list of its declared uniqueIndex, referenced through the schema objects so a schema change breaks the compile rather than the behavior. (b) Value-merge semantics are preserved without a read: a single-row upsert sets literal values, and upsertPortalSettings's partial-patch merge becomes "insert defaults, on conflict SET only the keys the caller actually supplied" — which is what mergePortalSettingsInput(existing, input) computes anyway. (c) Where the caller distinguishes created-vs-existed (createRecusal's 201/200, enrollContact's duplicate 400), the distinction is derived from the atomic statement's own .returning() result, and the now-redundant route-level pre-check is DELETED rather than left in place — a losing duplicate is not kept (no-backwards-compat rule). (d) The regression bar is statement-shaped, not state-shaped: a fake-db harness (modelled on test/portal-edit-answer-upsert.test.ts) asserts ZERO selects against the target table before the write and exactly one write statement, and asserts the ON CONFLICT target equals the uniqueIndex's columns read from the former src/db/schema.ts (now split across src/db/schema/).

## Amendment (findings wave 14): a UNIQUE index guarded by SELECT-then-INSERT is still a 500 under a race — the constraint IS the check, and its violation is translated into the route's own already-documented refusal

createUser (src/server/repo/users.ts:85-111) documents 'Throws ApiError(conflict) on duplicate email (user_email_idx is unique)' but implements it as SELECT-then-INSERT with no onConflict handling, so a concurrent POST /api/v1/users — or a race with the speaker-account insert at src/routes/auth-claim.tsx — surfaces a raw D1 UNIQUE failure as a 500 `internal` instead of the documented 409. createEvent (src/server/repo/events.ts:160-175) has the identical shape behind isSlugTaken against the globally-unique event_slug_idx. Both contradict DEC-552's own finding, already applied everywhere else (submissions/status.ts:100,167, forms.ts:195, participants.ts:117, segments.ts:66). RULING: both writers make the DB constraint the authority — insert atomically, and translate the constraint outcome into the SAME ApiError the pre-check already raises: 409 `conflict` with fields {email: 'already in use'} for users, 400 `invalid` with fields {slug: 'Already in use'} for events. Each keeps its EXISTING status code and copy; this ruling changes only where the refusal comes from, never what the caller sees. The pre-read may stay as a fast path but is never the only gate. No schema change, no migration.
