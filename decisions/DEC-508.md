# DEC-508: Dropdown options are required when a PATCH CHANGES a field's kind to 'dropdown', not merely when options are sent

Verified at file:line on current main. DEC-505 landed (src/server/repo/forms.ts:277-315 FieldPatch now carries kind+section; src/routes/api/forms.ts:222-231 409s a kind change over stored answers), and that re-opened DEC-500's hole from the other side. src/forms/builder.ts:116-124 requires non-empty dropdown options only `if (input.options !== undefined || existing === undefined)` — a guard written when `kind` was immutable on PATCH, so that a partial patch (`{label:'x'}`) on a live dropdown would not force re-sending options. Now that kind is patchable, `PATCH /api/v1/fields/:fieldId` with body `{"kind":"dropdown"}` and no `options` takes the skip branch: effectiveKind is 'dropdown', options is undefined, existing is set, so nothing is validated; patchField writes kind='dropdown' while optionsJson stays NULL (it only clears options when the kind moves AWAY from dropdown, forms.ts:291). Every subsequent answer then fails `!(field.options ?? []).includes(value)` (src/forms/validate.ts:92) — an unsatisfiable required dropdown no submitter can ever pass, created with a 200 and no error. DEC-505's own text asserts "DEC-500's effective-kind rule already forces non-empty options in the same request"; that claim is false against the code. Decision: the options requirement fires whenever the field is not ALREADY a dropdown — `input.options !== undefined || existing === undefined || existing.kind !== 'dropdown'`. This preserves the partial-patch exemption exactly (a dropdown staying a dropdown), and closes the only path that can produce an optionless dropdown. The rule stays in the pure validator, not the route, because both create and patch must obey it identically.
