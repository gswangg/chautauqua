# DEC-560: Every export is deterministically ordered — rows totally ordered, and every list-valued cell in a declared order

There is not one ORDER BY in src/server/repo/exports/. exportSubmissions (:104), exportSpeakers (:51), exportEvaluations (:140) and exportEmailLog (:19) return rows in whatever order SQLite happens to produce; exportAgenda sorts only by (day, startMin), which does not order two sessions in different rooms at the same time; showflow sorts partially. List-valued cells are worse: `tracks` is materialized from a Set built in arbitrary row order, so the same session exports as "AI; Infra" or "Infra; AI" run to run, and speaker lists tie whenever two participants share participant.order (the common case — the public submit path writes order 0). J12 is "The data stays theirs" and SPEC §3 sells own-your-data as a reason to switch: a CSV whose row order changes between two exports of unchanged data cannot be diffed, cannot be re-imported reproducibly, and cannot be trusted as the escape hatch that makes cancelling the contract possible. Two of these are worse than untidy — an agenda export not fully ordered by (day, start, room) is not an agenda, and the show-flow export (SPEC §10 #7: "final titles, full speaker lists, intro text, deck locations") IS a running order, so an arbitrary one is unusable on the day. Decision: (a) every export's row query ends in a unique column: submissions and showflow by (seq), speakers by (lastName, firstName, contact.id), evaluations by (submission seq, reviewer id, round, evaluation.id), email-log by (sentAt desc, emailLog.id), agenda by (day, startMin, roomName, seq). (b) every list-valued cell declares its order: tracks sorted by name, speakers by (participant.order, contact.id) so a shared order never leaves the pair arbitrary. (c) the JS sorts already present are kept but extended to a total order rather than replaced — the ORDER BY does the work, the JS sort becomes the tiebreak of record. (d) no row cap is introduced and the omission is dispositioned here so it is not re-raised: an export that refuses is a lock-in, which is the one thing J12 forbids; SPEC §7's oversized-read budget governs interactive reads, and this surface is a deliberate whole-dataset read behind an organizer-only, attachment-disposition route. (e) the regression bar is repeatability: shaping the same input rows twice, once shuffled, must produce byte-identical CSV.

## Amendment (wave 60): a per-contact export cell aggregated from several rows must state WHICH row wins, and `visible` must mean what the public page means

DEC-560 requires every export to be deterministically ordered, and exportSpeakers (src/server/repo/exports/speakers.ts) honours that for ROWS (sorted by lastName/firstName/contactId) while breaking it for CELLS: the driving participant join has no ORDER BY (:36-55) and the aggregation takes the FIRST row seen for company/title/bio (:78-96), so a speaker on two submissions exports whichever frozen DEC-258 title/org the driver happened to return — two exports of unchanged data can differ. The same loop ORs `visible` across participants of submissions in ANY status, so the column reads true for a speaker whose only visible participant row hangs off a pending or content-unapproved submission — a speaker who will never appear on the public speakers list. J12's promise is that the export is the same fact as the screen beside it (DEC-649 already holds the submissions export to exactly that), so a `visible` column that disagrees with /e/:slug/speakers is a lie in the file the customer takes with them. RULING: the query gains a total order; company/title resolve from the contact's ACCEPTED participant row (lowest submission seq), falling back to the first row overall when they have none; and `visible` is computed from the same three facts the public gate composes — participant.visible AND inviteStatus in ACTIVE_INVITE_STATUSES AND submission accepted AND content_status approved — with the columns selected into the same single query and a comment naming src/server/repo/public/gates.ts as the predicate it mirrors, never a restated literal.
