# DEC-275: cloneSubmission copies ACTIVE participants (invite_status none|accepted) as invite_status 'none'; a participant-less submission is a legitimate TBA session and acceptance planning is a documented no-op for it

J3 names cloning as the invited-talk workflow, but cloneSubmission (src/server/repo/submissions/create.ts:125) copies submission_track and submission_answer rows and stops -- the clone has no speakers, so with DEC-274 it renders speaker-less and, on acceptance, produces no onboarding tasks (src/server/repo/submissions/status.ts:113 returns early on an empty participant set). Copying participants is the obvious repair, but WHICH ones is a design question, so I answer it here rather than leaving it to a worker: copy only rows whose invite_status is 'none' or 'accepted'. An 'invited' row is an unanswered question about a DIFFERENT session and a 'declined' row is a refusal; neither transfers. Copied rows are inserted with invite_status 'none' -- the same state createSubmission uses for an organizer-attached contact (create.ts:95) and submit.ts uses for a CFP submitter (submit.ts:214), meaning 'no coordination pending'. role/order/visible and DEC-258's frozen titleAtTime/orgAtTime are copied verbatim from the stored columns, never re-read from the live contact. The residual case -- an accepted submission with zero participants -- is NOT a bug to throw on: it is a manually created TBA session, and after DEC-274 it is publicly visible with an empty speaker line, which is what an event producer wants. It gets a comment and a test, not an exception.
