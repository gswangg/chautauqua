# DEC-995: A served file's Content-Type is the validated DB column; the object store returns bytes and never a content type

SPEC.md §6's guarantee that no user content is served with an HTML content type is enforced at UPLOAD time by validateUpload's extension allowlist (src/domain/files.ts:113-166), which writes file.content_type. Five serve paths then throw that guarantee away by preferring mutable R2 object metadata: src/routes/files.ts:486, src/routes/portal/tasks.tsx:520 and :560, src/routes/portal/tasks/resources.tsx:47 and src/routes/portal/profile.tsx:442 all read `obj.contentType ?? <db column>`, and files.ts:491 makes the inline-vs-attachment decision from that same untrusted value — so an object whose metadata reads image/svg+xml is served inline, same-origin. Five copies of one mistake means the fix cannot be five edits: makeFileStore's get() (src/server/context.ts:95) stops projecting httpMetadata?.contentType and the FileStore return type loses the field, so TypeScript makes the wrong source unreachable rather than merely unused — hide a transitive fixed point STRUCTURALLY. The DB column is the only authority for both the Content-Type header and the disposition choice; R2 metadata may still be WRITTEN on upload (it is what a direct bucket reader sees), it is simply never read back.

## Amendment (wave 42) — every route that echoes a stored contentType passes it through assertServedContentTypeHeader, and the rule (with DEC-551's nosniff twin) is bound by a source scan, not by the writer

SPEC §6 requires 'no user-content served with HTML content types'. Only ONE of five R2-streaming routes enforces it: src/routes/files.ts:644. src/routes/portal/tasks.tsx:707 and :746, src/routes/portal/profile.tsx:465 (headshot) and src/routes/portal/tasks/resources.tsx:49 echo the DB column straight into the header, so the invariant rests entirely on the upload-time writer — a serializer invariant held only by the writer is held by nobody (field-guide: A GUARD THAT NARROWS < NONE; A PREDICATE FAMILY IS A LATTICE). RULING: inside src/routes/**, any `"Content-Type": <expr>` whose value is not a source literal must be the return value of assertServedContentTypeHeader(...), and every such route must also set X-Content-Type-Options: nosniff (DEC-551). Content-Disposition policy is UNCHANGED and is NOT part of this rule: the resources route's isImageContentType split is the house rule — images stream inline (the headshot renders in an <img>, so it deliberately carries no Content-Disposition), non-images get contentDispositionAttachment. Do not add a Content-Disposition to the headshot route.
