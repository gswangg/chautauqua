# DEC-629: Merging duplicates is set-based: one call collapses a whole cluster into one survivor

POST /api/v1/contacts/merge takes exactly one mergeId (src/routes/api/contacts/merge.ts:19), so a three-way duplicate group needs two round trips and leaves an intermediate state visible between them — contradicting the house invariant that bulk ops are set-based. The endpoint takes mergeIds[], every id is ownership-checked BEFORE any write (full-set match, DEC-133 style: one foreign id means zero writes), and each pair still folds through the SAME single-pair core so the login-account, email-owner and planMerge precedence guards cannot diverge. No compatibility shim for the old key — the caller is updated.

## Amendment (wave 49)

Org-ownership verification for a set operation is ONE read. DEC-629 already declares merging set-based, but src/routes/api/contacts/merge.ts:30-33 and :61-65 still prove ownership one id at a time: up to 21 sequential D1 SELECTs on POST /contacts/merge and again on GET /contacts/merge/preview — and MergePage re-fires the preview on every "Swap which is kept" click. The verify-EVERYTHING-before-ANY-write contract is the valuable half and must be preserved exactly; only its cost changes. One `inArray` read over keepId + mergeIds, then a loud 404 naming the FIRST id in REQUEST order that is missing or foreign, keeps both the zero-partial-merge guarantee and a deterministic error message.
