# DEC-482: The three surviving perPage clamp copies collapse onto clampPerPage (default 50), NOT listPerPage (default 200)

DEC-480 diagnosed three live re-implementations of the DEFAULT_PER_PAGE=50 / MAX_PER_PAGE=200 rule. The obvious-looking repair — point them all at listPerPage — would silently change the default page size of GET /api/v1/contacts, GET .../submissions and the onboarding grid from 50 to 200, and that breaks the SPA: app/src/pages/submissions/filters.ts:14 omits `perPage` from the query string whenever it equals its own client default of 50, while app/src/pages/submissions/SubmissionsTable.tsx:327 computes the Next-button predicate as `filters.page * filters.perPage >= total` with perPage=50. Server 200 / client 50 desynchronizes offset math and skips rows (page 2 of a 150-row result returns nothing). src/lib/pagination.ts already exports clampPerPage, which IS the rule those three copies re-implement, with byte-identical semantics for every input (absent/empty/NaN/0/1.5 -> 50; n>200 -> 200). So the fix is deletion plus an import, with zero behavior change, and DEC-480's criterion grades 'defined in exactly one place', never 'one default for every endpoint'. listPerPage keeps its own distinct population (endpoints whose consumers render every row, DEC-461(a)/465) untouched.
