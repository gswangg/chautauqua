# DEC-868: The Contacts filter row states its conjunction, edits in place, and counts N of M; a half-typed rule is never a query

The design pack (docs/design/README.md:293-301, frame 08-contacts--00, AUTHORITATIVE v5) specifies a rules row directly under the tab row: `Matching all of [company ▾][is ▾][Latticework Systems][Remove] … Add a rule    41 of 318 match   Save as a segment`. What is on main (app/src/pages/contacts/FilterRulesPanel.tsx) is a draft-then-commit form — one Field/Operator/Value triple plus an 'Add filter' button, with committed rules rendered as read-only chips above it. Three consequences: a rule cannot be corrected, only deleted and retyped; 'Matching all of' (which states the AND without a boolean control) is absent, so a stack of chips does not say how it composes; and the row never reports how much it matched, which is the fact that makes 'Save as a segment' a considered act rather than a guess. Decision: each rule renders as an editable [field ▾][op ▾][value][Remove] group that writes back through onChange; 'Add a rule' appends a blank rule; the row ends with '<N> of <M> match' (N = the list response's own total, M = stats.total from the KPI fetch — no third count, no client re-derivation) and a 'Save as a segment' control that does exactly what DirectoryRail's onSaveCurrentFilters already does (setPanel('segments')), because two save paths for one row is one too many (DEC-860). A rule whose value is blank (or whose custom key is blank) is INCOMPLETE, never a query: ONE exported reader, activeRules(), filters them out, and the list request, the export href and the segment-save filters all read through it, so the table, the CSV and the saved segment cannot disagree (DEC-649/DEC-671). The field vocabulary stays imported from SEGMENT_STANDARD_FIELDS + custom.<key> — never hand-listed.

## Amendment (wave 45): the filter rules row carries one eyebrow and one bordered control per rule

app/src/pages/contacts/contacts.css:78-92 styles the row's caption as plain muted body text and `Add a rule` as a dashed-bordered button; frame 08 draws a letterspaced uppercase eyebrow and a green text link. The dashed button also reads as a third control tier the design system does not have. Decision: the caption adopts the section-label eyebrow vocabulary through CSS (text-transform + tracking) so the DOM text stays sentence-case and the accessible name is unchanged; `Add a rule` becomes a tertiary text link (.chq-btn-tertiary, which already carries the olive focus ring); the only bordered controls on the row are the per-rule Remove and Save-as-a-segment. Presentation-only uppercase is the correct tool here precisely because nothing about the control's NAME is changing.
