# DEC-583: Demo credentials are one importable module conformance-tested against the fixture, and the login prefill renders only when those exact accounts exist in this database

The homepage mandate resolves the demo-affordance question: no demo buttons on the hub; instead /login offers three links that PREFILL email+password for the seeded organizer/reviewer/speaker. That requires the login page to know credentials the seed reads from docs/fixtures/sample-data.json, which a Worker cannot read at runtime. Hand-copying them into the route is exactly the drift the field guide forbids, so they become src/lib/demo-identities.ts with a test that reads the fixture and asserts equality — the DEC-518 enumeration rule. Rendering a password in HTML is only defensible when it is already public knowledge, so the block renders if and only if a user row exists for every one of those emails (a single query, in its own repo module); on any real deployment it renders nothing. Prefill only: never auto-submit, no new endpoint, no auto-login — the real auth flow stays visible, which is the point of the login design's 'one door, three roles' framing.
