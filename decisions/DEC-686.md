# DEC-686: A paged read touches only the page: per-page aggregates key to the page's rows, and a thread pages in SQL

DEC-680 named this family for the headshots tab; two more instances are live. src/server/repo/email.ts:266-281 fetches the per-status tally for the batch list with a grouped query bounded only by eventId/q — every batch in the event — and then discards the rows that are not on the page in JS (`if (!batchKeys.includes(r.batchKey)) continue`), so rendering page 1 of the Comms history costs a full grouped scan of email_log at any scale. src/server/repo/files-comments.ts:69-94 reads EVERY comment on a deliverable's version chain into memory and slices the requested window with Array.slice, even though its `total` is already an honest count(*) — the page window exists precisely to avoid that read. Both are the same rule: the query that produces a page is scoped BY that page (WHERE over the page's keys; ORDER BY + LIMIT/OFFSET in SQL), never a materialized scan narrowed afterwards in JavaScript.
