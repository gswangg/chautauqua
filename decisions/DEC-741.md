# DEC-741: The content note endpoint: POST /submissions/:id/content-note posts to the chain thread, optionally sets changes_requested, and mails the speakers

DEC-720 decided that asking for changes is a message and named the shape only in prose; pinning the wire contract here stops the SPA and the route inventing two. Body: { fileId: string; body: string; requestChanges: boolean } — fileId names the DEC-573 version chain so the note lands in the thread the speaker already reads in /portal/tasks, and the control is absent until a deliverable is selected. The handler posts the comment, then (when requestChanges) sets content_status='changes_requested' through the existing repo helper, then mails each of the submission's active-invite participants through makeMailer with eventId+contactId so the send appears in Comms history, per-recipient try/catch (DEC-238 class 2). Response is the house send shape { sent, failed: [{email, message}] } — the toast counts actual sends, never intent. It lives in a NEW file (src/routes/content-notes.ts) because src/routes/files.ts carries the DEC-009 invariant "this module MUST NEVER import a mailer"; approval deliberately stays silent.
