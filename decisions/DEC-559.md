# DEC-559: The J6 reminder carries the recipient's portal link, resolved by the ONE shared portal-link rule — a notification with nothing to click is half-built

buildReminderMessage (src/server/repo/tasks/reminders.ts:83-101) renders "You have outstanding tasks for {event_name}" plus a list of titles and due dates, and stops. There is no link. Every other send path in the product resolves one: the CFP confirmation (routes/public/submit.tsx:760-778) and compose (routes/comms.ts:296-308) both go through findAccountUserId/findAccountUserIds and then either `${origin}/portal` or a freshly minted `${origin}/claim/<token>`. The reminder path is the single send that addresses the contact by `first.email` alone and never consults findAccountUserId — the exact shape the standing rule forbids ("ONE email rule via findAccountUserId, NEVER email alone"). For the speaker persona SPEC describes — a busy professional who interacts a handful of times — the automated chase is the ONE message that is supposed to convert into an action, and for an accepted speaker who has not yet claimed an account it is a dead end with no reachable next step at all. J6 promises reminders that make onboarding run itself; clarifications.md insists emails actually send on an MVP basis, which is not satisfied by a message that cannot be acted on. Decision: (a) comms.ts's private resolvePortalLink moves verbatim into a new src/server/repo/portal-link.ts and becomes the ONE implementation; comms.ts imports it and keeps no copy (no-backwards-compat: the local function is deleted, not wrapped). (b) buildReminderMessage takes a `portalLink` and appends it through the same renderTemplate {portal_link} idiom the confirmation uses, so the cron send and the DEC-441 preview stay byte-identical builders. (c) the send path batches findAccountUserIds over the capped recipient group (DEC-530), and mintClaimTokens is TRUE for remindNow/sendDueRemindersForEvent and FALSE for previewRemindNow — DEC-397's rule that a preview never mints credentials is preserved exactly. (d) the cron has no request, so origin resolution gets a second, explicit entry point: `resolveBaseUrlForCron(env)` in src/server/origin.ts returns PUBLIC_BASE_URL's parsed origin and THROWS when it is unset — a scheduled job may not guess a host, and header sniffing has no meaning without a request (DEC-252's precedence is otherwise untouched). (e) the regression bar: a contact with an account gets /portal, one without gets /claim/<token>, the preview mints zero KV writes and its body differs from a real send only in the token.
