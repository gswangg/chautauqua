# DEC-416: An unknown track id is rejected even when the form offers zero tracks, and the public track join is scoped to the event

DEC-301 made validateTrackChoice return ok on an empty offered set so a track-less event cannot dead-end submissions -- but that early return (src/lib/submit-core.ts:49-51) happens BEFORE the membership check, so with zero offered tracks any client-supplied trackIds flow straight into submission_track (src/server/repo/submit.ts:279-284 for public submit, src/server/repo/portal-edit.ts:277-284 for portal edit), and hydrateSessions joins submission_track -> track with no event scoping (src/server/repo/public/sessions.ts:159-161), so another org's track name and colour render on this event's public page. This contradicts SPEC.md:319-320 ('validates against the server's form schema ... never trusts the client's rendering'). DEC-301's actual intent -- never REQUIRE a track that isn't offered -- is preserved by reordering rather than reverting: unknown ids are rejected unconditionally; an empty offered set only relaxes the 'at least one' requirement. The read-side scoping lands in the same wave because a write-side fix alone leaves rows already written by this hole rendering publicly.
