# DEC-538: The saved-view validator IMPORTS its vocabularies; a hand-copied enum is a second implementation and this one has already drifted

`src/server/repo/views.ts:16-20` hand-copies two enums with a comment justifying the copy ("to keep this module's shape validation self-contained and dependency-light"). One copy has already gone stale: its `SORT_ORDERS` lists four values, while the canonical `SORT_ORDERS` at `src/server/repo/submissions/query.ts:20` has five -- `worklist` was added by DEC-341 and never propagated. So `isValidSavedViewConfig` today REJECTS a sort value that the very list endpoint a saved view describes both accepts and produces (`app/src/pages/content/ContentApp.tsx:44` sends `sort=worklist`), meaning the SPEC-section-2.3 worklist ordering -- "dashboards are worklists, not reports" -- is the one ordering a producer can never save a view for. The second copy (`SUBMISSION_STATUSES`) happens to still match `src/domain/status.ts` today, which is precisely how the first one looked before DEC-341. Decision: (a) delete both local copies; import `SUBMISSION_STATUSES` from `src/domain/status.ts` and `SORT_ORDERS` from `src/server/repo/submissions/query.ts`, and delete the comment that justified the duplication; (b) the guard test DERIVES its cases by iterating those imported constants and asserting `isValidSavedViewConfig` accepts every member -- never a hand-written list of literals, which would just be a third copy. The client-side `SORT_ORDERS` in `app/src/pages/submissions/types.ts` is deliberately left as-is: adding a worklist option to the Submissions grid's sort control is a feature, not this defect, and this decision is about the server contradicting itself.
