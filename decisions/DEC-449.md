# DEC-449: The reviewer queue's remaining budget miss is fixed by deleting per-90-id chunked round-trips, not by paging the queue or reshaping assignment; a plan+round COUNT GROUP BY is not the SQL laundering DEC-440 forbids

task-w16-c-perf-smoke-stage1.md:94-152 measured `GET /api/v1/review/plans/:id/queue` at 54-88ms adjusted p95, 4/4 runs over SPEC.md:331's 50ms read budget at the 2k perf seed -- worse and more consistent than before DEC-439's fix, and unowned by any decision. The diagnosis is precise and is not the one DEC-439 addressed: for an unrestricted reviewer the matched set is still all 2,000 event submissions, and the request now issues ceil(2000/90)=23 chunked queries for the post-match track lookup plus 23 more for evaluation counts, ~51 sequential D1 round-trips for one read. Both chunk loops are removable without restructuring anything, which is what DEC-439's own rule demands (fix by loading less). resolveReviewerSubmissions has exactly one caller and that caller never reads trackIds, so the track lookup is deleted outright and the return type narrowed (DEC-346 payload width; house rule forbids leaving a dead slow path behind a flag). countEvaluationsBySubmission's WHERE already scopes by plan+round, so its submissionIds parameter buys nothing but round-trips: delete the parameter and the loop, leaving one GROUP BY query whose extra map entries are never emitted because the route reads it only via .get(id) over the scoped set. Boundary stated once so no worker has to guess: DEC-440 governs score aggregation (aggregateSubmission/aggregateDropdownCriterion must keep throwing on a missing score in JS); a count(*) GROUP BY has no invariant to throw and is not covered. Acceptance is a number, not a code shape: reviewer queue under 50ms adjusted p95 on 4/4 runs at the 2k seed, and a unit test proving the queue path's query count is constant as the matched set grows.
