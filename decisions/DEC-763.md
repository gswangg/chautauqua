# DEC-763: Evaluations-for-submission is plan-scoped, and the results export carries the sort the table is showing

VERIFIED BUG: app/src/pages/review/ResultsTable.tsx:211 fetches `/submissions/{id}/evaluations` with no plan filter, while the row's `# Evaluations` count comes from the plan-scoped results query -- so plan-2's "Reviews (2)" expands to 3 entries including another plan's evaluation. A disclosure that expands to a different set than the count beside it is a lie, and cross-wave evaluations leaking between plans defeats the point of running review in waves. Decision: listEvaluationsForSubmission takes an optional planId; the route accepts ?planId= (verified to belong to the same event/org); the results disclosure ALWAYS passes the plan it belongs to. Separately, PlanList.tsx:179's title-row "Export results CSV" builds its href from plan+round only, so it silently exports a different order than the table on screen. The export link stays on the title row (v4 design), but ResultsTable reports its current sort upward so the one href is always the one the organiser is looking at -- an export that disagrees with the screen is worse than no export.
