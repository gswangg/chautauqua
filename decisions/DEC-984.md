# DEC-984: A recusal is server state, not session state: the reviewer submission detail carries the caller's own recusal and the scorecard hydrates from it

DEC-271 says scoring is disabled once a reviewer recuses. That is true only until the page reloads: app/src/pages/review/Scorecard.tsx initialises `recusal` to null and only ever sets it from its own POST, while GET /api/v1/review/submissions/:id (src/routes/review/reviewer.ts:218-259) returns summary + answers + criteria + myEvaluation and says nothing about recusals. So a reviewer who recused themselves, then returns to the scorecard by URL or from the queue's RECUSED list, is shown the un-recused UI — live rating pills, an enabled Submit, and the "I have a conflict of interest" checkbox as if nothing had been declared — and only learns otherwise from the PUT's 409 after filling the card in. The server gate is correct and stays the authority; the defect is that the client cannot see the state the server is enforcing. The detail route carries the caller's OWN recusal for the plan's active round as `myRecusal` (present only when one exists, the same property-absent convention myEvaluation already uses per DEC-561) and never any other reviewer's, and the scorecard's recused branch renders from that value on first paint. Any state a route refuses on must be readable on the route that renders the form.
