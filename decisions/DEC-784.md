# DEC-784: A participant's role is chosen where the participant is added, and always rendered as a label

VERIFIED app/src/pages/submissions/SubmissionDetailPage.tsx:396 — the organiser's Add co-presenter POSTs `{ contactId }` only, so the server's default silently decides the role; this is the exact defect ABS-11 was judged on ("organizer form silently defaults 'speaker'"), and the CRM grader's "role IS sent to API but moderator/panelist surfaces NOWHERE" is its other half. VERIFIED :709 renders `{p.role}` — the raw stored value, not participantRoleLabel, in violation of the standing "raw id leaks — render LABELS" rule. src/domain/participant-roles.ts already exports PARTICIPANT_ROLE_OPTIONS and participantRoleLabel and the portal form already imports both (routes/portal/edit.tsx:285). Decision: the organiser's add-co-presenter row carries the same imported vocabulary (never a hand-copied list), POSTs the chosen `role`, and the Role column renders participantRoleLabel; the server validates `role` on POST /api/v1/submissions/:id/participants against PARTICIPANT_ROLE_OPTIONS, rejecting an unknown value loudly with a field error rather than defaulting.
