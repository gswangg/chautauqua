# DEC-947: A calendar invite's ORGANIZER is the deployment's configured sender; noreply@chautauqua.local is dev-only

ICS_ORGANIZER_EMAIL = "noreply@chautauqua.local" (src/mail/ics.ts:15) is hardcoded into every VEVENT the product emits: the METHOD:REQUEST invite attached to a compose send (src/routes/comms.ts:578) and both anonymous METHOD:PUBLISH exports (src/routes/public/index.tsx:323 and :343). `.local` is a reserved, non-routable TLD, so every RSVP a speaker's calendar client sends bounces, and the same-UID/bumped-SEQUENCE update flow the brief explicitly names ('the initial invite has no room; the room is assigned later') is exactly the case that degrades — an update from an unroutable organizer is what clients treat with most suspicion. src/server/context.ts's makeMailer already owns this policy for mail itself: isDevMode(env) selects the dev sink, and every other configuration without MAIL_FROM_EMAIL THROWS rather than degrading (DEC-547). The .ics organizer must be governed by the same predicate, not by a module constant. Rule: src/server/context.ts gains `resolveIcsOrganizerEmail(env: Pick<Bindings,"DEV_MODE"|"MAIL_FROM_EMAIL">): string` beside makeMailer — MAIL_FROM_EMAIL when set, the dev-local placeholder when isDevMode(env), and a loud throw otherwise, with the same message shape makeMailer uses. ICS_ORGANIZER_EMAIL stays exported from src/mail/ics.ts as the DEV placeholder only (its doc comment says so), src/mail/ics.ts stays pure (it never reads env; the caller passes the resolved address), and all three call sites resolve through the new function. This is code, not provisioning: setting MAIL_FROM_EMAIL remains the operator's stage-2 job.

## Amendment (wave 43): ICS organizer resolution belongs inside the guarded per-recipient region

resolveIcsOrganizerEmail (context.ts:76-80) throws on missing MAIL_FROM_EMAIL and is called at src/routes/comms.ts:581 INSIDE the recipient loop but OUTSIDE the try that makes a send failure per-recipient — so an unconfigured deployment turns an attach-ICS send into a 500 rather than N honest 'failed' rows. The policy (never ship a non-routable .local organizer) is unchanged; only its placement moves: every expression that can throw for a configuration reason must sit inside the same guarded region as mailer.send, so the outcome is always a per-recipient status, never a request-level 500.

## Amendment (wave 58): ORGANIZER is REQUIRED for METHOD:REQUEST and OPTIONAL for METHOD:PUBLISH — a public, no-login .ics degrades rather than 500ing on unrelated mail config

src/routes/public/index.tsx:329 and :349 (schedule.ics, agenda.ics — anonymous J10 deliverables) call resolveIcsOrganizerEmail(c.env), which THROWS when MAIL_FROM_EMAIL is unset and DEV_MODE !== '1' (src/server/context.ts:91). Any non-dev deployment without mail configured — a fork, a self-hoster, the window before mail secrets land — serves a 500 HTML error page at a .ics URL. A calendar feed has no business failing on the mailer's configuration. RFC 5545 makes ORGANIZER optional for PUBLISH and meaningful only where there is an RSVP target; the invitation path (compose/REQUEST) genuinely needs a routable sender and keeps the loud throw. Ruling: IcsOptions.organizer becomes optional; buildIcsCalendar throws when METHOD:REQUEST arrives without one (mirroring its existing attendee guard); the public PUBLISH feeds resolve through a new non-throwing reader and simply omit the ORGANIZER line when mail is unconfigured. Same predicate underneath (mailConfigStatus) — the throwing wrapper stays, it just stops being the only door.
