# DEC-965: A version number is the row's stored identity, everywhere — a chain length is not a version

DEC-818 settled it server-side ('a version number is an identity, not a position among the survivors') and DEC-902 applied it to the files library, but the organizer's own deliverable screen never got the fact. GET /api/v1/submissions/:id/files (src/routes/files.ts:173-185) projects id/kind/filename/sizeBytes/contentType/previousFileId/uploadedByContactId/createdAt and NOT versionNo — listSubmissionFiles' FileVersion (src/server/repo/files-versions.ts:300) doesn't select the column at all — so app/src/pages/content/VersionList.tsx computes `chain.length - idxInChain` (:86), a POSITION. Delete a middle version and the survivors silently renumber, while deleteFileVersion (:491) writes the system note 'Removed version 3' from the stored identity and the speaker portal's own history (src/routes/portal/tasks.tsx:152) prints row.versionNo: the same file then reads v2 to the organizer, v3 to the speaker, and the note above it names a version no row claims. The worklist repeats the error in the other direction: SessionList.tsx:154 prints `v{versionCount}` — a chain-LENGTH marker types.ts:98-101 explicitly says is never what a VERSION column shows — beside a latestFileVersionNo the API already ships and nothing renders. Rule: listSubmissionFiles selects version_no and throws on a null (the data-corruption idiom listFileChainVersions already uses); the route projects it; DeliverableFile carries `versionNo: number`; VersionList's tag is `v${file.versionNo}` (plus ' · Latest' on the single newest row, DEC-901 unchanged) and the position arithmetic is deleted; the worklist's Latest-file cell prints latestFileVersionNo, dropping the clause when it is null rather than falling back to a count.
