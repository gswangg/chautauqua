# DEC-745: The plan editor is the v4 shell: the plan's NAME is the page title, Duplicate + Save sit on the title row, rounds are waves not a field, and the anonymise switch moves into "Who reviews what"

docs/design/Chautauqua Review.dc.html:251-327 draws the whole screen: back-link + plan name as the 27px title, Duplicate and Save on that row, a 2x2 field grid (Opens / Closes / Reviews per talk / Rating scale + "Applies to every criterion in this plan"), the criteria section that already landed, and a section headed "Who reviews what" whose rule carries "Assign a reviewer", whose rows read name/email · track · "6 talks" · Remove, and which ends with "A reviewer never sees a talk they are recused from." Main still renders a NAME field, INSTRUCTIONS, ROUNDS, an Anonymize checkbox, "Reviewer assignment" and a page-bottom Save/Delete. Two removals would cost capability, so they are redirected rather than deleted: the name becomes the editable title (renaming survives), and ROUNDS goes because POST /plans/:id/waves already exists as "Start a new wave" — a number input that can disagree with the wave action is a second source of truth. Anonymisation is a reviewing rule, so its control moves into "Who reviews what" as one checkbox above the footnote; SPEC's blind review (§5.7, J4) must stay reachable even though the mock omits it. Delete stays a quiet tertiary at the very end of the document, never beside Save.

## Amendment (wave 49)

Plan editor: FIELDS draft behind Save, ACTIONS apply immediately; a dirty editor never navigates away silently. Verified open today: app/src/pages/review/PlanEditor.tsx holds name/dates/criteria AND the anonymize checkbox (:1382-1383) in local `draft` state committed only by `save` (:822/:836), while Assign-a-reviewer/Distribute/Remove/Duplicate fire their own APIs on click; a grep of app/src for `dirty|beforeunload|isDirty` returns only settings/TracksRoomsPanel — there is NO navigation guard anywhere in the SPA. The mandate records this costing a scored critical (an eval agent checked anonymize and never clicked Save; the "critical" was an unsaved draft). Two conventions were on the table; ONE is picked: every FIELD is draft state committed only by Save, every ACTION applies immediately and is labelled with an immediate-effect verb. Anonymize stays a FIELD rather than becoming instant-apply, because it sits inside the same 2x2 field grid as name/dates and an instant toggle inside a field grid is exactly the inconsistency being removed; the DEC-799 ratchet confirm therefore fires at Save time when anonymize goes true->false, not at click time. A dirty editor must block in-app navigation with a confirm that NAMES what is unsaved, and register a beforeunload warning.

## Amendment (wave 72): the cap row is a persistent row under the section rule, and its summary comes off a count the progress query already loads

Frame 05 draws Who-reviews-what as head (label + `Assign a reviewer` right) → rule → a PERSISTENT row: `CAP PER REVIEWER [8] talks each  [Distribute the unassigned]  18 talks · 36 reviews needed at 2 each · 4 reviewers`. On main the cap input and the Distribute control are both crammed INTO `.chq-section-head` (PlanEditor.tsx:1394-1428), and the summary line exists only inside the confirm panel (line 1504) — so the organiser cannot see the shape of the run before triggering a preview, and the head carries four competing controls. Ruling: head keeps the label and `Assign a reviewer` alone; a persistent row below the rule owns the cap input, Distribute (a real button, not a text link — it opens a preview, which is an action), and the summary. The summary must not be a second opinion: GET /api/v1/plans/:id/progress already loads `listPlanFilteredSubmissions(db, plan)` in full (plans-progress.ts:58) and throws the count away, so the envelope gains `submissionsInScope` — zero extra queries — and the row derives talks/reviews/reviewers from that one number, the plan's own reviews-per-talk, and the reviewer roster already on the page. DEC-786's preview-then-confirm is untouched: nothing here issues a non-GET.

## Amendment (wave 18): the immediacy caption states only what is actually immediate

PlanEditor's section caption reads 'Assign a reviewer applies immediately. Distribute the unassigned applies immediately.' (app/src/pages/review/PlanEditor.tsx:1506-1508) while Distribute is a preview-then-confirm flow whose own panel says 'Nothing is saved until you confirm'. One page tells the organizer two contradictory things about the same button; the frame carries no such caption for Distribute. RULING: the caption keeps the Assign clause (true) and drops the Distribute clause. Copy that contradicts the flow it labels is a defect, not a nit — it is the reason an organizer hesitates over a destructive-looking button.

## Amendment (wave 25)

**Plan editor — anonymise sits with the plan fields, Delete plan is a frozen footer link, Reset password is gone**

Ruling A10 supersedes DEC-745's clause that the anonymise switch moves into "Who reviews what": it is a PLAN-WIDE property, exactly like Rating scale, so it belongs in the plan fields block beside it, labelled "Hide speaker names from reviewers" with the consequence "Reviewers see the abstract and track only" beneath, and it freezes with the criteria at the first submitted review for the same reason they do (DEC-213's predicate). Ruling A9: Delete plan stays a capability but becomes a tertiary link in the plan-editor FOOTER, disabled once any review has landed, naming "Start a new wave" as the alternative — an irreversible action never sits next to Assign as a peer control. Ruling 9: the per-reviewer "Reset password" control is DELETED — a reviewer's credentials are not a property of a review plan, and Settings > People and roles owns them (this is also the surface that DEC-014's amendment now serves through a real self-service reset).


## Amendment (wave 28): the plan editor's save rejection is a summary with anchors that names BOTH failure kinds — cross-field and empty-collection

validatePlanDraft already computes errors (PlanEditor.tsx:373) and the Save handler already refuses on them (:468), but the refusal renders as a single .chq-error box, so a plan rejected for a close-date-before-open-date and for zero criteria reads the same as a server outage. The v9 pack draws this exact screen (docs/design/Chautauqua Review.dc.html:797, 'Two things need fixing before this plan can open'). Ruling: the rejection is an ErrorSummary at the top of the form with one anchor per problem, every field repeats its own message, and the two shapes are worded as consequences rather than rules — a date ordering failure says which date moved, an empty collection says what the collection is for ('a plan needs at least one criterion — reviewers score against them'). Rule 9 binds here too: field errors stay silent until submit (generalise the existing nameTouched gate), because a half-built plan must always be storable.

## Amendment (wave 40): "N reviewers" on the cap row counts reviewer ACCOUNTS, sourced from the progress envelope's own total — never the length of a page of assignment rows

DEC-745 put a persistent summary on the plan editor's cap row and fed it "from the progress endpoint's submissionsInScope + the plan's own reviews-per-talk + the reviewer roster already on the page" (app/src/pages/review/PlanEditor.tsx:161-168). The third term is wrong in two independent ways. plan_reviewer rows are (userId, trackId|submissionId) tuples — one reviewer scoped to two tracks is two rows — so `reviewers.length` (PlanEditor.tsx:1667) states assignment rows where the frame's sentence ("18 talks · 36 reviews needed at 2 each · 4 reviewers") means people, and the organizer reads more capacity than exists before deciding a cap. And that array is page 1 of `/plans/:id/reviewers` (no perPage, listPerPage caps at 200), so at distribute scale it is also a page count. The truthful figure is already on the wire and already discarded: GET /plans/:id/progress builds ONE ROW PER USER and returns the full-array `total` (src/routes/review/plans-progress.ts:120-138), which PlanEditor.tsx:416-419 throws away while keeping only res.items. RULING: the cap row's reviewer term is the progress envelope's `total` (distinct reviewer accounts, server-computed); the reviewer ROSTER below it is a paged list that requests an explicit perPage, states its bound and can page the remainder in, so a reviewer past row 200 can still be seen and Removed.

## Amendment (findings wave 4): the selected-row edge is ONE shared rule, and a selected band never bleeds past the measure

DESIGN-RULINGS B8 item 28 is the only unbuilt half of the interaction-states standard. Verified on main: `.chq-review-plan-row.is-active` (app/src/pages/review/review.css:53-57) sets the #EFEBDF fill but NO 3px olive left edge, and buys its inset with `margin-inline:-16px; padding-inline:16px`, i.e. the band is drawn 16px OUTSIDE the reading measure it belongs to. `.chq-participation-menu-item.is-current` (speakers.css:438) has the same fill and the same missing edge. Ruling: a selected row is `--chq-surface-sunk` fill PLUS a 3px `--chq-brand` left edge that REPLACES 3px of the row's own left padding (declared in both states so selection shifts nothing), and it inherits the parent's box rather than escaping it with a negative margin. One shared declaration in app/src/styles.css; the page stylesheets consume it. The durable half is the scan: a rule that paints the selected fill without the edge is a build failure, so the next surface cannot re-invent a half-state.

## Amendment (wave 21): the plan editor's criteria, reviewer and distribute-preview rows take the frame's exact tracks

The plan editor is the eval-relevant surface behind rulings A9/A10/B4, and three of its row grids drift from docs/design/Chautauqua Review.dc.html. (1) Criteria rows and their head share one rule at review.css:782-785, `auto minmax(0,1fr) minmax(0,1fr) 150px 70px`, against the frame's `20px 1fr 260px 132px 62px` (:470,474): the drag column is content-sized rather than a pinned 20px — the very drift the w41-f/DEC-715 comment above it says it exists to prevent, since a locked row's blank handle cell and an unlocked row's handle button are different content — and, more visibly, GUIDANCE takes an equal 1fr share of the 820 measure instead of a fixed 260px, so the criterion label the reviewer actually reads is half the width the frame gives it. (2) `.chq-review-reviewer-row` (review.css:935-937) is `1fr 190px auto auto` against the frame's `1fr 190px 130px auto` (:526) — the load column is unpinned, so it sizes from whichever row happens to have the longest text. (3) `.chq-review-distribute-table` (review.css:1054) carries no tracks at all against the frame's `1fr 120px 150px` (:513), and this is the preview of an irreversible bulk write, where reviewer / track / '6 -> 8 talks' must line up down the column. Ruling: transcribe the frame's tracks in all three places, keep `minmax(0, ...)` on the flexible track (w18-e/DEC-715: a bare 1fr has a min-content floor and a long label can push the row past its container), keep the head and body sharing ONE declaration so they cannot drift apart, and leave every `@media (max-width: ...)` single-column collapse untouched.

## Amendment (wave 22): the reviewer queue's action column and the criteria row's weight/remove columns take the frame's fixed widths

Two track lists in review.css still size from content where the frame pins them. (1) `.chq-review-queue-row` (review.css:448-455) is `minmax(0, 1fr) auto`; docs/design/Chautauqua Review.dc.html:363 declares `1fr 176px`. Under `auto` each row's action column sizes from its OWN button label -- Score vs Continue vs a recusal reason -- so the queue's right edge staggers row by row, which is the same 'last unwidthed column' family as the table work and is worse here because the frame's whole point is one action column down the page. (2) `.chq-review-criterion-row` / `.chq-review-criteria-head-row` (review.css:820-823) declare `20px minmax(0,1fr) 260px 150px 70px` in a comment that cites frame :470/:474 -- but those frame lines read `20px 1fr 260px 132px 62px`. The landed rule contradicts the frame it cites, which is precisely the 'a frame track list is a contract, a CSS comment about it is not' shape. Ruling: 176px on the queue's action track, 132px on Weight and 62px on Remove; the phone (max-width 700px) single-column blocks are untouched.
