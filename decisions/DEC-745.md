# DEC-745: The plan editor is the v4 shell: the plan's NAME is the page title, Duplicate + Save sit on the title row, rounds are waves not a field, and the anonymise switch moves into "Who reviews what"

docs/design/Chautauqua Review.dc.html:251-327 draws the whole screen: back-link + plan name as the 27px title, Duplicate and Save on that row, a 2x2 field grid (Opens / Closes / Reviews per talk / Rating scale + "Applies to every criterion in this plan"), the criteria section that already landed, and a section headed "Who reviews what" whose rule carries "Assign a reviewer", whose rows read name/email · track · "6 talks" · Remove, and which ends with "A reviewer never sees a talk they are recused from." Main still renders a NAME field, INSTRUCTIONS, ROUNDS, an Anonymize checkbox, "Reviewer assignment" and a page-bottom Save/Delete. Two removals would cost capability, so they are redirected rather than deleted: the name becomes the editable title (renaming survives), and ROUNDS goes because POST /plans/:id/waves already exists as "Start a new wave" — a number input that can disagree with the wave action is a second source of truth. Anonymisation is a reviewing rule, so its control moves into "Who reviews what" as one checkbox above the footnote; SPEC's blind review (§5.7, J4) must stay reachable even though the mock omits it. Delete stays a quiet tertiary at the very end of the document, never beside Save.

## Amendment (wave 49)

Plan editor: FIELDS draft behind Save, ACTIONS apply immediately; a dirty editor never navigates away silently. Verified open today: app/src/pages/review/PlanEditor.tsx holds name/dates/criteria AND the anonymize checkbox (:1382-1383) in local `draft` state committed only by `save` (:822/:836), while Assign-a-reviewer/Distribute/Remove/Duplicate fire their own APIs on click; a grep of app/src for `dirty|beforeunload|isDirty` returns only settings/TracksRoomsPanel — there is NO navigation guard anywhere in the SPA. The mandate records this costing a scored critical (an eval agent checked anonymize and never clicked Save; the "critical" was an unsaved draft). Two conventions were on the table; ONE is picked: every FIELD is draft state committed only by Save, every ACTION applies immediately and is labelled with an immediate-effect verb. Anonymize stays a FIELD rather than becoming instant-apply, because it sits inside the same 2x2 field grid as name/dates and an instant toggle inside a field grid is exactly the inconsistency being removed; the DEC-799 ratchet confirm therefore fires at Save time when anonymize goes true->false, not at click time. A dirty editor must block in-app navigation with a confirm that NAMES what is unsaved, and register a beforeunload warning.

## Amendment (wave 72): the cap row is a persistent row under the section rule, and its summary comes off a count the progress query already loads

Frame 05 draws Who-reviews-what as head (label + `Assign a reviewer` right) → rule → a PERSISTENT row: `CAP PER REVIEWER [8] talks each  [Distribute the unassigned]  18 talks · 36 reviews needed at 2 each · 4 reviewers`. On main the cap input and the Distribute control are both crammed INTO `.chq-section-head` (PlanEditor.tsx:1394-1428), and the summary line exists only inside the confirm panel (line 1504) — so the organiser cannot see the shape of the run before triggering a preview, and the head carries four competing controls. Ruling: head keeps the label and `Assign a reviewer` alone; a persistent row below the rule owns the cap input, Distribute (a real button, not a text link — it opens a preview, which is an action), and the summary. The summary must not be a second opinion: GET /api/v1/plans/:id/progress already loads `listPlanFilteredSubmissions(db, plan)` in full (plans-progress.ts:58) and throws the count away, so the envelope gains `submissionsInScope` — zero extra queries — and the row derives talks/reviews/reviewers from that one number, the plan's own reviews-per-talk, and the reviewer roster already on the page. DEC-786's preview-then-confirm is untouched: nothing here issues a non-GET.

## Amendment (wave 18): the immediacy caption states only what is actually immediate

PlanEditor's section caption reads 'Assign a reviewer applies immediately. Distribute the unassigned applies immediately.' (app/src/pages/review/PlanEditor.tsx:1506-1508) while Distribute is a preview-then-confirm flow whose own panel says 'Nothing is saved until you confirm'. One page tells the organizer two contradictory things about the same button; the frame carries no such caption for Distribute. RULING: the caption keeps the Assign clause (true) and drops the Distribute clause. Copy that contradicts the flow it labels is a defect, not a nit — it is the reason an organizer hesitates over a destructive-looking button.

## Amendment (wave 25)

**Plan editor — anonymise sits with the plan fields, Delete plan is a frozen footer link, Reset password is gone**

Ruling A10 supersedes DEC-745's clause that the anonymise switch moves into "Who reviews what": it is a PLAN-WIDE property, exactly like Rating scale, so it belongs in the plan fields block beside it, labelled "Hide speaker names from reviewers" with the consequence "Reviewers see the abstract and track only" beneath, and it freezes with the criteria at the first submitted review for the same reason they do (DEC-213's predicate). Ruling A9: Delete plan stays a capability but becomes a tertiary link in the plan-editor FOOTER, disabled once any review has landed, naming "Start a new wave" as the alternative — an irreversible action never sits next to Assign as a peer control. Ruling 9: the per-reviewer "Reset password" control is DELETED — a reviewer's credentials are not a property of a review plan, and Settings > People and roles owns them (this is also the surface that DEC-014's amendment now serves through a real self-service reset).
