# DEC-544: The CSRF double-submit rule has exactly one implementation, and it is the one the middleware calls -- a test-only twin tests nothing

src/server/middleware.ts contains the double-submit comparison three times: inline in csrfForm (:264), inline again in csrfFormOrHeader (:304), and once more in checkDoubleSubmitCsrf (:283), which is documented as "Pure helper for tests". Grep confirms the exact failure that shape invites: checkDoubleSubmitCsrf is referenced by test/server-middleware.test.ts and test/tokens.test.ts and by NOTHING in src/. So the predicate the suite proves correct is not the predicate that guards the public CFP, the portal, /login, /claim and /logout -- change either inline copy and every CSRF test still passes. This is the field guide's standing rule ("two implementations of one invariant means one is wrong") applied to the one place where being wrong is a security bug rather than a slow query, and it compounds DEC-181's fix, which added the third copy rather than removing the second. Decision: (a) checkDoubleSubmitCsrf becomes the ONE comparison; csrfForm and csrfFormOrHeader both delegate to it and their inline comparisons are deleted. (b) The two distinct 400 messages stay distinguishable -- "Missing CSRF cookie" when the cookie is absent, "CSRF token mismatch" when the delegate returns false -- because an operator debugging a blocked form post needs to know which half failed; the middleware keeps the cookie-presence branch and delegates only the comparison. (c) csrfFormOrHeader's DEC-181 header short-circuit and csrfJson's DEC-027 bearer exemption are untouched. (d) The regression bar is a source scan, not a memory: no file under src/server may compare a parsed body's chq_csrf field to a cookie value outside checkDoubleSubmitCsrf's body.
