# DEC-919: Every public surface narrows a list with ONE idiom: the same search box and the same pill bar

The three public list surfaces answer the identical question three different ways. /e/:slug/sessions renders a GET search form plus .chq-pub-filter-bar PILL navs for track, format and room (sessions.tsx:165-215). /e/:slug/schedule renders a GET form whose track and format are SELECT dropdowns living inside the search form, so narrowing requires a submit (agenda.tsx:334-383). /e/:slug/speakers renders a third form, labelled 'Search by name' rather than 'Search', with no filters at all (speakers.tsx:16-25). A visitor moving between two tabs of one event meets pills, then a dropdown, for the same act. The design brief states the target directly ('one filter idiom everywhere'), and the field guide's own rule is that one shared vocabulary plus a scan-lock beats per-page fixes. Rule: src/routes/public/filters.tsx owns PublicSearchBox and PublicFilterBar; all three surfaces render them and none writes its own; the pill bar is the filter idiom and the select disappears; every existing query contract (q, trackId, format, roomId, day, limit) round-trips unchanged and a pill href carries the OTHER active params forward, reusing agenda.tsx's existing day-pill param composition rather than writing a second one -- because a filter control that silently drops the day you were reading is worse than no control.


## Amendment (wave 40)

**Public search is one compact input at the head of ONE pill row — no label, no button, no second and third ruled row**

Verified on main: src/routes/public/filters.tsx renders PublicSearchBox as a labelled GET form with a visible 'Search' submit button, and every list surface stacks it above two or three separately ruled pill navs (tracks, formats, rooms). The frames draw one ~259x40 inline input at the HEAD of a single wrapping pill row, with no label and no button — the row reads as one narrowing gesture instead of three. RULING: PublicSearchBox keeps its exported props signature (another lane calls it this wave) and changes only its markup: a visually-hidden label, one compact search input, and a visually-hidden submit button retained so the form still works without JS and still announces itself to assistive tech (a form with one text field submits on Enter regardless, but a search form with no submit control is a keyboard trap for anyone who cannot press Enter). The surfaces render exactly one .chq-pub-filter-row containing the input followed by their pill bars, wrapping rather than stacking — and /schedule, which parses ?q= but never rendered an input at all, gets the same row.

## Amendment (wave 47): the public surfaces get ONE zero-state renderer, and a public zero-state never carries an action

The public list surfaces answer B7 with a bare sentence and no split: src/routes/public/sessions.tsx:340-342 picks between 'No sessions match your search.' and 'No sessions to show yet.' with no facet named, no escape and the filter bar left standing in both cases; src/routes/public/speakers.tsx:225-226 and :287-288 (list and gallery, DEC-593 twins) print 'No speakers to show yet.' even when a ?q= search excluded every row — the filtered voice missing entirely. DESIGN-RULINGS §B7 rule 3 settles the part that differs from the admin side: where the user genuinely cannot act — an attendee waiting on a programme — there is NO button at all, never a disabled one. Ruling: one server-rendered component, src/routes/public/empty-state.tsx, exporting PublicEmptyState(props: { variant: 'fresh' | 'filtered'; what: string; reason?: string; escapeHref?: string; escapeLabel?: string }). It has NO action prop by construction, so no public surface can grow a primary button. 'fresh' renders what + optional reason and the CALLER hides the filter bar above it; 'filtered' keeps the filter bar visible above the message, names the facet in `reason`, and renders the escape as a plain <a href> to the surface's bare path (SSR has no onClick). Copy: sessions fresh = 'The programme is not out yet.' + 'Sessions appear here once the schedule is published.'; sessions filtered = 'No sessions match your search.' + a reason naming the facets in flight + escape 'Clear filters'; speakers/gallery fresh = 'No speakers listed yet.'; speakers/gallery filtered = 'No speakers match your search.' + escape 'Clear filters'. CSS lives in src/routes/public/public.css.ts under the existing .chq-pub-* vocabulary — no new design tokens, and the admin .chq-empty-block anatomy is mirrored at the public type scale rather than re-invented. The public AGENDA day view is deliberately out of scope this wave (its readers were rewritten one wave ago); it adopts the same component in a later wave.

## Amendment (wave 59): a visually-hidden control may never occupy a visible control's hit area

VERIFIED on main: src/routes/public/css/chrome.css.ts:22-32 implements .chq-visually-hidden with `position:absolute; width:1px; height:1px; margin:-1px; clip:rect(0,0,0,0)`. With no offset the element keeps its STATIC position, so PublicSearchBox's hidden submit (filters.tsx:48) lands one pixel inside the right edge of #chq-pub-search-q, and every pointer aimed at the accessible 'Search' control is intercepted by the input on top of it. Two independent graded runs reported the public search submit as unclickable on two different surfaces; the design is not at fault (DEC-919 wave-40 deliberately draws no visible submit) — the hiding recipe is. RULING: .chq-visually-hidden takes the OFF-SCREEN recipe (an explicit large negative inline offset with `top:auto`) so a hidden element is never geometrically on top of, or underneath, a control a visitor can see. It stays in the a11y tree, stays focusable, and keeps the no-JS submit path working — the four hidden labels and four hidden submits across filters.tsx, speakers.tsx and agenda-controls.tsx are unchanged markup. Nothing in this amendment touches the phone tap-floor rules in the same file (wave-57 scope, landed).

## Amendment (wave 69): an actionable control is never rendered off-screen; visually-hidden is for labels only

`src/routes/public/filters.tsx:48` renders the ONE public search submit as `class="chq-visually-hidden"`, and `css/chrome.css.ts:30-42` puts that class at `left:-9999px; width:1px; height:1px`. The wave-59 change traded an overlapping control (absolutely positioned one pixel inside the input) for an ABSENT one: a real pointer can never hit it, and the judge's click timed out on sessions AND agenda in both runs — only Enter submits. Ruling: `.chq-visually-hidden` stays exactly what it is and keeps its label/announcement consumers, but no control a user is expected to ACT on may carry it. The public search box becomes an input+submit PAIR that spends the SAME 190px the input alone spent (`.chq-pub-search` 190px -> 150px, a new 40x40 `.chq-pub-search-submit` butted to its right edge), so `chrome.css.ts`'s 'all five controls fit one row at 820' budget stays true and no other control moves. The button carries a visible magnifier glyph (svg `aria-hidden`), an `aria-label`, the shared control vocabulary (1px `var(--chq-border)`, `var(--chq-r-ctl)` on the right corners only) and B8 hover: `background-color` only, 120ms, 0ms under reduced motion — never a size or border-width change. Deliberately NOT changed: `PublicFilterSelectForm`'s hidden submit — its primary gesture is the select's change event and its submit is a no-JS fallback, not the thing a pointer aims at.

## Amendment (wave 74): a carve-out is licensed by BEHAVIOUR, not by component name — a `.chq-visually-hidden` submit is legal only beside an auto-submitting select

The wave-69 amendment fixed the public search submit and closed with an explicit exemption: "Deliberately NOT changed: `PublicFilterSelectForm`'s hidden submit — its primary gesture is the select's change event and its submit is a no-JS fallback, not the thing a pointer aims at." That premise is true of `filters.tsx:84` and `agenda-controls.tsx:200`, which both carry `onchange="this.form.submit()"`. It is FALSE of `src/routes/public/speakers.tsx`'s `TrackFacetSelect` — a hand-inlined copy of the same form written before the shared component existed (its own comment at `:64-75` says so and asks for the consolidation), whose `<select>` at `:90` has NO `onchange` and whose only submit is `<button class="chq-visually-hidden" type="submit">` at `:102`, i.e. at `left:-9999px`. On `/e/:slug/speakers` and its embed, choosing a track therefore does nothing a pointer can complete: the exemption was applied by class name to a form that does not do what the name promises. RULING: the exemption is restated as a PAIRING that a scan can check — a public GET filter form may render its submit `.chq-visually-hidden` only if its `<select>` carries `onchange="this.form.submit()"`; a form with neither an auto-submitting select nor a visible submit is a dead control and fails. `TrackFacetSelect` is deleted and the speakers surface consumes the shared `PublicFilterSelectForm` (identical class names `.chq-pub-select-form`/`.chq-pub-select`, `q`/`limit` passed through the existing `hidden` prop), which restores the auto-submit and removes the duplicate component in one move — no new visual language, no width change, and the one-row-at-820 budget is untouched. `filters.tsx` and `agenda-controls.tsx` are NOT modified: they satisfy the pairing already.


## Amendment (wave 84, v12 mobile campaign w2): At 390 the Submissions head is the frame's three chips plus the search box, and a column picker with no columns is not shown

Audit finding 2 (docs/design/audit/submissions-v12.md) is explicitly filed as needing a ruling rather than a CSS fix. Frame `Chautauqua Submissions.dc.html:137` draws the head as a search box over exactly three chips — `Needs triage`, `Accepted`, `All 47` — with no Status caption, no divider, no track select and no column picker. The app reflows the entire desktop toolbar (`.chq-submissions-filterbar`: a Status caption, up to six SUBMISSION_STATUSES pills, a divider, the track `<select>`, and the ColumnPicker `<details>`) into one horizontal scroller. Ruling: at 390 the strip carries the frame's three chips and the search box, and the rest of the toolbar is not rendered. The track facet remains reachable through the search box the frame keeps, and every status beyond the three remains reachable at desktop width. This is DEC-919's own thesis (one narrowing idiom: the same search box and the same pill bar) applied at the phone breakpoint. Nothing is deleted; the desktop toolbar is untouched, and the phone rule is a display change inside the max-width block.
