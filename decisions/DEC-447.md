# DEC-447: The completion ledger is scheduled behind its wave's only source-changing lane, so it audits a tree that contains its own wave's fix

DEC-438 diagnosed the failure precisely -- 'a ledger cut from main at wave start structurally cannot see its own wave's fixes' -- and remedied the reporting (FAIL-unowned vs PENDING-OWNED) but not the scheduling, so three consecutive ledgers (w13-f, w14-h, w15-f) have now returned NOT PASS with an empty FAIL list and a PENDING-OWNED list naming only their own wave's in-flight branches. That is a scheduling problem wearing a reporting problem's clothes, and it will repeat forever unless a wave breaks it. The remedy: a wave that intends to close dispatches exactly ONE source-changing lane and orders the ledger behind it with dependsOn, so the ledger's cut sha contains the fix it would otherwise have to report as pending. Every other lane in a closing wave must be log-only -- log-only lanes write only under docs/verification-log/ and own no SPEC item, so they can never produce a PENDING-OWNED row no matter when they merge. The corollary constrains me, not the workers: a planner may not add a second implementation lane to a closing wave and still expect its ledger to read PASS. goalComplete remains licensed only by a ledger with both lists empty, cited file:line at its own audited sha, cross-read by the next planner against that wave's other verification logs.
