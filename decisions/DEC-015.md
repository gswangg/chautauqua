# DEC-015: Additive migration discipline; submission_track join; form.tracks_json

The initial schema (wave-1 task, still in flight) follows DEC-003, which omitted two things wave 2 needs; and parallel workers must never rewrite an already-committed migration. Discipline: migration files are append-only history — never edit a committed migration; all later schema changes ship as new numbered migration files plus append-only edits to the former src/db/schema.ts (now split across src/db/schema/). First addition (owned by exactly one task, w2-a, as the next-numbered migration — skip anything main already has an equivalent for): table submission_track { submission_id text references submission, track_id text references track, primary key (submission_id, track_id) } with FK indexes, because talks are submitted to one or more tracks (swyx) and reviewer assignment, filtering, and the agenda all key on a real join — track membership is NOT a form_field answer. Also form.tracks_json (JSON array of track ids offered on the form; null/empty means all event tracks) so J1's 'set one or more tracks on the form' has a home; add via ALTER TABLE in the same migration if the landed schema lacks it.

## Amendment (wave 80): form.tracks_json has ONE validated parser, and "empty means all event tracks" is normalised in exactly one place

Verified on main: `form.tracks_json` has two readers that give different answers for the same stored bytes. `resolveOfferedTrackIds` (src/lib/submit-core.ts:95-103) validates array-ness, treats an empty array as DEC-015's "all event tracks are offered", and silently filters non-string members; `toFormRow` (src/server/repo/forms.ts:69) does `row.tracksJson ? (JSON.parse(row.tracksJson) as string[]) : null` with no validation at all, and that value is what `src/routes/api/forms.ts:49` puts on the admin wire as the CFP builder's offered-tracks control. So for a stored `"[]"` the builder says "no tracks offered" while the public form at /submit/:slug offers every track; for a stored array with a non-string member the builder ships it to the SPA while the public form drops it. This is the same fracture wave 79 closed one table over on form_field.options_json/rule_json — a column that decides what the public CFP asks, hand-parsed with two different empty answers. RULING: a new pure-core module `src/forms/form-tracks.ts` is the only place `tracks_json` is parsed. `parseFormTracks(json, formId)` returns `null` for null/undefined/""/an empty array (the ONE spelling of DEC-015's "no restriction") and throws a named `FormTracksError` on invalid JSON, a non-array, or a non-string member — the silent `.filter(typeof v === 'string')` is deleted, matching `parseFieldOptions`'s policy on the same public page. The write path (src/routes/api/forms.ts:122-135) already validates array-of-strings against known track ids, so the throw is unreachable from the product's own writes and only fires on legacy/hand-edited rows, which is exactly when we want it loud.
