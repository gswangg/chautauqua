# DEC-927: The speaker portal's round-trip count is independent of its row count: a chain read carries its own version numbers, a home read is set-based

Three per-row awaits, all wearing a Promise.all. src/routes/portal/tasks.tsx maps the version chain and calls getFileVersionNumber once PER version, even though listFileChainVersions' own docstring promises 'one extra query, not N' -- the batch select simply forgets to include version_no, the column DEC-818 stores at insert time. src/routes/portal/index.tsx does it twice more: getLatestDeliverable once per session, and listDeliverableCandidates once per file_request task, a query whose only inputs are contactId+eventId and which therefore repeats itself verbatim. Rule: FileChainVersionRow carries versionNo, selected in the batch it already issues (throwing on a null exactly as getFileVersionNumber does), and the portal task page reads it -- including the page's own 'version N', which is the chain's last entry, not a fifth query. repo/portal/sessions.ts gains listLatestDeliverables(db, submissionIds) and repo/portal/tasks.ts gains listDeliverableCandidatesForEvents(db, contactId, eventIds), both chunked per DEC-078 and returning a Map, with the singular helpers kept only where a single-row caller still needs them and no compatibility shim anywhere. Ownership is split so two tasks never edit one file: files-versions.ts + routes/portal/tasks.tsx belong to one task, repo/portal/*.ts + routes/portal/index.tsx to the other. A counting-fake-db test (modelled on test/review-queue-roundtrips.test.ts) holds the count equal at 3 rows and 300.
