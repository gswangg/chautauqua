# DEC-913: A tab strip's counts are ONE grouped query on the list envelope, not one request per tab

app/src/pages/content/ContentApp.tsx:102-111 loops WORKLIST_TABS and issues a bounded perPage=1 aggregate read per tab, plus a fourth for the 're-uploaded' headline — four round trips on every content page load and every tab switch, purely to print four numbers about the same filtered set. DEC-825 was right that one constant must own each tab's predicate (worklist.ts's WORKLIST_TAB_CONTENT_STATUS stays), and right that a page-count stand-in lies; it was wrong about where the number comes from. This is the field guide's own rule — a per-kind count re-scanning per kind is N scans even wearing a Promise.all — and it is the same fix already being made for the files library's kind chips. Rule: the submissions list envelope carries `contentStatusCounts` and `reuploadedCount`, computed by one grouped aggregate over the SAME filtered base query minus the contentStatus/reuploaded narrowing, so the chips, the headline and the rows are one query's arithmetic and cannot drift. The client derives every chip from the envelope it already has and issues no count request at all. DEC-825 is narrowed, not reversed: one owner for the predicate, one query for the counts.
