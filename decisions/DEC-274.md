# DEC-274: Public visibility is TWO predicates, not one: visibleSessionConditions (accepted + content-approved) gates sessions, visibleParticipantConditions (visible + invite-state) gates speakers, and session-rooted queries stop inner-joining participant

Verified at HEAD, not inherited: src/server/repo/public.ts:38 `visibleSubmissionConditions()` ANDs the session gate (submission.status='accepted', submission.content_status='approved') together with the speaker gate (participant.visible=1, participant.invite_status IN ('none','accepted')), and every session-rooted query mandatorily innerJoins participant -- getVisibleSubmissionIdsOrdered (:167,:178), getPublicSessionsByIds (:373), getPublicSessionDetail (:635), getPublicAgenda (:694). Consequence: an accepted + content-approved session whose participants are all hidden, or which has none at all, renders on NO public surface and is absent from schedule.ics, silently. That state is reachable today by ordinary organizer actions -- POST /api/v1/events/:id/submissions takes `contact` as optional (src/routes/api/submissions.ts:103) and cloneSubmission copies tracks and answers but no participants (src/server/repo/submissions/create.ts:125-179) -- i.e. exactly J3's manual-session/invited-talk paths. SPEC section 5 states the gates are 'distinct, never collapsed'; a TBA keynote or a session whose speaker is not yet announced must still appear on the program with an empty speaker line. Fix by splitting the predicate in three and keeping the composite ONLY for the two genuinely speaker-rooted queries (getPublicSpeakers, getPublicSpeakerDetail). The EMB-02 speaker-name search keeps working by turning the participant/contact joins into a leftJoin whose ON clause carries visibleParticipantConditions(), so title-only matches and speakerless sessions survive while a hidden speaker's name still cannot be searched. hydrateSessions already applies the speaker gate separately and is the single place speakers are emitted, so speakerless sessions get speakers: [] with no leak.
