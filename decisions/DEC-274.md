# DEC-274: Public visibility is TWO predicates, not one: visibleSessionConditions (accepted + content-approved) gates sessions, visibleParticipantConditions (visible + invite-state) gates speakers, and session-rooted queries stop inner-joining participant

Verified at HEAD, not inherited: src/server/repo/public.ts:38 `visibleSubmissionConditions()` ANDs the session gate (submission.status='accepted', submission.content_status='approved') together with the speaker gate (participant.visible=1, participant.invite_status IN ('none','accepted')), and every session-rooted query mandatorily innerJoins participant -- getVisibleSubmissionIdsOrdered (:167,:178), getPublicSessionsByIds (:373), getPublicSessionDetail (:635), getPublicAgenda (:694). Consequence: an accepted + content-approved session whose participants are all hidden, or which has none at all, renders on NO public surface and is absent from schedule.ics, silently. That state is reachable today by ordinary organizer actions -- POST /api/v1/events/:id/submissions takes `contact` as optional (src/routes/api/submissions.ts:103) and cloneSubmission copies tracks and answers but no participants (src/server/repo/submissions/create.ts:125-179) -- i.e. exactly J3's manual-session/invited-talk paths. SPEC section 5 states the gates are 'distinct, never collapsed'; a TBA keynote or a session whose speaker is not yet announced must still appear on the program with an empty speaker line. Fix by splitting the predicate in three and keeping the composite ONLY for the two genuinely speaker-rooted queries (getPublicSpeakers, getPublicSpeakerDetail). The EMB-02 speaker-name search keeps working by turning the participant/contact joins into a leftJoin whose ON clause carries visibleParticipantConditions(), so title-only matches and speakerless sessions survive while a hidden speaker's name still cannot be searched. hydrateSessions already applies the speaker gate separately and is the single place speakers are emitted, so speakerless sessions get speakers: [] with no leak.

## Amendment (wave 42): the gate that publishes needs a set-based writer

visibleSessionConditions demands submission.content_status='approved' while the column defaults to 'pending' (src/db/schema/submissions.ts:25), and the ONLY writer is single-id POST /api/v1/submissions/:id/content-status (src/routes/files.ts:226) — unlike the bulk submission-status route at src/routes/api/submissions.ts:558. At the SPEC's 200-800-speaker scale (SPEC §2 principle 2, volume-first: 'a feature that demos well with 10 rows and dies at 2,000 is not built') the entire J10 public surface stays empty until a producer clicks approve once per session; the gap is measured (agenda publish returns heldBack) but not remediable. Bulk ops are set-based (house invariant), and the affordance is one conditional worklist action that approves exactly the rows the current filter shows — not a per-row checkbox column, which the v6 content frames do not carry.

## Amendment (wave 23): the public session gate is enforced at hydrateSessions, not only at its callers, and the hydrator is event-scoped

src/server/repo/public/sessions.ts:329 hydrateSessions reads schema.submission with `where(inArray(schema.submission.id, batch))` and nothing else: no visibleSessionConditions(), no eventId predicate. Its only protection is the docstring 'already visibility-checked by the caller', spread across seven call sites (sessions.ts:555 and :584, agenda.ts:157 and :271, detail.ts:219). All seven happen to gate today — verified each — so this is a latent, not a live, leak; but the gate is exactly what SPEC §6 calls out ('Server-side filtering for all public and anonymized data') and a docstring is not a gate. The predicate is two cheap equality checks on rows already being fetched by id, so enforcing it at the hydrator costs nothing and changes no caller's behavior. Ruling: gate and event-scope inside hydrateSessions, delete the caller-trust claim, and back it with a scan-lock over src/server/repo/public/** in the shape test/participant-invite-audience.scan.test.ts already uses for the participant gate — the session gate has never had one.

## Amendment (wave 12): the public session gate's population is the public surface's import closure, not one repo directory

`test/public-session-gate.scan.test.ts:15,45-51` roots its population at a single non-recursive `readdirSync` of `src/server/repo/public/`. Its sibling for the OTHER half of the same DEC-274 split — `test/participant-invite-audience.scan.test.ts:106` — walks all of `src/` and carries a named exemption map. One decision, two scan-locks, two different ideas of what the population is; the field guide's own standing rule (A DIRECTORY IS NOT A POPULATION, DEC-367/DEC-808) says the directory-rooted one is the weak twin. `publiclyVisibleIds` (`src/server/repo/agenda/payload.ts:192-203`) is a genuine public-gate reader living outside the walked directory — correct today, and completely invisible to the scan that exists to watch it. I rule the population is DERIVED: the static import closure of the public/embed/feed route surface. An ungated `schema.submission` reader reachable from a public route is a defect; a reader reachable only from admin routes is out of population by construction, not by an allowlist entry.
