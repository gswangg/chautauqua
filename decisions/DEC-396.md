# DEC-396: compose/preview and compose/send take a bounded id array: the one bulk endpoint DEC-182 missed

DEC-182 enumerated five bulk-ids endpoints and switched them to parseBoundedIdArray; src/routes/comms.ts:158 was not among them and still validates submissionIds as merely 'a non-empty array of strings'. That ordering is backwards: resolveComposeInput accepts an unbounded list, repo.loadComposeSubmissions then drives chunked D1 loads over it and buildRenderTargets does one KV write per recipient, all before expandRecipients' MAX_COMPOSE_RECIPIENTS cap (src/domain/compose.ts:57) can reject the batch. A 5MB string element reaches D1 the same way DEC-182 described. Rule: both compose handlers validate through parseBoundedIdArray(b.submissionIds, 'submissionIds', { maxCount: MAX_COMPOSE_RECIPIENTS }), importing the existing exported constant rather than inventing a second number -- one submission yields at least one recipient, so any id list longer than the recipient cap can never succeed downstream, and rejecting it at the door costs nothing a legitimate caller wanted.
