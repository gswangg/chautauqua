# DEC-338: Perf enforcement extends to the three hot admin screens nobody measures, and the perf seed grows the rows that make them measurable; the overview check loses its `optional` flag

Companion to DEC-331 (which covers public surfaces). scripts/perf-smoke.ts times submissions list, submission detail, organizer agenda, plan progress, contacts list and a rating write — but not the J6 onboarding grid (/api/v1/events/:id/onboarding, a per-speaker x per-task grid over 800 contacts), not the J4 reviewer queue (/api/v1/review/plans/:id/queue, the reviewer's ONLY screen, which loads every evaluation in the plan to compute counts), and not the comms history (/api/v1/events/:eventId/email-log). Two of those are unmeasurable today for a second reason: scripts/perf-seed-lib.ts seeds 2,000 submissions, 800 contacts, 12 reviewers and 600 evaluations but ZERO task/task_assignment rows and ZERO email_log rows, so the onboarding grid, the comms history and the overview comms card all measure an empty table — which is why the overview check could be carried as `optional: true` without anyone noticing. The seed therefore gains a deterministic onboarding fixture (5 tasks x 800 contacts) and 5,000 email_log rows spread across the last 30 days so the 7-day window is a real subset; the overview check loses `optional: true` (DEC-331: a check is never dropped or marked optional). All new checks take cls 'read' and are graded by DEC-309's budget minus the /health overhead floor. Over budget is a LOGGED PRODUCT FINDING naming the owning module and function — the lane does not optimise src/ (DEC-331), and a finding on the overview comms aggregate is already owned by this wave's DEC-334 lane and must not be double-fixed.

## Amendment (wave 31): a read route's independent repo calls issue as ONE concurrent wave — the server-side twin of SPEC §7's "one round trip per view"

SPEC.md:333-334 states "One round trip per view: each screen's data loads in a single joined query/endpoint — no client-side request waterfalls." The rule has only ever been enforced against the CLIENT. The two review reads DEC-338/DEC-347 added to the harness break it on the SERVER: `GET /api/v1/review/plans/:id/queue` (src/routes/review/reviewer.ts:99-215) awaits eleven repo calls strictly in sequence — getReviewerScopeTrackIds, getTrackNamesByIds, resolveReviewerSubmissions (itself 3 statements), countEvaluationsBySubmission, listSubmissionIdsRatedBy, listEvaluationScoresForReviewer, listFormatLabelsBySubmission, listAudienceLevelLabelsBySubmission, listSpeakerIdentitiesForSubmissions, listRecusalsForReviewer — and `buildResults` (src/routes/review/shared.ts:433-460) awaits five, of which three are mutually independent. Measured: reviewer queue adjusted p95 66.8ms, plan results 71.8ms, both against a 50ms read budget, at a D1 round-trip cost of a few ms each. RULING: on a read route, calls whose arguments do not depend on another call's RESULT are issued as one `Promise.all` wave; only a genuine data dependency creates a second wave. Three things a worker must not re-decide: (a) the response envelope, key order, row order and every number must be byte-identical before and after — this is a scheduling change, not a semantics change; (b) failures stay loud — `Promise.all` (never `allSettled`), first rejection propagates, no per-call catch; (c) the lane proves concurrency behaviourally, with an instrumented fake `Db` that records maximum in-flight statements and asserts it exceeds 1, not with a source grep for `Promise.all`. If, after the waves collapse, one statement still dominates, the index is the next lever (evaluation carries `evaluation_plan_id_idx` on plan_id alone, src/db/schema/review.ts:94, while both hot reads filter (plan_id, round) and order by (submission_id, id)); a fix that changes an aggregate's arithmetic is out of scope for this rule.
