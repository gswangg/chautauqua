# DEC-338: Perf enforcement extends to the three hot admin screens nobody measures, and the perf seed grows the rows that make them measurable; the overview check loses its `optional` flag

Companion to DEC-331 (which covers public surfaces). scripts/perf-smoke.ts times submissions list, submission detail, organizer agenda, plan progress, contacts list and a rating write — but not the J6 onboarding grid (/api/v1/events/:id/onboarding, a per-speaker x per-task grid over 800 contacts), not the J4 reviewer queue (/api/v1/review/plans/:id/queue, the reviewer's ONLY screen, which loads every evaluation in the plan to compute counts), and not the comms history (/api/v1/events/:eventId/email-log). Two of those are unmeasurable today for a second reason: scripts/perf-seed-lib.ts seeds 2,000 submissions, 800 contacts, 12 reviewers and 600 evaluations but ZERO task/task_assignment rows and ZERO email_log rows, so the onboarding grid, the comms history and the overview comms card all measure an empty table — which is why the overview check could be carried as `optional: true` without anyone noticing. The seed therefore gains a deterministic onboarding fixture (5 tasks x 800 contacts) and 5,000 email_log rows spread across the last 30 days so the 7-day window is a real subset; the overview check loses `optional: true` (DEC-331: a check is never dropped or marked optional). All new checks take cls 'read' and are graded by DEC-309's budget minus the /health overhead floor. Over budget is a LOGGED PRODUCT FINDING naming the owning module and function — the lane does not optimise src/ (DEC-331), and a finding on the overview comms aggregate is already owned by this wave's DEC-334 lane and must not be double-fixed.

## Amendment (wave 31): a read route's independent repo calls issue as ONE concurrent wave — the server-side twin of SPEC §7's "one round trip per view"

SPEC.md:333-334 states "One round trip per view: each screen's data loads in a single joined query/endpoint — no client-side request waterfalls." The rule has only ever been enforced against the CLIENT. The two review reads DEC-338/DEC-347 added to the harness break it on the SERVER: `GET /api/v1/review/plans/:id/queue` (src/routes/review/reviewer.ts:99-215) awaits eleven repo calls strictly in sequence — getReviewerScopeTrackIds, getTrackNamesByIds, resolveReviewerSubmissions (itself 3 statements), countEvaluationsBySubmission, listSubmissionIdsRatedBy, listEvaluationScoresForReviewer, listFormatLabelsBySubmission, listAudienceLevelLabelsBySubmission, listSpeakerIdentitiesForSubmissions, listRecusalsForReviewer — and `buildResults` (src/routes/review/shared.ts:433-460) awaits five, of which three are mutually independent. Measured: reviewer queue adjusted p95 66.8ms, plan results 71.8ms, both against a 50ms read budget, at a D1 round-trip cost of a few ms each. RULING: on a read route, calls whose arguments do not depend on another call's RESULT are issued as one `Promise.all` wave; only a genuine data dependency creates a second wave. Three things a worker must not re-decide: (a) the response envelope, key order, row order and every number must be byte-identical before and after — this is a scheduling change, not a semantics change; (b) failures stay loud — `Promise.all` (never `allSettled`), first rejection propagates, no per-call catch; (c) the lane proves concurrency behaviourally, with an instrumented fake `Db` that records maximum in-flight statements and asserts it exceeds 1, not with a source grep for `Promise.all`. If, after the waves collapse, one statement still dominates, the index is the next lever (evaluation carries `evaluation_plan_id_idx` on plan_id alone, src/db/schema/review.ts:94, while both hot reads filter (plan_id, round) and order by (submission_id, id)); a fix that changes an aggregate's arithmetic is out of scope for this rule.

## Amendment (wave 32): /api/v1/plans/:id/progress is the last seven-deep sequential await chain — independent reads issue as one Promise.all wave

DEC-338's wave-31 amendment established that SPEC §7's 'one round trip per view' has a server side and named reviewer.ts and buildResults. Re-read at the tip: reviewer.ts was fixed (w29-e, merged), buildResults was not, and a third route was never named. `plans-progress.ts:56,58,62,71,76,86,103` awaits SEVEN reads in a row; four of them (`listReviewerRowsForPlan`, `listEvaluatedPairsForPlan`, `listPlanFilteredSubmissions`, `listRecusalsForPlan`) depend on nothing but `plan`, and the remaining three form a two-step dependent tail. That is 7 serialized round trips where 3 waves suffice, on a screen an organizer opens to chase reviewers. RULING: independent reads in a route body issue concurrently; the envelope, ordering and every number stay byte-identical; concurrency is proven with an instrumented Db that counts in-flight statements, never with a grep. Corollary carried from wave 31: never hoist a read above an early return (a closed plan must not pay for a query it discards).

## Amendment (wave 33): four doors still serialize, and a parallel wave may not outrun its own authz gate

DEC-338's wave-31 amendment ruled that SPEC.md:333-334 ("One round trip per view") has a server side; its wave-32 amendment named `/api/v1/plans/:id/progress` as the last offender and ruled the fix but did NOT land it (field guide: A RECORDED RULING IS NOT A LANDED FIX). Re-read at `ce2c5a65`: `plans-progress.ts:52,56,58,62,71,76,86,103` still awaits eight reads in a row, and three MORE doors were never named — `src/routes/portal/index.tsx:558-594` (7 sequential awaits on the speaker's own submission page), `authzServeFile` (`src/routes/files.ts:641,649,655,660`, up to 3 sequential population probes before every authenticated file byte is served), and `buildRenderTargets` (`src/routes/comms/compose-core.ts:276,278,288,296,322`, 5 sequential batch reads on the J5 per-recipient preview at up to 100 recipients). RULING (unchanged core): independent reads issue as one Promise.all wave; envelope/ordering/every number byte-identical; Promise.all never allSettled; concurrency proven behaviourally with an instrumented fake Db, never a grep for the string. NEW COROLLARY, because parallelising a detail route can silently widen a read: a read whose ONLY scoping is a caller-supplied path id (e.g. `getPortalParticipants(id)`) may not be hoisted into the same wave as the read that PROVES ownership — it stays behind the 404. Reads that are themselves caller-scoped (contactId+orgId in their own arguments) and reads that jointly CONSTITUTE the ownership resolution (the three file-population probes) may run concurrently. Authorization order is a contract; scheduling may not reorder it.

## Amendment (wave 33): `/api/v1/plans/:id/progress`'s wave-32 ruling is now landed

Task w33-a landed the fix this file's own wave-32 amendment had only recorded (field guide: A RECORDED RULING IS NOT A LANDED FIX). `src/routes/review/plans-progress.ts`'s `GET /:id/progress` handler now runs three waves instead of eight sequential awaits: (1) `requireOwnedPlan` stays the FIRST, solo await — the authz gate this file's own wave-33 corollary above forbids joining into any concurrent wave, since it is what proves ownership of the path id before any other read runs; (2) one `Promise.all` of the four reads that depend only on `plan`/`round` (`listReviewerRowsForPlan`, `listEvaluatedPairsForPlan`, `listPlanFilteredSubmissions`, `listRecusalsForPlan`), followed by pure-JS index building; (3) one `Promise.all` of `getUsersByIds`, `getTrackNamesByIds` and `batchUserDisplayNames` — the last of which is fed the deduped `userIds` array resolved from wave 2's `reviewerRows` rather than `users.map(u => u.userId)`, so it no longer has to wait on `users` (wave 3's own sibling) first; extra keys the returned name map might carry beyond the eventual `users` set are inert, since every lookup is `nameByUserId.get(user.userId)` over `users`. Eight serialized trips become three. Proven behaviourally in `test/plans-progress-round-trip-depth.test.ts` (instrumented fake `Db`, max-in-flight assertion, plus an envelope-pinning test), mirroring `test/reviewer-queue-round-trip-depth.test.ts`.

## Amendment (wave 35): the speaker portal is a MEASURED surface — the perf seed mints one speaker and perf-smoke gains three portal read rows

DEC-338's own premise was that a hot screen nobody measures is a screen whose cost nobody knows, and it grew `scripts/perf-seed-lib.ts` so the onboarding grid and comms history stopped measuring empty tables. The speaker portal was never given the same treatment: `scripts/perf-smoke.ts`'s 33 checks contain zero `/portal/*` rows and its `login()` reads only the ORGANIZER credentials from `docs/fixtures/sample-data.json`, so there is no speaker session in the harness at all. Meanwhile wave 33 rewrote `/portal/submissions/:id` into a caller-scoped wave plus a gated wave (DEC-777 wave-33) and wave 34 is rewriting `/portal/tasks` from five waves to three — two scheduling rewrites on a surface with no row, which is DEC-644's own "A ROW NEVER ADDED MEASURES NOTHING" in its purest form. RULING: `scripts/perf-seed-lib.ts` mints ONE deterministic perf speaker — a `user` row with a known password, its `contact`, `participant` rows on a bounded set of accepted perf submissions, and task assignments — and emits its credentials in the perf profile's own fixture output, never into `docs/fixtures/sample-data.json` (the demo seed owns that file, and `task-w28-c` already recorded the trap that perf-smoke's login depends on it). `scripts/perf-smoke.ts` gains a second authenticated session and three `read`-class rows: `GET /portal`, `GET /portal/tasks`, `GET /portal/submissions/:id`. Over budget is a LOGGED PRODUCT FINDING naming the owning module — the lane does not optimise `src/` (DEC-331), and a new row that fails is a finding, not a reason to omit the row (DEC-644 wave-32).


## Amendment (wave 61): a round-trip-depth closure is proven behaviourally on the in-flight harness; the perf-env measurement is the operator's, not the worker's

The mandate's NO-REGRESSION RULE asks every P1-perf closure for a before/after on the remote perf env. Workers have no deploy and no perf env (stage-2 provisioning is out of scope), so demanding that of a lane would make the lane unclosable and invite a worker to fake it. DEC-338 already rules that concurrency is proven behaviourally, never by a source grep, and test/agenda-round-trip-depth.test.ts is the working instrument: an instrumented fake Db whose every SELECT resolves after a real macrotask delay, tracking maximum simultaneously in-flight statements. Ruling: a perf lane's evidence is (a) a max-in-flight assertion on that harness, (b) a WAVE COUNT assertion (increment a counter each time in-flight rises 0->1) so a lane cannot satisfy the test by widening one wave while leaving the ladder's depth intact, and (c) an unchanged-envelope pin. The remote re-measurement stays on the operator's checklist and is not a worker deliverable.
