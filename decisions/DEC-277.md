# DEC-277: A schedule slot's day must lie inside the event date range at write time; an out-of-range placement reads as UNSCHEDULED in the agenda payload, and the wire shape does not change

isValidSlotInput (the former src/server/repo/agenda.ts:353 (now split across src/server/repo/agenda/)) shape-checks `day` against /^\d{4}-\d{2}-\d{2}$/ and never compares it to event.start_date/end_date, while getAgendaPayload (:251) builds `days` from computeDays(start,end) and pushes EVERY slotted session into `placed` regardless of day. A slot on a day outside the range therefore renders in no column of the day grid, yet is counted as placed, so the 'N unplaced . M conflicts' counter reports 0 -- the worklist lies, which SPEC section 2.3 and J9 make the whole point of that screen. PATCH /api/v1/events/:eventId (src/routes/api/events.ts:227-278) validates start<=end but never touches existing schedule_slot rows, so shrinking the range manufactures this state. Two-sided fix. Write side: reject an out-of-range day with ApiError('invalid', ...) -- this is not the 'never blocking' rule (DEC-010), which is about CONFLICTS; a day the event does not span is an impossible input like endMin<startMin. Read side: classify an out-of-range slot as unscheduled -- it lands in `unscheduled`, counts in summary.unplaced, and stays draggable, so the producer fixes it by dropping it on a real day (the upsert overwrites the stale row). I explicitly reject deleting orphaned slots when the range shrinks: silently destroying a producer's placements on a date typo is worse than surfacing them. I also explicitly reject adding an `offGrid` field or a new summary key, because test/spa-contract-sweep.test.ts pins the exact key sets of placed/unscheduled/summary and the SPA reads them -- the honest counter is available with zero contract churn.


## Amendment (wave 60) — the event's calendar-day list has one implementation, it fails loudly, and both public surfaces read it

Two implementations answer 'which calendar days does this event span?'. src/server/repo/agenda/days.ts:10 computeDays throws on a malformed range (used by the admin agenda payload and auto-schedule). src/routes/public/sessions.tsx:43 eventDayList returns [] instead, after which :88 silently degrades the public day-index rail to only the days that already have sessions — the exact behaviour the rail's own comment at :81-85 forbids ('a day with zero sessions still reads "0 sessions" rather than vanishing'). Worse, the two PUBLIC surfaces disagree with each other: src/routes/public/dispatch.tsx:195 builds the agenda's day switcher from `dayCounts.map(d => d.day)` — scheduled days only — while sessions.tsx:86 uses the full event range, so on a three-day event whose first day is unscheduled the sessions rail lists three days and the agenda switcher lists two. RULING: src/domain/event-days.ts owns `eventDays(startDate, endDate)`, inclusive, throwing on a malformed or reversed range (event.startDate/endDate are already isIsoDate-gated at write time, so a malformed range is data corruption and gets the DEC-012 treatment, never a soft-degraded public page); computeDays and eventDayList are deleted and their callers re-pointed; dispatch.tsx:195's SWITCHER day set becomes the event's full range while the DEFAULT active day stays the first day that actually has sessions (read from dayCounts, not from the switcher set) so no default changes. Declared out of scope and deliberately unchanged: dispatch.tsx:235's /schedule itinerary day set, which is the visitor's own picks, not the event's range.
