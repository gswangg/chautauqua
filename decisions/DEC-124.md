# DEC-124: Server-side answer length caps in validateAnswers: text-kind answers max 2,000 chars, long_text max 20,000; field-level error 'Too long (max N characters)'

src/forms/validate.ts enforces required/type/options but no maximum length, so an unauthenticated public submit persists a 2,000,000-byte description verbatim (reproduced by a reviewer as SES-031) — unbounded payload bloat per submission against SPEC §6's server-side form-schema validation posture. Ruling: exported constants MAX_TEXT_LENGTH = 2000 and MAX_LONG_TEXT_LENGTH = 20000 in src/forms/validate.ts, enforced for kinds 'text' and 'long_text' respectively after the required check, producing a per-field error 'Too long (max N characters)' in the standard errors map. Dropdown values are already bound to the options list, number/checkbox are non-string, and file answers are server-generated keys, so no cap is needed there. The caps apply uniformly to public submit and portal edit since both flow through validateAnswers; all fixtures, seeds, and walkthrough inputs are far below these bounds.

## Amendment (wave 26): there is no red in this system — an invalid field is 1px ink border + 3px ink left edge + a 13px/600 ink message, summarised at the top and repaired in place

The V9 intake records an error-and-validation-states standard with nine frames and thirteen rules, and nothing on main implements it: src/routes/public/submit-views.tsx has per-field `.chq-field-error` paragraphs and no top summary, no anchors, no 'nothing was lost', no over-count. Ruling, binding on every future error surface: errors are set in WEIGHT AND RULE, never colour — the invalid control takes a 1px ink border with a 3px ink left edge (the same vocabulary 'overdue' uses) and its message renders in ink at 13px/600. Add the classes ONCE (`.chq-field-invalid`, `.chq-field-error`, `.chq-error-summary`, `.chq-error-summary-link`) and never invent a per-surface treatment. The four rules that bind this wave's public-submit application: (1) summarise at the top — "Three things need fixing before this can be sent" with one anchor link per problem — AND repeat the message at each field; (2) say what was kept — "Nothing was lost. Everything you typed is still below."; (3) count against the limit — "1,412 of 1,200" in the counter and "212 characters over" in the message, never a bare 'too long'; (4) required means pick one — "Pick one — a talk needs a track so the right people review it" — and a field whose cost is invisible says why it matters ("we send your portal link here, so a typo means you never get it"). Credentials still fail with ONE message for both causes; that half is wave 25's.


## Amendment (wave 28): the SPA error vocabulary is ONE file and is CLASS-NAME-FIRST — surfaces emit the agreed class names, one module styles them

The wave-26 amendment named four classes (.chq-field-invalid, .chq-field-error, .chq-error-summary, .chq-error-summary-link) and shipped them only into src/routes/public/cfp.css.ts. The admin SPA has none of them: app/src/styles.css:764 styles .chq-error/.chq-error-banner as a rounded bordered box and :1054 styles .chq-field-error as an 11px uppercase micro-label, and app/src/components/modal-frame.css:148 adds a THIRD register (.chq-form-row-error). Ruling: the SPA's copy of the vocabulary lives in exactly one new file, app/src/components/error-states.css, imported once from app/src/main.tsx AFTER ./styles.css; it owns .chq-field-invalid, the .chq-error-summary family, and the RESTYLE of .chq-field-error and .chq-form-row-error to the standard's 13px/600 sentence ink. No other app/src CSS file may declare those selectors, and a scan pins that. Corollary that decides task ordering: because the vocabulary is class names plus copy, a surface can emit the markup and be tested (render tests assert classes and text, not computed style) before the CSS module lands — so applying the standard to a surface is NOT sequential on the CSS, and only a surface that imports the shared ErrorSummary component is.

## Amendment (wave 50): ONE error vocabulary, two bundles — the SSR module and the SPA stylesheet are scan-bound, and the leading '!' marker is dropped

DEC-124 declares the no-red error vocabulary ONCE and reuses it by class name. It is now declared twice: src/views/error-states.css.ts (ERROR_STATES_CSS, composed by AUTH_CSS, PORTAL_CSS and CFP_CSS) and app/src/components/error-states.css (the admin SPA). Verified at the file on main, they disagree on the message rule: the SSR module declares `.chq-field-error { font-size:13px; font-weight:600; margin:0; color:ink }` PLUS `.chq-field-error::before { content: "! " }`, while the SPA declares the same three properties for `.chq-field-error, .chq-form-row-error` and no marker at all — so the identical class renders with a leading '!' on the portal and CFP and without it in the admin, and the SPA's own header comment claims 'weight + a leading marker/border' it never declares. The vendored ERROR & VALIDATION STATES STANDARD names exactly three properties for an invalid field — '1px ink border + 3px ink left edge + 13px/600 ink message' — and no marker glyph. RULING: the frames are the authority, so the '!' pseudo-element is dropped from ERROR_STATES_CSS rather than added to the SPA; the non-colour signal the standard actually relies on (the 3px ink left edge, plus role="alert"/aria-describedby, both already present on both sides) is unchanged, so nothing regresses for assistive tech. The two bundles are then bound by a scan test that extracts the shared declarations (.chq-field-invalid, .chq-error-summary and its children, .chq-field-error) from both files and fails naming any property whose value differs — the vocabulary is one contract or it is two grammars, and a comment is not a binding.

## Amendment (wave 59): a printed character budget is an enforced cap — FormFieldDef.maximum NARROWS validateAnswers' kind cap, and the locked abstract's 1,200 is set by the one projection

src/routes/public/submit-views.tsx:36 declares CFP_ABSTRACT_MAX_LENGTH=1200 and :384 applies it as a DISPLAY-ONLY `maximum` on the locked description field; src/views/form-render.tsx:138 turns that into the visible "412 / 1,200" counter. src/forms/validate.ts:98 computes its cap from `field.kind` alone and never reads `field.maximum` — so the public CFP shows every submitter a 1,200-character budget the server does not enforce until 20,000. submit-views.tsx:26-35 admits this in a comment and defers it to "a follow-up decision"; this is that decision. The design side is unambiguous: docs/design/Chautauqua Public and Portal.dc.html:1198 frames the OVER-LIMIT state as "1,412 of 1,200", DESIGN-RULINGS.md:204 requires "212 characters over" in the message, and docs/design/Chautauqua Submissions.dc.html:694 gives the Abstract field the hint "Up to 1,200 characters". RULING: `FormFieldDef.maximum` is an enforced per-field cap, not a display hint. validateAnswers takes `min(field.maximum, kindCap)` — a field maximum may only NARROW, never widen, so no form definition can raise a text answer past MAX_TEXT_LENGTH/MAX_LONG_TEXT_LENGTH. The 1,200 stops being a view-layer override and becomes a property of the locked `description` field, set inside projectFieldForAnswers (DEC-486's ONE projection, called by src/server/repo/submit.ts:142 and src/server/repo/portal-edit.ts:135), so the public CFP and the speaker's portal edit render the same counter and refuse at the same number. The refusal string stays byte-identical ("Too long (max N characters)") so src/routes/public/submit.tsx:134's overLengthErrorMessage keeps producing the counting copy the ruling asks for. A stored abstract longer than 1,200 is now unsaveable until trimmed; that is the intended meaning of a stated budget, and any seeded row over it is the seed being wrong, not the cap.

## Amendment (wave 61): a locked session field's character budget is a property of the field, not of the role writing it: ONE constant per locked field, read by every writer and declared by every control

submission.title and submission.description each carry TWO caps today, split by role, and each split produces a dead end. description: the speaker path (public CFP + portal edit) enforces LOCKED_ABSTRACT_MAX_LENGTH=1,200 via projectFieldForAnswers -> validate.ts:102, while src/routes/api/submissions.ts:210/290 lets an organizer POST/PATCH 20,000 — so an organizer can MINT an abstract its own speaker can never re-save (validate.ts refuses the untouched answer at 1,201). title: the mirror image — validate.ts caps the speaker's locked `text` title at MAX_TEXT_LENGTH=2,000 while submissions.ts:208/286 caps the organizer at MAX_NAME_LENGTH=200, so an organizer cannot open 'Edit title and abstract' and save ANY change to a submission whose speaker typed a 500-character title. And app/src/pages/forms/FieldList.tsx:160 prints 'Up to 20,000 characters' on the Abstract row whose own doc-comment claims it shows 'the real imported length cap' — the design frame (docs/design/Chautauqua Submissions.dc.html:694) reads 'Up to 1,200 characters'. Ruling: the tighter, human-scaled number wins in both directions — title 200, abstract 1,200 — declared once in src/forms/types.ts, stamped by projectFieldForAnswers for both locked session fields, imported by the organizer routes, and printed by every control that edits them. Restoring a stored revision (submissions.ts:409) deliberately stays unbounded: it replays a value the product already accepted.
