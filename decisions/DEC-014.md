# DEC-014: Public CFP account, draft, and claim-token flow (no inbox required)

SPEC J2 requires no-account start plus a post-submission password path, and the eval agent has no inbox (CFP-S2 allows signup 'as part of submitting'), so account creation must be reachable on-screen. Drafts: 'Save draft' on /submit/:eventSlug persists { formId, answers, savedAt } as JSON in KV under key draft:<sha256(token)> with 30-day TTL; the random 32-byte b64url token lives in cookie chq_draft_<formId> (Path=/submit). Returning with the cookie shows a resume banner and prefills answers. Drafts never create submission rows and are invisible to organizers; the KV entry is deleted on successful submit. Claim tokens: on submission creation, store claim:<sha256(token)> -> { contactId, eventId } in KV, 30-day TTL; the confirmation email's {portal_link} is /claim/<token>; GET /claim/:token shows a create-password form; POST creates the user row (role 'speaker', contact_id set, DEC-004 hash format), deletes the KV key, starts a session, and redirects to /portal. The on-screen confirmation page ALSO links the same /claim/<token> URL ('Create a password to track your submission') so the whole account flow works with zero email access; if a user already exists for the contact's email, both the email and the page link /login instead. Repeat submitters are matched to their existing contact by case-insensitive email.

## Amendment (wave 25)

**Password reset is a hashed, single-use, 1-hour KV grant, newest-only, and answers identically for unknown addresses**

USER DEC (2026-08-14): password reset WILL be built; the mechanism is design-independent and the frames for all four screens are already vendored. It is deliberately NOT claim.ts's shape: a claim token lives 30 days and supersedes with a 48h grace because an organiser's batch send can fail after minting and strand a speaker; a reset is requested by the person themselves, who can trivially ask again, so it is single-use, RESET_TTL_SECONDS = 3600, and a fresh mint HARD-deletes the prior record (index `pwreset-for:<userId>` names the one live hash). Enumeration is closed the DEC-004 way: POST /forgot renders the same "Check your email" card echoing the submitted address whether or not a user row exists, and never branches its response; the DEC-180 failures-only limiter is keyed on the normalised email. Completing a reset enforces MIN_PASSWORD_LENGTH and calls issueSessionRevokingAll — a reset asserts the credential was lost, which is the opposite of login's rotate-this-session-only rule (DEC-994). The token is stored hashed only; plaintext exists nowhere but the email.
