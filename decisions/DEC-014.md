# DEC-014: Public CFP account, draft, and claim-token flow (no inbox required)

SPEC J2 requires no-account start plus a post-submission password path, and the eval agent has no inbox (CFP-S2 allows signup 'as part of submitting'), so account creation must be reachable on-screen. Drafts: 'Save draft' on /submit/:eventSlug persists { formId, answers, savedAt } as JSON in KV under key draft:<sha256(token)> with 30-day TTL; the random 32-byte b64url token lives in cookie chq_draft_<formId> (Path=/submit). Returning with the cookie shows a resume banner and prefills answers. Drafts never create submission rows and are invisible to organizers; the KV entry is deleted on successful submit. Claim tokens: on submission creation, store claim:<sha256(token)> -> { contactId, eventId } in KV, 30-day TTL; the confirmation email's {portal_link} is /claim/<token>; GET /claim/:token shows a create-password form; POST creates the user row (role 'speaker', contact_id set, DEC-004 hash format), deletes the KV key, starts a session, and redirects to /portal. The on-screen confirmation page ALSO links the same /claim/<token> URL ('Create a password to track your submission') so the whole account flow works with zero email access; if a user already exists for the contact's email, both the email and the page link /login instead. Repeat submitters are matched to their existing contact by case-insensitive email.

## Amendment (wave 25)

**Password reset is a hashed, single-use, 1-hour KV grant, newest-only, and answers identically for unknown addresses**

USER DEC (2026-08-14): password reset WILL be built; the mechanism is design-independent and the frames for all four screens are already vendored. It is deliberately NOT claim.ts's shape: a claim token lives 30 days and supersedes with a 48h grace because an organiser's batch send can fail after minting and strand a speaker; a reset is requested by the person themselves, who can trivially ask again, so it is single-use, RESET_TTL_SECONDS = 3600, and a fresh mint HARD-deletes the prior record (index `pwreset-for:<userId>` names the one live hash). Enumeration is closed the DEC-004 way: POST /forgot renders the same "Check your email" card echoing the submitted address whether or not a user row exists, and never branches its response; the DEC-180 failures-only limiter is keyed on the normalised email. Completing a reset enforces MIN_PASSWORD_LENGTH and calls issueSessionRevokingAll — a reset asserts the credential was lost, which is the opposite of login's rotate-this-session-only rule (DEC-994). The token is stored hashed only; plaintext exists nowhere but the email.

## Amendment (wave 34): a reset grant is consumed as the gate in front of the write, never at the top of the handler

POST /reset/:token deletes the grant before validating anything, then re-renders the password form pointing back at the now-dead token: one mistyped confirmation permanently burns the only live link and every retry lands on the 410 card with no explanation of why. Single-use does not require consume-first, only consume-before-write. The ordering becomes peek -> load user -> validate -> consume (410 if a concurrent POST won the race) -> write -> revoke sessions, which keeps replay dead (the write is unreachable without a successful consume) while making a typo recoverable. Two same-handler corollaries: resolveBaseUrl must be hoisted out of the `if (user)` branch, because a deployment missing PUBLIC_BASE_URL would 500 for a known address and 200 for an unknown one, re-opening exactly the enumeration oracle DEC-004 closes; and the eventless-org case, where no email_log anchor exists and the send is skipped, must log loudly rather than mint a token nobody can ever receive - while never changing the response.


## Amendment (wave 10, sha e770146d): a KV record is external input — it is validated at its reader, and the draft's track ids are a declared field, not a reserved key smuggled into AnswerMap

src/lib/draft.ts:77 and src/auth/claim.ts:104,115 each do `JSON.parse(raw) as <Record>` on a KV blob with no shape check. On the public CFP that is a live 500: submit-get.tsx:56-57 does `answers = draft.answers` and `draft.answers.__trackIds`, so a record missing `answers` throws on an ANONYMOUS GET and the submitter's own cookie keeps it broken for 30 days with no route out. The same file also shows why the shape drifted: submit-draft.tsx:181 launders an array into AnswerMap with `(answers as Record<string, unknown>).__trackIds = selectedTrackIds`, so DraftRecord's declared type is a lie and submit-get.tsx pays for it with a second cast — the double-cast pattern DEC-212 named as "the type system overruled in silence". RULING: (1) DraftRecord gains `trackIds: string[]` as a first-class field; the reserved-key smuggle and both casts are deleted. (2) Each KV reader gets a validating parser. A blob that fails validation is treated as ABSENT — this is the sanctioned external-input boundary exception, not a silent fallback, so it must be visible: the CFP renders the empty form with a stated banner and deletes the unusable record; a malformed claim record 404s exactly as a missing token does, and never reaches user creation as a half-record. Fail-loudly is about the message reaching the person, not about something throwing (DEC-023, wave 82).
