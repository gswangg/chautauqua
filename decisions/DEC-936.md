# DEC-936: A roster row that covers two of the event's sessions carries BOTH participations; a lowest-id pick is not an answer to "which of your talks"

src/server/repo/tasks/grid.ts:220-222 resolves a roster row's invite-status control with three correlated scalar subqueries, each `order by participant.id asc limit 1`. A contact who is an accepted participant on TWO sessions of the same event -- routine for a returning speaker -- therefore shows exactly ONE arbitrary participation, and the organizer's menu writes to that one participant row while the other session's status is invisible and unreachable from the roster. This is precisely the shape DEC-891 rejected for the portal's deliverable picker: a deterministic tie-break answers "which row" but not "which of your talks" -- when the data admits two, the surface must ASK. It is also a predicate mismatch: the ?inviteStatus= filter pill (grid.ts:191-196) is an EXISTS over ANY of the contact's participations, so a contact can match the Declined pill while their row's control renders Confirmed. Rule: the grid row's contact object carries `participations: [{participantId, submissionId, ref, title, inviteStatus}]`, ordered by submission seq, replacing the singular participantId/submissionId/inviteStatus triple entirely (no shim, no duplicate field). It is built from ONE grouped query over the page's contact ids, chunked per DEC-078 -- never a subquery per column, never a query per row. The identity column renders the existing single ParticipationMenu when the array holds exactly one entry, and one menu per session, each labelled with that session's ref, when it holds more; the filter pill's EXISTS-any predicate is then honest because every participation it matched on is visible on the row. The empty array remains impossible (rosterParticipantExistsForContact guarantees at least one) and is still a loud throw. This wave scopes the change to the grid; DEC-930's per-speaker detail page keeps its own shape.
