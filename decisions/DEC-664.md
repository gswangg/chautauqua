# DEC-664: One reporter for every send: the SPA renders every reminder/send outcome through a single describeSendResult that must account for every intended recipient

Three call sites report the same kind of result three different ways and two of them drop fields the server actually returned. app/src/pages/review/ProgressPanel.tsx:42-43 reads only `sent` from POST /api/v1/plans/:id/remind, which returns { reminded, sent, failed, remaining } (src/routes/review/plans.ts:515) -- so a run where every mail throws renders "Reminder sent to 0 reviewer(s)." beside a button that just said "Remind laggards (11)", the exact dishonesty the sbek re-run flagged. app/src/pages/Overview.tsx:161-167 reads {sent, skipped, remaining} and drops failures; app/src/pages/speakers/OnboardingGrid.tsx:184-192 hand-builds a third sentence. The helper lives SPA-side (app/src/lib/sendResult.ts) rather than crossing the pure-core boundary, because DEC-660 is already spending this round's one app-side boundary module on merge fields and the bundle budget is measured. Its contract: the sentence must account for sent + failed + skipped + remaining, must never restate an intent count, and when sent === 0 must say why.

## Amendment (wave 59): a send report names the REASON per failed recipient — a count is not a report

Every send endpoint computes a per-recipient reason and puts it on the wire: src/routes/comms/send.ts:152, src/routes/api/contacts/bulk-email.ts:213, src/routes/content-notes.ts:166 and src/routes/comms/portal-invites.ts:81-84 all emit `failed: {email, message}[]`, and portal-invites deliberately synthesises `{email: "", message: "<Name> has no email address on file"}` so a contact with no address is named rather than silently skipped. Three of the five SPA readers then throw the message away: app/src/pages/speakers/SpeakerDetailPage.tsx:122 renders only describeSendResult's "Nothing was sent. 1 failure." on a SINGLE-recipient action where the reason is the entire answer; app/src/pages/contacts/BulkEmailModal.tsx:326 lists bare addresses; app/src/pages/content/CommentThread.tsx:109 joins addresses with commas. The other two get it right — app/src/pages/comms/ComposeWizard.tsx:1028-1032 renders email + message per row (the B1 step-4 report anatomy), and app/src/pages/speakers/OnboardingGrid.tsx:542 appends the messages to its toast — which is the proof this is a drop, not a policy. RULING: DEC-238's "a boundary fails per RECIPIENT, not per REQUEST" binds the READER too. One shared reporter renders a SendResult's failures (address when there is one, the message always, the message alone when `email` is empty), one shared helper produces the same text for toast contexts, and every reader uses one of the two. A scan keeps the population honest so the sixth reader cannot re-drop the reason.
