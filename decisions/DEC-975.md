# DEC-975: DEC-904's read gate gets its write counterpart: you cannot delete a saved view you could not list

DEC-904 made a saved view private until its author shares it and pushed visibleToViewer (shared OR author) into the WHERE of both listSavedViews and countSavedViews. It has no write counterpart. DELETE /api/v1/views/:id (src/routes/api/views.ts:89-93) checks only ownership.orgId, and getSavedViewOwnership (src/server/repo/views.ts:146-157) never projects createdByUserId or shared — so any organiser in the org can delete another organiser's PRIVATE saved view, a row the API will not even show them, contradicting SPEC §6's 'object-level ownership checks on every fetch-by-id'. A destructive gate must be at least as tight as the read gate. Rule: getSavedViewOwnership additionally projects createdByUserId and shared; the DELETE handler keeps the cross-org 403 first, then answers 404 'Saved view not found' when the row is invisible to the caller (not shared AND authored by someone else) — an invisible row must not have its existence confirmed by a 403 — and 403 'Only the organiser who created a saved view can delete it' when it is visible but authored by someone else. createdByUserId IS NULL is legacy org-owned and any organiser in the org may delete it; that branch is explicit, not an accident of a null comparison.
