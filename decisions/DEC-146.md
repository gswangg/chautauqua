# DEC-146: SPA date rendering rule: shared null-safe helpers only — date-input helpers return '' and display formatters return an em dash for null/undefined/invalid; no raw new Date().toISOString()/toLocale* on nullable values in page components

The plan-detail blank-page crash ('Invalid time value') came from new Date(ms).toISOString() on a nullable plan date (app/src/pages/review/PlanEditor.tsx:18), and the same pattern is a latent crash anywhere a nullable timestamp meets a formatter. House rule: app pages convert timestamps only through shared helpers (msToDateInput -> '' for null/undefined/NaN; formatDate -> '—' for the same), each unit-tested for the null/undefined/NaN cases. This is a rendering-guard rule at the UI boundary, not a fallback that hides data bugs: server-side invariants still fail loudly; a null plan date is a legitimate domain state (unbounded window, per isPlanOpen) that the UI must render, not throw on.

## Amendment (wave 44): one date-input grammar for the SPA — a text DateField speaking "11 May 2028", never a native input[type=date]

DEC-146 already fixed date DISPLAY on shared null-safe helpers; date ENTRY was left to the browser. 13 `<input type="date">` across 7 app files render whatever the UA locale picks (07/14/2026 on the review plan editor), while every v6 frame that shows a date field shows "24 Mar 2027" / "11 May 2028". A locale is not a design decision we made. One `DateField` component owns parse/format; the wire shape stays the existing yyyy-mm-dd string so no caller changes its data model; unparseable text is refused inline rather than coerced (fail loudly). Half-adoption is forbidden — the value of one grammar is that there is exactly one.

## Amendment (wave 49): DateField accepts every unambiguous date grammar and a rejected date BLOCKS the submit that contains it

Two halves of one measured defect. (1) parseDayInput (app/src/lib/dates.ts:275) accepts only '11 May 2028' and ISO, so the eval agent's 'May 1, 2027' was refused — a month-first spelling is unambiguous and cheap to accept; all-numeric slash forms (05/11/2028) stay refused because they are genuinely ambiguous, and the OUTPUT grammar (formatDayInput) does not move: one display grammar, several input spellings. (2) Worse: DateField (app/src/components/DateField.tsx:51) keeps its rejection entirely to itself — it sets local state, never calls onChange, and the parent's value stays as it was, so the New-task modal saves with 'No due date'. A validation error the submit path cannot see is a silent drop and a direct fail-loudly violation. Ruling: while the field's text is non-empty and unparseable, DateField calls setCustomValidity on its own input, so the field is a first-class participant in its enclosing form's constraint validation exactly like `required` — one component change fixes all seven call sites, and no form containing a DateField may set noValidate.
