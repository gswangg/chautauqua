# DEC-805: Inviting a speaker to the portal is a send, not a pill

VERIFIED there is no portal-invite path anywhere in src/ (zero matches for portal-invite/sendPortalInvite); the roster and grid offer no invite affordance and the submission detail shows only a read-only invite-status pill, so an organiser who wants one named speaker in the portal must go to Comms, select that speaker's session, and compose a message from scratch. The rubric asks for the invitation; the product has every part of it already — resolvePortalLink mints exactly the right link (src/routes/comms.ts:393), the Mailer port sends, and d1EmailLogWriter records the send so Comms history stays the one place every message is auditable. Decision: POST /api/v1/events/:eventId/portal-invites {contactIds} is the one invite path: organiser-only, bounded id array, every recipient verified as a participant on this event before anything is sent, message rendered from ONE exported invitation template (speaker_name/event_name/portal_link only) rather than typed into the route, sent through the same mailer and logged through the same email_log writer compose uses, returning {sent, skipped, failed} so a recipient without an address is NAMED rather than silently dropped. This does not weaken DEC-009: nothing here is triggered by a status change — an organiser pressed a button that says it sends an email.
