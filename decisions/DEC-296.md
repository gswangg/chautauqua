# DEC-296: Stage-1 dev links: .dev.vars.example ships PUBLIC_BASE_URL=http://localhost:8787, and under DEV_MODE an observed loopback origin outranks a loopback PUBLIC_BASE_URL

wrangler.jsonc's routes/custom_domain: chautauqua.cc entry (human stage-2 wiring, left untouched) makes new URL(c.req.url).origin resolve to the live production host under wrangler dev, so DEC-252's final fallback (src/server/origin.ts:98) emits http://chautauqua.cc/claim/<token> in the fresh-clone quickstart whenever no loopback Origin/Referer header is present — a judge following the README literally gets a claim link that does not resolve on their machine (task-w8-g OPEN ITEM 2, task-w8-f). Two changes, both in app-owned files, neither touching the operator's deploy config. (1) .dev.vars.example — the tracked template scripts/ensure-dev-vars.ts copies to the gitignored .dev.vars on first predev — gains PUBLIC_BASE_URL=http://localhost:8787, so the zero-secret default path is correct by construction and stays consistent with SPEC section 6's '.dev.vars gitignored'. (2) Because a checked-in default cannot know the port, DEC-252's precedence is amended for the dev branch ONLY: when DEV_MODE === '1' and the configured PUBLIC_BASE_URL is itself a loopback origin, an observed loopback origin among [request URL origin, Origin header, Referer origin] wins over it. A non-loopback PUBLIC_BASE_URL always wins and production (no DEV_MODE) is byte-identical to today, so an attacker-supplied header still can never poison a real mailed link. Battery lanes that pass --var PUBLIC_BASE_URL:http://localhost:<their port> keep working under both rules.

## Amendment (findings wave 7) — the instance's own origin is read at render time, never typed into copy; `chautauqua.cc` is one deployment, not the product

DEC-296 established that emitted links resolve against the running instance's origin rather than a compiled-in host. The same rule was never applied to visible copy: app/src/pages/settings/YourDataPanel.tsx:192 and :220 both render the literal string `chautauqua.cc/docs/api` as the API-docs value. On every local `wrangler dev` run and on every self-hosted deployment — and this is an MIT open-source product whose premise is that the data and the instance are the customer's — the Settings page tells the operator their API documentation lives on a hostname they do not own. It is the same env-leak-into-copy class the fleet caught when the reminders modal printed a raw localhost URL, only pointing the other way. The frame (docs/design/Chautauqua Settings.dc.html:261/432) draws `chautauqua.cc/docs/api` because the mock IS that deployment; rendering the live host satisfies the frame exactly on production and tells the truth everywhere else, and the precedent already exists one directory away — FormsPage.tsx:252 renders the CFP share link as `${window.location.host}/submit/${slug}`. RULING: derive the host, single-source it, and add a scan test that no product source file under `src/` or `app/src/` carries a hard-coded deployment hostname in copy.

## Amendment (wave 37): a dev base-URL/port mismatch is detected in the walkthrough's pre-flight, not forty steps in; the resolveBaseUrl gap behind it is FILED for wave 38

resolveBaseUrl (src/server/origin.ts:104-133) applies DEC-296's dev-loopback exception only when a loopback origin is observable ON THE REQUEST — request URL origin, Origin header, or Referer (firstLoopbackCandidate, :152-163). A scripted fetch against `wrangler dev` with wrangler.jsonc route shadowing presents none of the three: c.req.url resolves to the shadowed production host and no browser-set Origin/Referer exists. So the loopback PUBLIC_BASE_URL default from .dev.vars.example wins and every mailed link points at :8787 while a gate lane drives a per-worktree port. This has now cost two walkthrough gates a full run each (task-w26-f, task-w36-b), each diagnosed mid-run at producer/J2 on an off-origin scraped reset link. The instrument fix is a five-second pre-flight in scripts/walkthrough.ts comparing --url's origin against the configured PUBLIC_BASE_URL origin, aborting with the exact remediation before spawning any module; the pure comparison lives in scripts/walkthrough-lib.ts so it is unit-testable. Reading .dev.vars for exactly the PUBLIC_BASE_URL key is sanctioned here — scripts/ensure-dev-vars.ts's prohibition is on reading or logging the file's contents generally, and an origin is not a secret; no other key may be read or printed. The underlying resolveBaseUrl gap is a product change and is therefore FILED with file:line for wave 38, not fixed in a frozen wave.

## Amendment (wave 38): the dev-loopback exception reads the Host header — the request the exception was written for has no other loopback evidence (the gap DEC-296's wave-37 amendment filed for this wave)

DEC-296's own wave-37 amendment (`decisions/DEC-296.md:9-11`, already on main) files this explicitly for wave 38: `firstLoopbackCandidate` (`src/server/origin.ts:152-163`) looks only at the request URL origin, the `Origin` header and `Referer`, and a scripted fetch against route-shadowed `wrangler dev` presents none of the three — `c.req.url` resolves to the shadowed production host and no browser sets Origin/Referer. So the exception is unreachable in exactly the situation it was written for, the loopback `.dev.vars.example` default wins, and every mailed link points at :8787 while a gate lane drives a per-worktree port. That has now cost two walkthrough gates a full run each. RULING: `firstLoopbackCandidate` gains the `Host` header as its SECOND candidate (after the request URL origin, before Origin/Referer), built as `http://<host>` and accepted only when it parses as a LOOPBACK origin. Scheme is `http:` by construction rather than inherited from `c.req.url` — under route shadowing the request URL's scheme belongs to the shadowed production host, not to the local dev server, and a loopback dev server is http. Both existing gates are untouched, so this can never widen production: the caller only consults candidates when `DEV_MODE === "1"` AND (no PUBLIC_BASE_URL, or a PUBLIC_BASE_URL that is itself loopback); a non-loopback PUBLIC_BASE_URL still wins outright. This is a best-effort widening, not the enforcement — the enforcement is wave 37's pre-flight, and battery lanes still pass `--var PUBLIC_BASE_URL:http://127.0.0.1:<port>`; if wrangler rewrites Host too, the branch simply does not fire and behaviour is exactly today's.
