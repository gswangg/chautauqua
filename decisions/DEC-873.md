# DEC-873: A rating is chosen from the scale, the blend is computed by the server's own function, and an evaluation is submitted or absent — the frame's "Save draft" ships as "Save"

VERIFIED across app/src/pages/review/Scorecard.tsx: ratings are `<input type="number">` (291-301), there is no OVERALL block, no per-criterion weight, and one action button (335-339). Three rulings. (1) The 1-5 SEGMENTED control is the section's defining control per the Review GATE-1 report: a radiogroup of buttons over [plan.scale.min, plan.scale.max] with aria-checked and a filled selection — a single choice rendered as a single choice — while DEC-148's 1-9 keyboard path (scorecardKeyAction) keeps working unchanged. (2) The OVERALL block and the per-criterion "Weight N · NN%" are computed by the SAME pure functions the server and plan editor already use — computeWeightedScore and criterionWeightShares from src/domain/evaluation.ts — never re-derived client-side, so the reviewer's number and the organizer's number cannot disagree; computeWeightedScore fails loudly on a missing score, so the block renders an em dash until every rating criterion is scored and is never an input. (3) validateEvaluationScores refuses partial scores by design ("no partial submissions", evaluation.ts:203) and three separate readers already key on `submitted_at is not null` in their own ways, so a genuinely half-saved evaluation is a cross-cutting schema change, not a button. A control must name what it does: a button that cannot save a partial score is not a "draft". The frame's "Save draft" therefore ships as **Save** — the same PUT, no advance, a "Saved" confirmation — beside the primary renamed to the frame's "Submit and next". Reasoned deviation, documented here in the manner DEC-830 established.

## Amendment (wave 27): an evaluation with a null submittedAt IS the draft, and a draft never validates

DEC-873 shipped 'Save draft' as 'Save' on the premise that a half-saved evaluation would be a cross-cutting schema change. That premise is false on the current tree: evaluation.submittedAt is already nullable and every read side already treats null as not-yet-submitted (plans.ts counts a `draft` column, progress and results filter `submittedAt is not null`, submission history skips it, the comms feedback merge skips it, the delete guard only refuses on submitted rows). Only the WRITE unconditionally stamps submittedAt. So the draft is one flag on the PUT, not a remodel. Rules: a draft accepts partial scores and runs no completeness check; Submit runs the full check; a draft PUT against an already-submitted evaluation is a loud 400, never a silent un-submit; no read behaviour changes.

## Amendment (wave 46): a draft is invisible to every evaluation read that COUNTS, GATES, or RENDERS a recorded review — one exported predicate, one allowlisted exception

DEC-873's wave-27 amendment made submittedAt null mean 'draft' and said 'every read side treats null as not yet submitted'. Four reads keep that promise (listEvaluationScoresForPlan src/server/repo/review/evaluations.ts:71, listEvaluatedPairsForPlan :232, and the two route-level guards) and three do not, each with a user-visible consequence: (1) countEvaluationsForSubmission (:115, no predicate) is the cap check at src/routes/review/reviewer.ts:361-363, so ANOTHER reviewer's unsubmitted draft 409s a real reviewer with 'This submission has reached its evaluation cap'; (2) countEvaluationsBySubmission (:145) feeds ratingsCount at reviewer.ts:199/222, so a draft both corrupts SPEC J4's fewest-ratings-first ordering and, through needsMoreRatings at reviewer.ts:205, DROPS an actionable row out of the queue entirely; (3) listEvaluationsForSubmission (:255) is the organiser's per-submission Reviews section, so an organiser reads scores a reviewer never submitted. /results and /progress disagree with the queue and nothing errors. Ruling: evaluations.ts exports ONE `submittedEvaluationCondition()` (the `submittedAt is not null` SQL), every read in that module that counts, gates, orders or renders a recorded evaluation composes it — including listSubmissionIdsRatedBy and listEvaluationScoresForReviewer, so a reviewer's OWN draft reads as unscored (which is true: it has not been submitted) and no weighted myScore is computed from a partial draft. getEvaluation is the ONE exception and stays draft-inclusive by design: it is the draft's own resume read and the source of the 'already submitted' guard at reviewer.ts:356; it is named in an allowlist keyed by FUNCTION NAME (never a line number) inside a scan that derives every `.from(schema.evaluation)` select in src/ — because the next sibling read added at wave N+1 must fail the scan rather than quietly join the wrong half of the lattice. Where an existing test asserts the draft-inclusive behaviour, the test is wrong and is updated citing this amendment.

## Amendment (wave 54): an export is a read side — the evaluations CSV carries the submitted-evaluation predicate, and the predicate's population is enumerated, not remembered

DEC-873's own rule (src/server/repo/review/evaluations.ts:22-32) says every read side outside the reviewer's own resume read (getEvaluation) must carry submittedEvaluationCondition() in its WHERE, and it names "the organiser's evaluations list" explicitly. exportEvaluations (src/server/repo/exports/evaluations.ts:146-148) builds its own conditions array and carries no such predicate, so GET /api/v1/events/:id/export/evaluations emits in-progress drafts (blank submittedAt, blank weightedScore, partial score cells) that /api/v1/plans/:id/results excludes — the CSV and the screen disagree on the row count for the same plan. The fix is one predicate; the durable part is the enumeration: the rule was previously kept by memory across eight call sites and a ninth was written without it. Every `.from(schema.evaluation)` query in src/ must either carry the predicate or appear in a one-entry exemption ledger with a written reason, so the tenth query fails a test instead of shipping.
