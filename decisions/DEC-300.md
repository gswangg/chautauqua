# DEC-300: Deleting a form field is a declared cascade: 409 with the dependent counts unless the caller passes cascade=1, then dependent rules are cleared and orphaned answers deleted in one operation

src/server/repo/forms.ts:261 deleteField is a bare row delete. Today it leaves other fields' rule.fieldId dangling, so src/forms/visibility.ts:11 compares against undefined and an eq-ruled REQUIRED question silently vanishes from the public CFP with its required flag dropped, and it orphans submission_answer rows that then disappear from every inner-joined read (portal, review, exports) while still occupying the table. DEC-229 set the house precedent that deletes never cascade silently — but a track is structural while a question is editorial, and refusing to delete any question anyone has answered would freeze the form the moment the CFP opens. So the cascade is DECLARED rather than forbidden: DELETE /api/v1/fields/:fieldId returns 409 naming the dependent questions and the collected-answer count unless the request carries cascade=1, and with cascade=1 it clears ruleJson on dependents (they become unconditional — a question that shows up is a visible, arguable state; a required question that silently disappears is not), deletes the field's submission_answer rows, then deletes the field. The form builder turns the 409 message into its confirm prompt, so the non-technical producer is told exactly what they are about to lose. isVisible is deliberately NOT changed: it sees answers, not the field list, so it cannot distinguish a deleted trigger from an unanswered one — the invariant 'no rule references a missing field' is maintained by the cascade and asserted in test.
