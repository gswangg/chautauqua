# DEC-529: The evaluations export carries one labelled column per scored criterion plus the weighted score, derived from the score keys actually present — a raw scoresJson blob keyed by opaque criterion ids is the lock-in DEC-515 forbade

`the former src/server/repo/exports.ts:436-469 (now split across src/server/repo/exports/)` emits the `evaluations` kind with a `scoresJson` column holding the stored JSON verbatim, e.g. `{"cri_a1b2":4,"cri_c3d4":"Strong"}`. The criterion labels live in `evaluation_plan.criteria_json`, which this export never reads, so the single artifact SPEC J12 names as proof that "the data stays theirs" hands a producer a spreadsheet column no human or Airtable automation can interpret without separately dumping the plan definitions and hand-joining on generated ids. This is the same failure DEC-515 called the lock-in forbidden when the submissions export shipped identifiers without the substance, and the fix must not be the plan-results CSV (`src/routes/review/plans.ts:349-372`) — that surface is per-SUBMISSION aggregates, whereas this one is the per-REVIEWER record with the comment attached, and both are wanted. Decision: (a) the column set is derived from the UNION OF SCORE KEYS actually present across the exported evaluation rows, so no stored value can ever be dropped by construction — that property, not the label quality, is the anti-lock-in guarantee, and it is what the test asserts (every key of every scoresJson lands in exactly one column); (b) each key is named `${planName}: ${criterionLabel}`, resolved from a label map built per plan by merging `criteria_json` with every array in `round_criteria_json` (so a round-override criterion still gets its human label), falling back to the raw criterion id when no label resolves; (c) collisions reuse `nameCustomColumns`'s existing policy in this same file — append ` (${key})` when a name is empty, duplicated, or shadows a fixed column; (d) a `weightedScore` column is computed with `computeWeightedScore` from `src/domain/evaluation.ts` over that plan's rating criteria, rendered as the empty string when it throws (a plan with no rating criteria, or a legacy partial scorecard) — an export is a read of possibly-legacy history and must never be the thing that 500s, a deliberate and documented exception to the house fail-loudly default; (e) `scoresJson` is DELETED, not kept alongside, because the labelled columns supersede it and a duplicated blob invites a consumer to depend on the opaque form. `the former src/server/repo/exports.ts (now split across src/server/repo/exports/)` must NOT import from `src/routes/review/**` — it parses the two JSON columns directly.

## Amendment (wave 4): the evaluations CSV emits criterion columns in the plan's DECLARED order, not a scores map's key order

shapeEvaluationsExport derives its dynamic columns from Object.keys(r.scores) in row order, so the CSV's criterion columns follow whatever order a JSON object serialized and two plans interleave by first appearance — while /plans/:id/results renders the plan's declared criteria order. Same family as the Choice-distribution ruling: a map is not an order. Declared criteria first, in order; any score key not in the declared list (legacy or removed criteria) appended in stable first-seen order so the "no stored score value is ever dropped" property survives unchanged.
