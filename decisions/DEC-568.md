# DEC-568: Content approval is a bulk action: one event-scoped endpoint plus multi-select in the J8 worklist, so accepting N talks is N clicks away from publishing, not 2N

submission.content_status gates all five public surfaces via visibleSessionConditions() (src/server/repo/public/gates.ts:26, DEC-022/DEC-274) but is single-submission-only: acceptance never touches it (src/server/repo/submissions/status.ts:400-415 writes status + acceptedAt only), the bulk endpoint carries `status` alone (src/routes/api/submissions.ts:371-386), and both fresh and cloned rows default to 'pending' (src/server/repo/submissions/create.ts:89, :167). The only writer is POST /api/v1/submissions/:id/content-status (src/routes/files.ts:183-199), and the J8 worklist exposes it one row at a time (app/src/pages/content/SessionList.tsx:109-126). So after bulk-accepting 200 talks a producer faces 200 more individual clicks before the public sessions/speakers/agenda/gallery/schedule.ics show anything — a direct hit on SPEC §2.2 volume-first ('a feature that demos well with 10 rows and dies at 2,000 is not built'). It is invisible to every eval run and walkthrough only because scripts/seed.ts:652 writes content_status straight to D1. Note the gate itself stays: DEC-030's overview card and CNT-12 both depend on approval being a real, separate, human decision — the fix is throughput, not auto-approval, so acceptance still must NOT set content_status. Decided contract, binding on both implementing tasks so neither re-decides it: POST /api/v1/events/:eventId/submissions/content-status, requireOrganizer + csrfJson, body `{ ids: string[], contentStatus: 'pending'|'approved'|'changes_requested' }`; ids via parseBoundedIdArray(body.ids, 'ids') (DEC-182); contentStatus via isValidContentStatus -> ApiError('invalid', ..., { contentStatus: 'Invalid value' }); event ownership via getEventFilesScope + orgId compare, exactly as files.ts:216-221 does; repo fn `updateContentStatuses(db, eventId, ids, contentStatus): Promise<{ updated: number }>` in src/server/repo/files-content-status.ts, chunked SELECT first with a loud full-set guard (ApiError('invalid', 'One or more submission ids do not belong to this event', { ids: `unknown ids: ...` }), mirroring updateSubmissionStatuses at status.ts:337-357), then one chunked UPDATE per batch scoped `and(eq(eventId), inArray(id, chunk))`; empty ids -> `{ updated: 0 }` with zero statements; response `{ updated }`. The DEC-009 no-mailer-import invariant on both files still holds.
