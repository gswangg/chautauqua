# DEC-707: Reviewer progress speaks three states, and a reminder's label names the scope it actually sends -- from ONE predicate both the route and the SPA import

"3 of 8 · not done" collapses two different situations an organizer acts on differently: a reviewer who has started and a reviewer who has not. The mock's vocabulary is DONE / N TO GO / NOT STARTED, and its action reads "Remind the 4 not started" -- a label that is a lie unless the send targets exactly those four. DEC-704 already established that a bulk label states the scope it sends; this applies it to Review by moving the classification into src/domain/evaluation.ts (reviewerProgressState + selectRemindTargets) so the /plans/:id/remind route and the label that counts them are the same function. A hand-copied predicate in app/ and another in src/routes/ is exactly the drift the field guide warns about.

## Amendment (wave 61): a reviewer nudge is addressable and actionable, and targets the round it was labelled from

POST /plans/:id/remind (plans-progress.ts:222-241) sends `to: {email, name: email}` with the body "You have N submissions left to review in \"<plan>\"." -- no recipient name (the same handler's sibling GET /progress already resolves display names through repo.batchUserDisplayNames), no deadline, and, decisively, NO LINK. The one job of a laggard nudge is to put the reviewer back in their queue; a message with no URL makes the volunteer hunt for the product. This is DEC-707's rule ("a reminder's label names the scope it actually sends") extended from the label to the message. Second, smaller half: /progress honours `?round=` while /remind hardcodes `plan.currentRound`, so on a multi-round plan the count that labelled the button and the set the button reaches are resolved against different rounds -- latent today only because the SPA never passes the param. RULING: the nudge addresses the reviewer by resolved display name (falling back to email), links `${resolveBaseUrl(c)}/admin/review/plans/${plan.id}`, states the plan's close date via formatCalendarDate when the plan has one (a DEC-522 day label, never re-zoned), and resolves completion against the round named in the request (same parse as /progress), defaulting to currentRound. Also delete the dead `makeMailer` try/catch -- DEC-547's wave-43 amendment made makeMailer total; the honest-failure path is the per-recipient catch below it.

## Amendment (wave 3): the plan-progress envelope's sibling counts share ONE predicate — `completed` is a subset of `assigned`

GET /plans/:id/progress computes `assigned` from resolveAssignments over the plan-filtered submissions MINUS the reviewer's recusals (plans-progress.ts:76), but `completed` comes from countCompletedByReviewerForPlan — an unrestricted per-plan count that also includes evaluations on submissions the reviewer is no longer assigned, has recused from, or that the plan's filters no longer select. That is how the landing prints '37 of 34 evaluations in' (SBEK run-4 P2). A ratio whose numerator and denominator answer different questions is a lie about work done. Ruling: `completed` counts only evaluations whose submissionId is in that reviewer's own resolved assigned set for the round; `completed <= assigned` becomes an asserted invariant, and the same envelope gains `submissionsInScope` (the count DEC-745's wave-72 amendment needs) so the cap row reads one number, not a second opinion.

## Amendment (wave 74): a denominator is only honest if the queue it measures shares its predicate — `assigned` excludes cap-saturated submissions the reviewer has not rated

`GET /plans/:id/queue` drops from the actionable queue every submission that already holds `plan.maxEvaluations` submitted evaluations and that this reviewer has not rated (`src/routes/review/reviewer.ts:242`, via `needsMoreRatings`). `GET /plans/:id/progress` (`plans-progress.ts:136`) and `POST /plans/:id/remind` (`:294`) compute `assigned` with `assignedExcludingRecused` only — recusals are removed, cap-saturated rows are not. So for any plan with a cap, `completed < assigned` is permanent, `reviewerProgressState` can never return "done", and `selectRemindTargets(rows,'incomplete')` keeps emailing reviewers whose queue is empty and whose PUT would 409 (`reviewer.ts:524`). SPEC J4's "sorted fewest-ratings-first so coverage closes" is unreachable while the two disagree. RULING: the progress/remind denominator applies the SAME `needsMoreRatings` predicate the queue applies — an assigned submission is dropped from `assigned` iff its round-scoped submitted-evaluation count is >= `plan.maxEvaluations` AND this reviewer has not rated it (a submission the reviewer HAS rated always stays, preserving DEC-707's `completed <= assigned` invariant). Zero new queries: `listEvaluatedPairsForPlan` already carries `submittedEvaluationCondition()` (`review/evaluations.ts:348`), so per-submission counts folded from the pairs both routes already load are identical to `countEvaluationsBySubmission`'s. A reviewer whose entire scope is saturated lands on the existing vacuous-done branch (assigned 0 => "done"), which is correct: they owe nothing. `maxEvaluations` null leaves every number unchanged. Note the seed deliberately hides this class — `scripts/seed.ts:1359-1369` sets the cap above every seeded per-submission count precisely so `needsMoreRatings` "removes nothing from any reviewer's queue" — so the falsifying test must construct a saturated submission.

## Amendment (wave 79): a branch with no seed-reachable case is untested where it matters — the cap-saturation denominator gets a real fixture

`assignedExcludingSaturated` exists to make the reviewer-progress denominator honest when a submission has already collected its plan's maximum evaluations, but no seeded plan can reach its own cap: plan 1 caps at 3 and tops out at 2 by construction (`scripts/seed.ts:1359-1369` says so explicitly), plan 3 caps at 2 with ZERO evaluations (`:1732-1735`), plan 4 caps at 2 with 2 scored submissions and one reviewer (`:1795-1862`). So the branch is exercised only by a hand-built mock harness that agrees with itself, and neither the seed-driven integration suite nor a judge walking the product can ever see it. A guard whose only witness is its own mock is a contract with itself (the DEC-663 lesson, one subsystem over). Ruling: the seed carries at least one genuinely cap-saturated submission — plan 4's cap drops to 1, saturating the two submissions already scored there, and a second reviewer is scoped to the same plan/track so the saturation is observable in SOMEONE ELSE's denominator rather than being degenerate. The seed comments state the new fact plainly instead of the old "safe against needsMoreRatings" reassurance, and a seed-shaped test pins the denominator.
