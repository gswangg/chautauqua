# DEC-563: Room and track order is the producer's — assigned on create, totally ordered on every read, and honored by the public day grid and the auto-scheduler that both invent their own today

`room.position` and `track.position` exist (src/db/schema.ts:413 and the track table) and the seed populates them 0,1,2 — but `createRoom` (repo/events.ts:417-435) and `createTrack` (:272-290) NEVER set the column, so every room and every track a producer creates through J1 lands on the `.default(0)` and the whole column is dead for any event not built by the seed. Consequences run downhill: repo/agenda.ts:299 and :493 order rooms by `position` alone, so with all-zero positions the admin day grid's columns can swap between two refreshes, and `autoSchedule`'s room preference list (:493-494) — the order the greedy placer tries rooms in — is arbitrary, making the J9 auto-schedule action nondeterministic on identical input. repo/public/detail.ts:132 orders track chips by `position` alone for the same reason. Worse, the PUBLIC day grid never consults the producer's order at all: src/routes/public/agenda.tsx:18 builds its columns as `[...new Set(items.map((i) => i.roomId ?? 'tbd'))]` — first appearance in (day, startMin) order — so an attendee gets Main Hall as column 1 on Tuesday and column 3 on Wednesday, while the admin grid beside it reads room order from the event. Two surfaces render one fact and the public one is invented: the standing rule. And `autoSchedule`'s session ordering (src/domain/schedule.ts:222-227) breaks a (durationMin, track) tie by input array order, which is a DB return order — a greedy algorithm's input order IS its output. Decision: (a) createRoom and createTrack compute `position` inside the INSERT as `(SELECT COALESCE(MAX(position), -1) + 1 FROM <table> WHERE event_id = ?)` — atomic, no read-then-write, the exact idiom repo/participants.ts:81 already uses — so creation order becomes display order with no new endpoint and no migration. (b) Every room/track read ends in a unique tiebreak: agenda.ts:299 and :493 and public/detail.ts:132 gain `asc(<table>.id)`, matching repo/events.ts:404/259 which already do. (c) `PublicAgendaItem` carries `roomPosition: number | null`, and AgendaDayGrid orders its columns by (roomPosition asc, roomName asc, roomId asc) with the TBD column always last — the producer's order, identical on every day of the event. (d) autoSchedule's session sort ends in `submissionId asc`. The regression bar: create three tracks and three rooms through the API in a named order and read them back in that order after a reload; render the public grid twice from shuffled item arrays and get identical columns; run autoSchedule twice on a shuffled session array and get byte-identical placements.
