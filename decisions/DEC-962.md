# DEC-962: A batched read carries its scope in the WHERE, not in its caller's discipline

src/server/repo/portal/sessions.ts exposes getLatestDeliverable(db, submissionId) (:99) and listLatestDeliverables(db, submissionIds) (:122). Both select from `file` with a submissionId predicate and NOTHING else — no participant join, no contact predicate, no event.orgId. The entire ownership check lives in a doc comment: 'Scoped to the caller's own submission — the route resolves submissionId from the speaker's own PortalSession rows only, never a request param.' That is the multi-tenant boundary of the speaker portal written in prose, in a function whose plural form was introduced by a batching commit that asserted 'no IDOR widening' about itself. An assertion in a commit message is not a test, and a comment is not a predicate: the day any caller derives its id list from a wider query — a co-presenter list, an event roster, an admin reuse — the reader answers happily. DEC-312 already settled the shape for exactly this class ('the SQL WHERE clause is normative … pushed into the query itself rather than filtered in application code') and src/server/repo/tasks/crud.ts already has the idiom (acceptedSpeakerExistsForContact's correlated sql`exists (...)`). Rule: both readers take (db, contactId, orgId, …ids) and AND a correlated EXISTS over participant ⋈ submission ⋈ event asserting participant.contactId = contactId and event.orgId = orgId; a foreign id contributes no row, silently and by construction. Every other exported reader under src/server/repo/portal/ that accepts an id ARRAY is audited to the same standard in the same pass, and a cross-tenant test — speaker A asking for speaker B's submissionId — is what proves it, not a comment.

## Amendment (wave 47): the portal's content-bearing read doors carry contactId in the WHERE; the JS ownership test survives as a fail-loud invariant

This DEC already ruled this shape for `src/server/repo/portal/sessions.ts` ("a comment is not a predicate"), and `listDeliverableCandidates` (`src/server/repo/portal/tasks.ts:227-232`) is the landed counter-example. Two doors were never converted: `getPortalSubmissionDetail` (`src/server/repo/portal/data.ts:208-273`) selects title/description/schedule with `where(eq(submission.id, submissionId))` alone and checks `eventOrgId !== orgId` at `:248` and participation at `:273` in JS afterwards; `getResourceDownloadScope` (`src/server/repo/portal/resources.ts:117-152`) selects the resource on id alone and checks org/participation in JS at `:135-138`. Both take `submissionId`/`resourceId` straight off a request param. RULING: extend this DEC to every portal reader that accepts a SINGLE id, not just id arrays — the scope predicate (`event.orgId = orgId` AND a correlated `exists` over participant ⋈ submission for `contactId`, restricted to PORTAL_VISIBLE_INVITE_STATUSES) moves into the `.where(...)`, so a foreign id yields zero rows and content is never materialized. The existing JS checks are KEPT, not deleted, as fail-loud invariants (same null return) so a bug in the predicate surfaces rather than leaks — the same pattern the wave-43 preflight used for `mergeOnePair`.

## Amendment (wave 63): a repo write reachable from a speaker-authenticated route carries its own scope, and the population is read from the import graph

DEC-962 put scope in the WHERE for submission writes after `files-content-status.ts` was found mutating on a bare id, safe only because one caller checked first. The same shape is live on the portal — the surface whose callers are UNTRUSTED: `src/server/repo/portal/tasks.ts:316-330` updates `task_assignment` by assignmentId alone, correct today only because `assertOwnAssignment` ran upstairs. SPEC §6 requires object-level ownership on every fetch-by-id; a rule that depends on a caller's memory is not that rule. Ruled: every mutator reachable in one hop from `src/routes/portal/**` either names a scope column beyond its own primary key, or appears in a ledger whose reasons are STRUCTURAL (the WHERE key IS the caller's identity) — never a branch note, and the population is derived by walking the imports, never hand-listed (DEC-367/DEC-808).

## Amendment (wave 58): a WRITE carries its scope in the WHERE, exactly like the batched read

DEC-962 ruled this for reads and `src/server/repo/portal/submissions.ts:51-56` carries the re-scoping comment. Verified the write side drifted: `files-content-status.ts:39-44` mutates on `eq(schema.submission.id, submissionId)` alone while its bulk twin at :56-91 re-scopes on `eventId` in BOTH the guard SELECT and the UPDATE. It is safe today only because `src/routes/files.ts:297-299` checks ownership first — the second caller (`content-notes.ts:110`) inherits zero scoping, and this governs public content visibility. Ruling: the signature becomes `updateContentStatus(db, eventId, submissionId, contentStatus)` and the statement carries both predicates; both callers already hold the event id. Per the wave-57 population doctrine the enforcing scan derives its subjects as a PROPERTY — every exported function under `src/server/repo/**` whose body issues `db.update(schema.submission)` or `db.delete(schema.submission)` — and each must name `schema.submission.eventId` in that statement or sit in a NAMED exemption list whose entries carry STRUCTURAL reasons only (never a branch note). Negative control required.
