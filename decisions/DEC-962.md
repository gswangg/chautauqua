# DEC-962: A batched read carries its scope in the WHERE, not in its caller's discipline

src/server/repo/portal/sessions.ts exposes getLatestDeliverable(db, submissionId) (:99) and listLatestDeliverables(db, submissionIds) (:122). Both select from `file` with a submissionId predicate and NOTHING else — no participant join, no contact predicate, no event.orgId. The entire ownership check lives in a doc comment: 'Scoped to the caller's own submission — the route resolves submissionId from the speaker's own PortalSession rows only, never a request param.' That is the multi-tenant boundary of the speaker portal written in prose, in a function whose plural form was introduced by a batching commit that asserted 'no IDOR widening' about itself. An assertion in a commit message is not a test, and a comment is not a predicate: the day any caller derives its id list from a wider query — a co-presenter list, an event roster, an admin reuse — the reader answers happily. DEC-312 already settled the shape for exactly this class ('the SQL WHERE clause is normative … pushed into the query itself rather than filtered in application code') and src/server/repo/tasks/crud.ts already has the idiom (acceptedSpeakerExistsForContact's correlated sql`exists (...)`). Rule: both readers take (db, contactId, orgId, …ids) and AND a correlated EXISTS over participant ⋈ submission ⋈ event asserting participant.contactId = contactId and event.orgId = orgId; a foreign id contributes no row, silently and by construction. Every other exported reader under src/server/repo/portal/ that accepts an id ARRAY is audited to the same standard in the same pass, and a cross-tenant test — speaker A asking for speaker B's submissionId — is what proves it, not a comment.
