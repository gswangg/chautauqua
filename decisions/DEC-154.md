# DEC-154: Shell chrome: admin SPA gets a catch-all NotFound route; a Sign out control (POST /logout then location to /login) appears in the admin nav and in the portal SSR header

Two Section D findings with real UX cost and trivial risk: unknown /admin/* paths currently render the nav shell with an empty main (soft-404), and no sign-out control exists anywhere. POST /logout already exists in src/routes/auth.tsx and clears the session cookie — this is pure wiring. A visible 404 page also makes the DEC-144 render-sweep's negative space legible.

## Amendment (wave 53): an unknown /admin path is answered by the SERVER with a real 404, from a route manifest the SPA itself renders from

src/routes/root.tsx:79-88 serves the admin SPA shell for EVERY /admin/* path, so a bad admin URL is HTTP 200 and app/src/App.tsx:307's catch-all draws NotFoundPage inside the full header/nav/footer chrome — the frame is chromeless and the honest status is 404. The Worker cannot answer 404 without knowing the SPA's route table, and a hand-copied second list is the desync the field guide names. So: one pure `src/lib/admin-routes.ts` exports `ADMIN_ROUTE_PATTERNS` plus a `matchesAdminRoute` segment matcher; the Worker consults it; and App.tsx RENDERS its `<Route>` elements from that same tuple through a `Record<(typeof ADMIN_ROUTE_PATTERNS)[number], ReactNode>`, so a missing or extra element is a compile error. Parity is not use — the list must be the thing the router is built from, not a thing a test compares the router to. app/ already imports from src/lib (dates.ts, embed-formats.ts), so the boundary crossing is an established one.

## Amendment (wave 8): GET /logout is a real page, not a 404 — a guessable URL never dead-ends

src/routes/auth.tsx registers only POST /logout (:394); src/server/pubcache.ts:150 already treats /logout as a known no-cache path, and the SPA's signOut() posts correctly. A human or an agent who types or bookmarks /logout gets a 404 from a URL the product itself publishes in its own cache list — the re-measure filed exactly that. GET must not perform the logout (a bare GET side effect is a CSRF hole: <img src="/logout"> would sign a producer out), so the ruling is: anonymous GET /logout redirects to /login (nothing to end); a signed-in GET renders the existing auth-card notice chrome with a POST form carrying the double-submit token (DEC-181 unchanged) and a 'Stay signed in' link back to the caller's own home — /admin for organizer/reviewer, /portal for speaker, the same dest rule login already applies. No new CSS class, no new vocabulary: the irreversible-ish action is a page that names what it will do.

## Amendment (wave 14) — the SPA's auth boundary is honest in both directions: sign-out asserts nothing until res.ok, and a 401 from /me is the login door

app/src/App.tsx:132-138 navigates to /login without checking res.ok, so a rejected POST /logout leaves the chq_session cookie live while the UI asserts the user is signed out — a silent failure on exactly the path where failing loudly matters. The mirror defect is on the way in: app/src/lib/useMe.ts:36 swallows a 401 into me=null, after which RoleGate renders the shell with no identity and every page fetch 401s, with no visible way back — the same dead-end class as a guessable URL that 404s. Ruling: sign-out navigates only on res.ok and surfaces a loud failure otherwise (the cookie is still live, so claiming otherwise is a lie); a 401 from GET /me sends the browser to /login, which is the same door the Worker's /admin gate already uses for an anonymous request — one policy, two enforcement points, not a new policy.

## Amendment (wave 25)

**/logout has no screen; the login card owns the one status line**

Ruling 24 is a MUST-FIX: a route that destroys the session and then renders its own confirmation screen is a bug wearing a design question. POST /logout keeps its CSRF guard and session delete, then redirects 302 to /login?signed-out=1; GET /logout redirects 302 to /login and mutates nothing (a bookmarked GET must never sign anyone out, and there is no dedicated screen). The wave-8 LogoutConfirmPage is deleted. Both this and the password-reset flow need a muted one-line status on the sign-in card, so there is exactly ONE owner of that line — an exported `loginStatusLine(url)` helper in src/routes/auth.tsx keyed on the query string. Two flows inventing two banners is precisely the SECOND READER INHERITS NO MANNERS shape the field guide already records.

## Amendment (findings wave 7) — an in-SPA destination is a router navigation, never a literal <a href>; and a link's target must be a route that exists

DEC-154 owns the admin shell's chrome and its catch-all NotFound. Two defects share one root: the SPA writes literal same-origin anchors for destinations the router already owns. (1) app/src/pages/Agenda.tsx:395 links the "no rooms configured" empty state's only escape — "Add a room or track" — at `/settings#chq-settings-section-tracks`. The SPA route is `/admin/settings` (app/src/routeManifest.ts:108) and the settings drill-in vocabulary is `?section=<key>&edit=1` (app/src/pages/settings/SummarySection.tsx:59) with the tracks key `tracks-rooms` (TracksRoomsPanel.tsx:66), so both the path and the fragment are wrong: B7 rule 3 asks for "one action, and only a real one" and this one leaves the page. (2) Four `/admin/*` anchors in ComposeWizard and two in the contacts modals force a full document reload — re-downloading the bundle and re-fetching every view — against SPEC §7's "navigation to any admin screen: interactive < 300 ms". RULING: every destination the SPA router serves is reached with `Link`/`useNavigate`; a literal `href` is reserved for genuinely server-rendered targets (`/api/v1/`, `/files/`, `/headshots/`, `/e/`, `/submit/`, `/portal`, `/docs/api`, `/account/password`, `/login`, `/logout`). A scan test pins both halves so the class cannot come back — a link target nobody navigated is a route nobody checked.
