# DEC-994: Session minting is ONE helper that revokes first: login, claim and password-change all rotate, and no path inserts an auth_session by hand

SPEC.md §6 line 308 states "session rotation on login" as a hard security property, and the login handler (src/routes/auth.tsx:356-368) does not implement it: it mints a fresh 30-day row and sets the cookie with no delete against auth_session, so a stolen token survives the victim re-authenticating — the one recovery action a user has. src/routes/account.tsx:182 already purges every session on password change, which is the correct shape, but it lives as one hand-written delete beside one hand-written insert; a second hand-written pair (login) drifted, and the claim/password-set path is a third. Three call sites spelling one invariant is the DEC-402/DEC-406 incomplete-coverage failure mode. Therefore ONE exported helper — issueSession(db, userId, now) -> plaintext token — that deletes every existing auth_session row for that user inside the same call before inserting the new one, and every mint goes through it. Revoking ALL of the user's sessions (not merely the cookie presented on this request) is the deliberate reading: the product has no device manager and no other revocation surface, so re-authenticating is the user's only takeover recovery, and it must actually work. The 30-day expiry, the cookie builder and the secure-flag inference are unchanged — only who owns the delete+insert pair moves.
