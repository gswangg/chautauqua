# DEC-994: Session minting is ONE helper that revokes first: login, claim and password-change all rotate, and no path inserts an auth_session by hand

SPEC.md §6 line 308 states "session rotation on login" as a hard security property, and the login handler (src/routes/auth.tsx:356-368) does not implement it: it mints a fresh 30-day row and sets the cookie with no delete against auth_session, so a stolen token survives the victim re-authenticating — the one recovery action a user has. src/routes/account.tsx:182 already purges every session on password change, which is the correct shape, but it lives as one hand-written delete beside one hand-written insert; a second hand-written pair (login) drifted, and the claim/password-set path is a third. Three call sites spelling one invariant is the DEC-402/DEC-406 incomplete-coverage failure mode. Therefore ONE exported helper — issueSession(db, userId, now) -> plaintext token — that deletes every existing auth_session row for that user inside the same call before inserting the new one, and every mint goes through it. Revoking ALL of the user's sessions (not merely the cookie presented on this request) is the deliberate reading: the product has no device manager and no other revocation surface, so re-authenticating is the user's only takeover recovery, and it must actually work. The 30-day expiry, the cookie builder and the secure-flag inference are unchanged — only who owns the delete+insert pair moves.


## Amendment (wave 6): login rotates THIS session; only credential-setting paths revoke the user's whole fleet

DEC-994 read SPEC §6's "session rotation on login" as global eviction: issueSession (src/server/auth-session.ts:16) deletes every auth_session row for the user before minting, and it is the sole minting path. The standard meaning of rotation-on-login is session-fixation defence — the identifier presented across the authentication boundary must not survive it — not "destroy the user's other devices". The chosen reading costs real behaviour: a producer signing in on a phone silently 401s their laptop, and the four SHARED seeded demo personas mean the eval agent and a human judge log each other out mid-run, which reads as a product failure and burns turn budget. The takeover-recovery argument survives without global eviction because password change (src/routes/account.tsx) and the /claim/:token password-set path both still revoke everything, and those are exactly the credential-setting actions a compromised user takes. Ruling: src/server/auth-session.ts exports TWO minters and stays the only file that inserts an auth_session row — issueSession(db, userId, now, presentedTokenHash) deletes the presented row (if any) plus that user's EXPIRED rows and then inserts (login), and issueSessionRevokingAll(db, userId, now) keeps the current delete-everything semantics (claim/password-set, password change). The source-grep scan in test/session-rotation.test.ts stays; its login case flips from "the first cookie dies" to "a second login from a different device leaves the first cookie working, and presenting the same cookie rotates it".

## Amendment (wave 22): the presented-token session delete carries the owner predicate — a tokenHash from a cookie is client input, never sufficient alone

The wave-6 amendment ruled that login rotates THIS session and leaves the user's other sessions alone, and src/server/auth-session.ts:34-39 states that contract verbatim ("Leaves other live sessions for this user untouched"). The implementation does not honour it: line 51 deletes `where(eq(authSession.tokenHash, presentedTokenHash))` with no userId predicate, while its sibling on line 48 IS user-scoped. presentedTokenHash is derived straight from the request's chq_session cookie (src/routes/auth.tsx:384-387), so a login as user A that carries user B's cookie silently revokes B's live session — precisely the cross-user eviction the wave-6 amendment removed, reintroduced through the back door. Ruling: every delete against auth_session states WHOSE row it is deleting — `and(eq(userId), eq(tokenHash))` — and the invariant is enforced by an enumeration over every `delete(schema.authSession)` statement in src/**, with exactly one ledgered exception (POST /logout, which by definition ends the session presented on the request), a stale-entry check, and a match-count tripwire. Ownership predicates belong in the statement, not in the comment above it.
