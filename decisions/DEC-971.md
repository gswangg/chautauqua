# DEC-971: Two chains of one kind are two deliverables, and the chip you pick is the chain you see

The design is explicit: 'A submission can carry several deliverables … each is a separate version chain with its own comment thread', with a chip per deliverable and the caption 'Versions and notes below are for the selected deliverable' (docs/design/README.md:237). app/src/pages/content/DeliverableDetail.tsx keys everything on KIND instead: the chip prints grouped[kind].length (:337, :347) — the flat count of every file of that kind — the version list receives the whole flat group, the comment thread anchors activeLatest (the newest chain's head) and UploadZone chains onto it. app/src/pages/content/version-chain.ts:20-26 warns about this in its own doc comment ('Two files sharing a kind are NOT necessarily versions of the same document … callers that compute a v2/v3 label must number within a file's own chain'), and orderVersionChains already returns exactly the sub-arrays needed. So a task upload and an organizer upload of the same kind read as 'Presentation · 2 versions' when they are two v1 documents (the gate's SES-005 report), the second chain's thread is unreachable, and an upload silently re-versions whichever chain happens to be newest. Rule: the chip strip is built from CHAINS, not kinds — one chip per independent chain, labelled '<Kind> · N versions' (countOf) and disambiguated with that chain's latest filename only when its kind holds more than one chain; selection is the chain's head file id; the version list, the comment thread and the upload target are all that one chain, so the caption is true as written. VersionList's props and its per-chain numbering (DEC-901/DEC-965) are untouched.
