# DEC-754: The speaker roster and the set a task expands over are ONE predicate: the onboarding grid's rows ARE the event's accepted speakers

Verified on main: src/server/repo/tasks/grid.ts:71-88 defines a grid row as "a contact with at least one task_assignment for a task in this event", while createTask expands over listAcceptedContactIds (tasks/crud.ts:90) and the headshots tab uses acceptedSpeakerConditions (files-library.ts:457). Those are three different sets sharing one screen. That divergence is exactly the SPK grader's P2: a roster row that shows a speaker who then does NOT receive the new task, because he carries an old assignment but is no longer an active participant on an accepted submission. A screen that lists someone an action silently skips is lying about who owes what — the only question J6's dashboard exists to answer. So the grid's base row set becomes the accepted-speaker predicate (expressed as a correlated EXISTS over participant+submission so the contact query stays one row per contact), the filters stay an additional EXISTS on top, counts.speakers becomes the size of that same set, and an accepted speaker with zero assignments now renders with empty cells rather than vanishing. The predicate lives once, beside acceptedSpeakerConditions, so it cannot drift again; the test asserts set equality with listAcceptedContactIds by enumeration, never by sampling a row.

## Amendment (wave 38): the set a task may be ASSIGNED to is the roster set, not the org directory

DEC-754 made the roster and the expansion target one predicate; DEC-829 then widened LISTING (rosterParticipantExistsForContact) above EXPANSION/CHASING (acceptedSpeakerConditions). POST /api/v1/tasks/:id/assign never joined either: src/routes/tasks.ts:421 validates only findContactsForOrg, so assigning any other org contact returns 200 plus a refreshed grid the assignee is absent from (grid.ts's base row predicate), and that row is never reminded by cron or by 'remind everyone outstanding' (reminders.ts's chaseableContactExists). A write guard that does not match the read predicate mints rows nothing lists and nothing chases — a silent J6 'falls through the cracks'. The guard is the ROSTER predicate, not the chase predicate, so a 'declined' participant stays assignable and visible per DEC-829's listing/expansion split; the refusal is a 400 that names the offending ids AND the forward path, because a dead-end error is the failure class this mandate already files twice.
