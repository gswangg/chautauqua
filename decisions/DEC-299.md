# DEC-299: A NULL participant attribution snapshot was never frozen: any write of contact.title/company backfills participant rows whose snapshot column IS NULL, and the CFP form gains no title/company fields

DEC-258 froze speaker attribution into participant.title_at_time/org_at_time and forbade a read-time fallback, which is right for the case it addressed (a speaker changes jobs; last year's program must not be rewritten). But the public CFP path creates a brand-new contact with no title or company (src/routes/public/submit.tsx:533-534 passes existingContact?.title ?? null), and no write path ever revisits those columns — so every real public submitter renders permanently blank on the J10 speakers list, the gallery and the speakers CSV, even after they complete their portal profile. The seeded fixtures set the values, which is why no test or walkthrough caught it. The defect is at capture, not at read: a NULL snapshot never froze anything, it recorded that nothing was known. So any write that sets contact.title/company (the portal profile update in src/server/repo/profile.ts, J7's 'one record, two views'; and the organizer's CRM contact PATCH) backfills that contact's participant rows whose corresponding snapshot column IS NULL, and never touches a non-null snapshot. DEC-258's no-fallback read rule in src/server/repo/public.ts stands unchanged. Rejected alternative: adding locked Job title / Company fields to the default CFP form — it would change the form contract, the locked-field id machinery, the seed and a dozen tests this late for a value the portal already collects and the onboarding task set already chases.
