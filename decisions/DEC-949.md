# DEC-949: One live claim grant per contact and event, and the organizer's audit view never renders it

createClaimToken (src/auth/claim.ts:55) mints a fresh 30-day {contactId,eventId} grant on every compose send, every bulk email and every portal invite, with no index and no revocation, so a contact who has been emailed five times has five independent live 'set this speaker's password' links, and the resulting `/claim/<token>` URL is written verbatim into email_log.body_text (src/server/context.ts:23) and handed back indefinitely by the organizer-readable send-detail route (src/routes/comms.ts:725-735). A credential in an audit log is not an audit trail. Two mechanisms, one posture. (1) A grant is SINGLE-ACTIVE: createClaimToken writes an index key `claim-for:<contactId>:<eventId>` → tokenHash and deletes the previously indexed grant before storing the new one, so the newest email is the one that works and every older link is dead; consumeClaimToken deletes the index alongside the record when the index still points at the hash being consumed. Only the hash is ever stored — the plaintext still exists nowhere but the email, so this adds revocation without weakening DEC-014. (2) The organizer-facing disclosure REDACTS: a pure `redactClaimUrls(text: string): string` in src/auth/claim.ts rewrites `/claim/<base64url>` to `/claim/<redacted>` and is applied to bodyText/bodyHtml on the way out of the send-detail route (and of the history list route if it returns bodies). /dev/mailbox is untouched: it is mounted only when DEV_MODE="1" and therefore does not exist in production, which is what keeps the walkthrough gates able to click a claim link. Finally the two byte-identical copies of resolvePortalLink — src/server/repo/portal-link.ts (the one DEC-559 declared canonical) and the private copy at src/routes/api/contacts/bulk-email.ts:32 — collapse to the shared one: two paths for one row is one too many, and a revocation rule that only one of them honours is worse than none.

## Amendment (wave 38): a send response reports counts and failures — the rendered bodies never ride back

DEC-949 redacts /claim/<token> on the organizer's audit READ (comms.ts:742-746) but both send WRITES return `items: result.rendered` (src/routes/comms.ts:613, src/routes/api/contacts/bulk-email.ts:168), and those renders were produced with mintClaimTokens=true (comms.ts:543, bulk-email.ts:132) — so the freshly minted one-time credential for every recipient comes back on the wire, unredacted, in the very response that minted it. The predicate was applied half. The SPA never reads the field: app/src/lib/sendResult.ts's SendResult is {sent, failed, skipped, remaining} and ComposeWizard renders describeSendResult(). House rule forbids compatibility shims, so the ruling is deletion, not redaction: a send response is {sent, failed[]} and nothing else. Preview is untouched — DEC-397 already makes preview mint PREVIEW_CLAIM_TOKEN, so preview may keep returning bodies.
