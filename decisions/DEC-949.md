# DEC-949: One live claim grant per contact and event, and the organizer's audit view never renders it

createClaimToken (src/auth/claim.ts:55) mints a fresh 30-day {contactId,eventId} grant on every compose send, every bulk email and every portal invite, with no index and no revocation, so a contact who has been emailed five times has five independent live 'set this speaker's password' links, and the resulting `/claim/<token>` URL is written verbatim into email_log.body_text (src/server/context.ts:23) and handed back indefinitely by the organizer-readable send-detail route (src/routes/comms/email-log.ts). A credential in an audit log is not an audit trail. Two mechanisms, one posture. (1) A grant is SINGLE-ACTIVE: createClaimToken writes an index key `claim-for:<contactId>:<eventId>` → tokenHash and deletes the previously indexed grant before storing the new one, so the newest email is the one that works and every older link is dead; consumeClaimToken deletes the index alongside the record when the index still points at the hash being consumed. Only the hash is ever stored — the plaintext still exists nowhere but the email, so this adds revocation without weakening DEC-014. (2) The organizer-facing disclosure REDACTS: a pure `redactClaimUrls(text: string): string` in src/auth/claim.ts rewrites `/claim/<base64url>` to `/claim/<redacted>` and is applied to bodyText/bodyHtml on the way out of the send-detail route (and of the history list route if it returns bodies). /dev/mailbox is untouched: it is mounted only when DEV_MODE="1" and therefore does not exist in production, which is what keeps the walkthrough gates able to click a claim link. Finally the two byte-identical copies of resolvePortalLink — src/server/repo/portal-link.ts (the one DEC-559 declared canonical) and the private copy at src/routes/api/contacts/bulk-email.ts:32 — collapse to the shared one: two paths for one row is one too many, and a revocation rule that only one of them honours is worse than none.

## Amendment (wave 38): a send response reports counts and failures — the rendered bodies never ride back

DEC-949 redacts /claim/<token> on the organizer's audit READ (comms.ts:742-746) but both send WRITES return `items: result.rendered` (src/routes/comms/send.ts, src/routes/api/contacts/bulk-email.ts:168), and those renders were produced with mintClaimTokens=true (comms.ts:543, bulk-email.ts:132) — so the freshly minted one-time credential for every recipient comes back on the wire, unredacted, in the very response that minted it. The predicate was applied half. The SPA never reads the field: app/src/lib/sendResult.ts's SendResult is {sent, failed, skipped, remaining} and ComposeWizard renders describeSendResult(). House rule forbids compatibility shims, so the ruling is deletion, not redaction: a send response is {sent, failed[]} and nothing else. Preview is untouched — DEC-397 already makes preview mint PREVIEW_CLAIM_TOKEN, so preview may keep returning bodies.

## Amendment (wave 18): a mint SUPERSEDES, it does not instantly revoke — the superseded grant keeps a bounded grace window

createClaimToken (src/auth/claim.ts:70-82) deletes the prior grant's record key BEFORE the new token is minted, and every batch sender mints through resolvePortalLinks(..., mintClaimTokens=true) BEFORE a best-effort per-recipient send loop whose catch reports {sent, failed} with a 200 (src/routes/content-notes.ts:124-160, src/routes/comms/send.ts, src/server/repo/portal-link.ts:69-82 applyMintedPortalLinks, src/server/repo/tasks/reminders.ts:394/584). So a send that fails permanently revokes that speaker's only working portal link and reports it as one line in a 200 body. Only hashes are stored, so nothing can restore it. The house rule is that minting is IO and a boundary fails per RECIPIENT, not per request; the missing half is that a mint is not a delivery. RULING: createClaimToken no longer deletes the superseded record — it REWRITES it with SUPERSEDED_GRACE_SECONDS (48h) while the index key moves to the new hash. The newest link is canonical; the previous link keeps working for 48 hours instead of 30 days (DEC-949's real target was five month-long live credentials, not the 48h overlap), so a failed send leaves the speaker able to get in and the organizer time to see the `failed` row and retry. Safe against double-account creation: the claim POST already refuses when a user exists for the contact and redirects to /login (src/routes/auth.tsx:499-506).


## Amendment (wave 34): the audit-view redactor is a SET of credential URL shapes, not one /claim/ regex

DEC-949 closed claim-link disclosure in the organizer-readable send detail with a single `/claim/<token>` regex. A second credential path shipped since (POST /forgot logs `${origin}/reset/<token>` into email_log through the ordinary mailer, and the reset token is a one-hour single-use password equivalent), and it is disclosed verbatim through Comms -> "Show what was sent" to any peer organizer in the org. The redaction contract is therefore restated as a SET: one module, src/auth/credential-urls.ts, owns CREDENTIAL_URL_SEGMENTS = ["claim", "reset"] and redactCredentialUrls(text); the claim-only helper is deleted outright (no shim, no re-export). Read-time (not write-time) redaction still stands: /dev/mailbox is DEV_MODE-only and the walkthrough and the reset route tests both pull the live link out of the stored body. The set is bound to the tree by a scan over every file that mints a token, so a third credential path cannot ship without teaching the redactor about it.

## Amendment (wave 43): the set of password_hash writers is DERIVED, not a hand-listed trio — the organizer re-issue route joins the revoke family

DEC-949's own docstring (src/auth/password-reset.ts:145-166) rules that "recovering that credential by ANY other route settles the claim and the outstanding link becomes pure attack surface", then enumerates by hand exactly the three paths that existed at wave 27: POST /reset/:token (via consumeResetToken), POST /account/password, POST /claim/:token. DEC-215's organizer re-issue — POST /api/v1/users/:id/reset-password (src/routes/api/users.ts:124-138) — writes a fresh password hash and deletes the target's sessions but never calls revokeResetTokenForUser, and test/password-reset-revocation.test.ts covers only the two wave-27 call sites. Concretely: a user asks for a reset link, an organizer re-issues their password out of band, and the 1-hour takeover link the user (or whoever read that inbox) still holds stays live and can set a new password AND revoke every session. RULING: every site in src/** that writes user.password_hash must revoke the user's outstanding reset grant, ordered BEFORE the hash write wherever the userId is already known (so a failed write never leaves a live link), and the family is bound by a source scan whose population is re-derived at test time with a closed reason-bearing ledger and a negative control — not by a comment listing three routes. Field-guide shape: A FAMILY ENUMERATED BY HAND AT WAVE N IS BLIND TO THE SIBLING ADDED AT WAVE N+1.

## Amendment (wave 27): a password-reset token REVOKES its predecessor; a claim token supersedes it

claim.ts deliberately re-puts a superseded grant under a 48h grace (DEC-949) because a batch send that fails after minting must not strand a speaker. A reset token has the opposite premise: the user asserted the credential is lost, and the request is self-service and instantly repeatable, so there is no failed-batch hazard to hedge against and a live older link is pure attack surface. Therefore: 256-bit token, stored ONLY as sha256 under KV key `pwreset:<hash>` with a 1h expirationTtl, plus an index key `pwreset:user:<userId>` -> hash so only the newest token per user is live; minting HARD-DELETES the prior hash key; consuming deletes both keys (single use); a successful password change through any path (/reset/:token, /account/password, /claim/:token) revokes the user's outstanding reset token. Plaintext exists nowhere but the email. Same KV-and-Web-Crypto shape as claim.ts, so no schema change and no migration.

## Amendment (wave 29): a password change REVOKES the outstanding reset grant before it writes, and a missing KV binding is loud — the wave-27 amendment's other two call sites get wired

DEC-949's wave-27 amendment rules that "a successful password change through any path (/reset/:token, /account/password, /claim/:token) revokes the user's outstanding reset token". Only /reset/:token honours it: consumeResetToken deletes both keys. src/auth/password-reset.ts:141-158 exports revokeResetTokenForUser and its own docstring records that wiring /account/password and /claim/:token "is outstanding work" — a decision with no code is a lie, and the residue is a live one-hour account-takeover link that survives the very credential recovery it was minted for. Ruling: both paths call revokeResetTokenForUser, and the ORDER is decided here so two implementers cannot answer it differently. /account/password knows the userId before it writes, so it revokes FIRST, before the password update: if the update then fails, the worst case is a legitimate outstanding link killed early (self-service, instantly re-requestable), whereas write-then-revoke leaves a live takeover link when the revoke throws — security beats the mild UX cost. /claim/:token only learns the userId once the user row is written, so it revokes immediately after that write, in the same handler, before the session is issued. Neither call is best-effort: a KV error PROPAGATES (fail loudly, SPEC §2.6). The KV binding is the same one /forgot already resolves; a handler that cannot reach it is a loud error, never a silently skipped revocation.
