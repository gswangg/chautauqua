# DEC-736: Anonymised review hides the SPEAKER from the REVIEWER; the organiser is always told who reviewed (supersedes DEC-622's null-iff-anonymized rule)

docs/sessionboard-reference/00-how-sessionboard-works.md §5.7 is explicit: "anonymized review actually hides speaker identity from evaluators", and SPEC J4 makes results producer-only. DEC-622 read `plan.anonymized` as a reviewer-identity switch and made src/domain/review-identity.ts return null whenever the plan is anonymised, so an organiser reading a submission detail sees "Anonymous reviewer" for the same person that Progress, Assignment and the reminder dialog name in full — one fact, two answers, and the organiser cannot tell who to chase. Blind review is one-directional: `anonymizeForReviewer` strips speakers/speakerAnswers from the REVIEWER's payload, and that stays. resolveReviewerIdentity therefore loses its anonymized branch and becomes "First Last, else email"; the evaluations export always carries the reviewer's email; the DEC-622 agreement test flips (both surfaces AGREE by naming). ANONYMIZED_REVIEWER_CELL and the "(anonymized)" literal disappear rather than lingering as a shim — no reviewer-facing surface ever lists other reviewers.

## Amendment (wave 79): one resolver means one INPUT — the evaluations export feeds resolveReviewerIdentity the contact row, and the column is named `reviewer`

`src/domain/review-identity.ts:1-6` says in its own header it exists "so the evaluations screen and the evaluations export can never disagree about who a reviewer's identity is shown as." They disagree: the screen (`src/server/repo/review/evaluations.ts:400-429`) leftJoins contact and passes {firstName,lastName,email}, so it renders "First Last"; the export (`src/server/repo/exports/evaluations.ts:175,227`) joins only `user` and passes {email}, so it always renders the address. A shared resolver fed different inputs is half a contract — the same shape wave 76 prosecuted on social_links_json. Ruling: the export joins contact the same way the screen does and passes the same row. Consequently the fixed column MUST be renamed from `reviewerEmail` to `reviewer`: a column named for an address that sometimes holds a name is a worse lie than the one being fixed, and the resolver's documented fallback to email keeps the renamed column honest in both cases. Header-pinning tests and any prose in decisions/DEC-027.md that names the old column are updated with the rename, not around it.
