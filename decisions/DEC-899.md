# DEC-899: A same-room pile-up is ONE card at any size — the pair case was never the rule, only the case we implemented

app/src/pages/agenda/DayGrid.tsx:48-52 already groups placements into maximal connected overlap clusters with union-find, then throws that generality away: only a cluster of exactly two merges into DEC-742's inverted clash card (:122-123), and three or more fall back to side-by-side lanes (:144-150, :322-341) — three truncated columns at 1/3 width with the same caption repeated three times, which is the frame's complaint. A cluster is the unit; two was never the rule. Rule: any same-room cluster of size >= 2 renders ONE inverted clash card naming every session in it, over ONE caption from the existing conflictKindLabel('room_overlap', n) (wording 'ROOM DOUBLE-BOOKED'), and the lane path serves only genuinely non-overlapping neighbours. The render test asserting three separate cards for a 3-way overlap is asserting the defect and is rewritten — where a test contradicts the design authority, the test is wrong. Legibility is part of the merge: the card's text must sit above the grid's own hour rules (they currently strike through it while a placement is armed), the armed ring must clear 3:1 against the quieted card, and an armed cell must answer the pointer ('Place here · N MIN FREE' on hover), because an affordance that only announces itself to the keyboard is half-built.

## Amendment (wave 60): one header line, one denominator — the agenda summary's three numbers come from one source

Verified at app/src/pages/Agenda.tsx:303-305, the summary line concatenates `agenda.summary.unplaced` (a SERVER count), `agenda.summary.conflicts` (server) and `placedPercent(agenda)` (:67-71, re-derived CLIENT-side as placed.length / (placed.length + unscheduled.length)). Two of the three numbers come from the server's summary and the third is recomputed from arrays whose scoping need not match the summary's — which is precisely how a judge saw 84% and then 79% on the same underlying counts. DEC-899 already rules that the summary is derived from the same population it describes. RULING: every number in that header line is read from `agenda.summary`; the client derives none of them, and the server supplies the percentage's numerator and denominator explicitly if it does not already. The conflict badge is likewise recomputed from the payload the last mutation returned, so a resolved clash cannot leave a stale badge behind.
