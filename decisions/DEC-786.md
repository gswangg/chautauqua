# DEC-786: Reviewer workload is distributed by a pure, deterministic round-robin behind a preview

ABS-06 asks for auto-distribution across reviewers OR a true per-reviewer cap; VERIFIED there is no distribute path anywhere (src/routes/review/plans.ts offers only POST /plans/:id/reviewers for a single user+track or user+submission), and the only cap in the tree is per-SUBMISSION (reviewsPerSubmission). Decision: a pure `distributeAssignments` in src/domain/review-distribute.ts computes the NEW (userId, submissionId) pairs — walk the plan's submissions in their existing deterministic order, and for each one fill up to reviewsPerSubmission distinct reviewers, always choosing the eligible reviewer with the fewest assignments so far (tiebreak userId asc), skipping anyone recused (DEC-271) or already assigned. No randomness, no clock: the same inputs give the same plan twice. It ships behind the established preview/confirm shape (DEC-572): a GET preview that writes nothing, then a POST that applies exactly what the preview showed.

## Amendment (wave 52): distribution reads "who reviews what" through the SAME resolver every other reader uses — a track scope is eligibility, not decoration

src/routes/review/plans-distribute.ts:53-55 builds `existing` from only those plan_reviewer rows with submissionId !== null, and hands distributeAssignments a flat pool of userIds. Every other reader of that table resolves through src/domain/evaluation.ts's resolveAssignments, where an all-null row means EVERY submission and a trackId row means every submission in that track — plans-progress's reminder denominators, the reviewer queue, and isSubmissionInReviewerScope (the authz gate on the scorecard PUT) all read it that way. Two consequences, both live: (a) coverage is undercounted — a submission already covered by two track-scoped reviewers reads as covered 0, so the run proposes duplicate explicit rows on top of scope-implied ones, and the confirm dialog's `before` shows 0 for a reviewer who in fact carries the whole plan, which also makes the per-run cap a no-op for exactly the busiest reviewers; (b) eligibility is ignored — the distributor can hand a track-scoped reviewer a talk outside their tracks, and because isSubmissionInReviewerScope honours the explicit row it just wrote, that WIDENS the reviewer's scope, while the same dialog's closed vocabulary ('unchanged · wrong track') asserts the opposite. Rule: coverage per submission and load per reviewer are computed from resolveAssignments' resolution, not from explicit rows; a reviewer is eligible for a submission only when an all-null row makes them broad, or one of their trackId rows matches one of the submission's tracks (a reviewer with neither shape stays broad, matching the dialog's existing "All submissions" reading); and because eligibility now depends on trackIds, the APPLY path must load them too — plans-distribute.ts:49 currently passes withTrackIds:false on apply and true on preview, which after this change would resolve two different pair sets and void DEC-840's byte-identical preview/apply promise.
