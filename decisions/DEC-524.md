# DEC-524: `app/src/lib/dates.ts` is the ONE home for date-input <-> epoch conversion in the SPA

DEC-146 wrote the rule into the file itself ('Pages must never call new Date(x).toISOString()/toLocale* directly on a nullable/unvalidated value -- go through these helpers'), and two pages ignore it with private copies. the formerly-separate `app/src/pages/forms/FormSettings.tsx:18-26` (since consolidated into the forms/settings surfaces) defined `toDateInputValue`/`fromDateInputValue` that are line-for-line `msToDateInput`/`dateInputToMs`; `app/src/pages/speakers/TaskModal.tsx:75` inlines `new Date(dueDate).getTime()`, which -- unlike `dateInputToMs` -- yields NaN instead of throwing on an unparseable value, so a bad date silently posts NaN as a task due date rather than surfacing a field error. Three implementations, one of which already behaves differently, on the exact values DEC-522 has just made semantically load-bearing. Fourth instance of the DEC-503/511/513/518 shape and the cheapest one to close. Decision: both pages import from `app/src/lib/dates.ts` and their private copies are deleted (no re-export shim), and a re-runnable source-scan test globs `app/src/**/*.tsx` and fails, naming the file, on any date-input conversion performed outside that module -- an enumeration, not a spot check.
