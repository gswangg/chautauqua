# DEC-026: CRM API contract: org-level contacts, CSV import mapping, merge repoints FKs, segments as stored rules, capped bulk email

J11 is one API task and one SPA task in parallel, so the wire contract is fixed here, consuming the landed pure core src/domain/contacts.ts (findDuplicateGroups, planMerge, SegmentRule/matchesSegment, mapImportRow). All endpoints organizer-only (requireOrganizer + csrfJson on mutations), org-scoped via auth.orgId. GET /api/v1/contacts — DEC-013 pagination, q (case-insensitive LIKE over first/last name, email, company), segmentId (server-side filter via matchesSegment), sort name|recent. POST /api/v1/contacts { firstName,lastName,email,... }. GET /api/v1/contacts/:id -> contact + history { submissions: [{ id, ref, title, eventName, status }], emails: last 20 email_log rows, events: distinct event names }. PATCH /api/v1/contacts/:id (core fields, notes, customFields object -> custom_fields_json). POST /api/v1/contacts/import { csvText, mapping: { column -> field } } using parseCsv + mapImportRow; upsert matched by case-insensitive email; returns { created, updated, skipped: [{ line, reason }] }. GET /api/v1/contacts/duplicates -> groups from findDuplicateGroups with display fields. POST /api/v1/contacts/merge { keepId, mergeId } applies planMerge to the kept row, repoints participant, task_assignment, email_log, user.contact_id from mergeId to keepId, then deletes the merged row — losing history on merge is a data bug. Segments: GET/POST /api/v1/segments, PATCH/DELETE /api/v1/segments/:id with { name, rules: SegmentRule[] } stored in segment.rules_json (DEC-025). GET /api/v1/contacts/stats -> { total, returningSpeakers (contacts with participant rows in >1 event), topCompanies: [{ company, count }] top 5 }. Bulk email: POST /api/v1/contacts/bulk-email { contactIds, eventId, subject, bodyText } with DEC-019 semantics — render every recipient first, any failure rejects the whole batch, >100 recipients rejects 'invalid', one email_log row per send via makeMailer; merge whitelist limited to {speaker_name}, {event_name}, {portal_link}; submission-scoped fields ({talk_title}, {feedback}) in the body reject 'invalid'. This endpoint is separate from w3-c's compose files to avoid touching an in-flight branch.

## Amendment (wave 56): the contact drawer's history is bounded on BOTH sides, and the events list is its own query

getContactHistory (src/server/repo/contacts/history.ts:37-85) caps emails at 20 but reads EVERY submission the contact participates in across every event with no LIMIT, and GET /contacts/:id (src/routes/api/contacts/crud.ts:207) runs it on every drawer open. The asymmetry is an oversight, not a decision. The fix must not shrink a second reader: `events` is currently derived from that same submission array (history.ts:82), so capping the submissions silently truncates the ACROSS YOUR EVENTS list too -- the distinct-events list becomes its own DISTINCT query, and the drawer states the shortfall (`Showing N of M`) rather than presenting a truncated list as complete.

## Amendment (wave 52)

The contact drawer's email history states its bound, exactly as its submissions sibling does.

src/server/repo/contacts/history.ts caps submissions at MAX_CONTACT_HISTORY_SUBMISSIONS and carries `submissionsTotal` from a separate count(*) over the full join, and ContactDrawer.tsx:574-577 renders 'Showing 20 of 47 submissions'. Its sibling three statements below caps emails at .limit(20) (history.ts:98) and the ContactHistory interface has NO emailsTotal, so the drawer shows the last 20 sends of a contact with 300 and says nothing — the reader believes that is the whole history. Same file, same shape, one sibling carries the fact and the other does not (the w46 'A PREDICATE FOUR SIBLINGS CARRY AND THE FIFTH DOESN'T' shape, in count form), on a J11 surface an organiser uses to decide whether someone has been over-mailed. RULING: `emailsTotal` joins `submissionsTotal` on ContactHistory, computed the same way (a count(*) over the same predicate, never the row array's length), and the drawer renders the same 'Showing N of M' line for emails whenever the total exceeds the rendered rows. The 20-cap itself stands; what changes is that it is stated.

## Amendment (wave 43): mergeContacts is ALL-OR-NOTHING across the whole id list, not per pair — every refusal is decided before the first write

`mergeContacts` (`src/server/repo/contacts/merge.ts:703-714`) folds `mergeOnePair` over `mergeIds`, and each pair commits its seven FK repoints and its `DELETE FROM contact` before the NEXT pair's pre-checks run. So a conflict raised on pair k — both-contacts-have-a-login (`merge.ts:401`) or merged-email-owned-by-another-account (`merge.ts:421`, DEC-456/DEC-479/DEC-565) — returns 409 to the organizer with contacts 1..k-1 already merged and destroyed and no way to tell which. The "no partial merge — a merge that silently orphaned one login would be worse than refusing it" guarantee written into the docstring (`merge.ts:355-383`) is true per pair and false for the operation the API actually exposes. RULING: both refusals are hoisted into a pre-flight that runs before ANY write, over the WHOLE id list, and the guarantee becomes true of `mergeContacts` itself. Two cumulative subtleties the pre-flight must get right, and which per-pair checking cannot see: (a) login accounts are counted across `[keepId, ...mergeIds]` as a set — three contacts where the keeper and the THIRD merge id each hold a login trip nothing pairwise until two writes have already landed; (b) the merged email CHANGES as the fold proceeds (planMerge picks it), so the email-ownership check must run against every intermediate merged address, and ownership must be evaluated in JS against `user.contactId`, never as a SQL `NOT IN`, because staff logins carry `contactId = NULL` and SQLite's NOT IN yields NULL rather than TRUE for them (DEC-565). The conflict decision is therefore a PURE function of loaded rows (new module `contacts/merge-preflight.ts`), unit-testable without a db, and `mergeOnePair`'s existing per-pair checks stay in place demoted to fail-loud invariants that must now be unreachable.

## Amendment (wave 47): a merge preview that cannot refuse is not a preview — preview runs the write door's own preflight

The wave-43 amendment made `mergeContacts` all-or-nothing behind a whole-operation preflight (`planMergeFold` + `detectMergeConflicts`, `src/server/repo/contacts/merge.ts:735,763`) that refuses the entire batch on a second login account or a claimed email. `GET /contacts/merge/preview` (`src/routes/api/contacts/merge.ts:44-74`) runs `previewMerge` + `countMergeImpact` and nothing else, so the producer is shown a clean field-by-field preview of a merge that the POST will then reject — the preview and the write have drifted in exactly the dimension the preview exists to cover, and its own docstring claims they "can never drift." RULING: export a READ-ONLY `checkMergeConflicts(db, keepId, mergeIds)` from `src/server/repo/contacts/merge.ts` containing the identical preflight the write path runs (same `planMergeFold` fold order, same `detectMergeConflicts` judgement, zero writes), have `mergeContacts` call it so there is ONE implementation rather than a parallel copy, and have the preview call it and return `blocked: { code, message } | null` alongside `fields`/`impact`. The preview stays 200 with a stated refusal reason rather than becoming a 409 — a preview's job is to describe, including describing that the merge will be refused.

## Amendment (wave 81): segment.rules_json is parsed through a validated pure-core reader at every site

The write path validates rules (POST/PATCH /segments) and the matcher fails loudly on an unknown field or op (`src/domain/contacts-parts/segments.ts:48,72,85`), but three readers cast the stored column raw — `src/routes/api/contacts/segments.ts:147`, `src/routes/api/contacts/shared.ts:69`, `src/server/repo/contacts/crud.ts:454` — so a rule whose `value` is not a string reaches `rule.value.toLowerCase()` as a TypeError 500 with no field named, and a `rules_json` holding a non-array reaches `.every` the same way. The segment predicate decides who a bulk email reaches; its reader must refuse in the product's own error shape naming the segment, not crash in a domain helper. `MAX_SEGMENT_RULES` already bounds the write side and must bound the read side too, so a stored segment can never exceed what a live `?rules=` query is allowed to send.


## Amendment (wave 83, v12 mobile campaign w1): CSV column mapping is one column per screen at 390, with a radio target list and a Next column / Skip dock

Frame Contacts.dc.html:487 ("Import CSV · 390", captioned "one column per screen") draws a mapping step the build does not have: head = `‹ Contacts` + "Match the columns" + "speakers.csv · 214 rows · 2 of 5"; body = a "Column 2 of 5" 11px/800 eyebrow, the source column name at 22px display face, "First three values: …", then an "Import it as" section whose targets are a RADIO LIST of marked rows — not the select control the current phone layer pins (contacts-phone-frames.test.ts:282-286 pins `.chq-contacts-import-column-select` at width:100%) — closing with the match note "9 rows match an existing contact by email · those get updated"; dock = filled "Next column" + bordered "Skip". Ruling: at 390 the mapping step paginates one source column at a time. Rationale beyond the drawing: N stacked 44px selects is a scroll marathon in which the user loses track of WHICH column they are mapping, and the injective-mapping constraint (contacts-import-mapping-injective) is far easier to enforce and explain one column at a time. Desktop's full list is unchanged; the pagination is phone-only state, and the wizard's existing mapping model and POST payload are untouched.
