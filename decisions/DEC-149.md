# DEC-149: CRM filters ARE segment rules: GET /contacts accepts a rules JSON query param evaluated server-side by matchesSegment; SegmentRule.field gains pseudo-field 'any' (email/firstName/lastName/company/title); save-segment persists exactly the active rules

CRM-02 needs a true multi-criteria filter and the lossy segment-from-search bug comes from approximating free-text q as a firstName-contains rule. Making the directory filter and the segment model the same SegmentRule[] closes both at once: the SPA builds field/op/value rows, sends them URL-encoded as ?rules= to GET /api/v1/contacts (AND-composed with q/segmentId, applied via the existing matchesSegment authority in src/domain/contacts.ts), and 'save as segment' stores those exact rules so a reopened segment reproduces the same result set. The 'any' pseudo-field ('contains'/'eq' match if any standard field matches; 'ne' requires all to differ) gives free-text q a lossless rule form. One domain change, one query param — no schema change.

## Amendment (wave 2): the rules row states its own match count and owns Save as a segment; a segment delete asks first

The design's rules row reads "Matching all of [rule][rule] Add a rule — N of M match — Save as a segment": the count is the feedback that makes rule-building legible and the save is the moment a rule set becomes durable. The app's row carries neither, spells "Add a rule" as a dashed-outline button where the frame draws a green text link, and segment Delete fires with no confirmation. Ruling: the rules row ends with the match count taken from the directory's OWN list response (never a re-derived count, and no invented denominator when the unfiltered total is unknown — then it reads "N match") followed by Save as a segment; Add a rule is a text link; deleting a saved segment goes through the shared ConfirmDialog.
