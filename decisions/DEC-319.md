# DEC-319: Reminder sends are capped and ordered like every other bulk send: MAX_REMINDER_BATCH=100 contacts per pass, deterministic contactId ordering, a 1-hour manual dedupe window, and a reported remainder — never a hard reject

Verified: every other bulk send in the tree is capped — compose at MAX_COMPOSE_RECIPIENTS=100 (src/domain/compose.ts:9, DEC-019) and CRM bulk email at MAX_BULK_EMAIL_RECIPIENTS via parseBoundedIdArray (the former src/routes/api/contacts.ts:599 (now split across src/routes/api/contacts/)). The onboarding reminder is the sole exception: remindNow (src/server/repo/tasks.ts:680, reached from src/routes/tasks.ts:366) and the cron pass sendDueRemindersForEvent (:712) both hand an unbounded group list to sendReminderEmails, which issues one sequential mailer.send per contact. At SPEC's 200-800-speaker scale one click exceeds the Worker subrequest/CPU budget and half-sends. A hard 400 like DEC-019's is the WRONG guardrail here: the producer selects a compose batch and can narrow it, but remindNow's population is 'everyone who still owes something' and narrowing by taskIds does not shrink it, so rejecting would make the feature unusable at exactly the scale it exists for. Instead: cap at 100 contacts per pass, order groups by contactId ascending so batching is stable and repeatable, and return the remainder so the organizer can click again. That composes with the second half of the fix — remindNow currently bypasses DEC-023's dedupe entirely ('an explicit organizer action'), so a double-click re-spams everyone. Keep the deliberate override of the 72h due-window (that IS the point of remind-now) but add a 1-hour manual dedupe window, deliberately distinct from planReminders' 24h schedule-driven window: an organizer working a list must be able to chase again the same day, but must never turn an accidental second click into duplicate mail. Together these make repeat clicks drain the queue 100 at a time with nobody double-mailed. Both constants and both selection functions live pure in src/domain/reminders.ts (DEC-002) so they are unit-testable without D1; the cron pass reuses the same cap. Response becomes { sent, failed, skipped, remaining } and the confirm dialog reports it.

## Amendment (wave 56): the manual reminder batch chooses its 100 contacts in SQL; the cron sweep refuses loudly above a scan ceiling

listOutstandingForEvent (src/server/repo/tasks/reminders.ts:39-73) has no LIMIT: remindNow (:258) and previewRemindNow (:310) load every pending task_assignment for the event -- joined to task, event and contact -- and only then does planManualReminders (src/domain/reminders.ts:140-170) drop the dedupe-window contacts and capById-slice to MAX_REMINDER_BATCH=100. Thousands of rows are read to send 100 emails, on an organizer-triggered write path. The frontier is a set of contact ids and belongs in SQL: one GROUP BY contact_id query with the dedupe predicate in HAVING, ordered by contact_id, LIMIT 100, plus aggregate counts for `skipped`/`remaining`, then the existing contactIds-filtered row load. Preview and send MUST call the same frontier function or the review dialog shows more drafts than the send delivers (design handoff, Speakers grid rules). The cron path keeps its due-window predicate in TS (no SQL twin of effectiveAssignmentDueDate) but gets a MAX_REMINDER_SCAN ceiling with the loud refusal MAX_CONTACT_DIRECTORY_SCAN already uses -- refuse, never truncate.

## Amendment (wave 38): 'never a hard reject' binds the CRON too — bound the READ by choosing recipients first, never refuse the pass

DEC-319's own text ends 'never a hard reject', yet sendDueRemindersForEvent (src/server/repo/tasks/reminders.ts:626) calls listOutstandingForEvent unfiltered, which throws ApiError('invalid','...narrow with taskIds/contactIds first') past MAX_REMINDER_SCAN=20000 — a remediation the cron's only caller cannot supply — and runDueReminders (src/routes/tasks.ts:621) buries it in failedEventIds, so that event's automated reminders stop permanently with no in-app surface. Since DEC-932 back-fills every event task onto every active contact, one legal bulk accept can park an event at the ceiling. Ruling: the cron picks a bounded, contact-ordered recipient set FIRST (one grouped query, LIMIT MAX_REMINDER_BATCH, composing the same DUE_WINDOW/DEDUPE/overdue-tail constants planReminders gates on, documented as a COARSE SUPERSET pre-filter exactly like listEventIdsWithOutstandingAssignments's own pre-filter) and only then reads rows scoped to those contacts. planReminders stays the sole authority for what sends. The organizer-facing filtered paths keep their refusal — an organizer CAN narrow.
