# DEC-319: Reminder sends are capped and ordered like every other bulk send: MAX_REMINDER_BATCH=100 contacts per pass, deterministic contactId ordering, a 1-hour manual dedupe window, and a reported remainder — never a hard reject

Verified: every other bulk send in the tree is capped — compose at MAX_COMPOSE_RECIPIENTS=100 (src/domain/compose.ts:9, DEC-019) and CRM bulk email at MAX_BULK_EMAIL_RECIPIENTS via parseBoundedIdArray (src/routes/api/contacts.ts:599). The onboarding reminder is the sole exception: remindNow (src/server/repo/tasks.ts:680, reached from src/routes/tasks.ts:366) and the cron pass sendDueRemindersForEvent (:712) both hand an unbounded group list to sendReminderEmails, which issues one sequential mailer.send per contact. At SPEC's 200-800-speaker scale one click exceeds the Worker subrequest/CPU budget and half-sends. A hard 400 like DEC-019's is the WRONG guardrail here: the producer selects a compose batch and can narrow it, but remindNow's population is 'everyone who still owes something' and narrowing by taskIds does not shrink it, so rejecting would make the feature unusable at exactly the scale it exists for. Instead: cap at 100 contacts per pass, order groups by contactId ascending so batching is stable and repeatable, and return the remainder so the organizer can click again. That composes with the second half of the fix — remindNow currently bypasses DEC-023's dedupe entirely ('an explicit organizer action'), so a double-click re-spams everyone. Keep the deliberate override of the 72h due-window (that IS the point of remind-now) but add a 1-hour manual dedupe window, deliberately distinct from planReminders' 24h schedule-driven window: an organizer working a list must be able to chase again the same day, but must never turn an accidental second click into duplicate mail. Together these make repeat clicks drain the queue 100 at a time with nobody double-mailed. Both constants and both selection functions live pure in src/domain/reminders.ts (DEC-002) so they are unit-testable without D1; the cron pass reuses the same cap. Response becomes { sent, failed, skipped, remaining } and the confirm dialog reports it.
