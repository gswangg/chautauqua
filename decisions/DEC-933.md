# DEC-933: A task column is editable and removable from the grid it defines, and removing one states what it destroys

PATCH /api/v1/tasks/:id and DELETE /api/v1/tasks/:id have existed since DEC-023 and NOTHING under app/src calls either -- verified by grepping every apiPatch/apiDelete call site. The Speakers grid's columns are therefore write-once: a mistyped title, a wrong due date, or a task created in error is permanent on every speaker's portal, which is the recovery gap the SPK grader filed from the other direction. Worse, deleteTask hard-deletes every task_assignment for the task, completed ones included, with no confirmation anywhere in the product. Rule: each task column header carries two quiet controls in the conditional-and-quiet grammar -- Edit, which opens the existing TaskModal in edit mode and PATCHes title/description/dueDate/required/deliverableKind but NEVER kind or formId (a task's kind is its shape; changing it would orphan the responses already stored against it), and Remove, whose confirmation is a ConfirmDialog with a BODY (DEC-886/DEC-929: a confirm dialog with no body names nothing) stating the numbers in prose: "N speakers are assigned this task and M have completed it. Their uploaded files stay in the files library; their form responses do not." Those numbers are computed from the grid rows already in memory -- the cells the page has already fetched -- never a new count endpoint and never a query per row. Both controls render only for an organizer, and Remove refetches the grid rather than splicing, so the column count and the counts panel can't disagree.
