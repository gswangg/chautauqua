# DEC-912: Whether a recipient has a slot is a fact about the recipient, not about the calendar checkbox — and a recipient row names the talk

The compose frame's step-3 recipient list (docs/design/Chautauqua Comms.dc.html:84-93, 380-383) shows, per row, the name over 'email · DFC-014' with a right-aligned 'Scheduled' / 'No slot yet' flag, and closes with '18 more · 23 is under the 100-recipient cap'. The build shows name and email only, and app/src/pages/comms/PreviewPane.tsx:56 gates the Scheduled/No-slot tag on `attachIcs` — because the server only resolves a slot at all when attachIcs is set (RenderedRecipient.ics, app/src/pages/comms/types.ts:16-38). So the organiser learns which of twenty-three speakers has no room only by ticking a checkbox about calendar attachments, which is a different question. Rule: RenderedRecipient carries `ref` and a boolean `scheduled`, both resolved on EVERY compose render regardless of attachIcs; `ics` (the attachment payload) stays gated, and so do the two footnote blocks that describe the attachment — those genuinely are about the checkbox. The client reads `scheduled` for the always-on flag and `ref` for the row's second line. The cap footer reads its number from the existing recipient-cap constant, never a second literal 100.
