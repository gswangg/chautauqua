# DEC-473: The list-envelope enumeration is a re-runnable artifact with one row per site in four fixed classes, not prose

DEC-459 forbade grading an "all"/"every"/"never" row from a sample; DEC-466 answered by declaring a mechanical criterion — and then shipped a three-item prose list anyway, which DEC-471 has now shown was short by two. The gap is that "mechanical" was asserted rather than instantiated. The artifact contract: docs/verification-log/task-w21-b-list-envelope-enumeration-stage1.md opens with the exact, copy-pasteable command that generates the site set (a ripgrep over src/routes matching `c.json(` calls whose object literal contains an `items` key, multiline-aware so the wrapped forms at src/routes/api/tokens.ts:66, api/contacts/crud.ts:41, api/submissions.ts:77 and api/contacts/bulk-email.ts:189 are included) plus that command's raw output and its line count, so any later reader re-runs it in one paste. Every returned site gets exactly one row classified into one of four classes and nothing else: BOUNDED-IN-SQL (repo LIMIT/OFFSET + sibling count fn — cite both call sites), BOUNDED-IN-JS (DEC-461(e) slice of a materialized array — cite the clamp and that `total` is the pre-slice length), CAPPED-ECHO (a mutation echoing back its own bounded input — cite the cap constant, e.g. MAX_COMPOSE_RECIPIENTS at src/routes/comms.ts:187 and src/routes/api/contacts/bulk-email.ts), or UNBOUNDED (defect; name the owning DEC/branch or mark it unowned). No fifth class, no "naturally small", no row without a file:line. Each UNBOUNDED and each BOUNDED-* row is then live-probed against the 2k perf seed with the row count actually returned, because a LIMIT in the source is a claim and a response body is a measurement (DEC-453).
