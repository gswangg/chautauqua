# DEC-610: Saving a view is a dialog like every other dialog, and on a phone the decision lives on the card

window.prompt is the one modal in the product the design system cannot style, cannot label, and cannot validate — it also blocks the event loop and is suppressed outright in some automation contexts, so the save-view path can fail invisibly. It becomes the same dialog contract every other modal uses. The phone reflow of the submissions table, meanwhile, turns rows into cards but leaves the triage decision only in the bulk bar, which needs a selection first; the designed phone card carries the decision itself, using the single-id form of the bulk status endpoint that already exists.

## Amendment (wave 14) — the phone submission row is four lines, and capability is relocated rather than removed

Frame 02 phone (docs/design/Chautauqua Submissions.dc.html:157-169) draws a triage card as exactly four lines: ref + status, title, one meta line 'speakers · track · format', then the action row. The app's CSS reflow gives every <td> its own full-width line, so the same row renders as select / ref+status / title / speakers / track / sent / one line per custom column / Clone / triage — the 'verbose fields' finding. Ruling: at phone width the metadata cells (speakers, track, sent, and every derived custom column) share one wrapped line separated by '· ' rendered as ::before on all but the first, so no trailing separator can appear and the separator count follows the column count; Clone joins the triage action row; and the select checkbox joins the ref+status line. Selection and Clone are NOT dropped to match the frame — J9 says a phone surface that refuses what desktop allows is a different product, and DEC-274's bulk capability is deliberate — they are relocated, which is what a reflow is. The custom-column and Clone cells get real class names so the CSS names what it means instead of counting nth-child positions past a variable-length column set.


## Amendment (wave 83, v12 mobile campaign w1): the phone submission card's third action is the frame's bordered "Read"; Waitlist is not a card verb

Frame Submissions.dc.html:137 draws exactly three card actions: Accept (filled olive, flex:1), Decline (bordered, flex:1), Read (bordered, natural width, `padding:0 14px`). The build ships Accept/Decline/Waitlist (SubmissionsTable.tsx:548; submissions-phone-card.render.test.tsx:124 pins the trio). Three competing STATUS verbs on one 390 card is the defect DESIGN-RULINGS names for the worklist bar — controls whose scopes differ, side by side, leave the user unable to tell which one they are pressing — and it costs the card its only route into the record, because at 390 the title is not a link. Ruling: adopt the frame. The third control is "Read", a bordered secondary at its natural width, navigating to /admin/submissions/:id where Waitlist already lives on the decision rail (SubmissionDetailPage.tsx:165) and in the bulk bar (BulkActionBar.tsx:33). Waitlist stays fully reachable; it is never on the card. DEC-610's own thesis — "the designed phone card carries the decision itself" — is preserved: Accept and Decline ARE the decision; Waitlist is a third holding state, not a decision.
