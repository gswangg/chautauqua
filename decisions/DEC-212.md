# DEC-212: Rating-less scorecards are legal; aggregateSubmission returns {count: evals.length, average: 0, perCriterion: {}} when the criteria list is empty; computeWeightedScore keeps its empty-list throw

parseCriteriaList has accepted dropdown/text-only criteria since DEC-018/DEC-148 (both kinds are documented as "excluded from weighted scoring"), so a dropdown-only advance/no-advance scorecard is a legal plan shape — retroactively rejecting it would 400 persisted plans on SPA round-trip PATCHes. But once one evaluation exists, buildResults (review.ts:408) filters to rating criteria and aggregateSubmission calls computeWeightedScore with an empty list, which throws → unhandled 500 on GET /api/v1/plans/:id/results and its CSV. Resolution: define the aggregate for zero rating criteria in the domain — aggregateSubmission (src/domain/evaluation.ts) short-circuits when criteria.length === 0, returning real count, average 0, empty perCriterion, with an explanatory comment. computeWeightedScore retains its fail-loudly throw as an invariant guard; callers must never invoke it with empty criteria. The CSV simply emits zero per-criterion columns. No route changes required.

## Amendment (wave 81): evaluation.scores_json gets ONE validated home, and `as unknown as EvaluationScores` is banned

The domain declares `EvaluationScores = Record<string, number>` (`src/domain/evaluation/scoring.ts:24`) while every repo read of the column declares `Record<string, number | string>` (`src/server/repo/review/evaluations.ts:40,54,71,98,296,314,367,430`) and `src/routes/review/shared.ts:487` launders one into the other with a DOUBLE cast (`as unknown as`). `computeWeightedScore`'s own guards cannot catch what that cast admits: `score < scale.min` and `score > scale.max` are both FALSE for a non-numeric string, so the value walks past the loud-failure ladder and lands on `weightedSum += score * criterion.weight` as NaN, silently poisoning a plan's weighted mean and its ranking. Tolerance is legitimate for a DISPLAY LABEL (DEC-529's export projects columns from the score keys actually present) and never for a value that enters arithmetic. Ruling: one pure-core parser owns the column; the numeric view is derived by a named function that refuses loudly per criterion; no `as unknown as` may bridge the two shapes; and the population is defined by directory (every `scores_json` read under `src/server/repo/review/` and `src/routes/review/`), not by a hand-list.


## Amendment (wave 7, sha ddc9a7d9): the evaluations export is the tolerant reader scores-json.ts names — so it must actually call the parser

`src/domain/evaluation/scores-json.ts:24-26` writes the tolerance boundary as a rule and names its owner: "A display projection (an export's per-criterion label column) may tolerate what arithmetic must not — that tolerance belongs to the export's own reader, never to this parser." There is no such reader. `src/server/repo/exports/evaluations.ts:254` does a bare `JSON.parse(r.scoresJson) as Record<string, unknown>` OUTSIDE any try, so one corrupt row throws an anonymous SyntaxError and 500s the entire CSV — ten lines below, the same file states the opposite policy in its own words (`:262-266`: an export reading possibly-legacy history "must render empty rather than 500 the whole export"). It then launders the result into arithmetic with `scores as Record<string, number>` (`:272`), the single-cast cousin of the `as unknown as` DEC-212 closed in `routes/review/shared.ts`. RULING: the export reads through `parseEvaluationScoresJson` and narrows through `numericScoresFor`; an `EvaluationScoresJsonError` blanks THAT ROW's score cells and weightedScore while the row still prints its identity columns. The named error must identify the row — a tolerated bad row that cannot be found is not tolerance, it is silence.
