# DEC-892: Submission history is DERIVED from rows that already exist -- one union, no audit table, no new column

src/server/repo/revisions.ts is the only source behind the detail page's HISTORY disclosure (app/src/pages/submissions/SubmissionDetailPage.tsx:662-690), and it lists post-edit snapshots only -- so a submission nobody edited shows an empty panel behind SHOW, and the 02-submissions frame's timeline (submitted / confirmation sent / review in / opened-by) is unimplemented. Every fact that timeline needs is already stored: submission.created_at, submission_revision, evaluation.submitted_at, and email_log (which carries contact_id and its own event+sent_at indexes, src/db/schema/email.ts:52-58). Rule: GET /api/v1/submissions/:id/history returns ONE time-ordered list assembled in ONE repo function from those four sources -- submitted (created_at + source), edited (today's revision rows, unchanged), reviewed (evaluations with submitted_at set, naming the plan, honouring the same anonymization the review surface applies), emailed (email_log rows whose contact_id is one of this submission's participant contacts and whose sent_at >= the submission's created_at, labelled by subject). No table, no column, no trigger: a decision that needs a migration to record what the data already says is a decision to store the same fact twice, and it will drift. Entries share one shape {id, at, kind, label, detail} and render through the page's existing timestamp formatter.


## Amendment (wave 61): an `edited` history entry names WHAT CHANGED, not the title it happened to leave behind

history.ts:112 sets an edited entry's detail to the revision's title. Two same-author edits to the description therefore log two rows with the same label, the same minute-granular timestamp and the same detail — indistinguishable, and Restore has nothing to aim at. Adding seconds would make the rows unequal without making them meaningful; the missing fact is which field moved. The wave-59 baseline revision closed the last gap that made this uncomputable: every revision now has a predecessor, so a diff is always defined. Ruling: an edited entry's `detail` is the changed-field summary against the immediately preceding revision in createdAt order — 'Title changed', 'Description changed', 'Title and description changed', and 'No text change' when neither differs (an honest empty answer, never a fabricated one). `label`, `at`, `revisionId` and the entry ids are untouched, no query is added and no column is added — listRevisions already returns both fields.
