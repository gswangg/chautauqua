# DEC-775: XML is an output format of the surface feeds, not a gap in the builder

docs/eval-rubric/06-public-widgets.yaml:16 and EMB-15's pass_criteria name the expected format set verbatim: "styled HTML script, basic HTML, JSON/XML, iCal". We ship iframe/element/link/json/ics (app/src/pages/settings/embedSnippet.ts:15) -- XML is the one named format absent, and it is the cheapest possible win because the .json branch (src/routes/public/index.tsx:219) already resolves the event, the surface and a paged feed. Decision: `/embed/:slug/<surface>.xml` mirrors the .json route exactly -- same getSurfaceFeedPage data, same envelope fields, same cache headers -- serialized by a pure buildSurfaceFeedXml in src/routes/public/feeds.ts with correct escaping of &, <, >, " in every text node and attribute; 'xml' joins EMBED_FORMATS so the builder offers it and buildSnippet returns the bare URL for it, as it already does for json/ics. Same data, one more shape: no second query path can drift from the first.

## Amendment (wave 62): the public XML feed is a well-formed XML document or it is an error — illegal characters are stripped at the serializer, the declaration is emitted, and an element name that isn't an XML Name throws

escapeXml (src/routes/public/feeds.ts:100-107) escapes the five significant characters and nothing else. XML 1.0 forbids most C0 controls (0x00-0x08, 0x0B, 0x0C, 0x0E-0x1F) in a document at all — no entity form exists for them — and a public CFP title reaches this serializer having been length-checked only (src/forms/validate.ts:93). So a control byte in a talk title makes /embed/:slug/:surface.xml serve an anonymous, edge-cacheable 200 that no parser will accept, silently breaking a J10/EMB deliverable that the probe log lists as verified working. The identical rule was already reasoned out and shipped one directory away for the ICS serializer (sanitizeIcsText/sanitizeCn, DEC-499/DEC-540: strip C0/DEL at the SERIALIZER because the value comes from unauthenticated public text) — feeds.ts is the sibling that never received it. Two smaller correctness gaps ride along: no <?xml version="1.0" encoding="UTF-8"?> declaration, and fieldToXml (:114-124) builds element names straight from object keys, so a key that isn't a valid XML Name emits a broken tag instead of failing. Fail loudly on the name, strip on the text: the first is our bug, the second is a stranger's input.
