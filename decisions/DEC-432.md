# DEC-432: Event scope belongs in the WHERE: the two surviving JS post-filters over unbounded row sets move into SQL

Two survivors of the DEC-333/DEC-418 sweep, both on hot reads carrying SPEC.md:331's p95 budgets. src/server/repo/portal.ts:686-701 (getMyResources) SELECTs every resource row in the ORG — all events, every year — and then keeps only the speaker's with rows.filter((r) => eventIds.includes(r.eventId)); the scope belongs in the WHERE as inArray(resource.eventId, eventIds) batched through the repo's existing chunkIds convention, with the position ordering in orderBy. src/server/repo/contacts/stats.ts:30-40 (getContactStats) returns one row per participating contact for the whole org and computes returningSpeakers as .filter(...).length; it becomes a single count(*) over a GROUP BY contact_id HAVING count(distinct event_id) > 1 subquery. Both are the case SPEC.md:193-195 forbids ("a feature that demos well with 10 rows and dies at 2,000 is not built") at the org scale target of 200-800 speakers across multiple events, and both are inconsistent rather than intentional — the admin list at src/server/repo/submissions/list.ts and the public lists after DEC-418 already do this correctly.

## Amendment (wave 21): sibling KPIs computed in one function share one predicate — returningSpeakers means SPEAKERS, on this org's events

DEC-432 moved returningSpeakers into a single count(*) over a GROUP BY/HAVING subquery for scale, and that half holds. But the query it produced (src/server/repo/contacts/stats.ts:44-52) counts any contact holding ANY participant row on more than one event, with no role filter and no invite-status filter — while its sibling ten lines below (speakerCount, DEC-711) filters participant.role = 'speaker' AND inviteStatus IN ACTIVE_INVITE_STATUSES for the very same population. Two readers of one table in one function, one with manners and one without: a moderator or a declined invitee counts as a 'returning speaker'. The distinct-event count is also unscoped — it counts DISTINCT submission.eventId with no join to event.orgId, so the figure's honesty rests on an invariant it never states. Ruling: ONE exported predicate helper backs both subqueries, and the returning count is DISTINCT over this org's own events. The field stays on the endpoint (it is DEC-432/DEC-809 contract and the J11 walkthrough asserts its shape) even though the header no longer prints it — a figure the API states must be true whether or not a surface renders it today.
