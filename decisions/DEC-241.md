# DEC-241: Results table: numeric Average stays rating-only; dropdown criteria get modal-plus-distribution columns; text criteria get no column; all result columns client-sortable

ABS-10 flagged that dropdown answers vanish ('—' column) while appearing folded into the Average. The Average was already rating-criteria-only and stays that way (mixing option indices into a weighted mean would fabricate meaning). Dropdown criteria gain a real aggregate: a pure aggregateDropdownCriterion(evals, criterion) in src/domain/evaluation.ts returning per-option counts, rendered as the modal option plus distribution (e.g. 'Just right x3 / Too long x1') in the table and as per-option count columns in the CSV. Text criteria are scorecard-only and get no results column (dropping the misleading permanent '—'). Sorting is client-side on the loaded result set (results are one bounded plan, not a paginated table): Average, count, and each criterion column toggle asc/desc.

## Amendment (wave 82): the Choice distribution is computed, shipped and must be READ — its home is the expanded reviews band

The server already aggregates it: `aggregateDropdownCriterion` (`src/domain/evaluation/criteria.ts:246`) is called per Choice criterion at `src/routes/review/shared.ts:492` and shipped on every results row as `perDropdown` (`:441`), and the SPA declares it on the wire type (`app/src/pages/review/types.ts:158`) — and `ResultsTable.tsx` never reads it. A declared, computed, transmitted field with no reader is a lie (DEC-851 family). DEC-737 folded per-criterion columns into the Reviews disclosure, so the V12 ruling's "distribution in the footer where the mean sits" resolves to a footer row inside the expanded band, one line per Choice criterion, reading `<Label> · <Option> N · <Option> M` in the criterion's OWN option order (the order `aggregateDropdownCriterion` already returns, so ties and zeros stay stable). Nothing renders when the round has no Choice criterion — the band must not grow an empty row.

## Amendment: Choice criteria are excluded from the weighted mean and their distribution follows the DECLARED option order — pinned by a domain test

The v12 intake ships Scale-or-Choice into scoring paths that scored 91-100 on the interim run, with the user's own REGRESSION SENSITIVITY flag and an explicit ask for "a results-math test (shares 60/40 not 50/33 with a Choice present)". Verified at planning runtime that the domain already implements the contract — `criterionWeightShares` (`src/domain/evaluation/criteria.ts:198-205`) filters to `typeof weight === 'number' && weight > 0`, and `DropdownCriterionDef` declares `weight?: undefined`; the freeze is real too (`src/routes/review/plans-crud.ts:153-158`, DEC-123, whole-array `deepEqual`). Ruling: because three concurrent branches are editing the SPA above these functions, the contract gets pinned in the DOMAIN where it cannot be re-litigated per-component — shares are computed over Scale criteria alone, a Choice pick never reaches `computeWeightedScore`, the distribution renders in the criterion's DECLARED option order (never alphabetical, never by count), and the plan PATCH refuses a criterion TYPE change once any evaluation exists. Pinning an existing correct behaviour is cheap; discovering it broke after the freeze is not.

## Amendment (wave 2): a Choice aggregate ships an ORDERED distribution; a counts map is not an order

aggregateDropdownCriterion returns `counts: Record<string, number>` and the ruling requires the distribution be shown 'in the per-criterion breakdown' as the committee declared it — 'Strong 2 · Weak 1'. A JavaScript object hoists integer-like keys to the front in ascending numeric order, so a Choice criterion whose options are '5' / '3' / '1' (or any list containing '0') silently re-sorts for any consumer that iterates Object.keys(counts). The CSV at src/routes/review/plans-progress.ts:208 escapes this only by accident, because it happens to iterate dc.options. Rather than leave three parallel SPA branches to each rediscover the rule, the domain gains `dropdownDistribution(criterion, counts): {option, count}[]` — declared option order by construction — the CSV column builder becomes its first real reader, and the parser header states the rule so the next consumer cannot get it wrong. Deliberately NOT a wire-shape change: adding a `distribution` field to perDropdown would churn the SPA wire type and four render-test mocks that three unmerged branches are editing right now.
