# DEC-459: A ledger row phrased with a universal quantifier is graded from an enumeration of the whole population, never from a sample

Every defect this wave fixes sat under a row that a prior ledger graded VERIFIED from one citation: "Rate limits on auth + public submission" cited one call, "Public submission validates server-side against form schema" cited one function, "Authz + object-level ownership" cited one middleware plus one IDOR test out of ~157 route registrations across 35 files under src/routes. DEC-453 already forbids grading a MEASURED row from code presence; this generalizes it to QUANTIFIED rows. Any ledger row whose claim contains "all", "every", or "never" must be backed by an artifact that enumerates the full population -- every route, every list endpoint, every ingress -- with a per-member verdict and citation, and names the members it could not confirm. Producing that enumeration is a lane of its own, and its log is the ledger's evidence rather than the ledger re-deriving it. Two such enumerations run this wave (route authorization, unauthenticated-surface input handling); an enumeration lane MAY land a missing guard in a route file it owns, but must record rather than fix anything in a file another lane owns this wave.

## Amendment (wave 21): the route-authorization enumeration is executable — a markdown table is pinned to the sha it was written at

DEC-459 requires any 'all/every/never' claim to be graded from an enumeration of the whole population, and the route-authz enumeration it mandated exists: docs/verification-log/task-w18-d-route-authz-inventory-stage1.md, 157 registrations across 35 files, 135 GUARDED, 22 PUBLIC-BY-DESIGN, 0 GAP. But it is prose, pinned to sha d034a9e0, and its runtime companion (test/route-authz-inventory.test.ts) probes three route files and says so in its own header: "a representative set". The enumeration therefore stops being true the moment a route is added — the same defect the anonymous-route probe had before wave 18 taught it to compose from src/index.ts's real mount list. Ruling: the population is re-derived AT TEST TIME. One scan enumerates every route registration under src/routes/**, classifies each as GUARDED (a role middleware in the chain, or an ownership marker in the handler) or PUBLIC-BY-DESIGN via a ledger seeded from the doc's own PBD rows with their reasons; every mutating registration must additionally name a CSRF guard; a ledger entry matching no live registration fails as stale; and a registration-count tripwire keeps the regex from silently matching nothing. The doc becomes the ledger's evidence, not the guard.

## Amendment (wave 32): a guard's NAME in a scan is not a refusal at runtime — a speaker session and a reviewer session are driven against every /api/v1 registration

DEC-459's enumeration classifies a route GUARDED when the registration text names a role guard or an ownership marker. That proves a guard was written, not that a non-organizer actor is refused: SPEC §6 requires role + event grant on every admin/API route, and the review lens has only ever sampled this by hand (four probes on four ids). requireOrganizer/requireReviewerOrOrganizer refuse synchronously off c.var.auth, so a throwing-db stub makes the invariant crisp: a speaker or reviewer session must get 401/403/404 with zero db access. Ruling: a runtime probe drives every /api/v1 registration (all methods) with a speaker session and with a reviewer session; each must refuse without touching the db, or appear in a two-directional ROLE_REACHABLE ledger naming the actor, why that actor legitimately reaches it, and the existing test that covers its object-level ownership check. An entry with no named covering test is a finding, never an absorption.

## Amendment (wave 35): a CSRF guard is not an authorization guard — the route-authz enumeration's guard vocabulary is role guards and ownership markers only

test/route-authz-enumeration.scan.test.ts is the repo's population-level proof of SPEC §6 ("authz middleware on every admin/API route"). It harvests middleware exports with /export (?:const|function) (require\w+|csrf\w+|sessionLoader|noStoreByDefault)\b/ (:340), folds ALL of them into one GUARD_NAMES set (:368), and treats any of those names appearing in a registration's text as proof of authorization (:526/:509). Every mutating route in this repo carries csrfJson or csrfForm, so every mutating route self-certifies as GUARDED — the exact direction the scan exists to police is the one it cannot fail on. A double-submit CSRF check proves the request came from our own page; it says nothing about who may perform it. sessionLoader only SETS c.var.auth and noStoreByDefault only sets a header; neither refuses anything. RULING: the vocabulary splits into ROLE_GUARD_NAMES (require* exports from middleware.ts plus the four out-of-middleware guards requireReviewerOrOrganizer/requireAssignedPlan/requireAuthOr302/speakerGate) and a separate CSRF_GUARD_NAMES, asserted DISJOINT; sessionLoader and noStoreByDefault leave the vocabulary entirely. The classifier becomes a pure function so it can be shown a violation (a registration whose only middleware is csrfJson must classify as a GAP). Second direction added at the same time: a PUBLIC_BY_DESIGN row for a non-GET method must name its real, non-session protection (rate limit, or possession of an unguessable token) in its reason — the two mutating recovery endpoints POST /forgot and POST /reset/:token are ledgered under that rule rather than passing on their CSRF middleware.

## Amendment (wave 37): tenant refusal is proven AT THE ROUTE, over REAL ROWS, by ENUMERATION

The three existing runtime probes (test/anonymous-route-probe.test.ts, test/anonymous-mutation-probe.test.ts, test/role-refusal-probe.test.ts) all vary the ROLE or its absence, and every refusal they assert happens BEFORE any data access — which is why a db stub that throws on first property access works as their touch detector. A tenant (wrong-ORG) refusal is structurally different: you must READ the object to learn whose org it belongs to, so a throwing stub can never prove it. The per-route cross-org tests that do exist (test/review-idor.test.ts et al.) mock the very resolver whose org predicate is the thing under test — they prove the route asks the right question and assume the answer. And nothing enumerates a route POPULATION on this axis, so a route added tomorrow is uncovered. This matters concretely: the SPA's event context is client-controlled (localStorage 'chq.currentEventId', app/src/lib/useCurrentEvent.ts), so /api/v1/events/:id/* is attacker-parameterized by design. Wave 37 adds four enumerated probes, each booting the real migrations/ DDL over node:sqlite + drizzle sqlite-proxy (harness pattern: test/rate-limit-atomicity.test.ts:22-64), authenticating as a real actor in org B, and driving org A's ids. RULES, binding on all four: (1) a clean tenant refusal is 403 or 404 ONLY — a 2xx fails, and a 5xx fails too (a crash is not a guard); (2) each probe asserts org A's rows are byte-identical after the whole sweep (a refusal that mutates is not a refusal); (3) each probe carries a TWO-DIRECTIONAL ledger — every enumerated route is either exercised or named with a one-line reason, and every ledger entry must still match a live registration (a deleted route cannot leave a stale, unverifiable line); (4) each probe DUPLICATES the composition rather than sharing a helper, the convention test/role-refusal-probe.test.ts:5-11 already records, so one weakened helper cannot silently weaken four probes.

## Amendment (wave 40): the tenant axis includes ids supplied OUTSIDE the path — JSON body and query string — enumerated the same way

DEC-459's wave-37 amendment closed the tenant axis for PATH params: four probes drive an org-B actor against org-A ids over real rows, and their populations are derived from source by path shape (test/cross-org-event-scope-probe.test.ts filters `/api/v1/events/:id/*`; test/cross-org-object-probe.test.ts filters `/^\/api\/v1\/(?!events\/)[a-z-]+\/:[A-Za-z]+/`). Both derivations are blind to the id that arrives in a request BODY or query string — POST /contacts/duplicates/dismiss {contactIds}, POST /contacts/merge {keepId, mergeIds}, POST /pipeline {contactId}, POST /plans/:id/reviewers {userId, submissionIds}, POST /tasks/:id/assign {contactIds}, GET /contacts?segmentId=, and their siblings. That is not a hypothetical class: wave 38's assign-guard defect lived on exactly this surface, and every guard on it today is a per-route hand check with no population-level proof (field guide: SPOT-CHECKED IS NOT ENUMERATED). The field guide still carries "TENANT axis SPOT-CHECKED not ENUMERATED" as open since w37; this amendment names what actually remains. RULING: one more enumerated probe, deriving its population at test time from route source (registrations whose handler reads a known entity-id key from `body.` or `c.req.query(...)`), driving each as an org-B organizer whose PATH params name org-B objects while the body/query carries org-A's real ids — so a path check can never be what refuses. DEC-459's four wave-37 rules bind unchanged: refusal is 400/403/404 only (a 2xx leaks, a 5xx is not a guard); org A's rows are byte-identical after the sweep; the ledger is two-directional with an enumeration floor; and the composition is DUPLICATED, not shared with the sibling probes. It stays in the fast tier per DEC-727's wave-37 amendment.
