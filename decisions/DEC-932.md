# DEC-932: Every active accepted speaker holds an assignment for EVERY task the event owns: activation BACK-FILLS, it never snapshots

createTask (src/server/repo/tasks/crud.ts, DEC-746) expands a new task to every accepted speaker AT CREATION TIME and there is no opt-out -- but the only other assigner in the product, planAndPersistOnboardingTasks (src/server/repo/submissions/status.ts), plans exclusively the five DEFAULT_ONBOARDING_TASKS templates through the pure planAcceptance (src/domain/acceptance.ts:155). So a contact who becomes an active accepted participant AFTER a custom task was created -- via bulk accept, via a co-presenter invite, or via the Speakers participation menu flipping 'invited' to 'accepted', all three of which already call ensureOnboardingTasks -- never receives that task: the Speakers grid renders their row with a permanently blank cell in that column, their portal never lists it, the reminder cron never chases it, and no UI can assign it (the SPA calls neither PATCH nor POST on /tasks/:id/assign). This is the SPK grader's "task assignment misses portal-linked rows" defect, and it is a data invariant, not a rendering nit. Rule: planAndPersistOnboardingTasks gains a SECOND pass, after the template pass and inside the same call, enforcing the invariant "an active accepted participant of this event holds a task_assignment for every task row the event owns" -- ONE select of the event's task ids, ONE chunked select of the existing (task_id, contact_id) pairs for exactly those contact ids, ONE chunked insert with onConflictDoNothing on the (task_id, contact_id) uniqueIndex (DEC-556). Never a query per contact and never a query per task. An existing assignment row is NEVER touched (a completed one stays complete) and none is ever deleted; the planned write count is checked against DEC-528's MAX_TASK_ASSIGNMENT_WRITES before the first insert and refused loudly if it exceeds it. The narrower ACTIVE_INVITE_STATUSES gate (DEC-278/283) is unchanged -- an 'invited' or 'declined' participant is still not chased.

## Amendment (findings wave 6): acceptance back-filling every event task to the newly accepted is the DENSE model on purpose — affirmed, not a defect

A review lens filed the DEC-932 back-fill (src/server/repo/submissions/status.ts:297-379, re-firing on every entry into 'accepted' at :529) as silently overwriting a producer's targeted `POST /api/v1/tasks/:id/assign` scoping. Verified against the tree, the premise is wrong in one place and the model is deliberate in the other. The back-fill ranges over the participants of the ACCEPTING submissions only, not "the whole roster"; and its twin, DEC-746 at src/server/repo/tasks/crud.ts:326-329, already makes createTask expand to every active accepted contact with no opt-out. Together they define the product: the J6 grid is speaker x task and dense, which is also why the SPA never calls the assign endpoint at all (grep of app/src: zero call sites) — a task created after acceptance would otherwise render a column nobody owes. Sparse per-task audiences would need a task.audience column, a picker in the New-task modal and a new vocabulary, to serve a scoping affordance the UI does not offer and SPEC does not ask for. test/onboarding-task-backfill.test.ts already pins the invariant that matters (the back-fill only ever inserts missing pairs; it never updates or deletes, so a completed assignment stays complete). No task is filed; this amendment exists so the finding is not re-filed a third time.

## Amendment (wave 43): the acceptance back-fill covering EVERY event task is DELIBERATE — per-contact assignment is additive, never a restriction

Adjudicating a review-lens claim rather than leaving it to accrete: `activateAcceptedParticipants` (`src/server/repo/submissions/status.ts:297-350`) gives every active participant of a (re-)accepting submission an assignment for EVERY `schema.task` row of the event, so a task an organizer deliberately handed to a subset via `POST /api/v1/tasks/:id/assign` (`src/routes/tasks.ts:449`) also lands on newly-accepted speakers, and the J6 grid grows accordingly. The claim is factually correct — I read the nested loop at `:345-350`. It is nevertheless the designed behavior, and the alternative is worse at this stage. An event task is event-wide in the model: there is no `audience` column, and adding one at the exit gate would mean a migration, a seed change and a perf-seed change against a tree that currently passes 12002 tests, to represent a distinction SPEC never asks for — §J6 describes the producer's dashboard as a per-speaker x per-task grid over the event's task set, and lists the default task set, not per-task audiences. The back-fill exists for a real reason this DEC already states: a custom task created AFTER a contact went active would otherwise never reach them, which is the more common and more damaging failure. RULING: DELIBERATE. `POST /api/v1/tasks/:id/assign` is an ADDITIVE door (it adds assignments now; it does not declare an audience forever), the back-fill never UPDATEs or DELETEs an existing row so a completed assignment is never downgraded, and the behavior is pinned by a test so it stays a choice rather than decaying into an accident. If a future wave wants subset-only tasks, it adds the `audience` column deliberately and amends this DEC — it does not discover the gap again from the grid.

## Amendment (wave 43, task-w43-e): the falsifying checks this ruling needs, named by file and describe-block

`test/onboarding-task-backfill.test.ts` (pre-existing) already pinned: a custom task lands on every active participant across all three call shapes (`updateSubmissionStatuses`, `ensureOnboardingTasks` with an explicit list, `ensureOnboardingTasks` with `contactIds=null`), idempotency on re-run (zero new rows), that an already-`complete` assignment is never UPDATEd/DELETEd, and query-count scaling by chunk not by row. Those checks already satisfy two of the three assertions this wave scoped (custom-task coverage including the strict-subset case in spirit, and the complete-assignment-never-downgraded proof).

New in `test/acceptance-backfill-scope.test.ts` (task-w43-e), describe `"DEC-932 amendment (wave 43): back-fill scope — new falsifying checks"`:
- `"a task with an existing STRICT-SUBSET assignment (to a different, non-participant contact) still back-fills onto a newly-active contact"` — proves the organizer's earlier narrow `POST /tasks/:id/assign` scoping is not a ceiling: both the prior pair and the back-filled pair coexist.
- `"NEGATIVE CONTROL: a task belonging to a DIFFERENT event is never assigned to this event's newly-active contact"` — seeds two events, each with its own task, and asserts only the accepting event's task is assigned.
- `"NEGATIVE CONTROL: a contact who is NOT an active participant of the accepting submission (still 'invited') receives nothing"` — seeds one active and one still-`invited` participant on the same submission and asserts zero rows for the latter.

These three, together with the pre-existing file, are the exercised checks wave 44's triage closure can cite in place of this DEC's prose.
