# DEC-505: A field's kind and section are patchable, and a kind change is refused while answers exist

Verified defect at file:line on current main. app/src/pages/forms/FieldModal.tsx renders an editable Section select (:96) and Kind select (:104-111) when editing an EXISTING field and submits both (:60-61). The PATCH handler src/routes/api/forms.ts:189-217 validates them (it now passes {id, kind} into validateFieldDefInput per DEC-500) but repo.patchField's FieldPatch (src/server/repo/forms.ts:277-283) carries neither section nor kind, so patchField (:285-300) silently discards them and the route returns 200 with the UNCHANGED field. A producer changes Text -> Dropdown, clicks Save, sees no error, and nothing happened; worse, in that same request options ARE persisted (:212, :292) onto a field whose kind is still text. A visible control that does nothing is the opposite of "fail loudly" and of "legible over configurable". Decision: section becomes freely patchable (it is pure grouping). kind becomes patchable ONLY while the field has zero stored answers -- existing submission_answer rows were validated against the OLD kind and a number answer under a now-dropdown field fails every subsequent validateAnswers -- so the route counts answers via the EXISTING repo.describeFieldDependents(db, formId, fieldId).answerCount (no second counter) and 409s naming the count when it is non-zero, the same shape DEC-300 already uses for a field delete with dependents. When kind changes away from 'dropdown', patchField clears optionsJson to null in the same write (options exist only on dropdowns, DEC-500); when it changes TO 'dropdown', DEC-500's effective-kind rule already forces non-empty options in the same request. Locked built-in fields reject kind/section changes outright, exactly as they already reject a required change (:197-199).
