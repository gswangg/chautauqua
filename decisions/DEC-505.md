# DEC-505: A field's kind and section are patchable, and a kind change is refused while answers exist

Verified defect at file:line on current main. app/src/pages/forms/FieldModal.tsx renders an editable Section select (:96) and Kind select (:104-111) when editing an EXISTING field and submits both (:60-61). The PATCH handler src/routes/api/forms.ts:189-217 validates them (it now passes {id, kind} into validateFieldDefInput per DEC-500) but repo.patchField's FieldPatch (src/server/repo/forms.ts:277-283) carries neither section nor kind, so patchField (:285-300) silently discards them and the route returns 200 with the UNCHANGED field. A producer changes Text -> Dropdown, clicks Save, sees no error, and nothing happened; worse, in that same request options ARE persisted (:212, :292) onto a field whose kind is still text. A visible control that does nothing is the opposite of "fail loudly" and of "legible over configurable". Decision: section becomes freely patchable (it is pure grouping). kind becomes patchable ONLY while the field has zero stored answers -- existing submission_answer rows were validated against the OLD kind and a number answer under a now-dropdown field fails every subsequent validateAnswers -- so the route counts answers via the EXISTING repo.describeFieldDependents(db, formId, fieldId).answerCount (no second counter) and 409s naming the count when it is non-zero, the same shape DEC-300 already uses for a field delete with dependents. When kind changes away from 'dropdown', patchField clears optionsJson to null in the same write (options exist only on dropdowns, DEC-500); when it changes TO 'dropdown', DEC-500's effective-kind rule already forces non-empty options in the same request. Locked built-in fields reject kind/section changes outright, exactly as they already reject a required change (:197-199).

## Amendment (wave 54): a field's `section` is not pure grouping — it is the anonymisation boundary, so a section change is refused while answers exist, exactly as a kind change is, and the field editor names the consequence

DEC-505's own text rules that "section becomes freely patchable (it is pure grouping)". That was true when nothing read `section`; it is false now — src/routes/review/reviewer.ts:301-302 splits speakerAnswers from sessionAnswers on `section` and DEC-018 anonymises only the first, so `section` decides what an anonymised reviewer may see. Verified on main: src/routes/api/forms.ts:245-254 refuses a `kind` change when answerCount > 0 and then, twelve lines later at :262, writes `section` through patchField with no dependents check at all. Flipping a collected "Your employer" question from `speaker` to `session` moves already-answered rows out of the anonymisation strip mid-plan, silently, with reviews already submitted under the promise. This is the sibling test in guard form: two properties of one row, one guarded and one not. RULING: this amendment overrules the "pure grouping" clause. A section change with collected answers is refused with the same 409 shape as the kind change, from the SAME describeFieldDependents result (one query, two guards — never a second counter), and the refusal names the count and the reason rather than a bare "not allowed". Locked built-ins keep refusing outright (unchanged). Second half of the rule, at the authoring surface: the field editor's Section select carries a consequence line stating what each section means for anonymised review, so a producer choosing the default is choosing it knowingly instead of discovering it from a reviewer.

## Amendment (wave 57): removing a select/radio OPTION that already has collected answers is refused with the same conflict shape as a kind or section change

The wave-54 amendment refuses a `kind` change and a `section` change on a field with collected answers, both because they orphan data. Removing an option does exactly the same damage and is unguarded: src/routes/api/forms.ts:281 writes `options` through patchField with no dependents check, and src/forms/validate.ts:118 then rejects any answer whose stored value is not in `field.options` — so a speaker who opens their own submission to edit an unrelated field is refused on a question they never touched, and the stored answer is unreachable. Additions and reordering are harmless and stay allowed; only the disappearance of an ANSWERED option value is refused, 409, naming each blocked option and its answer count, saying nothing was changed, and offering the way out. This keeps DEC-300's delete-and-re-create as the deliberate, cascading path for genuinely destructive edits.

## Amendment (wave 49): a patch that invalidates a sibling's stored rule is a conflict, not a silent hide

Verified in-tree, not inherited: PATCH /api/v1/fields/:fieldId (`src/routes/api/forms.ts:298-370`) refuses an option removal only when COLLECTED ANSWERS reference it (:344-359, `countAnswersByOptionValue`) and a kind/section change only when `answerCount > 0` (:319-337). It never consults sibling fields whose `rule.value` targets that option or whose rule is typed by this field's kind — `describeFieldDependents`'s dependentLabels is read ONLY on DELETE (:398). `validateFieldDefInput` at :300 validates this field's OWN rule against siblings, never the siblings' rules against this field's new shape. The consequence is real and traced: `validateRuleReference` (`src/forms/builder.ts:90-94`) treats a dropdown rule.value outside the trigger's options as invalid, and `resolveHiddenFieldIds` (`src/forms/visibility.ts:66`) then hides the dependent question for EVERY answer — including a `required` one — permanently on the public CFP, with no 409 and no rule cleanup. RULING: the PATCH door re-validates every sibling rule that targets this field against the field's EFFECTIVE post-patch definition and 409s naming the dependent labels, in the same conflict shape DELETE already uses; `?cascade=1` clears exactly those now-invalid sibling rules in the same write and reports `clearedRules`. One check covers both triggers (option removal and kind change) because both are the same invariant violation.

## Amendment (wave 53): a refusal that ships an escape hatch must be reachable from the UI — the CFP field-EDIT cascade has no SPA half

The wave-49 server fix landed and is correct (`src/routes/api/forms.ts:361-397`): a PATCH whose post-patch shape invalidates a sibling's visibility rule 409s with `fields.dependents` and completes when retried with `?cascade=1`, clearing exactly those rules and reporting `clearedRules` in the 200 body. But `app/src/pages/forms/FormsPage.tsx:118-124` calls `apiPatch('/fields/:id', input)` with no conflict handling at all, and `FieldModal` (`:107-116,142`) catches the throw and paints the message into a banner. The organizer is told what is wrong and given no way to proceed — a dead end on the CFP builder, the surface docs/clarifications.md:41 calls the product's front door. The DELETE path in the SAME file (`:132-147`, `:399-417`) already carries the correct two-step grammar. RULING: the edit path mirrors it. A `conflict` carrying `fields.dependents` opens a ConfirmDialog whose confirm re-issues the PATCH with `?cascade=1` and then REFETCHES the form (the server cleared sibling rules; local state still shows them, and a stale rule is exactly the silent divergence DEC-505 exists to prevent). A `conflict` WITHOUT `dependents` (collected answers on a kind/section change, an option with answers) is terminal by design — it keeps the banner and offers no retry, because the server offers no cascade for it.
