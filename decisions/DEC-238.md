# DEC-238: Mailer failure taxonomy: system sends are per-recipient best-effort; organizer-triggered batch sends return a structured {sent, failed} summary, never a 500

The mailer port logs an email_log row with status 'error' before rethrowing (src/mail/email-binding.ts:60-82), so callers own the failure policy. Three classes: (1) system-initiated sends — public submit confirmation, cron due reminders (sendDueRemindersForEvent), account-creation notices — catch per recipient, console.error, continue; one bad recipient must never abort the loop or the primary action. (2) organizer-triggered batch sends — comms compose/send, plan remind, CRM bulk email, bulk task reminders — catch per recipient and respond 200 with {sent: n, failed: [{email, message}]} so the organizer who clicked send sees exactly what failed; a provider failure is never a 500. (3) internal invariant violations still throw. This forecloses both silent swallowing and all-or-nothing aborts.

## Amendment (wave 3): compose/send refuses to deliver the same message to the same address twice within the hour, and step 4 is a {sent, skipped, remaining} report

DESIGN-RULINGS item 1 (B1, the highest-leverage owed seam) specifies that the bulk-communications flow 'end on a result panel that reports {sent, skipped, remaining} as three plain lines'. On main, src/routes/comms/send.ts returns `{ sent, failed }` with no notion of a skip, and ComposeWizard.tsx:1047 says so in a comment — honestly, since a fabricated field is worse than a missing one. But the field is missing because the MECHANISM is missing: a gate-7 probe re-sent the same template to the same recipients 40 seconds apart and both were emailed again, 0 skipped. Task reminders already hold this line (`MANUAL_DEDUPE_WINDOW_MS` in src/server/repo/tasks/reminders.ts), and DESIGN-RULINGS item 14 blesses the EMAILED marker precisely BECAUSE 'the one-hour dedupe window means a second click does nothing'. The product's most consequential fan-out is the one surface with no such window. RULING: (1) The dedupe key is (eventId, lower(toEmail), exact rendered subject) over `email_log` rows with status 'sent' whose `sent_at` is within COMPOSE_DEDUPE_WINDOW_MS = 3_600_000, declared once in a new pure module `src/domain/comms-dedupe.ts` and imported by the route — keyed on the MESSAGE, not on templateId, so it is independent of DEC-846's provenance work and catches ad-hoc re-composes too. (2) A matched recipient is not emailed; it appears in a new response field `skipped: { email, name, submissionId, reason: 'already_sent_recently', retryAtIso }[]`, where retryAtIso = last sent_at + window. (3) The wire keeps `failed` under its existing name — it has readers — and step 4 renders the ruling's three plain lines: sent, skipped, remaining (remaining is the failed set: a recipient the product still owes a message). (4) There is deliberately NO `resend` override in this wave. An override flag that no surface sets is a parsed-and-discarded field, and the honest escape already exists and is disclosed: change the subject, because a different subject is a different message. If the operator later wants a one-click override it lands as its own amendment with the control that sets it. (5) A skip is never silent — every skipped recipient is named with the time it becomes eligible again, which is what makes this a disclosure rather than a swallowed write.

## Amendment (findings wave 5): step 4's three facts are carried by the framed report's own parts, not by a counts stack beside it

The wave-3 amendment implemented DESIGN-RULINGS item 1 while that ruling still read "needs frames (owed)" and specified {sent, skipped, remaining} as three plain lines. The frame has since landed: docs/design/Chautauqua Comms.dc.html :495-536 draws the send report as an eyebrow + "21 of 23 speakers were emailed" headline, a TEMPLATE / SUBJECT THEY SAW / SENT definition grid between rules, a "Two were skipped" section naming each held-back recipient with its reason and retry time, and a footer row pairing "Compose another" with "Back to Comms". A frame outranks the interim prose it was owed for. RULING: sent lives in the headline, skipped in its own named section, remaining in the existing SendFailures block — so the standalone .chq-comms-send-report-counts paragraph is deleted rather than rendered twice. No count in this report is recomputed client-side from a preview: every number still comes off sendResult.

## Amendment (findings wave 14): the CRM bulk-email send is the SAME dedupe class as compose/send — one window, one key, plus an intra-batch address collapse

DEC-238's wave-3 amendment gave POST /compose/send a (event, lower(email), exact rendered subject) one-hour window against email_log (src/routes/comms/send.ts:112 loadRecentlySent + src/domain/comms-dedupe.ts). POST /api/v1/contacts/bulk-email (src/routes/api/contacts/bulk-email.ts:227) is the same organiser-triggered batch class and has NEITHER that window nor any per-address collapse: parseBoundedIdArray dedupes only by contact id, so a retried or double-submitted batch re-mails every recipient, and two contact rows sharing one address — the exact state the duplicate-merge tool exists to fix — each receive a byte-identical message. RULING: bulk-email reuses repo.loadRecentlySent and domain/comms-dedupe's dedupeCutoff/dedupeKey/retryAtMs verbatim (never a second window constant, never a second key shape), and additionally collapses to the FIRST contact per lower-cased trimmed address within the batch, because a bulk email is contact-scoped (DEC-026) and renders the same subject for everyone — unlike compose, whose per-submission subjects legitimately differ. The response gains `skipped: number` — a COUNT, matching app/src/lib/sendResult.ts's SendResult contract that BulkEmailModal already renders through describeSendResult, so the SPA needs no change — NOT the per-recipient array compose/send returns, which exists only because its own report is per-submission.
