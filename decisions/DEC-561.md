# DEC-561: The reviewer's submission view shows the submission — named speakers, the CFP's custom answers in form order, and their own stored evaluation; the queue keeps completed items instead of erasing them

J4's whole surface is the reviewer's scorecard, and it is currently broken in four ways that compound. (1) `listSpeakersForSubmission` (src/server/repo/review/submissions.ts:325-339) returns `{contactId, firstName, lastName, email, company, title}`; app/src/pages/review/Scorecard.tsx:172 renders `submission.speakers.map((s) => s.name).join(', ')`. On every NON-anonymized plan the header literally reads "Speakers: undefined" — and app/src/pages/review/types.ts:176 declares `{contactId, name}[]`, a shape the server has never sent, while Scorecard.render.test.tsx:68 mocks that fiction and therefore passes. That is the standing rule in its sharpest form: a render test whose MOCK is invented proves nothing. (2) The route ships `sessionAnswers`/`speakerAnswers` (src/routes/review/reviewer.ts:168-169) and the SPA type declares `answers?: Record<string, unknown>` (never sent) — so the Scorecard renders NO custom answer at all. A producer's CFP questions (J1: text/long-text/dropdown/checkbox/number) are invisible to the committee that is supposed to judge them; ABS-03 (weight 3) requires all three field types to render and store on the reviewer side. (3) `listAnswersForSubmission` (:351-370) has no ORDER BY though `form_field.position` is the authored order every other reader honors (repo/submit.ts:85, repo/forms.ts:109, exports/submissions.ts:169) — the questions would shuffle even once rendered. (4) `buildReviewerQueue` (src/domain/evaluation.ts:347-361) FILTERS OUT everything this reviewer already rated, so `alreadyRatedByMe` in the emitted item is permanently false, the SPA has no completed state, and the route never returns `myEvaluation` even though `getEvaluation` exists — a reviewer cannot reopen a submitted review, see their stored 4/2/Accept, or revise it. ABS-S3 steps 5-6 demand exactly that ("reopen the submitted review... screenshot the queue showing both items complete"). Decision, one contract for two workers: GET /api/v1/review/submissions/:id returns `{id, ref, title, description, sessionAnswers: {fieldId,label,kind,value}[], speakers?: {contactId,name,company,title}[], speakerAnswers?: same, criteria, myEvaluation?: {scores, comment}}` — `name` is `${firstName} ${lastName}`.trim(); `email` is NEVER sent to a reviewer through this endpoint (organizers read the admin submission detail); answers are ordered (form_field.position asc, form_field.id asc); `myEvaluation` is this reviewer's row for `plan.currentRound`, omitted when absent; `anonymizeForReviewer` keeps its exact two-key strip so an anonymized payload still has NO `speakers`/`speakerAnswers` KEY AT ALL (scripts/walkthrough/review.ts:475 asserts the raw text, keep it passing). GET /api/v1/review/plans/:id/queue keeps already-rated items with `alreadyRatedByMe: true`; `buildReviewerQueue` stops filtering and orders by (alreadyRatedByMe ? 1 : 0, ratingsCount asc, submissionId asc) — fewest-ratings-first is preserved for everything actionable, completed work sinks to the bottom instead of vanishing; the route's max-evaluations filter is unchanged (an unrated item at the cap is still dropped, a rated item is always kept). The regression bar is the words on the screen: no rendered reviewer surface may contain the string "undefined", and the mocks in every review render test are corrected to this payload, never the assertions loosened.


## Amendment (wave 60) — one answer-value text module, two declared renditions; no surface prints [object Object]

Four implementations answer 'render one CFP answer value as text', and they disagree exactly where nobody looked. app/src/pages/review/answerText.ts:7 (scorecard): ', ' lists, Yes/No, em-dash for empty, JSON for objects. app/src/pages/submissions/columns.ts:56 (the J3 'any form answer as a column' table): ', ', Yes/No, bare '' for null, and `String(value)` for an object — '[object Object]' on screen. src/server/repo/exports/submissions.ts:59: '; ' lists and 'true'/'false' booleans — so a multi-select answer reads 'A, B' on screen and 'A; B' in the CSV a producer is reconciling against it, and a checkbox reads 'Yes' on screen and 'true' in the file. src/server/repo/tasks/response-detail.ts:32: a fourth mixture. RULING: src/domain/answer-text.ts owns `answerDisplayText(value, opts?: { empty?: string })` (', ' lists, 'Yes'/'No', caller-declared empty token defaulting to '') and `answerExportCell(value)` (kept at '; ' because that IS the export file's declared list grammar for tracks/speakers/emails, 'true'/'false', '' for missing). Both render a non-array object as JSON, never '[object Object]'. All four sites import the owner; a scan bans a second declaration. The two grammars stay two because a machine file and a screen legitimately differ — but they are now named once each instead of guessed four times.
