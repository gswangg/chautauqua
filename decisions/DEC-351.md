# DEC-351: /plans/:id/progress and /plans/:id/remind stop loading whole-round evaluation rows; /results keeps the full load because ranking genuinely needs the scores

DEC-346 shed the whole-round evaluation load from the reviewer-facing queue but scoped itself there deliberately. The two producer-facing routes still call repo.listEvaluationsForPlan — which is a bare `db.select()` with no column list (src/server/repo/review/evaluations.ts:34) — at src/routes/review/plans.ts:221 (/progress) and :309 (/remind), and then use the rows for exactly one purpose: building Map<reviewerId, Set<submissionId>>. At SPEC §0's reviewer scale (2,000 submissions × 10–50 reviewers) that drags every scores_json blob and comment of the round into the isolate to compute two integers per reviewer. That is the same shape DEC-333 already ruled a stage-1 product defect rather than stage-2 tuning, and it is now observable on local D1 because task-w20-d raises the perf seed's evaluation count. Contract: add `listCompletedPairsForPlan(db, planId, round): Promise<{ reviewerId: string; submissionId: string }[]>` selecting ONLY those two columns with the round constrained in SQL (so the routes' redundant `.filter(e => e.round === round)` disappears), call it from both routes, and leave listEvaluationsForPlan untouched for buildResults at src/routes/review/shared.ts:252, which legitimately needs scores_json to rank. This is load shedding with NO observable difference: both routes' JSON must stay byte-identical, and any test whose assertion has to change is evidence the change went too far (DEC-346's rule). The single assertion that must be RE-POINTED rather than weakened is test/review-rounds.test.ts's listEvaluationsForPlan call-site sweep; per DEC-329 it may narrow what it fetches but must still assert every remaining call passes `round`.
