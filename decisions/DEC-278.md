# DEC-278: Onboarding auto-creation fires at the LAST of (submission accepted, participant becomes active); one idempotent ensureOnboardingTasks with three call sites; 'invited' and 'declined' participants are excluded

swyx's must-have is that acceptance auto-creates the speaker record, the session and the onboarding tasks. The shipped trigger is one-shot: runAcceptancePlanning (src/server/repo/submissions/status.ts:107, private) runs only inside updateSubmissionStatuses, plans for EVERY participant regardless of invite state, and nothing anywhere plans for a participant added to an ALREADY-accepted submission (src/server/repo/participants.ts:67 inviteParticipant just inserts a row). Because getOnboardingGrid (src/server/repo/tasks.ts:117) is built from task_assignment rows joined to contacts, such a speaker is not merely task-less -- they never appear on the who-owes-me-what dashboard at all, which is precisely the crack SPEC section 2.3 forbids. The correct rule is a join of two conditions rather than a single event: a (submission, contact) pair owes onboarding once the submission is accepted AND the participant is active, whichever happens last. Implement as one exported idempotent ensureOnboardingTasks(db, eventId, submissionId, contactIds|null, now) called from (a) the acceptance transition, (b) the organizer invite route when the submission is already accepted and the new row is active, (c) the portal invitation-accept transition when the submission is already accepted. 'invited' means the question is still open and 'declined' means the answer was no -- neither owes a hotel form -- so both are excluded, which also means the acceptance path stops planning for them. The active-status literal set is defined twice on purpose (a TS predicate in src/domain/acceptance.ts for this layer, DEC-274's SQL predicate for the query layer); they must carry the identical two literals and each cites the other. No mailer import may enter any of these paths (DEC-009).

## Amendment (wave 58): acceptance planning fires on EVERY entry into 'accepted'; accepted_at is still stamped exactly once — the timestamp and the trigger are two facts, not one

src/domain/status.ts:58 derives BOTH the accepted_at stamp and the fireAcceptance trigger from the single predicate `current.acceptedAt === null`, and accepted_at is never cleared on un-accept (correct, per DEC-009). The compensating guards (src/routes/api/submissions.ts:481, :545, src/routes/portal/index.tsx:639) only fire when the submission is CURRENTLY accepted. So accept → un-accept → add co-speaker → re-accept creates ZERO onboarding tasks for that speaker: they are invisible on the J6 who-owes-me-what dashboard forever, which is exactly the question SPEC §5 says that dashboard exists to answer. Ruling: split the two facts. `fireAcceptance = next === 'accepted' && current.status !== 'accepted'` (every true ENTRY into accepted, and planning is already idempotent on (contact, task-title) so a re-entry is a no-op when nothing changed); `setsAcceptedAt = next === 'accepted' && current.acceptedAt === null` keeps the timestamp write once-only, so a re-accept must NOT overwrite the original accepted_at with `now`. DEC-079's ordering is preserved: planning still runs before any firing row's UPDATE.
