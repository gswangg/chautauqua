# DEC-008: Form engine: field model, conditional visibility, server-side validation

FormField = { id, section: 'session'|'speaker', kind: 'text'|'long_text'|'dropdown'|'checkbox'|'number'|'file', label, helpText?, required, position, options?: string[], rule?: { fieldId, op: 'eq'|'ne'|'in', value } }. rule controls visibility (show when matched) — basic show/hide only, per swyx "conditional fine for now". Locked built-ins: session Title + Description (required, non-removable), speaker first/last/email. Answers stored one row per field in submission_answer with value_json. Validation is server-side always and never trusts client rendering: required enforced only for VISIBLE fields, answers for hidden fields stripped, dropdown values must be members of options, numbers coerced/validated. Validation returns structured { ok } | { errors: Record<fieldId, message> } — user input errors are expected external input, not exceptions (per house style, exceptions are for violated invariants). Close-date lock enforced server-side: past form.close_date rejects new submissions and edits by non-accepted submitters; accepted speakers keep editing.

## Amendment (wave 45): the CFP builder's question list is the whole question set the public form asks, Track included

app/src/pages/forms/FormsPage.tsx never mentions Track, yet the public form renders a REQUIRED single-choice Track question (TrackChoices, sourced from the event's tracks rather than from `form_field`). The builder is the organiser's authoritative view of what the form asks, so a question it cannot see is a second reader of one form — the exact class this codebase keeps re-filing. Decision: the builder synthesises a Track row from the event's tracks and renders it in the locked-row treatment already used for Title/Abstract — Single choice · REQUIRED · one option per track — not editable, not deletable, not reorderable, positioned immediately after Abstract per frame 04. It is a VIEW of the event's tracks, never a new form_field row and never a write path: editing tracks stays in Settings. A scan-lock test asserts every question the public form renders has a row in the builder, so the next synthetic question cannot go missing the same way.
