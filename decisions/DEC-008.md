# DEC-008: Form engine: field model, conditional visibility, server-side validation

FormField = { id, section: 'session'|'speaker', kind: 'text'|'long_text'|'dropdown'|'checkbox'|'number'|'file', label, helpText?, required, position, options?: string[], rule?: { fieldId, op: 'eq'|'ne'|'in', value } }. rule controls visibility (show when matched) — basic show/hide only, per swyx "conditional fine for now". Locked built-ins: session Title + Description (required, non-removable), speaker first/last/email. Answers stored one row per field in submission_answer with value_json. Validation is server-side always and never trusts client rendering: required enforced only for VISIBLE fields, answers for hidden fields stripped, dropdown values must be members of options, numbers coerced/validated. Validation returns structured { ok } | { errors: Record<fieldId, message> } — user input errors are expected external input, not exceptions (per house style, exceptions are for violated invariants). Close-date lock enforced server-side: past form.close_date rejects new submissions and edits by non-accepted submitters; accepted speakers keep editing.

## Amendment (wave 45): the CFP builder's question list is the whole question set the public form asks, Track included

app/src/pages/forms/FormsPage.tsx never mentions Track, yet the public form renders a REQUIRED single-choice Track question (TrackChoices, sourced from the event's tracks rather than from `form_field`). The builder is the organiser's authoritative view of what the form asks, so a question it cannot see is a second reader of one form — the exact class this codebase keeps re-filing. Decision: the builder synthesises a Track row from the event's tracks and renders it in the locked-row treatment already used for Title/Abstract — Single choice · REQUIRED · one option per track — not editable, not deletable, not reorderable, positioned immediately after Abstract per frame 04. It is a VIEW of the event's tracks, never a new form_field row and never a write path: editing tracks stays in Settings. A scan-lock test asserts every question the public form renders has a row in the builder, so the next synthetic question cannot go missing the same way.

## Amendment (findings wave 10): a never-seeded event is the conformance baseline — the seed is a demo, not the product

The session-format defect existed for many waves behind a full green suite because every test that needed a working CFP reached for the seeded demo event, where the literal field id happens to exist. A constant only the seed satisfies is a demo, not a product. RULING: the repo carries a standing no-seed conformance guard — one test that provisions an org, an organiser, an event and its default form from scratch, with no fixture ids, no persona names and no invocation of scripts/seed.ts, and walks the chain a real customer walks: default form -> public CFP GET -> public CFP POST -> accepted -> onboarding tasks -> public sessions read. Anything that only works because a row was seeded fails there. The guard is additive to, not a replacement for, the J1-J12 walkthrough; and it is the file future waves extend when a new surface is added, rather than each wave re-discovering the same class by hand.

## Amendment (wave 79): form_field.options_json and rule_json get one validated parser, and a malformed rule fails loudly instead of hiding a question

The two JSON columns that decide what the public CFP asks and which questions are conditional are hand-parsed at four independent sites — `src/server/repo/submit.ts:153-154`, `src/server/repo/portal-edit.ts:144-145`, `src/server/repo/forms.ts:52-53`, `src/server/repo/form-roles.ts:44` — every one an unvalidated `JSON.parse(...) as string[] / as FormFieldRule`, and the four already disagree on the empty answer (`undefined` at three sites, `[]` at the fourth). This is the third JSON column family in four waves to show the fracture (social_links w76, custom_fields w77, branding w78 in flight), and it is the one SPEC §6 leans on hardest: "Public submission endpoint validates against the server's form schema (required, types, conditional visibility) — never trusts the client's rendering." The failure mode is silent, not loud: a rule object missing `fieldId` makes `resolveHiddenFieldIds` (`src/forms/visibility.ts:56`) take the "rule names a field that isn't in this list" branch and HIDE the question — a required question disappears from the form with no error anywhere. Ruling: one pure-core parser module owns both columns, validates the parsed shape (options = array of strings; rule = {fieldId:string, op ∈ FORM_FIELD_RULE_OPS, value present}) and throws a NAMED error on anything else, matching `roundMetaFor`'s discipline rather than `criteriaForRound`'s silent `?? base`. Sites that want `[]` rather than `undefined` express that at the call site, where the difference is visible.
