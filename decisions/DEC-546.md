# DEC-546: /dev/mailbox is organizer-only and scoped to the viewer's org — the wave-18 "public by design" disposition rested on a false premise

docs/verification-log/task-w18-d-route-authz-inventory-stage1.md:230-232 classifies all three /dev/mailbox routes PUBLIC-BY-DESIGN because they are "single-tenant local dev tooling ... no secrets present in Stage 1". That premise is false: the mailbox renders every email body verbatim, and two of those bodies carry one-time /claim/<token> password-setup links (minted at src/routes/public/submit.tsx:759 and src/routes/comms/send.ts). DEV_MODE=1 is exactly the configuration stage 1 ships and grades in, guardDevMailbox (src/server/app.ts:59-68) checks only that flag, and neither route reads c.var.auth — so any anonymous visitor, or any speaker, can page every message in the instance and take over any account. That is a cross-account credential leak, which is the class SPEC §6 ("authz middleware on every admin/API route ... no IDOR") and J7 ("only their own content, ever") forbid outright. listEmailLog is additionally called with no org filter at all, so even a legitimate organizer sees other orgs' mail. Decision: (a) the DEV_MODE existence gate stays FIRST and unchanged (404, never 403 — DEC-005 existence-hiding), and a second gate runs behind it: no session redirects 302 to /login (mirroring rootRoutes' /admin), a non-organizer session gets ApiError('forbidden'). (b) EmailLogListParams gains `orgId?: string` (filtering schema.event.orgId through the join listEmailLog already has) and getEmailLogById takes an `orgId` scope argument; all three mailbox routes pass c.var.auth.orgId, so the list, the detail page and the .ics download are org-scoped — an out-of-org emailId 404s. (c) src/routes/root.tsx's landing-page "Dev mailbox" link renders only when dev mode is on AND the viewer is an organizer, so the nav never advertises a dead end. (d) The regression bar is authz, not the mount predicate: with DEV_MODE='1', anonymous → 302, speaker → 403, reviewer → 403, organizer → 200, and an organizer of org B gets 404 on an org-A message id and on its /ics.

## Amendment (wave 45): a manifest row's declared role is DERIVED from the route's own guard, never hand-declared — /dev/mailbox is organizer, not public

guardDevMailbox (src/server/app.ts:90-104) redirects an anonymous caller to /login and 403s a non-organizer, yet app/src/routeManifest.ts:237 and :251-255 declare `/dev/mailbox` and `/dev/mailbox/seed_email_log_0001` as `role: "public"`, and scripts/render-sweep.ts:138,141 repeats both as public in MOBILE_ROUTE_MANIFEST. The render-sweep therefore visits all three in an anonymous context, follows the 302, and grades the sign-in page: three route-visits (one desktop, two at 390px) that name the dev mailbox and verify nothing about it — no console errors observed, no overflow measured, on a surface that IS in the walkthrough's evidence path for password reset. Ruling: both rows become role "organizer" (the desktop pass already logs one in; ADMIN_MOBILE_ROUTE_MANIFEST derives the mobile pass from ROUTE_MANIFEST automatically, so the two hand-copied MOBILE_ROUTE_MANIFEST rows are deleted rather than re-roled — the public mobile pass has no organizer context by construction). And because a hand-declared role is exactly the fact that rotted, the parity is scanned, not trusted: a derivation test reads every `app.use("<pattern>", ...)` guard in src/server/app.ts whose body tests `auth.role !== "<role>"` and fails naming any manifest row whose path matches that pattern while declaring a weaker role.
