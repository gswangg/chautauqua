# DEC-550: Every GET route is authz-gated or on a declared public-by-design list, proven by an anonymous probe over the composed app's own route table — not by a markdown inventory

The only authz manifest this codebase has is prose: docs/verification-log/task-w18-d-route-authz-inventory-stage1.md hand-lists 157 routes and 22 "public by design" exceptions. DEC-546 shows what that costs — three of those 22 entries were wrong, and nothing failed. test/route-authz-inventory.test.ts probes three representative rows; test/w10-verify-no-blanket-wildcard.test.ts probes one leak shape. Neither enumerates. This is the standing rule ("hand-listed manifests desync — enumerate in a test"; "glob boundary validators rather than hand-picking call sites") applied to the one manifest where being stale is a data breach. Decision: a new test composes every sub-app src/index.ts mounts, in src/index.ts's exact order and including guardDevMailbox, over a db stub that THROWS on any access and an env of `{}` (DEV_MODE unset, so the dev-mailbox routes correctly 404 and DEC-546's dev-mode-on authz is covered by its own test instead). It enumerates the composed app's own route table, probes every GET with no session, and requires each route to either (a) appear in an exported PUBLIC_BY_DESIGN list carrying a one-line reason, or (b) answer without ever touching the db. The allowlist is asserted EXACT in both directions: an unmatched entry is as much a failure as an ungated route, so a deleted public route cannot leave a permanent hole behind. A route may only be allowlisted if its own source documents it as intentionally no-login (citing its DEC); anything else is reported as a finding, never absorbed.

## Amendment (wave 18): the anonymous authz probe composes from src/index.ts's own source — a hand-typed mount list is not an enumeration

test/anonymous-route-probe.test.ts's header claims it 'composes every sub-app src/index.ts mounts, at the same prefixes, in the same order', and it is the codebase's ONLY exhaustive authz guard. Its buildAnonymousApp (line ~223) is a hand-copied list that omits six of the mounts src/index.ts actually registers — importRoutes, publicSurfacesRoutes, embedsRoutes, breaksRoutes, contentNoteRoutes, mailStatusRoutes (src/index.ts:52,55,57,59,62,63) — so those routes have never been probed while the guard reported green. This is the field guide's 'A GUARD THAT QUIETLY NARROWS IS WORSE THAN NONE' in its purest form, and the fix is the technique this repo already uses elsewhere (DEC-518, reused by test/ssr-link-targets-scan.test.ts): parse every `app.route("<prefix>", <ident>)` out of src/index.ts, resolve the identifier through that file's own imports, dynamically import the module, mount it at the exact prefix. The real exported `app` (src/index.ts:90) cannot be used here because the probe must inject a throwing db through middleware registered BEFORE the routes. RULING: the probe derives its mount list; the parsed-mount count is asserted against a floor so it can never silently narrow again; guardDevMailbox is invoked immediately before the devMailboxRoutes mount, as src/index.ts does.

## Amendment (wave 32): the runtime authz probe is not GET-only — every MUTATING registration must refuse an anonymous request without touching the db

DEC-550's probe (test/anonymous-route-probe.test.ts) composes every mount from src/index.ts's own source and probes GET only; its header even records that POST-only sub-apps were skipped. DEC-459's scan (test/route-authz-enumeration.scan.test.ts) covers all methods but matches guard NAMES in registration text. So the one shape this repo has already been bitten by — MIDDLEWARE SCOPE IS REGISTRATION ORDER, a use(prefix, guard) that reads as covering but does not cover at runtime — is invisible to both: the text scan passes and the runtime probe never issues the request. Ruling: a sibling runtime probe issues POST/PUT/PATCH/DELETE against every mutating registration in the composed table over the same throwing-db stub, and requires each to answer non-2xx WITHOUT any db access, or to appear in its own two-directional PUBLIC_BY_DESIGN_MUTATIONS ledger with a one-line reason citing the route's own DEC. A refusal from the CSRF guard counts as a refusal (nothing anonymous reached the db), but the probe also runs a pass with the CSRF header satisfied so authz is exercised in its own right.

## Amendment (wave 35): wrong-ROLE and no-role probes miss wrong-OWNER — the speaker portal gets its own same-role IDOR enumeration

DEC-550 established that authorization is proven by a probe over the composed app's own route table rather than a markdown inventory, and three such probes now exist: anonymous GET, anonymous mutation, and non-organizer role refusal over /api/v1. All three vary the ROLE or the absence of one. None varies the OWNER while holding the role fixed, which is precisely the shape SPEC §6 names ("object-level ownership checks on every fetch-by-id (no IDOR)") and precisely what external graders probe by hand (speaker2 fetching speaker1's task assignment and submission). Today's coverage of that population is a sample — test/task-file-access.test.ts, test/review-idor.test.ts — so a newly added /portal/:id route joins the app with no proof at all. RULING: a fourth probe, same technique and same two-directional ledger discipline, drives every portal registration carrying a path param as speaker B while the ownership resolvers return objects owned by speaker A, and requires each to refuse (403 for task assignments, existence-hiding 404 for submissions) with no write and no 500. The ledger is exact in both directions, so a new portal route carrying an id cannot ship unprobed, and a 2xx or 500 is a hole to fix in the route, never a ledger row to add.

## Amendment (wave 37): a byte-serving route's refusal carries a second signal — the object store is never asked for the foreign key

For routes that stream stored bytes (src/routes/files.ts, src/routes/portal/tasks.tsx, src/routes/portal/tasks/resources.tsx, src/routes/portal/profile.tsx), a status code alone does not prove the bytes stayed put: a handler can fetch the object and then discard it, or check a header-only condition after the fetch. The wave-35 portal probe got its second signal from a throwing db ('the store was never touched' doubles as 'performed no write'); the byte routes need the same discipline pointed at R2. The file probe therefore supplies an object-store stub that RECORDS every requested key and throws, so 'refused' means both the ledgered 4xx AND that the foreign key was never requested. This also keeps the DEC-551 nosniff/attachment work honest: those rules describe how bytes are labelled when serving is legitimate; this rule is about never reaching that point for another tenant's object.
