# DEC-312: SQL WHERE clauses are normative; test doubles model the predicate, never the reverse

src/server/repo/tasks.ts:352-356 states in a comment that `listAcceptedContactIds` filters invite status in application code 'because the repo-layer fakeDb test harness can't evaluate a WHERE predicate' — production data-access strategy shaped by a test double's limitations, which inverts the dependency and is the one standing review-lens finding I could not refute. The concrete cost is that the function loads every participant row of every accepted submission (~3000 rows at the 2k perf corpus) to return a deduped contact-id list, which contradicts SPEC §7's 'server pagination + filtering on all admin lists' principle and the house rule against defensive shaping. The blast radius is smaller than the comment implies: fakeDb is defined per test file (test/tasks-assign-all-accepted-invite-gate.test.ts:17), not shared, so the fix touches one repo function and one test file. Move the filter into the WHERE using `ACTIVE_INVITE_STATUSES` (already exported at src/domain/acceptance.ts:80, so the tuple and `isActiveParticipant` cannot drift), and upgrade that one file's double to evaluate the condition so its two assertions keep passing for the right reason. No other test file's double may be refactored this wave — a general predicate-evaluating harness is a separate decision if anyone ever needs it.
