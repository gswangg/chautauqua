# DEC-290: Event-roster add and roster CSV import ride the existing add-to-event push; no new roster table, no new route file — `eventId` becomes an optional field on the two contact endpoints that already exist; phone and bio become first-class import targets

SPK-03's gap (task-w4-e-c2-rubric-coverage.md:164) is that importing onto an event roster takes two steps. The fix must not fork the contact->speaker ladder SPEC §5 protects. src/server/repo/contacts.ts:928 pushContactToEvent already does exactly the right thing — creates the submission as 'pending' then drives it through updateSubmissionStatuses so the DEC-009 acceptance planner runs, the contact gets onboarding tasks, appears on the Speakers grid, and NO email is sent — so roster add/import is defined as 'the existing import/create, then that push, per contact'. Therefore: `POST /api/v1/contacts/import` and `POST /api/v1/contacts` each accept an OPTIONAL `eventId`; when present the event is org-checked (404 if not) and every created-or-updated contact that is not already an active roster member is pushed. Idempotency uses listAcceptedContactIds(db, eventId) from src/server/repo/tasks.ts:274 (already DEC-283-gated to ACTIVE participants) as the skip set, so re-importing the same CSV never creates a second placeholder session. No new tables, no new route file, no src/index.ts mount edit, and hence no new /api/v1 path for the docs tripwire to police. Separately: docs/fixtures/speakers.csv carries a `bio` column and mapImportRow's switch (src/domain/contacts.ts:350) has no `bio` or `phone` case, so a mapped bio either throws 'unknown target field' or is silently ignored — both wrong for a speaker roster where bio is the headline field. `phone` and `bio` join the import target allowlist on BOTH sides (src/domain/contacts.ts and app/src/pages/contacts/csv.ts STANDARD_IMPORT_FIELDS) and are carried through resolveImportUpsert's create values and update patch. ContactRecord/ContactInput already have both fields — no schema change, no migration.

## Amendment (wave 59): importing into the directory has no event side effects — attaching to an event is an explicit opt-in

VERIFIED on main: app/src/pages/contacts/ContactsApp.tsx:149-153 defaults `importEventId` to the page's current event, and ImportWizard.tsx:347/443/631 make 'Session title for this batch' REQUIRED whenever an eventId is present — so there is no way to import contacts into the CRM directory without minting an accepted session on the current event and pushing every imported row onto it. The server has always supported the directory-only shape (src/routes/api/contacts/import.ts:120-138 treats eventId as optional); only the SPA forces the coupling. This contaminated three graded areas at once (CRM, SPK, CNT). RULING: the import wizard treats the supplied eventId as a CANDIDATE, not an instruction. The match step carries an unchecked-by-default control, 'Also add these people to <event> as accepted speakers'; the session-title field, its required-ness, the preview guard, the disabled-primary blocker hint and the eventId/sessionTitle request keys all hang off that control being ON. With it OFF the request body carries neither key and the import writes contacts only. DEC-810 is unchanged and unweakened: when the opt-in IS on, the batch title is still required, still collected in the step where the event is already chosen, and still names one shared session.
