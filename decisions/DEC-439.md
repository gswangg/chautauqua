# DEC-439: The three measured SPEC §7 budget misses are stage-1 product defects, and each is fixed by shrinking what one request loads

docs/verification-log/task-w13-d-perf-smoke-stage1.md ended RESULT: FAIL with three open items and no owner: `plan results (page 1)` 36-92ms against a 50ms read budget (FAILed outright on 2 of 4 runs), `reviewer queue` 23-113ms against the same budget, `schedule.ics (bare)` 80-216ms against a 150ms public budget. Wave 14 took none of them (its perf lane was another measurement lane). SPEC.md:331-332 is unambiguous that an over-budget route "is a bug (waterfall, N+1, oversized payload), not a tuning opportunity", and SPEC.md:36 ranks performance FIRST, ahead of feature completeness. I read all three call paths: every one is the same shape -- load the whole plan/event, then slice. resolveReviewerSubmissions (src/server/repo/review/submissions.ts:110-119) loads every plan-scoped submission plus every plan_reviewer row and recomputes all twelve reviewers' assignments in JS to answer one reviewer's queue; buildResults (src/routes/review/shared.ts:251-293) loads ~2,000 submissions, a second whole-event submission_track scan whose trackIds it never reads, and ~6,000 evaluation rows via `db.select()` (SELECT *, comment blobs included) to return a 50-row page. The fix in every case is to load less, not to restructure the product: the response shapes, the ranking, and the pure-core semantics stay byte-identical. These are stage-1 defects, not stage-2 perf tuning (DEC-333 already settled that classification).

## Amendment (wave 62): "cost scales with THIS reviewer's slice" is a claim about a SQL LIMIT, not about a WHERE clause — the reviewer-scoped reads are ordered, capped and loud too

DEC-439's promise is that the reviewer queue costs proportional to one reviewer's slice rather than the whole plan. The WHERE clauses deliver that; the LIMITs were never written. resolveReviewerSubmissions (src/server/repo/review/submissions.ts:254-257) issues its `matched` query with no ORDER BY and no LIMIT — sitting fifteen lines below buildPlanScopeConditions and ninety below the sibling that DOES refuse loudly — and its own plan_reviewer read at :235-238 is unbounded, which matters because a per-submission reviewer scope writes one plan_reviewer row per submission. getReviewerScopeTrackId (src/server/repo/review/reviewers.ts:154-158) and listPlanIdsForReviewer (:167-171) are unbounded on the same table for the same reason. The route above them (src/routes/review/reviewer.ts:212-214) then slices in JS and reports the FULL array length as total — that slice is blessed by DEC-466 because the fewest-ratings-first order genuinely needs the whole set materialized, which is precisely why the SET is what has to be bounded. A cap with no ORDER BY is a nondeterministic truncation, so ordering and capping land together; the refusal message names the cap and tells the organizer to narrow the scope, matching listPlanFilteredSubmissions' wording exactly rather than inventing a second voice. This decision is separate from DEC-346's so the two lanes amend different files.
