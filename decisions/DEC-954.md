# DEC-954: One slot predicate on the compose preview, and a blocked send is disabled, not narrated

app/src/pages/comms/ComposeWizard.tsx computes two different answers to one question. Line 593 prints r.scheduled — DEC-912's unconditional slot flag, set server-side at comms.ts:459 from icsScheduleMap.has(...) — while line 359 computes noSlotCount from `!r.ics`, and the server only attaches `ics` when attachIcs was true on THAT preview call (comms.ts:505). Toggling 'Attach calendar invite' re-runs the preview (handleAttachIcsChange, :282), but when the ICS preflight rejects the batch the catch path sets icsUnscheduledIds and leaves `preview` STALE — so the screen simultaneously shows 'Scheduled' on every row, 'N of N have no slot yet', and a 'Send blocked' banner over a Send button whose only disabled condition is `busy` (:694). The banner then prints raw submission ids (:663) although every row in `preview` already carries its human `ref`. Three rules, one shape: (a) the slot predicate on this screen is r.scheduled and nothing else — noSlotCount = preview.filter(r => !r.scheduled).length, and the caption renders only when attachIcs is on AND that count is above zero; (b) a block blocks — while icsUnscheduledIds is non-null the Send button is disabled, because a control that stays live under a message saying it is blocked teaches the operator to ignore the message; (c) the block names the rows, resolving each id through `preview` to '<ref> — <name>' and falling back to the id only for a row the preview does not carry. No server change: this is entirely the client reading the flag the server already sends.
