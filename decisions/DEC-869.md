# DEC-869: A menu of states names each state's consequence, marks the one in force, and emphasizes the only item that sends mail

DEC-830 landed the participation MENU (app/src/pages/speakers/ParticipationMenu.tsx) and the eval mandate's remaining Speakers residue names what the frame (04-speakers--05-participation-open) has that it doesn't: per-item consequence captions, a NOW mark on the current state, an identity header, and olive emphasis on the action. Today one shared caption ('Invited and Declined hide this speaker from the public pages and pause their uploads') sits above four bare labels, and the current state is marked by CSS class alone — invisible to a screen reader and to anyone reading the row quickly. It is also imprecise: 'none' (Not invited) is an ACTIVE invite status, so a not-invited speaker IS on the public pages — the single caption cannot say that, and per-item captions must. Decision: PARTICIPATION_CONSEQUENCE_CAPTION is replaced by an exhaustive `PARTICIPATION_STATE_CAPTIONS: Record<InviteStatus,string>` (a Record so a new state cannot ship caption-less), with exactly this copy — none: 'Nothing has been sent. They still appear on the public pages.'; invited: 'Records that the invite went out. Hidden from the public pages until they confirm.'; accepted: 'Public pages and uploads are open.'; declined: 'Hidden from the public pages, uploads paused.' The panel opens with the speaker's name as an identity header; the four state items become role="menuitemradio" with aria-checked (they are a single choice, and the frame's NOW badge is that fact rendered) and the current one carries a NOW badge; 'Send portal invite' stays role="menuitem", keeps PARTICIPATION_FOOTER_CAPTION beneath it, and is the only olive-emphasized item — it is the only one that sends anything. No behavior, vocabulary or PATCH changes.

## Amendment (wave 9) — in a menu of states the one IN FORCE is a tinted row, and its NOW marker is right-flushed in the panel, not inline after the label

DEC-869 already says a menu of states 'marks the one in force'. Verified open at app/src/pages/speakers/speakers.css:415-417: `.chq-participation-menu-item.is-current` sets `font-weight: 700` and nothing else — no tint band — while `:411-413` gives `:hover` the only background in the panel, so a hovered non-current row reads more 'in force' than the current one. And `:419-423` `.chq-participation-menu-item-label` is `display:flex; align-items:center; gap:6px`, so the NOW chip (`.chq-participation-menu-now`, :431) sits immediately after the label text rather than right-flushed in the ~260px panel — the gate-4 measurement placed it at x=135. ParticipationMenu.render.test.tsx:169-179 asserts the checked item and the NOW badge EXIST but pins neither the tint nor the alignment, which is why this survived four waves. RULING: (a) `.is-current` carries a background distinct from both the panel surface and `:hover`, so the state in force is legible without hovering; (b) the NOW chip is right-flushed within a full-width label row (`margin-left:auto`), never inline after the text. SCOPE NOTE for the merge/fidelity reviewers: the mandate tags this clause '(sub-800 modal frame)', but the 260px is the DROPDOWN PANEL's own width on the desktop speakers roster (OnboardingGrid renders ParticipationMenu), not a phone viewport — this is desktop scope and the mandate itself files it under carried-open 'Speakers / content' residue, not the mobile queue. Do not re-route it to the mobile round.

## Amendment (wave 50): the participation menu's selectable states are Not invited / Confirmed / Declined — 'Invited' is a consequence of sending, never a thing you pick

docs/design/README.md §'Speakers — where the portal invite lives' specifies the menu exactly: 'Not invited (current) · Send portal invite (emails a claim link and sets this to Invited) · Confirmed · Declined, with the footer "Only Invited sends anything — the other two just record what you already know"'. The Send-portal-invite action OCCUPIES the Invited slot; that is the whole point of the ruling, since 'sending an invite IS the Not invited -> Invited transition — a separate button would be a second way to do one thing'. Verified at the file on main: app/src/pages/speakers/ParticipationMenu.tsx renders a menuitemradio for every member of InviteStatus including 'invited' (PARTICIPATION_STATE_CAPTIONS at :31-36 keys all four), and its own footer at :38-39 says 'the other three', not the handoff's 'the other two' — the copy is counting the extra control. Beyond fidelity this is a capability hazard: picking 'Invited' records a state that mails nothing, and a participant at invite_status='invited' is portal-visible but not active, so they drop out of every ACTIVE-gated surface while the organiser believes an invitation went out. RULING: the selectable radios are exactly {none, accepted, declined}. When the participation is ALREADY 'invited', that state still renders in the list as a disabled current-state row carrying its NOW marker and aria-checked (the organiser must be able to see where they are), and the Send-portal-invite action stays enabled beneath it. Footer copy becomes 'Only Send portal invite sends anything — the other two record what you already know'. The API keeps accepting 'invited' on PATCH participant (routes/api/submissions.ts:533-542) — this ruling governs the menu's affordances, not the model.
