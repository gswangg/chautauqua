# DEC-773: The files library is ONE list; a headshot is a file kind, not a tab

docs/design/Chautauqua Content.dc.html:233-268 draws Files as a single list headed "31 files · 412 MB" with type chips and a per-row Download -- no tabs. app/src/pages/content/FilesLibrary.tsx:23-26 still splits Deliverables/Headshots into two tabs fed by two endpoints, and its stat line reports a count with no size. Meanwhile the SPK probe reported portal-uploaded headshots as invisible in Content -- they are reachable only behind the second tab, and only for contacts on an accepted submission. Decision: one server-paginated list over every file row of the event (deliverable kinds + 'headshot'), kind chips carrying counts (Headshot among them), an envelope that reports `totalSizeBytes` alongside `total` so the header stat is "N files · <size>" produced by the same query the rows come from, and a per-row Download. The separate /events/:id/headshots endpoint and its repo function are deleted, not left as a shim (house style: no back-compat).

## Amendment (wave 41): the files library is five columns — FILE / SESSION / VERSION / SIZE / Download — and carries no selection or ZIP control

The library currently renders eight columns (select-all, File, Kind, Session, Version, Size, Uploaded, download) plus a "Download ZIP (0)" button. KIND duplicates the chip filter directly above it (DEC-902's grouped counts), UPLOADED duplicates data that belongs on the FILE cell's subline, and the selection column exists only to feed a ZIP control whose grouping dialog is on the mandate's explicit SKIP LIST. Ruling: five columns; uploader + date fold into the FILE subline; the selection state, its select-all cell, the MAX_ARCHIVE_FILES bound and the ZIP button leave the library. POST /events/:eventId/files/archive is NOT deleted — it keeps exactly one caller, the deliverable detail's "Download all" (DEC-901 amendment), so the endpoint stays exercised and no capability is lost.
