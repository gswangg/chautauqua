# DEC-773: The files library is ONE list; a headshot is a file kind, not a tab

docs/design/Chautauqua Content.dc.html:233-268 draws Files as a single list headed "31 files · 412 MB" with type chips and a per-row Download -- no tabs. app/src/pages/content/FilesLibrary.tsx:23-26 still splits Deliverables/Headshots into two tabs fed by two endpoints, and its stat line reports a count with no size. Meanwhile the SPK probe reported portal-uploaded headshots as invisible in Content -- they are reachable only behind the second tab, and only for contacts on an accepted submission. Decision: one server-paginated list over every file row of the event (deliverable kinds + 'headshot'), kind chips carrying counts (Headshot among them), an envelope that reports `totalSizeBytes` alongside `total` so the header stat is "N files · <size>" produced by the same query the rows come from, and a per-row Download. The separate /events/:id/headshots endpoint and its repo function are deleted, not left as a shim (house style: no back-compat).

## Amendment (wave 41): the files library is five columns — FILE / SESSION / VERSION / SIZE / Download — and carries no selection or ZIP control

The library currently renders eight columns (select-all, File, Kind, Session, Version, Size, Uploaded, download) plus a "Download ZIP (0)" button. KIND duplicates the chip filter directly above it (DEC-902's grouped counts), UPLOADED duplicates data that belongs on the FILE cell's subline, and the selection column exists only to feed a ZIP control whose grouping dialog is on the mandate's explicit SKIP LIST. Ruling: five columns; uploader + date fold into the FILE subline; the selection state, its select-all cell, the MAX_ARCHIVE_FILES bound and the ZIP button leave the library. POST /events/:eventId/files/archive is NOT deleted — it keeps exactly one caller, the deliverable detail's "Download all" (DEC-901 amendment), so the endpoint stays exercised and no capability is lost.

## Amendment (wave 55): the unified files library is the last unbounded whole-population read -- bound the query and count with count(*)

src/server/repo/files-library.ts:320-331 and :339-353 SELECT every matching row for the event with no LIMIT of any kind, sort and slice in JS at :383-393, and derive `total` from array length at :365 -- the unbounded-scan/JS-slice shape DEC-418/DEC-461 ban, on the surface that grows fastest (one row per file version per submission) against SPEC section 7's 2,000-submission scale target. computeKindCounts at :255-263 additionally SELECTs every headshot file id purely to read .length -- A PER-ROW COUNT IS N SCANS. Ruling: copy the contacts directory's precedent exactly (MAX_CONTACT_DIRECTORY_SCAN in src/server/repo/contacts/rows.ts:14, the loud refusal at crud.ts:339-345) -- cap the query, refuse loudly above the cap rather than silently truncating a file list an organizer is auditing, and let `count(*)` produce `total` and each kind count instead of loading full row sets to measure `.length`.

## Amendment (wave 29): the files library's total/totalSizeBytes are SQL aggregates; only the requested page's chains are ever materialized

`listEventDeliverableFiles` fetches EVERY matching chain root up to `MAX_FILE_LIBRARY_SCAN + 1` (src/server/repo/files-library.ts:331-343) and then `loadDeliverableChains` loads every file row of every matching submission (`:153-183`) for the sole purpose of letting a JS loop sum `latestOf(chain).sizeBytes` (`:392-399`). The module header claims it is "server-paginated ... never a whole-event scan" and the comment at `:296-306` openly concedes the totalSizeBytes pass defeats that. Measured worst read in the harness: 474.4ms adjusted (default) and 414.7ms (aie), both breaching the 150ms raw ceiling as well as the 50ms read budget. RULING: (1) `total` and `totalSizeBytes` are computed by aggregate statements over the SAME predicate the list composes — a chain's latest version is the row with no successor, `not exists (select 1 from file s where s.previous_file_id = f.id)` — never by materializing chains in JS; (2) per-page hydration keeps its existing page-scoped shape (`:434-489`); (3) if measurement shows the headshot branch dominant, the sanctioned fix is a real FK — a new `contact.headshot_file_id` column with an index plus a backfill migration — because `HEADSHOT_JOIN` (`:215`, `contact.headshot_url = '/headshots/' || file.id`) is non-indexable by construction; `headshot_url` stays as the served path. The lane fixes what it MEASURES, choosing between (1) and (3) on evidence, not on suspicion.
