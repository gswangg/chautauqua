# DEC-179: CSV formula-injection neutralization in the single toCsv serializer

formatCell in src/lib/csv.ts:138 (moved to src/domain/csv.ts) emits attacker-controlled public-CFP strings (titles, answers, names) verbatim, so cells starting with '=', '+', '-', '@' execute as formulas in Excel/Sheets (CWE-1236) via both organizer exports (src/routes/api/exports.ts:49,77) and review results CSV (the former src/routes/review.ts:435 (now split across src/routes/review/)). Fix once at the choke point: string cells whose first character is '=', '+', '-', '@', tab, or CR are prefixed with a single apostrophe before the existing RFC-4180 quoting rules run. Number and null cells are exempt (negative numbers stay clean; all numeric cells arrive typed as number). Accepted tradeoff: string values like phone numbers beginning '+' gain a leading apostrophe in spreadsheet imports — safety beats cosmetics for organizer-opened files.

## Amendment (wave 65): formula neutralization is an EXPORT property and must never touch a payload the product itself re-parses

This is the trap the DEC-011 amendment above walks straight into if nobody names it. The `toCsv` at `src/lib/csv.ts:132-157` (moved to `src/domain/csv.ts`) prefixes an apostrophe onto any cell starting with `= + - @ \t \r` (DEC-179 anti-formula-injection) and joins rows with CRLF. `app/src/pages/contacts/csv.ts:134` exports a same-named `toCsv` that does neither — and `ImportWizard.tsx:396` uses it to RE-SERIALIZE the user's whole CSV into the `csvText` the import POST actually sends. So the app's copy is not "best-effort preview parsing" as its header claims; it is authoritative for the request. Collapsing the two under one name would silently rewrite every imported phone `+1 555 0100`, every bio or title beginning `-`, and every `=`-prefixed cell — a data-corruption bug introduced BY a correct-looking single-source refactor. RULING: one module, TWO NAMED functions with their difference in the names. `toCsv` keeps its identity and its DEC-179 neutralization and stays the export serializer (every `text/csv` surface, per `test/serializer-single-source.scan.test.ts:199`). `toCsvVerbatim(rows: string[][])` is byte-faithful — no neutralization, `\n` joins — and is reserved for a payload this product will parse again itself; its doc comment states that neutralizing here would corrupt the import. Neither is a default for the other.
