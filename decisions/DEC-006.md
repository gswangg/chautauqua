# DEC-006: Mailer port, dev sink, merge-field rendering

Port: interface Mailer { send(m: RenderedEmail): Promise<void> } with RenderedEmail = { to: { email, name }, subject, text, html, ics?: { filename, content }, templateId?, eventId, contactId }. Stage 1 ships exactly one implementation, DevSinkMailer, which takes an injected EmailLogWriter port and writes one email_log row per recipient with full rendered content inline (columns: subject, body_text, body_html, ics_text, provider='dev', status='sent', sent_at) — viewable at /dev/mailbox. Merge fields are single-brace '{name}' placeholders rendered server-side from an explicit whitelist: {speaker_name}, {talk_title}, {event_name}, {portal_link}, {due_date}, {task_list}, {feedback}; rendering an unknown placeholder or a missing value THROWS (fail loudly) — no silent blanks in emails to real speakers. The 100-recipient cap and per-recipient preview live in the compose/send service, not the port. Resend is a stage-2 second implementation of the same interface.

## Amendment (wave 51): a swallowed send may never be reported to the user as a delivery

DEC-547/DEC-923 correctly made the CFP confirmation email a best-effort side effect that never 500s a submission whose row already persisted (src/routes/public/submit.tsx:623-639 catches and logs). But the outcome is discarded, and the confirmation page asserts the delivery unconditionally: h1 'That's in. Check your email.', body 'We've emailed a confirmation for X to <email>', and in the pending-existing-contact branch 'A password-setup link was emailed to <email>' -- which is that user's ONLY route into the portal, deliberately not rendered on screen (DEC-098). On exactly the mail outage that scored five criticals on prod, the product tells the submitter to wait for mail that will never arrive and shows no recovery. Every OTHER mail boundary in the codebase already reports per-recipient failure to its caller (bulk-email, content-notes, remind, plan-remind all return `failed[]`); this is the one that lies. Rule: a boundary that swallows a send failure must carry the outcome to whatever the user reads next. ConfirmationPage takes `emailDelivered: boolean`; when false it states the submission is saved under its ref, never claims an email was sent, and names the recovery (the on-screen claim link for a fresh contact; /login plus 'ask the organiser to resend your invitation' for an existing one). Success-path copy stays byte-identical. Enforced by a ledgered scan over every catch wrapping mailer.send/makeMailer.
