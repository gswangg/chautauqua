# DEC-756: The content session detail shows ONE deliverable at a time: a chip scopes the version list AND the note thread, and Approve is absent once approved

docs/design/Chautauqua Content.dc.html:123-177 draws the session detail as a status bar (content status + Approve + "Download all"), then a two-column body: a deliverable chip strip ("Slides · 3 versions" active, "Recording · 1 version" quiet) with the caption "Versions and notes below are for the selected deliverable", the selected deliverable's versions and drop zone on the left, and a single thread headed "Notes on the slides" on the right. Main still renders three stacked kind sections each with its own version list AND its own comment thread (DeliverableDetail.tsx:172-197), so the same session shows three composers and the organiser cannot tell which thread a speaker will read — the field guide already recorded the rule (a chip scopes versions AND thread) with no code behind it, and a recorded decision with no code is a lie. Chip labels carry their counts so the strip is a fact, not navigation. "Download all" calls the one archive endpoint FilesLibrary already uses; a second zip path would be a second truth about what a session contains. Approve renders only while the session is not approved (DEC-733: an action that cannot apply is absent, never disabled), and the composer's caption states what each button does to the queue, which is the only thing distinguishing them.
