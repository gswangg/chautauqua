# DEC-824: Distribution states its cap and names what it could not do

VERIFIED DEC-786 landed a real preview-then-confirm (src/routes/review/plans.ts:425-466 writes nothing and returns per-reviewer before/after), and docs/design/README.md:307-311 now adds the two legs it lacks: a cap per reviewer, and — the load-bearing one — a statement of the shortfall. An auto-distribute that silently under-fills is worse than none, because the organiser walks away believing the round is staffed. Decision: the cap is a parameter of THIS RUN, not a column on the plan — it is passed to the preview and repeated on the apply, so the pairs an organiser saw are byte-identically the pairs that get written and no migration is needed to describe a decision that is about one afternoon's staffing. distributeAssignments returns both the pairs it created AND the demand it could not meet, per submission with a closed-vocabulary reason ('cap_reached' | 'no_eligible_reviewer'), and the dialog renders the total ('This would assign 22 reviews'), each reviewer's change ('6 → 8 talks'), and the shortfall sentence naming the constraint and the track. Reviewers the run cannot use are LISTED as unchanged with their reason rather than hidden, because an absent name reads as an oversight.

## Amendment (findings wave 11): distribution refuses pre-write above a declared cap, and the preview never promises a write the apply would refuse

`POST /plans/:id/assignments/distribute` computes every missing (reviewer, submission) pair and hands the whole list to `addReviewers`, which chunk-inserts unbounded. At SPEC's own stated scale (up to 5,000 submissions/event, maxEvaluations 3) that is 15,000 inserts in one request: it exhausts D1's per-request budget mid-write and 500s, leaving the plan half-distributed with nothing to roll back. Every sibling fan-out already refuses pre-write with a forward path the caller can act on — MAX_TASK_ASSIGNMENT_WRITES/maxUnitsForTaskAssignmentWrites (DEC-079/DEC-528) and MAX_AUTO_SCHEDULE_PLACEMENTS. Distribution is the omission. The cap and its derived 'largest plan this can take in one run' helper live in the pure domain module, so the message names a number the organiser can use rather than an internal literal. DEC-840's byte-identical promise then binds the preview too: if the apply would refuse, the preview must say so in the same run, or the organiser confirms a write that cannot happen. Auto-schedule's 'report the tail, never drop it' precedent does not transfer here — an over-cap distribution is a plan whose filters are too wide, and half-assigning a review wave silently is worse than refusing it.
