# DEC-375: Settings stays one route; the section rail is client state and becomes a drill-in index at phone width

The mock shows a 196px sticky section rail plus seven separate phone subscreens, which reads like seven routes. Adding them would change app/src/routeManifest.ts and therefore the render sweep and docs route coverage, all frozen contracts under DEC-366. Settings keeps exactly one route, /admin/settings, with the active section held as component state in SettingsPage. At >=700px the rail renders as `.chq-rail` with the h1 above it and the active link marked; below 700px the rail renders as a full-width list of section links, and choosing one replaces the list with that panel plus a tertiary back control that clears the selection — the mock's phone 'subscreens' are that swap, not navigation. No URL, no history entry, no route-manifest change; deep-linking to a section is deliberately not added, because no requirement asks for it and it would widen a frozen contract.
