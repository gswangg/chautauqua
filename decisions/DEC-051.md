# DEC-051: Calendar invites in compose: attachIcs flag + per-submission ics_sequence (migration 0008 reserved)

SPEC §3/§9/§10 require working .ics in speaker comms with the swyx flow: initial invite (no room) then an update with the SAME UID and bumped SEQUENCE when the room lands. One mechanism, not two: compose preview/send gain attachIcs?: boolean. A new submission.ics_sequence INTEGER NOT NULL DEFAULT 0 column (migrations/0008_w7_ics_sequence.sql — filename reserved; append idx-8 entry to migrations/meta/_journal.json per the 0007 pattern) tracks the RFC 5545 SEQUENCE. Send uses the stored value for every recipient of that submission (UID from src/mail/ics.ts uidFor — stable per SPEC §5), attaches via the existing RenderedEmail.ics field (filename chq-<submissionId>.ics), then bumps the stored value exactly once per submission per send call; preview NEVER bumps. Slot local→UTC conversion reuses the exact helpers GET /e/:slug/schedule.ics uses — never duplicated. Preflight is atomic per DEC-019: attachIcs with any selected submission unscheduled rejects with ApiError('invalid', …, {<submissionId>:'not scheduled'}) before any send; LOCATION is emitted only when a room is assigned (that IS the initial-invite-without-a-room flow). Public schedule.ics stays as-is (regenerated snapshot calendars, sequence 0) — do not 'fix' it.
