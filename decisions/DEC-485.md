# DEC-485: The import row cap is the write-burst bound; the import write path is O(rows) serial by design and no audit may grade it O(rows/90)

DEC-356 made the import LOOKUP side O(file/90) (src/server/repo/contacts/import.ts:61 chunked email lookup), and a prior spec audit recorded 'PASS — O(rows/90)' for the import as a whole. That is true of the lookup and false of the writes: the loop at :87-111 issues, per row, either createContact (INSERT + a findContactById read-back) or patchContact (UPDATE + up to two backfillNullAttribution participant UPDATEs + a read-back) — roughly 2-4 D1 statements per row, serially. Batching is not the cheap fix it looks like: D1's ~100 bound-parameter ceiling (the same limit DEC-078's ID_CHUNK_SIZE=90 was sized against) caps a multi-row contact INSERT near seven rows per statement, and per-row attribution values cannot share one UPDATE. Rather than a half-rewrite that trades real risk for a small constant factor, this wave writes the true per-row cost down at the cap's own declaration so the number is auditable and a future wave can decide batching (or client-side chunked import) on evidence rather than on a claim nobody re-derived.
