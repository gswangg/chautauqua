# DEC-748: The merge screen shows EVERY differing field, including value-versus-empty, and the duplicate rule is stated where the pairs are listed

Verified in src/domain/contacts.ts:353 — `if (dupVal === "" || dupVal === beforeVal) continue;` drops a field entirely when the DUPLICATE side is empty, so a pair whose primary carries AcmeCo/Engineer against a blank duplicate renders only the Email row and the organiser commits an irreversible merge without seeing what is on the table. The design's merge column is explicit that the discarded value is the evidence for the decision (docs/design/README.md: the struck value exists precisely because merge cannot be undone), so an empty side renders as a struck em dash rather than vanishing; the `fill` case (primary empty, duplicate has a value) already produces a row and keeps it. The screen also gains the Labels row that DEC-738's server-side formatter exists to serve — combined, not chosen, per the pack — a "1 of N pairs" counter, and a keep column headed by the record's own name instead of a generic DISCARD radio. Finally, DEC-143's matching rule (same email, OR same name at the same company, with a blank company matching any) is affirmed rather than widened — pairs at different named companies are usually different people — but it must be SAID on the Duplicates tab, because a detection rule the organiser cannot read looks like a bug.

## Amendment (wave 2): the merge compare table is a FIXED identity contract, not a diff

previewMerge (src/domain/contacts.ts) emits a row only for fields that DIFFER, so a pair that agrees on Company shows no Company row, Labels appear only when a customFields.* row exists, and Notes never render as a row at all while the page's own footnote promises "Notes are appended". Merge is irreversible: the fields the decision is ABOUT must be on screen whether or not they changed. Ruling: previewMerge always emits six identity rows FIRST, in fixed order and with fixed labels — Name (firstName+lastName folded into one row), Email, Company, Title, Labels (every customFields.* folded server-side through contactLabels), Notes — each with kept/discarded/outcome computed exactly as today (outcome 'keep', empty discarded, em-dash rendering when nothing is lost). Any remaining differing rows (Phone, Bio) follow. No raw customFields.* row ever reaches the client, and MergePage renders the array verbatim: one reader, no client-side fold. DEC-748's "shows EVERY differing field" survives as the tail of the contract, not the whole of it.

## Amendment (wave 39): the merge screen resolves its own pair server-side by ids; "no longer duplicates" is a server verdict, never a client failing to find a row on page 1

Verified: app/src/pages/contacts/MergePage.tsx:83-96 fetches /contacts/duplicates with no page/perPage, so src/routes/api/contacts/crud.ts:188-201 clamps it to listPerPage's 200 and slices; the component then locates its pair with res.items.findIndex(...) and, on a miss, renders "These records are no longer duplicates — they may already be merged." A genuine duplicate pair sitting past group 200 is therefore declared merged and cannot be merged at all, and DEC-748's "N of M pairs" reports res.items.length (the page) while the envelope already carries the true total. Ruling: GET /api/v1/contacts/duplicates accepts ?ids=<id,id[,id]> (parsed through parseBoundedIdArray, DEC-182) and answers with the single group whose contactId set equals the supplied set, plus `position` (that group's 1-based index in the same ordered array the unfiltered list pages) and the full `total`. An empty `items` for a supplied ids set is the ONLY thing that may render "no longer duplicates". The client never scans a page for its own row and never derives a total from one.
