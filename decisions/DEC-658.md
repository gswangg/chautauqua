# DEC-658: Cacheability is a closed rule with one default: a response that does not set its own Cache-Control gets no-store, app-wide (supersedes the /api/v1-only noStoreApi scope)

src/server/app.ts:44-45 mounts noStoreApi on /api/v1 and /api/v1/* only, so every authenticated non-API surface ships zero cache directives: /portal/* SSR pages, /files/:fileId downloads, /admin, /login, /account/password and /dev/mailbox (grep confirms the only Cache-Control setters in the tree are public/shell.tsx, public/index.tsx, portal/profile.tsx and pubcache.ts). One speaker's portal and deliverables are therefore cacheable by a shared browser or an intermediary. Making the DEFAULT no-store and letting a handler that deliberately sets Cache-Control win is closed in both directions: it cannot miss a route added later, and it cannot clobber the public edge-cache contract that SPEC section 7's sub-50ms budget depends on. A prefix list would have to be re-audited every time a route lands; a default never does.
