# DEC-258: Frozen speaker attribution: participant.title_at_time / org_at_time, captured at participant creation, read by every public/export/.ics surface

docs/clarifications.md (highest precedence) closes with the adopted field-wisdom list: "per-submission permalinks; fewest-ratings-first and average-descending sorts; warn-never-block scheduling; stable IDs everywhere with title_at_time/org_at_time frozen at submission; .ics UIDs that never churn; the post-acceptance content loop; decide != notify." Every other item on that list is implemented; a repo-wide grep for title_at_time/titleAtTime/org_at_time returns ONLY docs/clarifications.md — zero code. the former src/db/schema.ts (now split across src/db/schema/)'s participant table (line 239) carries id/submissionId/contactId/role/order/visible/inviteStatus and no attribution snapshot, so the public program renders the contact's CURRENT company/title. The product consequence is real for J11's premise (one speaker network across many events per year): a speaker who changes jobs silently rewrites the attribution on last year's published program, agenda, showflow export and calendar invites.

Decision: add nullable TEXT columns `title_at_time` and `org_at_time` to participant; populate them at EVERY participant-creation site (public submit, acceptance auto-creation, organizer add-to-event/manual participant, seed) from the contact's then-current title/company; backfill existing rows in the migration with a correlated UPDATE from contact so seeded and in-flight data renders identically.

Read rule, no fallback (house fail-loudly, no compat shims): public program surfaces, the speakers/agenda/showflow exports and the .ics speaker line read the participant snapshot ONLY — a null snapshot renders nothing, exactly as a null contact.title does today. The CRM directory, contact drawer and portal profile keep showing the LIVE contact fields, because those are the person's record, not the program's record. No organizer edit UI for the snapshot in stage 1. This does not disturb SPEC J7's "one record, two views" promise, which enumerates bio/social links/headshot — not title/company.


## Amendment (wave 46): the public speaker page HEADER carries the PERSON; the session rows carry the participation snapshot

`src/server/repo/public/detail.ts:106-107` selects the page's `title`/`company` from `schema.participant.titleAtTime`/`orgAtTime`, `:118` orders the rows by `submission.title`, and `:142,166-167` then applies `rows[0]`'s snapshot to the whole page. For a returning speaker with two visible sessions carrying different snapshots — the J11 returning-speaker case, and invisible to any one-session fixture — `/e/<slug>/speakers/<id>` therefore attributes to the person whichever employer happens to sort first alphabetically by talk title, while `/e/<slug>/sessions` renders the correct per-session `title_at_time`/`org_at_time` (`src/server/repo/public/sessions.ts:412`). Two public surfaces contradict each other about the same speaker, and the tiebreak is a talk title. DEC-258's snapshot exists to freeze what a speaker's affiliation WAS when they presented a given session; that is a fact about a participation, not about a person, and a speaker directory page is about the person. RULING: the speaker DETAIL page header reads `schema.contact.title` / `schema.contact.company` — the person's own current identity, one deterministic source, null when the CRM has none (never fabricated, never borrowed from a talk). The per-session entries in the same payload keep their DEC-258 snapshots unchanged, and `sessions.ts` is not touched. This also removes an ordering dependency from a rendered value, which is the deeper defect: no user-visible field should change because a submission was retitled.

## Amendment (wave 75): the frozen-snapshot rule is PERSON-vs-PARTICIPATION, not a list of pages — every surface that renders a PERSON reads the live contact, and that includes the speakers list and the gallery

DEC-258's wave-46 amendment moved the public speaker DETAIL header off `participant.titleAtTime`/`orgAtTime` because electing `rows[0]`'s snapshot ordered by `submission.title` meant "a user-visible field changes because a submission was retitled", and because "a speaker directory page is about the person". Verified at my own runtime: that ruling reached exactly ONE of the two person-rendering surfaces. `src/server/repo/public/speakers.ts:127-128` still selects `schema.participant.titleAtTime`/`orgAtTime`, orders by `(contact.lastName, contact.firstName, submission.title)` at `:138`, and `:143-159` keeps the FIRST row per contact — i.e. the alphabetically-first talk title's employer, the exact tiebreak the amendment called "the deeper defect". `/e/:slug/gallery` is the grid view of that same read (DEC-990), so it inherits it. The result is that the list a visitor clicks FROM and the detail page they land ON can print two different employers for one person, one click apart. The same row already mixes LIVE `contact.bio` and `contact.headshotUrl` (`:129-130`) with the frozen title/company, so the row is not internally consistent about which record it is showing either. RULING, stated as a predicate so it cannot be applied to one member again: a surface whose unit of rendering is a PERSON — the public speakers list, the gallery, and the speaker detail header — reads `contact.title`/`contact.company`, deterministic, null when the CRM has none, never borrowed from a talk. A surface whose unit of rendering is a PARTICIPATION — session cards (`public/sessions.ts:412-413`), agenda blocks, the session detail speaker line, and the `.ics` speaker line — keeps the DEC-258 frozen snapshot unchanged. SCOPE, stated so it is not re-filed: the CSV/JSON exports (`src/server/repo/exports/speakers.ts:43-44,118-127`) stay on the frozen snapshot — an export row is the program's archival record and its election is already a documented, order-independent DEC-560 rule, not an alphabetical accident.
