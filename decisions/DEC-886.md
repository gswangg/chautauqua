# DEC-886: A session can be deleted, from a confirmation PAGE that names what goes with it, and a submitted evaluation makes it undeletable

Nothing in the product removes a submission, so every CSV import, every add-to-event, and every judge's exploratory click permanently pollutes the event (the fidelity fleet alone left five test sessions behind). A seventh 'archived' status would touch every status vocabulary, filter, count, chip and export in the app to buy a cleanup affordance; a real delete is smaller and more honest. Guards: organizer only, event-scoped, CSRF-gated; a submission carrying ANY submitted evaluation is REFUSED with the reason named per row, because another person's recorded judgment is not the organizer's to erase. Everything the submission itself owns is removed set-based in the one request — answers, track joins, participants, task assignments, files (rows AND their R2 objects, through the existing per-file delete helper), file comments, recusals, revisions — and email_log rows are historical fact and stay. The irreversible action is a PAGE, not a dialog: /admin/submissions/delete?ids=… lists every session by ref and title, states exactly what will be removed, lists the refusals with reasons, and carries the single primary. The endpoint mirrors the existing bulk-status shape (POST /api/v1/events/:eventId/submissions/status): POST /api/v1/events/:eventId/submissions/delete { ids } -> { deleted, refused }.

## Amendment (wave 60): the session-delete cascade includes the review-side join rows — draft evaluations and per-submission reviewer assignments

DEC-886's cascade is enumerated in src/server/repo/submission-delete.ts's own module header (submission_answer, submission_track, participant, schedule_slot, file + file_comment, review_recusal, submission_revision), and that list is the checklist: two tables carrying a submission_id are missing from it. `evaluation` is READ at :140-148 only to refuse a submission with a SUBMITTED evaluation — so every DRAFT evaluation on an eligible submission survives the delete pointing at a row that no longer exists. `plan_reviewer` carries a nullable submission_id (the per-submission reviewer scope resolveAssignments reads, src/domain/evaluation.ts:563-602) and is neither counted nor deleted, so a reviewer keeps an assignment to a deleted session and the plan editor's who-reviews-what list renders "Submission (removed)" forever (app/src/pages/review/PlanEditor.tsx:1446). Both are the field guide's "a JOIN row cascades on contact delete" rule with a different parent. RULING: both tables join the cascade, deleted set-based/chunked before the submission row like every sibling; both are counted into the DEC-921 blast-radius plan under one new `reviewAssignments` count (foldGroupedSubmissionCounts already generalises over any table with a submissionId), so the confirmation page keeps naming everything that goes; and the module header plus docs/AUDIT.md's J3 sentence are updated in the same commit, because that prose IS the checklist. email_log stays untouched (historical fact), and a submitted evaluation still makes the session undeletable — this only ever removes drafts.
