# DEC-886: A session can be deleted, from a confirmation PAGE that names what goes with it, and a submitted evaluation makes it undeletable

Nothing in the product removes a submission, so every CSV import, every add-to-event, and every judge's exploratory click permanently pollutes the event (the fidelity fleet alone left five test sessions behind). A seventh 'archived' status would touch every status vocabulary, filter, count, chip and export in the app to buy a cleanup affordance; a real delete is smaller and more honest. Guards: organizer only, event-scoped, CSRF-gated; a submission carrying ANY submitted evaluation is REFUSED with the reason named per row, because another person's recorded judgment is not the organizer's to erase. Everything the submission itself owns is removed set-based in the one request — answers, track joins, participants, task assignments, files (rows AND their R2 objects, through the existing per-file delete helper), file comments, recusals, revisions — and email_log rows are historical fact and stay. The irreversible action is a PAGE, not a dialog: /admin/submissions/delete?ids=… lists every session by ref and title, states exactly what will be removed, lists the refusals with reasons, and carries the single primary. The endpoint mirrors the existing bulk-status shape (POST /api/v1/events/:eventId/submissions/status): POST /api/v1/events/:eventId/submissions/delete { ids } -> { deleted, refused }.
