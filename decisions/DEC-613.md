# DEC-613: The Sessionboard importer is one endpoint whose dry run and real run are the same planner

POST /api/v1/events/:eventId/import/sessionboard takes { dryRun, entity, csvText, mapping } and returns { dryRun, entity, created, updated, skipped: {row,reason}[], issues: {row,field,message}[] }. Dry run and real run go through ONE planner; the only difference is whether the writes execute. A preview computed on a second code path is a lie — the same lesson as the DEC-572 fan-out preview. Counts are of rows PLANNED, never of rows sampled, and the report is the only thing the UI is allowed to print. Payload caps are imported from the CRM importer (MAX_IMPORT_CSV_BYTES, MAX_IMPORT_ROWS), never re-declared, because two functions claiming the same semantics must end in the same helper.

## Amendment (wave 63): the Sessionboard import panel states its CSV byte budget on the screen where the file is chosen and refuses an over-cap payload before the request, naming the overage — on BOTH the file path and the paste path

src/routes/api/import.ts:46-50 refuses a csvText over MAX_IMPORT_CSV_BYTES (5 MB, src/domain/contacts.ts:25 — already pure core, so the SPA can import it). app/src/pages/settings/SessionboardImportPanel.tsx:235-263 discloses nothing: the file input announces only `.csv,text/csv`, the paste textarea announces nothing at all, and both march the whole payload across the wire to be told no. This is the same defect wave 62 filed against the CRM ImportWizard, on a different panel and a different endpoint; that task (w62-e) owns the ROW cap's move into pure core, so this one deliberately touches only the BYTE cap, which already lives where the screen can read it. The refusal must count against the limit (the v9 error standard's "212 characters over" rule) using the single byte formatter in src/domain/files.ts, not a second one.

## Amendment (wave 68): the Sessionboard planner refuses an over-cap value per row/field through its existing SbIssue grammar, using the same constants the API enforces

Verified on main: planSessionboardRows (src/domain/sessionboard.ts:136+) validates header mapping only; src/server/repo/import/sessionboard.ts writes `plan.values.*` verbatim (no MAX_ anywhere in the file); src/routes/api/import.ts bounds only MAX_IMPORT_CSV_BYTES and MAX_IMPORT_ROWS. One row can therefore create a submission.description of any length while PATCH /submissions/:id caps it at LOCKED_ABSTRACT_MAX_LENGTH=1200 and title at LOCKED_TITLE_MAX_LENGTH=200, and track/room/contact fields at MAX_NAME_LENGTH — an imported session no producer can ever re-save, and an imported contact whose CRM drawer can never save. The planner already emits SbIssue {row, field, message}, which is the right refusal shape here (four entities, per-field mapping); the CRM importer keeps ImportSkip. Shared: the CONSTANTS (src/forms/validate.ts, src/forms/types.ts), never a second copy of the numbers.

## Amendment (wave 60): one import vocabulary, one auto-mapper — the mapping UI derives from SB_TARGET_FIELDS and seeds itself from autoMapSessionboardColumns

Verified: src/domain/sessionboard.ts:76-81 declares SB_TARGET_FIELDS with `externalId` first for contacts/submissions/tracks, and planSessionboardRows refuses any row without one (`Missing external id (Record ID)`, :275-276). app/src/pages/settings/SessionboardImportPanel.tsx:47-52 hand-redeclares a DIVERGENT vocabulary with NO externalId entry, and src/routes/api/import.ts:90-91 auto-maps ONLY when the posted mapping is entirely empty. Consequence, reproduced by reading both halves: hand-mapping any single column makes the mapping non-empty, suppresses auto-map, and guarantees zero rows imported with an issue per row. This is the same class as DEC-817's hand-written route map and DEC-851's declared-but-unread knob — a second copy of a vocabulary the domain already owns. RULING: the SPA imports SB_TARGET_FIELDS and autoMapSessionboardColumns from src/domain/sessionboard.ts and deletes its local TARGET_FIELDS; on every CSV load/entity change the mapping state is INITIALIZED from autoMapSessionboardColumns(entity, header) so hand-editing one column can never silently unmap the rest; the server's empty-mapping fallback stays exactly as-is (an explicit mapping remains authoritative). A parity test asserts the picker's per-entity option list is SB_TARGET_FIELDS itself, not a copy.

## Amendment (wave 64): the Sessionboard import's step 2 is the DISPOSITION REVIEW, and its two facts sit on the controls they govern

`docs/design/DESIGN-RULINGS.md:356` rules three steps in one surface where step 2 shows counts per entity and what will happen to each, and states two facts: nothing is written until step 3, and Sessionboard is read-only to us. On main `SessionboardImportPanel.tsx:90` derives `step` so that the dry-run report lands on step 3 alongside the real import, the steps are labelled `Choose file · Match columns · Done`, and neither fact appears anywhere in the file (grepped: zero hits for 'read-only', 'nothing is written', 'until step 3'). RULED: the steps read `Choose file · Review what will change · Done`; the dry-run report renders INSIDE step 2 with its per-entity dispositions built from the report the server already returns (`created`/`updated`/`skipped[].reason`/`issues[]`) — counted, never invented; 'Nothing is written until you confirm on the last step' sits with the dry-run control that produced the numbers, and 'Sessionboard is read-only to us — importing never writes anything back' sits with the entity picker. The existing DEC-613 wire contract and the `SB_TARGET_FIELDS`-derived mapping pills (DEC-613 w60) are unchanged.
