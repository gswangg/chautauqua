# DEC-613: The Sessionboard importer is one endpoint whose dry run and real run are the same planner

POST /api/v1/events/:eventId/import/sessionboard takes { dryRun, entity, csvText, mapping } and returns { dryRun, entity, created, updated, skipped: {row,reason}[], issues: {row,field,message}[] }. Dry run and real run go through ONE planner; the only difference is whether the writes execute. A preview computed on a second code path is a lie — the same lesson as the DEC-572 fan-out preview. Counts are of rows PLANNED, never of rows sampled, and the report is the only thing the UI is allowed to print. Payload caps are imported from the CRM importer (MAX_IMPORT_CSV_BYTES, MAX_IMPORT_ROWS), never re-declared, because two functions claiming the same semantics must end in the same helper.

## Amendment (wave 7, sha ddc9a7d9): ONE organiser-facing criterion-type vocabulary — "Scale 1–5" / "Choice" / "Text", drawn from the frame, never the storage words

The v12 intake renamed the criterion TYPE at the label layer, not the column (field-guide w82: "map its vocabulary onto the stored one instead of migrating a column"). The mapping never happened for the controls: `PlanEditor.tsx:1974-2002` still renders the storage words `Rating / Dropdown / Text` while the frame's own support code writes `typeLabel: isChoice ? 'Choice' : 'Scale 1–5'` (docs/design/Chautauqua Review.dc.html:1017) and DESIGN-RULINGS §"Review criteria — Scale or Choice" says the criterion "gains a TYPE at creation: Scale 1-5 (default) or Choice". Two words for one concept in the same product is DEC-613's trap with a delay fuse. RULING: exactly one exported map, `CRITERION_KIND_LABELS = { rating: "Scale 1–5", dropdown: "Choice", text: "Text" }` (en dash per the frame), living in `src/domain/evaluation/criteria.ts` and re-exported for the SPA; every organiser-facing readout of a criterion's type renders through it. `text` stays "Text" deliberately — no design source renames it, and inventing "Comment" would collide with an evaluation's existing `comment` field. The SPA's own `CriterionKind` copy at `app/src/pages/review/types.ts:8` is a separate duplication and is explicitly OUT of scope this wave.

## Amendment (wave 63): the Sessionboard import panel states its CSV byte budget on the screen where the file is chosen and refuses an over-cap payload before the request, naming the overage — on BOTH the file path and the paste path

src/routes/api/import.ts:46-50 refuses a csvText over MAX_IMPORT_CSV_BYTES (5 MB, src/domain/contacts.ts:25 — already pure core, so the SPA can import it). app/src/pages/settings/SessionboardImportPanel.tsx:235-263 discloses nothing: the file input announces only `.csv,text/csv`, the paste textarea announces nothing at all, and both march the whole payload across the wire to be told no. This is the same defect wave 62 filed against the CRM ImportWizard, on a different panel and a different endpoint; that task (w62-e) owns the ROW cap's move into pure core, so this one deliberately touches only the BYTE cap, which already lives where the screen can read it. The refusal must count against the limit (the v9 error standard's "212 characters over" rule) using the single byte formatter in src/domain/files.ts, not a second one.

## Amendment (wave 68): the Sessionboard planner refuses an over-cap value per row/field through its existing SbIssue grammar, using the same constants the API enforces

Verified on main: planSessionboardRows (src/domain/sessionboard.ts:136+) validates header mapping only; src/server/repo/import/sessionboard.ts writes `plan.values.*` verbatim (no MAX_ anywhere in the file); src/routes/api/import.ts bounds only MAX_IMPORT_CSV_BYTES and MAX_IMPORT_ROWS. The planner already emits SbIssue {row, field, message}, which is the right refusal shape here (four entities, per-field mapping); the CRM importer keeps ImportSkip. Shared: the CONSTANTS (src/forms/validate.ts, src/forms/types.ts), never a second copy of the numbers.

## Amendment (wave 60): one import vocabulary, one auto-mapper — the mapping UI derives from SB_TARGET_FIELDS and seeds itself from autoMapSessionboardColumns

Verified: src/domain/sessionboard.ts:76-81 declares SB_TARGET_FIELDS with `externalId` first for contacts/submissions/tracks, and planSessionboardRows refuses any row without one (`Missing external id (Record ID)`, :275-276). app/src/pages/settings/SessionboardImportPanel.tsx:47-52 hand-redeclares a DIVERGENT vocabulary with NO externalId entry, and src/routes/api/import.ts:90-91 auto-maps ONLY when the posted mapping is entirely empty. Consequence, reproduced by reading both halves: hand-mapping any single column makes the mapping non-empty, suppresses auto-map, and guarantees zero rows imported with an issue per row. This is the same class as DEC-817's hand-written route map and DEC-851's declared-but-unread knob — a second copy of a vocabulary the domain already owns. RULING: the SPA imports SB_TARGET_FIELDS and autoMapSessionboardColumns from src/domain/sessionboard.ts and deletes its local TARGET_FIELDS; on every CSV load/entity change the mapping state is INITIALIZED from autoMapSessionboardColumns(entity, header) so hand-editing one column can never silently unmap the rest; the server's empty-mapping fallback stays exactly as-is (an explicit mapping remains authoritative). A parity test asserts the picker's per-entity option list is SB_TARGET_FIELDS itself, not a copy.

## Amendment (wave 64): the Sessionboard import's step 2 is the DISPOSITION REVIEW, and its two facts sit on the controls they govern

`docs/design/DESIGN-RULINGS.md:356` rules three steps in one surface where step 2 shows counts per entity and what will happen to each, and states two facts: nothing is written until step 3, and Sessionboard is read-only to us. On main `SessionboardImportPanel.tsx:90` derives `step` so that the dry-run report lands on step 3 alongside the real import, the steps are labelled `Choose file · Match columns · Done`, and neither fact appears anywhere in the file (grepped: zero hits for 'read-only', 'nothing is written', 'until step 3'). RULED: the steps read `Choose file · Review what will change · Done`; the dry-run report renders INSIDE step 2 with its per-entity dispositions built from the report the server already returns (`created`/`updated`/`skipped[].reason`/`issues[]`) — counted, never invented; 'Nothing is written until you confirm on the last step' sits with the dry-run control that produced the numbers, and 'Sessionboard is read-only to us — importing never writes anything back' sits with the entity picker. The existing DEC-613 wire contract and the `SB_TARGET_FIELDS`-derived mapping pills (DEC-613 w60) are unchanged.

## Amendment (wave 68): the submission sort vocabulary is one set, declared in domain and imported by both sides

src/server/repo/submissions/query.ts:23-25 declares five sort orders (newest|oldest|title|ref|worklist); app/src/pages/submissions/types.ts:35 declares four of them again, and app/src/pages/submissions/views.ts:51 casts a saved view's stored sort into that shorter type. The server's saved-view validator accepts the full five (src/server/repo/views.ts:47 imports SORT_ORDERS), and ContentApp.tsx:111 really does send sort=worklist — so a view created through the API with sort='worklist' reaches a <select> (FilterBar.tsx:30) with no such <option> and a sortLabel with no such case, silently changing the row order the organiser thinks they saved. This is the delay-fused second copy DEC-613 names. The SET moves to a pure src/domain module both sides import (the same relocation the wave-64 merge train did for the duplicate cap); which members a HUMAN may pick in the submissions control is then a separate, stated subset with a written reason — never an accident of which file was edited last.

The three-member task-kind vocabulary exists five times and agrees today only by luck: domain/acceptance.ts:7, routes/tasks.ts:78 (a string Set the type system cannot check against the type it guards), repo/portal/tasks.ts:16, app/src/pages/speakers/types.ts:11, app/src/pages/speakers/speakerDetail.ts:81. ## Amendment (wave 2): the docs role-group vocabulary has exactly one owner, DOCS_GROUP_META, and the leaving-link label is a declared constant

DOCS_GROUPS today exports six kebab ids and nothing else. Every renderer of the index — the unmerged /docs shell, any future nav, the phone article header — must turn `running-an-event` into `Running an event`, so the display vocabulary WILL be spelled a second time the moment a shell lands; that is exactly the DEC-613 trap with a delay fuse. The six labels are the ruling's own words ('Getting started / Running an event / Your contacts / For reviewers / For speakers / Running the software') and the index's leaving-link label is verbatim ('Leaves the docs — an operator surface'). Both become declared data inside docs-content, machine-checked against DOCS_GROUPS in both directions, with a guard that no file outside src/routes/docs-content/ hand-lists three or more of the six labels as string literals. Cheaper to own the vocabulary before the shell merges than to de-duplicate it after.

## Amendment (wave 4): the docs navigation order has exactly one owner, a pure model in docs-content/nav.ts

The article frame draws a sticky grouped side nav and a prev/next pager. Group order, per-group article order and the flattened cross-group neighbour order are the SAME order in three places; spelling it in the renderer would fork it the moment a phone header or a future breadcrumb needs it. docsNavGroups() and docsArticleNeighbours(slug) derive everything from DOCS_GROUPS + DOCS_ARTICLES, so the index, the nav and the pager cannot disagree about what comes next.

## Amendment (wave 139): the `<a>` control-primitive carve-out is a PARAMETER of the one shared tap-target extractor, never a second copy and never a widened default

`app/src/phone-tap-target-scan/core.ts`'s `tapTargetTagTokens` admits an `<a>` only when it composes `.chq-btn`. That carve-out is HONEST on the SPA, where `.chq-btn` is the control primitive that carries the floor, and BLIND on the SSR surfaces, which have no such primitive and where a bare `<a>` is the control — measured at fb926647, lifting it takes the SSR population 25 -> 75 and the unfloored count 0 -> 28, while `ssr.ts`'s own header cites `a.chq-docs-wordmark` at 112.6x28 as a live probe measurement of an offender the file could not see. There are exactly two wrong repairs and both have precedent in this repo: forking a second SSR extractor (DEC-613's delay-fused second copy of a vocabulary — `ssr.ts` already refused this once, passing `SSR_CLASS_ATTR_RE` into the SAME extractor rather than growing a second one), and widening the shared default (which would drag four SPA ratchets — base tap-target, undeclared-height, anchor-floor, SSR — into a population whose `.chq-btn` composition makes them honest today). RULED: one extractor, one behaviour switch. `tapTargetTagTokens(src, classAttrRe, opts)` gains `opts.anchorNeedsBtnToken` defaulting to `true`; `allSsrTapTargetTokens` is the only caller that passes `false`. The flag is proved by positive and negative controls over SYNTHETIC fixtures in a dedicated file — never by a product count, because a `toBeGreaterThan(0)` over a live number is itself a sentinel.
