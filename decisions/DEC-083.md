# DEC-083: Real purge-on-publish for public surfaces (supersedes DEC-022's "no purge machinery"): version-salted caches.default + KV version bumped by any successful mutation

J10's "edge-cached, purged on publish-affecting writes" is stage-1 product text; DEC-022 narrowed it to bounded 60s staleness, which the final review flagged as reframing rather than implementing. Version-keyed caching gives O(1) purge with no URL enumeration and is the same code stage 2 runs at the real edge: src/server/pubcache.ts holds PUBVER_KEY = 'chq:pubver' in KV; public/embed HTML GETs are served through caches.default keyed by URL + '__chqv=' + version; stored copies get Cache-Control: public, max-age=86400 (long TTL is safe because purge is a version swap) while client-facing headers keep DEC-022's max-age=60 + stale-while-revalidate=300. Purge is deliberately coarse: a middleware in createBaseApp sets KV to crypto.randomUUID() (random token, not a counter — race-proof, no lost-update window) after ANY non-GET/HEAD/OPTIONS request with status <400; over-purging costs only cache hits and can never serve stale program pages. /e/:slug/schedule.ics is never cached (per-user query strings would pollute the cache; it is cheap once DEC-080 lands). Missing KV binding throws — fail loudly. Core logic is written against the small KVStore interface (src/lib/draft.ts) plus a minimal CacheLike interface so it unit-tests with fakes.

## Amendment (wave 10): a cached response is CLONED before it is read, so a repeat hit on one cache instance still has a body

servePublicGet (src/server/pubcache.ts:97-105) consumes `hit.body` directly to build the client-facing response. The Workers Cache API happens to hand back a fresh Response per match(), so production survives; any CacheLike that returns the same Response object twice — which the interface at pubcache.ts:48-51 explicitly permits, and which the in-memory fake used in tests is — yields a disturbed/locked stream on the second identical request. The previous wave recorded this as a 'pre-existing double-read bug worked around in the test rather than fixed'; a workaround in a test that leaves the product code wrong is a stale excuse outliving its cause. RULING: the read path clones before reading (`new Response(hit.clone().body, hit)`), matching the store path which already clones (line 109). This is the byte-identical CLIENT_CACHE_CONTROL restore path — DEC-099's header contract is unchanged, and the version-salted key space is untouched. The regression test drives two consecutive identical GETs through ONE cache instance and asserts both bodies arrive whole; the test no longer needs to avoid the second read.

## Amendment (wave 15): the public cache WRITE leaves the response path

servePublicGet awaits `cache.put(...)` before returning the origin response, so every cache MISS on /e/* and /embed/* pays the edge-store latency before the visitor gets a byte — on exactly the surfaces SPEC §7 budgets. Ruling: the store is handed to an injected `waitUntil` (the middleware supplies the Worker execution context; tests supply a collector so the assertion is still deterministic) and the response returns as soon as the handler produced it. The wave-10 clone-before-read rule on the HIT path is unchanged and gets a regression pin in the same file.

## Amendment (wave 22): a middleware's scope is its REGISTRATION ORDER, and edge-cache prefix coverage is proven by counting passes at runtime

An external review filed the `publicCacheMiddleware` registration in src/routes/public/saved-embed.tsx:35 as a duplicate of publicRoutes' `/embed/*` registration (src/routes/public/index.tsx:90) and therefore as double work on every saved-embed request. Verified against the tree, that is FALSE and the opposite is true: Hono composes only the matched handlers in registration order and advances solely via next() (node_modules/hono/dist/compose.js:22,37), and `publicRoutes.route("/", savedEmbedRoutes)` (index.tsx:61) copies the sub-app's use+handler in BEFORE line 90's `use("/embed/*")`. The saved-embed handler returns without calling next(), so the parent registration never runs for /embed/e/*; deleting the "duplicate" would silently drop saved embeds out of the edge cache entirely — a plausible next-reviewer regression with no test to catch it. Ruling: both call sites carry a comment naming the ordering rule, and the claim is settled the way this mandate requires claims to be settled — by RUNTIME evidence: a test drives the real publicRoutes with counting KV/cache fakes and asserts exactly ONE version read and ONE cache lookup per request for a representative URL under each cached shape (/e/*, /embed/*, /embed/e/*), so both 0 (coverage lost) and 2 (nesting) fail, plus the shared-copy safety invariant that no response under those prefixes carries Set-Cookie. Reading `use()` lines is not evidence of what wraps what.
