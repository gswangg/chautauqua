# DEC-956: A refusal names the rows it refuses over, and states both ways forward

DELETE /contacts/:id (src/routes/api/contacts/crud.ts:294-328) reads countContactReferences and 409s with 'This contact is on 1 submission, 3 tasks and 1 user account. Merge it into another record instead of deleting it.' The counts are honest and the refusal is correct policy (DEC-758), but the field guide already records why this is a dead end: a 409 naming a CLASS is a dead end — name the ROWS. The organiser cannot act on '3 tasks': they do not know which tasks, on which event, or that DEC-921 deliberately REOPENS a file-request assignment when its session is deleted (src/server/repo/submission-delete.ts:273-276), which is exactly how a contact acquires assignments that no longer correspond to anything the organiser can see. The message also offers one way forward when there are two. Rule: a new bounded reader, listContactReferenceRows(db, contactId), returns the actual rows — submissions as {id, ref, title, eventName}, tasks as {id, title, eventName}, pipeline entries as {id, stage}, user accounts as {id, email} — capped at five per class with a remainder count, one joined query per table and never a query per row (DEC-078/DEC-418). The 409 names them in prose and states both routes out: merge this record into the one you are keeping, or remove them from those sessions and tasks first. The `fields` map keeps its existing count keys so the current client banner keeps working. countContactReferences is deleted rather than left beside its replacement, and its call sites updated — no compatibility shim.
