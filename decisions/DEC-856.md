# DEC-856: A preflight names EVERY merge field each recipient is missing, in one message shape, and the banner announces itself

VERIFIED: renderTemplate (src/mail/render.ts:78-85) throws MergeFieldError on the FIRST unresolved placeholder, and preflightRender (src/domain/compose.ts:184-199) catches once per template, so a recipient missing {speaker_name} AND {talk_title} is reported with one of them. Worse, missingToFields (src/routes/comms/compose-core.ts) keys by `${contactId}:${submissionId}` into a flat Record, so the subject's entry and the body's entry for the SAME recipient overwrite each other — the organiser fixes the named field, re-runs, and is told about the next one. The DEC-793 banner that lists them (ComposeWizard.tsx:330-341) also carries no role='alert', unlike its capMessage sibling three lines below, so a screen-reader user gets no announcement of the thing that just blocked their send. Decision: shape-scanning replaces throw-on-first — `missingMergeFields(template, vars): string[]` in src/mail/render.ts returns every placeholder absent from vars in first-appearance order (renderTemplate keeps throwing, unchanged, for its single-value callers); PreflightMissingField becomes ONE entry per recipient carrying `fields: string[]` (subject's misses first, then the body's, deduped); and both routes emit the SAME message shape whether one field or five — `missing merge fields: speaker_name, talk_title` — so the client has one parser instead of a singular/plural pair that will drift. The banner takes role='alert'. A preflight exists to make a batch fixable in one pass; naming one field per round trip is a preflight that lies about how much is wrong.


## Amendment (wave 1)

The bulk-email context resolves exactly speaker_name/event_name/portal_link (BULK_EMAIL_MERGE_FIELDS, src/mail/render.ts:56; enforced at src/routes/api/contacts/bulk-email.ts:156/173/238), but BulkEmailModal offers every event template, so Acceptance / Content Reminder / Decline preview straight into a 400 that names no offending token and offers no forward path. A control whose only outcome is an error is the same defect as a control with nothing to write. Ruling: the modal computes each template's unmergeable tokens with the pure helpers that already exist (`missingMergeFields` over the three-key vocabulary) and renders those templates as DISABLED options that name the blocking token, with one forward path — Comms compose, which does resolve them, opened with the template preselected (the `?template=` parameter ComposeWizard already honours). The vocabulary is imported, never re-listed.


## Amendment (wave 60) — a pre-flight refusal names the PERSON on every surface that sends, not just the one that was measured

DEC-856 already rules that the compose pre-flight names every merge field each recipient is missing and resolves the id to the person (ComposeWizard.tsx:228-253 does exactly this). Its sibling surface does not: src/routes/api/contacts/bulk-email.ts builds the identical fields map at :158, :175 and :243 keyed by `m.contactId` — a ULID — and its only reader, app/src/pages/contacts/BulkEmailModal.tsx:116, collapses the whole envelope to `setError(err.message)`. The organizer therefore reads 'One or more recipients are missing merge fields (only speaker_name/event_name/portal_link are allowed)' with nobody named, no token named, and no forward path. RULING: (1) the three refusal sites key the fields map by the recipient's EMAIL (human-legible and unique within one send) and the value names the person plus the exact missing placeholders, resolved from the already-loaded recipient rows with NO additional D1 read; (2) the message leads with the count ('3 of 12 recipients are missing {talk_title}'); (3) BulkEmailModal renders the map as a RECIPIENT / MISSING list in the recorded error vocabulary (1px ink border, 3px ink left edge, 13px/600 ink message — no red), and never discards `err.fields`. This closes the shape 'a fields map keyed on a ULID is a server naming rows to itself'.

## Amendment (wave 63): a refusal's fields map is read by SHAPE, never dumped — a handler that emits several fields-map shapes gets a matcher per shape, and anything unmatched renders labelled by its key

app/src/pages/contacts/BulkEmailModal.tsx:122,159 does `setMissingMergeFieldLines(err.fields ? Object.values(err.fields) : null)` — it treats EVERY fields map POST /contacts/bulk-email{,/preview} can return as a list of merge-field sentences. That endpoint emits at least four shapes: bulkEmailMergeFieldError's `{ <email>: "<Name> is missing {company}" }` (the only one the bullets are for), plus the validators at src/routes/api/contacts/bulk-email.ts:47-59 — `{ subject: "required" }`, `{ subject: "Max 2000" }`, `{ bodyText: "Max 20000" }`, `{ eventId: "required" }`. Paste a long subject and the modal renders a bullet reading `Max 2000` with no field named — a server talking to itself in front of the user, and the control that caused it carries no mark. The DEC-856 sibling in ComposeWizard already does this correctly (extractIcsUnscheduledIds / extractMissingMergeFieldLines / extractNoRecipientRefs, locked by app/src/pages/comms/compose-refusal-shapes.test.ts): match on the message shape the server actually throws, resolve to a name, and never let an unmatched entry fall into an unlabelled list. The rule generalises: an entry that matches no known shape is rendered as "<field>: <message>" beside its control, never as an anonymous bullet.
