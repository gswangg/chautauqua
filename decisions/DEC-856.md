# DEC-856: A preflight names EVERY merge field each recipient is missing, in one message shape, and the banner announces itself

VERIFIED: renderTemplate (src/mail/render.ts:78-85) throws MergeFieldError on the FIRST unresolved placeholder, and preflightRender (src/domain/compose.ts:184-199) catches once per template, so a recipient missing {speaker_name} AND {talk_title} is reported with one of them. Worse, missingToFields (src/routes/comms.ts:689-695) keys by `${contactId}:${submissionId}` into a flat Record, so the subject's entry and the body's entry for the SAME recipient overwrite each other — the organiser fixes the named field, re-runs, and is told about the next one. The DEC-793 banner that lists them (ComposeWizard.tsx:330-341) also carries no role='alert', unlike its capMessage sibling three lines below, so a screen-reader user gets no announcement of the thing that just blocked their send. Decision: shape-scanning replaces throw-on-first — `missingMergeFields(template, vars): string[]` in src/mail/render.ts returns every placeholder absent from vars in first-appearance order (renderTemplate keeps throwing, unchanged, for its single-value callers); PreflightMissingField becomes ONE entry per recipient carrying `fields: string[]` (subject's misses first, then the body's, deduped); and both routes emit the SAME message shape whether one field or five — `missing merge fields: speaker_name, talk_title` — so the client has one parser instead of a singular/plural pair that will drift. The banner takes role='alert'. A preflight exists to make a batch fixable in one pass; naming one field per round trip is a preflight that lies about how much is wrong.


## Amendment (wave 1)

The bulk-email context resolves exactly speaker_name/event_name/portal_link (BULK_EMAIL_MERGE_FIELDS, src/mail/render.ts:56; enforced at src/routes/api/contacts/bulk-email.ts:156/173/238), but BulkEmailModal offers every event template, so Acceptance / Content Reminder / Decline preview straight into a 400 that names no offending token and offers no forward path. A control whose only outcome is an error is the same defect as a control with nothing to write. Ruling: the modal computes each template's unmergeable tokens with the pure helpers that already exist (`missingMergeFields` over the three-key vocabulary) and renders those templates as DISABLED options that name the blocking token, with one forward path — Comms compose, which does resolve them, opened with the template preselected (the `?template=` parameter ComposeWizard already honours). The vocabulary is imported, never re-listed.
