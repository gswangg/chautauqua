# DEC-353: The bulk ZIP archive gets a pre-fetch TOTAL-byte budget read from D1 metadata, and buildZip assembles exactly once — DEC-160's "cap keeps worst-case memory bounded" premise is arithmetically false

DEC-160 justified its 50-file cap with "cap and store-only keep worst-case memory bounded on the local Workers runtime." That premise does not survive arithmetic: src/domain/files.ts:42/47 admit 25 MB per document/text file, so 50 ids is up to 1.25 GB inside a 128 MB isolate. src/routes/files.ts:249 fully buffers every R2 object (`await new Response(obj.body).arrayBuffer()`), src/lib/zip.ts:189-192 then copies the whole body a second time (`out.bytes(body.toUint8Array())`) and a third at :192, and the route copies once more at :259-260 — peak ≈ 3-4x total bytes with a JS byte-loop CRC-32 over every byte. This is not a stage-2 production question like DEC-201: it OOMs the local dev runtime the walkthrough runs on, and it fails silently-loudly (an isolate kill, not an error envelope), which is exactly what the fail-loudly principle forbids. Rule: resolveLatestVersions (src/server/repo/files-library.ts:252) additionally returns file.sizeBytes; the archive route sums the RESOLVED latest versions' sizeBytes and, BEFORE the first R2 get, throws ApiError('invalid', ...) naming the request total and the cap when it exceeds ARCHIVE_MAX_TOTAL_BYTES = 40 * 1024 * 1024, declared next to MAX_ARCHIVE_FILES in src/routes/files.ts. No truncation, no partial archive, no silent skip — the producer is told to select fewer files. Separately, buildZip pushes the central directory and EOCD into the same ByteWriter as the body so toUint8Array() runs once; its emitted bytes must stay identical (test/zip.test.ts's assertions may not change). The 50-file cap (DEC-160) and parseBoundedIdArray (DEC-182) are unchanged; whichever bound binds first wins.
