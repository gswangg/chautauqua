# DEC-353: The bulk ZIP archive gets a pre-fetch TOTAL-byte budget read from D1 metadata, and buildZip assembles exactly once — DEC-160's "cap keeps worst-case memory bounded" premise is arithmetically false

DEC-160 justified its 50-file cap with "cap and store-only keep worst-case memory bounded on the local Workers runtime." That premise does not survive arithmetic: src/domain/files.ts:42/47 admit 25 MB per document/text file, so 50 ids is up to 1.25 GB inside a 128 MB isolate. src/routes/files.ts:249 fully buffers every R2 object (`await new Response(obj.body).arrayBuffer()`), src/lib/zip.ts:189-192 then copies the whole body a second time (`out.bytes(body.toUint8Array())`) and a third at :192, and the route copies once more at :259-260 — peak ≈ 3-4x total bytes with a JS byte-loop CRC-32 over every byte. This is not a stage-2 production question like DEC-201: it OOMs the local dev runtime the walkthrough runs on, and it fails silently-loudly (an isolate kill, not an error envelope), which is exactly what the fail-loudly principle forbids. Rule: resolveLatestVersions (src/server/repo/files-library.ts:252) additionally returns file.sizeBytes; the archive route sums the RESOLVED latest versions' sizeBytes and, BEFORE the first R2 get, throws ApiError('invalid', ...) naming the request total and the cap when it exceeds ARCHIVE_MAX_TOTAL_BYTES = 40 * 1024 * 1024, declared next to MAX_ARCHIVE_FILES in src/routes/files.ts. No truncation, no partial archive, no silent skip — the producer is told to select fewer files. Separately, buildZip pushes the central directory and EOCD into the same ByteWriter as the body so toUint8Array() runs once; its emitted bytes must stay identical (test/zip.test.ts's assertions may not change). The 50-file cap (DEC-160) and parseBoundedIdArray (DEC-182) are unchanged; whichever bound binds first wins.

## Amendment (wave 46): the archive cap is DERIVED from the isolate budget divided by the peak materialisation multiplier, and the redundant whole-archive copy is removed rather than documented

DEC-353's own body computes 'peak ~= 3-4x total bytes' and then sets ARCHIVE_MAX_TOTAL_BYTES = 40MB, which at 4x is ~160MB against a 128MB isolate — the arithmetic the decision was written to fix survives inside the decision. Worse, the guard placed before the first R2 get is only honest about the bytes it counted: the entry buffers (T), buildZip's ByteWriter growth transient, and the deliberate second whole-archive copy at src/routes/files.ts:371 all stack, and every R2 GET has already been paid before the isolate dies, so an at-cap archive fails as a silent isolate kill after doing all the IO — precisely what fail-loudly forbids. Nothing in the suite ever builds a near-cap archive, so the number was never exercised. Decision: (a) the copy goes away by typing the producer instead of the consumer — buildZip is declared `export function buildZip(entries: ZipEntry[]): Uint8Array<ArrayBuffer>` and backs its output with a plain ArrayBuffer, so the route can hand `built` straight to c.body (the w22-a note that 'tsc rejects the narrowing' was a statement about the old signature, not a law); (b) the cap stops being a magic literal and becomes derived arithmetic with both inputs named and exported — ISOLATE_MEMORY_BUDGET_BYTES = 128MB, ARCHIVE_PEAK_MULTIPLIER = 4, ARCHIVE_MAX_TOTAL_BYTES = 20MB — with a test asserting ARCHIVE_MAX_TOTAL_BYTES * ARCHIVE_PEAK_MULTIPLIER <= 0.75 * ISOLATE_MEMORY_BUDGET_BYTES so any future cap raise must first lower the multiplier; (c) a test actually builds an archive at the cap through buildZip so the number is measured once, not asserted about. A smaller cap that always completes beats a larger one that sometimes kills the isolate; the 400 already tells the producer to select fewer files.
