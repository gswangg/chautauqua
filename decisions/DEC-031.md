## Amendment: a saved view's config is bounded in every direction, and views per event are capped (wave 2)

DEC-031 fixed the saved-view SHAPE; nothing bounds its size. Verified in src/server/repo/views.ts: isValidSavedViewConfig accepts `q` of any length, a `columns` array of any cardinality with strings of any length, and a `trackId` of any length; src/routes/api/views.ts bounds only the view NAME and never limits how many views one organiser may create per event -- and every one of them is read back on the submissions page's tab strip, an unbounded surface that is never paged. Ruling: MAX_SAVED_VIEWS_PER_EVENT and MAX_SAVED_VIEW_COLUMNS live in a new pure-core src/domain/saved-views.ts; the config's string bounds REUSE the existing MAX_TEXT_LENGTH/MAX_NAME_LENGTH rather than minting new *_LENGTH names (which would land in the sibling text-cap scan's population for no benefit); and the 'Save this view' dialog states the count against the cap, because a cap the control does not disclose is the defect this swarm keeps re-filing.

## Amendment (wave 81): a validator that exists on the write side must be spent on the read side

`src/server/repo/views.ts` declares `isValidSavedViewConfig` at `:38` and the create/patch route spends it (`src/routes/api/views.ts:68`), while the read at `:84` is a bare `JSON.parse(row.configJson) as SavedViewConfig` in the same file, twelve lines below the validator it declines to call. A saved view's config drives the submissions list's status/track/sort/columns; a config that survives `JSON.parse` with a bad status token silently filters the list rather than refusing. The general rule this amendment states: when a module owns both the validator and the row reader, the reader spends the validator — a predicate applied on one side of a column only is half a contract, and the side that skips it is always the side that renders.
