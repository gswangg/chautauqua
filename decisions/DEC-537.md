# DEC-537: The cron's event sweep is a DISTINCT, not a whole-table scan reduced in JS

`listEventIdsWithOutstandingAssignments` (src/server/repo/tasks/reminders.ts:297-304) selects `task.event_id` for EVERY pending task_assignment row in the entire database -- across every org, every event -- and then reduces it to a handful of ids with `new Set(...)` in JavaScript. At the SPEC scale target of 200-800 speakers against the five-task default set, across the several events per year the customer runs, that is tens of thousands of rows pulled out of D1 on every cron tick to produce roughly three strings, and DEC-520 has just made auto-created tasks universal so the row set only grows. This is the identical shape DEC-531 removed from the overview last wave: materializing rows to compute something SQL already computes, in a module whose siblings (`grid.ts:221-230`) are all conditional aggregates. Decision: the query becomes `selectDistinct({ eventId: schema.task.eventId })` with the same WHERE, and the JS `Set` is DELETED rather than left as a belt-and-braces second dedupe -- two implementations of one invariant is how they drift, and the SQL is the authority.
