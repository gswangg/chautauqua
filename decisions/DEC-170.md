# DEC-170: Reviewer file access is plan-scoped and anonymization-aware (supersedes DEC-066)

Verified: GET /files/:fileId grants any reviewer holding ANY plan_reviewer row in the event access to every submission file in that event (reviewerHasPlanForEvent existence check), contradicting SPEC §4's 'reviewer (assigned plans only)' and defeating server-side anonymization since filenames/slides identify speakers. Rule: a reviewer may download a submission file iff some NON-anonymized evaluation plan of the file's event both assigns that reviewer and passes isSubmissionInReviewerScope for the file's submission; anonymized plans never grant file access. reviewerHasPlanForEvent is deleted outright (no compatibility shim). Denial stays 403 on this surface, consistent with existing file-authz semantics.

## Amendment (wave 54): ONE reviewer-file-scope resolver, and the DEC-170 grant is READ-only

authzServeFile (src/routes/files.ts:547-566) computes `reviewerInScope` and passes it to canAccessFile; authzFileRead (files.ts:414-419) calls `canAccessFile(auth, scope)` with NO options, and files-authz.ts:148 returns `opts?.reviewerInScope === true` — so a reviewer holding a valid DEC-170 grant is always 403'd on GET/POST /api/v1/files/:fileId/comments. authzSubmissionRead (files.ts:88-103) refuses reviewers outright, so GET /api/v1/submissions/:id/files never hands a reviewer a file id either: the grant is unreachable through every door, and DEC-170 is a decision with no code. Two readers of one predicate, one of which forgot the argument. Rule: the reviewer-in-scope computation (including the `reviewer && !scope.submissionId -> 403` guard) lives in exactly one helper that BOTH authz paths call, and authzSubmissionRead admits a reviewer under the same predicate. The grant is READ-only: authzFileWrite refuses role 'reviewer' explicitly rather than inheriting the read predicate (a WRITE gated by a READ predicate is the house's standing bug) — the comment thread stays the organizer/speaker channel.
