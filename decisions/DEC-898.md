# DEC-898: A pipeline column accepts a dropped card, and a stage picker opens on the stage you are in

app/src/pages/contacts/PipelineBoard.tsx offers stage movement only through a per-card 'Move to' select (:186, :316) and no drag affordance, though the 08-contacts frame's pipeline is a drag board and the app already owns a drag contract -- app/src/pages/agenda/DayGrid.tsx sets the moved entity's id in text/plain on dragstart and reads it on drop. Inventing a second drag idiom for the second drag surface is how vocabularies desync. The select also opens on a blank option rather than the entry's current stage, so a control that could report state instead reports nothing. Rule: cards become draggable and columns become drop targets using the agenda's exact dragstart/dragover/drop contract; a drop calls the SAME stage-change request the select already calls (one write path, so the optimistic update and its loud rollback are written once); the select is KEPT as the keyboard and assistive path -- a drag-only board is unreachable for some organizers -- and its value is the entry's current stage; and within-column fit ordering (sortByFit) is untouched, because a drop changes stage, never rank.

## Amendment (wave 4): a pipeline card is DRAGGED, not configured -- the per-card MOVE TO select leaves the card face

All 20 cards carry a `Move to` select defaulting to their own stage (PipelineBoard.tsx:237-241); gate-4 calls it the single largest layout deviation on the screen (cards ~40% taller than the frame). The capability must not die with the control: DEC-898's "a stage picker opens on the stage you are in" is satisfied by the opened-card panel (PipelineBoard.tsx:276 already passes onMove), which is also the keyboard path. Ruling: the card face carries identity + fit + rationale + staleness only; stage change happens by drag or through the opened card's picker, and the board header states the affordance ("N people - drag between columns") so the gesture is discoverable.
