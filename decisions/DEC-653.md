# DEC-653: The SPA has no second upload vocabulary: delete the mirror, import the pure core

The former app/src/pages/content/upload-validation.ts (deleted per this decision's ruling below) hand-copied the DEC-020 allowlist and caps, and it is ALREADY WRONG: it caps .txt/.md at 8 MB (TEXT_MAX_BYTES = MEDIA_MAX_BYTES, line 16) while the server authority allows 25 MB (src/domain/files.ts:50), so a 12 MB .md is rejected in the browser with a message the server disagrees with — silent capability loss plus a false explanation. src/domain/files.ts even exports ALLOWED_UPLOAD_EXTENSIONS documented as "for UI hints (accept attr, help text)" with no consumer, and the file input carries no `accept` at all. DEC-002 made pure-core node/cf-free precisely so a browser bundle could share it; app/src/pages/content/types.ts re-declaring 'presentation'|'poster'|'handout' is the same duplication. Delete both copies (no compat shim, house rule) and import FILE_KINDS / validateUpload / uploadHintText / ALLOWED_UPLOAD_EXTENSIONS directly. Hand-copied vocabularies drift — IMPORT them.


## Amendment (wave 28): an upload refusal names the accepted formats, why they are the accepted formats, and what survived — from the pure core's own list

UploadZone.tsx:32 already validates through the pure core and refuses correctly, but prints only check.message ('File exceeds the 250 MB limit') inside a .chq-error box: no format list, no reason, and nothing about the version that is still current — so a replace that is refused is indistinguishable from a replace that destroyed the previous file. DEC-653 forbids a second upload vocabulary in the SPA, so the accepted-format sentence must be derived from allowedUploadExtensions(kind)/uploadHintText(kind) already imported at UploadZone.tsx:2, never re-typed. Ruling: the refusal renders the standard's field register (control gets .chq-field-invalid + aria-invalid, message in .chq-field-error with role=alert), states which formats and why in one clause, and — when replacesFileId is set — closes with the survival line 'The current file is unchanged. Nothing was replaced.'

## Amendment (findings wave 5): a refusal that discards the file the user chose is a modal, not an inline ribbon

UploadZone renders a rejected upload as a <span class="chq-field-error"> inside the dashed strip (UploadZone.tsx:112-122). The frame draws it as a 560px dialog (docs/design/Chautauqua Content.dc.html :431-457): "That file was not uploaded" over the session and deliverable kind, an error band (1px ink border, 4px ink left edge, sunk fill) carrying "<filename> is not a slide format" and the why-these-formats sentence, a "What was kept" block, and a footer of Choose another file / Cancel. The distinction is not decorative: an inline ribbon can scroll out of view while the user's file is already gone, which is exactly the error standard's "say what was kept / offer the way out" case. RULING: a validateUpload refusal opens the framed modal through the shared ModalFrame vocabulary; an onUpload network/server failure keeps its existing inline treatment, because that one is a retryable failure of the act, not a refusal of the file.
