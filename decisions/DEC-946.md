# DEC-946: A cron job that catches per-item failures must still fail the tick

src/server/scheduled.ts wraps each job in its own try/catch and rethrows an aggregate naming every job that failed (DEC-812). But runDueReminders (src/routes/tasks.ts:521-537) catches EVERY per-event failure and only console.errors, so it can never reject — which makes `failures.push("runDueReminders")` at scheduled.ts:26 dead code that has never executed. A mailer outage therefore drops every J6 due-date reminder for every event and the tick reports success, against SPEC §2.6's fail-loudly principle and against the house rule that a decision with no code is a lie. The per-event isolation itself is correct (DEC-238 class 1: one bad row must not cost every other event its reminders) — what is missing is the second half of that pattern. Rule: runDueReminders keeps the per-event try/catch and keeps going, collects the failing eventIds, and after the loop throws one aggregate Error naming every event that failed and how many; a tick where every event succeeded still resolves. The same shape scheduled.ts already uses for jobs, applied one level down. A test proves both halves: with a mailer that throws for exactly one of three events, the other two still receive their sends AND runDueReminders rejects with a message naming the failing eventId.
