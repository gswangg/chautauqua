# DEC-456: "Does this person already have an account?" is answered by contact_id (OR email), never by email alone; contact.email writes cascade to the linked user row or fail with 409

Three call sites decide portal_link vs. a freshly minted claim token by asking for a user whose EMAIL matches the contact's: src/routes/comms/compose-core.ts and src/routes/api/contacts/bulk-email.ts:34 (both via findUserIdByEmail, duplicated at src/server/repo/comms.ts:204 and src/server/repo/contacts/bulk.ts:25) and src/routes/public/submit.tsx:742 (findUserByEmail, src/server/repo/submit.ts:195). Nothing keeps user.email in step with contact.email: src/server/repo/contacts/crud.ts:99 rewrites contact.email alone, and src/server/repo/contacts/merge.ts:192 repoints user.contact_id without touching user.email. After either, those three sites report "no account", mint a claim link, and src/routes/auth.tsx:291-298 -- whose duplicate check is `eq(schema.user.email, contact.email)` only -- inserts a SECOND speaker user row against the same contact_id. Two rules, both stated here so no worker guesses: (1) the identity question is answered by one repo helper, findAccountUserId(db, {contactId, email}), a single select with `or(eq(user.contactId, contactId), lower(user.email) = lower(email))` -- contact_id catches the desync, email still catches an organizer account that owns the address but no contact row; the three email-only helpers are DELETED, not wrapped (house rule: no compatibility shims). (2) patchContact keeps login working: when the patch changes contact.email it also updates the user row linked by contact_id, and if a DIFFERENT user already owns the target address (user.email is uniqueIndex user_email_idx, the former src/db/schema.ts:45 (now split across src/db/schema/)) it throws ApiError("conflict") BEFORE any write -- repos already throw ApiError (13 files under src/server/repo do), so this needs no new machinery and keeps the route layer out of it. Merge is explicitly EXCLUDED from the cascade: two merged contacts can own two user rows and rewriting both emails would violate user_email_idx; rule (1) is what makes that safe, so src/server/repo/contacts/merge.ts is not to be touched.


## Amendment (wave 71): "does this person already have an account?" has ONE deterministic answer — contact_id beats email, in the single-row path exactly as in the batch

`findAccountUserIds` (src/server/repo/comms.ts:340-368) declares a priority in its own doc comment and implements it ("Associates hits back by contactId first, then by lowercased email", :363-364). Its single-row sibling `findAccountUserId` (:316-322), which the comment at :332 says expresses "the SAME predicate", is an `or(user.contactId = X, lower(email) = Y)` with `.limit(1)` and NO ORDER BY — SQLite picks the winner. When a contact's linked user row and an email-matching user row are different rows the two functions disagree, and the answer decides whether an unauthenticated submitter's confirmation email carries `/portal` or a freshly minted claim link (`src/routes/public/submit-post.tsx:496`) and whether a claim link creates an account or bounces to `/login` (`src/routes/auth-claim.tsx:114`). This is the DEC-248 wave-70 shape in a second file: an `or()` + `limit(1)` with no ORDER BY lets the database decide a credential question. The batched sibling is also not fully deterministic — its query has no ORDER BY, so `byContactId`/`byEmail` last-write-wins is arbitrary when two rows share a key. One implementation serves both: the single-row function delegates to the batch, and the batch's query orders by `user.id`.
