# DEC-456: "Does this person already have an account?" is answered by contact_id (OR email), never by email alone; contact.email writes cascade to the linked user row or fail with 409

Three call sites decide portal_link vs. a freshly minted claim token by asking for a user whose EMAIL matches the contact's: src/routes/comms.ts:291 and src/routes/api/contacts/bulk-email.ts:34 (both via findUserIdByEmail, duplicated at src/server/repo/comms.ts:204 and src/server/repo/contacts/bulk.ts:25) and src/routes/public/submit.tsx:742 (findUserByEmail, src/server/repo/submit.ts:195). Nothing keeps user.email in step with contact.email: src/server/repo/contacts/crud.ts:99 rewrites contact.email alone, and src/server/repo/contacts/merge.ts:192 repoints user.contact_id without touching user.email. After either, those three sites report "no account", mint a claim link, and src/routes/auth.tsx:291-298 -- whose duplicate check is `eq(schema.user.email, contact.email)` only -- inserts a SECOND speaker user row against the same contact_id. Two rules, both stated here so no worker guesses: (1) the identity question is answered by one repo helper, findAccountUserId(db, {contactId, email}), a single select with `or(eq(user.contactId, contactId), lower(user.email) = lower(email))` -- contact_id catches the desync, email still catches an organizer account that owns the address but no contact row; the three email-only helpers are DELETED, not wrapped (house rule: no compatibility shims). (2) patchContact keeps login working: when the patch changes contact.email it also updates the user row linked by contact_id, and if a DIFFERENT user already owns the target address (user.email is uniqueIndex user_email_idx, src/db/schema.ts:45) it throws ApiError("conflict") BEFORE any write -- repos already throw ApiError (13 files under src/server/repo do), so this needs no new machinery and keeps the route layer out of it. Merge is explicitly EXCLUDED from the cascade: two merged contacts can own two user rows and rewriting both emails would violate user_email_idx; rule (1) is what makes that safe, so src/server/repo/contacts/merge.ts is not to be touched.
