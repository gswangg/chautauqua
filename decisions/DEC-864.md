# DEC-864: A rail that prints N segment counts scans the directory ONCE: one bounded pass, the same matchesSegment predicate, N counts

VERIFIED. src/routes/api/contacts/segments.ts:102-106's `segmentCount` calls `listContactsForOrg(db, orgId, {page:1, perPage:1, segmentId})`, and line 117-119 runs it once PER SEGMENT inside a Promise.all on every GET /segments. Because `segmentId` is set, each of those calls takes crud.ts:349-361's documented whole-directory branch: `scanAndFilterContacts` re-reads the org's entire contact table (narrow projection, `.limit(MAX_CONTACT_DIRECTORY_SCAN + 1)` = 20,001 rows), `findSegmentForOrg` re-reads the segment row the caller is already holding, and the final page window re-hydrates one full row — three statements and one full scan per segment, for a caption. The Contacts page loads this on mount and again after every segment save or delete. At the spec's own scale target (SPEC §2.2 'Every table assumes thousands of rows… A feature that demos well with 10 rows and dies at 2,000 is not built'; §7 sub-200ms admin interactions) ten segments over two thousand contacts is twenty thousand row reads and thirty-two D1 round trips to print ten numbers. The fix is not caching and not a cap: the rules are pure and the rows are identical across all N evaluations. Decision: ONE new repo function performs the bounded scan once and evaluates every rule set against that single result through the same `matchesSegment` the list path uses — so the rail's number and the filtered list it drills into remain arithmetically the same fact, which is the whole reason the count went through listContactsForOrg in the first place. The MAX_CONTACT_DIRECTORY_SCAN guard is refactored into one shared helper so there is exactly one place that refuses-rather-than-truncates, and the per-segment `findSegmentForOrg` re-read is deleted because the route already has the rows.
