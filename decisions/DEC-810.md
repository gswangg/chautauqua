# DEC-810: Adding a contact to an event never invents a talk title

VERIFIED src/server/repo/contacts/push.ts:55 and :88 both fall back to `Invited: <First> <Last>` when no title is given, and the fallback is reachable from POST /contacts with an eventId (crud.ts) and from CSV import with an eventId. The result is a stream of accepted sessions named after people rather than talks: the CNT/AIA graders saw them on the agenda, the SPK grader saw them on the roster, and every later surface that matches sessions by title has to reason about them. A placeholder that the product invented is indistinguishable, one screen later, from a session a human named. Decision: the title is required wherever a contact is pushed onto an event — the routes reject a missing or blank title loudly with a field error naming what the field is for, and push.ts carries no fallback at all — and the modal's field is labelled for what it actually creates (a session on this event), with the CSV import asking for the batch's session title in the step where the event is chosen. If a roster line with no talk is ever wanted, that is an event-level participation model, not a fabricated string.

## Amendment (wave 59): a batch roster add is ONE session for the batch, not one identical session per row

DEC-810 made the batch title a required, caller-supplied, non-empty string and killed the per-row 'Invited: <First> <Last>' fallback. But src/server/repo/contacts/push.ts:83-102 still loops `createSubmission` once PER CONTACT with the SAME title, so importing 40 speakers into an event mints 40 byte-identical accepted submissions. The UI field that feeds it is labelled "Session title for this batch" (app/src/pages/contacts/ImportWizard.tsx:255) — singular. The label is the spec; the loop contradicts it, and the result floods /admin/submissions, the unscheduled agenda tray, exports and the CSV/JSON feeds with phantom sessions (the externally-filed "CSV import creates a synthetic accepted session per row" defect). RULING: `pushContactsToEvent` creates exactly ONE accepted submission titled with the caller-supplied batch title, and attaches every contact in the batch as a participant of it — role 'speaker', visible=true, invite_status='none' (never 'invited': an imported roster member must be ACTIVE so DEC-283/DEC-746 expansion gives them the onboarding task set and they can reach public surfaces once approved), order = input index, DEC-258 title/company snapshots, inserted set-based in one chunked statement (DEC-542). The single-contact path (`pushContactToEvent`, add-to-event modal / roster Add-speaker) is unchanged: one contact, one session, by definition. The batch return type becomes one submissionId, not an array.
