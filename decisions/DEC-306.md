# DEC-306: The contacts-merge task_assignment tie-break is CORRECT as written; the review-lens claim against it is refuted and must not be 'fixed'

A reviewer flagged src/server/repo/contacts/merge.ts (commit 50a2947, DEC-282) as having dedupe logic 'subtly backwards', claiming that the else branch 'silently keeps the merge row arbitrarily rather than the kept row' in the both-pending and both-complete cases, and that deleting keepTask.id discards assignment history. I read the loop at S. For each shared taskId it computes mergeComplete/keepComplete and pushes keepTask.id into the delete list ONLY when `mergeComplete && !keepComplete`; every other case — both pending, both complete, keep-complete-only — pushes mergeTask.id, so the KEPT row survives. That is the opposite of what the review claims, and it is the correct reading of the comment 'completion is never lost'. The surviving merge row in the one asymmetric case is not orphaned either: I confirmed `task_assignment` is one of the seven entries in CONTACT_FK_TABLES (src/server/repo/contacts/query.ts:108-116), so step (f) repoints it from mergeId to keepId before the merged contact row is deleted. Exactly one row per (task, contact) must survive a merge by construction — 'preserving both histories' is not a coherent post-merge state. Recording this as binding so no future wave burns a product commit reverting correct code on the strength of a misread, and so the wave-11 triage-closure lane does not open it as a finding.
