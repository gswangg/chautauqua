# DEC-540: iCalendar TEXT property values are control-byte sanitized at the SERIALIZER, exactly as DEC-499 did for PARAM values -- the output's only control bytes are its CRLF terminators

DEC-499 hardened CN *parameters* against injection at src/mail/ics.ts's serializer, with the exact reasoning that one of the three CN sources "originates in unauthenticated public CFP text answers". The property VALUES were never given the same treatment: escapeText (src/mail/ics.ts:59) normalizes CR/CRLF to \n and escapes backslash/;/, but passes every other C0 control byte (NUL, \x01-\x08, VT, FF, \x0e-\x1f) and DEL through raw into SUMMARY, DESCRIPTION and LOCATION. RFC 5545 TSAFE-CHAR excludes CTLs, so one submitter pasting a NUL into a talk title emits an invalid VEVENT into GET /e/:slug/agenda.ics -- a public, unauthenticated feed where one bad title breaks the whole event's calendar for every subscriber, and into the METHOD:REQUEST invites compose sends. test/ics-crlf-escaping.test.ts covers only CR/LF for these values and only CTLs for CN, so nothing catches it. Note the irony DEC-539 just established: a raw NUL is the byte that makes a file binary to every globbed scan this codebase's correctness strategy rests on, and here we would emit one over HTTP. Decision: (a) ONE exported `sanitizeIcsText(s: string): string` in src/mail/ics.ts is the single path from any string to a TEXT property value -- it normalizes CRLF and lone CR to LF, strips every remaining C0 control byte and DEL (HTAB included: it carries no meaning on a one-line SUMMARY and stripping it matches sanitizeCn's rule exactly), then applies the existing backslash/;/,/newline escaping. (b) It is applied INSIDE the serializer at buildVevent's SUMMARY/DESCRIPTION/LOCATION, never at a call site, for DEC-499's stated reason -- these values reach the serializer from public CFP answers, admin edits, and room names, and a call-site rule is a rule someone forgets. (c) The regression bar is a property, not an example: for every byte in 0x00-0x1f and 0x7f, a calendar built with that byte in title/description/location contains no control byte anywhere except the CRLF line terminators, and every raw line still starts with a known property name or a fold-continuation space. (d) Deliberately out of scope, so it is not re-raised: the mailto: addresses, which are already constrained by isValidEmail upstream and by the ICS_ORGANIZER_EMAIL constant.
