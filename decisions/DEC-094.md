# DEC-094: Perf-smoke 301-id cap probe: keep the 200/page clamp and the 300-accepted seed; the probe paginates for the 300 real ids and appends one syntactically-valid nonexistent id

task-w3-d's FAIL exposed a three-way collision: fetchAcceptedSubmissionIds requested perPage=301 in one page, but DEC-013's clampPerPage (src/lib/pagination.ts) caps at 200, and DEC-088's perf seed creates exactly 300 accepted submissions (aligned with 300 schedule slots). Ruling: both product invariants stand unchanged — no clamp exception, no seed-count bump. Instead fetchAcceptedSubmissionIds paginates at perPage=200 across successive pages (failing loudly if the server returns fewer than requested), and the DEC-080/089 cap probe builds its 301-id list as the 300 real accepted ids plus exactly one syntactically-valid nonexistent id (e.g. sub_cap_probe_nonexistent_0001). This is honest, not gaming: the former src/routes/public.tsx:580-583 (now split across src/routes/public/) rejects on the raw ids-list length BEFORE any DB hydration — that is the entire point of the cap (refuse oversized requests without doing work) — so a nonexistent 301st id exercises exactly the intended rejection path. The 150-id timed check is unaffected (single page under the clamp).
