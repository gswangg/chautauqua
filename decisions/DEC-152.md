## Amendment (wave 76): `social_links_json` has ONE parser on every wire — the organizer CRM projection is the last member still hand-parsing it, and the SPA's type and mocks describe a shape the server never emits

`serializeSocialLinks` (`src/server/repo/profile.ts:58-65`) deliberately OMITS empty keys, so the stored JSON is routinely partial. Every reader normalises that back to four string keys through `parseSocialLinks` (`:34-52`) — `src/server/repo/contacts/rows.ts:59`, `src/server/repo/profile.ts:110`, `src/server/repo/public/detail.ts:150`, `src/server/repo/exports/speakers.ts:155` — except one: `serializeContact` (`src/routes/api/contacts/shared.ts:52`) returns `row.socialLinksJson ? JSON.parse(row.socialLinksJson) : null`. That one exception is the organizer CRM wire, the surface DEC-152 exists for and the one SPK-08 sends the judge through, so a returning speaker's record is the single place where `socialLinks` arrives partial or `null` while every other view of the same row arrives complete. The drift has already propagated into the client's idea of the contract: `app/src/pages/contacts/types.ts:52-57` declares all four members `string | null` and `:67` declares the object itself `| null`, and the render-test mocks (`ContactDrawer.render.test.tsx:50`, `ContactDrawer-field-errors.render.test.tsx:30`) assert against `linkedin: null` — a value the server cannot produce, which is DEC-663's "a mock that matches nothing is a contract with itself". RULING: `socialLinks` is ALWAYS present on a serialized contact and ALWAYS carries `twitter`/`linkedin`/`github`/`website` as strings, empty string meaning not set — never `null`, never a missing key, never a `null` member. `serializeContact` derives it through `parseSocialLinks`, the one parser; the SPA type drops its optionals and nulls; the mocks are corrected to the emitted shape. Storage is untouched — `serializeSocialLinks` keeps omitting empties; this is a ruling about the WIRE, whose job is to be the same shape for every reader.
