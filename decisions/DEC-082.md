# DEC-082: Multi-round evaluation implemented (closes the "rounds" dead knob): evaluation_plan.current_round + advance-round endpoint; queue/rating/results operate per round

J4 promises "optional multiple rounds" and the schema already stores evaluation.round with per-round uniqueness (DEC-018), but the PUT hardcodes round=1 while accepting and persisting plan.rounds — a silently dead knob, against fail-loudly. Rather than reject rounds!=1, implement minimally: migration migrations/0005_review_rounds.sql (superseded by DEC-087, which renumbers it to migrations/0009_review_rounds.sql) adds current_round integer NOT NULL DEFAULT 1 to evaluation_plan (hand-written SQL + meta journal/snapshot per the 0004_wave3 pattern, DEC-015 append-only). Validation: rounds must be an integer ≥1 on create; on PATCH additionally ≥ current_round. POST /api/v1/plans/:id/advance-round (organizer + csrfJson) increments current_round while < rounds, else 409. The reviewer queue counts/filters evaluations of the current round only; the rating PUT binds round = plan.currentRound; results and progress accept ?round= (integer, 1..rounds) defaulting to current_round and aggregate only that round's evaluations. Admin UI shows "Round X of Y" with an Advance button (currentRound < rounds) and a results round selector when rounds > 1.

## Amendment (wave 43): plan `rounds` is a bounded small integer (MAX_PLAN_ROUNDS = 10) at all three writers — a server integer a client turns into an array length is bounded at the boundary

parseRounds (src/routes/review/shared.ts:171-182) enforces only `Number.isInteger(rounds) && rounds >= 1`. Three writers set it: POST /api/v1/events/:eventId/plans (plans-crud.ts:73), PATCH /api/v1/plans/:id (plans-crud.ts:122, floored at currentRound only), and POST /api/v1/plans/:id/waves (plans-crud.ts:256, `plan.rounds + 1`). The SPA turns the stored value straight into an array length in three production sites — app/src/pages/review/PlanEditor.tsx:365 and :1299, app/src/pages/review/ResultsTable.tsx:300 all do `Array.from({ length: rounds })` — so one organizer-authenticated POST with rounds: 1e9 permanently bricks that plan's editor and results page (and inflates roundCriteria's JSON keyspace) for every organizer in the org. This is w42-a's shape one level up: an integer is not a bound, and the reader cannot defend itself. SPEC J4 asks for "optional multiple rounds"; real committees run two or three, so 10 is generous while keeping the round strip and the roundCriteria map renderable. The bound belongs at the boundary predicate (so all three writers inherit it) AND explicitly at the wave ratchet — a bound on POST/PATCH that the ratchet can walk past is not a bound. Field-guide shape: A COUNT THE CLIENT TURNS INTO AN ARRAY LENGTH IS A CLIENT-SIDE DoS UNLESS THE BOUNDARY BOUNDS IT.
