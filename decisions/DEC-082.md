# DEC-082: Multi-round evaluation implemented (closes the "rounds" dead knob): evaluation_plan.current_round + advance-round endpoint; queue/rating/results operate per round

J4 promises "optional multiple rounds" and the schema already stores evaluation.round with per-round uniqueness (DEC-018), but the PUT hardcodes round=1 while accepting and persisting plan.rounds — a silently dead knob, against fail-loudly. Rather than reject rounds!=1, implement minimally: migration migrations/0005_review_rounds.sql adds current_round integer NOT NULL DEFAULT 1 to evaluation_plan (hand-written SQL + meta journal/snapshot per the 0004_wave3 pattern, DEC-015 append-only). Validation: rounds must be an integer ≥1 on create; on PATCH additionally ≥ current_round. POST /api/v1/plans/:id/advance-round (organizer + csrfJson) increments current_round while < rounds, else 409. The reviewer queue counts/filters evaluations of the current round only; the rating PUT binds round = plan.currentRound; results and progress accept ?round= (integer, 1..rounds) defaulting to current_round and aggregate only that round's evaluations. Admin UI shows "Round X of Y" with an Advance button (currentRound < rounds) and a results round selector when rounds > 1.
