# DEC-492: One atomic, set-based ics_sequence bump; auto-schedule's write burst is bounded and declared

Two implementations of the same invariant exist. src/server/repo/comms.ts:306-313 does the correct atomic SQL increment (icsSequence + 1). the former src/server/repo/agenda.ts:426-437 (now split across src/server/repo/agenda/) reads the current value and writes current + 1 -- a lost-update race on the one field docs/clarifications.md:12-14 makes load-bearing ("the initial invite usually has no room; the room is assigned later -- so invite updates, same UID bumped SEQUENCE, are the flow that matters"): two concurrent slot writes can leave SEQUENCE frozen and every calendar client silently keeps the stale time. That read-then-write also costs 2 statements, and runAutoSchedule (agenda.ts:500-513) pays it plus a single-row INSERT for every placement inside a serial loop with no bound on placements at all -- 15 rooms x 5 days of grid slots is thousands of statements in one request, the exact unbounded-write-burst class DEC-478/485 closed for the import, here without even a declared cap (DEC-298's AUTO_SCHEDULE_BOUNDS guards the CPU loop, not the writes). Decision: one exported bumpIcsSequences(db, submissionIds) in a new src/server/repo/ics-sequence.ts -- atomic SQL increment, chunked set-based UPDATE ... WHERE id IN (...) via src/lib/chunk.ts -- replaces both, with the old singular helper deleted outright (no compatibility wrapper); runAutoSchedule writes placements as chunked multi-row INSERTs and bumps once at the end; MAX_AUTO_SCHEDULE_PLACEMENTS = 2000 is declared and enforced by leaving the overflow unplaced rather than failing the run, which is J9's warn-never-block rule (the payload's existing unplaced count already reports it and a second run continues).

## Amendment (wave 46): auto-schedule's bulk slot write obeys the single-slot writer's atomicity rule, and its write-burst cap reports what it dropped

Two independent failures in the same twelve lines of src/server/repo/agenda/auto-schedule.ts. (1) Line 101 `.slice(0, MAX_AUTO_SCHEDULE_PLACEMENTS)` discards placements that autoSchedule already SUCCEEDED at computing: they are not in `unplacedFromRun`, so they never reach unplacedReasons (:135-143) and the producer finds them back in the unscheduled tray with no reason at all — a silent truncation this codebase refuses everywhere else (MAX_ACCEPTANCE_TASK_ASSIGNMENTS, EXPORT_MAX_ROWS, ARCHIVE_MAX_TOTAL_BYTES all throw). J9's rule that auto-schedule warns and never blocks stands, so the remedy is not a throw: the dropped tail is REPORTED, entering unplacedReasons under a new UnplacedReason 'write_cap_reached' whose copy names the cap and the count. A cap the caller cannot see is indistinguishable from a bug. (2) Line 115 does `db.insert(schema.scheduleSlot).values(chunk)` per chunk with no conflict clause against the schedule_slot_submission_id_idx uniqueIndex — reintroducing exactly the read-then-write race upsertSlot closed under DEC-552 ('one atomic statement'), so two concurrent or retried POST /events/:id/agenda/auto-schedule calls leave earlier chunks committed and 500 the loser. Ruling: each chunk becomes `.onConflictDoNothing({ target: schema.scheduleSlot.submissionId }).returning({ submissionId })` — the established pattern in src/server/repo/pipeline.ts:276-279 and portal-edit.ts:538-539 — and bumpIcsSequences is called with exactly the returned ids, never the requested list, because a SEQUENCE bump naming a row this run did not write is a lie to every subscribed calendar. A slot that appeared between the read and the write is left alone; a re-run is a no-op.
