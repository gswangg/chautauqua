# DEC-562: A submission's people and its answers have ONE order, expressed in SQL, at every surface that renders them

DEC-560 is fixing list-valued cells inside `src/server/repo/exports/`, but the same two lists are rendered arbitrarily everywhere else. Speakers: `arr.sort((a, b) => a.order - b.order)` at repo/submissions/list.ts:207 (the J3 table), repo/agenda.ts:270 (the admin agenda payload the day grid and its .ics ATTENDEEs read), repo/files-library.ts (~199), plus `.orderBy(participant.order)` alone at repo/submissions/detail.ts:132 and `.orderBy(asc(participant.order))` alone at repo/public/sessions.ts:266 (every public session card and detail page). `participant.order` ties are the norm, not the exception — submit.ts:259 and submissions/create.ts:101 both write literal `order: 0`, and cloneSubmission copies orders verbatim — so a two-speaker session prints its authors in whatever order SQLite returned, and can print them differently on the next refresh of unchanged data. Answers: repo/portal.ts:268-276 returns a speaker's own submission answers with no ORDER BY, and src/routes/portal/index.tsx:246 renders that array straight into a <dl>, so the speaker's view of their own proposal reorders between visits. This is DEC-534's rule (a LIMIT obliges a total order) generalized to its sibling: a LIST a human reads obliges a declared one. Decision: the canonical orders are `(participant.order asc, contact.id asc)` for any list of a submission's people and `(form_field.position asc, form_field.id asc)` for any list of a submission's answers, and both are expressed in the SQL ORDER BY rather than a JS sort wherever the query isn't chunked (where DEC-078 chunking breaks the SQL order, the accumulated array is sorted by the identical keys and that JS sort is the tiebreak of record). No shared comparator module is introduced — the rule lives in the ORDER BY, so no task has to wait on another's helper. Scope fences, so no two decisions own one line: `src/server/repo/exports/*` belongs to DEC-560 (in flight) and is NOT touched; `src/server/repo/review/submissions.ts` belongs to DEC-561; overview.ts's `pickLeadSpeaker` already carries DEC-558's contactId tiebreak. The regression bar is a repeat: hand the same rows in reversed order and the rendered list is byte-identical.
