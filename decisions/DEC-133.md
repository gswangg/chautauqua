# DEC-133: Bulk submission status change enforces a DEC-122-style full-set id match before any side effect: unknown/foreign ids yield 400 invalid naming the missing ids

updateSubmissionStatuses (src/server/repo/submissions/status.ts) silently drops requested ids that don't belong to the event and reports updated: rows.length, so a producer bulk-accepting with stale or foreign ids gets 200 OK — a silent contract violation of the fail-loudly principle and inconsistent with the comms path's DEC-122 requireFullMatch. Fix: after the chunked event-scoped SELECT and BEFORE the acceptance-planning/update loop (atomicity — nothing mutates when the check fails), dedupe requested ids, compute missing = uniqueRequested minus found, and if any are missing throw new ApiError('invalid', 'One or more submission ids do not belong to this event', { ids: `unknown ids: ${...}` }) (repo modules already import ApiError from ../http, e.g. src/server/repo/events.ts:8). Duplicate ids in the request are tolerated via dedupe; after the guard, updated = rows.length = distinct requested submissions, so the count is truthful.
