# DEC-930: A speaker has ONE event-scoped detail page at /admin/speakers/:contactId, served by ONE bounded GET

The GATE-1 SBEK report names the Speakers grid the number-one eval lever with a measured -11 and asks for 'a per-speaker detail row the agent can read in one snapshot': today the answer to 'what does this person owe me, and where is the evidence' is spread across 27px grid cells, a response modal, a participation menu and the Contacts drawer, none of it addressable by URL. Decision -- the wire contract, which neither implementing task may change: GET /api/v1/events/:eventId/speakers/:contactId (requireOrganizer + the file's existing assertEventOwnership; 404 for a contact who is not on this event's roster, existence-hiding like every other nested read) returns EXACTLY {contact:{id,name,email,company,title,hasAccount}, participation:{participantId,submissionId,inviteStatus}, sessions:[{submissionId,ref,title,status,contentStatus,role,scheduled:{day,startMin,endMin,roomName}|null}], tasks:[{assignmentId,taskId,title,kind,required,dueDate,status,completedAt,file:{id,filename,sizeBytes,versionNo}|null}], counts:{outstandingRequired,overdue}}. Every array comes from ONE query for the whole set -- the file join is the same join the DEC-920 grid cells already carry, never a query per task -- roster membership composes rosterParticipantConditions (DEC-829) and overdue composes the existing DEC-801 effective-due-date predicate rather than re-typing its grace window. The SPA renders it as a page whose rows are links (session -> /admin/submissions/:id, deliverable -> its download, form response -> its response view), so every action the grid offers is one click from one snapshot, and the grid's name cell becomes the link into it.
