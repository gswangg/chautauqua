# DEC-996: The production mailer is the Cloudflare Email Service send_email binding; Resend is deleted, not mis-typed

wrangler.jsonc:27-31 declares Cloudflare Email Routing's `send_email` binding, whose runtime API is send(new EmailMessage(from, to, rawMime)) and which only delivers to VERIFIED destination addresses — never an arbitrary speaker inbox. src/mail/email-binding.ts:41 calls env.EMAIL.send({to, from, subject, html, text, attachments}), a shape that binding does not have, and src/server/env.ts:19 self-types EMAIL as our own EmailSender interface, so the mismatch compiles, every test runs DevSinkMailer, and nothing anywhere can observe that production email cannot send at all. A decision with no code is a lie; an adapter that cannot work is worse, because it reads as done. SPEC.md §4 (line 239) names the stage-2 adapter as Resend, and docs/clarifications.md line 31 requires that emails actually send on an MVP basis — so the honest adapter is a plain fetch to https://api.resend.com/emails with an injected fetch (pure, testable, no key needed to compile or test), selected when RESEND_API_KEY is present. Provisioning that key and the sending domain stays operator/stage-2 work and is explicitly NOT in this scope; what lands is the adapter, the binding's removal, and a makeMailer that throws loudly in production when neither dev mode nor a key is configured rather than selecting a mailer that silently fails.

## Amendment (wave 43): mail configuration is a first-class READ (mailConfigStatus), surfaced in Settings

Switching production mail to Resend made 'is mail configured' an operational fact with no reader — the only way to discover it was a 500. One predicate, mailConfigStatus(env) in src/server/env.ts, returns { provider: 'dev-sink'|'resend'|'none'; configured: boolean; fromEmail: string|null } and is the single source for (a) makeMailer's selection, (b) GET /api/v1/mail-status, (c) the Settings 'Email' definition row that reads 'Sending as <addr>' or 'NOT CONFIGURED — sends will fail'. The status never echoes the key. This is the loud half of DEC-547's amendment: config errors surface where the operator configures, not where the speaker submits.

## Amendment (wave 62): the outbound MIME serializer is a boundary — every header value is stripped of CR/LF and encoded-word wrapped when non-ASCII, every message carries Date and Message-ID, and a calendar part is a SIBLING of the alternative, never a child

src/mail/email-binding.ts:42 interpolates `Subject: ${m.subject}` into a string joined with \r\n. Nothing on the path strips CR/LF from {talk_title} — src/forms/validate.ts:93 length-checks `text` answers and nothing else — so an unauthenticated CFP submission titled `X\r\nBcc: ...` injects headers into every production acceptance/decline mail. src/mail/ics.ts already settled the precedent for exactly this class (DEC-499/DEC-540: strip at the SERIALIZER, not upstream, because the value arrives from three call sites one of which is anonymous public text); the MIME serializer never got the same rule. Two structural defects ride along: :44 opens multipart/alternative and :57-67 pushes the text/calendar part into that same container, so a client renders the calendar INSTEAD of the body (it must be multipart/mixed around a multipart/alternative), and :39-45 emits neither Date: nor Message-ID:, both mandatory in RFC 5322 and both used by Gmail/Outlook spam scoring — against docs/clarifications.md's ONE hard email requirement ("a standards-compliant .ics email … for Gmail/Outlook/iCal"). A raw non-ASCII byte in a header is likewise illegal without an RFC 2047 encoded-word. The rule: buildRawMime owns header safety for every value it interpolates (subject, display names, ics filename), body parts are base64 so no body byte can impersonate a boundary or break the 998-octet line limit, boundaries are per-message random, and the .ics rides multipart/mixed. Unexercised until now because DevSinkMailer (src/mail/dev-sink.ts:13) never builds MIME, so every test, walkthrough and DEV_MODE=1 run bypasses this file entirely — which is why the regression bar is a hostile-input unit test, not a walkthrough.

## Amendment (wave 70): every MIME body part is transfer-encoded within its own line limit — base64 folds at 76 characters

src/mail/email-binding.ts emits each part's payload as one unwrapped base64 line (:87 text, :93 html, :133 .ics). RFC 2045 caps base64 lines at 76 characters and RFC 5322 hard-limits any line to 998 octets, so any body over roughly 740 characters — against a MAX_RICH_TEXT_LENGTH of 100000 — or a multi-session .ics ships a non-conformant message. Only the dev sink is exercised by tests, so this fails first in production, against clarifications.md's "emails must actually send on an MVP basis". The house already knows this discipline: src/mail/ics.ts:84 folds at 75 octets on UTF-8 boundaries. A line-limit rule holds per SERIALIZER, so the fix is the missing twin, not a redesign: fold at the encoder, keep the injected binding/factory, the never-throwing makeMailer and the DEC-923 single-writer log ordering untouched, and pin it with a round-trip test (decode back to the original bytes), not just a length check. This is a structural repair below the runtime-evidence question the mandate reserves for the gate deploy; it changes no mailer selection.
