# DEC-534: Every LIMIT+OFFSET list ends its ORDER BY in a UNIQUE column, and the rule is enforced by a globbed scan rather than by remembering

The field guide already states the pagination shape (`page?:{limit,offset}` + count* + `id asc`) and eighteen list queries obey it. Four do not, and the worst is the one J5 names explicitly. `src/server/repo/email.ts:106` orders the comms history by `desc(sentAt)` alone with LIMIT/OFFSET; a 100-recipient compose send (DEC-019's cap) writes up to 100 email_log rows through one `this.clock.now()` per row, so a large block of rows carries the identical millisecond. SQLite is free to return tied rows in any order per statement, so paging that history can show a row on page 1 and again on page 2 while another row is never shown at all -- SPEC J5 requires "every message logged per-recipient in history", and a log you cannot page through without losing rows does not satisfy it. The same defect: `src/server/repo/contacts/history.ts:66` (`desc(sentAt)` LIMIT 20 -- "last 20 emails" becomes an arbitrary 20 out of a same-millisecond bulk send, and its submissions query at :34-46 has no ORDER BY at all), `src/server/repo/public/sessions.ts:105,124` (`asc(title)` with LIMIT/OFFSET -- two sessions sharing a title, which real conferences have, break the public show-more list), and `src/server/repo/public/speakers.ts:81` (`asc(lastName), asc(firstName)` -- two speakers with the same name break the J10 speakers directory). Decision: (a) all four sites gain a unique final term (`asc(emailLog.id)`, `asc(submission.id)`, `asc(contact.id)`), and the untiebroken email/submission history reads are fixed even though they carry no OFFSET, because the "last 20" they promise must be a stable 20. (b) The rule is guarded by a test that GLOBS `src/server/repo/**/*.ts`, finds every `.orderBy(...)` belonging to a query that also chains an offset (including the conditional `offset > 0 ? q.offset(offset) : q` idiom this codebase uses), and asserts the final ordering term names a unique column (`id` or `seq`) -- zero hand-listed file names, per the standing lesson that a hand-maintained manifest desyncs. (c) The derived rule deliberately covers only the OFFSET class; capped non-paged reads (`.limit(ROW_CAP)`, `.limit(1)`, top-N aggregates like contacts/stats.ts's `orderBy(desc(count(*)))`) are outside it and must not be swept in, because a cap's boundary row being arbitrary is a different and much smaller sin than a page repeating rows.


## Amendment (wave 1)

All four query branches in src/server/repo/public/sessions.ts order by `submission.title, submission.id` (lines 158, 179, 200, 216), so the published programme reads alphabetically with days interleaved and an untimed row mid-list; frame 10--00 reads 9:00 -> 10:45. A programme is a sequence. Ruling: ONE ordering expression, defined once in that module and used by every branch (including the cumulative show-more window, whose page order must stay deterministic — the original DEC-534 reason title alone is not a key still holds, so title+id remain the final tiebreakers): scheduled rows by day, then startMin, then endMin; unscheduled rows sort after every scheduled row. This requires the unfiltered branches to LEFT JOIN schedule_slot (the day-filtered branches already inner-join it); a left join must not multiply rows, so the join predicate stays one-slot-per-submission exactly as the day-filtered branches assume.

## Amendment (findings wave 4): ONE public time/room gutter — 126px, one token, two consumers

docs/design/Chautauqua Public and Portal.dc.html:67 measures the sessions row as `126px 1fr auto` at gap 22, and the app's own schedule rail already renders the identical time-over-room stack at 126px (src/routes/public/css/rail.css.ts:284). But `.chq-pub-session-row` (cards.css.ts:16) was widened to 268px by an earlier wave on the theory that two lines needed twice the room — they do not; 15px display over 12px muted fits 126. So the same stack renders at two widths on two surfaces of one site. Ruling: 126px, declared once as a public token and consumed by both rules, so no future wave can move one without the other.
