# DEC-596: The organiser reads the same evaluation the reviewer wrote, and anonymity is decided by the plan, not by the surface

Reviewer comments persist but appear in no organiser surface — the results table shows averages and tallies only, so the single most useful artefact of a review round is invisible to the person making the decision. One event-scoped endpoint (GET /api/v1/submissions/:id/evaluations, organizer-only) returns every submitted evaluation for a submission with plan name, round, scores, comment and submittedAt; the reviewer's identity is suppressed exactly when that plan's anonymized flag is set, decided once server-side rather than by whichever component happens to render it.


## Amendment (wave 61): 'Reviews · N of M in' counts ASSIGNED reviewers, not rows that happen to exist

SubmissionDetailPage.tsx:1147 renders the denominator as evaluations.length — the number of evaluation ROWS returned. A submission with one assigned reviewer who has not scored yet therefore reads 'Reviews · 0 of 0 in', which tells an organiser the opposite of the truth: it says nobody is expected, when someone is late. Every other progress surface in the product already distinguishes assigned from completed (plans-progress.ts's assignedExcludingRecused, PlanEditor's 'Open · N of M reviews in'), and this one screen invented a second arithmetic. Ruling: GET /api/v1/submissions/:id/evaluations grows `assigned` in its envelope — the count of distinct (planId, reviewerUserId) pairs on the event's plans whose resolved scope covers THIS submission (all-scope row, a track row matching one of the submission's tracks, or a submissionId row naming it), minus that pair's recusals — scoped to the single plan when ?planId= is present. The header renders `{submitted} of {assigned} in`. The server always sends it; the client never falls back to items.length, because a fallback is how the two arithmetics got apart in the first place.
