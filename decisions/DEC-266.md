# DEC-266: Contact search semantics: AND-of-tokens x OR-of-columns, defined once as a pure predicate, with a superset SQL prefilter

Confirmed at src/server/repo/contacts.ts:319-331 - listContactsForOrg ORs a single `%q%` LIKE across firstName/lastName/email/company independently, so a producer typing the obvious query 'Priya Raman' gets zero results, in the one module whose entire premise (J11) is finding a person you met at last year's event. Decision: q is lowercased and split on whitespace into tokens; a contact matches when EVERY token substring-matches at least one of firstName/lastName/email/company (case-insensitive). AND-of-tokens keeps precision at the 5k-contact scale target; OR-of-columns is what makes 'priya acme' and 'raman priya' both work. The semantics live in ONE pure function pair in src/domain/contacts.ts (tokenizeContactQuery / matchesContactQuery, alongside matchesSegment, DEC-002 pure core) so they are unit-testable without a DB - the repo layer has no real-D1 harness, only fakeDb stubs, so a pure predicate is the only way to test this honestly. The repo keeps a SQL prefilter that ORs every token across the four columns and then applies matchesContactQuery in the same in-memory pass that already evaluates segment rules: the OR-prefilter is provably a superset of the AND result (a row matching all tokens matches at least one), so the scan stays narrow and no true match is dropped. The co-presenter picker (GET /api/v1/contacts?q=) inherits the fix for free.
