# DEC-488: A form's field set is actually bounded, and the reorder echo obeys the list-envelope contract

The last FAIL-unowned row in docs/verification-log/task-w21-f-stage-1-completion-ledger.md is src/routes/api/forms.ts:259 (POST /forms/:formId/fields/reorder), still a bare `c.json({ items })` at this sha. test/list-envelope-enumeration.test.ts:19-22 allowlists it with the rationale "a form's field set is small and bounded by the form itself" -- and nothing enforces that: src/routes/api/forms.ts:169 createField has no ceiling, src/server/repo/forms.ts:345 reorderFields issues one UPDATE per field, and serializeForm echoes every field. That allowlist comment is narration (DEC-481), so the enumeration test is currently grading a claim rather than a fact. Decision: MAX_FORM_FIELDS = 200 is declared once in src/server/repo/forms.ts beside createField (200 is an order of magnitude above the ~15-25 questions a real CFP carries and is simultaneously the reorder write/echo burst bound); the create route rejects the 201st field with a 400 naming the number; the reorder route returns the full DEC-461(a) envelope {items, total, page: 1, perPage: MAX_FORM_FIELDS} (perPage is the real per-request ceiling, never `items.length || 1`, which DEC-466 killed); and the allowlist entry is deleted so the site is graded like every other. Separately, describeFieldDependents/deleteFieldCascade count submission_answer rows by materializing every row (src/server/repo/forms.ts:310-315, :334-338) -- a DELETE preflight on a 5,000-submission event loads 5,000 rows to produce one integer; that becomes count(*) per DEC-333.
