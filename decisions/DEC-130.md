# DEC-130: autoSchedule uses incremental day-indexed conflict checks, never per-candidate findConflicts over the full trial

src/domain/schedule.ts:141 rebuilds `[...placed, candidate]` and runs O(n^2) findConflicts for every (day, slot, room) candidate, giving sessions x days x slots x rooms x n^2 work — a CPU blowup at SPEC's "designed for the top of these ranges" scale (~15 rooms, 3-5 days, hundreds of accepted sessions). Replace with incremental indexes maintained as sessions are placed: a room index keyed `${day}|${roomId}` and a speaker index keyed `${day}|${contactId}`, each holding {startMin,endMin} intervals, seeded from `existing` (null-room sessions skipped in the room index). A candidate conflicts iff any interval in its room bucket or any of its speakers' buckets overlaps (a.startMin < b.endMin && b.startMin < a.endMin; touching intervals do NOT conflict). Placement order, greedy first-fit semantics, and all exported signatures (findConflicts, scheduleSummary, autoSchedule, types) are unchanged; findConflicts itself stays O(n^2) — it runs once per request, which is fine at n<=~800.
