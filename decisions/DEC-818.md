# DEC-818: A version number is an identity, not a position among the survivors

VERIFIED src/server/repo/files-comments.ts:59 numbers versions as `chainIds.map((id, idx) => [id, idx + 1])` — a position in the surviving linked list — while deleteFileVersion (src/server/repo/files-versions.ts:398-449) physically removes the link and repoints its successor. Deleting v2 therefore renumbers v3 to v2, including in the system note 'Removed version 2 - <filename>' that the delete itself just wrote, which now names a version that still exists. A number a note refers to must not change meaning underneath the note. Decision: `file` carries its own version_no, assigned at insert as one past the maximum in its chain and never reused after a delete; migration 0025 adds the column and backfills it from today's positional order (correct for every chain that has not yet lost a link); getFileVersionNumber and listFileComments read the stored column and throw when it is missing rather than silently falling back to position.

## Amendment (wave 64): the show-flow export is the last reader that recomputes a version number it could have read

DEC-818 made file.version_no a stored identity, and five readers honour it — getFileVersionNumber (files-versions.ts:43-54), listFileComments/listFileCommentsForFiles (files-comments.ts:67-74, :241-248), listEventDeliverableFiles (files-library.ts:496-512), portal/index.tsx:572 — each throwing "has no stored version_no — data corruption" rather than guessing. src/server/repo/exports/showflow.ts:123 instead sets `versionNumber: arr.length` over the flat group of ALL presentation files for a submission and prints `${filename} (v${n})` into the CSV the producer hands the AV team. Two ways it is wrong: after a DEC-713 middle-version delete (which deliberately does NOT renumber survivors) the stored numbers are {1,3} and showflow prints v2; and when a submission carries two independent presentation chains — which the product supports and the content UI renders as separate chips — the count sums both chains and "latest by createdAt" can select a row that is not its own chain's head. The function's own comment cites app/src/pages/content/version-chain.ts as its authority; that file's doc-comment now says the opposite in terms: "callers that compute a 'v2/v3' label must number within a file's own chain, not by its flat position across every chain." Rule: showflow selects the chain HEAD (a row no other row in the set points at via previous_file_id, newest createdAt among heads, tiebroken by id — matching orderVersionChains) and prints that row's OWN stored version_no, throwing the same data-corruption error on null.

## Amendment (wave 47): a version-chain head has exactly one successor — uniqueIndex on file.previous_file_id is the mint's contract

`insertFile` (`src/server/repo/files-versions.ts:477-511`) SELECTs the predecessor's `version_no` (`:483-487`), adds one in JS (`:492`), and INSERTs (`:495-509`) — read-then-write with no transaction and, per `src/db/schema/content.ts:47-80`, no unique index anywhere on `file` that would stop two concurrent re-uploads from both minting version N and both claiming the same predecessor. That is the exact shape the house rules name twice (MINTING IS IO; atomic SQL beats read-then-write; uniqueIndex is a CONTRACT). RULING: the invariant to encode is the chain one, not the number one — `previousFileId` always names the CURRENT HEAD of its chain (the DEC-020 contract this repo already enforces), so "at most one row may name a given predecessor" is both necessary and sufficient, and it is expressible as a partial unique index that SQLite/D1 supports: `CREATE UNIQUE INDEX file_previous_file_id_unique ON file(previous_file_id) WHERE previous_file_id IS NOT NULL`, in `migrations/0043_file_version_chain_unique.sql` (0042 is the current maximum; no other wave-47 lane writes a migration) with the matching drizzle `uniqueIndex` in `src/db/schema/content.ts`, replacing the non-unique `file_previous_file_id_idx`. `insertFile` translates the constraint violation into `ApiError("conflict", ...)` telling the loser to reload — a loud, retryable refusal instead of a duplicated version number. Chained deletes stay legal because repointing a successor onto its grandparent removes the old row. If the existing local corpus violates the index, that is a defect to REPORT, not a reason to drop the constraint.
