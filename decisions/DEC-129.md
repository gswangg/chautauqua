# DEC-129: Wave-17 dual redundant triage-closure lanes; first-campaign homonym sections never satisfy the exit grep (validity requires `git merge-base --is-ancestor 675219f <cited-sha>`)

Four of five DEC-069 gates are green on main at code-bearing sha 675219f (task-w15-g build+test, task-w15-h + task-w16-b walkthrough, task-w15-i perf-smoke, task-w15-j spec-audit); only triage-closure lacks a section ending 'OPEN ITEMS: 0' at/after 675219f, and that lane has died twice (task-w15-k created with zero commits, task-w16-e never created). So wave 17 runs TWO identical, parallel triage-closure lanes — duplicates are harmless under DEC-068/069/128 and redundancy is cheaper than another dead wave. Hazard: docs/verification-log.md contains sections from the FIRST campaign whose branch names collide with current ones (e.g. 'task-w16-e — triage-closure @ 5692a6d ... OPEN ITEMS: 0'); those shas are ancestors of the campaign reset and MUST NOT be treated as confirms. A section is valid for the DEC-069 exit predicate only if `git merge-base --is-ancestor 675219f <cited-sha>` succeeds (cited sha at/after the newest code-bearing sha), which mechanically excludes every first-campaign homonym. Lanes are confirm-else-run per DEC-128, code-frozen per DEC-077 (only docs/verification-log.md plus an optional new detail file under docs/verification-log/ may change, append-only per DEC-068), never fix anything, and use fresh never-used ports 8871 (lane a) / 8872 (lane b) if a live spot-check server is needed. Exit remains a planner-only DEC-069 grep next invocation.

## Amendment (wave 25): verification-log detail filenames carry the measured sha, because branch names repeat across campaigns

docs/verification-log/ already contains task-w25-a-build-test.md, task-w25-b-walkthrough.md, task-w25-d-render-sweep.md, task-w25-e-spec-audit.md and task-w25-f-triage-closure.md from an earlier campaign, and docs/verification-log.md carries `## ... task-w25-* @ <old sha>` headings to match — the exact homonym hazard DEC-129 already names for the confirm-else-run grep, now reaching filenames as well. RULING: a wave-25 lane writes `docs/verification-log/task-w25-<lane>-<scope>-<tip sha>.md` and appends (never rewrites) a `## <date> task-w25-<lane> — <scope> @ <tip sha>` section to docs/verification-log.md. Overwriting a prior campaign's file destroys the only durable record of a measurement nobody can re-run.

## Amendment (wave 27): every receipt declares its own INVALIDATION SURFACE and its DIAGNOSTIC-vs-QUALIFYING status in its header

DEC-069 voids a green section on "any later code merge", which in a swarm where every wave lands code means no section ever survives to be read — the reason five campaigns of receipts sit in docs/verification-log.md with nobody able to say which are live. DEC-129 already fixed the filename half of this (sha-suffixed detail files, wave-25 amendment) because branch names repeat across campaigns. RULING, extending it to the semantic half: each section header reads `## <date> task-w27-<lane> — <scope> @ <sha> [DIAGNOSTIC|QUALIFYING]`, and the section body carries one `INVALIDATED BY:` line naming the path globs whose change voids it (e.g. build+test: `src/**`, `app/src/**`, `test/**`, `package.json`; spec-audit: `src/**`, `SPEC.md`, `README.md`; render-sweep: `app/src/**/*.css`, `src/**/*.css.ts`, `src/views/theme.ts`, `app/src/routeManifest.ts`). This makes "which gates must wave 28 re-run" a mechanical `git diff --name-only` against the declared globs instead of a judgement call, without weakening DEC-069's rule that a green counts only for its named sha. Every wave-27 lane writes `docs/verification-log/task-w27-<lane>-<scope>-<sha>.md` and APPENDS one section at EOF of `docs/verification-log.md` — never rewrites an existing one.
