# DEC-340: The J6 onboarding grid becomes a server-paginated, server-filtered, searchable roster; DEC-023's whole-event grid envelope is superseded

Read live on main at the post-w18 tip. src/server/repo/tasks.ts:201 getOnboardingGrid(db, eventId) returns EVERY task_assignment row for the event joined to contact+user, and src/routes/tasks.ts:100 hands it to the SPA whole; app/src/pages/speakers/OnboardingGrid.tsx:42 fetches it once and then filters (rowFilters.ts filterOnboardingRows) and counts (overdue.ts computeOnboardingCounts, outstandingContactCount) in the browser. Cost is a function of contacts x tasks for the whole event, never of page size, and w18-d's seed makes it observable at 5 tasks x 800 contacts — squarely DEC-333's stage-1 rule, and a direct violation of SPEC §7 'Server pagination + filtering on all admin lists'. docs/sessionboard-reference/03-speaker-management.md scores a roster with search over 12-400+ speakers, and eval-rubric 03 SPK-S1 step 7 lists 'Search narrowing to Priya' as a success signal the /admin/speakers screen cannot satisfy today (RosterPanel.tsx is add+import only). Binding contract: getOnboardingGrid(db, eventId, params) where params = { page, perPage, q, taskId, status, overdueOnly, now }, returning { tasks, rows, total, page, perPage, counts:{ speakers, outstandingRequired, overdue, outstandingContacts } }. Row selection is one correlated EXISTS over task_assignment JOIN task with ALL active predicates ANDed INSIDE the same EXISTS — this reproduces filterOnboardingRows' exact 'at least one cell matching every active filter simultaneously' semantics, and per DEC-312 the WHERE is normative. overdue predicate: task.due_date IS NOT NULL AND assignment.status <> 'complete' AND task.due_date < :now. q reuses likeContains from src/server/repo/contacts/query.ts with DEC-336's AND-across-tokens x OR-across-columns, columns first_name/last_name/email. Deterministic order for stable OFFSET paging: lower(last_name), lower(first_name), contact.id. perPage default 50, max 200 (the parseListQuery convention). Rows on the page carry ALL of that contact's cells regardless of the filters, so the matrix still renders every task column. counts are EVENT-WIDE and filter-independent (one aggregate query with count(distinct case when ...) forms) — a page-local header number would be a new lie, and computeOnboardingCounts/outstandingContactCount are deleted client-side rather than fed a page. isCellOverdue stays in the SPA for per-cell styling only.

## Amendment (wave 18): the onboarding grid's filter tokens fail loudly — an unrecognised token is a 400, never "no filter"

parseOnboardingGridQuery (src/routes/tasks.ts:156-172) collapses an unrecognised `status`, `inviteStatus` or `overdueOnly` value to null/false, which the grid reads as "apply no filter" — so `?status=completed` answers the UNFILTERED who-owes-what grid as though the narrowing applied. Every sibling list refuses instead (src/routes/files.ts:336-338 throws `Unknown kind '<token>'`; the submissions list rejects unknown status literals per DEC-843). A filter that silently widens is worse than one that errors: the caller believes a narrowing happened. RULE: absent/empty stays null (no filter, unchanged); present-but-unrecognised throws one ApiError("invalid") naming every offending param in a single fields map, accumulate-then-throw like the breaks writer.


## Amendment (wave 46): a grid-returning mutation echoes the CALLER's own grid query, never a hand-written page 1

`src/routes/tasks.ts:498-506` rebuilds the response grid from a literal object — `page: 1`, `q`/`taskId`/`status` nulled, `overdueOnly: false`, `inviteStatus` omitted entirely — while `GET /events/:eventId/onboarding` (`:220`) parses the same shape from the request through `parseOnboardingGridQuery` (`:212`). So `POST /api/v1/tasks/:id/assign` returns a grid that is not the grid the caller is looking at, silently: on a large roster the post-assign refresh is page 1 of everything, and `inviteStatus` is not merely nulled but structurally absent from the params object (`OnboardingGridParams.inviteStatus` is optional at `src/server/repo/tasks/grid.ts:85`, so the omission typechecks and the drift is invisible to the compiler). Recorded so it is not overstated: no SPA surface currently posts to this route — `app/src` has zero `/assign` call sites outside `review/PlanEditor.tsx` — so this is a server response-contract defect, not a live UI regression, and the fix must NOT add an SPA caller. RULING: a route that returns a paginated grid as the representation of a mutation derives that grid from the request's own query through the same parser the GET uses, so the two doors can never disagree about the shape. A caller that sends no grid query gets the parser's documented defaults, which is byte-identical to today's behavior; a caller that sends a bad token gets the same accumulate-then-throw `ApiError('invalid')` the GET already throws (`:208-210`), rather than having it silently discarded.
