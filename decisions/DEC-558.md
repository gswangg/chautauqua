# DEC-558: DEC-534's total-order rule extends to every LIMITed admin worklist and to the JS 'best row' reducers beside them

DEC-534 established that a LIMIT obliges an ORDER BY ending in a unique column, and it was swept through the public lists (repo/public/speakers.ts:84 tiebreaks on contact.id) and the CRM history panel (repo/contacts/history.ts:49,71). The admin worklists the rule exists for were never swept. src/server/repo/overview.ts — the first screen a producer opens, whose whole justification is SPEC §2.3 "nothing falls through the cracks" — takes five capped or arbitrary samples with no unique tiebreak: overdue tasks ordered by task.dueDate alone (:316) where dueDate is a DAY LABEL so ties are the norm, not the exception; the triage queue by submission.createdAt alone (:348), which the seed and any bulk import share to the millisecond; content approval by submission.updatedAt desc alone (:402); the unplaced-sessions slice taken from acceptedRows (:433) which has no ORDER BY at all; and two JS reducers that pick a 'best' row with a strict `>` / `<` comparison and therefore keep whichever tied row the database happened to return first — latestFileBySubmission (:420) and fetchLeadSpeakerNames (:638), the latter deciding which human's name is printed next to a session. src/server/repo/tasks/grid.ts:97-106 selects the J6 grid's task COLUMNS with no order at all, and repo/contacts/stats.ts:45-51 takes the CRM dashboard's top-5 companies with `order by count(*) desc` and no tiebreak. The result is a dashboard whose rows, and a grid whose columns, can differ between two refreshes of unchanged data — which is precisely the crack the screen exists to close. Decision: (a) every capped read in these three modules gets an ORDER BY that totally orders its row: overdue tasks (dueDate, taskAssignment.id), triage (createdAt, submission.id), content approval (updatedAt desc, submission.id), acceptedRows (submission.seq — unique per event), topCompanies (count desc, company asc — the group key). (b) the J6 grid's task columns get a legible AND total order: undated last, then due date ascending, then title, then id. (c) the two 'best row' reducers become named pure functions with an explicit id tiebreak and are unit-tested against a shuffled input, per the standing rule that a JS twin of a SQL ordering must be proven. (d) the regression bar is a repeat: the same input rows in reversed order must produce byte-identical output.

## Amendment (wave 73): a `.limit(1)` with neither a primary-key predicate nor an ORDER BY is a scanned, ratcheted population — SQLite must never be the one choosing the row

DEC-558 already extends DEC-534's total-order rule to every LIMITed worklist and every JS best-row reducer. Two authz/identity bugs in three waves were the same narrower shape and were each found by hand: DEC-248 wave-70 (getTaskFileScope's or()+limit(1) let SQLite decide which speaker may download a task file) and DEC-456 wave-71 (findAccountUserId picked arbitrarily between a contact-linked and an email-matching user, deciding whether a submitter's email carried /portal or a fresh claim link). src/ carries 177 `.limit(1)` chains across 67 files; the overwhelming majority are keyed on a primary key and are unambiguous by construction. The interesting minority is mechanically identifiable: a chain containing `.limit(1)` with no `.orderBy(`, no `eq(schema.X.id, …)` term in its WHERE, and no DEC-NNN citation in the six lines above it. RULING: that predicate becomes a scan with a ratcheted maximum seeded on the implementing branch, printing file:line for every flagged chain. This wave deliberately does NOT re-adjudicate the flagged sites — naming the population is the deliverable, and a site's resolution (add an ORDER BY that totally orders the candidate set, or write down why one row is unambiguous) is a per-site ruling a later wave makes with the list in hand.

## Amendment (wave 75): the 30-site .limit(1) population is adjudicated, not just named — order it, key it, or cite the uniqueIndex; the ratchet only falls

`test/limit-one-total-order.scan.test.ts` (landed w73-e) says of itself: "This scanner does NOT fix any of the flagged sites -- each one's resolution ... is a per-site ruling a later wave makes with this list in hand. This wave only NAMES the population and ratchets a ceiling." That is an open lane with a number on it (`MAX_UNORDERED_LIMIT_ONE = 30`), and the class has already produced two real defects — DEC-248 w70 let SQLite decide which speaker could download a task file, DEC-456 w71 let it decide whether a submitter's email carried `/portal` or a fresh claim link. I am ruling the resolution so two lanes cannot answer it differently: (1) if the `.where(...)` is already at most one row BY A DATABASE UNIQUE INDEX, keep `.limit(1)` and add a one-line comment naming that index and citing DEC-558 — the scan's own citation exemption, and the honest answer for e.g. `portal_settings_event_id_idx`; (2) otherwise add `.orderBy(...)` ending in `asc(schema.<table>.id)` as the final total-order tiebreak, so the chain is deterministic even when the leading column ties; (3) where the RIGHT row is semantically decided (newest, lowest position, accepted-before-invited), order by that column FIRST and then `asc(id)`, and say which fact decided it in the comment; (4) never resolve by widening the query to N rows and picking in JS — that trades an unspecified row order for an unbounded read (DEC-104). A site whose ambiguity turns out to be a real authz or identity decision is a DEFECT, not an annotation: fix the behaviour and say so. `MAX_UNORDERED_LIMIT_ONE` may only be lowered to a count the lowering lane itself measured; it is never raised.

## Amendment (wave 79): a cited index is machine-checked, and a bare DEC number no longer exempts an unordered .limit(1)

`test/limit-one-total-order.scan.test.ts:211` waives any unordered, non-key `.limit(1)` when ANY `DEC-\d{3}` appears in the six lines above it — a near-universal escape hatch in a tree where every comment cites a DEC. Underneath it, ~45 comments justify their `.limit(1)` by NAMING an index (`user_email_idx`, `form_event_id_title_idx`, `portal_settings_event_id_idx`, `pipeline_entry_org_id_contact_id_idx`, `schedule_slot_submission_id_idx`, `api_token_token_hash_idx`, …) and claiming it is unique. Nothing checks that the named index exists in `src/db/schema/**`, or that it is `uniqueIndex(` rather than plain `index(` — and the difference is load-bearing: `contact_email_idx` (org.ts:85) is NOT unique, which is exactly why `findContactByEmail` needed its wave-75 ordering. The existing `test/unique-index-guard-coverage.scan.test.ts` covers only the WRITE side (index → guarded write). Ruling: the READ side gets a symmetric, allowlist-free tripwire — every `*_idx` token appearing in a comment anywhere under `src/` must resolve to a declared index, and must resolve to a `uniqueIndex(` whenever the surrounding comment asserts uniqueness; and a DEC citation only exempts an unordered `.limit(1)` when it also names such an index or an explicit ordering. A DEC number is a reference, not an argument.
