# DEC-788: A duplicate is warned about at creation, by the same predicate the Duplicates tab uses

CRM grader P2: a new contact with an identical name+company saves silently, and the Duplicates tab is too late to help. VERIFIED GET /api/v1/contacts/duplicates already exists and is documented (src/routes/api/contacts/duplicates.ts, src/routes/docs.tsx:201) with a server-side pair-matching predicate, and DEC-770's dismissal store already exists beside it. Decision: the create form asks that SAME predicate before it writes — a read-only check endpoint returning the candidate matches for a proposed {firstName,lastName,company,email} — and renders an inline, non-blocking "possible duplicate" hint naming the matching record with a link to it. Non-blocking is deliberate: two real people can share a name, and DEC-758 already makes merge the repair path. Two different answers to "is this a duplicate?" in one product would be the same lie twice, so the check must import the predicate, not restate it.

## Amendment (wave 8): a duplicate-email refusal has ONE forward path, and every person-creating surface renders it from the same component

POST /api/v1/contacts (src/routes/api/contacts/crud.ts:150-157) answers a known email with a 409 naming the existing person. Contacts' NewContactModal grew a real forward path for that refusal (resolve the contact via GET /contacts?q=<email>, link to /contacts?openContact=<id>) plus the DEC-788 pre-submit duplicates/check hint. Speakers' Add-speaker modal (app/src/pages/speakers/RosterPanel.tsx:76-85) hits the SAME endpoint and inherits none of it: it prints err.message into a .chq-error div and stops, so re-clicking just re-renders the warning — the P1 dead-end in the 2026-08-14 re-measure. Ruling: the refusal's resolution is a shared component, not a per-modal habit. It always names the existing person and offers (a) open that contact and (b) — only where the surface already has an event context — add THAT contact to this event using the session title already typed, via the existing POST /contacts/:id/add-to-event {eventId,title,role}. Role is 'speaker' on the roster path (the roster is the speaker surface); no new endpoint, no change to the {error:{code,message,fields?}} envelope, because the client can resolve the person from the email it just typed. Two surfaces answering "this email is taken" two different ways is the same lie twice.
