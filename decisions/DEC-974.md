# DEC-974: The admin agenda's speakers are the ACTIVE participants — a declined co-presenter neither clashes nor blocks auto-schedule

the former src/server/repo/agenda.ts (now split across src/server/repo/agenda/)'s loadAcceptedSessions selects every participant row for an accepted submission with no invite filter, so speakerContactIds (:303) carries people who DECLINED or were merely 'invited' into findConflicts (:410) as phantom speaker_overlap rows, into autoSchedule as speaker_double_booked refusals, and onto the J9 grid as speakers. Meanwhile the public agenda excludes exactly those rows through visibleParticipantConditions (src/server/repo/public/agenda.ts:110-113), so admin and public disagree about who is speaking — and the disagreement is load-bearing, because a phantom clash is a warning an organiser cannot clear and a phantom double-booking silently refuses a placement the room can hold. The predicate already exists and is already the product's answer to this question everywhere else: ACTIVE_INVITE_STATUSES = ['none','accepted'] (src/domain/acceptance.ts:114), which DEC-278 uses to gate onboarding auto-creation, DEC-283 to gate task expansion, DEC-317 to gate file writes, DEC-275 to gate clone. Rule: loadAcceptedSessions' participant query adds inArray(participant.inviteStatus, ACTIVE_INVITE_STATUSES) — one filter, feeding display, conflicts and auto-schedule from one set. participant.visible is deliberately NOT part of this predicate: it is a public-display flag, and a speaker hidden from the public programme still cannot be in two rooms at once.

## Amendment (wave 29): the conflict engine's demo belongs in the SEED — one cross-room co-presenter clash, expressed as a participant row and never as a moved slot

AIA-04 was closed at wave 11 on unit tests (findConflicts emits one speaker_overlap for a same-slot different-room co-presenter pair; getAgendaPayload carries it; both cards render data-conflict) and then FALSIFIED by live judge evidence: no conflict indicator, counter stuck at "1 conflict". Reading scripts/seed.ts:2294-2382 settles it — the engine is right and the DATA is missing. The seed's whole schedule plan contains exactly ONE clash, the deliberate same-ROOM overlap between two non-approved submissions, and no participant row anywhere makes one person a co-presenter on a session that runs opposite another of their sessions. A renderer with no seeded data looks like a missing feature. Ruling: the seed carries one cross-room speaker double-booking, and it is created by ADDING A PARTICIPANT ROW — never by moving, adding or retiming a schedule_slot, because the slot plan's comment block is load-bearing (the 4-up/2-up/solo/TBD layout cases and the break clearances are all asserted off it, DEC-854). The clash rides the pair already scheduled at one start time in two different real rooms, so the demo costs one row and changes no layout. Conflicts stay organiser-side: the participating submissions remain publicly visible and the public surfaces must not gain a conflict marker.
