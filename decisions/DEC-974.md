# DEC-974: The admin agenda's speakers are the ACTIVE participants — a declined co-presenter neither clashes nor blocks auto-schedule

src/server/repo/agenda.ts's loadAcceptedSessions selects every participant row for an accepted submission with no invite filter, so speakerContactIds (:303) carries people who DECLINED or were merely 'invited' into findConflicts (:410) as phantom speaker_overlap rows, into autoSchedule as speaker_double_booked refusals, and onto the J9 grid as speakers. Meanwhile the public agenda excludes exactly those rows through visibleParticipantConditions (src/server/repo/public/agenda.ts:110-113), so admin and public disagree about who is speaking — and the disagreement is load-bearing, because a phantom clash is a warning an organiser cannot clear and a phantom double-booking silently refuses a placement the room can hold. The predicate already exists and is already the product's answer to this question everywhere else: ACTIVE_INVITE_STATUSES = ['none','accepted'] (src/domain/acceptance.ts:114), which DEC-278 uses to gate onboarding auto-creation, DEC-283 to gate task expansion, DEC-317 to gate file writes, DEC-275 to gate clone. Rule: loadAcceptedSessions' participant query adds inArray(participant.inviteStatus, ACTIVE_INVITE_STATUSES) — one filter, feeding display, conflicts and auto-schedule from one set. participant.visible is deliberately NOT part of this predicate: it is a public-display flag, and a speaker hidden from the public programme still cannot be in two rooms at once.
