# DEC-528: A multi-row INSERT is chunked by BOUND-PARAMETER budget, not by row count, through one canonical helper that derives columns-per-row from the rows themselves; the organizer task-assign path joins the set-based writers under its own named bound

Two defects with one root. (1) `src/lib/chunk.ts:2-4` documents the constraint in the codebase's own words — "D1 rejects statements above ~100 bound parameters ... 90 leaves headroom" — and `ID_CHUNK_SIZE = 90` is correct for an `inArray(...)` binding roughly one parameter per id. Three sites then reuse that same 90 to slice multi-row INSERTs, where each row binds every column: `src/server/repo/agenda.ts:509-511` (schedule_slot, 8 columns => 720 parameters per statement), `src/server/repo/submissions/status.ts:210-211` (task_assignment, 6 columns => 540, landed this wave under DEC-521), and `src/server/repo/submit.ts:299` which passes the whole array with no chunking at all. Each contradicts the constant's own stated budget by 5-7x; it is invisible on Miniflare and would surface as a hard D1 error at stage 2, which is precisely why the fix must be a pure, unit-testable derivation rather than a measurement. (2) `src/server/repo/tasks/crud.ts:99-108` is the last remaining per-row `db.insert(schema.taskAssignment)` loop in the product — the exact shape DEC-521 just removed from its sibling — and it is reachable two ways with no bound: POST /api/v1/tasks/:id/assign with up to `parseBoundedIdArray`'s 1000 contact ids, and POST /api/v1/events/:eventId/tasks with `assignToAllAccepted:true`, which expands to the event's whole accepted roster (200-800 speakers at the SPEC scale target) with no cap of any kind. Decision: (a) `src/lib/chunk.ts` gains `MAX_D1_BOUND_PARAMS = 100` and `chunkRowsForInsert<T extends Record<string, unknown>>(rows: T[]): T[][]`, which DERIVES columns-per-row from `Object.keys(rows[0]).length`, asserts every row carries the identical key set (fail loudly on a ragged batch), and slices at `max(1, floor((MAX_D1_BOUND_PARAMS - 10) / columnsPerRow))` — no call site may hand-declare its column count, so no call site can desync when a column is added; (b) all three existing multi-row inserts adopt it; (c) `createTaskAssignments` builds rows in memory and inserts through the same helper, under a named `MAX_TASK_ASSIGNMENT_WRITES = 5000` checked against the to-create count BEFORE the first write and refused with `ApiError('invalid', ...)` naming the cap — the DEC-521 rule, for the identical reason: a silently dropped onboarding assignment is invisible until a speaker was never asked for their hotel form; (d) the rule is enumerated by a globbed test over `src/server/repo/**/*.ts` asserting every `.insert(...).values(<non-object-literal>)` site's file imports `chunkRowsForInsert`.

## Amendment (wave 47): the Sessionboard importer resolves every lookup in the batched pre-pass and writes participants set-based

DEC-528 established chunkRowsForInsert as the way bulk rows reach D1 ("never a per-row insert loop"). src/server/repo/import/sessionboard.ts obeys it for its READ pre-pass (loadSubmissionIdsByRef, loadContactsByRef, loadExistingParticipantPairs at :225-228) but then, inside the per-row loop, (a) falls back to `await findContactByEmail(db, orgId, v.speakerEmail)` at :256 — one serial SELECT per row for exactly the rows whose external id is absent, i.e. the common case for a hand-exported CSV — and (b) issues one INSERT (:279) or one UPDATE (:304) per participant row. This is DEC-491's defect in a second importer, and the Sessionboard migration path is SPEC §3's "why they'd switch" feature: it is the first thing a defecting customer runs. Amendment: every id a row loop needs is resolved in the pre-pass (the email fallback set is collected from `plans` up front and looked up in ONE chunked query alongside the externalRef lookup), and the participant create/update flush is chunked and set-based. The `order` column's SQL sub-select must be preserved by pre-resolving the per-submission next order in the pre-pass rather than binding a correlated sub-select per row.

## Amendment (wave 49)

The sessionboard participant UPDATE path collapses to O(distinct value tuples), not O(rows). src/server/repo/import/sessionboard.ts:246-267 documents its own unfinished state: the wave-47 amendment hoisted the updates OUT of the read loop but left one statement per row ("Flagged as a narrower interpretation of chunked UPDATEs ... follow up if the update path also needs to collapse"). A 500-row idempotent re-import still pays 500 sequential D1 writes. Rather than a per-column CASE/WHEN expression keyed on id (which the comment correctly calls expensive to build), group the accumulated rows by their column-set signature (role only / order only / both) and then by the actual value tuple; each (signature, value) group is ONE chunked `UPDATE ... WHERE id IN (...)`. Re-imports carry few distinct roles/orders, so this is O(distinct values) statements. Which rows change, and to what, must be unchanged.

## Amendment (wave 52): the Sessionboard importer's other three entities batch too, and the seq/position allocators move into the pre-pass with them

DEC-528's wave-47 and wave-49 amendments batched the importer's PARTICIPANTS branch only. Verified on main, the contacts / submissions / tracks branch (src/server/repo/import/sessionboard.ts:480-654) is still one INSERT (:507, :538, :557, :580) or one UPDATE (:601, :616, :643) per CSV row — the exact shape those amendments removed next door — and test/serial-write-scan.test.ts:188-193 still carries it as a ledger line whose own text says the correct resolution is deleting the line, not keeping the loop. A 500-row speaker export is 500 sequential D1 writes on SPEC §3's "why they'd switch" path, the first thing a defecting customer runs. Two allocators block a naive multi-row VALUES: submission.seq's DEC-100 correlated sub-select and track.position's MAX+1 sub-select would each be re-evaluated as SQLite inserts each row of one statement, so both move into the batched pre-pass exactly as the participants branch's per-submission `order` did — ONE MAX read per event, incremented in JS. The UNIQUE index on (event_id, seq) is deliberately left to fail loudly if a concurrent public submit takes a number mid-import: a loud, retryable import beats 500 serial writes, and this is the same trade the participants branch already made. The update half groups accumulated rows by column-set signature then by value tuple, one chunked `UPDATE ... WHERE id IN (...)` per group — the wave-49 rule, unchanged — and the per-row replaceSubmissionTracks call is hoisted to one accumulated full-set replace after the loop. Which rows change, and to what, must be byte-identical; dry-run still writes nothing.

## Amendment (wave 58): a one-time allocator preload (MAX seq, MAX position) is a SQL aggregate — never a whole-table SELECT reduced in JS

src/server/repo/import/sessionboard.ts:377 loadMaxSubmissionSeq selects EVERY submission row of the event and reduces to one integer in JS; :390 loadMaxTrackPosition does the same for tracks. Its own comment defends this ("stays the same select-then-reduce shape every other loader in this file uses") — that is a decision doc arguing for the bug. Wave 52 introduced these preloads for a good reason (a correlated per-row sub-select cannot survive a multi-row VALUES insert); the reason for the preload never implied the SHAPE of the read. Every Sessionboard import — including a dry run, which writes nothing — pays an unbounded whole-event scan to learn one number, on an event whose submission count is exactly the thing that grows. Ruling: both allocators become `select max(col)` single-row aggregates with the same empty-set semantics they have today (0 for seq, -1 for position). This is the same rule the swarm already learned twice (a per-row count is N scans; a population you only reduce must be reduced in SQL) applied to the last place in the import that ignores it.

## Amendment (wave 10): a cap on DERIVED work is stated in the producer's units, and the query that counts that work respects the bind budget

Two defects in one function, both verified. (1) SCALE DEAD-END: planAndPersistOnboardingTasks (src/server/repo/submissions/status.ts:296-309) materialises event-tasks x firing-contacts and throws ApiError('invalid') past MAX_TASK_ASSIGNMENT_WRITES = 5000 (src/server/repo/tasks/crud.ts:199). The status route admits up to DEFAULT_BOUNDED_ID_ARRAY_MAX = 1000 ids (src/server/http.ts:67), five default onboarding tasks ship (src/domain/acceptance.ts:25-37), and SPEC's scale assumptions are 500-5,000 submissions and 200-800 speakers with 'every list view, bulk action, and query designed for the top of these ranges'. One maximal batch therefore exceeds the cap, and because DEC-079's ordering runs planning BEFORE the status UPDATEs (status.ts:481-521) the producer gets a 400 naming an internal constant and ZERO submissions accepted. A refusal is acceptable; a refusal with no forward path is not. (2) BIND-BUDGET VIOLATION: status.ts:280-282 binds `inArray(taskAssignment.taskId, eventTaskIds)` — an UNBOUNDED list — alongside a 90-id contact chunk, so an event with 11+ tasks exceeds MAX_D1_BOUND_PARAMS (src/lib/chunk.ts:21) and D1 rejects the statement outright. DEC-078 says every inArray over an unbounded id list must be chunked; this one never was. RULING: chunk BOTH dimensions so no statement can exceed the bind budget, and keep the refusal pre-write but restate it in producer vocabulary — it names the projected assignment count and the largest number of submissions acceptable in one batch, derived from the same constants, never a bare cap number.

## Amendment (wave 16): the bound-parameter budget is enforced per INSERT CALL SITE by a scan, not by whoever remembered the helper

DEC-528 already names chunkRowsForInsert as the canonical multi-row INSERT chunker, and test/inarray-chunk-scan.test.ts binds every inArray( call site to chunkIds or a reviewed allowlist entry. Nothing binds `.values(rows)`. Reading main: src/server/repo/forms.ts:220 seeds a new event's locked CFP fields as ONE 8-row x 10-column insert = 80 of D1's 100 bound parameters, with zero headroom left by the helper's own MAX_D1_BOUND_PARAMS-10 budget -- one added locked field, or one added column on form_field, silently turns every new event's FIRST CFP form read into a 500. src/server/repo/submit.ts:294 and :320 insert one row per track unchunked. A scan that binds one call shape (inArray) while its sibling shape (.values) goes unwatched is the same class of gap DEC-078's wave-14 tightening closed: the guard must bind the CALL, and both call shapes bind parameters. Chunking is preferred over allowlisting wherever the row list can grow with event data; an allowlist entry must name what bounds it.
