# DEC-528: A multi-row INSERT is chunked by BOUND-PARAMETER budget, not by row count, through one canonical helper that derives columns-per-row from the rows themselves; the organizer task-assign path joins the set-based writers under its own named bound

Two defects with one root. (1) `src/lib/chunk.ts:2-4` documents the constraint in the codebase's own words — "D1 rejects statements above ~100 bound parameters ... 90 leaves headroom" — and `ID_CHUNK_SIZE = 90` is correct for an `inArray(...)` binding roughly one parameter per id. Three sites then reuse that same 90 to slice multi-row INSERTs, where each row binds every column: `src/server/repo/agenda.ts:509-511` (schedule_slot, 8 columns => 720 parameters per statement), `src/server/repo/submissions/status.ts:210-211` (task_assignment, 6 columns => 540, landed this wave under DEC-521), and `src/server/repo/submit.ts:299` which passes the whole array with no chunking at all. Each contradicts the constant's own stated budget by 5-7x; it is invisible on Miniflare and would surface as a hard D1 error at stage 2, which is precisely why the fix must be a pure, unit-testable derivation rather than a measurement. (2) `src/server/repo/tasks/crud.ts:99-108` is the last remaining per-row `db.insert(schema.taskAssignment)` loop in the product — the exact shape DEC-521 just removed from its sibling — and it is reachable two ways with no bound: POST /api/v1/tasks/:id/assign with up to `parseBoundedIdArray`'s 1000 contact ids, and POST /api/v1/events/:eventId/tasks with `assignToAllAccepted:true`, which expands to the event's whole accepted roster (200-800 speakers at the SPEC scale target) with no cap of any kind. Decision: (a) `src/lib/chunk.ts` gains `MAX_D1_BOUND_PARAMS = 100` and `chunkRowsForInsert<T extends Record<string, unknown>>(rows: T[]): T[][]`, which DERIVES columns-per-row from `Object.keys(rows[0]).length`, asserts every row carries the identical key set (fail loudly on a ragged batch), and slices at `max(1, floor((MAX_D1_BOUND_PARAMS - 10) / columnsPerRow))` — no call site may hand-declare its column count, so no call site can desync when a column is added; (b) all three existing multi-row inserts adopt it; (c) `createTaskAssignments` builds rows in memory and inserts through the same helper, under a named `MAX_TASK_ASSIGNMENT_WRITES = 5000` checked against the to-create count BEFORE the first write and refused with `ApiError('invalid', ...)` naming the cap — the DEC-521 rule, for the identical reason: a silently dropped onboarding assignment is invisible until a speaker was never asked for their hotel form; (d) the rule is enumerated by a globbed test over `src/server/repo/**/*.ts` asserting every `.insert(...).values(<non-object-literal>)` site's file imports `chunkRowsForInsert`.

## Amendment (wave 47): the Sessionboard importer resolves every lookup in the batched pre-pass and writes participants set-based

DEC-528 established chunkRowsForInsert as the way bulk rows reach D1 ("never a per-row insert loop"). src/server/repo/import/sessionboard.ts obeys it for its READ pre-pass (loadSubmissionIdsByRef, loadContactsByRef, loadExistingParticipantPairs at :225-228) but then, inside the per-row loop, (a) falls back to `await findContactByEmail(db, orgId, v.speakerEmail)` at :256 — one serial SELECT per row for exactly the rows whose external id is absent, i.e. the common case for a hand-exported CSV — and (b) issues one INSERT (:279) or one UPDATE (:304) per participant row. This is DEC-491's defect in a second importer, and the Sessionboard migration path is SPEC §3's "why they'd switch" feature: it is the first thing a defecting customer runs. Amendment: every id a row loop needs is resolved in the pre-pass (the email fallback set is collected from `plans` up front and looked up in ONE chunked query alongside the externalRef lookup), and the participant create/update flush is chunked and set-based. The `order` column's SQL sub-select must be preserved by pre-resolving the per-submission next order in the pre-pass rather than binding a correlated sub-select per row.
