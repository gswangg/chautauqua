# DEC-373: SSR surface stylesheets: one co-located CSS-string module per surface family; tokens live only in THEME_CSS

Four wave-2 lanes restyle SSR bodies (public surfaces, portal, CFP form, auth/account). If each grows the shell's inline <style>, they collide inside src/routes/public/shell.tsx and src/routes/portal/shared.tsx on every merge and the shells become megafiles. Each family therefore gets one module exporting a plain string constant: src/routes/public/public.css.ts -> PUBLIC_CSS (classes .chq-pub-*), src/routes/portal/portal.css.ts -> PORTAL_CSS (.chq-portal-*), src/routes/public/cfp.css.ts -> CFP_CSS (.chq-cfp-*), src/routes/auth.css.ts -> AUTH_CSS (.chq-auth-*). The inline blocks currently inside BaseStyles and PortalLayout move into their module verbatim as the starting point. Every SSR shell then renders exactly two style elements — ThemeStyles() followed by its one surface string — and each lane's edit to a shell stays surgical (swap the inline literal for the imported constant, plus the accent attribute of DEC-374) so four lanes never rewrite each other's chrome. Surface CSS never restates a design token and never redefines a class THEME_CSS already defines; it composes them. src/views/theme.ts is not edited by these lanes — DEC-372's lane owns it. EmbedShell keeps the same pair so an iframe renders identically to the hosted surface.
