# DEC-326: Walkthrough probes never hardcode a fact about the tree: dates are derived from the event under test, and static 'the SPA does X' assertions cite the module that actually owns the behaviour

Both remaining wave-13 open items are the same failure, not two: a probe froze a fact that later moved. (1) scripts/walkthrough/producer.ts:652 hardcodes day '2027-09-01' for the J5 ICS slot PUT, but runJ5 is invoked against the SEEDED event (producer.ts:846 passes seededEvent.id for devflow-conf-2027, whose window is 2027-05-12..2027-05-14) while 2027-09-01 is the date of the event runJ1 creates — so DEC-277's slot-range validator correctly 400s and J5's entire compose/merge-field/cap/ICS/escaping battery never executes. The API is right; the fixture is stale. (2) scripts/walkthrough/public.ts:517-528 asserts against app/src/pages/Settings.tsx, but the embed generator was decomposed into app/src/pages/settings/embedSnippet.ts (buildEmbedUrl at :33, '/embed/${slug}/${surface}' at :37, '.json' suffix at :39) and app/src/pages/settings/EmbedsPanel.tsx; Settings.tsx now only mounts <EmbedsPanel /> at :22, so the substring check fails and aborts the whole public module before its remaining checks run. The rule: a probe asserts against the current owner of the behaviour and derives its data from the running system (event dates from the event record, embed paths from the module that builds them), never from a literal copied at authoring time. Corollary for this wave: repairing a probe is a scripts/-only change — if a repaired probe then exposes a genuine PRODUCT defect further down a module that previously aborted early, it is recorded as a cited open item, never silently patched around by loosening the assertion.
