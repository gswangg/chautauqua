# DEC-397: A preview never mints credentials: in preview mode the portal link for a userless contact renders a fixed placeholder, and only the send path issues claim tokens

resolvePortalLink calls createClaimToken for any contact without a user account, and it is reached from the read-only POST /compose/preview (src/routes/comms.ts:336 -> buildRenderTargets:292) and from POST /contacts/bulk-email/preview (the former src/routes/api/contacts.ts:718 (now split across src/routes/api/contacts/) -> renderBulkEmailTargets:638). Every preview click therefore writes a fresh 30-day one-time account-claim credential per userless recipient into KV -- never consumed, never invalidated, unbounded in count, and issued by an endpoint whose whole contract is that it changes nothing. It also buys nothing: the send mints its own tokens, so the URL a preview displays is already not the URL that gets mailed. DEC-150's 'previews can never lie' is about the merge-render path, and that path stays shared and unchanged -- vars still carry portal_link, so preflightRender's missing-merge-field verdict is identical in both modes; only the token segment differs. Rule: the shared render helper takes an explicit mintClaimTokens flag (true from send, false from preview); with it false, a contact who already has a user still gets `${origin}/portal` and a contact who does not gets `${origin}/claim/${PREVIEW_CLAIM_TOKEN}` where PREVIEW_CLAIM_TOKEN is a single constant exported from pure-core src/domain/compose.ts. Regression bar: a preview run against a fake KV performs zero puts.

## Amendment (wave 50)

DEC-397 already forbids preview from minting, but both send paths mint before preflight can reject: src/routes/comms/send.ts calls buildRenderTargets(..., mintClaimTokens=true) and only then preflightRender at :558 throws the 400, and src/routes/api/contacts/bulk-email.ts:144 has the identical ordering (mint at renderBulkEmailTargets:93, preflight at :122). A send that never happens therefore writes live one-time /claim/<token> credentials to KV for every recipient, and because a bad merge-field template fails deterministically the organizer can resubmit and mint the whole set again. Two house rules already say this is wrong: MINTING IS IO, and A GUARD PLACED AFTER THE COST GUARDS NOTHING. The mint flag only ever reaches resolvePortalLinks, so the fix is structural, not a reordering hack: the render pass that VALIDATES always resolves links with mintClaimTokens=false (PREVIEW_CLAIM_TOKEN, zero KV writes, non-empty so merge-field presence checks behave identically); only when preflightRender returns ok does the caller mint, overwrite vars.portal_link on the already-built targets, and render once more. The mintClaimTokens boolean is DELETED from buildRenderTargets and renderBulkEmailTargets rather than defaulted -- minting becomes a named second step at the callsite, so a future send path cannot inherit the old ordering by passing a boolean. DEC-949 still holds: the send response carries counts, never rendered bodies.

## Amendment (wave 62): mint only what the message carries — a send issues a portal claim credential only when its own subject or body actually references {portal_link}

DEC-397's wave-50 amendment moved minting AFTER preflight (MINT LATE), but left it unconditional: src/routes/comms/send.ts and src/routes/api/contacts/bulk-email.ts:159 call applyMintedPortalLinks for every send regardless of whether the template contains the token. createClaimToken revokes the prior grant first (src/auth/claim.ts:71-75, DEC-949 single-active), so an organizer email whose body omits {portal_link} silently kills the claim link a not-yet-registered speaker already received in their CFP confirmation (src/routes/public/submit.tsx:608) and replaces it with a token that is never delivered anywhere. MINTING IS IO was the wave-50 lesson; the missing half is that IO you don't consume is still IO, and here it is destructive IO. The predicate belongs in the one module that already owns placeholder scanning and the {due_date}->{task_due_date} alias (src/mail/render.ts PLACEHOLDER_RE + canonicalMergeField), not hand-rolled at two call sites that would drift. Deliberately NOT gated: content-notes (src/routes/content-notes.ts:141 always appends the link to the body), task reminders (buildReminderMessage always renders {portal_link}), and the portal-invite route (src/routes/comms/portal-invites.ts — delivering the link IS the action). Regression bar: a compose send with no {portal_link} in subject or body performs zero KV puts and leaves a pre-existing grant for that contact alive.

## Amendment (wave 62): MINT ONLY WHAT SHIPS — a claim credential is minted after the last refusal AND after the dedupe, for survivors only

DEC-397's wave-50 MINT LATE amendment moved minting below the merge-field preflight, but both fan-outs still mint too early. src/routes/comms/send.ts:96 mints before the templateId validation at :174-183 (a stale or cross-tenant templateId now supersedes all N recipients' grants while sending zero mail — the exact 'no KV credential minted before the 400' rule DEC-397 exists to state) and before the DEC-238 dedupe at :128-164; src/routes/api/contacts/bulk-email.ts:207 has the same ordering against its dedupe at :224-250. createClaimToken (src/auth/claim.ts:81-96) demotes the prior grant to a 48h TTL, so a recipient who lands in `skipped` (already_sent_recently / duplicate_in_batch) has their live, already-delivered portal link put on a 48h fuse and never receives the replacement. RULING: the mint is the LAST io before the send loop — below every 400 and below both dedupe stages — and covers only the recipients in `toSend`. Corollary: dedupe keys are computed from the UNMINTED render, because a minted subject carries a unique token and could never match a prior send (today's order makes cross-call dedupe unreachable for any subject containing {portal_link}). MINTING IS IO with a destructive side effect; it belongs at the last possible point.
