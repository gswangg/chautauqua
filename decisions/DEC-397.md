# DEC-397: A preview never mints credentials: in preview mode the portal link for a userless contact renders a fixed placeholder, and only the send path issues claim tokens

resolvePortalLink calls createClaimToken for any contact without a user account, and it is reached from the read-only POST /compose/preview (src/routes/comms.ts:336 -> buildRenderTargets:292) and from POST /contacts/bulk-email/preview (src/routes/api/contacts.ts:718 -> renderBulkEmailTargets:638). Every preview click therefore writes a fresh 30-day one-time account-claim credential per userless recipient into KV -- never consumed, never invalidated, unbounded in count, and issued by an endpoint whose whole contract is that it changes nothing. It also buys nothing: the send mints its own tokens, so the URL a preview displays is already not the URL that gets mailed. DEC-150's 'previews can never lie' is about the merge-render path, and that path stays shared and unchanged -- vars still carry portal_link, so preflightRender's missing-merge-field verdict is identical in both modes; only the token segment differs. Rule: the shared render helper takes an explicit mintClaimTokens flag (true from send, false from preview); with it false, a contact who already has a user still gets `${origin}/portal` and a contact who does not gets `${origin}/claim/${PREVIEW_CLAIM_TOKEN}` where PREVIEW_CLAIM_TOKEN is a single constant exported from pure-core src/domain/compose.ts. Regression bar: a preview run against a fake KV performs zero puts.

## Amendment (wave 50)

DEC-397 already forbids preview from minting, but both send paths mint before preflight can reject: src/routes/comms.ts:556 calls buildRenderTargets(..., mintClaimTokens=true) and only then preflightRender at :558 throws the 400, and src/routes/api/contacts/bulk-email.ts:144 has the identical ordering (mint at renderBulkEmailTargets:93, preflight at :122). A send that never happens therefore writes live one-time /claim/<token> credentials to KV for every recipient, and because a bad merge-field template fails deterministically the organizer can resubmit and mint the whole set again. Two house rules already say this is wrong: MINTING IS IO, and A GUARD PLACED AFTER THE COST GUARDS NOTHING. The mint flag only ever reaches resolvePortalLinks, so the fix is structural, not a reordering hack: the render pass that VALIDATES always resolves links with mintClaimTokens=false (PREVIEW_CLAIM_TOKEN, zero KV writes, non-empty so merge-field presence checks behave identically); only when preflightRender returns ok does the caller mint, overwrite vars.portal_link on the already-built targets, and render once more. The mintClaimTokens boolean is DELETED from buildRenderTargets and renderBulkEmailTargets rather than defaulted -- minting becomes a named second step at the callsite, so a future send path cannot inherit the old ordering by passing a boolean. DEC-949 still holds: the send response carries counts, never rendered bodies.
