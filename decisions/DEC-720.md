# DEC-720: Asking for changes is a message, not a column flip: one endpoint posts the note, optionally moves content status, and mails the speakers — the bare content-status route stays mailer-free

docs/design/README.md §'Content — required implementation' is unambiguous: 'Ask for changes must send an email, and today nothing does… Do not ship the flip without the send.' As built, a speaker learns their deliverable was rejected only if they happen to open the portal. DEC-009's invariant — that a status change never sends email — is about the decision pipeline (accept/decline), and src/routes/files.ts records it as 'this module MUST NEVER import a mailer'. Both hold at once if the send lives in a different act: a new organizer endpoint whose whole purpose is to tell the speaker something, carrying the note as its payload. It posts to the DEC-573 chain thread, optionally sets changes_requested, and mails and logs per recipient like every other send so it appears in Comms history. Approval deliberately does not notify — an approval asks nothing of the speaker, and a silent approval is not the trap a silent rejection is. The reported count comes from the shared send reporter, so the toast counts actual sends.

## Amendment (wave 39): "Ask for changes" is the filled primary of the note composer, and the helper sentence sits BELOW the pair

DEC-720 made asking for changes a message rather than a column flip, with one endpoint posting the note and optionally moving status. The composer inverted its own ruling in markup: `Ask for changes` renders `chq-btn-secondary` and `Send note only` renders `chq-btn-primary` (app/src/pages/content/CommentThread.tsx:79-94), so the filled action is the one that changes nothing, and content.css:417 carries a comment asserting the inversion as if it were the design. The helper explaining the difference sits ABOVE both buttons, where it reads as caption to the textarea rather than as the legend for a choice. The frames put the filled olive on `Ask for changes` — it is the action that moves work — and the helper under the pair. Ruling: the primary is the status-moving action, the outline is the note-only action, the helper follows the pair, and the CSS comment is rewritten to state the real order rather than the old one.

## Amendment (wave 53): `changes_requested` has exactly one writer, and no row anywhere offers "Ask for changes"

DEC-720 already rules that asking for changes is a message, not a column flip — the content-note endpoint posts the note, moves the status and mails the speakers, while "the bare content-status route stays mailer-free". The bare route was left able to WRITE `changes_requested` anyway (isValidContentStatus accepts all three values at src/routes/files.ts:280 and src/routes/api/submissions.ts:678), and app/src/pages/Overview.tsx:438 uses it: Overview section 03's "Ask for changes" button POSTs {contentStatus:'changes_requested'} to the mailer-free route. The speaker is never told, the thread gets no note, and the session leaves the worklist — the exact failure the design handoff forbids ("Do not ship the flip without the send"). Ruling: `changes_requested` is reachable only through POST /submissions/:id/content-note; both bare content-status routes (single and bulk) refuse it with a refusal naming the endpoint that does send; and per the handoff's worklist rule a collection ROW offers only Approve plus a control that opens the session's content screen, because asking for changes always carries a note and a note cannot be composed from a row.

## Amendment (wave 30): a refusal that protects a side effect must not block the main effect — the content note and its status move are durable, the mail fan-out is best-effort

src/routes/content-notes.ts:90-94 refuses the whole request with a 400 when loadComposeSubmissions resolves zero active-invite participants, BEFORE it writes anything. Because src/server/repo/files-content-status.ts:22-26 gives `changes_requested` exactly one writer (this route — src/routes/files.ts:305 and src/routes/api/submissions.ts:827 both refuse it and redirect the caller here), a session whose participants are all declined/uninvited can never be moved to `changes_requested` at all, and its organizer cannot even record the note. DEC-720's principle ("asking for changes is a MESSAGE, not a column flip") survives intact because the note is posted to the DEC-573 chain thread that the speaker reads in /portal/tasks — the design pack says exactly this (docs/design/README.md, '## Content — supporting rules': "the composer says 'the speaker sees it in their portal'"). So: insert the comment, apply the status when requested, then attempt the send over whatever recipients exist, and report `{sent, failed, recipients}`. Zero recipients is a reported outcome, never a refusal.

## Amendment (wave 32): changes_requested is settable without mail on both bare content-status doors; the content-note endpoint keeps note+flag+mail as ONE deliberate action

DEC-720's wave-53 amendment gave `changes_requested` exactly one writer — POST /submissions/:id/content-note — and made the two bare status doors refuse it (`ROUTE_SETTABLE_CONTENT_STATUSES`, files-content-status.ts:22-34). Verified still true at the tip. That refusal inverts SPEC §2 principle 4: 'Status changes never auto-email' becomes 'this status change ALWAYS emails', because there is no other path to the value. It also fails principle 2 (volume-first): the Content dashboard's bulk bar can offer Approve and Pending over 200 rows but cannot set the one content state that matters, so a producer flagging 40 decks sends 40 individual emails they did not ask for. This is exactly the wave-30 lesson (A REFUSAL THAT PROTECTS A SIDE EFFECT CAN LOCK THE MAIN EFFECT) applied only to the zero-recipient case and left half-done. RULING: both status doors validate with `isValidContentStatus` (all three values) and write mail-free — files-content-status.ts's 'MUST NEVER import a mailer' invariant is unchanged and now actually means something for all three values. The content-note endpoint is untouched: a note plus an explicit requestChanges flag plus a send is one deliberate organizer action, not an auto-email. No compatibility shim: the narrow predicate is deleted and every call site and test updated.
