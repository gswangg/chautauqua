## Amendment (wave 73): a participant's invite state is ONE vocabulary and ONE label map, both in pure core — and the roster's words win

Verified on main b2fe1367: the four-member set is re-typed six times (src/routes/tasks.ts:194 + a hand-written membership ladder and error string at :196-205; src/routes/api/submissions.ts:787 INVITE_STATUS_VALUES; src/server/repo/portal/invitations.ts:11; src/server/repo/tasks/grid.ts:18 GridInviteStatus; app/src/pages/submissions/types.ts:97; app/src/pages/speakers/types.ts:67+:69), and the LABEL map exists twice and DISAGREES on half its members: app/src/pages/speakers/types.ts:71-76 says none='Not invited', accepted='Confirmed' while app/src/pages/submissions/SubmissionDetailPage.tsx:165-170 says none='None', accepted='Accepted'. The same co-presenter is therefore CONFIRMED on the roster/speaker record and ACCEPTED on the submission detail — where 'Accepted' is also that page's own submission-decision word (STATUS_LABELS.accepted) — and 'None' is a raw wire literal shown to a user. This is GATE-8 P3 #14/#26 ('one identity rendering per person everywhere') reproduced byte-for-byte, plus the DEC-613 delay-fused-second-copy shape that waves 68 and 70 fixed for sort order and TaskKind. RULING: one pure src/domain/invite-status.ts owns INVITE_STATUSES (as const), the derived InviteStatus type, isInviteStatus, and INVITE_STATUS_LABELS; every other site imports or aliases it, and the runtime validator checks membership in that same array rather than re-listing it. The roster vocabulary is the winner — it has five call sites (ParticipationMenu, GridFilters, OnboardingGrid, SpeakerDetailPage, the roster grid), 'Accepted' collides with the decision word on the one page that used it, and a wire literal is never a user-facing word (DEC-843). The three subsets in src/domain/acceptance.ts (ACTIVE_INVITE_STATUSES, SCHEDULING_PARTICIPANT_STATUSES, PORTAL_VISIBLE_INVITE_STATUSES) keep their members and their written reasons but are pinned as subsets of the base via `satisfies` (never a type annotation, which would widen the tuples and break inArray typing); the fact that the last two are the SAME SET under two names is stated and pinned by a test so a future edit to one that should have been both fails loudly.
