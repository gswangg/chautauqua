# DEC-079: Acceptance side effects become retryable-exactly-once: planning runs BEFORE the status/accepted_at commit; bulk status changes are chunked and batched

updateSubmissionStatuses currently commits the accepted_at UPDATE first, then runs non-transactional planning; since fireAcceptance keys on accepted_at IS NULL, a planning failure permanently strands an accepted submission with zero onboarding tasks and no retry path — the SPEC §5 "exactly once, idempotently" invariant is unreachable. D1 has no interactive transactions, so ordering is the fix: on a first accept, run runAcceptancePlanning (already idempotent on (contact, task-title) pairs) BEFORE the row UPDATE; if planning throws, the submission stays un-accepted and the producer's retry re-fires the planner, which skips already-created rows. If the UPDATE fails after planning, retry re-runs planning as a no-op then updates. Bulk shape: chunked initial SELECT (DEC-078); non-firing rows updated in one chunked UPDATE statement per batch (set status + updated_at only — accepted_at untouched preserves it); firing rows handled individually (planning, then update with accepted_at=now).
