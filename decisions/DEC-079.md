# DEC-079: Acceptance side effects become retryable-exactly-once: planning runs BEFORE the status/accepted_at commit; bulk status changes are chunked and batched

updateSubmissionStatuses currently commits the accepted_at UPDATE first, then runs non-transactional planning; since fireAcceptance keys on accepted_at IS NULL, a planning failure permanently strands an accepted submission with zero onboarding tasks and no retry path — the SPEC §5 "exactly once, idempotently" invariant is unreachable. D1 has no interactive transactions, so ordering is the fix: on a first accept, run runAcceptancePlanning (already idempotent on (contact, task-title) pairs) BEFORE the row UPDATE; if planning throws, the submission stays un-accepted and the producer's retry re-fires the planner, which skips already-created rows. If the UPDATE fails after planning, retry re-runs planning as a no-op then updates. Bulk shape: chunked initial SELECT (DEC-078); non-firing rows updated in one chunked UPDATE statement per batch (set status + updated_at only — accepted_at untouched preserves it); firing rows handled individually (planning, then update with accepted_at=now).

## Amendment (wave 26): the bulk-status UPDATE phase is idempotent-retry, not atomic — RULED DELIBERATE, and pinned by a convergence test

DEC-079 already rules the ordering (plan BEFORE the row UPDATE, so a planning throw leaves rows un-accepted and a retry re-plans idempotently). The residual, correctly identified by review: `src/server/repo/submissions/status.ts:566-572` and `:578-584` issue separate chunked UPDATEs (90 ids per chunk) with no transaction, so a failure between chunks leaves a half-applied batch with onboarding rows already written at `:563`. RULED DELIBERATE, not a defect to fix this wave: `db.batch(` appears nowhere in `src/` — every repo test in this tree drives a hand-rolled drizzle-chain fake (`test/status-bulk-statement-count.test.ts:85-199` is the reference shape), so introducing D1 batch for one call site would force a `.batch` implementation into every fake, which is a harness change disguised as a fix. The operation is idempotent in both directions (re-applying the same status is a no-op for already-updated rows; `accepted_at` is stamped at most once by the DEC-009 amendment above; onboarding planning is idempotent on (contact, task-title)), so a retry converges. The obligation this amendment creates is EVIDENCE, not restructuring: a test that partially applies a batch, re-runs it, and asserts convergence with no double-stamp — a ruling with no scan drifts back.
