# DEC-527: Every ms-epoch value accepted at the API boundary passes DEC-517's isEpochMs, and the rule is locked by a globbed enumeration over the route layer rather than three hand-picked call sites

DEC-517 established `isEpochMs` (`src/routes/api/validators.ts:62`, `Number.isInteger` and nothing else) as the ONE ms-epoch boundary predicate, and adopted it at `src/routes/api/forms.ts:104,111` and `src/routes/review/shared.ts:189`. It missed the fourth ms-epoch body field in the product: `task.dueDate`. `src/routes/tasks.ts:167` accepts `typeof body.dueDate === "number"` on POST /events/:eventId/tasks and `:259` does the same on PATCH /tasks/:id, so three malformed values get through with no error: `NaN` (typeof is "number") reaches `src/server/repo/tasks/crud.ts:120`, is falsy, and is silently stored as NULL — the organizer set a due date, the row has none, nothing said so; `1.5` becomes 1 Jan 1970 and instantly flags the task overdue; `1e18` produces an Invalid Date whose getTime() is NaN and is bound into D1 as NaN. Separately, the same falsy coercion at `crud.ts:120,156` (`input.dueDate ? new Date(input.dueDate) : null`) discards a legitimate `0`. This matters more now than it did last wave, because DEC-520 just made due dates load-bearing for the J6 grid column, the overdue counters and the reminder cron. Decision: (a) both task routes validate through `isEpochMs` and reject with a fields error, never coerce; (b) the repo's null test becomes an explicit `=== null || === undefined` check so epoch 0 survives; (c) the invariant is guarded the DEC-511/DEC-518 way — a test GLOBS `src/routes/**/*.ts`, finds every source line that writes a ms-epoch body field into a validated value, and asserts the file imports `isEpochMs`, because the three previous spot-fixes are exactly why this fourth site was missed. A hand-listed manifest of "routes that take epochs" is forbidden; the test derives the list.
