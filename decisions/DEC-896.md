# DEC-896: A settings row is label / value / hint, and the rail names the section actually in view

app/src/pages/settings/SummarySection.tsx:58-63 renders a two-column label/value row, but the 09-settings frame's read views are a three-column definition grid whose right column carries the row's hint ('Used on the public pages', 'Last exported 4 Mar'). Six panels render through this one primitive, so the frame's structural complaint against all six is ONE change here, not six per-panel rewrites -- one shared vocabulary beats per-page fixes. Separately app/src/pages/Settings.tsx:73-88 derives the rail's active link from the ?section= param alone, while the page is a single scrolling column: the reader scrolls past three sections and the rail still claims the first. Rule: SummarySectionRow gains an optional `hint: ReactNode` rendered as the row's third grid column, collapsing when absent (never an empty cell); at least three panels supply real hints in the same change, because a prop with one call site is a setting nobody sets; and the rail's active state follows the section in view via IntersectionObserver, with an explicit rail click winning until the next scroll settles.

## Amendment (wave 26): a settings EDIT view is a form in the definition grid, never a phone screen in the content column — one shared shell owns width, pairing, and the footer row

That is exactly the phone anatomy DESIGN-RULINGS B10 condemns, and every other settings edit view repeats it, so a per-panel fix would be improvised five times. Each view carries its consequence line right-aligned per the B10 table. ## Amendment (findings wave 4): a paired settings field keeps its own content width — the pair box is content-sized, never the column

B10's first rule is "field width follows content, not the column", and the shell honours it: settings.css declares --chq-field-w-date 200px / seats 110 / name 320 / slug 420 and SettingsField applies them. Then `.chq-settings-field-pair .chq-settings-field { width: 100% }` inside a `1fr 1fr` grid spanning the 820 column overrides every one of those tokens, so a two-up date pair renders 401px per field and a paired seats field 401px instead of 110px. This is the exact measurement the fidelity fleet reported ("dates 401 vs 200, seats 178 vs 110") and it is one rule defeating the token it was built to honour. Ruling: the pair is content-sized (`auto auto`, justify-content:start, 18px gap) and members keep their own width class; nothing inside the pair may set width:100%. Fixes all three consumers (Event, CFP, Tracks and rooms) at once.

## Amendment (wave 20): the Public pages and embeds section rule carries its own consequence caption

The vendored read view puts a micro-label consequence on the section rule itself — 'Unpublishing returns 404 to anyone holding the link' (Chautauqua Settings.dc.html:131), the same register the Saved embeds rule uses for 'Turning one off breaks it wherever it is pasted'. It is the copy rule the pack states twice — 'Say the constraint you need before acting' (README Copy rules 4) and the wave-19 shape 'the row that sends must state its consequence' — and it matters here because the toggle is irreversible from the visitor's side: a link already pasted on someone else's site starts 404ing. RULING: PublicPagesPanel renders the caption right-flushed on its section head in the micro-label register (11px/600/0.04em uppercase, muted), reusing an existing eyebrow/caption class rather than minting a parallel one. This extends DEC-896 (which already owns this panel's B10 no-edit-view shape) rather than DEC-785, which wave 19 is amending for the saved-embed editor.

## Amendment (wave 22): a settings edit row is a per-entity width hook, and the frame's drag column is dropped rather than drawn dead

app/src/pages/settings/settings.css:1022 gives ONE class, `.chq-settings-edit-row`, `grid-template-columns: 1fr auto auto` -- and TracksRoomsPanel.tsx wears it on BOTH the track rows (:425) and the room rows (:616). The frame gives those two rows DIFFERENT column counts: tracks `20px 1fr 150px auto` (Settings.dc.html:825), rooms `20px 1fr 110px 150px auto` (:841). One class cannot carry two column counts -- the same 'a shared vocabulary class is not a width hook' shape wave 21 found on `.chq-content-table`. Consequence in the build: the room's seats input has no track of its own (it is stuffed into the `-meta` cell alongside the usage count), and both rows' meta columns size from their own content instead of the frame's fixed 150px, so nothing lines up down the column. Ruling: split into `.chq-settings-track-edit-row` and `.chq-settings-room-edit-row`; `.chq-settings-edit-row` keeps only the shared non-width properties and declares NO grid-template-columns. The frame's leading 20px drag column is deliberately NOT reproduced: no track/room reorder endpoint exists, and a drag handle that cannot drag is a dead control -- the house rule the templates and roster lanes already applied. Widths are therefore 1fr/150/auto and 1fr/110/150/auto.
