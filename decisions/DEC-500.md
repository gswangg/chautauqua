# DEC-500: A field's options are validated against its EFFECTIVE kind (patch value ?? stored value), and options exist only on dropdowns

src/forms/builder.ts:100 nests the dropdown-options check inside `if (input.kind !== undefined)`, but `PATCH /api/v1/fields/:fieldId` never carries `kind` (src/routes/api/forms.ts:208-214 patches label/helpText/required/options/rule only), so the check is dead on every edit. `{"options": []}` or `{"options": null}` therefore writes an empty option list onto a live dropdown, after which every answer fails `!(field.options ?? []).includes(value)` (src/forms/validate.ts:88) and a required dropdown becomes permanently unsatisfiable — a bricked public CFP with no error raised at edit time. The rule becomes one rule for create and patch alike: validation resolves an effective kind from `input.kind ?? the stored field's kind`, requires a non-empty string array on dropdowns whenever `options` is supplied (and on create), and rejects `options` on a non-dropdown field rather than silently storing a value nothing reads. The stored kind reaches the validator through a typed `existing: { id, kind }` parameter that replaces the bare `ownFieldId`, so the compiler — not a reviewer — proves both call sites pass it.
