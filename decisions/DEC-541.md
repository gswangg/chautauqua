# DEC-541: A submission's answers are written by ONE set-based upsert keyed on the (submission_id, form_field_id) unique index -- never a per-field read-then-write loop

There are two writers for submission_answer and they disagree about how the invariant is enforced. src/server/repo/submit.ts:283 createSubmissionAnswers builds all rows and issues one chunked multi-row INSERT per chunkRowsForInsert batch (DEC-528). src/server/repo/portal-edit.ts:286-309 saveSubmissionEdits instead loops every cleaned custom answer and issues a SELECT ... LIMIT 1 followed by an UPDATE or an INSERT -- two sequential D1 statements per field, on the J7 hot path a speaker hits every time they save. A 25-question CFP costs 50 serial statements per save, and the read-then-write is racy between two concurrent saves in a way the schema already makes unnecessary: the former src/db/schema.ts:223 (now split across src/db/schema/) declares submission_answer_submission_id_form_field_id_idx as a uniqueIndex, so SQLite's INSERT ... ON CONFLICT DO UPDATE does the whole thing atomically in one statement per chunk. The field guide's standing rules both point the same way -- "two implementations of one invariant means one is wrong -- atomic SQL beats read-then-write" and "delete a losing duplicate implementation, don't keep it unused". Decision: (a) src/server/repo/submit.ts gains `upsertSubmissionAnswers(db, submissionId, answers): Promise<void>` -- the same locked-field filter and row shape createSubmissionAnswers has today, written with `.onConflictDoUpdate({ target: [submissionId, formFieldId], set: { valueJson: excluded.value_json, updatedAt } })`, chunked by chunkRowsForInsert so DEC-528's bound-parameter budget still governs. (b) createSubmissionAnswers is DELETED, not wrapped -- its one call site (src/routes/public/submit.tsx:745) switches to the new name, because a create is just an upsert that cannot conflict and two names invite two behaviours. (c) portal-edit.ts's loop is replaced by one call; DEC-501's hidden-answer DELETE below it is untouched and still runs after the upsert. (d) The regression bar counts STATEMENTS against a fake db, not just final state: N custom answers must cost ceil(N/chunk) write statements and zero reads.
