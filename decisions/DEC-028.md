# DEC-028: Portal splits into parallel sub-apps with a create-if-missing shared gate/layout; headshots get kind 'headshot' and a public /headshots route

Two wave-4 tasks deepen /portal in parallel; DEC-012 says only src/index.ts mounts, so the portal becomes three sub-apps: existing src/routes/portal/index.tsx (dashboard + submission detail, gains nav links — declared overlap), new src/routes/portal/profile.tsx (portalProfileRoutes) and src/routes/portal/tasks.tsx (portalTasksRoutes), each mounted at /portal in src/index.ts. Shared chrome: src/routes/portal/shared.tsx exporting speakerGate (exact copy of index.tsx's redirect gate: no session -> /login, non-speaker -> /admin) and PortalLayout (the existing Layout markup taking { branding, children }) — created if missing by either task with exactly this contract (declared identical-content overlap; merge dedupes; a later cleanup rewires index.tsx onto it). All portal form posts use csrfForm with the checkDoubleSubmitCsrf token pattern already used by /login. Headshots: file.kind gains literal 'headshot' (text column — additive to DEC-003's enum, no migration) with submission_id null and uploaded_by_contact_id set; contact.headshot_url stores '/headshots/<fileId>'. GET /headshots/:fileId is a PUBLIC route (owned by the profile task): 404 unless the file row's kind is 'headshot'; streams from R2 with the stored image content type and Cache-Control: public, max-age=86400. Rationale: headshots of visible speakers are public content by definition (J10 renders them), and the authenticated /files/:fileId route belongs to in-flight w3-f with speaker/participant authz that would 401 public pages — a dedicated public route avoids both the leak-by-authz-hole and the mid-flight file collision. Upload validation inline per DEC-020 values: png/jpg/jpeg/webp only, 8 MB cap, never served as HTML.


## Amendment (wave 13) — PortalLayout IS the phone app shell: header / scrolling body / footer band, mirroring DEC-576 on the SSR side

Every v7 portal frame is 390 wide (docs/design/README.md's file table rules the portal out of desktop scope entirely), and each draws the three-region app shell with a fixed footer band. On main, PortalLayout (src/routes/portal/shared.tsx) renders <body> -> <header class="chq-header">, <main class="chq-measure">, <footer class="chq-portal-footer"> with no shell wrapper, and src/routes/portal/portal.css.ts's only <=700px block carries three rules (lines 332-336). The portal is the phone-first surface of this product and is the one shell that never got the pattern the admin shell has had since DEC-576. RULING: PortalLayout wraps its three regions in a .chq-portal-shell element that carries NO top-level declarations (desktop is byte-identical), and portal.css.ts's 700px block turns that wrapper into the flex column: header flex-shrink:0, main flex:1/min-height:0/overflow-y:auto, footer flex-shrink:0 with the ink top rule and sunk fill. No `overflow: hidden` anywhere (the frames' device-frame clipping is canvas presentation, and phone-wrap-conformance bans overflow-x:hidden); tokens only (DEC-383).
