# DEC-543: A list endpoint never selects a column none of its renderers display: the email-log list and the email-log detail read have separate projections

src/server/repo/email.ts has ONE SELECTED_COLUMNS projection shared by listEmailLog and getEmailLogById, and it includes bodyText, bodyHtml, icsText and icsFilename. Neither consumer of the LIST renders any of them: app/src/pages/comms/HistoryTab.tsx:52-60 renders exactly sentAt, subject, toEmail and status, and the dev mailbox list page renders Recipient/Subject/Status/Sent/Event. bodyText is capped at MAX_RICH_TEXT_LENGTH = 100000 and bodyHtml is its rendered twin, so a default page (clampPerPage default 50) of the J5 comms history can ship megabytes of email bodies that are parsed, JSON-serialized and then thrown away by the client. SPEC §7 names "oversized payload" as a bug in the same breath as waterfalls and N+1, and DEC-346 already set this precedent on the review side by dropping `description` from every plan-scoped whole-set load. Decision: (a) src/server/repo/email.ts declares two projections -- a LIST projection carrying exactly the columns its two renderers display, and the existing full projection kept for getEmailLogById, which is the detail read the dev mailbox message page and the .ics download need. (b) The types split with them: `EmailLogListRow` (narrow) is what listEmailLog returns, `EmailLogRow` (full) is what getEmailLogById returns; the SPA's app/src/pages/comms/types.ts mirror drops the fields the API no longer sends, so a future component cannot read a field that is silently undefined. (c) No route contract changes shape otherwise -- GET /api/v1/events/:eventId/email-log keeps its { items, total, page, perPage } envelope and its filters. (d) The regression bar asserts the ABSENCE: a list response's items must not carry bodyText/bodyHtml/icsText, and the detail read must still carry all three.
