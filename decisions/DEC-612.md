# DEC-612: External record identity is one namespaced external_ref column per imported table, unique inside its own owner scope

Idempotent re-import needs a stable key that is THEIRS, not ours. One nullable TEXT column `external_ref` on `contact`, `submission` and `track`; the value is always `"<source>:<their id>"` (lower-snake source, e.g. `sessionboard:12345`), never a bare id, so two sources can never collide and a ref always says where it came from. Uniqueness is scoped to the row's own owner — contact(org_id, external_ref), submission(event_id, external_ref), track(event_id, external_ref) — and SQLite treats NULLs as distinct, so hand-created rows are untouched by the constraint. A uniqueIndex is a contract: it exists in schema.ts AND in the migration (test/migration-parity.test.ts enforces both directions). Any read that filters on external_ref must handle NULL explicitly — a nullable column inside a negated set predicate silently skips NULL rows.

## Amendment (wave 54): external_ref is the import's PRIMARY key, not its only one — a contact row with no ref match resolves by normalised email before it is allowed to create, so a returning speaker keeps one CRM history

Verified on main: src/server/repo/import/sessionboard.ts:711 treats "no matching external_ref" as create for the contacts entity, and loadExistingRefs (:60-79) consults external_ref alone; `contact` carries no (org_id, email) uniqueness (src/db/schema/org.ts:75-89), deliberately. So importing a Sessionboard roster into an org that already holds CFP-created contacts forks EVERY returning speaker: two rows, two histories, two sets of tasks — the exact opposite of SPEC J11's "one speaker network across events", and the measured "same-email duplicates survive import" in the eval findings. The fix needs no new mechanism and no migration: the sibling importer already rules this way (src/server/repo/contacts/import.ts:254/308 keys creates on a normalised-email map), the one email-identity rule exists (DEC-454 normalizeEmail), and the batched resolver already exists IN THIS FILE — loadContactsByEmail (:194) — used for `participants` and never for `contacts`. RULING: for the contacts entity, an unmatched external_ref falls back to a normalised-email lookup over one pre-loaded batch map (never a per-row await); an email match is an UPDATE of that contact, counted as updated in both dry-run and apply so the preview cannot disagree with the result; the matched row ADOPTS the external_ref only when its own ref is null and no other row in the batch claims it, because the (org_id, external_ref) uniqueIndex is a contract and not a hint; a matched row that already carries a different ref is updated with its ref left alone, and future runs keep resolving it by email. Creates happen only when neither key resolves. The in-batch maps stay current so a second file row with the same email chains onto the first, exactly as the CSV importer already does.
