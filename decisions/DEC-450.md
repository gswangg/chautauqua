# DEC-450: The Airtable sync serves exactly one org, named by AIRTABLE_ORG_ID, and refuses loudly when configured without it; its code correctness is stage-1 even though its wiring is stage-2

src/sync/airtable.ts:115-165 holds the only where-less selects left in src/ (verified by a repo-wide scan): every contact and every submission across every org, plus whole-table participant and submission_track joins, pushed into one base each cron tick. That is a cross-tenant leak in a multi-tenant schema where every other read is org-scoped, and it is the unaddressed half of the same review-lens finding whose other half (a fabricated `SES-` ref) DEC-435 already fixed in stage 1 -- so the precedent is settled: the sync's live wiring (token, base, deploy, cron in production) is stage-2, its code correctness is stage-1, and fixing it needs no secret and no account. Scoping mechanism: an explicit AIRTABLE_ORG_ID binding, because one base belongs to one org and nothing in the data model lets the sync infer which. Fail-loudly resolves the partial-configuration case: token+base with no org id is a misconfiguration that would publish tenant A's roster into tenant B's base, so it throws instead of syncing everything; all three absent stays a silent no-op, since an unconfigured integration is a valid state. Unbounded memory is bounded the same honest way: a MAX_SYNC_ROWS cap that throws when exceeded rather than silently truncating a customer's base.

## Amendment (wave 64): an incremental Airtable tick reads CHILD rows only for the submissions it is actually pushing

DEC-450 caps every sync read at MAX_SYNC_ROWS and refuses rather than truncate; DEC-725 added the KV watermark so an incremental tick pushes only rows changed since the last success. But src/sync/airtable.ts:224-269 still reads participant and submission_track ORG-WIDE on every tick, watermark or not. Two consequences: an incremental tick that pushes three submissions still scans the whole org's children, and — the real defect — at SPEC §0's 5,000-submission scale those child tables exceed MAX_SYNC_ROWS (10,000), so the cap fires and the sync throws on EVERY tick, including ticks with nothing to push. A cap that protects a first full push must not condemn every incremental one. RULING: the child reads are scoped by chunked `inArray` over the ids actually being pushed, skipped entirely when the watermarked submission set is empty, and their MAX_SYNC_ROWS refusal now measures the children OF THE PUSHED SET. Determinism (participant.order/contact.id, track.position/track.id) is unchanged — a permuted Speakers or Tracks cell would re-fire the customer's automations on a non-change.
