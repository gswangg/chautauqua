# DEC-713: A file version is deletable: the chain re-links across the gap, the thread is re-homed, the object goes with the row, and the removal is recorded

## Amendment (wave 50): the version-delete route's population is the deliverable kinds only — an 'attachment'/'resource'/'headshot' file row is a disjoint population that 404s

Verified at the file on main: getFileDeleteScope (src/server/repo/files-versions.ts:624-638) selects the file row on id alone with no file.kind predicate, and DELETE /api/v1/files/:fileId (src/routes/files.ts:530-589) only requires scope.submissionId to be non-null. A CFP form-answer upload is written by insertAttachmentFile (src/server/repo/submit.ts:387-404) with kind='attachment' AND a non-null submissionId, so it lands squarely inside that population: an organizer can delete a public submitter's form attachment through a route whose whole contract is version-chain deletion. deleteFileVersion then repoints file_comment and task_assignment.file_id (files-versions.ts:753-785) but never submission_answer.value_json, where the answer stores that file id inline — leaving the submission's file-field answer pointing at a deleted row, a broken download on the organiser detail screen and in exports, with no error anywhere. The whole-submission cascade in submission-delete.ts already cleans both, so only this path leaks. RULING: this route serves exactly the deliverable version chains — FILE_KINDS. getFileDeleteScope projects file.kind and returns null for anything outside it, so the route answers not_found, mirroring the disjoint-population idiom the file already uses for getResourceFileScope and getTaskFileScope (both return null when the row is not theirs). No new capability is minted: deleting a CFP attachment remains something only the whole-submission cascade does.

A wrong or sensitive upload is currently permanent -- there is no delete affordance anywhere in Content. The version-chain model (previous_file_id, DEC-244) and the chain-scoped comment thread (DEC-573) dictate the semantics: removing a link must repoint its successor to its predecessor in one statement, or the chain silently forks; the removed row's comments must move to the surviving neighbour, or DEC-573's promise that a thread survives re-upload breaks on delete; and the R2 object must go too, or 'deleted' means 'hidden'. Authority follows the same asymmetry as every other content action: an organizer may remove any version, a speaker only their own latest while the submission is still pending review. The deletion appends a system note to the thread so the history says what happened rather than quietly shrinking.

## Amendment (wave 47): FileStore deletes are set-based — R2's own array form is the batch, and the destructive sweep uses it

DEC-713 fixed the ORDER of the delete-a-file dance (R2 object first, DB row second, so a throw leaves a retryable row rather than an orphaned object). src/routes/api/submissions.ts:631-636 honours that ordering and then violates its cost model: a nested loop `await store.delete(key)` per R2 key, with an eslint-disable acknowledging it. Bulk submission delete is the blast-radius page — deleting 50 sessions with their deliverables is 150+ sequential R2 round trips paid BEFORE the first DB row is touched, so a request that times out has deleted an arbitrary prefix of the blobs while every submission row survives, which is the exact failure DEC-713's ordering was meant to make retryable and instead makes silently lossy. R2's binding already accepts an ARRAY of keys in one delete call; the abstraction in src/server/context.ts narrowed it to a single key and thereby manufactured the loop. Amendment: FileStore gains `deleteMany(keys: string[]): Promise<void>` (chunked to R2's per-call key limit) and is the only method that talks to R2 delete; `delete(key)` survives ONLY as a one-line delegation to deleteMany([key]), justified by ENUMERATION — exactly two genuinely-single call sites exist (src/routes/files.ts:491 version delete, src/routes/api/portal-config.ts:339 resource delete) and zero other loops.

## Amendment (wave 51): the R2-delete ordering becomes a scanned class, and its third call site is converted

DEC-713's own wave-47 amendment ENUMERATED exactly two single-object delete call sites -- src/routes/files.ts and src/routes/api/portal-config.ts:339 -- and the wave-50 ordering flip converted only files.ts and the bulk submissions path. portal-config's resource delete still runs store.delete(r2Key) at :339 BEFORE deleteFileRow at :340, so a failure of the row delete strands a `file` row whose bytes are permanently gone: GET /files/:id 404s forever, which is exactly the data-loss corpse wave 50 ranked as the worse of the two asymmetric failures. Rule: EVERY FileStore delete commits its DB row first and deletes the bytes second, with an object-delete failure logged and swallowed (a committed delete is never reported as a failure). The rule stops being a per-path convention: a two-directional ledgered scan fails an unconverted or newly-added call site naming file:line, and fails a stale ledger line too. And the deleteFileVersion doc comment (src/server/repo/files-versions.ts:713-715) that still instructs callers to delete the object FIRST is rewritten, not annotated -- a comment naming an order the caller no longer performs is a trap laid for the next lane.

## Amendment (wave 50)

DEC-713's wave-47 ordering deletes every R2 object BEFORE the DB commit: src/routes/api/submissions.ts:632 calls store.deleteMany over every eligible submission's file keys and only then commitSubmissionDelete at :634, and src/routes/files.ts:491 deletes the object before deleteFileVersion at :493. Its stated rationale -- "a throw here leaves every submission row intact for a retry rather than orphaning an object" -- treats the two failure modes as symmetric. They are not. If the DB half fails, live submission and file rows survive pointing at bytes that are permanently gone: GET /files/:id 404s forever and the version chain lies, contradicting SPEC §5 "history complete and downloadable", and nothing in the product tells the organizer that happened. If the object half fails after a committed row delete, the result is an unreferenced blob -- storage cost, no user-visible consequence, reclaimable by a sweep. Rule: commit the DB delete first, then delete the objects; a failure of the object delete after a committed row delete is logged and reported, never turned into an error that tells the organizer the delete did not happen. Same shape as DEC-427 (a failed public-cache bump must not turn a committed mutation into a 500). deleteMany's chunking (DEC-713 wave-47) is unchanged; only the order moves.

## Amendment (wave 19): the RECEIVER is part of the call shape — the committed-delete guard matches any *store binding, not the identifier someone happened to type

test/file-delete-ordering.scan.test.ts claims to scan "every store.delete(/store.deleteMany( occurrence" and classify each as committed-delete-shape, exempt, or ledgered. It matches the case-sensitive literal `store.delete(`, so src/routes/public/submit.tsx:610's `fileStore.delete(pf.r2Key)` — an R2 compensation delete on the ANONYMOUS public CFP path, the one delete site a stranger can reach — has never been classified by it. This is the recurring shape (a scan that binds one call shape misses its sibling) applied to the receiver rather than the method. The guard must match any identifier ending in store/Store followed by .delete(/.deleteMany(, and its root widens to all of src on the same named-exclusions rule as DEC-948, so the two halves of the claim (which files, which calls) are both true.

## Amendment (wave 21): the public CFP submit rollback joins the committed-delete shape — the ledgered exception is fixed, not carried

test/file-delete-ordering.scan.test.ts's KNOWN_BYTES_BEFORE_ROW carries exactly one entry: src/routes/public/submit.tsx:610 deletes N R2 objects and only then calls commitSubmissionDelete, with the entry's own reason ending "deserves its own wave, not a drive-by fix inside this scan-widening task". This is that wave. The ordering is not academic: if commitSubmissionDelete throws (or the request dies between the two awaits), the submission and its file rows survive pointing at objects that no longer exist — the precise state DEC-713's row-first rule exists to prevent, on the one write path an anonymous visitor can drive. The rollback is also a transaction unwind, so the R2 half must never mask the original failure: it goes in an inner try whose catch logs and swallows, and `throw err` still rethrows the real cause. A ledger entry that outlives the lane that could not fix it becomes permission (DEC-635 wave-52's own words), so the entry is deleted rather than reworded, and the scan re-pins the call site by FILE + committedShape rather than by the line number 610, which this change moves.

## Amendment (findings wave 9): per-version Delete asks only for the newest version in its chain; a superseded version deletes on click

DEC-713 landed per-version delete as a quiet tertiary confirmed through the shared ConfirmDialog, which is right for the control's register but wrong for its scope: it asks on every row. docs/design/DESIGN-RULINGS.md item A3 rules the asymmetry explicitly — "Deleting the newest version must ask; deleting a superseded one need not" — and the reason is real. The newest file in a chain is what the speaker's portal, the public surfaces and the show-flow all resolve to; deleting it changes what is live. A superseded version is housekeeping on a row already marked REPLACED, and a modal per row is the friction that makes CNT-S3's content loop expensive. Scope the ask per CHAIN head (idxInChain === 0), not to the single globally-newest row: VersionList already renders several independent previousFileId chains, and each chain's head is the live file for its own document, so confirming only the global newest would leave a second live file deletable without a word. Everything else is unchanged — same apiDelete path, same loud error banner, same onDeleted refresh, same tertiary after Download, same grid columns.

## Amendment (wave 67): a rollback unit is every durable write the request minted, not every write below the try

`src/routes/public/submit-post.tsx:331` calls `createContact` in the else-branch of the existing-contact lookup, ABOVE both the R2 fan-out rejection path (:386-398) and the try/catch that owns rollback (:407-448) — whose own comment at :401-405 claims "The DB write phase is one committed unit". It is not: both failure paths delete the submission, clean up R2 and refund the email budget, but nothing deletes the CRM contact row an unauthenticated submit just minted, so every failed anonymous submit leaves an orphan in the org directory. RULING: the rollback's population is every row THIS REQUEST created, found by reading upward from the first durable write — not by trusting the comment that sits above the try. The pre-existing-contact case is untouched (the request minted nothing); the freshly-minted case is deleted in both failure paths, after the submission cascade and before the R2 sweep, and cleanup failure never masks the original error. DEC-713 is the right home because its standing rule is already "a rollback is still an ordering"; this amendment fixes the ordering's START, which the wave-21 amendment got wrong.
