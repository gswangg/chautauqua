# DEC-070: Organizer participant-management endpoints: POST /api/v1/submissions/:id/participants (invite co-presenter) + PATCH /api/v1/submissions/:id/participants/:participantId (visibility); invites never auto-email

J7 says session invitations can be accepted/declined and SPEC §5 gives participant an invite state, but no route on main ever writes invite_status='invited' or mutates participant.visible after creation — the walkthrough fakes both with raw SQL (w12-c open-PLANNER items 1-2). Shapes: POST body {contactId, role?} (role defaults 'speaker'); server verifies the submission belongs to the caller's org and the contact belongs to the same org, rejects an existing (submissionId, contactId) pair with ApiError 'invalid' fields.contactId, inserts visible=true, inviteStatus='invited', order=max+1, and returns the participant serialized like src/server/repo/submissions/detail.ts rows. PATCH body {visible: boolean} with the same org/submission scoping. Per product principle 4 (communications are deliberate) creating an invitation sends NO email — the invite surfaces in the portal and producers notify via the existing compose flow.
