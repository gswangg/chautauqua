# DEC-526: The reviewer bulk reminder counts outstanding work exactly the way the progress panel does — recusals excluded — because a nudge and a dashboard that disagree are two implementations of one invariant

Verified on current main: `src/routes/review/plans.ts:301-319` (GET /api/v1/plans/:id/progress) loads `repo.listRecusalsForPlan` and computes each reviewer's assigned total through `assignedExcludingRecused` (DEC-271: a recused submission never counts toward a reviewer's assigned total, because stranding it as permanently incomplete is dishonest). The POST /api/v1/plans/:id/remind handler in the SAME FILE at :384-420 never loads recusals at all: it uses the raw `assignments.get(user.userId) ?? []`, so its `completed >= assigned.length` skip test is computed against a larger denominator than the dashboard shows, and its body text literally states `You have ${assigned.length - completed} submission(s) left to review`. Two live consequences: a reviewer who recused from every remaining item is emailed a nudge for work the producer's own progress bar shows as finished, and every other reviewer is told a number the producer cannot reproduce anywhere in the UI. SPEC J4 pairs these two surfaces in one sentence ("Producer watches progress, nudges laggards with one bulk reminder") — they are one question asked twice. Decision: the remind handler loads `repo.listRecusalsForPlan(db, plan.id)` and routes its per-reviewer total through the identical `assignedExcludingRecused` call, so the skip test, the count in the body, and the progress row are one computation. Deliberately NOT changed here, so nobody re-litigates it: the `maxEvaluations` cap filter that `src/routes/review/reviewer.ts:109` applies to a reviewer's own queue stays out of both totals — that file is owned by an in-flight wave-30 task, and the cap is a coverage ceiling on a submission, not a reduction of a reviewer's assignment. Recusal is a per-reviewer withdrawal and is the only thing that shrinks an assignment.
