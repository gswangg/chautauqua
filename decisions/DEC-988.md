PUT /api/v1/events/:eventId/portal-settings (src/routes/api/portal-config.ts:98), mergePortalSettingsInput, and app/src/pages/settings/formState.ts's buildPortalSettingsPayload/validatePortalSettingsForm all exist and are exercised ONLY by their own unit tests — no surface in the product calls the endpoint. ## Amendment (wave 56): a portal setting with no reader is a lie — `showResources` gates both entry points AND the route itself, and the organiser preview shows what the speaker sees

VERIFIED at this plan's runtime, and it is DEC-851's wave-55 doctrine ('a declared knob with no reader is a lie') on a second surface. DEC-988's own body asserts that src/server/repo/portal/data.ts 'reads welcomeMessage/logoUrl/accentColor/showResources and renders them on every speaker's portal'. Three of those four are true. `showResources` is written by app/src/pages/settings/PortalSettingsPanel.tsx:293-301, validated at src/routes/api/portal-config.ts:137-139, defaulted true in the schema (src/db/schema/content.ts:17), merged at src/server/repo/portal-config.ts:97,118 and threaded into PortalBranding at src/server/repo/portal/data.ts:44,61,168 — and then read by nothing. A grep of src/routes/portal for the identifier returns zero hits: the footer link (index.tsx:288), the 'Read notes' CTA (index.tsx:220), GET /portal/resources and its download twin (tasks/resources.tsx:18,34) and the organiser preview's Resources section (preview.tsx:78-86) all render unconditionally. Turning the toggle off changes nothing anyone sees. RULING: OFF is a server-side visibility decision, not a link-hiding one — SPEC §6/§2's server-side-visibility invariant and this swarm's standing 'honoring on arrival and emitting on departure are two halves' rule both say a hidden link over a live route is half a contract. When showResources is false: both entry points are not rendered, GET /portal/resources and GET /portal/resources/:resourceId/download return the portal's existing 404 idiom (`c.text("Not found", 404)`) BEFORE any resource read, and the organiser preview replaces the Resources section with one muted organiser-facing line naming the Speaker-portal setting that hid it (the preview's job is to show what the speaker sees; a preview that shows more than the speaker gets is the DEC-026 'a preview that cannot refuse is not a preview' defect). The pairing is asserted by a test derived from the portal_settings schema — every boolean column names a reader under src/routes/portal or carries a written exemption — never a hand-listed pair.

## Amendment (wave 74): `showResources` is a per-EVENT visibility decision; `PortalBranding` is per-portal chrome and loses the field

`getPortalData` resolves exactly ONE event — the event of the speaker's most recent submission (`src/server/repo/portal/data.ts:152`), or nothing at all for a task-only speaker (DEFAULT_BRANDING, `showResources: true`) — and `branding.showResources` then gates `GET /portal/resources` and its download twin (`routes/portal/tasks/resources.tsx:28,47`), the footer Resources link (`routes/portal/index.tsx:297`) and every session card's "Read notes" (`:372`). But `getMyResources` and `getResourceDownloadScope` are ORG-WIDE across every event the contact participates in (`portal/resources.ts:52,165` via `getMyEventIds`). So a producer's per-event setting silently governs another event's content in both directions: Event B's resources are served whenever Event A's toggle happens to be on, and Event B's section 404s whenever A's is off. Every fixture in the tree is single-event, so the DEC-988 schema-derived reader test (`test/portal-show-resources.test.ts:305`) proves only that the column HAS a reader, never that the reader reads the right event. RULING: `PortalBranding` keeps only chrome — eventName, welcomeMessage, accentColor, logoUrl — resolved from the most-recent-submission event as today, and that chrome scoping is stated in the type's own comment so it is a choice rather than an accident. `showResources` moves to `PortalData.showResourcesByEventId: Record<string, boolean>`, covering every event the contact participates in (one batched `portal_settings` read over that event-id set; an absent row reads true, matching the schema default at `db/schema/content.ts:17` and `upsertPortalSettings`'s insert default). Readers resolve by the event that OWNS the thing being gated: the resources list filters `getMyResources`'s groups to permitted events and refuses only when NO event permits; the download gates on the resource's own event; the footer link renders when any event permits; the session card gates on that session's event, so `PortalSession` gains `eventId`. Same reading discipline fixes the sibling on the same page: `scheduledSubline` pairs `branding.eventName` with whichever placed session it finds across ALL events (`index.tsx:188-191,320`), so it must name the placed session's own `eventName`.
