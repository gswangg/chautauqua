# DEC-988: Portal branding is edited where it is summarised: the Speaker-portal section's Change drill carries the WHOLE portal_settings record, and there is exactly one save path for it

PUT /api/v1/events/:eventId/portal-settings (src/routes/api/portal-config.ts:98), mergePortalSettingsInput, and app/src/pages/settings/formState.ts's buildPortalSettingsPayload/validatePortalSettingsForm all exist and are exercised ONLY by their own unit tests — no surface in the product calls the endpoint. PortalSettingsPanel.tsx's own header comment (lines 11-18) records why: the DEC-815 SummarySection conversion deleted the panel's form and left "a decision on where that edit affordance should live" to a follow-up that never came. Meanwhile src/server/repo/portal/data.ts:141-164 reads welcomeMessage/logoUrl/accentColor/showResources and renders them on every speaker's portal, so an organiser can SEE those values summarised in Settings and can never set them — a value settable once and never editable is half a feature, and a decision with no code is a lie. The drill that already exists (?section=portal&edit=1) is the answer: it reveals the record's own fields — Welcome note (long text), Logo URL, Accent colour, Show resources — ABOVE the existing ResourcesPanel, saving through the existing PUT with the existing validate/build pair. No second quick-save form and no new endpoint: two save paths for one row is one too many. Blank clears (buildPortalSettingsPayload already maps '' to null); accent validation stays the client mirror of the server's isValidHexColor, so the field accepts exactly what its placeholder shows.
