# DEC-516: The public JSON feed asks D1 for ONE window (LIMIT+OFFSET); the route never slices a cumulative prefix

DEC-502 fixed the right contract at the wrong layer and said so in its own comment: `src/routes/public/index.tsx:277-287,295-298` fetches the cumulative prefix and slices it in JS because `boundedRowLimit` (`src/server/repo/public/bounds.ts:27-31`) is a bare `page * perPage` LIMIT with no OFFSET. The envelope is now correct but a `?page=100` feed request makes the id query select up to MAX_PUBLIC_ROWS (1200) rows and discards 1188 of them, on an unauthenticated public route, in a product whose stated first engineering priority is performance (SPEC §7: uncached public SSR < 150 ms). The cumulative shape is genuinely required by the HTML "show more" list, so this is not "delete the prefix" — it is "the caller states which shape it wants". Decision: `bounds.ts` gains `boundedWindow(page, perPage): { limit: number; offset: number }` clamped against the same MAX_PUBLIC_ROWS ceiling (an offset at or beyond the ceiling yields limit 0 / an honest empty page, never an error), `getPublicSessions`/`getPublicSpeakers` take an explicit opt (default = today's cumulative behavior, so no call site changes meaning by accident), the JSON feed passes the window opt, and the JS slice at index.tsx is deleted. MAX_PUBLIC_ROWS stays the single ceiling — this adds an OFFSET, it does not add a second ceiling constant (DEC-477/487).
