# DEC-879: A recording is a deliverable: the upload allowlist grows a video tier and `recording` is a file kind, both derived from one enumeration

docs/design "Chautauqua Content.dc.html" ships a "Recording · 1 version" deliverable chip (lines 131, 329) and a 186 MB flags-demo.mp4 library row (line 395), but src/domain/files.ts's FILE_KINDS is presentation|poster|handout and the DEC-020 allowlist has document/image/text tiers only — so the deliverable the design names can be neither requested nor uploaded, and every accept= attribute in the product (derived from ALLOWED_UPLOAD_EXTENSIONS) silently excludes it. Add `recording` to FILE_KINDS and a VIDEO_EXT_CONTENT_TYPE tier (mp4 -> video/mp4, mov -> video/quicktime, webm -> video/webm) with its own cap of 250 MB — comfortably above the design's largest artifact, and a distinct tier because reusing the 25 MB document cap would make the kind exist and still be unusable. validateUpload stays the single source of truth; a video is never served with a sniffable or HTML content type. src/routes/tasks.ts:64 hand-lists DELIVERABLE_KINDS as a second copy of the same vocabulary — it must be derived from FILE_KINDS, message included, because a hand-listed manifest desyncs the moment a kind is added (the exact failure this decision is fixing).

## Amendment (wave 10): the accept attribute and the caps text are ONE per-kind derivation

DEC-879 admitted a 250 MB video tier for kind 'recording' only, and uploadHintText(kind) (src/domain/files.ts:81-91) honours that — it filters the video extensions out for every other kind. But the raw list it derives from, ALLOWED_UPLOAD_EXTENSIONS (files.ts:67-72), is exported flat and is what every `accept` attribute is built from, so the two disagree at every call site. Verified: src/routes/portal/tasks/views.tsx:189 prints the tier-correct hint while line 194's accept offers ALL extensions including video; twenty-eight lines later the Replace form for the SAME assignment prints a bare uploadHintText() with no kind (line 217) beside the same over-wide accept (line 222) — two grammars for one assignment inside one component. app/src/pages/content/UploadZone.tsx:11 and 71 do the same, so a recording zone advertises no video while its picker offers it, and a presentation zone offers .mp4 the server will reject. src/views/form-render.tsx:110 offers video on form file fields the server validates as the non-video 'handout' tier (submit.tsx:425, portal/tasks.tsx:392). SPEC J8 requires the upload UI to state accepted types and size caps, and DEC-020's own last sentence says 'verbatim from this list'. RULING: one exported per-kind accessor, `allowedUploadExtensions(kind?: FileKind)`, is the single source for BOTH the accept attribute and the hint; uploadHintText is refactored to call it so the filter rule exists once; every accept site passes the same kind its hint passes. A PROJECTION MUST CARRY ITS SOURCE'S LIMITS.

## Amendment (wave 20): if a recording is a deliverable like any other kind, every reader of the deliverable vocabulary must speak all four

DEC-879 made 'recording' a first-class FILE_KINDS member (src/domain/files.ts:11). Two readers still speak the pre-879 three-word vocabulary from hand-typed copies. (1) src/server/repo/submissions/list.ts declares `deliverableCounts: { presentation: number; poster: number; handout: number }` at line 66, builds its zero map as `({presentation:0,poster:0,handout:0} as Record<FileKind, number>)` at line 425 -- a cast that asserts a shape the object does not have -- and defaults the same three-key object at line 476. The SPA's own contract (app/src/pages/content/types.ts:58) declares `Record<FileKind, number>`, so the client's type promises `deliverableCounts.recording: number` on a payload the server can ship without that key: a typed-as-number undefined across the wire. (2) src/routes/files.ts:170 throws "kind must be presentation, poster, or handout" while the pure core one line of provenance away derives the identical message from FILE_KINDS (src/domain/files.ts:136) -- the duplicate has already drifted and now tells an organizer that a legal kind is illegal. Ruling: the zero map and every message enumerating file kinds derive from FILE_KINDS; no `as Record<FileKind, ...>` cast may stand in for a complete object literal. This is the field guide's A HAND-TYPED EXTENSION LIST FORGETS ITS THIRD MEMBER, one member later.

## Amendment (wave 22): an advertised upload cap the platform refuses is a lie — the recording cap is DERIVED from the Workers request-body ceiling

DEC-879 chose 250 MB for the recording tier as a number "comfortably above the design's largest artifact" (186 MB), with no reference to what the runtime will accept. Cloudflare Workers cap the incoming request body at 100 MB on Free/Pro, so every upload between 100 MB and the advertised 250 MB is rejected at the edge before the Worker runs: validateUpload's over-cap branch (src/domain/files.ts:183) and the deliberately-designed on-screen error path it feeds (src/routes/portal/tasks.tsx:496 reRenderWithError) are unreachable for exactly the files the hint invites, and the speaker sees a raw platform error instead of the product's own message. The repo already has the correct pattern one file over: ISOLATE_MEMORY_BUDGET_BYTES / ARCHIVE_PEAK_MULTIPLIER / ARCHIVE_MAX_TOTAL_BYTES (src/routes/files.ts:348-359) derive a cap from a named platform limit and pin the derivation with a test. Ruling: src/domain/files.ts names WORKERS_REQUEST_BODY_MAX_BYTES (100 MB) and derives VIDEO_MAX_BYTES beneath it with explicit multipart-framing headroom (95 MB); every hint and error message computes its number from the constant rather than hand-typing it; a test asserts no upload tier can exceed the ceiling. A cap the user is shown must be a cap the request can actually reach.

## Amendment (findings wave 5): a zip is a handout, never a slide, a poster or a recording

The upload allowlist admits .zip for every deliverable kind (src/domain/files.ts:33, DOCUMENT tier), but the design rejects it by name: frame docs/design/Chautauqua Content.dc.html :448 refuses "keynote-final.zip is not a slide format" with the rationale "We take PDF, Keynote, PowerPoint and MP4 so reviewers and the AV team can open it without unpacking anything. A zip could hold anything" — while the same file's library row :480 lists "agents-workshop-pack.zip" as a legitimate 41 MB deliverable. Both are true at once only if the accept-list is per-kind, which DEC-879 already established for video/recording. RULING: zip is admitted only for the 'handout' kind, enforced in validateUpload (the server tier, not just the accept attribute) with the message "Zip archives are only accepted for a handout deliverable", and dropped from allowedUploadExtensions for the other three kinds so the accept attribute, the hint text and the server agree. A cap that exists only in the SPA is a suggestion.

## Amendment (wave 54): one upload surface, one kind — the accept attribute, the hint text and the server's validateUpload call name the SAME FileKind constant

DEC-879's amendment made allowedUploadExtensions(kind) "the ONE place this per-kind filter is applied" (src/domain/files.ts:116-130), with zip admitted only for 'handout'. The public CFP file field breaks the claim three ways in one control: src/views/form-render.tsx:124 builds `accept` from allowedUploadExtensions() with NO kind (zip excluded), :168 renders uploadHintText("handout") (zip included), and src/routes/public/submit-post.tsx:213 validates with kind:"handout" (zip accepted). The picker therefore filters out a file type the visible hint and the server both accept — a submitter with a .zip handout sees it greyed out and concludes the product refuses it. test/upload-cap-single-source.test.ts already forbids a hand-typed accept string but never checks that the kind argument agrees across the three sites, which is exactly the drift that occurred. One exported constant for the CFP tier, used by all three sites, and a scan that compares the kind expression rather than only the derivation.
