# DEC-337: An index declared in src/db/schema.ts that no migration creates does not exist: migration parity is extended from columns to indexes, and the three composite indexes the new queries need land in migration 0018

test/migration-parity.test.ts guards table/COLUMN parity only (it parses CREATE TABLE and ALTER TABLE ... ADD), so an index declared in schema.ts's index()/uniqueIndex() blocks but never written into a migration is invisible to CI and simply absent from D1 — SPEC §7 names 'D1 indexes on every FK + (event_id, status) + (event_id, slug)' as a mechanic, and migration 0016 exists precisely because that class of gap already happened once. The parity test therefore gains a second assertion: every index name declared on an exported schema table must appear in a CREATE [UNIQUE] INDEX statement in some migrations/*.sql. Migration 0018 (append-only per DEC-015, one file, single-lane ownership so no two lanes claim the 0018 number) carries any gap the extended test finds plus three composite indexes the wave's rewritten queries read through: email_log(event_id, sent_at) for the DEC-334 COUNT/MAX and the email-log list's ORDER BY sent_at DESC, submission(event_id, created_at) for DEC-335's default ORDER BY created_at DESC LIMIT, and contact(org_id, last_name, first_name) for DEC-336's ORDER BY/LIMIT. New indexes are declared in BOTH schema.ts and the migration so parity holds in the direction the test checks.
