# DEC-531: The overview's speaker counters are SQL conditional aggregates — the same form the J6 grid already uses — and aggregateSpeakerCounts is deleted rather than left standing as a second implementation

`src/server/repo/overview.ts:286-299` selects EVERY pending task_assignment row for the event (joined to task for scoping and due_date) and materializes them into JS purely to compute three scalars: `contactsOwing`, `overdueAssignments`, and `nextTaskDueDate`. At the SPEC scale target of 200-800 speakers against a five-task default set that is thousands of rows loaded on the producer's FIRST screen — the one SPEC §2.3 requires to answer "what needs my attention?" — and DEC-520 has just made due dates universal on auto-created tasks, so the row set only grows. Every other section of this same file is already a COUNT/MIN aggregate (`:241-245` grouped status counts, `:376-393` a conditional aggregate with a correlated EXISTS, `:269-272` a `min(close_date)`), and the file's own comment at `:375` states the rule: "One conditional-aggregate query ... never a per-row query". Worse, `src/server/repo/tasks/grid.ts:221-230` already computes the identical two numbers in SQL — `count(distinct case when status <> 'complete' then contact_id end)` and the overdue `count(distinct case ...)` — which by the w24 lesson means one of the two implementations is wrong, and it is the one that reads thousands of rows to count them. Decision: (a) the three scalars come from ONE conditional-aggregate SELECT plus the `min(task.due_date)` it can carry in the same row, expressed in the same SQL form grid.ts uses so the overview strip and the J6 grid can never disagree; (b) `status = 'pending'` and `status <> 'complete'` are equivalent because task_assignment has exactly two statuses (`src/routes/tasks.ts:60`), and the aggregate uses grid.ts's `<> 'complete'` spelling so the two are textually comparable; (c) the pure `aggregateSpeakerCounts` export and its unit test are DELETED, not kept as a now-unused helper — the house rule is delete the old code and update call sites, and leaving it invites the next wave to reintroduce the row-materializing path. `minNonNull` stays: it still serves the other deadline cells.
