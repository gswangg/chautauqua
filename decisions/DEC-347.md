# DEC-347: The wave-20 perf run is a BASELINE at a pre-fix tip: a new or newly-scaled check over budget is a logged finding owned by its fix lane, never an OPEN ITEM; a check over budget at UNCHANGED seed scale is a regression and is an OPEN ITEM

The perf lane must grow the seed before the endpoints it grades are observable at all (DEC-342: the files library 'is not yet observable on local D1 because the perf seed writes no file rows', so DEC-333's conjunctive test was unmet), but it branches from main at the same moment as the lanes that fix those endpoints, so its numbers are stale-by-construction for exactly the routes DEC-344/345/346 touch. Recording that ambiguity as a PASS/FAIL coin flip is the DEC-195/DEC-203 pattern DEC-339 named. Ruling, so the lane is decidable rather than arguable: (1) the seed grows deliverable file rows with real previous_file_id version chains and raises the evaluation count so the review subsystem is measurable at the SPEC's reviewer scale — a perf harness that cannot observe a table cannot grade it; (2) two checks are added, `files library (page 1)` and `plan results (page 1)`, both cls:'read', appended after the existing checks to minimise merge overlap, and neither is `optional` (DEC-338); (3) a check that is over budget only because THIS lane newly seeded the rows it reads — the two new checks, plus `reviewer queue`, `plan progress` and `rating PUT` under the larger evaluation scale — is recorded verbatim as a logged finding naming task-w20-a/b/c as its owner, per DEC-331's never-raised-never-dropped rule, and does not make the lane FAIL; (4) a check that is over budget at unchanged seed scale IS a regression and IS an OPEN ITEM; (5) the authoritative measurement is wave 21's perf gate at a tip containing every merged wave-20 lane, and this log must say so in its RESULT section rather than implying the numbers grade the fixed code.

## Amendment (wave 31): a perf receipt taken during a parallel wave grades a PAIRED DELTA measured in one session, never a bare absolute; migration numbers are pre-assigned per lane

DEC-347 already rules that a perf number belongs to the tip it was taken at. Wave 31 adds a condition that decision never faced: three lanes will each run `npm run seed` + `perf:seed` + `wrangler dev` + 30 measured iterations CONCURRENTLY on one machine, so every absolute p95 in this wave is inflated by an unknown, unrecordable amount of sibling load. Grading a fix PASS or FAIL on such an absolute is the DEC-195/DEC-203 coin-flip DEC-339 named, in both directions: a real fix can read FAIL, and a machine that happens to be quiet can read PASS on nothing. RULING: each perf lane runs the harness TWICE in one uninterrupted session on one machine state — once at its branch point before any edit (BEFORE), once at its own tip (AFTER) — and reports the pair plus the ratio for its own row. The lane's grade is the DELTA; the authoritative ABSOLUTE grade is the serial verification wave's single perf-smoke run at a tip containing every merged wave-31 lane, exactly as DEC-347 clause (5) already requires. A receipt that reports only an AFTER number is incomplete and does not close its item. Corollary, to stop a merge collision this wave's shape makes likely: migration numbers are pre-assigned — 0040 to the files-library lane (only for DEC-773's FK fallback), 0041 to the reviewer-queue lane, 0042 to the plan-results lane; 0039_user_name.sql is the current tip and is tracked and applied (docs/verification-log/task-w28-c-perf-smoke-c6dbdb7c.md:15, "all 39 migrations (0001..0039) applied"), so the wave-27 "untracked migration" alarm is retired, not carried.
