# DEC-839: The saved-embed wire contract: options are a parsed recipe validated by the live route's own parsers, and OFF is an empty 200

DEC-822 settled the semantics and its code never landed — SavedEmbedsPanel.tsx:49 still posts {name, surface, format:'iframe', options:{}} and PATCH /embeds/:id (src/routes/api/embeds.ts:100-110) still accepts only name+enabled, two waves after the decision was minted. Because the fix spans a server half and a builder half that must ship in parallel, the planner pins the shape rather than letting two workers each invent one. Contract: an embed row serialises as {id, eventId, name, surface, format, options, enabled, createdAt, updatedAt} where `options` is the PARSED object — {trackId?, day?, q?, limit?, fields?, accent?} — never the stored JSON string. POST /api/v1/events/:eventId/embeds and PATCH /api/v1/embeds/:id both accept {name?, surface?, format?, options?, enabled?} and validate every option through the SAME parsers the live route runs (parseTrackId/parseDay/parseNameQuery/parseLimit/parseCardFields/parseAccent, src/routes/public/query.ts), rejecting an unparseable value with a loud 400 naming the field instead of storing a value the renderer will silently drop — the builder's parameter set and the live route's parsers are ONE contract (DEC-817). GET /embed/e/:id: an unknown id keeps the designed public 404; enabled===false returns an EMPTY 200 (text/html, empty body, unchanged cache headers), because a page the organiser switched off must not shout 'not found' on a customer's website. The builder is addressed by ?embed=<id> (the ?section=/?tab= URL-state grammar of DEC-710/728), heads itself 'Editing · <name>', its primary action is Save changes and Copy snippet is secondary. The recipe string ('Sessions · iframe · AI Engineering · 6 fields') is produced by ONE shared formatter so the list row and the editor heading cannot drift.


## Amendment (wave 27): a saved-embed option value is length-bounded AND scoped to the embed's own event

DEC-839 promises every option is validated by the live route's own parsers so nothing is stored as junk the renderer will later ignore. Two holes: parseTrackId/parseRoomId/parseFormat/parseNameQuery are trim-or-null with no maximum, so unbounded text persists into embed.options_json (DEC-417 unapplied to this route), and a trackId or roomId belonging to a DIFFERENT event is stored happily, producing a permanently empty surface and desynchronising the DEC-931 delete guard, which only scans embeds whose eventId matches. Fix both at the one shared parseEmbedOptionsInput: parseBoundedText first, then the live parser, then an existence check against the embed's own eventId -- a 400 naming the field.

## Amendment (wave 12): an ownership ledger that measures a parser's PRESENCE is not measuring the thing it was built for; `owned` requires a refusal test

`test/json-column-parser-ownership.scan.test.ts` landed this hour and closes a real hole: all 16 `*_json` schema columns now carry exactly one ledger row and every named parser is proved to exist and be wired. But its `owned` predicate (`ownedRowHasLiveOwner`) is entirely structural — the file exists, exports the symbol, and something touches the drizzle property. It cannot tell a validating parser from a cast. Two of its sixteen owners are casts: `parseStoredEmbedOptions` (`src/server/repo/embeds.ts:41-45`) returns `parsed as EmbedOptions` after only an is-it-an-object check, and silently returns `{}` for an array/primitive; `parseEventBranding` (`src/domain/event-branding.ts:26-34`) does `JSON.parse(json) as {logoUrl?: string; accentColor?: string}` and throws an unnamed TypeError on stored `null`. The other fourteen validate and have refusal tests. I rule the `owned` verdict gains a required second citation — a test file that proves the parser REFUSES (or explicitly drops) a malformed value for THAT column — so the ledger measures behaviour, not presence. A column with no such test is `owed` with a principled reason, never a silent `owned`.

## Amendment (wave 12, sha 54b35ede): both cast owners now validate; the ledger's `owned` verdict carries the second citation

Implemented the ruling above. `parseStoredEmbedOptions` (`src/server/repo/embeds.ts`) now type/bounds-checks every DEC-839 option key (mirroring the write door, `parseEmbedOptionsInput` in `src/routes/api/embeds.ts`) and throws a named `EmbedOptionsJsonError` naming the offending key instead of casting or silently returning `{}` for a non-object stored value; existence-scoped checks (trackId/roomId belonging to the embed's own event) stay write-side only, since a read-side re-check would need a `Db` round trip per row. `parseEventBranding` (`src/domain/event-branding.ts`, DEC-322) now throws a named `EventBrandingJsonError` on invalid JSON, a non-object value (including the literal `null`), or a non-string `logoUrl`/`accentColor` — replacing the bare `TypeError` a stored `null` used to throw. Two behaviors stay deliberately as documented: `accentColor`'s hex GRAMMAR (not its string type) is still validated only at the render edge, per DEC-374 — duplicating the grammar check here would be a second, divergent copy of the same rule; and a `logoUrl` that fails `safeImageSrc` is still DROPPED, not replaced or thrown on, since the write door (`src/routes/api/events.ts`) already rejects an unsafe `logoUrl` before storage, so a row that fails here can only be pre-DEC-322 legacy data.

`test/json-column-parser-ownership.scan.test.ts`'s ledger now requires every `owned` row to carry `refusalTest` (a repo-root-relative test file path) and `refusalSymbol` (the exact exported symbol from `parser` that row claims proves refusal/drop for that column); a new check (`ownedRowHasRefusalTest`) fails the row if the file doesn't exist or doesn't mention the symbol, with two new falsifiability controls proving both failure modes are caught. All 16 `owned` rows now cite a real refusal test — 14 from tests already on disk (re-verified, not re-typed from memory), plus the two new tests for the columns fixed here (`test/embed-options-json-parser.test.ts`, `test/event-branding-json-parser.test.ts`). `contact.social_links_json`'s `parseSocialLinks` is a deliberate TOLERANT reader that never throws (malformed input degrades to the empty record, per its own header) — its refusal test (`test/profile.test.ts`) proves the "explicitly drops" half of the citation, not a throw; this is a legitimate, documented reading of the ruling's "or explicitly drops" clause, not a gap.
