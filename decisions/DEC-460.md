# DEC-460: "Server pagination on all admin lists" becomes an enforced bound on every /api/v1 list envelope, with no "naturally small" exemptions

SPEC.md:193-195 ("every table assumes thousands of rows: server pagination...") and SPEC.md:353 ("Server pagination + filtering on all admin lists") have been graded PASS by every prior ledger from one citation: test/pagination.test.ts, which only unit-tests the pure clampPage/clampPerPage helpers and no endpoint's use of them. task-w17-f-pagination-audit-stage1.md enumerated the actual population and found 14 /api/v1 handlers that return the DEC-013 {items,total,page,perPage} envelope with no server-side ceiling: the envelope's `page: 1, perPage: items.length || 1` is cosmetic shape-compliance, not pagination. Two of them (/api/v1/pipeline, /api/v1/users) grow with every contact ever pushed and every account ever invited across an org's whole lifetime; five more are org- or event-config lists with no enforced ceiling; the remaining seven are bounded only by an assumption about how organizers behave. I verified the finding still holds at the current tree (listPipelineForOrg src/server/repo/pipeline.ts:136, listOrgUsers src/server/repo/users.ts:32, listSegmentsForOrg src/server/repo/contacts/segments.ts:31, listEventsForOrg src/server/repo/events.ts:56, listTracksForEvent :211, listRoomsForEvent :343, listResourcesForEvent src/server/repo/portal-config.ts:170, listSavedViews src/server/repo/views.ts:80, listTemplates src/server/repo/comms.ts:41, listRevisions src/server/repo/revisions.ts:44, listPlansForEvent src/server/repo/review/plans.ts:79, listReviewerRowsForPlan src/server/repo/review/reviewers.ts:27 — every one a bare select with no .limit()). Every such handler must now derive `items` from a query the client cannot make unbounded and report a true `total`. No exemption list: "naturally small" is an assumption, not an invariant, and a single API-token client can violate it, which is exactly the kind of row DEC-459 forbids grading from a sample.
