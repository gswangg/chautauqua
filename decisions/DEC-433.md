# DEC-433: The public ?page= parameter gets two bounds, because one number endangers two different things

src/routes/public/query.ts:6 accepts any positive integer and it becomes the SQL LIMIT via page*perPage at src/server/repo/public/sessions.ts:325 and speakers.ts:67. Two distinct harms, so two distinct bounds, each stated once. (1) Number.isInteger(1e308) is TRUE, so ?page=1e308 produces LIMIT Infinity and a 500; and every distinct page value is its own caches.default key (src/server/pubcache.ts:60 versionedCacheKey salts the full URL), so the edge cache is trivially floodable. That is a parse-layer problem: parsePage clamps to [1, MAX_PUBLIC_PAGE=50] -- out-of-range clamps DOWN to the cap rather than resetting to 1, so a deep link stays useful. (2) ?limit=100 (parseLimit, 1..100) can still multiply a legal page into a 5,000-row response, which is exactly SPEC.md:193-195's forbidden case on the surfaces carrying SPEC.md:334-335's <150ms uncached-SSR budget. That is a repo-layer problem: a new boundedRowLimit(page, perPage) = min(page*perPage, MAX_PUBLIC_ROWS=600) that THROWS on a non-finite or non-positive-integer argument, so no future caller can bypass parsePage and reach SQL with garbage. The cap is not a hidden truncation: the Show more anchor (sessions.tsx:68, speakers.tsx:77 and :124) stops rendering at MAX_PUBLIC_PAGE, because a link that clamps back onto its own page is worse than no link. The DEC-418 two-step shape and the separate COUNT(DISTINCT) are untouched -- this bounds the existing design, it does not replace it.

## Amendment (wave 30): the public query grammar bounds its STRINGS too — an over-cap value parses to null and takes its request out of the edge cache

DEC-433 clamped `?page=` precisely because each distinct value mints its own caches.default entry AND sizes a LIMIT — but src/routes/public/query.ts's parseTrackId/parseFormat/parseRoomId/parseNameQuery are still trim-or-null with no maximum, so an anonymous `/e/<slug>/sessions?q=<1MB>` reaches a D1 LIKE parameter and, via versionedCacheKey (src/server/pubcache.ts:71, which keys off the whole URL), mints an unbounded number of cache entries. Bounding only the persisted embed options (DEC-839, already landed) closed the write side and left the live route open. Over-cap parses to null — degrade, never throw — because that is exactly the contract parseLimit/parseDay/parseAccent already keep for bad input on these anonymous surfaces; a 400 would be a second grammar for the same class of value. The cache half is closed the way DEC-442 closed the ics half: a request-shaped skip in publicCacheMiddleware, so a junk query is served uncached instead of polluting the key space.

## Amendment (wave 44): the public edge-cache key is a CANONICAL url — pathname plus a closed, derivation-checked param allowlist — not the raw request url

DEC-433 clamped ?page= and its wave-30 amendment bounded the query STRINGS, both because versionedCacheKey (src/server/pubcache.ts:72-76) salts the WHOLE url, so each distinct value mints its own caches.default entry. Both fixes bound values of params the surfaces actually read and leave the general case wide open: any unknown param still keys. Two consequences, one a correctness-of-the-promise failure and one the same flooding surface DEC-433 exists to close. (1) SPEC §7 promises 'edge-cache hit TTFB < 50 ms' for public pages, and every real-world share of a session or agenda link carries utm_source/fbclid/gclid — those requests miss the cache permanently and re-render SSR. /embed/e/:embedId reads no query params at all (src/routes/public/saved-embed.tsx), so 100% of any query string on it is pollution. (2) An anonymous caller mints unbounded entries with ?a=1..N under the length cap. Ruling: versionedCacheKey builds the key from pathname + only the params in one closed exported constant PUBLIC_CACHE_KEY_PARAMS (living in src/server/repo/public/bounds.ts beside the other public bounds), emitted in a fixed order, plus __chqv. Because a param that AFFECTS rendering but is missing from the key would serve the wrong page, the allowlist is not hand-trusted: a scan test derives every c.req.query("...") literal reachable under the two cached prefixes from src/routes/public/** and asserts the allowlist covers it exactly, with `ids` the one asserted exclusion (isUncacheableIcsRequest already bypasses the cache for it). hasOverlongQueryValue stays as a second, independent bound.

## Amendment (wave 45): the edge-cache key carries the value the HANDLER will use — an unusable query value is dropped from the key, and no query string takes a request out of the cache

The wave-44 amendment made versionedCacheKey canonical (pathname + PUBLIC_CACHE_KEY_PARAMS + __chqv) and closed with 'hasOverlongQueryValue stays as a second, independent bound'. That sentence is now wrong and this amendment supersedes it. hasOverlongQueryValue (src/server/pubcache.ts:109-115) scans EVERY param value and, on any value over MAX_PUBLIC_QUERY_VALUE_LENGTH=200, publicCacheMiddleware (line 390) serves the request with no match and no put. Its whole justification was key-space flooding — which the canonical key already closed for non-keyed params. What survives is a free lever: an anonymous `GET /e/<slug>/sessions?zz=<201 chars>` forces a full uncached SSR on every request, on precisely the surfaces SPEC §7 promises sub-50ms cache hits for, and `?q=<201 chars>` does the same through a keyed param, so scoping the check to the allowlist would only close half of it. Ruling: the key is built from what the route layer will actually use. Every parser behind PUBLIC_CACHE_KEY_PARAMS already ignores an over-cap value (it parses to null/default and the page renders identically to the param-absent page), so versionedCacheKey DROPS a keyed param whose value exceeds the cap, and hasOverlongQueryValue plus its call site are deleted outright — no compatibility shim. isUncacheableIcsRequest's per-user schedule.ics?ids= shape stays the ONE remaining bypass. The equivalence is proven, not assumed: a test asserts, for every name in the allowlist, that its parser returns the same result for an over-cap value as for an absent one.
