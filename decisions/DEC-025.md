# DEC-025: Wave-4 migrations: per-task reserved filenames 0005/0006/0007; 0004 left for w3-a; journal entries union

Wave 3's single-owner migration (DEC-017) serializes schema work; wave 4 needs three independent new tables and none touch the same rows, so each owning task ships its own migration under a filename reserved here — no numbering race, no shared file. Reserved: migrations/0005_w4_segment.sql (task w4-c): CREATE TABLE segment (id text PK, org_id text NOT NULL, name text NOT NULL, rules_json text NOT NULL, created_at integer NOT NULL, updated_at integer NOT NULL) + index on org_id. migrations/0006_w4_api_token.sql (task w4-e): CREATE TABLE api_token (id text PK, org_id text NOT NULL, name text NOT NULL, token_hash text NOT NULL, token_prefix text NOT NULL, created_by_user_id text NOT NULL, last_used_at integer, created_at integer NOT NULL, updated_at integer NOT NULL) + unique index token_hash + index org_id. migrations/0007_w4_saved_view.sql (task w4-g): CREATE TABLE saved_view (id text PK, event_id text NOT NULL, name text NOT NULL, config_json text NOT NULL, created_at integer NOT NULL, updated_at integer NOT NULL) + index event_id. 0004 is deliberately skipped — in-flight w3-a takes it per DEC-017; wrangler applies migrations in filename order and gaps are legal. Each task appends its own entry to migrations/meta/_journal.json and its matching drizzle table to src/db/schema.ts (declared mechanical-union overlap on both). DEC-015 append-only rule still binds: never edit committed migrations, and no wave-4 task recreates the DEC-017 ALTERs — those belong to w3-a's migration alone.
