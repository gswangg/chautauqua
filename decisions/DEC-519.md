# DEC-519: ics_sequence is bumped by every write that changes a field the VEVENT serializes — not only by slot writes

`src/mail/ics.ts:115-138` serializes SUMMARY from title, DESCRIPTION from description, and LOCATION from the room name, all keyed to `SEQUENCE:${e.sequence}` = `submission.ics_sequence` (`src/routes/public/feeds.ts:65-75`, `src/server/repo/comms.ts:262-297`). But `bumpIcsSequences` is called from exactly three places (`the former src/server/repo/agenda.ts:419 (now split across src/server/repo/agenda/),424,512` slot writes and `src/routes/comms.ts:481` after a send). Nothing bumps when the text changes: `src/routes/api/submissions.ts:154-195` (organizer PATCH of title/description) and :245-254 (revision restore) and `src/server/repo/portal-edit.ts:195-263` (a speaker renaming their own talk — legal after acceptance per swyx) all compute a changed/unchanged comparison already and then write without a bump; and `src/routes/api/events.ts:490` (PATCH /rooms/:roomId) renames a room without touching any of the sessions whose LOCATION it just changed. RFC 5545 requires a SEQUENCE increment on a significant change, and the product consequence is concrete: rename a talk or a room after invites went out and every subscriber's calendar keeps the old text forever, which directly contradicts SPEC §3's "calendar invites done right" and clarifications.md's "the room is assigned later — so invite updates are the flow that matters". Decision: every write path that changes title, description, or a room's name bumps through the single `src/server/repo/ics-sequence.ts` home; the room-rename case gets a set-based bump over the scheduled submissions in that room, in ONE statement (DEC-492: atomic SQL beats read-then-write, no per-row loop). Bumping is unconditional-on-change, never on a no-op write, since both the submission paths already have their before/after comparison in hand.

## Amendment (wave 11): the VEVENT-affecting write set includes event.timezone; ORGANIZER;CN (event.name) is deliberately NOT a bump trigger

DEC-519 enumerated the bumping writes BY EXAMPLE — title, description, room name — and the enumeration missed its next member. src/routes/api/events.ts:361-380 (PATCH /events/:eventId) writes `timezone` with no ics_sequence bump anywhere, yet every VEVENT's absolute DTSTART/DTEND is computed as zonedMinutesToUtc(day, startMin, event.timezone) in BOTH readers (src/routes/comms/send.ts for METHOD:REQUEST invites and src/routes/public/feeds.ts:196-197 for the PUBLISH feed). Change an event's timezone after invites went out and every subscriber's calendar keeps the old instant forever — the exact failure DEC-519 exists to prevent, one axis further out. Decision: a timezone change bumps ics_sequence for every submission with a schedule_slot in that event, in ONE set-based statement (DEC-492), only when the string actually changed (same-string PATCH is a no-op, mirroring the room-rename rule at events.ts:536-539). Explicitly REFUSED: event.name, which reaches the VEVENT only as ORGANIZER;CN (comms.ts:624) — an RFC 5546 non-significant property; bumping on a rename would re-notify every attendee of every session for a cosmetic edit. Also out of scope: window narrowing (DEC-844) orphaning a slot — stage 1 has no METHOD:CANCEL, and a PUBLISH feed drops the VEVENT on its own.

## Amendment (wave 6, sha d4584747): a slot write that changed nothing is not a calendar event, and the bump-site population is derived from the call sites, never hand-listed

DEC-519's own text is "ics_sequence is bumped by every write that changes a field the VEVENT serializes", and `test/ics-sequence-bumps.test.ts:1-8` states the second half out loud — "and must NOT bump on a no-op write". Two of the three VEVENT-affecting writes already honour it with written rationales (`src/routes/api/events.ts:394` timezone, `:564` room rename). The third — `upsertSlot` (`src/server/repo/agenda/slots.ts:78`), the single most frequent one, and the exact flow `docs/clarifications.md:12-14` names as "the flow that matters" — bumps unconditionally, so a drag that lands back in place re-notifies every calendar subscriber and churns `submission.updatedAt` (which is also the Airtable incremental cursor). The reason nobody noticed is the same test's scope line: it enumerates "every write path this task owns", a hand-listed population inside a rigorous body. Ruling: the differential goes on the slot write — `upsertSlot` compares day/startMin/endMin/roomId against the existing row before writing and bumps only on an actual change — and the test's enumeration is re-derived from every `bumpIcsSequences*` call site under `src/**`, with a ledger whose reasons are rule-shaped and never a wave, a branch, or a schedule.
