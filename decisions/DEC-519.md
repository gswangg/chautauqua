# DEC-519: ics_sequence is bumped by every write that changes a field the VEVENT serializes — not only by slot writes

`src/mail/ics.ts:115-138` serializes SUMMARY from title, DESCRIPTION from description, and LOCATION from the room name, all keyed to `SEQUENCE:${e.sequence}` = `submission.ics_sequence` (`src/routes/public/feeds.ts:65-75`, `src/server/repo/comms.ts:262-297`). But `bumpIcsSequences` is called from exactly three places (`src/server/repo/agenda.ts:419,424,512` slot writes and `src/routes/comms.ts:481` after a send). Nothing bumps when the text changes: `src/routes/api/submissions.ts:154-195` (organizer PATCH of title/description) and :245-254 (revision restore) and `src/server/repo/portal-edit.ts:195-263` (a speaker renaming their own talk — legal after acceptance per swyx) all compute a changed/unchanged comparison already and then write without a bump; and `src/routes/api/events.ts:490` (PATCH /rooms/:roomId) renames a room without touching any of the sessions whose LOCATION it just changed. RFC 5545 requires a SEQUENCE increment on a significant change, and the product consequence is concrete: rename a talk or a room after invites went out and every subscriber's calendar keeps the old text forever, which directly contradicts SPEC §3's "calendar invites done right" and clarifications.md's "the room is assigned later — so invite updates are the flow that matters". Decision: every write path that changes title, description, or a room's name bumps through the single `src/server/repo/ics-sequence.ts` home; the room-rename case gets a set-based bump over the scheduled submissions in that room, in ONE statement (DEC-492: atomic SQL beats read-then-write, no per-row loop). Bumping is unconditional-on-change, never on a no-op write, since both the submission paths already have their before/after comparison in hand.
