# DEC-111: Acceptance-created form tasks get real backing forms: find-or-create by exact title (isDefault=false, null open/close), task.formId set and self-healed when null; field specs are pure data FORM_TASK_FIELD_SPECS in domain/acceptance.ts

getOrCreateTask (src/server/repo/submissions/status.ts:20-44) creates the SPEC-mandated 'Hotel stay requirement form' / 'Flight reimbursement form' tasks (kind 'form', SPEC.md:131-132) with formId null, and both portal form routes hard-reject !scope.formId (src/routes/portal/tasks.tsx:240,291) — so the swyx must-have J6 onboarding forms 400 the moment a speaker clicks 'Fill out form' in any non-hand-wired event. Ruling: for kind='form' templates, getOrCreateTask finds-or-creates an event-scoped form titled exactly the task title with isDefault=false and null open/close dates (getDefaultForm filters isDefault=true, so it can never leak into public CFP submit), inserts that form's fields on first creation, sets task.formId, and BACKFILLS formId on an existing kind='form' task row whose formId is null (self-heal for already-broken events; idempotent). Exact field specs, all section 'speaker', deliberately no file-kind fields (the portal task-form POST has no upload path): Hotel stay requirement form -> dropdown 'Do you need a hotel room?' options [Yes, No] required; text 'Check-in date'; text 'Check-out date'; long_text 'Special requests'. Flight reimbursement form -> dropdown 'Do you need flight reimbursement?' options [Yes, No] required; text 'Departure airport'; number 'Estimated reimbursement amount (USD)'; long_text 'Notes'. Specs live in src/domain/acceptance.ts as exported pure data (DEC-002 pure-core); planAcceptance's signature and outputs are unchanged; status.ts still imports no mail module (DEC-009 tripwire).

## Amendment (wave 48): an event's task titles are unique within the event, enforced by a database index — find-or-create becomes insert-on-conflict-do-nothing then select

`getOrCreateTask` and `getOrCreateFormTaskForm` (src/server/repo/submissions/status.ts:40-116) are read-then-write find-or-creates keyed on `(eventId, title)` with no unique index behind them (src/db/schema/tasks.ts declares only `task_event_id_idx` and `task_form_id_idx`). Two concurrent acceptances therefore race and can each create a "Confirm participation" task row for the same event, each independently expanded to every accepted contact — a duplicate task, visible as a duplicate column on the organizer's speakers matrix and a duplicate row in the speaker portal. DEC-809 already established for segments that a uniqueness rule enforced only by a JS read-then-write is not enforced; migrations/0031 is the dedupe-then-index precedent this follows. Ruling: add a unique index on `(event_id, title)` in `task`, ship it via a dedupe-then-index migration exactly as DEC-809/migration 0031 did (merge any pre-existing duplicate title's assignments onto the surviving row before the index is added), and change `getOrCreateTask`/`getOrCreateFormTaskForm` from read-then-insert to insert-with-`onConflictDoNothing` followed by a select — the same shape as any other find-or-create the house now requires. A duplicate title is indistinguishable to the speaker who sees two identical rows, so uniqueness is the honest product rule; when the colliding title comes from an organizer-typed field (not the SPEC-mandated defaults), the conflict becomes a named field error on the task-creation form rather than a silent second row.

## Amendment (wave 54): a migration is D1 SQL or it is not a migration — no temp objects, and the dialect is scanned

migrations/0032_task_title_unique.sql opens with CREATE TEMP TABLE `_task_dedupe_keeper`. D1's SQL authorizer rejects every temp object with SQLITE_AUTH, so 0032 fails at statement 1 and is never recorded as applied — locally (`wrangler d1 migrations apply --local`) or in production. Consequence: `task_event_id_title_idx` (declared in src/db/schema/tasks.ts:35) exists in NO D1 database, and getOrCreateTask's `.onConflictDoNothing({target:[eventId,title]})` (src/server/repo/submissions/status.ts:108) therefore raises `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint` — a 500 on POST /api/v1/events/:id/submissions/status for every accept after the first task of that title exists. The whole J5/J6 accept journey is dead end to end. test/task-title-unique.test.ts runs the same SQL through node:sqlite, which ALLOWS temp tables, so a green suite was never evidence the migration could apply. Rule: the keeper set is expressed as a WITH-CTE (or correlated subquery) repeated per statement, never a temp table; 0032 is edited IN PLACE (a migration that never applied was never recorded, so renumbering would be a lie about history); and a new scan enumerates every migrations/*.sql for D1-forbidden constructs (TEMP/TEMPORARY, ATTACH, PRAGMA, BEGIN/COMMIT/SAVEPOINT) with an EMPTY exemption ledger.

## Amendment (wave 55): the form-task's backing form is the third find-or-create without a unique index -- give form(event_id,title) the same constraint task(event_id,title) got

getOrCreateFormTaskForm (src/server/repo/submissions/status.ts:40-46) is the same read-then-insert shape one level down -- SELECT form WHERE event_id=? AND title=? LIMIT 1, then INSERT -- and src/db/schema/event.ts:49-51 declares only a non-unique form_event_id_idx. Two accepts in one event racing the same template title both miss the read and both insert; the loser's form and its FORM_TASK_FIELD_SPECS field rows are orphaned, and getOrCreateTask's self-heal at :123-127 then attaches whichever row LIMIT 1 happens to return -- so a speaker's saved answers can reference form_field rows on a form the task no longer points at. Ruling: add a unique index on `(event_id, title)` in `form`, applied via a dedupe-then-index migration expressed as CTEs (never CREATE TEMP TABLE -- D1's authorizer refuses temp objects outright, per the wave-54 amendment above). The keeper is deterministic (oldest by created_at then id); losers' dependent form_field/answer rows are REPOINTED onto the keeper, never deleted -- no speaker answer may be lost, the same "a unique index that kills a feature is the wrong fix, check what it deletes first" rule DEC-556 applies. getOrCreateFormTaskForm changes from read-then-insert to insert-with-onConflictDoNothing followed by a select, matching getOrCreateTask's own shape.

## Amendment (wave 61): ONE unique-violation detector, and it walks `cause` at every site

The wave-48 amendment established the correct shape in tasks/crud.ts:233-243: the D1/better-sqlite3 driver wraps the raw SQLite error as `cause` (drizzle's DrizzleQueryError), so a translator that tests only `err.message` never matches and the promised 400 arrives as a 500. contacts/segments.ts:96 is the older, un-amended sibling: `err instanceof Error && /UNIQUE constraint failed/i.test(err.message)` -- one level short. Renaming a segment onto an existing name therefore returns an uncaught 500 on the exact path DEC-809 built the unique index to make friendly. A rule that lives as a private function inside one module cannot be applied by the next module that needs it. RULING: the detector is lifted verbatim into one shared, tested module (`src/server/repo/constraints.ts`), exporting `isUniqueViolation(err: unknown, fragment: string): boolean` which walks `[err, err.cause]`; tasks/crud.ts's private copy is deleted (no shim) and segments.ts uses it. Any future UNIQUE translator imports this or it does not exist.
