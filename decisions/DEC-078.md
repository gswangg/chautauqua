# DEC-078: Canonical id-chunk helper src/lib/chunk.ts (ID_CHUNK_SIZE=90); every inArray over an unbounded id list must iterate chunks

Three code sites hit or risk D1's ~100 bound-parameter ceiling (repo/public.ts, repo/submissions/status.ts, repo/review.ts), and two divergent local chunkIds copies already exist (repo/submissions/query.ts at 100 — no headroom for the extra eventId/status binds it is used with — and repo/comms.ts at 90). Decision: one pure module src/lib/chunk.ts with EXACTLY this content, so parallel tasks can each create the identical file and merge trivially:

```ts
// Canonical id-list chunking for D1 bound-parameter limits (DEC-078).
// D1 rejects statements above ~100 bound parameters; queries typically bind
// eventId/status alongside the id list, so 90 leaves headroom. Every
// inArray(...) over an unbounded id list MUST iterate chunkIds batches.
export const ID_CHUNK_SIZE = 90;

export function chunkIds(ids: string[]): string[][] {
  const out: string[][] = [];
  for (let i = 0; i < ids.length; i += ID_CHUNK_SIZE) {
    out.push(ids.slice(i, i + ID_CHUNK_SIZE));
  }
  return out;
}
```

repo/submissions/query.ts re-exports from it (dropping its local 100 — this also fixes the latent list.ts:150-158 headroom hazard) and repo/comms.ts deletes its local copy and imports it. Bounded lists (e.g. roomIds ≤ ~15 rooms, plan filter trackIds ≤ ~25) may stay unchunked with a comment saying why.

## Amendment (wave 11): the chunking rule is enforced by an enumerated source scan, not by a per-area sweep

src/lib/chunk.ts's own header states "Every inArray(...) over an unbounded id list MUST iterate chunkIds batches", and wave 10 found the rule obeyed on one axis only. Enforcement today is two per-area sweeps (test/chunk-sweep-overview.test.ts, test/chunk-sweep-exports.test.ts) — incomplete by construction, so a NEW file introducing an unchunked inArray lands silently. Decision: one repo-wide source scan asserts that every file under src/server/repo/** and src/routes/** containing `inArray(` either imports chunkIds from lib/chunk or appears in an exported allowlist that names, per file, why its id list is bounded (enum/literal set, single id, or a drizzle subquery rather than a JS array). Coarse on purpose: it cannot prove a chunked file chunks EVERY site, but it makes "a new unchunked reader" impossible to add unnoticed, and it forces the bounded cases to state their reason. The two per-area sweeps stay.

## Amendment (wave 14) — the chunk scan binds a CALL SITE, not a file

test/inarray-chunk-scan.test.ts passes a file the moment it imports chunkIds anywhere, so a second, unchunked inArray(...) in a file that already chunks elsewhere is invisible — which is exactly how the wave-10 D1 bind-budget overflow (unchunked inArray(taskId, eventTaskIds)) shipped and survived a repo-wide scan. A scan that a real bug walked past is a scan that measures imports, not behaviour. Ruling: the scan is per call site. For each inArray(col, X) occurrence under src/server/repo/** and src/routes/**, X must be a chunk-loop binding declared in that file (for (const X of chunkIds(...))), a module/file-level literal constant set (SCREAMING_CASE), or a per-call-site allowlist entry keyed file+identifier with a written reason. Whatever the tightened scan flags is fixed by chunking or allowlisted with a reason — never by loosening the predicate.

## Amendment (wave 18): the chunk scans are rooted at src, not at two directories someone named, and a comment is not a call site

test/inarray-chunk-scan.test.ts:18 and test/insert-chunk-scan.test.ts:22 both scan SCAN_ROOTS = ['src/server/repo', 'src/routes'] and only `.ts`. Every D1 call site outside those two directories is therefore unmeasured — src/sync/airtable.ts binds three real inArray() call sites and src/domain/acceptance.ts one more (in prose), none of them ever seen by the guard whose header says 'every inArray(...) over an unbounded id list MUST iterate chunkIds batches'. wave 17 already named this shape: A SCAN'S ROOT IS PART OF ITS CLAIM. RULING: both scans walk `src` (.ts and .tsx), strip line and block comments before extracting call sites (so a DEC citation inside a JSDoc block is never mistaken for a query), keep the per-call-site binding and the reasoned allowlist, and assert a floor on the number of files scanned so the root cannot narrow again. A newly-visible call site that is genuinely unbounded gets chunkIds, not an allowlist entry.

## Amendment (wave 21): every scan allowlist is two-directional — an entry that matches no live hit fails as stale

The wave-14/18 amendments made the chunk scans bind a CALL SITE and root themselves at src, but both allowlist checks assert only that the named FILE exists and was scanned (test/inarray-chunk-scan.test.ts:359-363, test/insert-chunk-scan.test.ts:141) — an entry whose call site was chunked, renamed, or deleted years ago keeps passing, and silently pre-clears any FUTURE call site that reuses that (file, identifier) pair. file-delete-ordering.scan.test.ts already got this right in wave 19 ("every EXEMPT_HITS / KNOWN_BYTES_BEFORE_ROW entry still matches a real hit — no stale lines"), and that direction is what forces a lane that fixes a ledgered site to delete its excuse rather than leave it to rot. Ruling: this is a house rule for every scan test in the repo, not one file's idea. Any scan carrying an allowlist/ledger/exempt list asserts, in both directions, that each entry still matches a live hit; a stale entry fails naming the line to delete.
