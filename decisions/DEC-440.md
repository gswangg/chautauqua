# DEC-440: buildResults keeps its JS aggregation: aggregateSubmission's fail-loudly throws must not be laundered into SQL

The obvious "fix" for the results endpoint is to push AVG/GROUP BY into SQL over json_extract(scores_json). I am ruling that out. aggregateSubmission (src/domain/evaluation.ts:78-124) THROWS on a missing score for a criterion, and aggregateDropdownCriterion throws on a missing, non-string, or out-of-option value -- these are deliberate data-integrity assertions under the house fail-loudly rule, and SQL aggregates silently coerce NULL instead of throwing. A SQL rewrite would convert a loud invariant into a quiet wrong number, and would have to re-derive the DEC-147 round-criteria resolution and DEC-241 dropdown modal tie-break in a second language. So results stays "rank the whole set in JS, then page" -- what changes is the width of the rows that reach JS: scores-only column selection instead of SELECT *, and no whole-event submission_track scan for a caller that never reads trackIds. This is the maximum win available without moving a throwing invariant into a place that cannot throw.
