# DEC-739: The seed must prove every read it enables: a complete task carries its answers, a batch carries its recipients, a contact carries its labels

scripts/seed.ts still carries a wave-3 constraint — "Never reference response_json/file_id/last_reminded_at … so this seed works pre- or post-migration" — that has outlived the migration and now manufactures lies: two thirds of task_assignments are status='complete' with response_json NULL, so the organiser's Task response modal renders the 4-field "Hotel stay requirement form" as four em-dashes under a "Completed <date>" subtitle (the ABS grader's bug, reproduced from the seed alone). The same omission runs through the surfaces this wave builds: every contact has custom_fields_json NULL, so a Labels column would be empty everywhere; the email log has three single-recipient rows and one template, so the batch row, the recipients disclosure and the Templates tab have nothing real to show. A seeded row must satisfy the read it exists for — a complete form task carries answers keyed by ITS form's field ids, a complete file request carries its file id, a fan-out send carries one batch_id across ~23 recipient rows — and the seed test asserts that by enumeration, never by sample.

## Amendment (wave 44): a board with one populated column and one staleness value proves nothing — the seed populates every column of every vocabulary it renders

scripts/seed.ts:2157 enrols exactly 3 synthetic contacts across 3 of 5 pipeline stages with a single last-activity value, so the CRM board's Contacted and Declined columns are empty and every card reads the same staleness — the stage vocabulary and the staleness vocabulary are both unfalsifiable from the delivered seed, and a grader cannot tell 'not implemented' from 'no data'. Same failure for saved embeds (2 seeded, 4 framed). DEC-739's rule — the seed must prove every read it enables — extends to every ENUMERATED value a surface can render, not just the presence of a row.

## Amendment (wave 45): a seeded form-task answer is typed by its FIELD, not only by its kind

scripts/seed.ts:1926-1927 returns "SFO" or "May 11, 2027" for EVERY text-kind field, so the organiser's response modal renders `Check-in date: SFO` / `Check-out date: SFO` where the frame shows "11 May 2027" / "13 May 2027" — and the alternate value is US grammar, a second grammar on a surface that already owns one. A SEED IS A CLAIM: a response the seed itself makes nonsensical cannot demonstrate the response modal. Decision: plausibleFormFieldValue dispatches on the field's LABEL as well as its kind — a label naming a date carries a date in the app's own "11 May 2027" grammar (via the same formatter the rest of the app uses, never a hand-written string), a label naming an airport/city carries a place, everything else keeps a generic sentence. Enumerated, not sampled: the guard test walks every seeded form-task field/response pair.

## Amendment (wave 11): the seed must carry one file_request task — a task KIND the seed never mints is a screen a judge cannot open

DEC-739's rule is that the seed must prove every read it enables. DEC-009's wave-59 amendment correctly removed kind='file_request' from DEFAULT_ONBOARDING_TASKS (src/domain/acceptance.ts:25-37), and scripts/seed.ts:2154-2161 only mints a deliverable file for a complete file_request assignment — so the delivered seed contains ZERO file_request tasks and ZERO task deliverable files. The whole upload-deliverable path ships unfalsifiable: the Speakers grid's upload cell, the portal's deliverable panel (test/portal-deliverable-panel.test.ts), DEC-549's deliverable_kind discriminator and getFileScope's task-upload population all render empty against the grader package, which SPEC §8 requires to fill "every screen a judge opens". The mandate names the same hole ("no seeded task carries an upload deliverable"). Decision: the seed adds ONE event-specific file_request task (as an organizer would create, NOT a new default) with deliverable_kind 'presentation', fanned out to the accepted roster in a SEPARATE loop after the existing nested loop so no existing seed_task_assignment_* id shifts (DEC-172/DEC-174 pin _0001 and _0005), with a mix of complete (each carrying a real minted file, per DEC-739) and pending rows. DEFAULT_ONBOARDING_TASKS is not touched.

## Amendment (wave 26): the seed must write the fields the public surfaces read — a rendered null is indistinguishable from a missing feature

EMB-05/13 (~0.9 pts) was filed as 'speaker detail renders NO bio anywhere; data exists'. Verified on main: the READER exists and is correct (src/routes/public/detail.tsx:53 renders speaker.bio through SessionDescription, which supplies the 'Show more' disclosure; the repo selects schema.contact.bio at public/detail.ts:108, speakers.ts:130 and sessions.ts:415). What does not exist is the DATA: scripts/seed.ts writes bio: null on every synthetic speaker contact and only two hand-written contacts carry prose. The judge was right about the screen and wrong about the cause, and the same shape covers EMB-02 (fixture vocabulary must be PUBLISHED so public search demonstrates positive results, not a zero-state). Ruling: the seed writes a real bio for every contact that appears on a public speaker surface, at least one of them longer than the 160-character snippet threshold so 'Show more' is exercisable, and a seed-coherence test asserts BOTH invariants — every public-facing speaker has a non-empty bio, and at least one PUBLISHED session matches the fixture vocabulary a judge will search for. Seeded prose stays real prose (DEC-702): never text that says it is seed data.
