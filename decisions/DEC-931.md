# DEC-931: A refused delete names the rows that refuse it, and finds every one of them in ONE query

deleteTrack (src/server/repo/events.ts:357) and deleteRoom (:498) both throw a 409 whose message names a CLASS and nothing an organizer can act on -- "Track is referenced by one or more submissions", "Room is referenced by one or more schedule slots" -- leaving the only recovery path a manual hunt through the whole event. deleteTrack additionally runs listReviewerRowsForPlan once PER PLAN (lines 385-390): an N-scan on a delete guard. DEC-886 made "an irreversible action is a page that names what goes AND what it refuses" the house grammar for deletes; a refusal that names nothing is the same failure from the other side. Rule: each refusal carries an ApiError `fields` map keyed by the blocking relation -- `submissions` | `form` | `plans` | `reviewers` for a track, `slots` for a room -- and each value NAMES up to five blocking rows by their human handle: a submission as "REF - Title", a schedule slot as "REF - Title (Tue 12, 10:00, Room 2A)" formatted through src/lib/event-time.ts against the OWNING EVENT's timezone, a plan or reviewer by its own name. When the true count exceeds five the value ends "... and N more", where N comes from a COUNT, never from an unbounded fetch: every blocker read is bounded (limit 5 + count) and set-based, and the reviewer-scope check becomes ONE query joining plan_reviewer to evaluation_plan on eventId instead of a query per plan. The refusal stays a refusal -- neither delete ever cascades, DEC-229/DEC-519 unchanged -- and Settings renders those field values as a list under the failing row instead of a bare sentence.
