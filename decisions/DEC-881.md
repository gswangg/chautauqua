# DEC-881: "Re-uploaded" counts re-uploads: the worklist's status cell and the header's number read ONE predicate

ContentApp.tsx's header prints the mock's "5 need a decision · 2 re-uploaded" but computes the second figure as a bounded aggregate filtered on contentStatus=changes_requested — that is the count of sessions AWAITING a re-upload, the exact opposite of what the label claims, and no worklist row can ever display the frame's status vocabulary at all (the cell renders Pending/Approved/Changes requested). docs/design "Chautauqua Content.dc.html" rows read "Re-uploaded" and "Not reviewed", and its header arithmetic is 5 = 2 re-uploaded + 3 not reviewed. Define the predicate once: a submission is RE-UPLOADED when its latest deliverable file's version_no > 1 (a replacement landed). The row's status cell resolves in a fixed precedence — approved -> "Approved"; re-uploaded -> "Re-uploaded"; changes_requested -> "Changes requested"; otherwise "Not reviewed" — and the header's count is that same predicate as a server-side list filter, so the printed number and the rows it summarizes cannot disagree. The default worklist tab becomes "Needs a decision" per the mock, with an honest empty state that links to All; this narrows DEC-665, whose "all" default existed only to avoid landing on a "0 submissions" screen.
