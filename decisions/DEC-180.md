# DEC-180: Login rate limiter counts only failed attempts; success resets the per-email window

src/routes/auth.tsx:116-127 increments both the per-email (20/15min) and per-IP budgets on EVERY POST /login including correct-password logins, so shared demo credentials self-lock during judging and 20 junk posts lock any named account. Keep DEC-072's two-scope keying but change semantics: peek (read-only) both budgets before verification and 429 if either is exhausted; increment both scopes only after a FAILED credential check; on success, delete the current per-email window key so accumulated failures from a shared account clear. Requires three pure helpers in src/lib/rate-limit.ts (peekScopedLimit, incrementScopedLimit, resetScopedLimit) alongside the existing checkAndIncrementScopedLimit, which claim/submit scopes keep unchanged. Residual risk accepted and documented: sustained junk-posting can still hold a 15-minute window shut — inherent to per-account limiting; removing it entirely would gut online-guessing protection.

## Amendment (wave 22): failures-only rate limiting covers every password-verifying endpoint, not only the anonymous ones

DEC-072/DEC-180 established peek-then-increment-on-failure limiting keyed by identity, and it is applied at /login (src/routes/auth.tsx:326-333, 358-365, 381), /claim/:token (:463) and the public submit/draft paths (src/routes/public/submit.tsx:213, 348, 500). POST /account/password (src/routes/account.tsx:156-177) has none: every request runs a 100,000-iteration PBKDF2 verify (src/auth/password.ts:117-126) against the caller's own current password, unmetered. That is both an unbounded CPU sink on an authenticated route and a current-password guessing oracle for anyone holding a borrowed session — SPEC §6 says "Rate limits on auth" without an authenticated-route exemption. Ruling: the password-change POST takes a per-user budget in the DEC-180 shape — peek before the verify (429 with the SAME RATE_LIMIT_ERROR copy /login and /claim already render), increment only when the current password is wrong, reset on success — under scope "password-change" keyed by auth.userId. The window/max/copy constants stay ONE definition (exported from src/routes/auth.tsx, never re-typed), because a duplicated limit constant is a limit that drifts.

## Amendment (wave 29): admission is ATOMIC and a failures-only budget is a REFUND, never a peek — peekScopedLimit is deleted

DEC-180's peek-then-increment-on-failure shape is still live at three call sites and wave 27 PROPAGATED it into a fourth: src/routes/auth.tsx:551/556 (login-user, login-ip), :748 (forgot, whose own comment names it "the SAME peek-then-conditionally-mutate shape as /login") and src/routes/account.tsx:183 (password-change). DEC-948's module header (src/server/repo/rate-limit.ts:1-14) exists precisely to forbid read-then-write limiting: N concurrent requests all read the same pre-increment count, all pass, and all reach a 100k-iteration PBKDF2 — so the advertised 20/15min per-email cap does not bound a parallel attack at all, and no serial unit test can see it. The two decisions are reconcilable and the reconciliation is one shape: CONSUME THEN REFUND. Every password-verifying route calls checkAndIncrementScopedLimit BEFORE the verify (one atomic insert-on-conflict-returning statement decides ok/deny off the RETURNED count); a SUCCESSFUL outcome then gives the budget back — the per-identity bucket via the existing resetScopedLimit, the per-IP bucket via a new atomic refundScopedLimit (a single `update ... set count = count - 1 where key = ? and count > 0`, never a read-then-write). Failures-only steady state survives; concurrency is bounded by the first statement. Two corollaries a worker must not re-decide: (1) if the per-identity bucket admits but the per-IP bucket denies, the identity bucket is REFUNDED before the 429 — a request that never reached verification must not spend the account's budget; (2) POST /forgot CONSUMES ALWAYS AND NEVER REFUNDS, because refunding on "the address exists" (or on "it does not") makes bucket depletion an account-enumeration oracle, which DEC-004 closes everywhere else. peekScopedLimit and incrementScopedLimit have no remaining caller after the migration and are DELETED (house rule: no compatibility shims), and a source scan keeps src/routes/** from naming them again.

## Amendment (wave 36): POST /forgot spends a per-IP bucket BEFORE the per-email bucket, and neither is ever refunded

Verified at the file: src/routes/auth-reset.tsx:76 keys its only rate-limit bucket on the normalised EMAIL, while src/routes/auth-login.tsx spends both `login-user` (per-email) and `login-ip` (per-IP, max 100). An attacker spraying one address per request never touches the same email bucket twice, so a single IP can mint unlimited reset tokens and fire unlimited reset mail — the exact vector `login-ip` exists to close. auth-reset.tsx even imports `requestIpFromHeaders` (:21) and never uses it, so the intent was there and the call never landed; test/route-authz-enumeration.scan.test.ts:449 already ledgers POST /forgot as protected by "per-email+per-IP rate limiting (DEC-180)" — a claim that is currently false. Ordering: the IP bucket is spent FIRST, so a denial there never touches the email budget and NO refund is ever needed. This deliberately differs from login (identity-first + refund on IP denial) because DEC-180's wave-29 corollary (2) forbids /forgot from ever refunding — a refund whose existence depends on any branch is an enumeration oracle. Spending IP-first is existence-independent, keeps both branches indistinguishable, and is strictly kinder to a legitimate user behind a hostile NAT.

## Amendment (wave 52): the anonymous mutating-door budget population is ENUMERATED from the real mount list, never hand-listed

test/security-invariants.test.ts:193-238 asserts the DEC-628 'unauthenticated write paths are rate limited' invariant against exactly FOUR hand-typed route literals: POST /login, POST /claim/:token, POST /submit/:eventSlug, POST /submit/:eventSlug/save-draft. src/routes/auth-reset.tsx registers two more anonymous POST doors (/forgot, /reset/:token) that the list never mentions — they happen to call checkAndIncrementScopedLimit today, so the omission is currently silent, which is precisely the failure mode DEC-550 already diagnosed for the anonymous GET manifest ('three public-by-design entries were wrong and nothing failed'). A universal needs a population (house rule): the population here is derivable — test/helpers/registered-routes.ts already yields every registration with method, resolved path, file and line, and test/anonymous-route-probe.test.ts already demonstrates composing the real mount list from src/index.ts's own source. Ruling: the budget assertion is rebuilt as an enumeration over that derived population, with a ledgered EXEMPT list carrying a written reason per entry, and any door found unbudgeted is FIXED (consume-then-refund per this decision), never exempted.

## Amendment (wave 73): a duplicated string-literal vocabulary is a SCANNED, RATCHETED population — hand-finding one per wave is not closing the class

Waves 60, 68, 69, 70 and 71 each closed exactly ONE duplicated vocabulary by hand (Sessionboard target fields, submission sort order, UnplacedReason, TaskKind, ConflictKind), and this wave found three more sitting in plain sight (invite status in six places, the four form-field vocabularies, content status in four). A hand-listed population is not a population: the remedy is a scan over the SHAPE, not another wave of grepping. RULING: a test enumerates every string-literal vocabulary declared in src/ and app/src — `export type X = 'a' | 'b' | …` unions and `export const X … = ['a','b',…]` arrays — normalises each to its sorted member set, and groups declarations by that set. A group of two or more declarations in different files is a duplicate unless the extra declaration is a re-export (`export type { X } from` / `export { X } from`) or carries a DEC-NNN citation within the six lines above it (the stated-exception form, e.g. speakerDetail.ts:55-60's DEC-930 leaf note). Sets of fewer than three members are out of scope — two-member sets are dominated by asc/desc and pending/complete pairs and would drown the signal. The assertion is a RATCHET on the number of duplicate groups, seeded at the count measured on the implementing branch and documented as only ever decreasing; the failure message prints every group with file:line so the next wave can shrink it. A ratchet, not a zero-assertion, because three in-flight branches are already shrinking this population and a hard zero would fail on a branch through no fault of its own.

## Amendment (wave 75): a duplicate vocabulary inside ONE file is still a duplicate, and a ratchet seeded before its siblings landed is a licence to regress

Two things verified at my own runtime. First, `test/vocabulary-duplication-ratchet.scan.test.ts:263-267` sets `MAX_DUPLICATE_VOCABULARIES = 4` and its own header (`:13-19`) admits the number was measured on a worktree cut BEFORE `task-w73-a/-b/-c` removed three duplicate groups — all three have since landed (reflog lines 2686-2688). A ratchet that is three above the truth does not ratchet; it licenses three new duplicated vocabularies to land silently, which is exactly the class DEC-789 found by hand in w73. Second, the scan deliberately excludes same-file groups (`:247-250`, "two declarations of the same set in the SAME file are a different bug class"), and that exclusion is currently hiding a live pair: `src/domain/acceptance.ts:155` `SCHEDULING_PARTICIPANT_STATUSES = ['none','invited','accepted']` and `:164` `PORTAL_VISIBLE_INVITE_STATUSES = ['none','accepted','invited']` are the identical member set under two names, and the doc comment on the first names only `ACTIVE_INVITE_STATUSES` as the thing it is "deliberately distinct from" — it never mentions its actual twin. Adjacent, and the reason this matters beyond tidiness: `src/server/repo/public/gates.ts:36-42` hand-inlines `['none','accepted']` into the SQL public-visibility gate while `acceptance.ts:132-136` declares `ACTIVE_INVITE_STATUSES` and its own comment concedes the SQL gate "carr[ies] the identical two literals" — so a change to the declared constant would silently NOT reach the gate that decides who is publicly visible. RULING: (a) the SQL gate composes the declared constant, never a second literal pair; (b) two constants with an identical member set must either be one declaration (re-exported under the second name) or each carry a DEC citation naming the OTHER and stating what would make them diverge — a comment that names the wrong sibling is not a citation; (c) the ratchet scan counts same-file groups under the same exemption rules as cross-file ones, and `MAX_DUPLICATE_VOCABULARIES` is lowered to the count measured after this lane's own fixes.

## Amendment (wave 79): a ratchet's ceiling is a measurement, and slack in it is a licence — the vocabulary ratchet is spent, not carried

`test/vocabulary-duplication-ratchet.scan.test.ts` has now twice recorded, in its own header, that a ceiling above the truth "doesn't ratchet, it licenses new duplicates to land silently": seeded at 4 against a pre-w73 worktree, re-seeded at 5 in wave 75 with the closing sentence "The next wave's job is to shrink this ratchet, not to raise it." Three waves have since passed (76, 77, 78) and the five groups are still there — the ratchet has been carried as a number instead of spent as a mandate, which is precisely the failure mode the wave-75 note named. Ruling: a wave that leaves a named ratchet slack has licensed the next duplicate; wave 79 collapses the measured groups (starting with the two same-file ones the header names, `submission-sort.ts` and `worklist.ts`) and re-seeds the ceiling AT the count measured at that task's own runtime, with the measurement and its runtime written into the note. The collapse idiom is the one `src/domain/acceptance.ts:162-171` already demonstrates: one declaration, re-exported under the second name when two names genuinely serve two readers.
