# DEC-926: Deleting a file version never leaves a task_assignment pointing at a hole: repoint to the surviving neighbour, else REOPEN the task

deleteFileVersion (src/server/repo/files-versions.ts) carefully repoints previous_file_id across the gap and re-homes the deleted row's file_comment thread onto the surviving neighbour -- and never touches task_assignment.file_id, the third pointer at that row. DELETE /api/v1/files/:fileId (src/routes/files.ts) is reachable by an organizer for ANY version and by the uploading speaker for the chain head, so the deliverable that completed a file_request task is deletable today. Afterwards the portal's task page and its download route call resolveTaskFileChainLatest, which THROWS 'file <id> not found -- data corruption' on a missing row: the speaker's own task page 500s permanently, while the organizer's roster cell (DEC-920's fileName join) goes blank with the status still reading 'complete'. An orphan is only cheap until a resolver treats it as corruption. Rule: inside the SAME survivingId branch deleteFileVersion already computes, update task_assignment set-based where file_id = the deleted id -- to {fileId: survivingId} when a neighbour survives (the successor that takes the vacated slot, else the predecessor), and to {status:'pending', completedAt:null, completedBy:null, fileId:null} when the whole chain is gone (DEC-921's reopen grammar: the task stays, its answer goes). The assignment row is NEVER deleted: a join row keyed on (task, contact) is not owned by the file that completed it.
