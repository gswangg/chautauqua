# DEC-656: A speaker-added co-presenter is RECORDED, not PUBLISHED: portal-created participants land visible=false and reach the public site only through the organizer's existing visibility toggle (amends DEC-604)

src/server/repo/portal-edit.ts:456 writes visible:true with inviteStatus:'none', which satisfies visibleParticipantConditions() outright (src/server/repo/public/gates.ts:36-42); since canEditSubmission stays true forever for status==='accepted', any speaker on an accepted+approved session can POST /portal/submissions/:id/participants and put an arbitrary name and email onto /e/<slug>/speakers instantly. The organizer's own invite path deliberately writes invite_status='invited' so it is NOT publicly visible -- the asymmetry is the defect: an organizer adding a speaker passes through a gate, a speaker adding a speaker does not. visible=false is chosen over invite_status='invited' because the organizer already has a working, tested control for exactly this (the Visible checkbox on the submission-detail participants table) and no dead end is created; an 'invited' state has no organizer-side transition to 'accepted'. The portal says so honestly rather than implying instant publication.
