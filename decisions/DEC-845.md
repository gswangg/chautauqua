# DEC-845: A queue headed by a plan carries the plan's facts on its own wire, including the reviewer's own score

The v5 pack (docs/design/README.md 'Review — the queue is scoped to a plan') requires the reviewer queue to head itself 'Review · <plan>' over a count, with '<scope> · closes in N days' beneath, rows reading SCORED 4.5 / NOT SCORED, and the scorecard's back link naming the plan. VERIFIED absent: app/src/pages/review/ReviewerQueue.tsx:173 renders the bare plan name as h1 with no count, no scope, no progress; rows show 'N ratings so far' (everyone else's work) with a 'Complete' pill; Scorecard.tsx:165 says '← Back to your queue'. The missing facts are per-reviewer and cannot be re-derived client-side: the reviewer's OWN blended score, and the track their plan_reviewer row scopes them to. Decision: GET /api/v1/review/plans/:id/queue's envelope gains planName: string, scopeTrackName: string | null (the caller's own plan_reviewer scope; null = all tracks) and closeDate: number | null, and each item gains myScore: number | null computed by the SAME weighted blend already in src/domain/evaluation.ts (never a second formula, per the weighted-score decision the results table and the scorecard already share). alreadyRatedByMe stays as the boolean; myScore is what the row PRINTS. One wire shape, so the queue heading, the row state and the scorecard eyebrow cannot disagree with each other or with the results table.

## Amendment (wave 38): a queue envelope's counts are computed over the WHOLE queue before the slice, and the client never derives a count from the page it loaded

app/src/pages/review/ReviewerQueue.tsx:75 fetches /review/plans/:id/queue with no page/perPage, so listPerPage clamps to MAX_PER_PAGE=200 and src/routes/review/reviewer.ts:232 slices; the component then derives every count from res.items (:138, :312, :378, :380), discards the envelope's truthful `total`, and renders no pager. At SPEC 2.2's stated 500-5,000 submissions/event a track-scoped reviewer cannot reach rows 201+ and is told a false 'N left to score' — contradicting J4's 'coverage closes'. Ruling: the envelope carries `total` plus a new `unscoredTotal`, both computed from the full materialized array BEFORE the slice; the SPA renders 'N left to score', the progress denominator, 'Showing X of N' and 'Show all N' exclusively from those; 'Show all' actually pages the remainder in; and the multi-plan landing row asks for perPage=1 instead of downloading 200 rows per plan to count them.

## Amendment (wave 40): the queue-envelope ruling binds EVERY reader of the endpoint, and "next" means the next UNSCORED item — its absence is the done state

DEC-845's wave-38 amendment ruled that the reviewer queue's counts come from the envelope's `total`/`unscoredTotal`, computed before the slice, and that no client derives a count from the page it loaded. It was applied to the component that prompted it (app/src/pages/review/ReviewerQueue.tsx:88 requests perPage=MAX_PER_PAGE and reads res.total/res.unscoredTotal) and to nothing else. The sibling reader drifted: app/src/pages/review/Scorecard.tsx:157 fetches `/review/plans/:id/queue` with no perPage and computes the scorecard header counter with queueDoneCounts(res.items) (app/src/pages/review/progress.ts:48-53 — completed = items.filter(alreadyRatedByMe).length, total = items.length), so past listPerPage's 200-row cap the reviewer's own progress is a page count while the queue page beside it prints the true one. The same file carries a second, size-independent defect: submitAndAdvance (Scorecard.tsx:177-183) advances to `queue.items[0]`, but the server deliberately KEEPS already-rated rows in the queue (src/routes/review/reviewer.ts:205 filter is `item.alreadyRatedByMe || needsMoreRatings(...)`, sorted rated-last by buildReviewerQueue, src/domain/evaluation.ts:445-460) — so once the reviewer scores the last unscored item, items[0] is a card they already scored and "Submit and next" re-opens it instead of returning to the plan. J4's "opens a link, sees exactly their queue, rates fast, done" has no done. RULING: every reader of the queue envelope (queue page, scorecard counter, any future surface) reads counts exclusively from the envelope's `total`/`unscoredTotal` and requests an explicit perPage; queueDoneCounts takes the ENVELOPE, not an item array; and "next" is the first item with alreadyRatedByMe === false other than the current submission — when unscoredTotal is 0 (or no such item exists) the reviewer lands on the plan, never on a scored card.

## Amendment (findings wave 6): a reviewer's scope is a LIST of tracks, and the label names every one of them

src/domain/evaluation/progress.ts:37-44 folds a reviewer's plan_reviewer rows to a single trackId and returns null whenever the count is anything but exactly one — so a reviewer covering two tracks resolves identically to a reviewer covering all of them, and both consumers (src/routes/review/reviewer.ts:97-100, src/routes/review/plans-progress.ts:97-127) put that null on the wire as scopeTrackName/trackName, which the SPA renders as 'All tracks'. The queue query itself restricts correctly, so the product tells the reviewer and the coverage dashboard the exact opposite of what it enforces, for the case docs/clarifications.md:18 specifies by name ("reviewers review one or more tracks"). Ruling: the resolver returns string[] ([] means genuinely unrestricted — no rows, or any row with trackId and submissionId both null), and ONE shared pure formatter turns names into the label: null for [], otherwise every name sorted ascending and joined with ' · '. No truncation and no "N tracks" summary — MAX_REVIEWER_SCOPE_ROWS already bounds the list, and abbreviating would restate the same lie in miniature. The label, not the id, is what both routes need, so both call the one formatter; a hand-copied join in either place is the drift this DEC exists to prevent. The wire field keeps its name, so the SPA's `?? 'All tracks'` fallback becomes correct with no app/src change — which also keeps this task off task-w5-a's file.
