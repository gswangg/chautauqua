# DEC-542: Cloning a session is a set-based copy: one chunked multi-row INSERT per child table, never one statement per copied row

cloneSubmission (src/server/repo/submissions/create.ts:168-225) is the last unchunked per-row insert loop in the product: it issues one INSERT per submission_track row, one per submission_answer row, and one per participant row, sequentially. Every sibling write path was converted away from this shape and named its bound -- DEC-521/DEC-528 for task_assignment, DEC-492 for the auto-schedule slot burst, DEC-491 for the import statement budget -- and chunkRowsForInsert already exists in src/lib/chunk.ts as the single home for the rule (derive columns-per-row from the rows, chunk by bound parameters, never by row count). J3 names cloning as the producer's path for invited talks, so a cloned 25-answer session with three speakers costs ~31 serial D1 statements for what is three statements of work. Decision: all three loops become `for (const chunk of chunkRowsForInsert(rows)) await db.insert(table).values(chunk)`, preserving exactly today's semantics -- the participant loop keeps its `inviteStatus !== 'none' && !== 'accepted'` skip and keeps forcing inviteStatus 'none' on the copies, and every copied row keeps a fresh newId(). Empty child sets stay a no-op (zero statements), which is the observable difference a test can pin. Deliberately NOT added, so it is not re-raised as a miss: a named MAX_CLONE_* cap. Unlike bulk accept or import, a clone's fan-out is bounded by ONE submission's own child rows, which the CFP form's field count and the participant editor already bound; a second cap would be a number with no failure mode behind it.
