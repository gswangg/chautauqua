# DEC-120: Task-assign contact org-scoping: POST /api/v1/tasks/:id/assign rejects contactIds outside the caller's org (400 invalid, atomic, chunked batch check)

src/routes/tasks.ts:229 passes client-supplied contactIds straight to assignTask's blind insert with no ownership check, violating SPEC §6 'object-level ownership checks on every fetch-by-id (no IDOR)': an organizer can attach another org's contacts to a task, leaking their PII into the onboarding grid and targeting them with reminders. Fix at the route boundary, before any insert (DEC-019 atomicity): dedupe the requested ids, batch-load them via a new repo helper findContactsForOrg(db, ids, orgId) in src/server/repo/contacts.ts (chunked via chunkIds per DEC-078/104), and if any requested id is missing from the result throw ApiError('invalid', ..., { contactIds: 'unknown ids: <list>' }) — no partial assignment ever occurs. assignTask itself stays unchanged; scoping is the route's job, matching the existing pattern at src/routes/api/submissions.ts:152.

## Amendment (wave 68): a refusal never prints a ULID — name the row the way the producer sees it, or state the count and the way out

Four id-rejection refusals interpolate raw ULIDs into a fields-map value the SPA renders verbatim: src/routes/tasks.ts:426 and :443, src/routes/comms/compose-core.ts:53, src/routes/comms/portal-invites.ts:42. Two are reachable from an ordinary stale selection (a submission deleted or a participant removed while the compose/invite modal is open), and the buyers are event producers who are "not technical at all". Where the rows resolve, name them — tasks.ts:443 already holds the contacts' names in `orgContacts`, so the roster refusal can say "Ada Lovelace, Grace Hopper are not on this event's roster"; submissions name ref + title through the existing formatRef. Where the id genuinely resolves to nothing (deleted/cross-org), the honest refusal is a count plus the way out — "2 of the sessions you selected are no longer in this event — reload the list and try again" — never the id. Names come from the existing single-source label helpers, never a fresh `${firstName} ${lastName}`.
