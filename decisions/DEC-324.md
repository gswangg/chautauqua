# DEC-324: DEC-297's no-cacheable-non-200 rule moves to the public sub-app's own onError: setCacheHeaders has already run by the time anything throws, so every public ApiError and every unexpected 500 currently ships max-age=60

My own finding, verified: src/routes/public/index.tsx:55-58 publicNotFound sets Cache-Control: no-store by hand precisely because setCacheHeaders(c) already stamped 'public, max-age=60, stale-while-revalidate=300' earlier in the handler — but that hand-fix covers only the explicit 404s. Every THROWN error escapes it. registerErrorHandler (src/server/http.ts:85-94) returns c.json(...) on the same Hono context, which re-applies the context's prepared headers, so `/e/:slug/schedule.ics?ids=<over MAX_ITINERARY_IDS>` (index.tsx:189-191) answers 400 with a 60-second public cache directive, and any unexpected exception in a public handler answers a publicly-cacheable 500. A stale error cached at a browser or proxy for a minute after the underlying data changed is exactly the harm DEC-297 exists to prevent. Fix at the boundary, not per handler: publicRoutes registers its own onError that sets Cache-Control: no-store and then returns the SAME envelope the global handler returns (reusing ApiError/errorEnvelope from src/server/http.ts — no second error shape, DEC-013 stays canonical), keeping console.error for non-ApiError. Hono's app.route() composition applies a sub-app's own errorHandler to its routes, so this is a single registration with no change to src/index.ts and no change for any other sub-app. Enforcing it at the sub-app boundary rather than sprinkling c.header() calls is what makes the invariant survive the next handler someone adds.
