# DEC-357: Bulk roster-add is set-based: one chunked contact load plus exactly ONE updateSubmissionStatuses call for every created submission; createSubmission stays per-row because seq is allocated by a SQL subquery

the former src/routes/api/contacts.ts:399-406 (now split across src/routes/api/contacts/) loops over every imported contact issuing repo.findContactForOrg (a row the import pass just wrote and already proved org-owned) and repo.pushContactToEvent, and src/server/repo/contacts/push.ts:48-52 makes each of those a createSubmission plus its OWN updateSubmissionStatuses call for a single id — which means a full acceptance-planning pass per contact. Importing 800 speakers onto an event is on the order of 15 statements per contact. Rule: add pushContactsToEvent(db, eventId, orgId, contacts, title?) that creates each submission with the existing per-row createSubmission — deliberately NOT batched, because src/server/repo/submit.ts:225 allocates seq via submissionSeqSubquery and a multi-row INSERT would evaluate that subquery against the pre-statement table state and collide — then calls updateSubmissionStatuses ONCE with every created id, returning ids in input order. The import route replaces its loop with one chunked findContactsForOrg over result.contactIds (keeping the existing loud throw if any id is not org-owned) plus one pushContactsToEvent for the not-already-on-roster subset; addedToEvent and the response shape are unchanged. The two single-contact callers (create-contact at :153, add-to-event at :327) keep pushContactToEvent. This composes with DEC-355 but does not depend on it: the array-taking signature of updateSubmissionStatuses is already public.
