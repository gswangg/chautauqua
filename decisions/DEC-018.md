# DEC-018: Review API contract, criteria kinds, reviewer UX, and /api/v1/me

J4 has a producer side and a reviewer side built by two parallel tasks, so the wire contract is fixed here. Criteria (evaluation_plan.criteria_json): [{ id, label, kind: 'rating'|'dropdown', weight?, options? }] — 'rating' requires weight>0 and numeric scores within scale_json {min,max}; 'dropdown' requires options: string[] and stores the chosen string; free text is evaluation.comment. Aggregation (computeWeightedScore/aggregateSubmission from src/domain/evaluation.ts) consumes rating criteria only. Producer endpoints (requireOrganizer + csrfJson): GET/POST /api/v1/events/:eventId/plans; GET/PATCH/DELETE /api/v1/plans/:id; POST/DELETE /api/v1/plans/:id/reviewers { userId, trackId?, submissionId? } (DEC-017 scope semantics); GET /api/v1/plans/:id/progress -> per-reviewer { userId, email, assigned, completed }; GET /api/v1/plans/:id/results -> { submissionId, ref, title, count, average, perCriterion } sorted by buildResultsRows, ?format=csv streams CSV via toCsv; POST /api/v1/plans/:id/remind sends a nudge via the DEC-006 mailer to reviewers with incomplete queues. Progress and results are organizer-only — reviewers never see aggregates. Reviewer endpoints under /api/v1/review/* accept role 'reviewer' OR 'organizer' via an inline check (requireReviewer's semantics are NOT widened): GET /api/v1/review/plans; GET /api/v1/review/plans/:id/queue — ordered by buildReviewerQueue (fewest-ratings-first), capped by needsMoreRatings, gated by plan open/close dates, and when plan.anonymized the server strips speaker names and speaker-section answers (anonymizeForReviewer; never client-side); GET /api/v1/review/submissions/:id?planId= (404 outside the reviewer's assignment); PUT /api/v1/review/plans/:planId/evaluations/:submissionId { scores, comment } upserts (unique per plan+submission+reviewer+round), validates against criteria/scale, 'conflict' when the plan is closed or the cap is reached. Bootstrap: GET /api/v1/me -> { userId, email, role, orgId, contactId? } (401 unauthenticated) so the SPA can role-gate; reviewers see only the Review nav section and land on /review.

## Amendment (wave 54): anonymised means the reviewer payload carries no speaker identity STRING, not merely no `speakers` key — the anonymiser redacts name/company/email out of every free-text field it forwards, and the payload says it is anonymised

Verified on main: anonymizeForReviewer (src/domain/evaluation.ts:618-622) returns `{...sub, speakers: undefined, speakerAnswers: undefined}` — a strip list of exactly two KEY NAMES. Its one call site (src/routes/review/reviewer.ts:311) ships `sessionAnswers` (:302), `title` and `description` verbatim, and app/src/pages/forms/FieldModal.tsx:44 defaults every NEW custom question to `section: 'session'`. So the first producer who adds "Link to a past talk", "Your GitHub" or "Company website" de-anonymises the whole plan server-side, which SPEC §Security ("Server-side filtering for all public and anonymized data") and J4 ("anonymization is server-side") promise it cannot. Stripping all session answers is the wrong cure — format/audience/notes are the framed FORM ANSWERS block and a session-shape fact is not identity (DEC-857/DEC-986 already rule that). RULING: anonymity is a property of the TEXT, so the anonymiser takes the submission's own identity strings and masks them wherever text crosses to a reviewer. One pure-core helper `redactIdentity(value, identities)` masks each occurrence with `[hidden]`, case-insensitive, literal (regex metacharacters escaped — a company may be "C++ Corp"), longest-identity-first so "Jane Smith Consulting" masks before "Jane Smith". The identity set is exactly ruling A10's promise — each speaker's FULL name, email address and company — never a bare first or last name, because a lone "Will" or "May" would eat ordinary prose. It applies to sessionAnswers values (strings and string arrays), title and description; non-string values pass through untouched. The anonymised branch also sets `anonymized: true` on the payload, because a reader cannot distinguish "no speakers" from "speakers withheld", and the scorecard is required to SAY which it is. Known and accepted residue, recorded rather than hidden: an identity-bearing link that contains no identity string (github.com/jsm) still passes — the authoring-side consequence line in DEC-505's amendment is the other half of this rule.

## Amendment (wave 57): anonymisation is a property of the PLAN, not of one route — the reviewer QUEUE redacts submission titles with the same identity list the detail route uses

src/routes/review/reviewer.ts:319 runs anonymizeForReviewer over title/description/sessionAnswers for GET /api/v1/review/submissions/:id, but the sibling GET /api/v1/review/plans/:id/queue ships `title: summary.title` verbatim at line 221 — and the recused list does the same at line 191 — for the very same anonymised plan. A title like "Priya Sharma on Raman spectroscopy" therefore de-anonymises the whole queue before a reviewer ever opens a scorecard, defeating SPEC §6's "server-side filtering for all public and anonymized data" and the wave-54 amendment's own promise that an anonymised plan "carries no speaker identity STRING anywhere in the payload". The queue must mask titles through the same redactIdentity primitive, built from the same name/email/company triple, loaded in ONE batched query rather than per row. Broader-not-narrower: the redaction identity set includes every participant regardless of invite status — a declined co-presenter's name in a title is still identity.

## Amendment (findings wave 10): the evaluation plan's open/close window gates reviewer READS and recusal writes, not only the queue and the score PUT

isPlanOpen is enforced on the queue (src/routes/review/reviewer.ts:126-128) and on the score PUT (:356-358), but NOT on GET /api/v1/review/submissions/:id (:267-343) and NOT in reviewerCanAccessSubmissionFile (src/server/repo/files-authz.ts:185-206), and not on the recusal POST/DELETE (src/routes/review/recusals.ts:19,50). An assigned reviewer can therefore read in-scope submissions — speaker names and all, on a non-anonymised plan — and download their deliverables BEFORE the plan opens and indefinitely after it closes, by holding or guessing a submission id the queue refuses to list. A window that only the list obeys is not a window. RULING: for auth.role !== 'organizer', a plan outside its window refuses the detail read, the file read, and both recusal writes, with the score PUT's exact existing vocabulary — ApiError('conflict', 'This review plan is not currently open') — so the four routes speak with one voice. Organizers are exempt: they own the plan and already read submissions through the admin routes; this is a reviewer-access window, not a data freeze. The queue's existing role-blind isPlanOpen check is deliberately LEFT AS IS this wave (changing it is a separate question about organiser preview and would move behaviour tests nobody filed against). reviewerCanAccessSubmissionFile gains a trailing `now: number = Date.now()` parameter so the clock is pinnable in tests; no call site changes.

## Amendment (wave 62): reviewer-anonymisation masking is anchored at Unicode word boundaries and ignores identity tokens under 3 characters

src/domain/evaluation.ts:653 builds `new RegExp(cleaned.map(escapeRegExp).join("|"), "gi")` from [speaker.name, speaker.email, speaker.company] (src/routes/review/reviewer.ts:339 and :175-178) with the only filter being `id.length > 0` (line 646). There is no boundary anchoring and no minimum-token floor, so a company literally named "AI", "IT" or "X" — or a one-character surname — masks those letters INSIDE ordinary words: "detail" becomes "det[hidden]l", "said" becomes "s[hidden]d", across title, description and every sessionAnswers[].value the reviewer is asked to score. The module's own doc-comment at line 338 already reasons about over-masking ("never a bare first or last name — that would mask ordinary words too aggressively") and then ships the aggressive case anyway. No fixture catches it because every seeded name and company is multi-word. THE RULE: (1) each escaped identity is wrapped `(?<![\p{L}\p{N}])…(?![\p{L}\p{N}])` and the pattern gains the `u` flag, so "Ekström", "C++ Corp" and an email still match while "IBM" no longer matches inside "IBMX"; (2) identities whose trimmed length is under MIN_REDACTABLE_IDENTITY_LENGTH = 3 are dropped before the alternation is built — a one- or two-character company cannot identify a speaker but can shred the text a reviewer must read; (3) longest-first ordering and the metacharacter escape are unchanged (escapeRegExp's class already escapes `]` and `}`, which the `u` flag makes mandatory). Anonymisation stays server-side and stays a superset of the dedicated-field strip; this narrows only WHERE a match may start and end.

## Amendment (wave 58): the plan-window gate exempts organizers on the QUEUE too, and the envelope says who is looking

Verified on main: `src/routes/review/reviewer.ts:333` gates the per-submission read with `auth.role !== "organizer" && !isPlanOpen(...)` and its comment at :328-332 asserts 'Organizers are exempt (same as the queue)' — but :154 applies `!isPlanOpen(...)` to EVERY role and returns an empty envelope. A producer opening a closed plan sees zero rows while the detail route behind those rows still loads. The route's own comment describes behaviour the route does not have. Ruling: :154 takes the identical role predicate (`auth` is already in scope at :86). The envelope's `open` flag stays TRUTHFUL — `Review.tsx:628-632` filters `openEnvelopes` on it and `ReviewerQueue.tsx:410` paints the plan-row pill from it, so flipping it would break two readers to fix one. Instead the envelope gains `viewerIsOrganizer: boolean` set server-side from `auth.role === "organizer"`, and the SPA changes voice rather than inferring the viewer from the presence of rows (a closed plan with zero submissions would fool that inference): `ReviewerQueue.tsx:177`'s reviewer dead end renders only when the viewer is not an organiser, and an organiser gets the list under a note naming what they are seeing.

## Amendment (wave 82): the STORED criterion-kind vocabulary is frozen; the DISPLAYED type names are Scale / Choice / Text, declared once

The V12 intake names the two types Scale 1-5 and Choice; the repo has shipped `'rating' | 'dropdown' | 'text'` since DEC-018/DEC-148 through `criteria_json`, `round_criteria_json`, every validator, the CSV export and the seed. The ruling itself says existing plans are untouched and nothing needs migrating — so the wire and the column keep `rating`/`dropdown`/`text` and only the words an organiser reads change. To avoid a second vocabulary with a delay fuse (DEC-613 lineage), the display names live in exactly ONE exported map in `app/src/pages/review/` and every surface that prints a type name reads it. Today only the plan editor's new-criterion segmented control (`PlanEditor.tsx:1856-1885`) prints one; the scorecard and results print criterion LABELS, never kinds, and must not start.
