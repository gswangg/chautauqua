# DEC-354: plan_reviewer scope ids are validated against the plan's event at write time, AND isSubmissionInReviewerScope's per-submission branch gets the event guard every other branch already has — both, not either

Two halves of one hole. (a) src/routes/review/plans.ts:183-187 writes body.trackId / body.submissionId into plan_reviewer as arbitrary strings after validating only userId (repo.requireOrgUser at :182). A stale or foreign id yields a reviewer whose queue is silently empty while /progress reports them assigned — a producer-visible wrong answer with no error anywhere. DEC-120's precedent at src/routes/tasks.ts:270-280 already rejects cross-org contact ids on the sibling surface, so this is inconsistency, not a new policy. (b) src/server/repo/review/submissions.ts:157-158 returns true for a per-submission assignment with no `submission.eventId === plan.eventId` check, while the unrestricted branch (:140-145) and the track branch (:166-177) both perform it. It is masked today only because src/routes/review/reviewer.ts:126 and :158 happen to call getSubmissionSummaryInEvent, and because DEC-170's file path derives the plan from the file's own event — a latent cross-event authz hole one refactor away from live, and DEC-170 makes this function load-bearing for file downloads. Rule: the write path rejects a trackId that is not a track of plan.eventId and a submissionId that is not a submission of plan.eventId, with ApiError('invalid') naming the field; and the repo predicate confirms event membership on the per-submission branch with the same bounded single-row query the unrestricted branch uses. plan.filters.trackIds is deliberately NOT applied to the per-submission branch — a per-submission assignment stays explicit per DEC-017. Defense in depth: neither half substitutes for the other.


## Amendment (wave 61): a narrower reviewer scope laid over a broader one is an ADVISORY, never a silent supersede and never a refusal

Assigning a reviewer 'One submission' on a plan where they already hold a track-wide (or plan-wide) row changes nothing about their effective queue — plan_reviewer rows are a UNION — but the organiser doing it plainly believes they are narrowing something. Today the POST returns 201 and says nothing, so the organiser walks away with a wrong model of who sees what. The two tempting fixes are both wrong: refusing would block a legitimate additive assignment, and silently deleting the broader row would destroy an assignment the organiser never asked to remove. Ruling: the write succeeds unchanged, and the 201 envelope carries `scopeAdvisory: string` when the new row is strictly narrower than one the same user already holds on the same plan (a submissionId row under an all-scope or covering-track row; a track row under an all-scope row). The sentence names the broader row and states that the effective queue is the union, not the narrower scope. The SPA renders it as a quiet advisory beside the reviewer list — not an error banner, since nothing failed.
