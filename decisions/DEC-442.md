# DEC-442: A public GET joins the edge cache exactly when its URL carries no per-user parameter: bare schedule.ics is cacheable, ?ids= is not

DEC-083 excluded every /schedule.ics request from publicCacheMiddleware because "per-user ?ids= query strings would pollute the cache" -- correct for the itinerary case, wrong for the bare case. src/routes/public/index.tsx:197-228 and :234-248 do provably identical work when ?ids= is absent (both call getPublicAgenda then agendaIcsEvents through the same mapper), yet the perf lane measured agenda.ics at 3.7-11.1ms and bare schedule.ics at 80-216ms across the same four runs. That is not a code-path divergence needing an A/B, as the previous lane guessed -- it is one route being served from caches.default and the other recomputing the whole agenda on every request. The predicate therefore moves from path-shaped to request-shaped: skip the cache only when the request URL actually has an `ids` search param. A bare schedule.ics mints exactly one cache key per public version, the same as agenda.ics, and stays subject to the same purge-on-write version bump; anything carrying ids stays excluded so key cardinality remains bounded (the same concern DEC-433 answers for ?page=).
