# DEC-887: Six Settings frame elements are unrepresentable because the seed never writes them — so the seed writes them

The Settings frames render saved embeds with names and recipes, API tokens with prefixes and last-used dates, room capacities (900/220/220/60), one public surface that is NOT published, people with display names, and reviewers scoped per track. The seed writes none of it — scripts/seed.ts:380 sets every room capacity to null, and the `embed` and `api_token` tables get no rows at all — so six panels render their empty states forever and no fidelity probe can ever pass them. Standing rule: the seed satisfies every read. Values come from the design frames, never invented. Two hard constraints: an api_token row stores only its sha256 hash plus the 12-char display prefix (a seeded working token would be a checked-in credential — stage-1 must run with no secrets present, and must not manufacture one), and the seed stays idempotent so a re-run never doubles the rows.


## Amendment (wave 40)

**The delivered seed's CFP window straddles now — a dark front door costs more than a not-yet-published row**

Verified on main: scripts/seed.ts:417 sets the default CFP form's open_date to SEED_NOW + 1 day, so /submit/<slug> reads "Submissions aren't open yet" for every judge who opens the demo on delivery day, while Settings simultaneously shows "Closes 31 Aug · IN 19 DAYS" with a live Open link — three surfaces disagreeing about one window, and the product's single most-graded public state (the OPEN call for papers, frames 10--11) unreachable. DEC-887's original reason for the future open_date was to give PublicPagesPanel exactly one row that is not live. That demo is worth far less than a working front door. RULING: the delivered seed's default form opens in the past (SEED_NOW - 12 days) and closes in the future (SEED_NOW + 18 days), and the 'not live' state is demonstrated instead by a DISABLED saved embed — a surface that is genuinely switchable, which the CFP window never was. The same seed lane adds the two saved-embed rows the frame draws (four, one off) and one real re-upload chain, because a header that counts '1 re-uploaded' with zero such rows is the same class of lie.

## Amendment (wave 66): a layout case needs data to exist — the seeded programme must contain concurrency, or the v7 agenda's auto-fit row is undemoable

DEC-887's own sentence is 'elements are unrepresentable because the seed never writes them — so the seed writes them', which is exactly this defect one surface over. Verified on main: `scripts/seed.ts:2096` places `acceptedSubmissions.slice(0, 5)` — five slots total, and the only two sharing a start window are the DELIBERATE same-room clash on day 1, which public surfaces never render as concurrency (clashes are an organiser concept). docs/design/README.md's 'Public agenda — desktop' specifies `repeat(auto-fit, minmax(228px, 1fr))` with named cases (1 session = full 712, 2 split, 3 at ~228, 4 wrap 2x2) and a rail of per-room counts; wave 64-b is building that grid against a seed on which every row is the 1-up case. eval-findings' SEED note says the same thing ('frames depict 18 published sessions across 3 days with breaks and 4 saved picks; current seed publishes 7 on 2 days'). RULING: the defect is CONCURRENCY, not headcount — the design README itself scopes the surface at '<=10 sessions a day over 1-4 rooms' and warns the frame numbers are illustrative. So the seed places every publishable accepted session and arranges deliberate concurrency (a 3-up start time, a 2-up start time, a solo), keeps the existing clash, the TBD (null-room) slot and a non-zero unplaced count, and keeps placements clear of the seeded breaks. Growing the accepted set wholesale is explicitly OUT: it ripples into onboarding, roster, overview, comms and review counts across hundreds of tests for no additional layout case. At most ONE extra pending submission may be promoted if a 4-up row needs it.
