# DEC-958: A dialog field is a FormRow, and the scan bans the retired class by name — not merely a missing one

DEC-950 (in flight) converts NewContactModal and adds a scan that 'fails any module importing ModalFrame that contains a <label> with no className'. That scan cannot see the second offender. app/src/pages/forms/FieldModal.tsx — a ModalFrame consumer — builds twelve fields as <label className="chq-field">Text<control/></label>, and every one of those labels HAS a className, so the proposed scan passes it and the claim that 'the sixth dialog cannot regress' is not yet true. .chq-field is the retired pre-DEC-685 layout class (app/src/styles.css:1010) and it survives in exactly one dialog. Rule: FieldModal's fields become FormRows (each control gets a stable id and the row a matching htmlFor; the Required row keeps .chq-checkbox-label, which is the checkbox grammar, not the retired field grammar; the conditional-rule fieldset keeps its <fieldset>/<legend> but its inner labels become FormRows), and the scan test bans the TOKEN — no module importing ModalFrame may carry the exact class token `chq-field`. Token-exact, so `chq-field-error` (still legitimate outside dialogs, and still present in NewContactModal until its own branch lands) does not trip it and the two waves cannot collide. Panels are explicitly out of scope: FormSettings.tsx and CallForPapersPanel.tsx keep .chq-field, because a settings panel is a read/edit surface with its own row grammar (DEC-896's three-column definition grid), not a dialog.


## Amendment (wave 28): a dialog field carries its invalid state on the ROW (data-invalid), and the scan bans improvised error markup, not merely a missing class

FormRow (app/src/components/ModalFrame.tsx:61) already owns label/help/error for every modal form, but it renders the message in .chq-form-row-error and marks nothing as invalid, so every dialog in the product refuses input with weight-free grey text and no aria-invalid. FormRow cannot put a class on its arbitrary children, so the invalid state is expressed as data-invalid="true" on the .chq-form-row wrapper and the ink treatment is written once, in error-states.css, under a selector list that includes both .chq-field-invalid and .chq-form-row[data-invalid='true'] .chq-form-row-control > .chq-input/.chq-select/.chq-textarea. One declaration block, two ways in — never two blocks. Rationale for the scan: DEC-958's own lesson was that a scan must ban the retired shape by name; here the retired shapes are a bare .chq-error box used for a FIELD refusal and any per-surface border/typography invented for invalidity.

## Amendment (wave 58): a joined string of field-error VALUES is not an error summary — every multi-field admin refusal renders through ErrorSummary with in-place marking

The V9 error standard (summarize at top, anchor each problem to its field, fix in place, say what was kept) has exactly two implementations on main: app/src/pages/settings/EventSettingsPanel.tsx and app/src/pages/review/PlanEditor.tsx, both through app/src/components/ErrorSummary.tsx. app/src/pages/speakers/RosterPanel.tsx:128 — the Add-speaker modal, five fields, four of them required, and an eval-measured trouble spot — does `Object.values(err.fields).join(' · ')` and renders the result as one bare .chq-error line. It is the only site in app/src with that shape: it parses the envelope's field map, throws away every KEY, and prints values like 'Required · Invalid email' with nothing marking which control is wrong and nothing to click. That is the same failure w57-e fixed in the portal (a server talking to itself in front of the user), one level worse because the map that would name the fields was already in hand. RULING: an admin form that can receive a fields map renders it through ErrorSummary + countHeading, with one anchor per problem pointing at that field's own id, `chq-field-invalid` + aria-invalid + an inline message on the field itself, and the 'nothing was lost' survival line — the form's own values are never cleared on a refusal. The conflict (duplicate-email) path keeps its existing DuplicateEmailNotice forward path unchanged; this is about VALIDATION refusals.

## Amendment (wave 61): the last two refusal surfaces that parse the server's fields map and throw it away

DEC-958 (RosterPanel) and DEC-856/DEC-013 established that a handler which reaches an ApiError keeps the WHOLE err.fields map keyed by the server's own wire keys and marks each named field. Five panels now do this; two do not. app/src/pages/settings/PortalSettingsPanel.tsx:141 collapses the refusal to `err.message` even though the panel already owns a `formErrors` state (populated only by its client-side validatePortalSettingsForm) and the server names every bad field individually (src/routes/api/portal-config.ts:97-127: logoUrl / accentColor / welcomeMessage / showResources) — so a server-rejected portal save renders one unstyled sentence with no field marked, the exact CLASS 5 shape the error standard was written against. app/src/pages/speakers/TaskModal.tsx:134 does the same to src/routes/tasks.ts:209-240's map (kind / title / description / dueDate / required / formId). A handler that names one key of a fields map has parsed the envelope and discarded it; a handler that names none has done worse.

## Amendment (wave 64): three more refusal readers that parse the server's fields map and print a message that names nothing — the review plan editor's three assignment paths, and the submissions area's two writers

Verified at the file on main. src/routes/review/plans-reviewers.ts emits SIX distinct refusals from POST /plans/:id/reviewers — userId (:68), submissionIds (:87, :96), trackId (:121), submissionId (:132, :144), plus parseBoundedIdArray's own submissionIds shape — and EVERY ONE carries the identical top-level message "Invalid reviewer assignment". app/src/pages/review/PlanEditor.tsx reads exactly one key per call site (:920 `err.fields?.submissionId ?? err.message`, :965 `err.fields?.submissionIds ?? err.message`) and the track-scope path (:936) reads none at all, so the most-used "Assign all N in track" refusal renders four words that name nothing. The same shape exists twice more in the submissions area: app/src/pages/submissions/NewSubmissionModal.tsx:88-89 and app/src/pages/submissions/SubmissionDetailPage.tsx (twelve catch handlers, all `err.message`) against src/routes/api/submissions.ts, whose email refusal is literally `ApiError("invalid", "Validation failed", { "contact.email": "must be a valid email address" })` — the message is a placeholder and 100% of the information is in the map that gets discarded. This extends the wave-58/61 rule (keep the WHOLE map keyed by the server's own wire keys, mark each named control, render an unmatched key labelled by its key rather than dropping it) to the three surfaces the earlier enumerations missed.

## Amendment (wave 64): the review plan editor's three reviewer-assignment paths now walk the WHOLE fields map (task w64-a)

Landed: app/src/pages/review/PlanEditor.tsx adds `reviewerAssignProblems(err: ApiError)`, a single helper that walks every key of `err.fields` (not one named key per call site) and maps each known key to the control that owns it — `userId` -> the reviewer select (`#plan-reviewer-select`), `trackId` -> the track select (`#plan-reviewer-track-select`, shared by the 'track' and 'submission' scope branches since only one is ever mounted), `submissionId` -> the single-submission select (`#plan-reviewer-submission-select`), `submissionIds` -> the choose-submissions checklist (`#plan-reviewer-choose-submissions`). All three call sites (`assignReviewer`, `confirmAssignAllInTrack`, `confirmAssignChosen`) now route any fields-bearing ApiError through this helper into a new `reviewerAssignErrors` state, rendered via the existing ErrorSummary + countHeading import at the top of the reviewer-assignment panel; a fields-less ApiError still falls back to the pre-existing `error`/err.message banner exactly as before. The operator's typed reviewer/track/submission selection is never cleared on a refusal (no catch block resets it). Test: app/src/pages/review/planEditor-refusal-shapes.test.ts (added to vitest.config.ts's environmentMatchGlobs since it renders via React.createElement without a .tsx extension, mirroring compose-refusal-shapes.test.ts's plain-.ts naming). The submissions-area half of this amendment (NewSubmissionModal.tsx / SubmissionDetailPage.tsx) is NOT part of this task and remains open.
TAKEN for the submissions area's two write paths (task w64-e), scoped to those two handlers only: NewSubmissionModal now keeps the whole err.fields map in state and marks each named control (title/description/trackIds/format/"contact.email") through FormRow's data-invalid + inline message + aria-invalid, rendered through the same ErrorSummary + countHeading anchor list wave 58/61 already gave RosterPanel/EventSettingsPanel/PlanEditor; an unmatched key still renders in the summary, labelled by its own raw wire key plus the server's message (there is no control to anchor it to).
