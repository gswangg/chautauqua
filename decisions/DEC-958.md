# DEC-958: A dialog field is a FormRow, and the scan bans the retired class by name — not merely a missing one

DEC-950 (in flight) converts NewContactModal and adds a scan that 'fails any module importing ModalFrame that contains a <label> with no className'. That scan cannot see the second offender. app/src/pages/forms/FieldModal.tsx — a ModalFrame consumer — builds twelve fields as <label className="chq-field">Text<control/></label>, and every one of those labels HAS a className, so the proposed scan passes it and the claim that 'the sixth dialog cannot regress' is not yet true. .chq-field is the retired pre-DEC-685 layout class (app/src/styles.css:1010) and it survives in exactly one dialog. Rule: FieldModal's fields become FormRows (each control gets a stable id and the row a matching htmlFor; the Required row keeps .chq-checkbox-label, which is the checkbox grammar, not the retired field grammar; the conditional-rule fieldset keeps its <fieldset>/<legend> but its inner labels become FormRows), and the scan test bans the TOKEN — no module importing ModalFrame may carry the exact class token `chq-field`. Token-exact, so `chq-field-error` (still legitimate outside dialogs, and still present in NewContactModal until its own branch lands) does not trip it and the two waves cannot collide. Panels are explicitly out of scope: FormSettings.tsx and CallForPapersPanel.tsx keep .chq-field, because a settings panel is a read/edit surface with its own row grammar (DEC-896's three-column definition grid), not a dialog.
