# DEC-557: A schedule conflict is rendered by its kind, in the names a producer knows — one describeConflict, never raw ids

findConflicts (src/domain/schedule.ts:102-119) builds a prose `detail` out of internal identifiers: `Room "room_x9f2" double-booked on 2026-03-04 between submissions sub_abc and sub_def`, and `Speaker(s) contact_9k2 double-booked ...`. app/src/pages/agenda/ConflictChip.tsx:19-24 puts that string straight into the hover title and then labels EVERY conflict "Two sessions in one room" regardless of kind — so a speaker_overlap (the same person booked into two rooms at once, which SPEC J9 names explicitly alongside room overlap) is reported to the producer as a room clash that isn't happening, with an id-soup tooltip underneath. Meanwhile src/server/repo/overview.ts:184-211 renders the SAME conflicts correctly on the Overview worklist: buildConflictRows resolves roomName, ref, title and speakerName from maps it already has. Two surfaces render one fact and one of them is wrong — the standing rule. J9's entire promise is that conflicts are SURFACED (never blocking), clarifications.md says screens that don't work are out of the spirit of the competition, and SPEC §2.1 makes legibility a requirement rather than polish. The labels cost nothing: getAgendaPayload already loads roomRows (id→name) and every accepted session with its speakers' names. Decision: (a) `Conflict` stops carrying prose and starts carrying facts — `{ kind, submissionIds, day, roomId: string|null, speakerContactIds: string[] }`; findConflicts stays pure, id-based, and keeps its DEC-533 emission order byte-identical. (b) ONE pure `describeConflict(conflict, labels)` in src/domain/schedule.ts is the single place a conflict becomes words, taking `{ roomNameById, titleBySubmissionId, speakerNameByContactId }`; the agenda repo applies it from data it already loaded (getConflictsAndSummary adds one bounded per-event room-name query, ~15 rows) and ships `Conflict & { detail: string }`. (c) ConflictChip's caption is chosen by `kind` — room overlap and speaker overlap read differently — and the hover detail is describeConflict's output, containing no id. (d) src/server/repo/overview.ts is NOT edited by this decision: it reads only `kind` and `submissionIds`, both unchanged, and it already does the right thing. (e) the regression bar is the words: a describeConflict unit test asserting no conflict string contains a submission/room/contact id when labels resolve, plus a render test that a speaker_overlap does not say "one room".

## Amendment (wave 48): the agenda's merged clash card reads its KIND from the server's Conflict[]; client geometry may choose LAYOUT, never KIND, and a room-less overlap is not a room conflict

`DayGrid.tsx:422` captions every merged clash card with a hardcoded `conflictKindLabel('room_overlap', n)` computed from the client's own `computeOverlapClusters` pass, which buckets by `roomKey(roomId)` and therefore treats the room-less TBD column as if it were a room. `src/domain/schedule.ts:319` emits `room_overlap` only when BOTH `roomId`s are non-null, so two unroomed overlapping sessions render an inverted card saying "Two sessions in one room" while the page's own conflict counter (built from the server's `Conflict[]`) says zero — one fact stated twice by two readers, disagreeing. Separately, cluster members are excluded from `lanedPlaced` (:146) and render without `ConflictChip`, so a `speaker_overlap` touching a clustered session is invisible entirely. Ruling: there is one reader of conflict KIND — the caption for a merged clash card is derived from the union of server `Conflict`s whose `submissionIds` intersect the cluster's session ids (using `describeConflict`/`conflictKindLabel` per DEC-557's existing kind vocabulary), and an empty intersection means the card renders no conflict caption at all. Client-side clustering (`computeOverlapClusters`) remains legitimate for choosing visual LAYOUT (how many lanes, how cards stack) but never for choosing which KIND label to print.

## Amendment (wave 71): a conflict carries a LIST of participants, not a pair tuple, and every renderer gets the third caption

`break_overlap` has exactly one session, so `Conflict.submissionIds` widens from `[string, string]` to `string[]` (documented: exactly 2 for room/speaker, exactly 1 for break) and gains explicit `breakId`/`breakLabel` fields that every constructor sets (null on the pair kinds), matching how `roomId`/`speakerContactIds` are already set explicitly rather than left optional. Widening is deliberately type-loud: the two places that index `submissionIds[1]` (`src/server/repo/overview.ts:442-443` and `describeConflict`) must narrow rather than silently read undefined. `describeConflict` stays the ONE server-side renderer and gains a break branch; `conflictKindLabel` in `app/src/pages/agenda/ConflictChip.tsx` stays the ONE SPA vocabulary (Overview.tsx already imports it) and gains "Scheduled over a break". Caption precedence is pinned: room+speaker > room > speaker > break; the hover title always lists every detail line. Today `captionForConflicts` returns null for a break-only set, which would render the inverted conflict card with no words — that is the bug the precedence rule closes.

## Amendment (wave 69): the SERVER emits break_overlap — a break is a conflict participant, not a session

The wave-71 amendment above is BINDING and its SPA half is fully built (`app/src/pages/agenda/types.ts:38-46` declares the third kind plus breakId/breakLabel, `ConflictChip.tsx:21-66` carries the caption and the room>speaker>break precedence, `PhoneAgenda.tsx:53` filters on it, `ConflictChip.render.test.tsx:58,87` mocks it). The server half never landed: `grep -rn 'breakId' src/` returns NOTHING, `src/domain/schedule.ts:47-53` still declares `kind: "room_overlap"|"speaker_overlap"` with `submissionIds: [string,string]`, and `describeConflict` has no break branch. So a producer who drags a session on top of lunch is never warned, while auto-schedule refuses to place there (`agenda/auto-schedule.ts:57,115` reads `listBreaksForEvent` as `blocked`) — the two halves of the same product disagree, and the SPA's break tests are a contract with themselves (DEC-663). Ruling: (a) `Conflict` becomes `{ kind: "room_overlap"|"speaker_overlap"|"break_overlap"; submissionIds: string[]; day; roomId: string|null; speakerContactIds: string[]; breakId: string|null; breakLabel: string|null }` — exactly 2 ids for the pair kinds, exactly 1 for break_overlap, breakId/breakLabel explicitly null on the pair kinds. (b) `findConflicts(placed, blocks: ScheduleBlock[] = [])` gains an OPTIONAL second parameter defaulting to `[]`, so every existing caller and `test/schedule-conflicts-equivalence.test.ts` stay byte-identical, and break conflicts are APPENDED after all pair conflicts so DEC-533's emission order is preserved. (c) A break blocks EVERY room: a break_overlap fires for any session whose day matches and whose [startMin,endMin) half-open interval overlaps the break, regardless of room, including the room-less TBD column; the conflict's `roomId` is the SESSION's room. (d) The overlap predicate is the one already inside findConflicts, never a second copy. (e) `summary.conflicts` counts break overlaps — one number, one population. (f) DEC-010 is untouched: conflicts warn, never block, so PUT .../slot onto a break still returns 200 with the clash in the refreshed payload. (g) The overview worklist renders break rows too (single session + breakLabel, never "X and undefined"), rather than filtering them, so the two surfaces cannot report different clash populations.
