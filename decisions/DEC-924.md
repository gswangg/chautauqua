# DEC-924: Assigning one reviewer to a chosen SET of talks is one request, all-or-nothing

app/src/pages/review/PlanEditor.tsx:606-625 implements the 'Choose submissions' confirm as N POSTs to /plans/:id/reviewers in Promise.all batches. That violates the product's set-based bulk rule, and it makes the DEC-572 confirm gate a lie: a rejection on request 7 of 20 leaves seven rows written, one generic error banner, and no statement of what did or did not happen -- 'nothing is saved until you confirm' cannot survive a partial write. Rule: POST /api/v1/plans/:id/reviewers additionally accepts submissionIds: string[] (bounded and deduped like every other id array, DEC-182); refs and internal ids resolve in ONE batched query, the plan-filter check is ONE batched query, and the rows insert set-based through a new addReviewers(db, planId, inputs[]). Validation is all-or-nothing: any unknown id, or any id outside the plan's own filters_json trackIds, refuses the WHOLE request naming the offending refs in fields.submissionIds and writes nothing. The array form answers 201 {items, total}; the existing single-submissionId form is unchanged so the DEC-623 ref-resolution path and its tests keep their contract.

## Amendment (wave 47): plan_reviewer has ONE write path — the singular addReviewer is deleted, not documented

DEC-924 shipped addReviewers (set-based, chunkRowsForInsert, one select-back) in wave ~40, and src/routes/review/plans-reviewers.ts:61 adopted it. But src/routes/review/plans-distribute.ts:221-223 — the LARGEST plan_reviewer fan-out in the product (the frame's own example is "36 reviews needed at 2 each") — still loops `await repo.addReviewer(...)` per created pair, and addReviewer issues INSERT + SELECT, so one Distribute click pays ~2N sequential D1 round trips against SPEC §7's writes-p95-<100ms budget. This is w46's own lesson verbatim (A CONVENIENCE WRAPPER INVITES THE FOURTH SERIAL LOOP): the singular stayed callable, so the next author called it. The only other caller (plans-reviewers.ts:110) is a genuine single-row POST and can express itself as addReviewers(db, planId, [input])[0]. Therefore: addReviewer is DELETED from src/server/repo/review/reviewers.ts and from the repo barrel; addReviewers is the only way a plan_reviewer row is written. A route that needs one row asks for a set of one.
