# DEC-588: Settings gains 'Call for papers' and 'People and roles', built strictly on endpoints that already exist

The design specifies seven sections; the app ships seven, but two of the designed ones are missing and two present ones are not in the design's set. The missing pair are the two a producer actually opens Settings to find: when the CFP opens and closes and where its public link is, and who else can sign in. Both are already fully served — GET /api/v1/events/:eventId/forms and PATCH /api/v1/forms/:formId cover the window, intro text and offered tracks; GET/POST /api/v1/users and POST /api/v1/users/:id/reset-password cover the roster, invitation and reset. So this is a rendering gap, not a feature gap, and the sections must add ZERO endpoints: a section that needs a new API is out of scope this wave and must be declared rather than invented. Placement in the rail is fixed and named so two waves cannot argue about it: Event, Call for papers, Portal, Tracks and rooms, Resources, People and roles, API tokens, Exports, Embeds. Reveal-once semantics for a generated password match the API-token panel's existing treatment — shown once, never re-fetchable.
