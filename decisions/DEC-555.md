# DEC-555: The itinerary picker MERGES localStorage with the checkboxes actually rendered; a day-filtered or row-capped render can never delete a pick

ItineraryScript (src/routes/public/agenda.tsx:146-176) persists `currentIds()` — the checked subset of `document.querySelectorAll('.chq-itinerary-toggle')`, i.e. only the checkboxes ON THE PAGE — with `localStorage.setItem(key, JSON.stringify(ids))`. It therefore treats the rendered set as the whole world. It is not: DEC-489 gave agenda/schedule a `?day=` knob (EMBED_KNOBS_BY_SURFACE lists day for both surfaces) that dispatch.tsx applies before rendering, so `/e/:slug/schedule?day=<d2>` renders only day 2 — and the first checkbox the attendee touches there overwrites the store, silently destroying every day-1 pick. The .ics link is rebuilt from the same truncated list, so the download loses them too. The in-flight DEC-548 makes this strictly worse by adding MAX_PUBLIC_ROWS to the agenda scan: any session past the cap becomes an unrendered id whose stored pick evaporates on the next toggle. SPEC J10 promises "personal picker, persists on reload" and the page itself tells the visitor "Your picks are saved in this browser and survive a reload"; EMB-10/EMB-11 grade exactly that.

Decision: (a) a new pure `mergeItinerarySelection(stored, renderedIds, checkedIds): string[]` in src/lib/itinerary.ts is the single definition of the rule — ids in `stored` that no rendered checkbox represents are PRESERVED in order, ids that are rendered survive only if checked, the result is deduped and capped at the existing MAX_ITINERARY_IDS (so the store can never grow past what GET schedule.ics will accept). (b) There is exactly ONE implementation: the inline script embeds the compiled function via `var __chqMerge = (${mergeItinerarySelection.toString()});` — a parenthesized function EXPRESSION, aliased to a stable local name so a minified declaration name cannot desync from the call site — rather than a hand-written JS twin (the standing "two implementations of one invariant means one is wrong" rule). (c) `stored` is re-read from localStorage at change time, not captured at load, so a second tab's writes are merged rather than clobbered, and the .ics `?ids=` is built from the merged set so a day-filtered view still exports the whole itinerary. (d) The regression bar is the pure function (day-2 toggle preserves day-1 picks; unchecking a rendered id removes it; dedupe; MAX_ITINERARY_IDS cap) plus an assertion that the rendered script embeds that function's own source.


## Amendment (wave 1)

Frame 10--12 (new in pack v7) draws /schedule as the 1180 pair listing the SAVED sessions with Remove, a "4 saved · 2 overlaps" subtitle, a TAKE IT WITH YOU rail (saved count + Download .ics) and an overlaps block — not the current all-sessions list with Save controls, a duplicate day-pill row, a "Show only my picks" checkbox and a highlight control (none of which appear in the frame). The load-bearing constraint is DEC-555 itself: picks live in `chq_itinerary_<slug>` in localStorage, so the server cannot know them. Ruling: the server keeps rendering the day's rows (the merge rule that stops a filtered render deleting a pick is unchanged); the SAVED/not-saved partition, the counts, the overlap markers and the empty state are all driven by the existing ItineraryScript over the rendered rows — one store, one script, no second itinerary source and no server round-trip.
