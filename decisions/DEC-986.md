# DEC-986: The public CFP picks ONE track; the many-to-many model, the wire shape and the multi-select edit surfaces stay, and the seed keeps exactly two multi-track sessions

DEC-951 refused the v5 frames' radio redraw of the public track control, reasoning that radios would silently truncate a submission already holding several tracks the next time its owner edited it. The user's dated decision (docs/eval-findings.md, 2026-08-13) resolves that objection rather than overruling it: single-select radios on the public form, the many-to-many model kept underneath, and the seed reduced so no demo row is unexpressible on the surface that created it. The truncation risk was never the create form's — a new submission has no prior tracks — it was the EDIT form's, and the edit form is /portal/submissions/:id/edit, which keeps its checkbox group. docs/clarifications.md:16 ("talks are submitted to one or more tracks") stays true of the product: a talk can hold several, composed where compositions are made (the portal edit form and admin), and the submission_track join, the `trackIds` array wire shape and every server validation are untouched — a radio simply posts one value into the same array. DEC-696's parity between the submit and edit fieldsets is about the chq-cfp-option chrome, not the input type, so the shared classes stay and only the caption differs by surface; /portal/edit's leftover "Tracks *" legend drops its asterisk, finishing the DEC-917/DEC-951 optionality grammar that stopped one file short. The Session-format dropdown takes the same frame treatment (radio cards) scoped to that one field id; no other dropdown field changes.

## Amendment (wave 45): the public CFP asks for ONE name, and the two locked fields stay the storage contract

submit-views.tsx:263-273 carries the only live deferral left in src/ — "First/last name stay two LOCKED fields (deferred name-collapse)" — while frame 10--11 draws a single NAME control. A DEFERRAL IS A DATED PROMISE; it is now due. Decision: the ANONYMOUS CFP (/submit/:slug) renders exactly one required control labelled "Name"; the route splits the submitted value on its LAST run of whitespace into the locked first_name/last_name answers BEFORE validateAnswers runs, so a single-token name stores the whole string as first_name and leaves last_name empty. The derived last_name is exempt from the required check — a form must never fail on a field it does not show. Nothing changes in the schema, the seeded form definition, the admin builder, the portal edit form or the organiser surfaces: those keep two fields, because the frames only respecify the public CFP. Error copy is "Enter your name". Same lane fixes the identity note, which currently says "Submitting this form creates your speaker portal account" — the design README's copy rule is explicit that it is *set a password on an emailed claim link*, never "create an account" (there is no public signup route), and DEC-814 means an existing contact is not created at all, so the sentence is false for that submitter.

Verified on main: src/routes/public/submit-views.tsx renders a bordered header card inside the reading column whose h1 IS form.title, with the track fieldset trailing the whole session section, audience level drawn as a caret-less <select>, a one-line abstract textarea, an untyped email input, and no rule between the last track row and the YOU section. The v6 frames draw a full-bleed page header (date·venue eyebrow / event wordmark / 'Call for papers · closes …'), a separate H1 'Submit a talk', TRACK and FORMAT paired 2-up right under the abstract, audience level as a three-pill segment, and a real section break before YOU. Chrome is always full bleed; only content is constrained. RULING: adopt that anatomy, reusing the excludeIds mechanism DEC-986 already established for the format field to pull audience level out of the generic renderer; the single-choice error copy becomes 'Select a track', never 'at least one'. DEFERRED WITH A REASON (a deferral is a dated promise): the frames' single NAME field stays two fields this wave — first_name/last_name are LOCKED built-ins (DEC-008) with server-side validation and a CRM identity behind them, so collapsing them is a domain change, not a layout change, and it does not belong in a lane whose subject is the page's chrome.

## Amendment (wave 14) — the phone CFP is ONE form stepped by one attribute, engaged only by script and never over an errored render

The phone frame (docs/design/Chautauqua Public and Portal.dc.html:969-1017) is a two-step wizard: 'Step 1 of 2 · your talk' over a progress bar, body scrolls, footer carries 'Next: about you' + 'Draft'; step 2 is 'about you' and submits. The rendered page already has exactly those two boundaries — the two <section>s labelled 'Your talk' and 'You' in src/routes/public/submit-views.tsx:467/519 — so the wizard is a phone-width presentation of one unchanged form, never a second POST shape, a ?step= route, or a split submission. Ruling: the form carries data-chq-cfp-step, server-rendered as 'all'; an inline progressive-enhancement script sets it to '1' on load, and only then do the phone-only step chrome and Next/Back controls (all display:none at top level, switched on inside cfp.css.ts's existing 700px block per DEC-385) become visible. With JS off, the phone keeps today's whole-form page — a degradation, never a wall. Next does not validate: DEC-008 keeps the server the only validator, and because an errored re-render must not hide the field that failed, the script refuses to engage when the rendered form contains any error node. Desktop pixels are untouched, which is the mobile round's standing rule.
