# DEC-682: {feedback} is a merge var only when feedback is actually attached, and attached feedback is scoped to the composing plan and round

Two verified defects in one call chain. (1) src/routes/comms/compose-core.ts passes [] when includeFeedback is false, and src/domain/compose.ts:97-105 unconditionally sets feedback: formatFeedback([]) = NO_FEEDBACK_TEXT — so a decision template containing {feedback} sent with the toggle OFF mails every recipient "No reviewer feedback was recorded." instead of failing preflight. A merge var the organizer did not populate must be ABSENT so renderTemplate raises MergeFieldError and preflightRender rejects the batch with the field named (DEC-019's atomic preflight); a polite sentence in place of missing data is the silent-death trap the DEC-5xx thread exists to kill. (2) src/server/repo/comms.ts:235-256 filters only on submissionId + submittedAt non-null and the caller passes no plan or round, so a decision email attaches every submitted comment from every plan and every earlier round, renumbered as one anonymous "Reviewer 1..N" list. Every other evaluation reader is round-scoped by construction — src/server/repo/review/evaluations.ts:32-35 states DEC-087's rule that round is a REQUIRED param at every call site — and comms is the one exception. Feedback therefore travels with an explicit scope {planId, round} chosen by the organizer (the seed carries three plans), defaulting to the plan's currentRound, and the unused singular listFeedbackComments is deleted rather than left as a second unscoped door.

## Amendment (wave 44): the walkthrough exercises the feedback-attachment path against an evaluation plan the producer module creates itself

DEC-682 made `includeFeedback: true` require a `feedbackPlanId` naming exactly which plan+round's comments to attach (src/routes/comms/compose-core.ts:57-84). scripts/walkthrough/producer.ts:755-760 still POSTs `{templateId, submissionIds, includeFeedback: true}` and asserts 200, so `npm run walkthrough` — a REQUIRED CI job (.github/workflows/ci.yml:75-104) — is red on main. The walkthrough's module order is producer -> review -> speaker -> public -> data (scripts/walkthrough.ts:5), so by the time J5 runs no plan exists on the producer module's own J1-created event; borrowing review.ts's plan would couple two modules that are spawned as independent processes. Ruling: runJ5 creates its own minimal plan on its own eventId (same body shape as scripts/walkthrough/review.ts:335-350) and passes that id, letting feedbackRound default to plan.currentRound. J5 then pins DEC-682 rather than contradicting it, and stays runnable standalone.
