# DEC-032: Settings page becomes a thin panel container; every feature adds its own file under app/src/pages/settings/

Three parties add Settings UI this cycle (w4-e tokens/exports, w4-h event/tracks/rooms/portal/resources, in-flight w3-i embeds), and a monolithic Settings.tsx would be a three-way merge knot. Settings.tsx becomes a container that imports and stacks self-contained panel components from app/src/pages/settings/<Name>Panel.tsx, each owning its own data fetching via app/src/lib/api.ts and rendering a titled <section>. Wave-4 panels: EventSettingsPanel, TracksRoomsPanel, PortalSettingsPanel, ResourcesPanel (task w4-h); ApiTokensPanel, ExportsPanel (task w4-e). Each task adds only its panel files plus its import/JSX lines in Settings.tsx — the container edit is a declared mechanical-union overlap (same pattern as src/index.ts mounts), and w3-i's embeds markup merges in as one more section whenever it lands.

## Amendment (wave 20): exports are ACTIONS, so the exports list has no read/edit split — and the frame's retention block is a recorded non-build

DESIGN-RULINGS B10 is explicit: 'Exports are actions — they download at once and there is nothing to save — so they need no edit view, and the edit screen says so rather than wrapping a download button in a form.' ExportsPanel.tsx:29-49 does exactly what that forbids: a local showEditor gate that, at rest, lists format NAMES as prose rows and hides every download link behind a 'Change' button — a second gate inside YourDataPanel's 'More export formats' disclosure, two gates deep over a set of anchors. DEC-896 already set the precedent on the sibling panel ('a Change gate that only exposed the SAME row markup underneath was a gate over nothing'). RULING: the download table renders unconditionally where the panel is mounted, and the panel carries the frame's own line verbatim — 'Exports are actions, not settings — they download at once and there is nothing here to save.' (Chautauqua Settings.dc.html:1191). This reverses the w1-f/DEC-785 convenience split for this panel only; the SECTION-level summary/edit drill (DEC-728/DEC-815, guarded by SettingsSummarySweep) is untouched, because ExportsPanel only ever renders inside the edit branch. Also recorded so it is not re-filed as an oversight: the 'Keeping and deleting' retention block drawn at Settings.dc.html:1161-1180 (retain declined submissions N months, keep files after the event, let speakers delete themselves) is NOT built — it has no column, no endpoint and no rubric item, and B10's own 'Your data splits by mutability' names only exports and API tokens. Building it would be inventing product from an unruled drawing.


## Amendment (wave 85): settings at 390 is a one-column list of groups, not the desktop tab rail, and its footer is the shell tab bar rather than a page dock

Chautauqua Settings.dc.html:275-312 replaces the desktop panel rail entirely: the body is `mobileGroups` rows — a 16px/600 label, a 13px muted detail line, a brand-olive `Open` at 13px/700, 18px vertical padding, hairline separators — and it closes with the plain sentence 'Embed codes are easier to copy on a laptop'. That sentence is an honest capability statement, NOT a disabled control, and it must render as text (the disabled token has exactly two legal uses and this is neither). The frame's footer strip (`padding:10px 8px 14px; display:flex; gap:2px` over `{{ tabs }}`) is the SHELL tab bar drawn inside the device box, not a page dock — building a dock there would stack two bands, the same defect DEC-989's wave-85 amendment rules against. Each Settings drill (:316 Event, :347 Tracks and rooms, :393 Your data, :444 Call for papers, :481 Public pages, :510 Speaker portal) therefore uses the drill head with a `‹ Settings` back link at the 26px cluster-local register the wave-83 DEC-643 amendment already records, and never invents a second footer.
