# DEC-068: Verification results are a tracked artifact: docs/verification-log.md, append-only, one dated section per run

Five consecutive verification lanes (w8-e, w9-a, w9-b originals, w10-e, w11-a) dropped with ZERO commits. Root cause: the task's only deliverable was triage text in a commit body, so a run that passes with nothing to fix yields an empty diff and the harness records a drop. Fix the mechanism, not the worker: every verification run appends a section to docs/verification-log.md with the format '## <date> <branch> — <scope> @ <main short-sha>' followed by bullet lines (PASS/FAIL per step, defects found, PLANNER: lines for unresolved questions). File starts with exactly two lines: '# Verification Log' and 'Append-only. One dated section per run.' Any task may create the file if absent (identical header makes concurrent creation trivially mergeable); sections from concurrent tasks merge as independent appends. This guarantees a non-empty committable diff, survives merges, and gives SPEC §9 an auditable persona-walkthrough record on main.

## Amendment (wave 37): docs/verification-log.md is a GENERATED artifact — duplicate 4-digit index sequences are a build error, and a merge conflict there is resolved by re-running the assembler, never by picking a side

scripts/assemble-verification-log.ts's nextSeq() returns one past the HIGHEST existing prefix, so N concurrent lanes in one wave all mint the same number by construction. Wave 35 hit this: the merge train silently hand-renumbered task-w35-a's entry 0188->0189 and regenerated the monolith — a repair performed by the party that measured nothing, invisible to every test, and in direct tension with the swarm's own rule that findings are filed rather than fixed by the finder. Detection belongs in the instrument: both --check and the default write path must fail loudly on a duplicate prefix, naming the colliding files and the remediation. And because the monolith is pure concatenation, a textual merge conflict in docs/verification-log.md carries no information — the correct resolution is always to take neither side and re-run `tsx scripts/assemble-verification-log.ts`. Codifying both removes a recurring merge-train hazard that has already cost one silent doc rewrite.

## Amendment (wave 39): the assembler's sequence collision is permanent by construction, so its remediation must be a command, not a merge-train hand-edit

Detection stays; only the remedy becomes mechanical.

## Amendment (wave 45): a section file whose first line does not match the header contract is INVISIBLE to the predicate and silently donates its verdict to its predecessor — the assembler must refuse it; wave 45 pre-allocates 0230-0237

Derived at my own runtime. `scripts/exit-predicate.ts:36` starts a new section ONLY on `/^## (\d{4}-\d{2}-\d{2}) (\S+) — (.+) @ (\S+)\s*$/`; `parseLogSections:69-84` folds every other line into the body of whatever section precedes it, and `:90-103` resolves each section by taking the LAST `RESULT:` and the LAST `OPEN ITEMS:` line in that body. Consequence: a malformed index file is not merely ignored — it OVERWRITES the verdict of the nearest preceding conforming section. `scripts/assemble-verification-log.ts` validates only duplicate 4-digit prefixes (`:55-84`); it never looks at a header.

At least six current index files do not conform, and their bodies all fold into one earlier section: `0176-...-task-w29-a-onboarding-grid-perf-1d274c8b.md:1` (`## task-w29-a: onboarding grid TIER-0 perf (...)`), `0180-...-task-w29-e-review-perf-b7060152.md:1` (conforming up to the sha, then a trailing ` [QUALIFYING]` breaks `\s*$`), `0181`, `0182`, `0183-...-task-w31-c-plan-results-perf-7581aa3b.md:1` (`## QUALIFYING (task-w31-c)`), `0184`, `0185`. `0184:9` carries `RESULT: files library (page 1) BEFORE ... FAIL -> AFTER ... PASS` — a line that does not start with the token `PASS` and therefore grades FAIL for whatever section swallows it. This is not hypothetical corruption; it is present corruption that happens to sit on ancestry-stale shas today.

RULING. (a) The assembler owns the header contract: `assemble()` and `--check` both fail loudly, naming every offending file, in exactly the shape `assertNoDuplicateSequences` already uses. Detection belongs in the instrument, not in a reviewer's eye — the same reasoning DEC-068's wave-37 amendment used for seq collisions after wave 35's merge train hand-fixed one silently. (b) Repairing a malformed FIRST LINE (date/branch/sha from the filename, scope verbatim from the existing title text, nothing else touched) is restoring the record, not rewriting it, and is permitted — but only under the same before/after `exit:predicate` abort condition DEC-099's wave-45 amendment imposes, because it changes which sections the predicate can see. (c) SEQ PRE-ALLOCATION (DEC-068's own plan-time rule, which the `0216` collision shows is worth honoring with a buffer): wave 45 takes `0230`-`0237`, deliberately leaving `0217`-`0219` and `0227`-`0229` free so wave 44's in-flight `0220`-`0226` can spill without colliding. If a lane finds its allocated number occupied at worktree cut, it takes the next free number at or above `0240` and records the collision in its own section the way `0216:7-17` did, rather than renumbering silently.


## Amendment (wave 46): a malformed header donates its verdict to its predecessor — the assembler SYNTHESIZES a conforming header from the filename, and index files are still never hand-edited

`scripts/exit-predicate.ts:36`'s HEADER_RE starts a section only on an exact `## <YYYY-MM-DD> <branch> — <scope> @ <sha>` match (EM DASH U+2014); every other line, including a `## `-prefixed one, is body text of whatever section it falls under. Read directly at my own runtime, at least nine index files fail that contract: `0176`, `0178`, `0181`, `0182`, `0183`, `0184`, `0185` carry no date/em-dash/@sha at all, and `0180` and `0187` are date-and-em-dash correct but append a trailing ` [QUALIFYING]` after the sha, which defeats the anchored `@ (\S+)\s*$` tail. The consequence is not merely invisibility: their whole bodies, `RESULT:` and `OPEN ITEMS:` lines included, fold into the PRECEDING conforming section, and the parser's own 'last RESULT line wins' rule then hands that predecessor a verdict it never wrote. Today `0179` (`files library perf fix`, ancestry-stale) absorbs `0180` through `0185` and reports `0185`'s RESULT as its own. It is harmless only by the accident of ancestry; the mechanism is live. Two repairs were available and one is wrong. Hand-editing the nine headers is rejected: DEC-068's own never-hand-edit rule exists precisely so a published verdict cannot be retouched after the fact, and a wave that edits nine section headers to change what the grader reads is indistinguishable from one that edits them to change what it says. Terminating a section on any non-conforming `## ` line is also rejected: real sections legitimately use `## STEP 1`, `## STEP 2`, `## RESULT` sub-headers (`0216:41,91,104`), and that rule would silently drop `0216`'s own `RESULT:`/`OPEN ITEMS:` lines. RULING: the repair belongs in the ASSEMBLER, which is the only component that knows file boundaries. When an index file's first line fails the contract, `scripts/assemble-verification-log.ts` emits a SYNTHETIC conforming header derived from the filename — which already encodes `NNNN-YYYY-MM-DD-<branch>-<scope-words>-<sha>.md` — and keeps the file's original first line as the section's first body line, so nothing published is lost, nothing on disk is retouched, and the assembled log is contract-conforming by construction. A filename that itself fails to parse throws.

## Amendment (wave 46): implementation (task-w46-b) — mechanical count is 31, not nine, and "sha" is a POSITION not a shape

The wave-46 ruling above was written from a spot check ("at least nine"). Mechanically testing every `docs/verification-log/index/*.md` file's first line against `scripts/exit-predicate.ts:36`'s HEADER_RE at task-w46-b's own runtime finds THIRTY-ONE non-conforming files, not nine: the nine already named, plus `0193` (same trailing-`[QUALIFYING]`-after-sha shape the ruling already covers), plus TWENTY-ONE wave-12-through-21-vintage files (`0140`, `0142`-`0154`, `0157`, `0164`-`0168`) that the spot check missed entirely because they predate the `@ <sha>` convention: their headers end in a parenthesized `(DEC-nnn)` or nothing at all, with no `@` token anywhere.

Implementing the ruling's own filename-derivation instruction against this full 31-file set surfaced a second gap: an early draft required the filename's trailing segment to look like a hex git sha (`/^[0-9a-f]{6,40}$/i`) before treating it as `<sha>`, and 14 of the 21 older files fail that check — some (e.g. `0143`, `0145`) never carried a sha in the filename at all (evidence-lane entries not tied to one commit), others (e.g. `0142`, `0146`, `0149`, `0151`, `0154`) were truncated at exactly 80 characters when created, losing the trailing sha entirely. Hex-validating would throw on all 14 and break `npm run verification-log:assemble` outright — a regression worse than the status quo, and not what "throw loudly if the filename itself does not parse" was written to cover (a malformed BASE shape, not an unfamiliar-looking trailing token). RULING (implementation-level): `deriveSyntheticHeader` in `scripts/assemble-verification-log.ts` treats the filename's trailing hyphen-segment as `<sha>` POSITIONALLY, with no content validation — exactly as HEADER_RE's own `@ (\S+)` group already does for every conforming header in this file. This is not a relaxation of the header contract; it refuses to invent a stricter one than the contract already has. It throws only when the filename doesn't even match the base `NNNN-YYYY-MM-DD-task-w<N>-<letter>-...md` shape, or when nothing at all follows the branch. Verified: all 31 non-conforming files under `docs/verification-log/index/` now parse and synthesize; `npm run verification-log:assemble` succeeds for the full 222-entry corpus; and comparing `gradePredicate` output before/after (best-effort ancestry, since `scripts/exit-predicate.ts`'s `git merge-base --is-ancestor` still crashes on an unresolvable ancient sha per task-w46-a's separate defect) shows no DEC-069 slot's winning section changes identity.

## Amendment (wave 48): docs/verification-log.md is DERIVED — regenerate it in the same commit as the index file, never hand-merge it; section sequences are planner-pre-allocated

Two mechanisms in the tree make this load-bearing, both re-read at my own runtime. First, `test/verification-log-verdict-contract.test.ts:130-141` asserts that `parseLogSections(docs/verification-log.md)` yields exactly one section per conformant `docs/verification-log/index/*.md` file, in filename order. A gate lane that adds its index file WITHOUT re-running `npm run verification-log:assemble` therefore leaves the suite red — and in a battery wave the very next thing that happens is the build+test lane grading that redness as a product FAIL. An instrument artifact would decide the slot, which is the exact class of failure `0216`, `0215` and `0226` already cost the swarm three waves. Second, `nextSeq()` (`scripts/assemble-verification-log.ts:292-297`) mints one past the highest existing prefix, so every concurrent lane in a wave gets the SAME number by construction — `assertNoDuplicateSequences` then throws for everyone, and the 0188/0191/0198 collisions are all this one bug. RULING: (a) every lane that adds an index file runs `npm run verification-log:assemble` and commits the regenerated `docs/verification-log.md` in the SAME commit; (b) any merge conflict in `docs/verification-log.md` is resolved by re-running the assembler over the merged index set, NEVER by hand-merging hunks — it is a derived artifact and a hand-merge can silently reorder or drop a section; (c) the exit-ledger lane re-runs the assembler after its own final sync so the artifact it grades is the merged one, and runs `npm run verification-log:check` (must exit 0) before reading the predicate; (d) sequences are PRE-ALLOCATED by the planner, one per section-writing lane — wave 48 uses 0240 (build+test+bundle), 0241 (walkthrough), 0242 (perf-smoke), 0243 (spec-audit), 0244 (render-sweep), 0245 (triage-closure), 0246 (stage-1 exit ledger), leaving 0238-0239 free for wave 47's own docs lane; no wave-48 lane runs `--next-seq`. `--renumber` stays the remedy of last resort, not the plan.
