# DEC-536: DEC-318's out-of-range-slot rule is not a public-surface rule, it is THE schedule-read rule -- the speaker portal joins it

DEC-318 established that a `schedule_slot` dated outside its event's `[startDate, endDate]` must never render as a placement; the session shows as unscheduled instead. Four schedule reads honour it -- `public/agenda.ts:40,120` and `public/detail.ts:43` via `slotWithinEventRange`, `repo/agenda.ts:283,339` via `isDayWithinEventRange`, `public/sessions.ts:300` via `slotWithinEventRange`. One does not: `getMySessions` (src/server/repo/portal.ts:600-635) left-joins `schedule_slot` and `room` with no range predicate at all. So the speaker portal -- SPEC J7's "my sessions" -- tells a speaker "Wed 30 Jun, Room 2A" for a slot that the public agenda, the .ics feed and the organizer's own grid all show as unplaced. That is the worst possible place for the disagreement to surface, because the speaker acts on it. Decision: the range predicate goes into the LEFT JOIN's ON clause (`and(eq(slot.submissionId, submission.id), gte(slot.day, event.startDate), lte(slot.day, event.endDate))`), compared against the already-joined `event` columns in SQL -- never into the WHERE, which would drop the whole session row rather than nulling its placement, and never as a JS post-filter (DEC-312: the WHERE is normative). An unscheduled portal session already renders correctly with all four schedule fields null, so the fix needs no view change.
