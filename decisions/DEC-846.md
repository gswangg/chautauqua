# DEC-846: A composer sends the text on screen; a template is a starting point, not a hidden source of truth — and history owes the WORDS

VERIFIED two halves of one dishonesty. (a) app/src/pages/comms/ComposeWizard.tsx:143-148: when a template is selected, composeBody sends ONLY {templateId} and the server (src/routes/comms/compose-core.ts) re-reads the stored template — so every edit the organiser typed into the visible Subject/Body textareas (including tokens inserted by the DEC-793 chip row) is silently discarded at send time. (b) src/server/repo/email.ts already selects bodyText on the per-recipient log row, but app/src/pages/comms/types.ts:39 drops it and RecentSends.tsx renders when/subject/to/status only — so a send is auditable to its metadata and not to its words, and a fully-failed batch can be inspected without ever seeing what it said. Decision: the composer ALWAYS posts the visible subject + bodyText (the server contract already accepts subject+bodyText as the alternative to templateId, so this needs no route change); selecting a template prefills those fields and nothing more. And the expanded batch disclosure in Recent sends renders each recipient's stored, already-rendered body text verbatim (whitespace preserved), because 'shows what it sends' and 'auditable to its words' are the same rule at two ends of one send.

## Amendment (wave 3): templateId is PROVENANCE, not authority — the composer posts it and still sends its own words

DEC-832/846 ruled that a template is a starting point, not a mode: the composer always posts its own subject/bodyText so history shows the words that actually went out. That ruling is correct and stands. What was over-applied is the corollary in app/src/pages/comms/ComposeWizard.tsx:140/194 — 'templateId is never sent'. Two different questions got one answer. `email_log.subject`/`body_text` (stored verbatim per DEC-006, disclosed per DEC-833) answer 'what went out'; `email_log.template_id` answers 'where did this send come from'. Suppressing the second does not protect the first — it just blanks the Template column for every wizard send (RecentSends.tsx:262 falls back to an em dash) and makes the templates list's 'Last used' permanently wrong for the product's main send path. The fleet read this as 'Recent Sends and History are two readers'; they are one reader (RecentSends is mounted twice), fed a null. RULING: the composer posts `templateId` — the id of the template it was seeded from, including via the `?template=<id>` landing — as pure provenance. The server stores it and continues to render exclusively from the posted subject/bodyText; it validates that the template belongs to the addressed event and refuses an unknown or foreign id with the standard `{error:{code:'invalid',...}}` envelope (an unvalidated foreign id in a log column is a cross-tenant leak, DEC-004 discipline). Nothing about which words are sent changes.

## Amendment (wave 66): a provenance field is cleared only by the control that disowns it

ComposeWizard.tsx:915-941 sets `setTemplateId('')` the instant a template is picked from the dropdown, so the ONLY path that ever posts provenance is the `?template=` landing (:225). Every dropdown-picked send therefore writes `email_log.template_id = NULL`: the History TEMPLATE cell renders the em dash (RecentSends.tsx:297), the History template chips can never match those sends, and Templates' "Last used" (repo/email.ts:224-233, which groups on a NOT NULL template_id) stays permanently blank. Two comments in one file describe opposite behaviour -- DEC-832's "then clear the selection" at :919 versus DEC-846's "when the composer still holds one, it's posted too" at :275-288 -- and the code implements the first, making the second unreachable. RULING: the select's value IS the provenance. Picking a template sets `templateId` to that id and LEAVES it set (the control then truthfully names what this draft came from); only the explicit "Write from scratch" option (`id === ''`) clears it, and that branch keeps its existing subject/body wipe. subject/bodyText stay the authority for what goes out, and the server keeps validating the id against the event (send.ts:142-151). The unreachable third branch (`id !== '' && !found`) is deleted rather than left as a silent fallback.
