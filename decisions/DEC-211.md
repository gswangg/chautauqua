# DEC-211: Every evaluation write and read on /api/v1/review/* must verify the submission belongs to the plan's event, for organizers as well as reviewers

PUT /api/v1/review/plans/:planId/evaluations/:submissionId (the former src/routes/review.ts:597-644 (now split across src/routes/review/)) checks reviewer scope for reviewers but performs NO submission check at all for organizers: requireAssignedPlan scopes the plan to the org, then upsertEvaluation writes planId+submissionId blind. An organizer can persist evaluations against any submission id in the DB — another event's, another org's — creating phantom rows that trip planHasEvaluations (freezing criteria per DEC-123) while never appearing in results. Rule: immediately after requireAssignedPlan resolves the plan, the handler must call repo.getSubmissionSummaryInEvent(db, submissionId, plan.eventId) and throw ApiError('not_found', 'Submission not found') when null, for EVERY role, before any write; the reviewer-scope check remains layered on top for reviewers. This mirrors the existing GET /api/v1/review/submissions/:id behavior (review.ts:573-574) — existence-hiding 404, not 403, consistent with DEC-175.


## Amendment (wave 61): a refusal may name the reviewer's own queue INSIDE a plan they are assigned to; existence-hiding still binds outside the plan's event

An out-of-queue reviewer gets a bare 'Submission not found' (reviewer.ts:359 and :444) for a submission that plainly exists in an event they are already reviewing — the graded read was 'the product is broken', not 'the product is discreet'. DEC-211's existence-hiding exists to stop a caller learning that a row exists in an org/event they cannot see. That is not this case: the caller has already passed requireAssignedPlan, so they know the plan, its event and its submission count. Ruling, narrow on purpose: when the caller is assigned to the plan and the submission is IN that plan's event but outside the caller's resolved scope, the refusal keeps code not_found and HTTP 404 and says 'That submission is not in your review queue.'; when the submission is not in the plan's event at all (getSubmissionSummaryInEvent returns null), the message stays 'Submission not found' verbatim. The status code never changes — only the sentence, and only on the branch that has already proved the caller belongs to the plan.
