# DEC-477: The public row ceiling is MAX_PUBLIC_PAGE x PER_PAGE and must clear SPEC's top-of-range speaker count -- and the new deepest page is MEASURED, not assumed

SPEC.md:73-76 states 200-800 speakers and 'Every list view ... must be designed for the top of these ranges'. src/server/repo/public/bounds.ts:9 clamps the cumulative LIMIT at MAX_PUBLIC_ROWS = 600, and src/routes/public/query.ts:10's MAX_PUBLIC_PAGE = 50 times src/routes/public/shell.tsx:20's PER_PAGE = 12 lands on exactly 600 too. At the top of SPEC's own stated range the last 200 speakers are unreachable from /e/:slug/speakers, /gallery and the /embed/*.json feed, while total still honestly reports 800 -- the caption is truthful and the product is still wrong. DEC-433 was right that one number endangered two things; it was wrong about the magnitude. Raise to MAX_PUBLIC_PAGE = 100, MAX_PUBLIC_ROWS = 1200, derived from one another so a future edit of either fails a test rather than silently shadowing the other, and make hasMore test the ROW ceiling as well as the page ceiling (a ?limit=100 embed reaches 1200 rows by page 12, where the page bound has not yet bitten and 'Show more' would otherwise link to a page identical to its own). SPEC J10 names 'show-more' explicitly, so the accumulate affordance stays; what changes is where it honestly stops. Because this raises worst-case uncached SSR by 2x against SPEC.md:334-335's budget, DEC-453 forbids grading it from code presence: the lane that raises the ceiling owns a perf:smoke check at the deepest reachable page against the 2k/800-contact seed, and lowers the ceiling to whatever actually measures under budget if 1200 does not.
