# DEC-020: File pipeline: upload validation, version chains, authenticated serving, comments, approval

J8 spans a server task and an admin-UI task; the contract is fixed here. Upload: POST /api/v1/submissions/:id/files, multipart fields file, kind ('presentation'|'poster'|'handout' per DEC-003), optional replacesFileId — allowed for organizers or speakers who are participants on the submission. Validation is a pure core (src/domain/files.ts): extension allowlist with a forced served-content-type map — pdf, ppt, pptx, key, odp, zip (25 MB cap), png, jpg, jpeg, webp, gif (8 MB cap), txt, md (served text/plain); anything else 'invalid'; user content is NEVER served with an HTML content type; unknown maps to application/octet-stream. R2 key: sub/<submissionId>/<newId()>-<sanitized-filename> via makeFileStore(env.FILES). replacesFileId must reference a file on the same submission with the same kind, else 'invalid'; the new row sets previous_file_id (DEC-003 chain). GET /api/v1/submissions/:id/files returns deliverables grouped by kind, versions newest-first with the full chain. GET /files/:fileId (root-mounted, DEC-005) streams from R2 with authz: organizer any; speaker only when participant on the file's submission or the uploader; Content-Disposition attachment for non-image types. Comments: GET/POST /api/v1/files/:fileId/comments { body } — same authz as file read; rows carry author name + role. Approval: POST /api/v1/submissions/:id/content-status { contentStatus } organizer-only, DEC-003 literals, never sends email. Upload UI must state the accepted types and size caps verbatim from this list (CNT-12).

## Amendment (wave 60): a new deliverable version REOPENS content review — approved/changes_requested returns to pending on upload

DEC-020 owns both halves of the file pipeline (version chains AND approval) but never connects them. Verified on main: `POST /api/v1/submissions/:id/content-status` (src/routes/files.ts:243-259) is the ONLY writer of submission.content_status outside create/submit/import — no upload path touches it. So the J8 loop is one-way: organizer approves -> speaker replaces the deck -> content_status stays 'approved', the session stays publicly live behind an unreviewed file, the row still reads "Approved" (DEC-881's precedence puts approved above re-uploaded), and it is absent from the "Needs a decision" tab and from Overview section 03 (src/server/repo/overview.ts:276-277 filters content_status='pending'). Worse for the changes_requested path DEC-741 built: the organizer asks for changes, the speaker re-uploads, and NOTHING tells the organizer — the session sits in changes_requested forever. It also makes DEC-881's own arithmetic ("5 need a decision = 2 re-uploaded + 3 not reviewed") false, because src/server/repo/submissions/list.ts:186-211 counts re-uploads across ALL content statuses while "needs a decision" counts only pending+changes_requested. RULING: inserting a file with a non-null submissionId and a deliverable FILE_KIND sets that submission's content_status back to 'pending' when it is currently 'approved' or 'changes_requested' — ONE set-based, idempotent UPDATE in the repo (never a read-then-write), applied by every deliverable-upload site. A headshot or resource upload (submissionId null / HEADSHOT_KIND) never reopens anything. This module still MUST NEVER import a mailer (DEC-009): reopening is a status fact, not a notification.

## Amendment (wave 42): the upload tier is chosen by KIND, and no upload path buffers a file in the isolate

Verified today: src/domain/files.ts:113 validateUpload dispatches purely on extension — `kind` is only checked for enum membership — so the anonymous CFP attachment field (src/routes/public/submit.tsx:365, which passes kind 'handout' with an inline comment claiming the kind 'selects the extension/size allowlist tier') accepts .mp4/.mov/.webm up to VIDEO_MAX_BYTES = 250 MB. An argument that is never read is a lie in a signature. The video tier is admitted ONLY for kind 'recording' (DEC-879's own reading — a recording is a deliverable, not a form attachment); every other kind gets the document/image/text tiers. Second half: every upload path then does `await file.arrayBuffer()` inside a 128 MB isolate (files.ts:168, submit.tsx:462, portal/tasks.tsx:407, api/portal-config.ts:207) — the ZIP path already caps at 40 MB citing exactly this constraint. FileStore.put already accepts a ReadableStream (src/server/context.ts:91), so uploads stream; a deliverable is never materialized as an ArrayBuffer.

## Amendment (wave 10): a re-upload that unpublishes SAYS SO — before the act and after it

DEC-020's wave-60 amendment deliberately makes a new deliverable version reopen content review (src/server/repo/files-content-status.ts:88-97), and DEC-274's session gate requires content_status='approved' (src/server/repo/public/gates.ts:26). Composed, a speaker posting a revised deck from the portal (src/routes/portal/tasks.tsx:588-590) drops their accepted, scheduled talk off /sessions, /agenda, /speakers, the .ics feeds and every embed. This amendment does NOT change the gate: SPEC J8 says 'unapproved content never reaches public surfaces', SPEC's data-model line makes accepted AND content-approved distinct gates 'never collapsed', rubric 04-content-management grades the gate, and the wave-60 amendment's reasoning (the organizer must not be blind to a swapped deck) is sound — the producer's own queue is `accepted AND content_status='pending'` (src/server/repo/overview.ts:247-268), so keeping 'approved' would trade a public-visibility bug for producer blindness. The defect is the SILENCE, not the demotion. RULING: the consequence is disclosed on both sides of the act, in the portal, with no mailer (DEC-009 stands). The upload and Replace affordances for a SUBMISSION-LINKED deliverable (the condition is exactly tasks.tsx:588's — deliverableKind non-null) state before submission that posting a new version sends it back to the producer and takes the session off the public schedule until it is approved again; a plain handout task (deliverableKind null, no reopen) states nothing, because nothing happens. After a successful submission-linked upload the portal returns a receipt naming what just happened rather than a bare redirect. A DISCLOSURE IS NOT A DELETION, and a receipt states what was received.

## Amendment (wave 43): replace is append-only on BOTH upload surfaces, and the deliverable chip counts versions per KIND

The version chain, its stored version_no identity (DEC-818) and the comment re-home on delete (DEC-713) all read correct on main, yet an external probe reports a replace showing a single v1 with its comments gone. The two replace surfaces reach insertFile by different routes (organizer UploadZone passes replacesFileId from the chain head; the portal task upload derives previousFileId from the assignment's stored file_id), so a divergence between them is invisible to any unit test of the pure core. Amendment: both surfaces are covered by one end-to-end regression that asserts v1+v2 with the v1 thread still readable on the deliverable, and the chip strip states version counts per KIND ('Slides · 3 versions'), not per upload-group — the frame's claim and the data must be the same reader.

## Amendment (wave 12) — every surface that can trigger reopenContentReview must re-read the status it displays; a status copied into component state is a snapshot, not a subscription

reopenContentReview (src/server/repo/files-content-status.ts:88) flips content_status approved -> pending, and visibleSessionConditions() requires 'approved', so a new version drops the session off /e/*, /embed/*, the agenda and the .ics. The two speaker paths disclose this (portal ReuploadReviewNotice + the ?uploaded= receipt, wave 10). The organizer path does not: DeliverableDetail seeds `pill` from a prop at mount and its handleUpload reloads only the file list, so after a replace the band still reads APPROVED, headerDetail.reuploaded stays false, and the `pill !== 'approved'` gate hides the Approve action — the one control that would put the session back on the public site. Ruling: one reader per surface. The status shown is re-read from the server after any write that can move it; optimistic writes reconcile against that read rather than replacing it.

## Amendment (wave 30): a request declares its size before the Worker buffers it — one global ceiling ahead of the FIRST body reader, not a per-route check after parseBody

Verified on main: every upload route calls `c.req.parseBody()` before `validateUpload` (src/routes/files.ts:154 vs :164; src/routes/public/submit.tsx:261/:406), Hono's parseFormData does `await request.arrayBuffer()`, and `grep -i content-length src/` returns NOTHING. With VIDEO_MAX_BYTES=95MB against this file's own ISOLATE_MEMORY_BUDGET_BYTES=128MB, an anonymous POST to /submit/<slug> can OOM the isolate before a single validation runs. The fix cannot be per-route: `csrfForm` in src/server/middleware.ts:283/331 itself calls parseBody to read the form token, so the body is already buffered before any handler executes. Therefore the ceiling is ONE middleware registered first in createBaseApp, keyed off Content-Length: over MAX_REQUEST_BODY_BYTES is refused; a `multipart/form-data` request with NO Content-Length is refused too (an upload must declare its length; browsers always do), while a length-less non-multipart request passes so bearer-token API clients using chunked encoding keep working. The refusal uses the DEC-013 envelope with a new `payload_too_large` code at 413 — the honest status. Per-kind caps in src/domain/files.ts stay exactly where they are: the ceiling protects memory, validateUpload protects policy.

## Amendment (wave 38): an allowlist keyed by an attacker-supplied string is an OWN-PROPERTY question, and the served content type is asserted at the byte boundary

Verified at the file: src/domain/files.ts:187/194/201/208 and :375 test `ext in <Record literal>`, and `in` walks Object.prototype — a file named `deck.constructor` / `x.__proto__` / `x.toString` clears validateUpload and validateHeadshotUpload, and servedContentType becomes a function/object that is persisted as file.content_type and echoed as a raw Content-Type at src/routes/files.ts:645. Reachable with NO account through the public CFP upload. src/forms/validate.ts:66 already uses Object.prototype.hasOwnProperty.call for exactly this shape, so this is drift, not a choice. Ruling: every extension->content-type lookup goes through one own-property helper; `in` is never used against a Record literal whose key came from user input. Second half: DEC-020's own claim 'never returns an HTML content type' is enforced only at write time, so the ONE route that echoes the stored string as a raw header asserts the invariant loudly (a throw, never a default) in the same spirit as contentDispositionAttachment's end-of-function ASCII assert.

## Amendment (wave 39): own-property discipline is a family rule, not a files.ts fix — every author/request-keyed lookup table reads own-property only, each with a negative control

Wave 38 closed `ext in DOCUMENT_EXT_CONTENT_TYPE` in src/domain/files.ts by routing every tier through one own-property reader. The same shape survives at four more module-level object literals whose documented fallback is defeated by a prototype key: src/mail/render.ts:34 (MERGE_FIELD_ALIASES[name] returns Object for `{constructor}`, so `?? name` never fires and a value typed `string` is a function), src/domain/acceptance.ts:88 read at src/server/repo/submissions/status.ts:97 (FORM_TASK_FIELD_SPECS[title] ?? [] — one PATCH away from being keyed by an organizer-authored task title, where the `?? []` would be skipped and `.entries()` would throw inside the acceptance write), src/domain/contacts.ts:350-369 (INVITE_STATUS_RANK, whose doc promises "an unrecognized literal ranks lowest" — true only by luck for a prototype key), and src/server/repo/forms.ts:118-133 (LOCKED_* label/kind tables). All four are latent today because their keys are literals; a family that is correct by luck drifts the moment one key becomes input. Ruling: each module gets one own-property reader in the shape of files.ts's allowedContentType, and each site ships a negative control feeding constructor/__proto__/toString/hasOwnProperty plus a positive control, so the scan can fail in both directions.

## Amendment (wave 55): one human byte-size renderer in pure core, crossed to the SPA by name; every byte figure in copy is built by it

Four byte figures, three grammars, two implementations. app/src/pages/content/format.ts:2 has formatBytes ("9.0 KB", space, no input validation); src/routes/portal/index.tsx:376-394 declares formatFileSize with its own BYTE_UNITS array and a comment asserting "no such helper exists yet elsewhere in the codebase", which is false; src/routes/files.ts:396 emits "20MB" with no space; src/domain/files.ts:275 emits "20 MB" with one. This is DEC-660/DEC-957's settled shape — a constant or a formatter the customer reads is declared once in pure core and crosses to app/ through one named module — applied to the vocabulary that states file caps. Pure core owns it, it fails loudly on a non-finite or negative input, and app/src/pages/content/format.ts becomes the named crossing so no importer changes its path.

## Amendment (wave 58): the ORGANIZER's own deliverable upload discloses the unpublish too — reopenContentReview reports whether it moved anything

DEC-020's wave-10 amendment ruled that a re-upload which unpublishes SAYS SO on both sides of the act, and built exactly that for the speaker portal (src/routes/portal/tasks.tsx:614-635, the ?uploaded= receipt). The organizer path was never covered: src/routes/files.ts:231 calls reopenContentReview unconditionally on POST /api/v1/submissions/:id/files, flipping content_status approved -> pending (src/server/repo/files-content-status.ts:102-111), which visibleSessionConditions() (src/server/repo/public/gates.ts) gates on — pulling the session and its speakers off /sessions, /agenda, /speakers, every embed and the .ics feeds — and the 201 at files.ts:233 says nothing about it. The wave-12 amendment's 're-read the status you display' is satisfied (DeliverableDetail refetches the header and moves the pill), but a pill silently changing colour is not a disclosure: nothing on the organizer's screen names the public-visibility consequence the speaker's screen names in a sentence. RULING: reopenContentReview stays ONE idempotent set-based UPDATE with no mailer (DEC-009) but reports its outcome — `{ reopened: boolean }` from the same statement, never a read-then-write — and the upload 201 carries that fact. The organizer surface then discloses on both sides of the act, in the same plain vocabulary the portal uses and with no new colour (DEC-367): the replace affordance for a submission-linked deliverable states beforehand that a new version returns the session to review and off the public schedule, and the post-upload receipt states what just happened. Symmetry is the point: two people performing the same act must be told the same thing.

## Amendment (wave 63): every file picker in the product derives its accept list AND its help text from src/domain/files.ts (allowedUploadExtensions/uploadHintText) and pre-validates the chosen file with validateUpload before any request

Five surfaces already obey this (src/views/form-render.tsx:114-160, src/routes/portal/tasks/views.tsx:271-308 x2, src/routes/portal/tasks.tsx:564's refusal, app/src/pages/content/UploadZone.tsx:46/94/105) and wave 62 brought the two headshot pickers in. The sixth — app/src/pages/settings/ResourcesPanel.tsx:334 — has no accept attribute, no hint, and no client-side check, while its server counterpart validates with validateUpload({..., kind: "handout"}) at src/routes/api/portal-config.ts:208. So the organizer's OS picker offers every file on the disk, a 40 MB video travels the whole wire, and the allowlist is disclosed only by the refusal. A rule proven on the surfaces someone enumerated stops at the surface they didn't; the fix is not a sixth hand-typed list but the same two pure-core functions the other five call, plus the same pre-flight validateUpload UploadZone runs, so a wrong pick is refused before the request and the refusal names what would have been kept.

## Amendment (wave 67): every upload byte budget has one home, and every sentence that prints one interpolates it

src/domain/files.ts is the ONE module that owns upload sizing, and its own doc-comment at :133-135 claims 'The recording size is interpolated from VIDEO_MAX_BYTES, never hand-typed, so this copy can't drift from the enforced cap' -- in the same sentence that hand-types 25 and 8 (:140-141). Four more hand-typed MB numbers sit in validateUpload's refusals (:200, :208, :216), each beside the constant it is supposed to name (DOCUMENT_MAX_BYTES :58, IMAGE_MAX_BYTES :59, TEXT_MAX_BYTES :63) -- constants exported ONLY as *_FOR_TEST (:68-70), which is the shape the field guide already names as 'a rule that no surface can print'. HEADSHOT_MAX_BYTES (:423) is a second declaration of IMAGE_MAX_BYTES' 8 MB. Ruling: the three tier constants become real exports, HEADSHOT_MAX_BYTES derives from IMAGE_MAX_BYTES, uploadHintText and all four size refusals interpolate, and a scan forbids a hand-typed ' MB' number anywhere in the module outside a constant declaration.

## Amendment (wave 30): an absent Content-Length is refused for every content type the app buffers before auth, not multipart alone

src/server/body-limit.ts:54-61 returns ok for a missing Content-Length on anything that is not multipart/form-data. But src/server/middleware.ts:283 (csrfForm) calls c.req.parseBody() in MIDDLEWARE, ahead of every handler and ahead of auth, on the unauthenticated POST /login, POST /forgot, POST /claim/:token and POST /submit/:eventSlug paths — so a chunked application/x-www-form-urlencoded body is buffered whole with no ceiling, which is precisely the pre-read buffering the module's own header (lines 1-9) says it exists to prevent. The ceiling therefore covers both shapes parseBody accepts (multipart/form-data and application/x-www-form-urlencoded). JSON bodies stay out of scope on purpose: they are read inside handlers behind requireRole/csrfJson, and refusing chunked JSON would break legitimate streaming API clients.
