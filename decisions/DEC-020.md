# DEC-020: File pipeline: upload validation, version chains, authenticated serving, comments, approval

J8 spans a server task and an admin-UI task; the contract is fixed here. Upload: POST /api/v1/submissions/:id/files, multipart fields file, kind ('presentation'|'poster'|'handout' per DEC-003), optional replacesFileId — allowed for organizers or speakers who are participants on the submission. Validation is a pure core (src/domain/files.ts): extension allowlist with a forced served-content-type map — pdf, ppt, pptx, key, odp, zip (25 MB cap), png, jpg, jpeg, webp, gif (8 MB cap), txt, md (served text/plain); anything else 'invalid'; user content is NEVER served with an HTML content type; unknown maps to application/octet-stream. R2 key: sub/<submissionId>/<newId()>-<sanitized-filename> via makeFileStore(env.FILES). replacesFileId must reference a file on the same submission with the same kind, else 'invalid'; the new row sets previous_file_id (DEC-003 chain). GET /api/v1/submissions/:id/files returns deliverables grouped by kind, versions newest-first with the full chain. GET /files/:fileId (root-mounted, DEC-005) streams from R2 with authz: organizer any; speaker only when participant on the file's submission or the uploader; Content-Disposition attachment for non-image types. Comments: GET/POST /api/v1/files/:fileId/comments { body } — same authz as file read; rows carry author name + role. Approval: POST /api/v1/submissions/:id/content-status { contentStatus } organizer-only, DEC-003 literals, never sends email. Upload UI must state the accepted types and size caps verbatim from this list (CNT-12).
