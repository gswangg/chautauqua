# DEC-598: A submission's tracks and session format are organiser-editable through the same join writer the portal edit uses

Tracks can only ever be set by the public CFP form or a speaker's portal edit: PATCH /api/v1/submissions/:id accepts title and description only, and the quick New-submission modal collects neither track nor format. A submission created in the admin is therefore permanently track-less, which silently removes it from track-scoped reviewer assignment, from the public track filter, and from any track-coloured agenda reasoning. PATCH takes an optional trackIds array as a full-set replace routed through the same submission_track writer portal-edit uses (two functions claiming the same semantics end in the same helper), and the quick-create modal collects tracks as multi-select per DEC-579 plus the DEC-592 format field.

## Amendment (findings wave 10): trackIds are a SET at every boundary and in the writer

submission_track is keyed primaryKey([submissionId, trackId]) (src/db/schema/submissions.ts:75-83) and both writers insert one row per array element (src/server/repo/submit.ts:294-297, :322-326). parseTrackIdsField validates shape, cap and event membership but never dedupes (src/routes/api/submissions.ts:112-136), and the public CFP's extractTrackIds does not either (src/routes/public/submit-body.ts:71-76, used at submit-post.tsx:157 and submit-draft.tsx:71) — so trackIds=T1&trackIds=T1 raises SQLITE_CONSTRAINT and surfaces as an uncaught 500 on an ANONYMOUS-reachable path, taking a create-then-rollback of the submission row and its R2 objects with it. The portal-edit twin already dedupes (src/routes/portal/edit.tsx:375), so this is an omission, not a policy. Separately, the public CFP enforces membership (validateTrackChoice, src/lib/submit-core.ts:61-81) but NO count cap, so MAX_SUBMISSION_TRACK_IDS binds on the API and not on the anonymous route. RULING: (a) both boundary parsers return a deduped array, and the cap is checked AFTER dedupe so it counts distinct ids; (b) the cap moves into validateTrackChoice so every caller of the pure gate — public CFP and portal edit alike — inherits it, with the cap-copy grammar, never a bare number; (c) the repo writers dedupe their own rows defensively, so no caller (including the sessionboard importer) can produce a constraint violation. Silent dedupe, not a 400: duplicate checkbox values are a transport artefact, and the portal already treats them that way.

## Amendment (wave 34): one validation wave, then ordered writes, on the submission write doors

POST /api/v1/events/:eventId/submissions (src/routes/api/submissions.ts:279-327) and PATCH /api/v1/submissions/:id (:360-456) each serialize parseTrackIdsField, parseFormatField and parseAudienceLevelField — and PATCH additionally getSubmissionContent (:412) — four independent reads, none consuming another's result, all behind an authz gate that has already resolved. SPEC §7 budgets writes at p95 < 100 ms and these are J3's two most-used organizer writes. RULE: those validators issue as ONE wave after the ownership/event check and BEFORE the first write; each stays conditional on its body field being present (an absent field still costs zero statements). Every write keeps its exact current order and stays sequential — createSubmission/updateSubmissionFields, replaceSubmissionTracks, writeRoleAnswer x2, appendSubmissionRevision, bumpIcsSequences, and the closing getSubmissionDetail — so DEC-019's atomic-or-nothing shape is untouched. CRITICAL: today the validators throw in source order (a request with both a bad trackId and a bad format sees the trackIds error). Promise.all would reject with whichever settles first, silently changing user-facing error copy; the wave therefore uses Promise.allSettled and re-throws the first rejection in DECLARATION order (trackIds, format, audienceLevel, then getSubmissionContent). Error messages, field keys and status codes are byte-identical.


## Amendment (wave 10, sha e770146d): the trackIds SET boundary has ONE owner, not one copy per route file

DEC-598's own comment in submit-body.ts:71-74 says "trackIds are a SET at every boundary", yet portal/edit.tsx:111-116 carries a private byte-near-identical `extractTrackIds` WITHOUT the dedupe, and only an incidental `new Set(...)` at its single call site currently prevents duplicate submission_track primary-key inserts. A duplicated predicate whose two copies already disagree is the exact bug class the repo's "ONE owner" rule exists to stop (DEC-073/DEC-248 family). RULING: the portal copy is deleted and both doors call the one deduping extractor. A second copy of an authz/integrity predicate is never justified by file locality.
