# DEC-916: A per-row count rides its own list's envelope, computed by one grouped query -- never one request per row

TracksRoomsPanel.tsx:74-80 loads the tracks list and then fans out one bounded /events/:id/submissions?trackId=<id>&perPage=1 read PER TRACK inside a Promise.all, purely to print '<N> submissions' beside each name. That is the exact shape DEC-913 just narrowed for the content tab strip and DEC-902 for the files-library kind chips, and it is SPEC section 7's stated bar ('one round trip per view: each screen's data loads in a single joined query/endpoint -- no client-side request waterfalls'). A Promise.all does not make N scans one scan. Rule: GET /events/:eventId/tracks returns submissionCount on each item, computed by ONE grouped aggregate inside listTracksForEvent (src/server/repo/events.ts:254) over schema.submissionTrack joined to schema.submission scoped to the event; the envelope stays the product's one list shape {items,total,page,perPage}; the client issues zero count requests. The grouped query must reproduce the arithmetic the submissions list's own trackId predicate produces, so the number Settings prints and the number the Submissions list prints for the same track cannot drift -- read that predicate before writing the aggregate rather than inventing a second definition of 'submissions in a track'.
