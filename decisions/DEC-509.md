# DEC-509: An evaluation plan's numeric fields are validated at the route on BOTH POST and PATCH; a bad value is a 400, never a silent coercion and never an uncast bind

Verified at file:line. src/routes/review/plans.ts:90-91 and :98 coerce with `typeof body.X === 'number' ? body.X : null`, so `openDate: '2027-01-05'` silently becomes null (the plan opens immediately, no error surfaced to the producer) and `maxEvaluations: 0` or `-2` or `1.5` is stored verbatim. Lines :169-170 and :177 on PATCH have NO type check at all — `body.maxEvaluations as number` binds whatever arrived, including a string or an object. Consequence is not cosmetic: max_evaluations = 0 makes `needsMoreRatings` (src/domain/evaluation.ts:354-360) return false for every item, so src/routes/review/reviewer.ts:109 filters every reviewer's queue down to items they already rated and :215 refuses every rating submit — J4's review round dies with an empty screen and no message. The plan's own SPA validator already states the contract the server does not enforce (app/src/pages/review/planForm.ts:58-61, 'Max evaluations must be at least 1, if set'), which is the DEC-505 family exactly: a rule the UI asserts and the server ignores. The repo already has the right pattern one function away — parseRounds (src/routes/review/shared.ts:154-165) rejects a non-integer or < 1 with a field error — so the fix is two sibling parsers in that same shared module (parseMaxEvaluations, parseEpochMs) used by both handlers, not per-handler inline checks that would drift. Alternative rejected: clamping a bad value to a default, which hides producer error and violates fail-loudly.
