# DEC-160: CNT-14 bulk ZIP export: pure-TS STORE-only ZIP builder in src/lib/zip.ts plus POST /events/:eventId/files/archive returning latest versions, folder-per-session naming, hard cap 50

CNT-14 needs multi-select bulk download of latest file versions with a generation confirmation ('download start' passes). A STORE-method (no compression) ZIP is ~100 lines of pure TypeScript — local file headers, CRC-32 table, central directory, EOCD — so src/lib/zip.ts stays pure-core per DEC-002 (no node:/cloudflare imports, Uint8Array in/out) with `buildZip(entries: {name: string, data: Uint8Array}[]): Uint8Array` that throws on empty input or duplicate entry names (fail loudly). Endpoint: POST /api/v1/events/:eventId/files/archive (organizer, csrfJson) with {fileIds: string[]} (1-50; every id must resolve to a deliverable in that event or the whole request 404s — no silent skips); each id resolves to its chain's LATEST version, bytes read from R2, response application/zip with Content-Disposition attachment. Entry names are '<seq>-<slugified submission title>/<filename>' — the folder-per-session grouping the rubric counts as bonus evidence and a collision-free namespace (residual collisions throw). Cap and store-only keep worst-case memory bounded on the local Workers runtime.

## Amendment (wave 49)

The archive's R2 reads are one parallel wave, not a queue. src/routes/files.ts:372-381 issues up to MAX_ARCHIVE_FILES (50) SEQUENTIAL `store.get` calls on a user-visible "Download all". The memory ceiling is already enforced BEFORE the first GET (DEC-353's arithmetic at :331-367, ARCHIVE_MAX_TOTAL_BYTES = 20 MB, ARCHIVE_PEAK_MULTIPLIER = 4), and zip entry order is fixed by request order independently of completion order, so a concurrent fetch changes neither the output bytes nor peak memory — it only removes ~50 round trips. Determinism must be preserved: a missing object still 404s loudly naming the file, and when several fail the reported one is the FIRST in request order, not whichever rejected first.

## Amendment (wave 24)

ZIP entry names are UTF-8-flagged (general-purpose bit 11) and carry exactly the path separators the builder put there. src/lib/zip.ts encodes every entry name with `utf8.encode(entry.name)` but writes a general-purpose bit flag of 0 in both the local file header (line 151) and the central directory (line 170). APPNOTE 4.4.4 is explicit: with bit 11 clear the name MUST be interpreted as IBM CP437, so Windows Explorer, macOS Archive Utility and 7-Zip all mojibake any non-ASCII entry name — and the archive's entry names are built from a session title plus the speaker's own uploaded filename (src/routes/files.ts:409), both routinely non-ASCII. The bytes we write are already UTF-8; only the flag that declares them is missing, so this is a two-line correctness fix, not a format change. Separately, the raw `latest.filename` is joined into the entry PATH, so a filename containing `/`, `\` or `..` (an API client sets file.name freely) writes traversing or extra-nested entries into an archive an organizer unpacks. Ruling: always set 0x0800 in both records, and derive the entry path through one exported helper that sanitizes each segment (C0 controls, `/`, `\`, `.`/`..` collapse) and joins with the single separator the builder intends — the seq-prefixed folder stays the only `/`.

## Amendment (wave 65): "all" is honest only when the shown set IS the whole filtered set — a page-scoped bulk action names the page, and the event's total is the only number allowed to say "all"

The wave-26 amendment already ruled that the files library's bulk control is scoped to the rows it is showing and that its label "states its own scope … and never lies about what it will produce". Measured at the file, the label breaks its own ruling as soon as the library pages: app/src/pages/content/FilesLibrary.tsx:27 sets PER_PAGE = 50 and :186 renders `Download all ${items.length} (.zip)` from the CURRENT PAGE, while :167 renders `${countOf(total,'file')} · ${formatBytes(totalSizeBytes)}` from the FILTERED TOTAL. On an event with 120 files the header says "120 files" and the button eight pixels to its right says "Download all 50" — two counts, two scopes, one row, and the word that reconciles them is false. ARCHIVE_MAX_FILES is also 50, so `overCap` (items.length > 50) can never fire on a full page: the disabled-with-a-reason escape the wave-26 ruling relies on is unreachable in exactly the case that needs it. Decision: the word "all" is reserved for the case where the rendered set is the whole filtered set (items.length === total). When the library is showing a page of a larger filtered set the control names its true scope instead of claiming the event's — label the shown count without the word "all", and carry one quiet meta line stating how many of the filtered total are not in this download and that narrowing the search or the type chip changes what it produces. The header's total stays the only "all" on the row. Derive both strings from the ONE envelope the table already renders from (items/total), never a second fetch, and keep the existing cap-derived disable path intact.

## Amendment (wave 53, context)

CNT-14 is the single largest uncovered eval item (~1.0 coverage) and the mandate asks for a ruling before building. The skip list forbids the Sessionboard per-file-share-links + ZIP-GROUPING DIALOG; it does not forbid bulk download, and POST /events/:eventId/files/archive already exists (src/routes/files.ts:362, MAX_ARCHIVE_FILES 50, ARCHIVE_MAX_TOTAL_BYTES 20 MB, folder-per-session naming). Ruling: restore a single bordered-secondary 'Download all' on the files-library header block — NOT in the table's text flow, NOT a per-row share link, and with NO options dialog of any kind. Its scope is exactly the rows the library is currently showing (the active kind filter + search + page), so the control's label states its own scope ("Download all 23 (.zip)") and never lies about what it will produce. When the visible set exceeds the caps the control stays visible and DISABLED with a message naming the real limit ("50 files or 20 MB at a time — narrow the filter"), because a hidden control teaches nothing; a disabled one with a reason teaches the way out. This supersedes the DEC-901 amendment that removed the header control from FilesLibrary — that removal was a fidelity call made before the eval coverage was known, and the gate-4 P2 batch independently asks for it back.

## Amendment (wave 53): the archive's two caps live in pure core, not in the route and again in the library

The bulk-ZIP caps are declared three times: MAX_ARCHIVE_FILES=50 (module-private, src/routes/files.ts:357), ARCHIVE_MAX_TOTAL_BYTES=20MB (exported from the same Hono-importing module, :372), and hand-copied again in app/src/pages/content/FilesLibrary.tsx:33-35 together with a hand-written sentence '50 files or 20 MB at a time'. The library's whole purpose for holding them is to disable the control with a TRUE reason before posting, so a drift between the two makes the control either block a legal download or promise one the server refuses. Under DEC-660's generalized rule both caps (and the derivation constants DEC-353 reasons about) move to src/domain/files.ts; the route imports them, the library imports them and DERIVES its cap sentence from them. Also settles the file's own contradiction: FilesLibrary's header comment claims 'no bulk ZIP control here … exactly one caller' while line 185 renders 'Download all N (.zip)'.
