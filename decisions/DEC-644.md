# DEC-644: The perf harness measures a PROFILE — the same one the seeder built — and the one bar the scale mandate says to verify becomes a timed check

DEC-619 made scale a profile threaded through the seeder rather than a second seeder, but the measuring end never got the same treatment: scripts/perf-smoke.ts imports PERF_EVENT_ID/PERF_EVENT_SLUG (the `default` 2k event) as literals, so scale-mandate's "all measured against the aie profile" is unmeasurable and `npm run perf:seed:aie` seeds an event nothing ever times. Same rule, other end of the pipe: one `--profile=` flag resolving through PERF_PROFILES. And contacts/duplicates — the one bar the mandate explicitly says to "verify, don't assume" — becomes a timed read check rather than an assumption about O(n) hashing.

## Amendment (wave 46): the perf harness must populate every SPEC §7 budget class it claims to grade — one rating PUT is not the write column

scripts/perf-smoke.ts declares fourteen `cls: "read"`/`"public"` checks and exactly ONE `cls: "write"` (the reviewer rating PUT, itself default-profile-only, so on non-default profiles the write column is empty). SPEC §7 states a write budget of p95 < 100ms and calls a route over budget a bug rather than a tuning opportunity — a board with one populated column proves nothing about that budget, and it is not an accident that the two serial-KV fan-out defects this wave fixes lived on write paths the harness never timed. Decision: the harness grows write-class checks over the paths whose cost is structural rather than incidental — a contact bulk-email send fanned out across a real recipient set, a task reminder fan-out, a submission PATCH and a pipeline stage move — and test/perf-smoke.test.ts enforces the shape by scanning the harness source: at least four `cls: "write"` checks, each named path present, and at least one write check that runs on every profile (not default-only). The class taxonomy is the harness's own claim about what it verifies; a class with one member is a claim it cannot support.

## Amendment (wave 31): the plan and reviewer fixtures are profile-resolved like every other one — DEFAULT_ONLY_CHECK_NAMES is deleted, not extended

DEC-644's whole point is that "the perf harness measures a PROFILE — the same one the seeder built." The seeder side finished the job: `PERF_PROFILES` in scripts/perf-seed-lib.ts threads `planId`, `reviewerEmailPrefix` and `reviewerPassword` per profile (the aie profile has its own at :106-110), and `perfReviewerEmail(i, prefix)` / the per-profile plan-id helper already exist. The measuring side did not: scripts/perf-smoke.ts:72-73 still hardcodes `PERF_PLAN_ID = "seed_perf_plan_0001"` and `PERF_REVIEWER_EMAIL = "perf.reviewer.1@example-perf.test"`, and its own comment at :67-71 records the consequence and names the owner — "DEC-645's lane is expected to make these profile-resolved." That lane never landed, so `DEFAULT_ONLY_CHECK_NAMES` (:945-950) silently removes four checks — plan progress, rating PUT, reviewer queue, plan results — from every non-default run, which is to say the entire review subsystem is unmeasured at the only scale the mandate says to measure it at. RULING: both literals resolve through the already-resolved `PERF_PROFILE`, the `isDefaultProfile` gate and `DEFAULT_ONLY_CHECK_NAMES` are DELETED (house rule: no compatibility shims), and `test/perf-smoke.test.ts` grows a scan asserting no check name is excluded by profile. Two boundaries a worker must not cross: the default profile's resolved values must remain byte-identical to today's literals, and any newly-observable aie overrun is a LOGGED FINDING naming its owning route per DEC-347 clause (3), never an OPEN ITEM and never a reason for this lane to fail.

## Amendment (wave 32): an organizer-routine endpoint whose cost scales with plan size must have a perf-smoke row, and a NEW row that fails is a finding, not a reason to omit it

DEC-644's wave-31 amendment established that a harness which skips a check measures nothing. The dual is unclosed: a harness which never had a check measures nothing either, silently. `GET /api/v1/plans/:id/progress` and `GET /api/v1/plans/:id/reviewers` both scale with the plan's whole submission population and are the two tabs an organizer lives in while chasing a review round, and neither has ever appeared in the 27-row perf table (verified against the w28-c verbatim receipt). SPEC §7 is explicit that 'budgets that aren't enforced are decoration'. RULING: add both as `read`-class rows, skipped under a non-default profile by the same DEC-644/645 mechanism as the existing plan/reviewer rows, each asserting a 200 with a non-empty payload so a silently-empty answer cannot pass as fast. The lane that adds a row does NOT get to fix the route it exposes — it records the number and the file:line, so the finding is owned by a later lane rather than laundered into the same commit.
