# DEC-644: The perf harness measures a PROFILE — the same one the seeder built — and the one bar the scale mandate says to verify becomes a timed check

DEC-619 made scale a profile threaded through the seeder rather than a second seeder, but the measuring end never got the same treatment: scripts/perf-smoke.ts imports PERF_EVENT_ID/PERF_EVENT_SLUG (the `default` 2k event) as literals, so scale-mandate's "all measured against the aie profile" is unmeasurable and `npm run perf:seed:aie` seeds an event nothing ever times. Same rule, other end of the pipe: one `--profile=` flag resolving through PERF_PROFILES. And contacts/duplicates — the one bar the mandate explicitly says to "verify, don't assume" — becomes a timed read check rather than an assumption about O(n) hashing.

## Amendment (wave 46): the perf harness must populate every SPEC §7 budget class it claims to grade — one rating PUT is not the write column

scripts/perf-smoke.ts declares fourteen `cls: "read"`/`"public"` checks and exactly ONE `cls: "write"` (the reviewer rating PUT, itself default-profile-only, so on non-default profiles the write column is empty). SPEC §7 states a write budget of p95 < 100ms and calls a route over budget a bug rather than a tuning opportunity — a board with one populated column proves nothing about that budget, and it is not an accident that the two serial-KV fan-out defects this wave fixes lived on write paths the harness never timed. Decision: the harness grows write-class checks over the paths whose cost is structural rather than incidental — a contact bulk-email send fanned out across a real recipient set, a task reminder fan-out, a submission PATCH and a pipeline stage move — and test/perf-smoke.test.ts enforces the shape by scanning the harness source: at least four `cls: "write"` checks, each named path present, and at least one write check that runs on every profile (not default-only). The class taxonomy is the harness's own claim about what it verifies; a class with one member is a claim it cannot support.

## Amendment (wave 31): the plan and reviewer fixtures are profile-resolved like every other one — DEFAULT_ONLY_CHECK_NAMES is deleted, not extended

DEC-644's whole point is that "the perf harness measures a PROFILE — the same one the seeder built." The seeder side finished the job: `PERF_PROFILES` in scripts/perf-seed-lib.ts threads `planId`, `reviewerEmailPrefix` and `reviewerPassword` per profile (the aie profile has its own at :106-110), and `perfReviewerEmail(i, prefix)` / the per-profile plan-id helper already exist. The measuring side did not: scripts/perf-smoke.ts:72-73 still hardcodes `PERF_PLAN_ID = "seed_perf_plan_0001"` and `PERF_REVIEWER_EMAIL = "perf.reviewer.1@example-perf.test"`, and its own comment at :67-71 records the consequence and names the owner — "DEC-645's lane is expected to make these profile-resolved." That lane never landed, so `DEFAULT_ONLY_CHECK_NAMES` (:945-950) silently removes four checks — plan progress, rating PUT, reviewer queue, plan results — from every non-default run, which is to say the entire review subsystem is unmeasured at the only scale the mandate says to measure it at. RULING: both literals resolve through the already-resolved `PERF_PROFILE`, the `isDefaultProfile` gate and `DEFAULT_ONLY_CHECK_NAMES` are DELETED (house rule: no compatibility shims), and `test/perf-smoke.test.ts` grows a scan asserting no check name is excluded by profile. Two boundaries a worker must not cross: the default profile's resolved values must remain byte-identical to today's literals, and any newly-observable aie overrun is a LOGGED FINDING naming its owning route per DEC-347 clause (3), never an OPEN ITEM and never a reason for this lane to fail.

## Amendment (wave 32): an organizer-routine endpoint whose cost scales with plan size must have a perf-smoke row, and a NEW row that fails is a finding, not a reason to omit it

DEC-644's wave-31 amendment established that a harness which skips a check measures nothing. The dual is unclosed: a harness which never had a check measures nothing either, silently. `GET /api/v1/plans/:id/progress` and `GET /api/v1/plans/:id/reviewers` both scale with the plan's whole submission population and are the two tabs an organizer lives in while chasing a review round, and neither has ever appeared in the 27-row perf table (verified against the w28-c verbatim receipt). SPEC §7 is explicit that 'budgets that aren't enforced are decoration'. RULING: add both as `read`-class rows, skipped under a non-default profile by the same DEC-644/645 mechanism as the existing plan/reviewer rows, each asserting a 200 with a non-empty payload so a silently-empty answer cannot pass as fast. The lane that adds a row does NOT get to fix the route it exposes — it records the number and the file:line, so the finding is owned by a later lane rather than laundered into the same commit.

## Amendment (wave 35): a branch-local PASS is not a closure — a perf row closes only on a reading taken at a boundary carrying every fix credited with closing it

Measured, not inherited: `task-w32-a` recorded `plan results (page 1)` raw 44.8ms / adj 39.0ms PASS (docs/verification-log.md:4590-4596) in a run where `reviewer queue` still FAILed and `src/routes/review/reviewer.ts` was untouched; `task-w32-b` recorded `reviewer queue` 48.7/32.2/38.9ms adj PASS (docs/verification-log.md:4625-4634) in a run where `plan results (page 1)` still FAILed at 72.9/50.3/57.3ms and `src/routes/review/shared.ts` was untouched. Each lane's own receipt names the other row as "pre-existing, out-of-scope". So the tree has two PASS readings and zero readings of the tree that actually shipped — both fixes rewrote the same review read path's wave structure, and a scheduling change measured with its sibling absent measures a different program. DEC-069 already voids a gate section on any later code merge; this extends the same rule one level down, to the individual perf row: a TIER-0 row moves out of FAIL only on a reading taken at a boundary that contains every fix credited with closing it, and the receipt names that boundary's sha. The corollary binds the render sweep identically — `task-w29-c`'s `.chq-cfp-step-next` focus PASS and `task-w29-d`'s `.chq-participation-menu-caret` contrast PASS were likewise never observed in one run.

## Amendment (wave 37): the three-sha receipt block is GENERATED from .git, not hand-derived — a hand-derived block is a defect in the receipt

DEC-644's wave-36 amendment requires every receipt to name three shas: HEAD, the newest product-code-bearing first-parent sha, and a `merge-base --is-ancestor` verdict per live sibling ref. task-w35-a's perf reading was voided because its author took boundary state from a brief instead of from .git; task-w36-b derived the block correctly but paid real time for it, and its correctness is unverifiable by anything but a re-derivation. The triple is a pure function of .git plus the product globs (src/, app/src/, migrations/, package.json), so it should be computed by scripts/ref-state.ts and pasted. Two traps the tool must encode rather than leave to prose: .git/packed-refs can carry a stale refs/heads/main that the loose ref overrides, and globbing .git/refs/heads misses packed refs entirely — so refs are read through git, never off the filesystem.

## Amendment (wave 36): a gate receipt names THREE shas — its HEAD, the newest product-code-bearing first-parent sha, and an ancestry verdict for every live sibling ref

DEC-644's wave-35 amendment ruled that a perf row closes only at a boundary carrying every fix credited with closing it, and its own examples (w32-a measured plan results with reviewer.ts unfixed; w32-b measured reviewer queue with shared.ts unfixed) were only discoverable because someone re-derived ref state by hand. The same hole is open again this wave: `task-w35-a`'s perf reading was taken at a0b8501b, which predates `task-w35-c`'s src fix and `task-w35-d`'s three new /portal perf rows, and its receipt header cannot say so because the receipt format records one sha. RULING: every gate section this wave carries, in its body, (1) the full HEAD sha of the worktree it measured, (2) `git log --first-parent -1 --format=%H -- src/ app/src/ migrations/ package.json` — the sha the reading is INVALIDATED BY, and (3) one line per live `task-w3*` ref quoting `git merge-base --is-ancestor <ref> HEAD` as ANCESTOR/NOT-ANCESTOR. A row is graded closed only when the fixes credited with closing it are proven ancestors by (3); otherwise it is recorded as MEASURED-WITHOUT(<ref>) and stays open. This makes the boundary a property of the receipt rather than of a later archaeologist.

## Amendment (wave 39): a perf timing runs under a dedicated measurement lock, and a fix lane never produces its own closing measurement

`task-w35-a` measured `reviewer queue` at adjusted 46.4/44.0/45.1ms and `task-w36-c` measured the SAME handler with the SAME credited fix set at 51.5/34.1/55.3ms (`docs/verification-log/task-w36-c-perf-smoke-f5783479.md:274-289`) — a ~60% swing that is machine load, not code, because 4-6 worker agents share one laptop. Two consequences. (a) Every perf timing run executes under a dedicated lock: `CHQ_TEST_LOCK_DIR=/tmp/chq-perf.lock sh scripts/with-test-lock.sh <perf command>` (`scripts/with-test-lock.sh` already takes LOCK_DIR from that env var), so no two lanes ever time the tree simultaneously; a reading taken without the lock is not a closure. (b) Applying DEC-453 and DEC-644's own wave-35 "a branch-local PASS is not a closure" rule: the lanes that FIX the two review handlers do not produce the closing perf reading — their landing evidence is a statement-count regression test in the unit suite (falsifiable in CI, which is what SPEC §7's "budgets that aren't enforced are decoration" actually asks for), and the closing timing is taken by wave 40's perf-smoke gate lane at the merged boundary containing BOTH fixes. This is why neither review-perf lane is chained behind the harness-repair lane.

## Amendment (wave 40): one machine, one heavy gate — every heavy gate phase runs inside a single acquisition of the DEFAULT test lock, and never nests npm test

DEC-644's wave-39 amendment established that a reading taken under load is not a reading: the same handler with the same fix set read 46/44/45ms at one moment and 51/34/55ms at another, purely because sibling agents were compiling. A perf lane that takes its own lock while three sibling gate lanes run a 1084-file suite, a Playwright sweep and a walkthrough on the same box measures the swarm, not the product — and a lock keyed on a different directory excludes nobody. RULING: every wave-40 phase that compiles, tests, boots a server, or times anything runs as `sh scripts/with-test-lock.sh sh -c '<block>'` against the DEFAULT lock dir (/tmp/chq-test.lock, scripts/with-test-lock.sh:16) — build+test+bundle, walkthrough, perf-smoke, render-sweep and the spec-audit's own bundle:check build. That serializes the battery against itself AND against the merge train's own `npm test`, which is the point: the wall-clock cost is the price of a reading anybody can cite. Corollary, stated because it is a real deadlock and not a style note: `npm test` and `npm run test:full` are themselves `sh scripts/with-test-lock.sh vitest run` (package.json:27,29), so putting either INSIDE the wrapper makes the inner acquire spin forever on a lock the outer already holds — the build+test lane runs `npx vitest run` inside the wrapper instead. The lock steals itself after 45 minutes (STALE_MINUTES), so any single wrapped block must stay under that.
