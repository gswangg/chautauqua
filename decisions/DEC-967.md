# DEC-967: A send is irreversible, so it asks once and names what it is about to do

app/src/pages/comms/ComposeWizard.tsx's send() (:297) POSTs /events/:id/compose/send straight from a button click: up to 100 real emails leave on one unguarded click, with no statement of how many or to what subject. Every other irreversible act in this product already asks — DEC-631 replaced window.confirm with the shared ConfirmDialog, DEC-713's version delete confirms, and the field guide records that 'a delete with no dialog is five deletes with no dialog'. A send is worse than a delete: it cannot be undone even in principle, it reaches people outside the org, and the wizard's own preview step is a rendering, not an acknowledgement. The Comms frame draws the confirm step for exactly this reason. Rule: the preview step's Send opens the shared ConfirmDialog (app/src/components/ConfirmDialog.tsx — NOT a hand-built scrim, DEC-651/DEC-960) titled 'Send this email?', whose body states the recipient count and the resolved subject and whose confirm label counts what will go ('Send 11 emails', via countOf); the POST fires only on confirm, Cancel returns to the preview with nothing sent, and the dialog carries `pending` while the request is in flight. The same guard applies to the Contacts bulk-email send (BulkEmailModal.tsx), because two send paths with one policy must not have two behaviours. The existing hard blocks are unchanged: a send blocked on unscheduled ICS recipients stays disabled and never reaches the dialog.
