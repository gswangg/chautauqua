# DEC-967: A send is irreversible, so it asks once and names what it is about to do

app/src/pages/comms/ComposeWizard.tsx's send() (:297) POSTs /events/:id/compose/send straight from a button click: up to 100 real emails leave on one unguarded click, with no statement of how many or to what subject. Every other irreversible act in this product already asks — DEC-631 replaced window.confirm with the shared ConfirmDialog, DEC-713's version delete confirms, and the field guide records that 'a delete with no dialog is five deletes with no dialog'. A send is worse than a delete: it cannot be undone even in principle, it reaches people outside the org, and the wizard's own preview step is a rendering, not an acknowledgement. The Comms frame draws the confirm step for exactly this reason. Rule: the preview step's Send opens the shared ConfirmDialog (app/src/components/ConfirmDialog.tsx — NOT a hand-built scrim, DEC-651/DEC-960) titled 'Send this email?', whose body states the recipient count and the resolved subject and whose confirm label counts what will go ('Send 11 emails', via countOf); the POST fires only on confirm, Cancel returns to the preview with nothing sent, and the dialog carries `pending` while the request is in flight. The same guard applies to the Contacts bulk-email send (BulkEmailModal.tsx), because two send paths with one policy must not have two behaviours. The existing hard blocks are unchanged: a send blocked on unscheduled ICS recipients stays disabled and never reaches the dialog.

## Amendment (wave 25)

**Send lives at step 4, the confirm dialog is deleted, and step 4 is a report about recipients**

Ruling B1 (highest-leverage owed frame, now delivered). The four-step rail is the only navigation and every step's primary is the NEXT step, so the preview step's primary becomes "Next: send". Step 4 pre-send REPLACES the ConfirmDialog rather than adding to it — DEC-967's principle (a batch asks once before it leaves) is better served by a full screen that names who is about to be mailed than by a modal, and click depth is unchanged (Next+Send replaces Send+Confirm). Post-send the same step is a REPORT ABOUT THE ORGANISER'S RECIPIENTS, not a copy of the email: it leads with the audience ("21 of 23 speakers were emailed"), states template / resolved subject / when / from address as metadata, and NAMES each failed and each pre-flight-excluded recipient with its reason. It names only what the app actually knows — the failed[] rows the send envelope already returns and the exclusions the wizard already computes (no slot, unresolvable merge field). It does NOT invent a retry clock or a skipped-name list: compose/send returns skipped: 0 on this path, and a fabricated field is worse than a missing one. Step 1 gains the seam line: the selection survives filter changes and says so, with the recipient cap named.

## Amendment (findings wave 8): a decided selection travels to Comms, and the wizard opens at the first step whose input is not already supplied

SPEC J5 states the notify act as one motion: 'select decided records -> compose from a template with merge fields -> per-recipient preview -> send'. On main the first arrow does not exist. app/src/pages/submissions/BulkActionBar.tsx offers three status moves and Clear; SubmissionDetailPage.tsx:1643 says 'Deciding sends nothing. Notify from Comms.' as prose with no link. An organizer who has just ticked and accepted 23 rows must navigate to Comms, re-filter to accepted, and re-tick the same 23 — the product asks for the selection twice and keeps no memory of the first. The same defect is what eval-findings Tier 1 item 2 measures as the compose-flow turn diet: CFP-S4 step 3 asks for TWO sends (accepted and declined) and the scenario runs out of budget before the close-the-call steps, taking CFP-04 and CFP-16 to cannot_judge. A second, smaller bug sits in the same seam: the ?template= landing effect (ComposeWizard.tsx:147-159) jumps to step 2 with an EMPTY step 1, so the organizer's first act on arrival is to go backwards. RULING: (a) the submissions bulk bar carries a router Link 'Email these N' to /comms?tab=compose&ids=<ids> (basename-relative — the router's basename is already /admin, DEC-834/DEC-837 — never an <a href>, which reloads the SPA); when the selection exceeds MAX_COMPOSE_RECIPIENTS the bar states 'first 100 of N · a send is capped at 100' and carries the first 100 in the selection's stable order, because a silently truncated handoff is a lie about who will be emailed. (b) ComposeWizard hydrates that bounded id list into its existing selection reducer once per mount and then applies ONE landing rule — open at the first step whose input is not already supplied: no selection -> step 1; a selection -> step 2, whether or not a ?template= came with it. Ruling B1 is unharmed: the four-step rail is still the only navigation and every step's primary is still the next step; a step whose input arrived with the request is complete, not skipped. This never widens what a send may reach — the server still validates every submissionId against the caller's event and still applies the 100 cap.

## Amendment (findings wave 11): the receiving side of the DECIDE->NOTIFY handoff states its own truncation

BulkActionBar caps the `?ids=` link at MAX_COMPOSE_RECIPIENTS and states the over-cap case in its own sentence — on the submissions page. ComposeWizard then re-applies the same cap on arrival and drops malformed entries silently before jumping to step 2. For the bulk-bar path that is merely redundant; for every other arrival — a bookmarked, typed, or shared /comms?tab=compose&ids=..., or the same link re-opened after the selection grew — the organiser composes an irreversible send against a quietly shortened audience with no sentence anywhere on screen. A constraint stated on the page you came FROM is not stated on the page you act ON. Ruling: the wizard records how many ids arrived and how many it kept, and renders one muted line in the step-2 header when they differ, naming kept, arrived and the cap. Nothing renders when they agree, the landing-step rule is unchanged, and the cap itself is untouched — this is a disclosure, not a new policy.
