# DEC-037: Email HTML built only via escapeHtml/textToHtml in src/mail/render.ts

Five send sites interpolate user- or producer-controlled text into HTML bodies raw (comms.ts:259, api/contacts.ts:411, public/submit.tsx:398, review.ts:309, repo/tasks.ts:498); the dev-mailbox iframe sandbox masks it in stage 1 but the stored body_html is delivered verbatim once the Resend adapter lands. Canon: src/mail/render.ts exports escapeHtml(s) (escapes & < > " ') and textToHtml(text) (escape, then blank-line-separated <p> blocks with <br/> for single newlines). Every mailer.send html field is built from these; renderTemplate must never be called with an HTML template whose vars carry user content. Anchors are built by callers with both href and text escaped.

## Amendment (wave 24)

HTML is the sixth wire format, and it gets one escaper owner (src/lib/html-escape.ts) like the other five. Wave 23 pinned ICS, MIME, XML, CSV and Markdown-to-HTML to one serializer each. HTML escaping — the output language every one of those five ultimately shares a page with — has THREE definitions: src/mail/render.ts:155 (escapeHtml, the DEC-037 sanctioned one), src/lib/markdown.ts:16 and src/server/http.ts:209 (escapeHtmlText). They are byte-identical today, which is exactly the state that precedes drift: the field guide already records SECOND READER INHERITS NO MANNERS and HAND-TYPED LIST FORGETS 3RD MEMBER, and this codebase has twice shipped a security-relevant escaping rule to one copy and not its siblings. All three feed dangerouslySetInnerHTML or a raw HTML string, so a future rule (stripping C0 controls, escaping backtick) applied to one copy and not the others is a live hole. Ruling: one pure owner at src/lib/html-escape.ts; mail/render.ts keeps textToHtml and becomes a consumer; DEC-037's 'only sanctioned path' clause now names the owner, not the mail module. No compatibility re-export (house rule) — the two importers of escapeHtml-from-mail/render move. src/routes/public/feeds.ts's escapeXml stays separate and ledgered: different entity set (&apos;) plus XML 1.0's control-byte stripping.


## Amendment (wave 27): every outbound HTML body is wrapped by ONE email shell

DEC-037 made escapeHtml/textToHtml the only path from text to email HTML; seven send sites now pass its bare `<p>` output straight to mailer.send, so the product's receipts of record have no wordmark, no measure, no footer and no statement of why the recipient got them. Ruling B9 specifies one shell: 560px centred, 16/1.6 body, at most one olive button, a text wordmark, and a footer naming the event and the reason. It lands as a single `renderEmailHtml` in src/mail/shell.ts that CALLS textToHtml for the body, so the escaping contract is unchanged and undelegated. Email clients do not resolve CSS custom properties, so this file is the one sanctioned place in the repo where colour literals appear outside a token block -- the surface-CSS no-literal rule does not reach it.

## Amendment (wave 34): the B9 shell sweep is a closed set over the real send sites, and the CFP confirmation is inside it

The B9 amendment claimed every outbound HTML body renders through renderEmailHtml, and test/email-shell-sweep.scan.test.ts claims to enumerate the send sites so a new one cannot silently skip the shell. Neither holds: src/routes/public/submit.tsx hand-assembles the CFP confirmation body (the one email every submitter receives, shipping with no wordmark, no event name and no reason line), src/routes/auth-reset.tsx is unlisted, and the scan's final test asserts the identical thing in both branches, so it enumerates nothing. The rule is restated as an equality: the set of files under src/ that call mailer.send with an html property must EQUAL SWEPT_SITES, each with its expected renderEmailHtml count. The shell itself is unchanged - deviations are content, not styling.

## Amendment (wave 49): the compose preview renders the SAME artifact the send delivers — one shell call, one options builder

src/routes/comms/send.ts:140 wraps every outbound body in renderEmailHtml with a specific eventName + reason; src/routes/comms/preview.ts:62 returns bare `text`, and PreviewPane prints it in a <pre>. So step 3 shows the organiser something no recipient will ever receive, on the one screen whose whole job is 'this is what we are about to send' — and the reason clause exists in exactly one place, meaning nothing pins the two together. Ruling: the shell options are built by ONE exported helper in src/routes/comms/compose-core.ts called by BOTH preview and send, and the preview item carries the rendered `html`. The SPA renders it in a fully sandboxed iframe (sandbox="", srcDoc) — mail HTML is data, never script, and an iframe is the only container that shows it at true fidelity without letting email CSS into the admin document. No new secret crosses the wire: DEC-397 already forbids the preview from minting credentials, and the html is derived from the text the endpoint already returns.
