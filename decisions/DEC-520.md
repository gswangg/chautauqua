# DEC-520: Auto-created onboarding tasks carry a due date derived from the event start date, because J6's dashboard column and its cron are both due-date-driven

Verified on current main: `src/server/repo/submissions/status.ts:91` inserts `schema.task` with no `dueDate`, and `DEFAULT_ONBOARDING_TASKS` (`src/domain/acceptance.ts:14-20`) carries no due-date field, so every task acceptance auto-creates gets `due_date = NULL` (column at `src/db/schema.ts:447`). Three J6 surfaces then go dead for exactly those rows: `src/domain/reminders.ts:42` short-circuits `if (a.dueDate === null) return false`, so the cron never reminds; `src/server/repo/tasks/grid.ts:83,225` and `src/server/repo/overview.ts:323` both require `due_date is not null` for overdue/at-risk counting; and `app/src/pages/speakers/OnboardingGrid.tsx:303` renders an em dash in the header column SPEC J6 names first ("a per-speaker x per-task status grid -- due dates, filters, live upload state"). It is masked in every demo and eval because `scripts/seed.ts:995` sets `due_date` explicitly on seeded tasks, so the grid and the reminder both look alive. SPEC J6 also says "Automated due-date reminders go out via cron" -- a default task set with no default schedule cannot satisfy that sentence. Decision, so no worker re-decides the shape: (a) `OnboardingTaskTemplate` gains `dueDaysBeforeEventStart: number`, with the canonical values travel-first: hotel form 30, flight form 30, finalize talk description 21, finalize bio + headshot 21, announce participation 14 -- logistics need the most lead time, content next, promotion closest to the show. (b) The due value is a DEC-522 day label: UTC midnight of (event.start_date minus N days), computed by a pure `onboardingTaskDueDate` in `src/domain/acceptance.ts` that throws on a malformed start date rather than defaulting. (c) A computed due date that already lies in the past is left in the past -- a speaker accepted a week before the show genuinely owes those forms now, and the honest overdue flag is the product's answer; no clamping (fail loudly, DEC-517's precedent against hiding producer/timeline reality). (d) The due date is written ONLY on the INSERT branch of `getOrCreateTask`; the find-or-reuse branch never back-fills, because an organizer who cleared a due date via PATCH meant it (unlike DEC-111's formId self-heal, a null due date is a legal organizer choice).
