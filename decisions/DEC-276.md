# DEC-276: Bearer API tokens re-resolve the minting user on every request: existence + role='organizer' + org match, or the token does not authenticate

src/server/middleware.ts:144-159 resolves a chq_ bearer token to `role: "organizer"` as a hard-coded literal read off the api_token row, and never touches the user table. schema.apiToken (src/db/schema.ts:580) has no expiry. So a token minted by an organizer who is subsequently demoted to reviewer, or whose user row is deleted, retains full org-wide read AND write across /api/v1 -- and bearer requests are deliberately CSRF-exempt (middleware.ts:235), so nothing else catches it. SPEC section 6 requires role + grant checks on every API route; a credential whose authority is frozen at mint time is not a role check. Fix is minimal and needs no migration: resolveBearerAuth gains a UserLookup parameter and requires the api_token row, a live user at row.created_by_user_id, user.role === 'organizer' (after assertRole, so a corrupt role literal still throws loudly rather than degrading), and user.orgId === row.orgId. Any failure returns undefined so the request falls through to the normal 401/403 path -- an unauthenticated request, not a 500. I deliberately do NOT add token expiry columns this wave: revocation already exists (DELETE /api/v1/tokens/:id) and a migration would collide with wave 5's 0017.

## Amendment (wave 63): authentication is ONE database round trip, and the last-used stamp is not part of it

DEC-276 requires every bearer request to re-resolve the minting user so a demotion revokes the token immediately; the cookie path likewise re-resolves the user behind the session. Both are implemented as two sequential SELECTs (session→user, api_token→user) in src/server/middleware.ts, so every authenticated request in the product — every SPA API call, every SSR portal page, every admin screen — pays a two-hop waterfall before its handler starts, against SPEC §7's "one round trip per view" and a 50 ms p95 read budget that this tax is subtracted from. The re-resolution rule is preserved exactly; only the number of trips changes: one innerJoin returns the session/token row and its user together, and the pure resolver evaluates the same predicates (unexpired, user exists, role, org match) against the joined row. Separately, the bearer path's `api_token.last_used_at` write is documented as "best-effort ... never gates whether auth is set" and is in fact awaited inline with no catch, so a write failure 500s a read — a comment claiming a property is not that property. The stamp moves off the critical path (waitUntil where available, failure logged, never propagated) and reuses the hash already computed instead of recomputing it.
