# DEC-774: The sessions surface filters on the facets it displays

The EMB probe scored 72% on missing capability, first item: "Sessions facets beyond track (format/location)". src/routes/public/sessions.tsx renders a track filter bar only, while every card already prints the session's format and room -- src/server/repo/public/sessions.ts:442 hydrates `format` and :441 `roomName`. A surface that shows an attribute and refuses to filter on it makes the visitor scroll. Decision: `?format=` and `?roomId=` join `?trackId=`/`?q=`/`?day=` as server-side predicates on getVisibleSubmissionIdsOrdered AND countVisibleSubmissions (never a post-filter over the page -- the count and the list are one query pair), parsed in src/routes/public/query.ts beside parseTrackId, rendered as chips in the existing .chq-pub-filter-bar, and composing with each other and with show-more. Sessions with no slot are excluded when a room filter is active, because "in Room 2A" is a claim about a placement.

## Amendment (wave 34): the public surface's reads are one wave per dependency level, not one await per filter list

DEC-338's "one round trip per view" has a PUBLIC side that no lane has ever owned. renderSurfaceContent (src/routes/public/dispatch.tsx) serializes up to SEVEN independent reads on `sessions` (getPublicTracks :58, getPublicRooms :62, getPublicFormatOptions :63, getPublicSessions :68, the unfiltered grandTotal probe :85, getPublicScheduleDayCounts :90, getPublicCfpWindow :91) — none of which consumes another's result. speakers/gallery serialize two, schedule four. These are the SPEC §7 "uncached SSR < 150 ms" surfaces, and the signed-in organiser pays the full waterfall on EVERY request because publicCacheMiddleware skips the cache for cookie-bearing requests. RULE: within each surface case, every read that does not consume another read's result issues in ONE Promise.all wave. `agenda` keeps exactly TWO waves and no fewer, because effectiveDay is derived from dayCounts (:200-203) and both the agenda rows and the breaks read consume it. `schedule` is ONE wave because its day comes from the query string. A read that is conditional today (grandTotal only when a filter is active; dayCounts/cfpWindow only when !embed, DEC-683's chromeless-closed rule) stays conditional inside the wave — a skipped read is never fetched-then-discarded, and the total statement count must be identical to today's for both the embed and non-embed shapes. Concurrency is proven BEHAVIOURALLY with an instrumented fake Db, never a source grep.

### Amendment (wave 34): landed — collapsed to Promise.all waves per the rule above

Implemented exactly as specified: `sessions` is ONE wave (getPublicTracks, getPublicRooms, getPublicFormatOptions, the filtered getPublicSessions, the grandTotal probe folded in as a ternary — `Promise.resolve(null)` when `!anyFilter` — and getPublicScheduleDayCounts/getPublicCfpWindow folded in as ternaries — `Promise.resolve([])`/`Promise.resolve(null)` when `query.embed`). `speakers`/`gallery` are each ONE wave (getPublicTracks, getPublicSpeakers). `agenda` is exactly TWO waves: wave 1 is `[getPublicTracks, getPublicScheduleDayCounts]`; wave 2 is `[getPublicAgenda(effectiveDay), getPublicBreaksByDay(effectiveDay)]`, gated on wave 1's result for `effectiveDay`. `schedule` is ONE wave: `[getPublicTracks, getPublicAgenda(query.day), maybe getPublicScheduleDayCounts, getPublicBreaksByDay(query.day)]` — the day-switcher read folds in as a ternary on `query.day`. No repo signature changed; src/server/repo/public/* untouched.

GOTCHA for the next lane touching this file (or any dispatch case that wraps a Promise.all around a read whose OWN internal implementation makes several sequential `await db.select()` calls, e.g. getPublicSessions/getPublicAgenda via hydrateSessions): a test fake keyed to a GLOBAL POSITIONAL `db.select()` call counter (`let selectCall = 0; if (selectCall === N) return ...`) is NOT robust to this change, even though the counter still literally counts calls in the order they happen. The reason: JS evaluates a `Promise.all([...])` array's entries strictly left-to-right, and each async function call in that array runs synchronously up to its OWN first `await` before the NEXT array entry is even invoked — so the first `db.select()`/`selectDistinct()` call of every wave member preserves array order. But once the wave's members resume (their earlier-queued microtasks run first), a multi-step callee's SECOND, THIRD, ... internal call now interleaves ONE STEP AT A TIME with any other multi-step callee running concurrently in the same wave (round-robin), and single-call reads that used to run strictly after a multi-step callee's entire cascade (dayCounts/cfpWindow after getPublicSessions, in the old serial code) now land INSIDE the initial synchronous burst, ahead of that cascade's later steps. Concretely: sessions non-embed/no-filter's old order was `event,tracks,rooms,formatOptions,[5 hydrate calls],count,dayCounts,cfpWindow`; the new order is `event,tracks,rooms,formatOptions,dayCounts,cfpWindow,[5 hydrate calls],count` — dayCounts/cfpWindow moved from the tail to slots 5-6. When a filter is active (so the grandTotal probe — a SECOND full getPublicSessions call — also runs), its hydrate cascade interleaves call-for-call with the main call's: main-subRows, grandTotal-subRows, main-trackRows, grandTotal-trackRows, ... This broke 8 pre-existing test files (~30 tests: public.test.ts, public-day-filter, public-feed-window, public-feeds, public-format, public-session-tag-line, public-filter-idiom, public-agenda-rail, public-agenda-schedule-filters, public-embed-config, public-embed-knob-parity, public-w64-c-agenda-track-highlight) whose fakes hard-coded the OLD serial position numbering; all were fixed in place by recomputing the new position (verified empirically with a throwaway instrumented-`from()`-table-logging harness, not hand-simulated) rather than converting them to table-keyed fakes. `getPublicSessions`'s own doc comment ("Sequenced (not Promise.all'd): hydrateSessions' own select() calls stay contiguous right after the id query, matching every existing fake-db harness...") is the tell that this project's positional test fakes are a KNOWN, accepted fragility specifically bounded to a single repo function's OWN internal sequencing — cross-function concurrency at the dispatch level was never covered by that guarantee and remains fair game for reordering.
