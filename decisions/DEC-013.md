# DEC-013: API conventions for /api/v1 and the SPA client contract

The SPA table task and the API tasks are opposite sides of the same wire and run in parallel, so the shapes are fixed here. JSON only; timestamps are ms-epoch numbers matching DEC-003. List endpoints accept ?page (1-based), ?perPage (default 50, max 200 — server-clamped), ?q, plus per-resource filters, and return { items, total, page, perPage }. Errors: non-2xx bodies are { error: { code, message, fields? } } with codes 'unauthorized' (401), 'forbidden' (403), 'not_found' (404), 'invalid' (400, validation details in error.fields as Record<field,message>), 'conflict' (409); unexpected exceptions propagate to a 500 with code 'internal' — fail loudly, no swallowing. Session-authenticated mutations require the x-chq-csrf header (DEC-004); bearer tokens are deferred to the J12 wave (needs an api_token table via DEC-015 discipline). Admin API endpoints are organizer-only by default; reviewer- and speaker-accessible endpoints are explicit, narrower routes. The SPA consumes the API exclusively through app/src/lib/api.ts: fetch with credentials 'include', sets x-chq-csrf on mutations, unwraps the list envelope, and throws a typed ApiError on any error envelope.

## Amendment (wave 54): clampPage has an upper bound — a page param is clamped, never trusted into an offset

clampPage (src/lib/pagination.ts:13-17) enforces only `n >= 1`, so `?page=1e21` passes Number.isInteger and `(page-1)*perPage` reaches `.offset()` on every admin list (views.ts:45, submissions/query.ts:134, email.ts:181, files, comments) as a non-safe-integer float — an unhandled input class that 500s instead of answering. The public side already solved this: parsePage clamps to MAX_PUBLIC_PAGE (src/routes/public/query.ts:26) rather than rejecting, and clampPerPage's own contract is clamp-not-throw. Rule: pagination.ts exports MAX_PAGE and clampPage clamps to it, keeping the pure-core rule (no ApiError import in src/lib) and keeping one shape across public and admin; the invariant the tests assert is that `(clampPage(x)-1)*clampPerPage(y)` is always a safe integer for ANY input.

## Amendment (wave 14) — exactly one API client module in app/src; the duplicate is deleted, not deprecated

The former app/src/api/client.ts (deleted per this decision's own ruling below) was a second fetch wrapper with its OWN ApiError class whose message is 'API request failed with status N' and which carries a raw `body` instead of the {code, message, fields} the whole SPA switches on. It has no production callers — only its own test keeps it alive — so today it is dead code that will read as available to the next worker, and a page that adopts it would silently lose every server-supplied field error and fail every `err instanceof ApiError` check against lib/api.ts's class. The house rule is delete, don't deprecate. Ruling: app/src/lib/api.ts is the only module in app/src that may call fetch() against /api/v1; app/src/api/ is deleted; the one remaining direct fetch (app/src/pages/settings/YourDataPanel.tsx:94) routes through apiGet; and a scan test pins the invariant, allowlisting exactly one non-API fetch — App.tsx's POST /logout, which is not under /api/v1 and cannot use the prefixed helper.

## Amendment (wave 26): 'the org's anchor event' is ONE named, ordered, single-row repo read — never `list(...)[0]`

Two call sites take an org's first event as the anchor for an `email_log.event_id` that is NOT NULL. One is bounded, one is not: `src/routes/api/users.ts:92` pages to `{ limit: 1, offset: 0 }`, but `src/routes/auth-reset.tsx:152` reads `const orgEvents = await listEventsForOrg(db, user.orgId);` with NO page argument and then takes `orgEvents[0]` (:153) — an unbounded org-wide read on the password-reset path to select one row, which is exactly the field guide's UNBOUNDED SURFACE NEVER PAGED shape. Both also depend on an unwritten contract — that `listEventsForOrg`'s default ordering IS the anchor ordering (`src/server/repo/events.ts:76` `.orderBy(desc(schema.event.startDate), asc(schema.event.id));`) — which no test pins, so a future re-order silently changes which event every welcome and reset email is logged against. RULING: `src/server/repo/events.ts` exports `getAnchorEventForOrg(db, orgId): Promise<EventRecord | undefined>` performing the ordered `limit 1` read, both call sites go through it, and a repo test pins the ordering contract itself (most recent `start_date` first, `id` ascending as the tie-break) so the assumption is guarded rather than implied.
