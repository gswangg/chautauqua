# DEC-905: A list the reader just changed refetches through the mutation signal the app already owns; a printed count is its own query's count

app/src/pages/Comms.tsx:54-65 fetches the compose column's Recent Sends once per (eventId, tab), so the list under the composer still shows the world as it was BEFORE the send the organizer just made — the precise staleness DEC-700 built app/src/lib/mutationSignal.ts to end (every successful non-GET already bumps the counter inside api.ts; this consumer simply never subscribed). Rule: the effect takes useMutationVersion() in its deps and the fetch stops being gated on the compose tab, so both mounts and the head read one current answer. The head then states the send rhythm the frame asks for — 'N sent in the last 7 days · last <date>' — and that N comes from the list endpoint's OWN total under a new `since` filter pushed into SQL (src/server/repo/email.ts), never summed over a page of batches: a number derived from a truncated page is a number that goes wrong exactly when it matters. And the send step is the confirmation — no extra dialog is added; the terminal step names the recipient count, the cap and that a send is logged and cannot be recalled, because a wizard whose last screen is a summary does not need a modal asking whether it meant it.

## Amendment (wave 61): "sent" is a status, not a row count; and `groupBy=batch` never silently drops a filter

The Comms head prints `{sentLast7Days} sent in the last 7 days` (Comms.tsx:155) from `GET .../email-log?since=…&perPage=1`'s envelope total -- a request that passes no `status`, so it counts every email_log row in the window including `status='failed'`. On the gate-3 prod run a fully-failed 13-recipient send would have read as "13 sent" in the head while the batch row underneath honestly said 0 sent / 13 failed. DEC-905's own rule is that a printed count is its own query's count; the missing half is that the query must also carry the predicate the copy claims. RULING: the head asks for `status=sent`, and asks a second bounded question for `status=failed` over the same window, printing "N sent in the last 7 days · M failed" only when M > 0 (never a bare failure count, never a silent merge). Second half, same class: email-log.ts:57-60 routes `?groupBy=batch` into listEmailBatches, which accepts only `{eventId,q,page,perPage}` -- `since`, `status`, `contactId` and `batchId` are parsed and then thrown away. A filter the caller supplied and the handler ignored is a wrong answer with a confident envelope. `since` becomes a real SQL lower bound on the batch query and its total; the three that batch grain cannot express refuse loudly with a named 400.

## Amendment (wave 31): a filter is validated against its closed vocabulary BEFORE it reaches SQL — an unrecognised value is a 400, never an authoritative empty page

DEC-905's wave-61 amendment ruled that a filter the caller supplied and the handler ignored is a wrong answer with a confident envelope. The sibling case is a filter the handler PASSES to SQL without validating: src/routes/api/email-log.ts:36 hands `status` straight to eq(emailLog.status, ...), so ?status=snet returns a confident empty list, while the same file's `since` (:43-51) already fails loudly — an inconsistency inside one handler. src/routes/api/breaks.ts:51 does the same with `day`. Ruling: email_log's status vocabulary is exactly {sent, failed} — the only two literals its writers produce (src/mail/dev-sink.ts:27, src/mail/email-binding.ts:225ff, src/mail/unconfigured.ts:34) — spelled once as EMAIL_LOG_STATUSES in src/mail/types.ts and enforced at the route; `day` must match the event-day format the breaks WRITE path already validates (one format, not a second definition). Both refuse with a 400 naming the field. A test enumerates the writers so the vocabulary cannot drift into silence.

## Amendment (wave 59): the send rhythm has ONE producer — RecentSends is handed the figure, it never re-derives it from the batches it was given

app/src/pages/Comms.tsx:101-122 fetches "sent in the last 7 days" the way DEC-905 requires: two dedicated `?since=&status=…&perPage=1` requests, read off `res.total`. app/src/pages/comms/RecentSends.tsx:232-239, rendered on the same compose tab a few dozen pixels below, prints the same sentence — `${sentIn7Days} sent in 7 days · last …` — from `batches.filter(b => b.sentAt >= cutoff).reduce((sum,b) => sum + (b.statusCounts.sent ?? 0), 0)`, a sum over the ONE PAGE of batches its parent fetched (`apiList('/events/:id/email-log?groupBy=batch')` at Comms.tsx:78; src/routes/api/email-log.ts:85 passes page/perPage straight into listEmailBatches). DEC-905's own text forbids exactly this: "never summed over a page of batches: a number derived from a truncated page is a number that goes wrong exactly when it matters." The two also answer different questions — the head counts email_log rows with status=sent inside the window, the subtitle counts rows belonging to batches whose batch timestamp falls inside it. test/spa-count-source-ledger.scan.test.ts:143-148 ledgers RecentSends 'page-scoped' with the justification "computed from the `batches` prop it was given … rather than a fetched total" — a verdict about where the number came from, applied to copy that makes a whole-window claim. RULING: RecentSends renders no aggregate of its own. Comms.tsx owns the figure and passes it (with the last-send timestamp) to BOTH mounts; the sentence is built once so head and section cannot diverge in wording either; RecentSends' third copy of SEVEN_DAYS_MS goes with it. The ledger row is corrected rather than left as a green claim about a red surface.
