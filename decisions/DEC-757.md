# DEC-757: An author is a PERSON: attribution resolves the stored contact, then the account's contact, then the address — and never prints "Unknown"

Two verified leaks of internal identity into organiser-facing prose. (1) src/server/repo/files-comments.ts:150 resolves a comment's author only through user -> contactId, falling back to the raw email and finally the literal "Unknown", with authorRole falling back to "unknown" — the CommentThread renders them as "Unknown (unknown)", which is what the CNT grader saw on speaker replies. The comment row already stores authorContactId; reading the person from the column that names the person removes the whole fallback chain. (2) src/routes/api/submissions.ts:233 and :301 store editorName as `getUserEmail(...) ?? auth.userId`, so the session history reads "sbek-organizer@example.com" while the portal's own edit path (portal-edit.ts:281) already stores a real name — the same fact recorded two ways. One exported resolveActorName(db, userId) serves both write paths, so a third caller cannot invent a third format. A user row that cannot be found throws rather than degrading to an id (house rule: fail loudly). authorRole stays the stored enum on the wire; naming it for the reader is the client's job, because the role vocabulary is display copy.

## Amendment (wave 26): a teammate account is a named person — the create route PERSISTS the name the inviter typed; `user.name` is a real nullable column

DEC-757's rule is that attribution resolves a PERSON and never degrades to an address. The org-user half of it never landed: `app/src/pages/settings/PeopleRolesPanel.tsx:106-118` refuses to submit unless first AND last name are filled (`if (newEmail.trim().length === 0 || newFirstName.trim().length === 0 || newLastName.trim().length === 0) return;`) and posts `firstName: newFirstName.trim(), lastName: newLastName.trim()` (:116-117), but `src/routes/api/users.ts` contains no occurrence of either token, `src/db/schema/org.ts:15-34` has no name column, and `OrgUserRecord` (`src/server/repo/users.ts:36-43`) has no name field — so `nameOrEmail` (`PeopleRolesPanel.tsx:51`) falls back to the email address for every teammate, forever, and the panel's own `fieldErrors.firstName`/`fieldErrors.lastName` renderers (:255, :267) are unreachable code. This is also the ONE red test on main: `test/spa-mutation-contract.scan.test.ts:560-563` asserts `gaps` is empty and it is not (flagged by task-w16-f, re-flagged by `docs/verification-log/task-w17-c-build-test.md:46`, unfixed for nine waves). RULING: add a nullable `user.name` column via a new migration; the POST route accepts OPTIONAL `firstName`/`lastName`, validates them with the same bounded-text accumulation the email/role checks already use (one `errors` map, one refusal), stores the composed `name`, and `listOrgUsers` returns it. Optional-on-the-wire, not required: making it required would break every existing API caller for no correctness gain, and the SPA already enforces presence at its own door — what was broken was the silent discard, not the absence of a server-side requirement.
