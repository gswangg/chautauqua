# DEC-757: An author is a PERSON: attribution resolves the stored contact, then the account's contact, then the address — and never prints "Unknown"

Two verified leaks of internal identity into organiser-facing prose. (1) src/server/repo/files-comments.ts:150 resolves a comment's author only through user -> contactId, falling back to the raw email and finally the literal "Unknown", with authorRole falling back to "unknown" — the CommentThread renders them as "Unknown (unknown)", which is what the CNT grader saw on speaker replies. The comment row already stores authorContactId; reading the person from the column that names the person removes the whole fallback chain. (2) src/routes/api/submissions.ts:233 and :301 store editorName as `getUserEmail(...) ?? auth.userId`, so the session history reads "sbek-organizer@example.com" while the portal's own edit path (portal-edit.ts:281) already stores a real name — the same fact recorded two ways. One exported resolveActorName(db, userId) serves both write paths, so a third caller cannot invent a third format. A user row that cannot be found throws rather than degrading to an id (house rule: fail loudly). authorRole stays the stored enum on the wire; naming it for the reader is the client's job, because the role vocabulary is display copy.
