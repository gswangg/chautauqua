# DEC-757: An author is a PERSON: attribution resolves the stored contact, then the account's contact, then the address — and never prints "Unknown"

Two verified leaks of internal identity into organiser-facing prose. (1) src/server/repo/files-comments.ts:150 resolves a comment's author only through user -> contactId, falling back to the raw email and finally the literal "Unknown", with authorRole falling back to "unknown" — the CommentThread renders them as "Unknown (unknown)", which is what the CNT grader saw on speaker replies. The comment row already stores authorContactId; reading the person from the column that names the person removes the whole fallback chain. (2) src/routes/api/submissions.ts:233 and :301 store editorName as `getUserEmail(...) ?? auth.userId`, so the session history reads "sbek-organizer@example.com" while the portal's own edit path (portal-edit.ts:281) already stores a real name — the same fact recorded two ways. One exported resolveActorName(db, userId) serves both write paths, so a third caller cannot invent a third format. A user row that cannot be found throws rather than degrading to an id (house rule: fail loudly). authorRole stays the stored enum on the wire; naming it for the reader is the client's job, because the role vocabulary is display copy.

## Amendment (wave 26): a teammate account is a named person — the create route PERSISTS the name the inviter typed; `user.name` is a real nullable column

DEC-757's rule is that attribution resolves a PERSON and never degrades to an address. The org-user half of it never landed: `app/src/pages/settings/PeopleRolesPanel.tsx:106-118` refuses to submit unless first AND last name are filled (`if (newEmail.trim().length === 0 || newFirstName.trim().length === 0 || newLastName.trim().length === 0) return;`) and posts `firstName: newFirstName.trim(), lastName: newLastName.trim()` (:116-117), but `src/routes/api/users.ts` contains no occurrence of either token, `src/db/schema/org.ts:15-34` has no name column, and `OrgUserRecord` (`src/server/repo/users.ts:36-43`) has no name field — so `nameOrEmail` (`PeopleRolesPanel.tsx:51`) falls back to the email address for every teammate, forever, and the panel's own `fieldErrors.firstName`/`fieldErrors.lastName` renderers (:255, :267) are unreachable code. This is also the ONE red test on main: `test/spa-mutation-contract.scan.test.ts:560-563` asserts `gaps` is empty and it is not (flagged by task-w16-f, re-flagged by `docs/verification-log/task-w17-c-build-test.md:46`, unfixed for nine waves). RULING: add a nullable `user.name` column via a new migration; the POST route accepts OPTIONAL `firstName`/`lastName`, validates them with the same bounded-text accumulation the email/role checks already use (one `errors` map, one refusal), stores the composed `name`, and `listOrgUsers` returns it. Optional-on-the-wire, not required: making it required would break every existing API caller for no correctness gain, and the SPA already enforces presence at its own door — what was broken was the silent discard, not the absence of a server-side requirement.

## Amendment (wave 72): the attribution ladder has FOUR rungs — linked contact, then the org-scoped contact match, then the account's own stored name, then the address — and no rung ever prints "Unknown"

DEC-757's title declares the ladder as contact -> account's contact -> address, and its wave-26 amendment made `user.name` a real nullable column that the Settings create-account route persists (`src/routes/api/users.ts:80-92` composes firstName+lastName into `name`, `src/server/repo/users.ts:118` writes it). Verified at main: exactly ONE reader exists — `listUsers` projects it at `src/server/repo/users.ts:53` for the People & roles list. Six other display-name paths select only `email` + `contactId` and never the column: `resolveActorName` (`src/server/repo/users.ts:204-223`), `resolveAuthorName` (`src/server/repo/pipeline.ts:83-99`), `batchUserDisplayNames` (`src/server/repo/review/users.ts:40-97`, projection at `:48`, fold at `:90-95`), both ladders in `src/server/repo/files-comments.ts` (`:188-191`, `:313-316`), and `GET /api/v1/me` (`src/routes/me.ts:21-35`, which composes `name` from the contact alone and therefore returns `null` for every staff teammate). So a teammate invited as a named person appears by name in one settings list and as a raw email address in every revision, pipeline note and file comment they author, and as `name: null` in the SPA's own identity endpoint. Two further disagreements ride along: `resolveAuthorName` returns the literal string "Unknown" at `:90` — the exact string DEC-757's title forbids — where its sibling `resolveActorName` throws on the same invariant violation; and `src/routes/api/users.ts:116` addresses the welcome email to `{ email, name: created.email }` while `created.name` sits in scope. RULING: one ladder, four rungs, stated here once — the linked contact's `${firstName} ${lastName}`; else (where a resolver already does an org-scoped contact-email match) that contact's name; else `user.name` when non-blank; else `user.email`. "Unknown" is never emitted: a missing user row is an invariant violation and throws, matching `resolveActorName`. IMPLEMENTATION CONSTRAINT, binding on every lane: the new rung is added to each resolver's EXISTING select projection — never a new query, never a changed query count or order. `src/server/repo/users.ts:195-203` records that dozens of route tests script this module's db calls as an exact ordered select queue, so a second round trip would desync them; adding a column to a select that already runs cannot.


## Amendment (wave 5, sha ee8ceffa): a mononym is a name, not a missing name — one owner for a person's display name, and the both-names-required ladder is retired

`splitSubmittedName` (src/lib/submit-core.ts:112-127) DELIBERATELY produces `lastName: ''` for a single-token name — DEC-986's ruling that the public CFP's one Name control 'never rejects' a mononym. Two readers in the whole tree require BOTH names before they will render one: `src/routes/me.ts:38-43` (falls through to userName, then the EMAIL) and `src/domain/review-identity.ts:18` (falls back to the email). Every other site — 57 of them — joins mononym-safely with `${firstName} ${lastName}`.trim(). So a single-token speaker reads 'Prince' on the public speakers list, the agenda, the portal and every comms merge field, and reads as their raw email address in the SPA chrome, on the organiser's reviewer-identity surfaces and in the evaluations CSV. That is eval finding P3 #14 ('one identity rendering per person everywhere') with a reachable path. Ruling: `src/domain/person-name.ts` owns the join — `personName({firstName,lastName})` returns the non-empty trimmed parts joined by one space ('' when both are empty) and `personNameOrEmail(row)` is `personName(row) || row.email`. THE DEFECT IS THE LADDER, NOT THE JOIN: the two both-required ladders are converted and `contacts-parts/types.ts`'s `fullName` delegates, but the 57 already-correct call sites are NOT migrated — a 38-file churn on the eve of a freeze buys nothing the scan cannot buy.
