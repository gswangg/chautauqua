# DEC-317: Participant invite state defines THREE scopes, not one: public display (visible AND active), notification (active only, ignoring `visible`), portal access (read = not declined; write/upload = active)

Verified on main, not inherited. DEC-274 built exactly one participant gate — visibleParticipantConditions() = visible=1 AND invite_status IN ('none','accepted') — and applied it only to public reads. Every other contact-scoped surface still scopes on participant.contact_id alone: src/server/repo/portal.ts:128 (submissions list), :243 (detail), :431 (deliverable target), :588 (my sessions), :634 (my events), src/server/repo/portal-edit.ts:75 (the EDIT loader), and src/server/repo/files-authz.ts:25 getSubmissionScope's participantContactIds (consumed by src/routes/files.ts:70). Consequence, reachable by ordinary use: a contact who DECLINED an invitation keeps read AND write access to someone else's submission — they can open /portal/submissions/:id/edit and overwrite title/description/tracks, and upload/download its files — while DEC-274 correctly hides them from every public surface. One gate is not enough because the three questions differ. (1) PUBLIC DISPLAY keeps DEC-274 unchanged: visible AND active. (2) NOTIFICATION is active-only and must NOT consult `visible`: `visible` governs whether a name appears on the program, and silencing a real co-speaker's acceptance email because a producer unticked a display flag would be a worse bug than the one being fixed. (3) PORTAL ACCESS splits by verb: a PENDING invitee ('invited') must be able to READ the session they are being asked to accept — docs/sessionboard-reference/00-how-sessionboard-works.md:138's 'Invited Sessions' section is exactly that surface — but must not be able to EDIT it; a DECLINED participant gets neither. So read = invite_status != 'declined' (PORTAL_VISIBLE_INVITE_STATUSES = none|accepted|invited), write = ACTIVE_INVITE_STATUSES (none|accepted), both declared as pure constants in src/domain/acceptance.ts beside the existing ACTIVE_INVITE_STATUSES and pushed into the SQL WHERE per DEC-312, never applied as an app-code post-filter. The self-upload clause in canAccessFile (uploadedByContactId === auth.contactId) survives untouched: you can always reach a file you yourself uploaded, regardless of what you later did with the invitation. Corollary for compose (src/server/repo/comms.ts:129 loadComposeSubmissions, whose own contract comment at :125 already claims 'visible participants' but implements no filter at all): applying gate (2) can leave a selected submission with zero eligible recipients. That must fail loudly, not silently send fewer mails — the batch rejects with an ApiError('invalid') carrying a per-submission `fields` map, exactly mirroring the existing unscheduledIcsFields preflight at src/routes/comms.ts:194 and DEC-019's atomic preflight-before-send rule.
