# DEC-317: Participant invite state defines THREE scopes, not one: public display (visible AND active), notification (active only, ignoring `visible`), portal access (read = not declined; write/upload = active)

Verified on main, not inherited. DEC-274 built exactly one participant gate — visibleParticipantConditions() = visible=1 AND invite_status IN ('none','accepted') — and applied it only to public reads. Every other contact-scoped surface still scopes on participant.contact_id alone: src/server/repo/portal.ts:128 (submissions list), :243 (detail), :431 (deliverable target), :588 (my sessions), :634 (my events), src/server/repo/portal-edit.ts:75 (the EDIT loader), and src/server/repo/files-authz.ts:25 getSubmissionScope's participantContactIds (consumed by src/routes/files.ts:70). Consequence, reachable by ordinary use: a contact who DECLINED an invitation keeps read AND write access to someone else's submission — they can open /portal/submissions/:id/edit and overwrite title/description/tracks, and upload/download its files — while DEC-274 correctly hides them from every public surface. One gate is not enough because the three questions differ. (1) PUBLIC DISPLAY keeps DEC-274 unchanged: visible AND active. (2) NOTIFICATION is active-only and must NOT consult `visible`: `visible` governs whether a name appears on the program, and silencing a real co-speaker's acceptance email because a producer unticked a display flag would be a worse bug than the one being fixed. (3) PORTAL ACCESS splits by verb: a PENDING invitee ('invited') must be able to READ the session they are being asked to accept — docs/sessionboard-reference/00-how-sessionboard-works.md:138's 'Invited Sessions' section is exactly that surface — but must not be able to EDIT it; a DECLINED participant gets neither. So read = invite_status != 'declined' (PORTAL_VISIBLE_INVITE_STATUSES = none|accepted|invited), write = ACTIVE_INVITE_STATUSES (none|accepted), both declared as pure constants in src/domain/acceptance.ts beside the existing ACTIVE_INVITE_STATUSES and pushed into the SQL WHERE per DEC-312, never applied as an app-code post-filter. The self-upload clause in canAccessFile (uploadedByContactId === auth.contactId) survives untouched: you can always reach a file you yourself uploaded, regardless of what you later did with the invitation. Corollary for compose (src/server/repo/comms.ts:129 loadComposeSubmissions, whose own contract comment at :125 already claims 'visible participants' but implements no filter at all): applying gate (2) can leave a selected submission with zero eligible recipients. That must fail loudly, not silently send fewer mails — the batch rejects with an ApiError('invalid') carrying a per-submission `fields` map, exactly mirroring the existing unscheduledIcsFields preflight at src/routes/comms/compose-core.ts and DEC-019's atomic preflight-before-send rule.

## Amendment (wave 50): the read/write split lands where DEC-317 itself names it — files-authz.ts's getSubmissionScope and portal/sessions.ts's listPortalSessions

DEC-317 already names src/server/repo/files-authz.ts's getSubmissionScope as one of the surfaces that must carry the read/write split, and its body states the rule outright: read = invite_status != 'declined' (none|accepted|invited), write = active (none|accepted). Verified at the file on main: getSubmissionScope (files-authz.ts:52-60) builds ONE participantContactIds list from ACTIVE_INVITE_STATUSES, and routes/files.ts:106 uses that single list as the READ predicate for GET /api/v1/submissions/:id/files, while canAccessFile's speaker branch (files-authz.ts:145) uses it for GET /files/:fileId. Consequence, reachable by ordinary use: a participant sitting at invite_status='invited' sees the submission in the portal (portal/data.ts:99 and portal-edit.ts:405 both correctly use PORTAL_VISIBLE_INVITE_STATUSES) but 403s on its deliverables — two gates for one stated rule, and the invited co-presenter cannot read the thing they are being asked to accept. The same read/write confusion appears in src/server/repo/portal/sessions.ts:102, where listPortalSessions ('My sessions', a pure read) uses ACTIVE while its sibling reader in portal/data.ts uses PORTAL_VISIBLE. RULING: SubmissionScope carries TWO named populations — readParticipantContactIds (PORTAL_VISIBLE) and activeParticipantContactIds (ACTIVE). Read paths (authzSubmissionRead, canAccessFile's speaker branch) consult the read population; every write path (authzSubmissionWrite and therefore upload, comment POST, version delete) consults the active one, so the write gate does not widen. listPortalSessions is a read and moves to PORTAL_VISIBLE. The write populations elsewhere — task planning, portal upload targets, compose recipients, public visibility — are untouched. New pins are behavioural, at the route.

## Amendment (wave 37)

An UNTRUSTED write path was more permissive than the trusted one, inverting
this DEC's own gate. Verified on main: src/server/repo/participants.ts:93
and :118 — the ORGANIZER's add-participant path writes
`inviteStatus: "invited"` (src/routes/api/submissions.ts:477's comment says
so explicitly: "always writes inviteStatus='invited' (not active)"). But
src/server/repo/portal-edit.ts:508 — `addCoPresenter`, driven entirely by a
speaker typing a name and an email into their own portal — wrote
`inviteStatus: "none"`, and "none" is a member of ACTIVE_INVITE_STATUSES
(src/domain/acceptance.ts:114). Consequence, traced through the tree: any
speaker could type any known contact's email and that contact became an
ACTIVE participant on their submission — portal-edit.ts:96 grants read AND
write on someone else's submission, portal/tasks.ts:188/236 and
files-authz.ts:42 grant task and file access, server/repo/comms.ts:249 made
them an automatic recipient of the organizer's sends, and
routes/api/submissions.ts:480 auto-created onboarding tasks for them on
acceptance. DEC-604/DEC-656 reasoned only about PUBLIC visibility
(`visible: false` handles that); the ACTIVE grant was never reasoned about.

RULING: a participant a SPEAKER names lands `inviteStatus: "invited"` —
portal-visible for reading, never active for writing — exactly like the
organizer's own path, and gains access only by accepting. No email is sent
from this path (this DEC's no-notification rule for compose, and the house
invariant that status changes never auto-email, both stand); the
accept/decline machinery already exists and is already rendered
(src/routes/portal/index.tsx:601 POST /portal/invitations/:participantId,
canTransitionInvite, and the DEC-278 onboarding-task back-fill at :627),
and the organizer can still promote the row by hand via PATCH participant
(routes/api/submissions.ts:526). The two paths that may still mint an
ACTIVE status are the submission's OWN author (src/server/repo/submit.ts:268,
createParticipant, order 0 — the person the claim link authenticates) and
the organizer's Sessionboard import (src/server/repo/import/sessionboard.ts:290).
Fixed in src/server/repo/portal-edit.ts (`addCoPresenter` now writes
`inviteStatus: "invited"`); enumerated going forward by
test/participant-invite-write-audience.scan.test.ts (the WRITE mirror of
test/participant-reader-invite-filter.test.ts, which scans reads only).


## Amendment (wave 60) — the compose pre-flight's third refusal shape names its sessions, and the shapes are enumerated so a fourth cannot land unread

DEC-317's active-invite filter means a selection whose participants all declined composes to zero people, so preview.ts:45 and send.ts:57 refuse with `noRecipientFields` (compose-core.ts:192-200) keyed by submissionId. ComposeWizard resolves ids for the OTHER two refusal shapes — extractIcsUnscheduledIds (:208) and extractMissingMergeFieldLines (:235) — but routes this one into the generic `else { setError(err.message) }` at :278, so the organizer is told 'Some selected sessions have no eligible recipients' and never learns WHICH. The composer already owns a resolver (`submissionLabel`, :200-203, `REF — name`). RULING: every fields-map refusal shape reaching the composer resolves its ids through submissionLabel before rendering; the server message carries the count ('3 of 12 selected sessions…'); and a test enumerates the three shapes the compose routes can emit and asserts the composer has a named-resolution branch for each, so a fourth shape cannot be added silently. Out of scope by declaration: src/routes/content-notes.ts:94's single-session twin, whose message already names the session ('This session has no eligible recipients to notify').

## Amendment (wave 18): a refusal branch must render on the step that can fire it — an invisible refusal is a dead end

runPreview (app/src/pages/comms/ComposeWizard.tsx:399-419) resolves four outcomes; three set a message, and the fourth — the DEC-051 ics-unscheduled refusal — only calls setIcsUnscheduledIds, whose sole rendered surfaces (:1056, :1172) live inside the step==='preview'/'sent' sections. Fired from step 2 (attachIcs turned on at preview, Back, edit, "Next: preview") the button registers, the wizard does not advance, and the product says nothing — precisely the P0 compose step-2 dead-end shape the gate-8 fleet measured. RULE: every extract*/refusal branch reaches a surface that is mounted on every step from which its request can be issued; the ics-unscheduled refusal is hoisted into the wizard-level banner region beside {error} for non-preview steps, carrying the same named session list and the same schedule-them / send-without-them escape. compose-refusal-shapes.test.ts grows from "a branch exists" to "a branch exists AND renders where it fires".

## Amendment (wave 30): the no-eligible-recipients refusal binds the COMPOSE path only, never a write path that merely also notifies

noRecipientFields (src/routes/comms/compose-core.ts, consumed at src/routes/comms/preview.ts:43) is correct where the entire request IS a send — composing to nobody is a no-op the organizer must be told about before it runs.
