## Amendment (wave 50): a cross-org object refusal is not_found, never forbidden — one existence-hiding convention, scanned

The tree carries two conventions for the same refusal and a document asserting only one of them. docs/AUDIT.md:189 states 'Cross-org access returns 404, never 403, so an attacker can't distinguish "not yours" from "doesn't exist"'. Several families honour it: requireOwnedEvent (src/routes/api/exports.ts:46-48), the token delete route (pinned at test/route-authz-inventory.test.ts:134 '404s when the token belongs to a different org'), src/server/repo/review/users.ts:101, src/server/repo/email.ts:229 (DEC-546), and the headshot serve route, whose own comment reads 'Never leak existence to an unauthorized caller — 404, not 401/403' (src/routes/portal/profile.tsx:451). Against that, ~32 route sites across eleven files throw ApiError('forbidden', '<Object> belongs to a different org') — src/routes/api/submissions.ts (x9), src/routes/agenda.ts (x5), src/routes/tasks.ts (x5), src/routes/files.ts (x5), src/routes/api/embeds.ts (x3), src/routes/api/views.ts (x2), plus api/overview.ts, api/breaks.ts, api/public-surfaces.ts, review/evaluations.ts and content-notes.ts — each confirming to an authenticated organiser of another org that a given submission/event/file/task/view/embed id exists. SPEC §6 requires 'object-level ownership checks on every fetch-by-id (no IDOR)'; a refusal that answers differently for a real id than for a fabricated one is an enumeration oracle inside that check. RULING: every org-mismatch comparison answers ApiError('not_found', '<Object> not found') with the same body a nonexistent id produces. The role refusals that are NOT cross-org (a speaker who is not a participant, a reviewer refused a write, a non-organizer role) keep 403 — they leak nothing an authenticated caller does not already know about their own relationship. A scan test bans the string 'belongs to a different org' from src/ so the next writer cannot reintroduce the oracle, and AUDIT.md's claim becomes derived rather than aspirational.

## Amendment (wave 50)

DEC-005 owns the FileStore port. Five upload paths write the object and then insert the row with no compensation on failure -- src/routes/files.ts:176 then insertFile at :178, src/routes/portal/tasks.tsx:454 then insertFile at :476, src/routes/portal/profile.tsx:374 then setContactHeadshot at :376, src/routes/api/contacts/crud.ts:413, and src/routes/api/portal-config.ts:223 -- while src/routes/public/submit.tsx:553-573 does exactly the opposite, deleting every object it wrote when the row writes throw. The codebase disagrees with itself about the same two-store write, and the divergent half leaks bytes that no row references and no operator can find. Rule: src/server/context.ts, beside the FileStore port it already documents, exports putThenRecord<T>(store, key, data, contentType, record: () => Promise<T>): Promise<T> -- put, await record(), and on ANY throw from record() delete the object and rethrow the ORIGINAL error (the cleanup failure must never mask or replace it, and must never be swallowed into a success). Every single-object upload path calls it; public/submit.tsx's multi-object batch keeps its own rollback and is the single ledgered exception in a scan test asserting no file-store .put outside src/server/context.ts.
