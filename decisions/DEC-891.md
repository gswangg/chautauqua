# DEC-891: A task-assignment deliverable upload names WHICH session it belongs to when a speaker has more than one

task_assignment is UNIQUE(task_id, contact_id) (migrations/0019_join_table_uniqueness.sql:33), so a speaker with two
accepted sessions in the same event has exactly ONE file_request assignment for a given task, but two candidate
submissions an upload could belong to. The prior DEC-240 resolver (`pickDeliverableSubmission`) silently and
deterministically always linked the upload to the lowest-seq accepted submission — slides for the second session
landed on the first, with no way for the speaker to correct it.

Replaces that deterministic tie-break with an explicit choice: `listDeliverableCandidates` lists every accepted-session
candidate the caller's own participant rows admit in the task's event (seq asc, `ref` built from the event's record
prefix), and the pure `resolveChosenDeliverable` requires the speaker to name one via a posted `submissionId` whenever
there are two or more — an absent choice there is a validation error (`invalid`), and a choice outside the candidate
set is a `forbidden` rejection (never evidence-revealing). Zero or one candidate stays quiet: zero resolves to null (a
plain handout, nothing to link), and one resolves to itself whether or not the (necessarily absent, since the UI
renders no control for a single candidate) `submissionId` was posted.

The upload UI mirrors this: `<select name="submissionId">` renders only when 2+ candidates exist
(conditional-and-quiet — a lone candidate gets no control), each option paired with the filename currently linked to
that candidate so a second upload reads as belonging to the second session, not an overwrite of the first.
