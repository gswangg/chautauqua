# DEC-891: A deliverable belongs to the session the speaker NAMES; a tie-break is not a choice

migrations/0019_join_table_uniqueness.sql:33 makes task_assignment UNIQUE on (task_id, contact_id), so a speaker with two accepted sessions in one event has exactly ONE file_request assignment, and src/server/repo/portal/tasks.ts:152-158 (pickDeliverableSubmission, DEC-240) always links the upload to the lowest-seq accepted submission. Slides for the second session therefore land silently on the first, and J8's per-session deliverables cannot be satisfied by any sequence of clicks. A deterministic tie-break is the right answer to "which row do we join" and the wrong answer to "which of your talks is this". Rule: the upload form ASKS. When the uploading contact has more than one active-participant submission in the task's event, the file page renders a required session select (ref -- title, seq order) and the POST carries submissionId, which the server re-validates against that contact's OWN candidate set (403 otherwise -- a posted id is never trusted). With exactly one candidate the select is not rendered and that candidate is used; with zero candidates the file keeps today's null linkage. pickDeliverableSubmission is DELETED rather than kept as a fallback: two paths deciding one thing is one too many, and a silent fallback is exactly the bug. The assignment row still points at the latest file; the page lists each candidate session beside the file currently linked to it, so a second upload reads as a second session's, never as a replacement.

## Amendment (wave 34): the portal tasks page's candidate read is ONE batched statement and joins the wave it does not depend on

loadTasksPageData (src/routes/portal/tasks.tsx:134-247) issues FIVE sequential waves, and its DEC-891 per-event fan-out at :210-214 is `Promise.all(eventIds.map(async … await listDeliverableCandidates))` — a per-id loop, not a batch: concurrency hides latency, it does not cut statements. The batched reader already exists (listDeliverableCandidatesForEvents, src/server/repo/portal/tasks.ts:230) and portal/index.tsx already uses it. RULE: the candidates read becomes ONE call over the distinct event ids, and because it consumes only `assignments` it joins wave 2 (alongside resolveTaskFileChainLatestMany/listFileChainVersionsMany); listLatestDeliverables consumes candidates, so it joins wave 3 (alongside listFileCommentsForFiles). Net: 5 waves -> 3, and N per-event statements -> 1. The pure-JS render-map loops after each wave are untouched, every loud data-corruption throw is preserved verbatim, and the rendered page is byte-identical.

## Amendment (wave 49): a server-rendered deliverable picker carries its own memory — the first candidate never wins by position

src/routes/portal/tasks/views.tsx:112 DeliverableSelect emits every candidate <option> with no `selected` attribute, so the browser selects the FIRST one on every load — the lowest-seq session. A speaker who uploaded v1 against SES-032 comes back to a form pointing at SES-001 and their v2 silently forks a new version series on the wrong session; because comments are scoped per chain (DEC-573), the fork orphans the thread. That is the measured CNT judge-major, and it is a data-loss shape the product refuses everywhere else. Ruling: exactly one option may carry `selected`, and it is the candidate this assignment already has a file linked to (info.linkedFilenames). When nothing is linked yet there is no defensible default, so the control opens on a valueless disabled placeholder and its existing `required` refuses an empty submit — the server contract already answers this correctly (resolveChosenDeliverable 400s a missing choice, src/server/repo/portal/tasks.ts:292), so no server change is needed and the picker stops being the one place a silent wrong answer is prefilled.

## Amendment (wave 66): a deliverable belongs to an accepted session

`listDeliverableCandidates` (repo/portal/tasks.ts:191-219) documents itself as "Every accepted-session candidate" and its WHERE filters only contactId + submission.eventId + ACTIVE_INVITE_STATUSES; `submission.status` is SELECTed at :195 and returned at :216 and never used to filter, and the batched twin at :230-274 repeats it. No consumer filters either (routes/portal/tasks.tsx:189-190,237-243 and tasks/views.tsx:163 gate on `candidates.length < 2` alone). So a speaker's file-request upload picker offers their declined/pending/waitlisted submissions, an upload links a deck to a declined talk and reopens content review on a rejected session, and a speaker with one accepted plus one declined talk is forced through a spurious required-`submissionId` 400 because the picker only appears at 2+ candidates. RULING: both queries add `eq(schema.submission.status, "accepted")` -- the same literal the sibling portal reader already uses at repo/portal/sessions.ts:101 -- so the docstring becomes true in SQL rather than in prose.
