# DEC-891: A deliverable belongs to the session the speaker NAMES; a tie-break is not a choice

migrations/0019_join_table_uniqueness.sql:33 makes task_assignment UNIQUE on (task_id, contact_id), so a speaker with two accepted sessions in one event has exactly ONE file_request assignment, and src/server/repo/portal/tasks.ts:152-158 (pickDeliverableSubmission, DEC-240) always links the upload to the lowest-seq accepted submission. Slides for the second session therefore land silently on the first, and J8's per-session deliverables cannot be satisfied by any sequence of clicks. A deterministic tie-break is the right answer to "which row do we join" and the wrong answer to "which of your talks is this". Rule: the upload form ASKS. When the uploading contact has more than one active-participant submission in the task's event, the file page renders a required session select (ref -- title, seq order) and the POST carries submissionId, which the server re-validates against that contact's OWN candidate set (403 otherwise -- a posted id is never trusted). With exactly one candidate the select is not rendered and that candidate is used; with zero candidates the file keeps today's null linkage. pickDeliverableSubmission is DELETED rather than kept as a fallback: two paths deciding one thing is one too many, and a silent fallback is exactly the bug. The assignment row still points at the latest file; the page lists each candidate session beside the file currently linked to it, so a second upload reads as a second session's, never as a replacement.
