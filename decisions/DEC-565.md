# DEC-565: A nullable column may never sit inside a negated set predicate used as a safety pre-check: read the row, decide in JS, and export the decision as a pure function

src/server/repo/contacts/merge.ts:132-144 pre-checks merge conflicts with `and(lower(user.email) = merged, notInArray(user.contactId, [keepId, mergeId]))`. SQL three-valued logic makes `contact_id NOT IN (...)` evaluate to NULL — never TRUE — for every row where contact_id IS NULL, and src/server/repo/users.ts always inserts organizer/reviewer logins with `contactId: null`. So merging onto an address already owned by a staff login passes the DEC-479 pre-check, and the merge then dies on the `user_email_idx` UNIQUE at merge.ts:279-282 — AFTER the kept contact row was rewritten (:146-162) and duplicate participant / task_assignment / pipeline rows were deleted (:168-250). D1 has no interactive transaction, so that leaves a permanently half-applied merge. patchContact (src/server/repo/contacts/crud.ts:104-118) already gets this right — select the single row by `lower(email)`, then compare `owner.contactId` in JS — so this is a bug, not a variant. Decision: merge.ts's (b2) check becomes the patchContact shape, and the comparison is extracted as an exported PURE predicate `emailConflictsWithOtherAccount(ownerContactId: string | null, keepId: string, mergeId: string): boolean` returning true when an owner row exists and its contactId is neither keepId nor mergeId — NULL included. The negation lives in JS where NULL is just a value; `notInArray` leaves merge.ts entirely. The pure fn exists so the regression is provable: this repo has no D1 test driver (test/contacts-merge-integrity.test.ts:14-16), and a fake db does not evaluate predicates, so a test that merely queues a NULL-contact user row and asserts a throw would pass on the broken code too. General rule for the codebase: a nullable column may never appear inside NOT IN / != in a check whose FALSE branch authorizes a destructive write.
