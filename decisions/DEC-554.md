# DEC-554: A whole-directory contact scan selects only the columns its own pure predicate and sort read, refuses above a declared cap, and re-hydrates only the page it returns

Two J11 paths still load an org's entire contact table with SELECT * and no bound. (i) findDuplicateGroupsForOrg (repo/contacts/merge.ts:25) does `db.select().from(contact).where(orgId)` — every column, every row — then maps through toContactRecord, while findDuplicateGroups (domain/contacts.ts:76) reads only id/email/firstName/lastName/company and the returned DuplicateGroup exposes only id/firstName/lastName/email; bio, notes, socialLinksJson, customFieldsJson, headshotUrl, phone and title are pure freight. DEC-466 then pages the array AFTER materializing all of it. (ii) listContactsForOrg's segment/rules branch (repo/contacts/crud.ts:213) does the same SELECT * whenever ANY filter is active — and DEC-149 made CRM filters BE segment rules, so this is the ordinary interactive path, not an exotic one. matchesSegment reads only STANDARD_FIELDS plus custom.*, and compareContacts reads only the sort keys. SPEC's scale note is explicit that the org network spans multiple events per year (500-5,000 submissions and 200-800 speakers each), and SPEC §7 calls an oversized payload a bug rather than a tuning opportunity. Every other scan in this codebase now carries a declared bound (MAX_PUBLIC_ROWS, MAX_ACCEPTANCE_TASK_ASSIGNMENTS, MAX_IMPORT_WRITE_STATEMENTS, MAX_AUTO_SCHEDULE_PLACEMENTS); these two are the holdouts.

Decision: (a) both scans project ONLY the columns their consumers actually read, derived from those consumers rather than hand-picked (DEC-543's rule). (b) Both carry ONE shared bound, `MAX_CONTACT_DIRECTORY_SCAN = 20000`, exported from src/server/repo/contacts/rows.ts, applied as `.limit(MAX_CONTACT_DIRECTORY_SCAN + 1)` over a deterministic `order by id asc`; exceeding it throws ApiError('invalid') naming the cap and the remedy (narrow with search first, which already runs in SQL). Refuse, never truncate — a silently-dropped duplicate group or filtered contact is invisible to its producer, which is exactly why DEC-521 chose refusal over MAX_AUTO_SCHEDULE_PLACEMENTS's slice. (c) The list path re-hydrates full ContactRows for the <= perPage ids it actually returns, so `items` is byte-identical to today while the scan stops carrying bio/notes across the whole org. (d) The default (no segment/rules) directory path is already two SQL statements and is not touched. (e) The regression bar is the projection and the cap: tests assert the selected key set equals the set the consumer reads (enumerated from the consumer, not written out by hand) and that cap+1 rows throw while cap rows do not.

## Amendment (wave 11, sha 85d8b9ac): a segment rule's FIELD is part of its stored shape — one predicate serves parse time and match time

src/domain/contacts-parts/segments.ts:102-108 promises in its own header that parseSegmentRulesJson "fails loudly rather than letting a malformed row reach matchesRule as an unnamed TypeError", but isValidSegmentRule (:91-100) checks only that op is in SEGMENT_RULE_OPS and that field is a string. A stored rule whose field is neither 'any', a SEGMENT_STANDARD_FIELDS member (:40) nor a well-formed custom.<key> therefore passes the parser and throws from fieldValue (:48) mid-match — an unnamed 500 on the contacts list and on the bulk-email recipient count, with no segment id in the message, which is precisely the outcome the parser was written to prevent. DEC-554 already ruled that this field enumeration is derived and exported rather than hand-listed; the ruling now extends to the VALIDATOR. RULING: one exported predicate decides what a legal segment field is, and both the parse-time check and the match-time refusal call it — a rule the API will save must be a rule the matcher can evaluate, at both doors, with the same vocabulary.
