# DEC-728: Settings is a read-only summary with drill-in editing, and the drilled section is URL state

Verified on main: SettingsPage renders every panel as an edit-everything form (EventSettingsPanel is nine inputs with no summary), which is the single most divergent surface per the mandate (items 39/64/26). The mock's pattern is label:value rows under the section rule with ONE right-aligned action ('Change' / 'Edit the form' / 'Replace'); the form appears only after drilling. Drill state is `?section=&edit=1` in the URL, matching DEC-710's rule that tab/panel selection is URL state, so a settings form is bookmarkable and the back button leaves it. Desktop keeps the rail as a static one-document (rail = scroll target); the drilled single-panel mode stays phone-only, in a media block, per the additive-reflow rule.


## Amendment (wave 13) — the drilled settings section is URL state at EVERY width, so a section URL renders the section on a phone

DEC-728 already says "the drilled section is URL state", and app/src/pages/settings/SummarySection.tsx writes ?section=<key>&edit=1 accordingly. But app/src/pages/Settings.tsx:61 seeds `active` with useState(null) and never reads the URL, while settings.css:126-166 hides .chq-settings-content and .chq-settings-section at <=700px unless .chq-settings-layout[data-drilled='true']. Composed: /admin/settings?section=cfp&edit=1 — a URL the product itself mints, bookmarks and links — renders the rail and NOTHING ELSE on a phone, and the device Back button cannot leave a drilled section because no history entry was ever written. One drill is URL state and its twin on the same page is component state. RULING: one reader. `active` is derived from the validated ?section= param (unknown key -> null) on mount and re-synced whenever the param changes; a rail click writes section=<key> into the search params, preserving every other param, so Back returns to the phone index; the back control clears it. The scroll-driven IntersectionObserver highlight stays local and NEVER writes the URL — a reader that follows the eye must not spam history.

## Amendment (wave 15): a settings section drill keeps its door — the section action relabels to Back, it never disappears

SummarySection.tsx:63 renders its one action ONLY when `!editing`, so `?section=<key>&edit=1` — a URL the product itself mints (openEdit) and a user can bookmark — renders a view with no control that leaves it. The drill must keep exactly one action on the section rule: 'Change' at rest, 'Back' while editing, the latter clearing `section`/`edit` from the search params. Sibling of the standing rule that a guessable URL which 404s is a dead end: a reachable URL with no way out is the same defect wearing a 200.

## Amendment (wave 49): a settings EDIT view is a screen, not a form dropped into the read scroll

SummarySection swaps one section's rows for its edit form, but SettingsPage (app/src/pages/Settings.tsx:193-208) still renders all seven panels, so ?section=cfp&edit=1 puts a form in the middle of six other sections' read rows with no page-level title change. That is the fleet's CLASS 3 in one line, and it has a measured cost: a CNT eval scenario burned ~9 turns wandering the settings edit views hunting one action. The read view stays exactly as designed — the rail is navigation and a rail click only scrolls, it never hides a section (this amendment does not touch that). Ruling: while ?edit=1 names a valid section, the content column renders ONLY that section, the page H1 becomes that section's own label, and a '‹ Settings' control above it clears both params. The rail stays visible — it is chrome, and chrome is full bleed.

## Amendment (wave 3): one settings section key — the rail's key IS the panel's drill key, scan-locked

Verified on main: app/src/pages/Settings.tsx:58 registers `{ key: 'tracks' }` while app/src/pages/settings/TracksRoomsPanel.tsx:66 declares `SECTION_KEY = 'tracks-rooms'`, and app/src/pages/forms/FieldList.tsx / FormsPage.tsx mint `?section=tracks-rooms`. Settings.tsx only honours keys in `validKeys` (built from SECTIONS), so `?section=tracks-rooms&edit=1` — a URL the product itself mints — computes `urlSection = null`, `editing = false`: all seven panels mount and tracks-and-rooms opens its edit form INLINE in the read scroll instead of as the B10 SCREEN every other section gets. The rail's own `?section=tracks` conversely never opens the tracks edit view at all. SettingsSummarySweep.render.test.tsx papers over this with a `DRILL_KEY` translation map, which is the tell: a test that translates between two spellings of one identifier is documenting a bug, not pinning a contract. RULING: there is exactly ONE key per settings section. The rail adopts the already-minted spelling `tracks-rooms` (superset fix — no live URL breaks), the scroll anchor id follows it, and DRILL_KEY is deleted rather than maintained. Guard: a parity scan that reads every app/src/pages/settings/*Panel.tsx source for its `SECTION_KEY = '<key>'` literal and asserts the set equals SECTIONS' keys, so the next panel that invents a second spelling fails the build instead of silently losing its edit screen. Foreclosed alternative: renaming the panel to 'tracks' — it breaks bookmarks the product already handed out.
