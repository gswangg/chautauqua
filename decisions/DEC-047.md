# DEC-047: File-kind resources: multipart create on the existing resources API, file rows kind 'resource'

Schema and the portal download route already support kind='file' resources; only creation is missing. POST /api/v1/events/:eventId/resources accepts multipart/form-data (title + file) alongside the existing JSON wiki create; uploads validate through src/domain/files.ts validateUpload, create a file row with kind 'resource' and submissionId null plus the resource row pointing at it. Organizers download via the authenticated /files/:fileId route (serve scope extended: kind 'resource' is served to organizers whose org owns the resource's event); speakers keep /portal/resources/:id/download. DELETE of a file resource also deletes the file row and R2 object — fail loudly, no orphans.

## Amendment (wave 64): adding a portal resource is a modal with two EXCLUSIVE kinds, and the product has no Link kind

`docs/design/DESIGN-RULINGS.md:354` rules the add path as a modal with kind chips "one or the other, never both". `ResourcesPanel.tsx:319-371` on main is an inline block that renders BOTH add-forms stacked (a wiki-page title+body form and a file title+upload form) behind one 'Add a resource' toggle, so an organizer sees two Titles and two submits at once and the frame's exclusivity does not exist. RULED: add opens the shared `ModalFrame` with two exclusive chips and only the selected kind's fields below it. The frame's word is "Link", but the store has exactly two kinds — `wiki` and `file` — so the chips read **File** and **Wiki page**; inventing a link kind to match a drawing would ship a control the store cannot carry, which DEC-733 forbids in the same panel. Delete keeps the DEC-941 irreversible confirm it already has. The frame is a drawing width, not a ruler (DEC-989) — no measure chasing in this lane.
