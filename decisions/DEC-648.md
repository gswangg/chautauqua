# DEC-648: Saved views are a VISIBLE tab row derived from the live filter state, never a disclosure — the floating panel is deleted, not restyled

The former app/src/pages/submissions/ViewsDropdown.tsx (deleted per this decision's ruling below, in favor of the visible tab row) was still a `<details>` summary opening an absolutely-positioned `.chq-submissions-views-panel` that collides with the toolbar beside it — the user re-flagged this as "poorly BUILT, not merely unintuitive". The mock (docs/design/Chautauqua Submissions.dc.html:66-78) draws a first-class row: a `VIEW` caption, then tabs, then `Save current as view` as the trailing action, with search+sort pushed right. The row's membership is built-in presets (Needs triage / All submissions / Accept queue) followed by the event's own saved views, and the ACTIVE tab is derived by comparing the live filter state to each view's serialized config — never from click state, the same rule the nav already follows (mandate item 11). A disclosure that has to be opened to learn which view you are in is a state the screen refuses to show.

## Amendment (wave 39): a built-in view preset carries the page's DEFAULT columns, resolved per event — `columns: []` means "no columns", and no preset means that

DEC-648 made saved views a visible tab row whose active tab is DERIVED from live state. All three built-ins ship `columns: []` (app/src/pages/submissions/ViewTabs.tsx:31/36/41), which `applyViewConfig` faithfully honours as an empty visible-field set — so clicking Needs triage prints "Columns: 0" and destroys the FORMAT column that DEC-243/249 default-shows, and because `activeViewKey` compares the column set too, the landing state (Format visible) matches NO tab, leaving the row with nothing current. Both symptoms are one cause: a preset that means "these filters, default columns" was written as "these filters, no columns". Field ids are per-event so a preset cannot hardcode one. Ruling: `builtInViews(fields: FormField[])` resolves the page's default column set exactly as the table already does — `findFormatField(fields)` (app/src/pages/submissions/columns.ts:51) — and every preset carries `columns: formatField ? [formatField.id] : []`. `activeViewKey` takes the same fields so derivation and application read one source. `columns: []` keeps its literal meaning for a user-SAVED view (a submitted blank clears); it is simply never what a preset means.
