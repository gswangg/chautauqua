# DEC-318: A schedule_slot whose day falls outside the event's date range is never published: the public schedule reads carry the same [startDate,endDate] bound the admin agenda classifies on

Verified: the former src/server/repo/agenda.ts:280 (now split across src/server/repo/agenda/) and :336 reclassify any placed session whose schedule_slot.day is outside event.startDate..endDate as 'unscheduled' (and count it in summary.unplaced) via isDayWithinEventRange, and src/routes/agenda.ts:69 rejects a slot write outside that window with a 400 — DEC-277's boundary. But NONE of the four public slot reads in src/server/repo/public.ts carry that bound: hydrateSessions (:331-342, session cards + embed sessions.json), getScheduleInfoForSubmissions (:502-512, session and speaker detail pages), getPublicAgenda (:707-719, /e/:slug/agenda + agenda.ics) and getPublicAgendaByIds (:782-799, schedule.ics itineraries). So the moment a producer shortens an event's dates, admin says the session is unplaced while /e/:slug/agenda and the .ics feeds keep publishing it at its stale time — a direct violation of SPEC J10's 'widgets read the same tables as admin'. The admin classification is normative because it is the one a producer can act on (the session shows up in the unscheduled tray to be re-placed) and because the slot-write validator already refuses to create such a row deliberately; an out-of-range slot is by construction stale data, not a hidden feature. Fix in the SQL WHERE per DEC-312 — a single shared condition helper ANDed into all four queries — never as a post-filter in the mapper, so pagination counts and .ics contents agree. Out-of-range sessions then render as unscheduled (day/startMin/endMin/roomName all null) on cards, which is what the card renderer already handles. This requires threading the event's date bounds into hydrateSessions and getScheduleInfoForSubmissions; changing getPublicSpeakerDetail to take the PublicEvent instead of a bare eventId is the accepted cost.

## Amendment (wave 38): one slot predicate for three surfaces — the comms/.ics read carries the event-range bound too

DEC-318 rules that a schedule_slot whose day falls outside [event.startDate, event.endDate] is never published, and both the admin agenda (the former src/server/repo/agenda.ts:391 (now split across src/server/repo/agenda/) isDayWithinEventRange) and every public read (slotWithinEventRange in src/server/repo/public/gates.ts:65) apply it. src/server/repo/comms.ts:387-435 loadIcsScheduleData does not — it does not even receive the event — so an out-of-range slot reads as SCHEDULED to the compose screen's per-row flag (DEC-912) and to the .ics preflight, and a calendar invite gets minted for a placement the agenda classifies as unplaced and the public schedule refuses to render. A decision that reaches two of three readers of the same column is the width-system failure in miniature. Ruling: loadIcsScheduleData takes the event's date range and applies the same SQL bound, in the WHERE (DEC-312), so "scheduled" means one thing product-wide.
