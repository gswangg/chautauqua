# DEC-921: Deleting a session takes its agenda placement with it and REOPENS (never destroys) the task responses its files completed; the confirmation page reads ONE plan that names both

src/server/repo/submission-delete.ts:137-169 contradicts its own header ('Everything a submission owns is removed'): it never deletes schema.scheduleSlot, so a deleted session leaves an orphan placement that makes deleteRoom (src/server/repo/events.ts:469-483) return 409 'Room is referenced by one or more schedule slots' forever, with no session left on the agenda to un-place. In the other direction it deletes TOO much: line 153 hard-deletes every task_assignment whose completion file hung off the submission, destroying event-scoped onboarding progress that is not submission-scoped -- 'Finalize bio + headshot' is a DEFAULT_ONBOARDING_TASKS row keyed on (task, contact), and a session delete must not silently un-assign a speaker from work they still owe the event. Rule: the cascade deletes schedule_slot for every deleted submission; a task_assignment completed by one of the deleted files is UPDATED set-based to {status:'pending', completedAt:null, completedBy:null, fileId:null} -- the task stays, its answer goes; and planSubmissionDelete carries, per eligible submission, counts:{files,comments,participants,answers,tracks,recusals,revisions,taskResponses} plus scheduled:boolean, each from ONE grouped query over the whole eligible id set (a per-row count re-scanning per row is N scans even wearing a Promise.all). The wire contract, implemented by both halves of this wave: GET /api/v1/events/:eventId/submissions/delete-plan?ids=a,b,c (organizer) returns EXACTLY {eligible:[{submissionId,ref,title,counts,scheduled}], refused:[{id,ref,reason}]} -- fileR2Keys stays server-internal and must never appear on the wire. DEC-886 promised a page that names what goes with it; a static sentence that omits the agenda slot and the reopened task is that promise unkept.
