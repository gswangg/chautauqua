# DEC-989: The v6 width system is three tokens and three classes applied at the PAGE ROOT; canvas is the ABSENCE of a class, and an enumerating scan proves every page picks one

docs/design/README.md's "Widths" section is now the page-width authority and supersedes DEC-877's 820-everywhere reading, but the tree implements only one measure: app/src/styles.css defines --chq-measure: 820px and app/src/page-measure.test.ts enforces that EVERY page container clamp uses it — so the table class (1440) and the 1180 submission detail do not exist, and page-measure.test.ts actively ratifies the old rule ("submission detail is an aside page and clamps nothing"). The class is a property of the CONTENT, not the route, so it belongs on the page root element as a class name, not re-declared in each page's stylesheet: --chq-measure (820, reading), --chq-measure-wide (1180, submission detail + the public sessions pair), --chq-measure-table (1440, scan-many surfaces), consumed by .chq-measure / .chq-measure-wide / .chq-measure-table in styles.css only. The agenda grid is the ONE canvas and expresses that by carrying no measure class — the test is whether the column COUNT can grow, which is why the speaker matrix (min-width 1060) and the pipeline board (min-width 1000) are table class despite looking like canvases. A hand-listed manifest of "the pages that need a class" desyncs the moment someone adds a page, so the guard ENUMERATES every `className="chq-page …"` site under app/src/pages and asserts each carries exactly one measure class or is the named canvas. Chrome stays full bleed: only content is constrained.

## Amendment (wave 41): "full bleed" means the PAGE'S OWN BOX — a chrome band declares no max-width, no side margins, and never viewport math

docs/design/README.md's width system says "chrome always full bleed" but the tree has no bleed mechanism, and the obvious one (100vw + negative margins) is wrong here: .chq-main is an internally-scrolling flex child with 34px padding, so a viewport-width child overshoots by the scrollbar and produces horizontal scroll — the same internal-scroll trap the mandate's own TOOLING NOTE records probes fighting. The precedent already on main is right and must be the ONLY one: .chq-review-editor-title-row (review.css:995-1007, DEC-989 w39) is "full bleed" purely by carrying no max-width of its own, so its border-bottom runs edge to edge of the page-root box while the content below sits in the same box. Ruling: a chrome band inside a measured page bleeds by ABSENCE (no max-width, no auto side margins, no vw/cqw), never by escape. Second instance: .chq-content-status-band. This also composes with the w40 clamp lesson — a nested clamp must say width:100%, and a chrome band must declare no clamp at all.

## Amendment (wave 72): a chrome band inside a PADDED parent bleeds by cancelling that padding through its token — absence is only enough when the parent has none

The wave-41 amendment ruled that a chrome band bleeds "by ABSENCE (no max-width, no auto side margins, no vw/cqw), never by escape", using `.chq-review-editor-title-row` as the precedent. Gate-4 measured `.chq-content-status-band` at x34→1406 in a 1440 frame that draws it x0→1440 — because absence only reaches the PARENT'S CONTENT BOX, and `.chq-main` pads 34px (styles.css:368, 16px under the phone media query). Ruling: the wave-41 rule stands for what it forbids — no max-width, no auto side margins, and viewport units remain banned because `.chq-main` scrolls internally — but bleeding across a padded ancestor is done by cancelling exactly that padding: `.chq-main`'s horizontal padding becomes a token (`--chq-main-pad-x`, re-declared at the phone breakpoint), the band sets `margin-inline: calc(var(--chq-main-pad-x) * -1)` and restores the same value as its own padding. One token, two consumers, so the two can never drift; the band's existing no-max-width guard test is widened to assert the negative margin is expressed through the token and never through vw/cqw. The band's bottom edge also takes `--chq-rule`, not the hairline, and the band's copy stacks two lines using the ONE worklist status vocabulary rather than a second label set.

## Amendment (wave 56): a page root whose className is not a static literal is invisible to the measure scan; and 820 is the reading measure — a frame's measured content width is a drawing artifact

Two halves, one decision, because both are about which artifact is authority for a width. FIRST: app/src/page-measure.test.ts:226-256 enumerates page roots by regex over `className="chq-page..."` STATIC literals. app/src/pages/review/ProgressPanel.tsx:118 builds its root as an object property — `const wrapperProps = embedded ? {} : { className: 'chq-page chq-review-page' }` — so it is invisible to the scan and carries no measure token at all; /plans/:id/progress renders unclamped (the gate-9 fleet measured 1532). ContentApp's template-literal root and Comms's per-tab root escape the same regex but are each pinned by a dedicated test with a written delegation reason (:277-286, :328-349); ProgressPanel has neither, which is the whole defect. RULING: the scan reads the `chq-page` token in any string literal in a page file, not just `className="..."`, so a root cannot dodge it by changing quoting; the two structural exemptions stay exactly Agenda and Settings. ProgressPanel takes `chq-measure` (820): its own loading branch at :110 already declares chq-measure, so the loaded state disagreeing with its own skeleton is the bug, and a reviewer-progress list is prose-plus-decisions reading class, not a scanning table. SECOND: gate-9 items 2 and 7 both ask a landed 820 to move to a width measured off a drawn frame — the CFP builder's content (756 @ x422 in a 1600 frame) and src/routes/public/home.css.ts:21's HOME_MEASURE (732). Both are ADJUDICATED NOT-A-DEFECT and must not be re-filed. docs/design/README.md:409 states the frames' own status outright — 'The mock frames are 1240px, which is a drawing width, not a monitor' — :413 fixes the reading measure at 820, :423 names the CFP form builder and the Comms template editor as the two editors that sit at 820 whatever their rows look like, and :425 gives the reason. FormsPage already conforms: forms.css `.chq-forms-content` clamps to `var(--chq-measure)` with `margin: 0 auto`, and the page root's chq-measure-table is the deliberate full-bleed-chrome split that app/src/pages/forms/forms-header-measure.test.ts pins on purpose — the 'regressed to chq-measure-table' report misread a tested design as a regression, and the only real delta was 820 vs a ruler on a drawing. The vendored Widths table is authority over a pixel measured off a frame.
