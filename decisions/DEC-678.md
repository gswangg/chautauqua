# DEC-678: A loading indicator is DELAYED, and an empty state never renders while a load is in flight

Mandate item 20 (user QA, generalizing item 18's pipeline flash). Today every list surface hand-rolls its own `<p>Loading…</p>` / `<p>Loading agenda...</p>` / `<p>Loading event...</p>` at ~15 call sites, .chq-loading in app/src/styles.css carries no animation-delay, and several surfaces render both a spinner and an empty state during the same frame. Fast operations therefore flash for one frame and read as flicker, and slow ones show 'No results' before results arrive — the surface asserts an absence it has not yet measured. The rule is one shared delayed-loading primitive plus the invariant that an empty state is only reachable from a settled load; a hand-applied convention drifts, so the vocabulary is locked by a source scan the way DEC-651/DEC-406 locked the modal and control classes.

## Amendment (wave 3): a loading admin page renders its STRUCTURE, never an empty main region

DEC-678's delayed-loading policy withholds any indicator for 250ms so fast responses don't flicker — correct for an inline sub-region, wrong for a whole page: /admin/review, per-plan Results and Speakers render nav + h1 and nothing else on first load, which two independent SBEK run-4 areas captured and read as broken, and which taxes every eval agent a turn. Ruling: a page's MAIN region gets a shared PageSkeleton that renders on the first frame (no timer) with role=status/aria-busy and N placeholder rows in the shape of what is coming (table/list/detail); DelayedLoading stays exactly as it is for inline waits inside an already-structured page. One component decides skeleton shape app-wide, so this can never become per-page hand-rolled markup again.
