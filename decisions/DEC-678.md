# DEC-678: A loading indicator is DELAYED, and an empty state never renders while a load is in flight

Mandate item 20 (user QA, generalizing item 18's pipeline flash). Today every list surface hand-rolls its own `<p>Loading…</p>` / `<p>Loading agenda...</p>` / `<p>Loading event...</p>` at ~15 call sites, .chq-loading in app/src/styles.css carries no animation-delay, and several surfaces render both a spinner and an empty state during the same frame. Fast operations therefore flash for one frame and read as flicker, and slow ones show 'No results' before results arrive — the surface asserts an absence it has not yet measured. The rule is one shared delayed-loading primitive plus the invariant that an empty state is only reachable from a settled load; a hand-applied convention drifts, so the vocabulary is locked by a source scan the way DEC-651/DEC-406 locked the modal and control classes.

## Amendment (wave 3): a loading admin page renders its STRUCTURE, never an empty main region

DEC-678's delayed-loading policy withholds any indicator for 250ms so fast responses don't flicker — correct for an inline sub-region, wrong for a whole page: /admin/review, per-plan Results and Speakers render nav + h1 and nothing else on first load, which two independent SBEK run-4 areas captured and read as broken, and which taxes every eval agent a turn. Ruling: a page's MAIN region gets a shared PageSkeleton that renders on the first frame (no timer) with role=status/aria-busy and N placeholder rows in the shape of what is coming (table/list/detail); DelayedLoading stays exactly as it is for inline waits inside an already-structured page. One component decides skeleton shape app-wide, so this can never become per-page hand-rolled markup again.

## Amendment (wave 8): a page-level wait renders STRUCTURE on the first frame; DelayedLoading is for sub-regions inside an already-structured page

The wave-3 amendment created PageSkeleton for exactly this and wired three surfaces (SubmissionsTable, OnboardingGrid, Review.tsx). Ten page-level waits were left behind, including the two every route pays: App.tsx:319-321 (RoleGate while identity loads) and App.tsx:337 (the lazy-route Suspense fallback). Both render the header and nav over an empty <main> for 250ms and then a bare "Loading…" — precisely the 'admin pages render blank/heading-only on first load' P1 that two independent SBEK run-4 captures scored as broken. The rule is now stated once so it cannot drift: a wait that occupies a page's MAIN content region uses PageSkeleton (no timer, shaped like the content coming); a wait inside an already-structured sub-region — a drawer, a modal, a table cell, an expandable row — keeps DelayedLoading's 250ms withholding, because label flicker is a real risk there and structure flicker is not. A source-scan test pins it, because a policy with no scan goes stale one page at a time.

## Amendment (wave 15): the first-paint scan's page list is DERIVED from App.tsx's pageLoaders, never typed by hand

page-loading-structure.scan.test.ts enforces 'a page's main region renders PageSkeleton, not a delayed label' against a hand-written PAGE_FILES of 9 entries. Overview.tsx, content/ContentApp.tsx and forms/FormsPage.tsx each render a `chq-page`-classed block whose only content child is `<DelayedLoading />` — precisely what the scan exists to forbid — and the scan never looks at them, which is why /admin blank-on-first-load survived three gates. The route-level page set is already machine-readable (App.tsx's `pageLoaders` import specifiers); the scan reads that, plus one DELEGATES record naming the child module that owns a delegating page's main region. Same shape as wave 14's DEC-078 ruling: a scan with a typed list measures the files someone remembered.

## Amendment (wave 17): first-paint skeleton coverage is derived from the route table, not from the pages someone remembered

Gate-4 and SBEK run 4 both filed 'admin pages render blank/heading-only on first load' as a cross-area turn tax on every eval agent; the house answer is PageSkeleton, and w15-b closed the last named instance (/review/plans/:id/results). Landed (w17-f): test/page-skeleton-coverage.scan.test.ts. Failure messages name both the offending module and every nav/route entry the derivation found reaching it.

## Amendment (wave 19): a page-structure guard measures the class ATTRIBUTE, not one spelling of it; zero blocks found is a failure, and a hint for a file the scan never visits is a failure

app/src/page-loading-structure.scan.test.ts extracts page blocks with /<div className="([^"]*)">/ — literal double quotes, no other attributes, div only. app/src/pages/Comms.tsx:189 renders <div className={`chq-page chq-comms-page ${pageMeasureClass}`}>, so that file yields ZERO blocks: needsPageSkeletonImport() returns false and the DelayedLoading-only-child assertion iterates an empty array. The guard reports green while measuring nothing. Separately, ALLOWED_SUBREGION_HINTS carries entries for pages/review/ResultsTable.tsx, ProgressPanel.tsx and ReviewerQueue.tsx — none of which are in PAGE_FILES (they are sub-components of pages/Review.tsx, not pageLoaders entries), so those hints are never checked and those files' loading branches are unscanned. Those are precisely the reviewer surfaces the mandate reports rendering heading-only on first load. Two rules follow: a scan that finds nothing to measure must fail by name (vacuous coverage is a bug, not a pass), and an allow-list key naming a file the scan never visits must fail as dead config.

## Amendment (wave 20): an allow-list reason that names a delegate is a claim the scan must check, not prose

test/page-skeleton-coverage.scan.test.ts derives its page-module list from App.tsx (good) but its PAGE_SKELETON_ALLOWLIST is six [file, reason] string pairs, four of which assert "delegates its entire body to X, which renders PageSkeleton" -- and nothing anywhere resolves X or checks it. The scan verifies only that the allowlisted FILE still exists in the derivation; the load-bearing half of every reason is unverified prose. This is the wave-17/18 shape (A GUARD THAT QUIETLY NARROWS IS WORSE THAN NONE) applied to the guard's own excuse list. Ruling: an allowlist entry is a structured record naming its delegate, and the scan resolves that delegate and requires it to EITHER contain PageSkeleton OR render at most one chq-page-classed block (a single-return module has no partial frame for a skeleton to stand in for). A reason with no machine-checkable predicate is not a reason. Verified on main: pages/contacts/ContactsApp.tsx and pages/Settings.tsx each render exactly one chq-page block, so the tightened rule is satisfiable today -- the point is that it can no longer drift silently.


## Amendment (wave 27): an empty state is FRESH or FILTERED, and the two have different anatomies

DEC-678 already forbids rendering an empty state while a load is in flight; it says nothing about what one looks like. `.chq-empty` is a single muted line reused everywhere, which cannot express ruling B7's load-bearing distinction. Fresh-and-empty hides the filter chrome entirely (a status filter over zero rows is noise), gets 44px of room and ONE real primary action. Filtered-to-nothing keeps its chrome visible ABOVE the message (the fix is in the chrome), is tighter at 30px, has NO primary button, names the excluding facet, and offers an escape link that clears exactly that one facet. Neither ever renders a disabled button, an illustration, a centred hero, or column headers over nothing. One component owns the split so no surface re-decides it.

## Amendment (wave 36): first-paint structure is proven by RENDER; the source scan is a tripwire, not the proof

"Admin pages render blank/heading-only on first load" is filed by both gate-4 and SBEK run 4 as a cross-area turn tax on every eval agent — the most eval-expensive item still open. The repo answers it with TWO source scans (test/page-skeleton-coverage.scan.test.ts derives the page list from App.tsx's pageLoaders and greps each module for the literal string `PageSkeleton`; app/src/page-loading-structure.scan.test.ts inspects chq-page blocks) and one component test (app/src/components/PageSkeleton.render.test.tsx). Grepping a module for an identifier proves an import, not a paint — the field guide's own shapes cover this twice: SOURCE-SCANNED IS NOT MEASURED, and A SHARED COMPONENT W/ONLY ITS OWN TEST MARKS THE SHAPE NOBODY BUILT. The measurement lives in jsdom at the page level (mount the module, never resolve fetch, assert skeleton structure in the DOM), which is disjoint from the browser render-sweep another lane owns. The source scans stay as cheap tripwires; the render measurement becomes the authority.

Landed (w36-d): app/src/admin-first-paint.render.test.tsx. Derives the same App.tsx-sourced page-module list test/page-skeleton-coverage.scan.test.ts uses (copied, not imported, so importing this file never re-registers that file's `describe` blocks), plus one addition (deriveComponentNames) to resolve each module's exported page component without hand-typing a list. Two modules are CANNOT_MOUNT (Settings.tsx, NotFound.tsx) with a reviewable, module-specific reason each — not "infrastructure this harness lacks" but "this module's own first paint has no page-level async gate at all" (Settings: the rail renders synchronously, each panel owns its own sub-region fetch; NotFound: the 404 card renders in full immediately, its event-name eyebrow fills in the background without gating the card). Every other derived module is mounted with the same MemoryRouter/Route wiring its own existing app/src/pages/**/*.render.test.tsx already uses, fetch stubbed to a promise that never resolves, one microtask flushed, then asserted against the real DOM for a `chq-skeleton`-classed element and zero `chq-empty`-classed elements.

Result on first landing: 9 of 13 mounted modules passed and 4 FAILED — pages/Content.tsx (delegates to ContentApp.tsx), pages/Comms.tsx, pages/Contacts.tsx (delegates to ContactsApp.tsx), and pages/speakers/SpeakerDetailPage.tsx each gated `<PageSkeleton>` ONLY on useCurrentEvent's `eventLoading` flag, the one-time "which event am I looking at" resolution. Once an eventId is already known (the common returning-admin path: localStorage carries `chq.currentEventId` across page loads, so `eventLoading` is false on the very first render), each page's OWN primary data load — ContentApp's worklist, Comms's batches, ContactsApp's contact list, SpeakerDetailPage's speaker detail — fell through past that guard to a bare `<DelayedLoading>` (250ms-withheld per DEC-678's own sub-region rule, so it renders nothing at the one-microtask mark this test measures) inside an otherwise page-chrome-only frame. That was precisely 'admin pages render blank/heading-only on first load' for the common case, and precisely why grepping a module's source for the literal string `PageSkeleton` (true for all four — they DID reference it, just for the wrong branch) proved an import, not a paint.

All four were fixed on the same integration, so the render authority is green rather than a standing red: the wait that owns a page's main region now paints PageSkeleton on the first frame keyed to its OWN load flag (pages/content/SessionList.tsx, pages/contacts/ContactsTable.tsx and pages/comms/ComposeWizard.tsx swap their 250ms-withheld DelayedLoading for a `variant="table"` skeleton in the body they were leaving empty under live column headers; pages/speakers/SpeakerDetailPage.tsx returns a `variant="detail"` page skeleton, so it no longer calls DelayedLoading at all and its ALLOWED_SUBREGION_HINTS entry in app/src/page-loading-structure.scan.test.ts is gone). The same pass closed the second half of the rule — an empty state is only reachable from a settled load — where an empty ARRAY was standing in for a settled one: pages/contacts/DirectoryRail.tsx takes a per-list settled flag (`topCompaniesLoaded`/`segmentsLoaded`/`duplicatesLoaded`, since its three sections are three separate requests) and pages/comms/RecentSends.tsx takes `batchesLoaded`, each withholding its empty row until its own request comes back.

## Amendment (wave 46): B7 rule 6 is structural — on an admin worklist the message REPLACES the table, and the fresh/filtered split is decided by the query the list actually ran

docs/design/DESIGN-RULINGS.md §B7 rule 6 is unambiguous: 'Never an empty table with headers. Column headings over nothing read as a load failure. The message replaces the table; it does not sit under it.' app/src/components/EmptyState.tsx already owns the fresh/filtered vocabulary and is honoured by PlanList, HistoryTab and PipelineBoard, but the three highest-traffic worklists still render a full <thead> over a one-cell apology: SubmissionsTable.tsx:301-342 ('No submissions match the current filters.' under nine live headers plus the select-all checkbox), SessionList.tsx:205-252, FilesLibrary.tsx:229-252. A component that exists and is not called is a rule that is not enforced. Ruling, binding on every admin worklist so no two surfaces answer it differently: when the list has LOADED and its row set is empty, the <table> element — thead included — is not rendered at all and EmptyState renders in its place (the loading path is untouched; a skeleton is not an empty state). The variant is decided by the query the list actually ran, never by row count alone: any narrowing facet in flight (search text, status/contentStatus tab, track, kind, reuploaded, saved view) means 'filtered' — the filter chrome and tabs stay ABOVE the message, `reason` names the facet that excluded everything, and `escape` clears exactly that facet back to its default; no facet in flight means 'fresh' — the filter chrome and pager are hidden and the surface offers its ONE real primary action (New submission on the worklist) or none at all where the producer cannot act. EmptyState's own guards already refuse an action on 'filtered' and an escape on 'fresh'; call sites must not work around them. No new CSS vocabulary: .chq-empty-block/-fresh/-filtered and .chq-empty-what/-reason already exist in app/src/styles.css.

## Amendment (wave 47): B7 rule 6 finished — the fresh/filtered mapping for the five admin tables the wave-46 ruling did not name, plus a structural guard

The wave-46 amendment on this DEC bound 'the message replaces the table' on the three worklists it named (SubmissionsTable landed; SessionList/FilesLibrary are on a parallel branch). Five more admin tables still draw a live <thead> over a one-cell apology, each verified on main: OnboardingGrid.tsx:793-800 (speakers matrix, thead = Speaker + one column per task) and its phone card list at :911; ContactsTable.tsx:89-93; TemplatesTab.tsx:238-241; ResultsTable.tsx:537-541; ComposeWizard.tsx:535-538. Three of the five also break B7 rules 1/4/5: their single message is written in the FILTERED voice ('No contacts match the current search/filter.', 'No speakers match the current filters.') and is shown even when the collection has never held a row, names no facet, and offers no escape. Because three workers touch this in parallel, the variant and the copy are decided HERE, once, not per surface. (a) SPEAKERS matrix: 'filtered' iff hasActiveNarrowing(filters) — reason from the existing narrowingDescription(filters, grid.tasks), escape 'Clear filters' resetting every narrowing facet to its default; otherwise 'fresh' — what 'No speakers on the roster yet.', reason 'Speakers appear here once a submission is accepted.', action null (the roster is derived from accepted submissions; there is no row to create from this page). The <table> including its <thead>, and the phone card list, are not rendered at all when the settled row set is empty. (b) CONTACTS directory: ContactsTable is presentational, so ContactsApp.tsx computes the split and passes ONE new prop `empty: { variant: 'fresh' | 'filtered'; reason?: string; onClear?: () => void }` — 'filtered' whenever search text, a segment, a filter rule or a company-rail selection is in flight (reason names it, onClear clears exactly that facet under the label 'Clear filter'); 'fresh' → what 'No contacts yet.', action null (the page header already carries the collection's primary: New contact / Import CSV). STRUCTURAL GUARD: a new scan under app/src forbids, in app/src/pages/**/*.tsx, any <td> carrying className 'chq-empty' and any <td colSpan=...> cell whose literal text is a zero-row sentence (matches /\b(No|Nothing)\b/ outside JSX expressions), permitting only loading cells (PageSkeleton/DelayedLoading) and expansion bands (chq-review-reviews-detail). Its allowlist holds exactly two entries — content/SessionList.tsx and content/FilesLibrary.tsx, being converted on a parallel branch — and is checked for file EXISTENCE only, deliberately not for 'still violates': a stale entry excuses only those two named files and can never mask a new violation elsewhere, whereas a dead-config assertion would turn the scan red the moment the parallel branch lands.

## Amendment (wave 51): a zero-row message that names a live filter value is EmptyState variant="filtered" with an escape — and the B7 scan gains that second fingerprint

B7 rules 4 and 5 split 'empty because nothing has happened' from 'empty because a filter excluded everything': the filtered state keeps its chrome, names the facet, and offers an escape that clears exactly that facet. app/src/b7-empty-table.scan.test.ts enforces only one fingerprint — a <td> apology — so the same sentence written in a <p> passes. HistoryTab is the witness: its fresh branch renders EmptyState and its search-filtered branch renders a bare .chq-empty line with no escape, four lines apart in one file. Ruling: any zero-row message that interpolates or names the live query/filter must be EmptyState variant="filtered" with an escape callback, and the scan must fingerprint the SENTENCE (a chq-empty element whose children interpolate the search/filter state), not the tag. The scan keeps its existence-checked ALLOWLIST convention so a parallel branch's file can be deferred with a reason rather than double-fixed.

## Amendment (wave 3): a search term IS a narrowing facet — a search that found nothing never speaks in the fresh voice

app/src/pages/speakers/OnboardingGrid.tsx:127 defines `hasActiveNarrowing` as taskId||status||overdueOnly||inviteStatus and its doc comment excludes free-text `q` deliberately, and `clearNarrowingFacets` (line 364) leaves `q` alone for the same stated reason. But `q` is sent to the server by `buildGridQuery` and does narrow the result set. So an organizer with 40 speakers who searches for a name that is not on the roster is told 'No speakers on the roster yet.' — the FRESH voice — with an escape link that clears everything except the one thing that actually emptied the list. B7's rule is that a filtered zero state names the facet and offers the way out; the app currently states something it can see is false. RULING: the predicate that chooses between the fresh and filtered voices includes every input the request carried, search included. `narrowingDescription` names the term (matching "<q>"), the escape clears `q` along with the four facets, and the same rule binds every other surface whose EmptyState variant is computed from a subset of its own query. The general shape, for the field guide: A ZERO STATE THAT PICKS ITS VOICE FROM A SUBSET OF THE QUERY WILL EVENTUALLY TELL THE USER THEIR DATA IS GONE.

## Amendment (wave 58): six skeleton rows is the CONTRACT, not the default, and the varied width is the title column only

DESIGN-RULINGS:325-333 rules 'ALWAYS six rows, never a guess at the real count: a skeleton that guesses lies twice, once while loading and again when the number differs.' Verified `PageSkeleton.tsx:83` makes six a DEFAULT (`rows = 6`) that any caller may override, and `SubmissionsTable.tsx:405` does exactly that with `rows={4}`. The frame's second half is also unmet: `page-skeleton.css:55-61` gives every table row the identical `flex: 2 1 0` title bar, which reads as a loading GRAPHIC — varied widths land on the title column only, the narrow meta columns stay uniform, and the no-shimmer/no-pulse property (true today) is pinned by a scan rather than left to habit.

## Amendment (wave 59): narrowing by one task collapses the grid to that task's column

VERIFIED on main: src/server/repo/tasks/grid.ts:220-224 applies a taskId filter as an ADDITIONAL row predicate (onboardingMatchExists), which is correct — but because createTask expands to every accepted speaker, every roster row already has a cell for every task, so filtering by a task removes no rows and the SPA still renders all N task columns. The externally-filed report reads 'Showing 16 of 16 · task X' with all eight columns still on screen: the control retitles the header and changes nothing a reader can see, which is the same failure mode DEC-678 ruled against for empty states.
