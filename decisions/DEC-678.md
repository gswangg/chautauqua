# DEC-678: A loading indicator is DELAYED, and an empty state never renders while a load is in flight

Mandate item 20 (user QA, generalizing item 18's pipeline flash). Today every list surface hand-rolls its own `<p>Loading…</p>` / `<p>Loading agenda...</p>` / `<p>Loading event...</p>` at ~15 call sites, .chq-loading in app/src/styles.css carries no animation-delay, and several surfaces render both a spinner and an empty state during the same frame. Fast operations therefore flash for one frame and read as flicker, and slow ones show 'No results' before results arrive — the surface asserts an absence it has not yet measured. The rule is one shared delayed-loading primitive plus the invariant that an empty state is only reachable from a settled load; a hand-applied convention drifts, so the vocabulary is locked by a source scan the way DEC-651/DEC-406 locked the modal and control classes.

## Amendment (wave 3): a loading admin page renders its STRUCTURE, never an empty main region

DEC-678's delayed-loading policy withholds any indicator for 250ms so fast responses don't flicker — correct for an inline sub-region, wrong for a whole page: /admin/review, per-plan Results and Speakers render nav + h1 and nothing else on first load, which two independent SBEK run-4 areas captured and read as broken, and which taxes every eval agent a turn. Ruling: a page's MAIN region gets a shared PageSkeleton that renders on the first frame (no timer) with role=status/aria-busy and N placeholder rows in the shape of what is coming (table/list/detail); DelayedLoading stays exactly as it is for inline waits inside an already-structured page. One component decides skeleton shape app-wide, so this can never become per-page hand-rolled markup again.

## Amendment (wave 8): a page-level wait renders STRUCTURE on the first frame; DelayedLoading is for sub-regions inside an already-structured page

The wave-3 amendment created PageSkeleton for exactly this and wired three surfaces (SubmissionsTable, OnboardingGrid, Review.tsx). Ten page-level waits were left behind, including the two every route pays: App.tsx:319-321 (RoleGate while identity loads) and App.tsx:337 (the lazy-route Suspense fallback). Both render the header and nav over an empty <main> for 250ms and then a bare "Loading…" — precisely the 'admin pages render blank/heading-only on first load' P1 that two independent SBEK run-4 captures scored as broken. The rule is now stated once so it cannot drift: a wait that occupies a page's MAIN content region uses PageSkeleton (no timer, shaped like the content coming); a wait inside an already-structured sub-region — a drawer, a modal, a table cell, an expandable row — keeps DelayedLoading's 250ms withholding, because label flicker is a real risk there and structure flicker is not. A source-scan test pins it, because a policy with no scan goes stale one page at a time.

## Amendment (wave 15): the first-paint scan's page list is DERIVED from App.tsx's pageLoaders, never typed by hand

page-loading-structure.scan.test.ts enforces 'a page's main region renders PageSkeleton, not a delayed label' against a hand-written PAGE_FILES of 9 entries. Overview.tsx, content/ContentApp.tsx and forms/FormsPage.tsx each render a `chq-page`-classed block whose only content child is `<DelayedLoading />` — precisely what the scan exists to forbid — and the scan never looks at them, which is why /admin blank-on-first-load survived three gates. The route-level page set is already machine-readable (App.tsx's `pageLoaders` import specifiers); the scan reads that, plus one DELEGATES record naming the child module that owns a delegating page's main region. Same shape as wave 14's DEC-078 ruling: a scan with a typed list measures the files someone remembered.

## Amendment (wave 17): first-paint skeleton coverage is derived from the route table, not from the pages someone remembered

Gate-4 and SBEK run 4 both filed 'admin pages render blank/heading-only on first load' as a cross-area turn tax on every eval agent; the house answer is PageSkeleton, and w15-b closed the last named instance (/review/plans/:id/results). Nothing keeps the NEXT page honest: coverage today is whichever pages a wave happened to touch. Deriving the page-module list from App.tsx's ROUTES/NAV_SECTIONS and requiring each resolved module to render PageSkeleton — with reasoned allowlist entries for pages that have no async first paint — turns a remembered list into an enumerated one, exactly as DEC-678's own wave-15 lesson (TYPED FILE LIST SCAN MEASURES FILES SOMEONE REMEMBERED) demands.

Landed (w17-f): test/page-skeleton-coverage.scan.test.ts. Distinct from page-loading-structure.scan.test.ts (which walks the file list `pageLoaders` alone yields, resolving whole-body delegates like Speakers.tsx -> OnboardingGrid.tsx via a DELEGATES map before checking for hand-rolled DelayedLoading-only blocks) — this scan derives its module set from THREE sources parsed out of App.tsx's own source: NAV_SECTIONS' `loader: pageLoaders.KEY` entries, ELEMENT_BY_PATTERN's `'<pattern>': <Comp />` entries, and the admin catch-all `<Route path="*" element={<Comp />} />`, resolving each to a pageLoaders key and then to a file. It does NOT chase delegate shells through to their child component; instead a shell that hands its entire body to one child (Submissions/Speakers/Content/Contacts) is a `[modulePath, reason]` entry in PAGE_SKELETON_ALLOWLIST, same as a page with no page-level async gate at all (Settings.tsx's static rail, NotFound.tsx's static card). The allowlist is checked against the derivation on every run, so an entry cannot outlive the module it excuses. Failure messages name both the offending module and every nav/route entry the derivation found reaching it.

## Amendment (wave 19): a page-structure guard measures the class ATTRIBUTE, not one spelling of it; zero blocks found is a failure, and a hint for a file the scan never visits is a failure

app/src/page-loading-structure.scan.test.ts extracts page blocks with /<div className="([^"]*)">/ — literal double quotes, no other attributes, div only. app/src/pages/Comms.tsx:189 renders <div className={`chq-page chq-comms-page ${pageMeasureClass}`}>, so that file yields ZERO blocks: needsPageSkeletonImport() returns false and the DelayedLoading-only-child assertion iterates an empty array. The guard reports green while measuring nothing. Separately, ALLOWED_SUBREGION_HINTS carries entries for pages/review/ResultsTable.tsx, ProgressPanel.tsx and ReviewerQueue.tsx — none of which are in PAGE_FILES (they are sub-components of pages/Review.tsx, not pageLoaders entries), so those hints are never checked and those files' loading branches are unscanned. Those are precisely the reviewer surfaces the mandate reports rendering heading-only on first load. Two rules follow: a scan that finds nothing to measure must fail by name (vacuous coverage is a bug, not a pass), and an allow-list key naming a file the scan never visits must fail as dead config.
