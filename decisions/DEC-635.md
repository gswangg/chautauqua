# DEC-635: A request the router cannot answer still gets our answer: the API gets the envelope, a human gets a page

No app.notFound() handler is registered anywhere, so every unmatched path falls through to Hono's default bare-text '404 Not Found'. Two consequences: /api/v1/<typo> answers text/plain instead of the {error:{code,message}} envelope every other API failure promises (DEC-013), so a client cannot parse our errors uniformly; and any mistyped human URL is an unstyled dead end on a product whose design pack ships a not-found screen. Decision: one handler, registered once in the base app from its own module, classifies by the /api/v1 prefix — envelope for the API, an SSR 404 page (public CSS family, noindex, links home and to sign-in) for everyone else. ApiError-thrown 404s keep flowing through the existing error handler untouched.


## Amendment (wave 40)

**The public 404 imports the CARD, not just its stylesheet — one component, or it is two documents again**

Verified on main: src/server/not-found.tsx and src/routes/public/not-found.tsx both claim to draw DEC-945's one card, and they diverge on every visible fact — title 'Not found - Chautauqua' vs 'Not found', eyebrow = the event name vs the literal 'Not found', two links vs one, <main class=card> vs a bare <main> wrapping a <div class=card> (which shrink-wraps to 293.9px because the bare main is not the card), noindex vs no noindex, ThemeStyles+AUTH_CSS vs BaseStyles+AUTH_CSS. Sharing a stylesheet is not sharing a card: the markup is where the divergence lives, so the shared thing must be the component. RULING: src/server/not-found.tsx exports the page renderer (eyebrow + body message + both links + noindex + title), and the public 404 calls it, keeping only what is genuinely its own — the caller-supplied message and DEC-297's Cache-Control: no-store on the 404. Out of scope, deliberately: the /admin/* SPA catch-all's HTTP 200. The Worker cannot know the SPA's route table without duplicating app/src/routeManifest.ts across the src/ boundary, and a wrong 404 on a real admin route is worse than a right 200 on a typo.

## Amendment (wave 50)

DEC-635 says a request the router cannot answer still gets our answer -- the API gets the envelope. Two organizer routes break it by parsing the body with a bare JSON.parse of c.req.text(): src/routes/review/plans-progress.ts:165 (POST /api/v1/plans/:id/remind) and src/routes/review/plans-distribute.ts:217 (POST /api/v1/plans/:id/assignments/distribute). Both chose text() because the body is legitimately OPTIONAL (empty body = default scope / uncapped), and in doing so lost the .catch every sibling route has, so a truncated or hand-typed body surfaces as a 500 internal instead of a 400 invalid. The optional-body case is the reason the drift happened, so the fix is to give it a name: src/server/http.ts exports readOptionalJsonBody(c): Promise<Record<string, unknown>> -- reads the raw text, returns {} for an absent/blank body, and throws ApiError("invalid", "Invalid JSON body") on a parse failure -- and both routes call it. Enforced two-directionally by a scan so the class cannot recur: no JSON.parse in src/routes/** may be applied to a request body, and every c.req.json() call in src/routes/** must carry a .catch that throws an ApiError.

## Amendment (wave 52): a REQUIRED body gets the same named reader the optional one got — the ledger of unguarded c.req.json() sites is emptied, not carried

DEC-635's wave-50 amendment already ruled that every c.req.json() in src/routes/** must carry a .catch that throws an ApiError — and then shipped a 13-entry KNOWN_MISSING_CATCH ledger in test/request-body-envelope.scan.test.ts excusing the sites it "did not own the files for." Verified on main, all 13 are still live and all are REQUIRED-body routes written as `asRecord(await c.req.json())`: event create/update (api/events.ts:216,312), track create/update (:405,435), room create/update (:488,518), portal settings + resource create/update (api/portal-config.ts:103,250,291), plan create/update (review/plans-crud.ts:65,112), plan reviewers (review/plans-reviewers.ts:26) and the reviewer scorecard PUT (review/reviewer.ts:295). Each answers a truncated or hand-typed body with a raw SyntaxError, which the shared onError can only report as a 500 `internal` — never the 400 `invalid` envelope DEC-013 promises every client. The reason the optional case got a name (readOptionalJsonBody) and the required case did not is the whole defect. Rule: src/server/http.ts exports the required twin `readJsonBody(c): Promise<Record<string, unknown>>` — a blank body, malformed JSON, or a non-object each raise ApiError('invalid','Invalid JSON body') — every ledgered site adopts it, and KNOWN_MISSING_CATCH is DELETED rather than shortened, so the scan becomes absolute with nowhere left to record an exception. A ledger that outlives the lane that could not fix it becomes permission.

## Amendment (wave 14) — a recovery link must resolve: every 404-card href is a real Worker route, enforced by scan

ORGANIZER_NOT_FOUND_LINKS (src/server/not-found.tsx:51-54) points at /overview and /submissions. Those are React-Router patterns relative to the /admin basename (src/lib/admin-routes.ts:15), not Worker paths — the SPA is mounted at /admin/*. So every organiser-facing 404 card (the app-wide notFound handler, the unknown /admin/* card in src/routes/root.tsx, and the portal gate in src/routes/portal/shared.tsx:59) offers two recovery links that both 404 again. A 404 card whose only two doors are also 404s is worse than no card. Ruling: admin destinations are written as '/admin' + an ADMIN_ROUTE_PATTERNS pattern, and the invariant becomes a test — every href in every exported NOT_FOUND_LINKS constant must be '/', '/login', or an /admin path whose suffix satisfies matchesAdminRoute. The frame's labels ('Overview ›', 'Submissions ›') are unchanged; only the hrefs were lying.

## Amendment (wave 17): the error card renders with zero IO — a door that needs the database is no door when the database is why you're here

publicErrorDocument (src/routes/public/not-found.tsx:55, landed w16-d) awaits resolveNotFoundEyebrow(c.var.db), which issues two D1 reads (getHubOrg + listHubEvents) from INSIDE publicRoutes.onError. When the thrown error is itself a database failure — the single most likely cause of a public 500 — that await rejects, Hono's onError returns a rejected promise, and the runtime answers with its own bare 500: exactly the naked door the wave-16 amendment was written to close, in the one case it most needed closing. The 5xx/4xx card therefore resolves its eyebrow from a module constant, not a query. publicNotFound's 404 path is untouched: it only runs after getPublicEventBySlug returned cleanly, so the database is demonstrably alive there and the event-naming eyebrow stays.

## Amendment (wave 21): a catch that returns a default is not a guarded body read — the scan checks the catch BODY, and the last 28 silent sites adopt the named readers

DEC-635's wave-50 amendment already ruled that "every c.req.json() call in src/routes/** must carry a .catch THAT THROWS AN ApiError", and wave-52 emptied the exception ledger so the rule is absolute. The implemented guard (test/request-body-envelope.scan.test.ts:127-140) only asserts that the characters `.catch(` follow the call — and its own failure message recommends `.catch(() => ({}))`, the exact shape the decision forbids. 28 live call sites across 11 route files (files.ts 3, agenda.ts 2, tasks.ts 6, content-notes.ts 1, api/breaks.ts 2, api/users.ts 2, api/tokens.ts 1, api/embeds.ts 2, api/submissions.ts 7, api/views.ts 1, review/recusals.ts 1) therefore answer a truncated or hand-typed body by pretending it was `{}` — on an all-optional PATCH that is a silent 200 no-op, which is a fail-loudly violation (SPEC §2.6) and a broken promise of the {error:{code,message}} envelope (DEC-013). Meanwhile 22 sites in 7 other files already read through readJsonBody/readOptionalJsonBody, so this is finishing a half-done migration, not inventing one. Ruling: every route body is read through readJsonBody (required body) or readOptionalJsonBody (absent body == defaults); the scan's direction (b) passes a c.req.json() call ONLY if its chained catch body contains `throw`, and gains a match-count tripwire so a rename cannot make it vacuous.
