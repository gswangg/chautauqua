# DEC-418: Public list surfaces bound their result set in SQL and count separately -- never a JS slice, and never a LIMIT on fanned-out join rows

getPublicSessions materializes every visible submission id through an unbounded selectDistinct and then slices in JS (src/server/repo/public/sessions.ts:74-108, 275-278), and getPublicSpeakers has no bound at all (src/server/repo/public/speakers.ts:44-60). At SPEC.md:73-76's 500-5,000 submissions and 200-800 speakers these are precisely the 'demos well with 10 rows and dies at 2,000' case SPEC.md:194-195 forbids, on the two surfaces carrying the <50ms cache-hit / <150ms uncached-SSR budget (SPEC.md:335). The admin list (src/server/repo/submissions/list.ts:108-114) already does this correctly. Rule, stated once: every public list query carries LIMIT in SQL and takes its `total` from a separate COUNT(DISTINCT ...) over the identical joins and conditions; where the row shape is a join fan-out (one row per speaker x session) the bound goes on a distinct-key subquery FIRST and hydration happens by id, because a LIMIT on fanned-out rows truncates a speaker mid-session-list. The speakers and gallery surfaces adopt the show-more control the sessions surface already ships (same `page` param, same 'N of M' line, same carried `q`) rather than inventing a new affordance -- this is the existing pattern applied, not a redesign.
