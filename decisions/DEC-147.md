# DEC-147: Per-round scorecards: evaluation_plan gains nullable round_criteria_json (map of round -> criteria array); round 1 and any round without an override uses criteria_json; a single pure criteriaForRound() helper is the only resolution point

ABS-01 requires a distinct scorecard per round, but today one shared criteria_json serves every round. Migrations are append-only (DEC-015), so we add migration 0010 with a nullable round_criteria_json TEXT column on evaluation_plan holding JSON like {"2": [criteria...]}. Round resolution lives in one pure function criteriaForRound(baseCriteria, overrides, round) in src/domain/evaluation.ts so queue rendering, score validation, and results aggregation can never disagree about which criteria govern a round. Plans without overrides behave exactly as before — zero migration risk for existing seeds and tests. Evaluations already carry a round column with a per-round unique index, so storage needs no change.

## Amendment (wave 62): a blended score has one rendering grammar — one decimal place and one empty token, from one exported formatter

DEC-147 already rules that computeWeightedScore is the single blended-score formula. Its RENDERING is five hand-rolled copies in four files, and they disagree: app/src/pages/review/ResultsTable.tsx:426 `{row.average.toFixed(1)}` and :533 `{ev.score !== null ? ev.score.toFixed(1) : '—'}`, app/src/pages/submissions/SubmissionDetailPage.tsx:896 (same expression, third spelling of the null branch), app/src/pages/review/ReviewerQueue.tsx:210 `typeof item.myScore === 'number' ? item.myScore.toFixed(1) : '—'`, and app/src/pages/review/Scorecard.tsx:611 `overallScore === null ? '—' : overallScore.toFixed(1)` sitting six lines above :617's `plainAverage(...).toFixed(2)` — the same screen printing the same kind of number at two precisions, so a reviewer reads "4.3" and "4.33" for one talk. Three spellings of "is this null" is how a fourth renderer gets the empty token wrong. THE RULE: a new pure-core module src/domain/score-copy.ts exports SCORE_EMPTY_TOKEN and formatScore(value: number | null | undefined): string — the em-dash token for null/undefined/NaN, one decimal place otherwise — and every human-facing score renderer calls it, Scorecard's plain-average hint included. The CSV writer in src/routes/review/plans-progress.ts:179-180 deliberately keeps 2 decimals and is out of the formatter's population: a CSV is data, not copy, and the source must say so in a comment naming this amendment, so the divergence is a recorded choice rather than a fifth accident.

## Amendment (findings wave 8): a review round is a NAMED WINDOW, not just an index — round_meta_json joins round_criteria_json, resolved by one function and printed by one formatter

DEC-147 gave each round its own scorecard and named ABS-01 as the reason. ABS-01 asks for three things per round — 'its own name, open/close dates, and its own scorecard' — and only the third landed. On main a round is an integer: evaluation_plan carries rounds/current_round/round_criteria_json (src/db/schema/review.ts:31-39), the plan editor's round tabs are labelled by number, and the reviewer's eyebrow says 'round 1'. That is thin as product, not just as score: a producer running a two-round wave has no way to say what round 2 IS ('Final Review') or when its window opens, and the plan's single open/close pair cannot express two sequential windows. This is NOT the nested per-round remodel the standing skip list forbids — no new table, no per-round reviewer pool, no per-round submission set. It is the same override shape DEC-147 already established, for two more facts. RULING: one nullable TEXT column round_meta_json on evaluation_plan, a map of round -> {name?, opensAt?, closesAt?}, mirroring round_criteria_json exactly; ONE pure resolver in the evaluation domain returns a fully-resolved {name, opensAt, closesAt} for any round, falling back to 'Round N' and the plan's own open/close dates so every existing plan behaves precisely as before; ONE exported label formatter is the only place a round becomes human copy, so the plan editor's tab, the reviewer queue head and the scorecard eyebrow can never disagree. Unlike criteria, round meta does NOT freeze at the first submitted review — a name and a window are not scoring inputs, and renaming a round rescoresnothing; the freeze rule stays exactly where DEC-213/DEC-676 put it, and the code says why.

## Amendment (wave 63): a round is named only when the plan has more than one round, from one predicate

eval-findings item 17 filed 'Round 1 of 1' as a wrong denominator. It is not wrong — rounds are per-plan (DEC-082) — but it is noise, and the product already decided so: `Scorecard.tsx:413` guards its round label with an inline `plan.rounds > 1` while `ProgressPanel.tsx:136`, `PlanList.tsx:281` and `ReviewerQueue.tsx:530` print one unconditionally. One surface having quietly made the ruling and three not honouring it is the same defect class as a comment claiming a sibling's behaviour. Ruled: one exported predicate in the domain (where DEC-147 already put `roundLabel`, 'the ONE place a round becomes a label'), consumed by every surface that has the plan's rounds count in scope; the two surfaces that do not (ResultsTable's row envelope carries `ev.round`/`ev.planName` but no `rounds`; ComposeWizard's line names the PLAN, a different grammar) are structural exemptions recorded on the predicate itself.

## Amendment (wave 79): an export resolves a round exactly as the screen does — criteriaForRound is the only door, in exports too

`src/db/schema/review.ts:37` states round_criteria_json is "resolved ONLY via src/domain/evaluation.ts's criteriaForRound()", and `listPlanCriteriaByIds`'s own doc (`src/server/repo/review/evaluations.ts:442-445`) tells callers to resolve "each row's own round through criteriaForRound(info.criteria, info.roundCriteriaJson, row.round)". Every screen obeys: plans-progress.ts:205, review/shared.ts:471, review/evaluations.ts:55, reviewer.ts:226/451/558. `exportEvaluations` does not — `src/server/repo/exports/evaluations.ts:194-200,205` builds a per-PLAN criteria map from `criteriaJson` alone and computes weightedScore from it, while the very same loop reads `r.roundCriteriaJson` for labels at :191 and selects `round` at :167. For a plan whose round 2 reweights or replaces criteria, the CSV's weightedScore column is a different number from the one /plans/:id/results shows for the same evaluation. DEC-873's "an export is a read side" and DEC-649's "an export is the same WHERE clause as the list beside it, or the file lies" both already bind; this amendment extends the identity from the row SET to the row's own arithmetic. Ruling: the export resolves per (planId, round) through criteriaForRound and passes the plan's parsed scale, so the export and the screen can only ever print the same number or the same blank.

## Amendment (wave 80): evaluation_plan's five JSON columns get one validated home; a tolerant reader may resolve a LABEL and must never be the source of a WEIGHT

Verified on main: `toPlanRecord` (src/server/repo/review/plans.ts:58-86) casts all five of the plan's JSON columns with zero validation — `scale` to `{min,max}`, `criteria` to `EvaluationCriterionDef[]`, `filters` to `{trackIds?}`, `roundCriteria` and `roundMeta` to record maps — and its own comment concedes only that `JSON.parse` throws on bad JSON. A well-formed-but-wrong-shape row therefore reaches `computeWeightedScore` (a criterion with a missing/non-numeric weight yields NaN on the results screen) and the scorecard's range control (a scale missing min/max renders an unusable input). The same columns are re-parsed uncast at review/evaluations.ts:460-462 and criteria.ts:292. Meanwhile `labelByCriterionId` (exports/evaluations.ts:25-51) reads the SAME criteria_json under the opposite policy — try/catch swallow, silently skipping any criterion whose id/label is not a string. Two readers of one column with opposite failure policies is the half-a-contract shape. RULING: a new pure-core `src/domain/evaluation/plan-json.ts` owns the five columns with named throwing parsers, spent by plans.ts, review/evaluations.ts and criteria.ts's internal parse. The export's tolerant label lookup stays as it is, and the boundary is written into the new module's header as a rule rather than a schedule: a display-label reader may be tolerant of legacy history, and must never be the source of a criterion's weight. `criteria.ts`'s exported signatures are frozen this wave — a parallel branch is adding a new caller of `criteriaForRound`; only the internal parse moves.
