# DEC-147: Per-round scorecards: evaluation_plan gains nullable round_criteria_json (map of round -> criteria array); round 1 and any round without an override uses criteria_json; a single pure criteriaForRound() helper is the only resolution point

ABS-01 requires a distinct scorecard per round, but today one shared criteria_json serves every round. Migrations are append-only (DEC-015), so we add migration 0010 with a nullable round_criteria_json TEXT column on evaluation_plan holding JSON like {"2": [criteria...]}. Round resolution lives in one pure function criteriaForRound(baseCriteria, overrides, round) in src/domain/evaluation.ts so queue rendering, score validation, and results aggregation can never disagree about which criteria govern a round. Plans without overrides behave exactly as before — zero migration risk for existing seeds and tests. Evaluations already carry a round column with a per-round unique index, so storage needs no change.

## Amendment (wave 62): a blended score has one rendering grammar — one decimal place and one empty token, from one exported formatter

DEC-147 already rules that computeWeightedScore is the single blended-score formula. Its RENDERING is five hand-rolled copies in four files, and they disagree: app/src/pages/review/ResultsTable.tsx:426 `{row.average.toFixed(1)}` and :533 `{ev.score !== null ? ev.score.toFixed(1) : '—'}`, app/src/pages/submissions/SubmissionDetailPage.tsx:896 (same expression, third spelling of the null branch), app/src/pages/review/ReviewerQueue.tsx:210 `typeof item.myScore === 'number' ? item.myScore.toFixed(1) : '—'`, and app/src/pages/review/Scorecard.tsx:611 `overallScore === null ? '—' : overallScore.toFixed(1)` sitting six lines above :617's `plainAverage(...).toFixed(2)` — the same screen printing the same kind of number at two precisions, so a reviewer reads "4.3" and "4.33" for one talk. Three spellings of "is this null" is how a fourth renderer gets the empty token wrong. THE RULE: a new pure-core module src/domain/score-copy.ts exports SCORE_EMPTY_TOKEN and formatScore(value: number | null | undefined): string — the em-dash token for null/undefined/NaN, one decimal place otherwise — and every human-facing score renderer calls it, Scorecard's plain-average hint included. The CSV writer in src/routes/review/plans-progress.ts:179-180 deliberately keeps 2 decimals and is out of the formatter's population: a CSV is data, not copy, and the source must say so in a comment naming this amendment, so the divergence is a recorded choice rather than a fifth accident.
