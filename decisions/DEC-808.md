# DEC-808: One page measure, finally adopted by the admin SPA

VERIFIED DEC-744's --chq-measure token exists in both app/src/styles.css:94 and src/views/theme.ts:83, but adoption is lopsided: the server-rendered surfaces (submit-views, docs, mailbox) all wear <main class="chq-measure"> while the admin SPA has only three consumers (NotFound, RouteErrorBoundary, two rules each in forms.css/review.css). The user re-confirmed the symptom on a recent commit — submission detail content stops around 75% width with a dead right gutter, and the form builder clamps at 720px inside a 1372px frame. Decision: finish the sweep by the token's own rule — a single-column subscreen clamps with var(--chq-measure) and centres; a page that carries an aside fills the frame and clamps nothing — and pin it with a scan that ENUMERATES app/src CSS files rather than naming them, because a hand-listed manifest desyncs the moment someone adds a page. Hard-coded pixel clamps on page/content containers are the defect being removed, not a style preference.


## Amendment (wave 40)

**The Comms template editor is reading class, taken by the editor block rather than by flipping the page root**

Verified on main: app/src/pages/Comms.tsx:144 puts the whole Comms page — every tab, including Templates and its editor — on .chq-measure-table (1440), and the v6 README names the Comms template editor as reading class (you compose one thing) while Comms compose stays table. The obvious move, flipping the page root's class when the editor opens, would require lifting TemplatesTab's `editingId` into Comms.tsx purely to choose a CSS class — state plumbing in service of typography. RULING: the .chq-comms-editor block itself takes the reading measure and centres inside the table page, and it does so with width: 100% alongside max-width: var(--chq-measure) — the legal form of a nested clamp under DEC-744's amendment, since without it the auto margins would shrink-wrap the editor to its text. Its BODY textarea, byte-identical at 187x166 across three gates, fills the field column (width: 100%) with a real min-height.

## Amendment (wave 23): a contract lands with its scan in the same wave, or it drifts back

Both new contracts this wave (DEC-902's column idiom, DEC-976's citation quote) are enumerated with readdirSync over app/src and src — never a hand-listed manifest of "the tables that matter" or "the files with citations", which desyncs the moment someone adds one. A guard whose exemption list can be grown from the failure output is not a guard: every exemption carries a written reason in the test source naming why the contract cannot apply (data-driven column count, phone reflow block), and adding an entry without a reason is a failing change, not a passing one.


## Amendment (wave 57) — one derived enumerator for the SSR stylesheet population: `test/helpers/ssr-css-sources.ts`

Two independent scans define "the SSR stylesheets" two different wrong ways, and both miss the biggest one. app/src/no-fitted-geometry.scan.test.ts:21-32 globs `src/routes/**` for names ending `.css`/`.css.ts`; test/public-tap-floor-scope.scan.test.ts:20 (since renamed to test/ssr-tap-floor-scope.scan.test.ts) globs `src/routes/public/**/*.css.ts`. Neither reaches src/views/theme.ts — a ~500-line THEME_CSS that owns the phone tap floor for the entire SSR half of the product — because it is a plain `.ts` file, nor src/views/bare-page.css.ts / src/views/error-states.css.ts, because they are outside `src/routes`. The honest population is a PROPERTY, not a path: a module that exports a `*_CSS` template literal. One helper, derived at test time (the DEC-808 readdirSync idiom, never a hand-listed manifest), consumed by both scans, with a vacuous-population tripwire so a rename can't make the sweep go quiet. Same shape as wave 53's `resolveRegisteredRoute`: when several lanes need the same derived population, they get ONE function in ONE file, not a copy each.


## Amendment (wave 83, v12 mobile campaign w1): the 53 phone frames are an enumerated population with a claim ledger and a ratchet

The campaign's goal is "every screen matches its v12 frame on desktop AND phone", and nothing in the tree can currently answer "how many of the 53 width:390 frames are claimed?" — the mandate's own per-cluster counts are a hand-written list in docs/mobile-campaign.md, which is exactly the desync DEC-808 rules against ("a scan that ENUMERATES … rather than naming them"; field guide: A DIRECTORY IS NOT A POPULATION, A HAND-LISTED POPULATION IS NOT A POPULATION). Ruling: a scan enumerates every `width:390px` frame in docs/design/*.dc.html by reading the files, resolves each frame's title from its preceding label span, and requires a claimed frame to be cited by `docs/design/<file>.dc.html:<line>` inside some *.test.ts/*.test.tsx — the same citation form DEC-976 already governs. The claimed COUNT is a ratchet (house idiom, cf. vocabulary-duplication-ratchet.scan.test.ts), never an allowlist populated from failure output: it may only go up, and the failure message names the unclaimed frames so the planner schedules them. This is the campaign's completion metric; goalComplete is reachable only when it reads 53 of 53.
