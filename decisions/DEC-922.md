# DEC-922: A file version chain never crosses a submission or a kind -- including the portal task upload path

src/routes/portal/tasks.tsx:415-424 re-resolves submissionId from the speaker's own DEC-891 choice and then unconditionally sets previousFileId: scope.fileId, with none of the isValidVersionChain guard the organizer path applies at src/routes/files.ts:136. So a speaker who uploads for talk A, then re-uploads the same task naming talk B, chains B's first deliverable onto A's file: insertFile (src/server/repo/files-versions.ts:221-237) labels B's FIRST deliverable 'v2', and resolveTaskFileChainLatest (:77) then serves A's file as this task's deliverable and anchors B's comment thread on A's chain. Rule: the chain rule is ONE predicate for every writer -- chain only when the predecessor's {submissionId, kind} equals the new upload's {submissionId, kind} (null===null for the handout case, which has no submission); otherwise previousFileId is null and a new chain starts at v1. The portal path composes src/domain/files.ts's existing isValidVersionChain semantics rather than inventing a second rule, and it never 400s the speaker for it -- starting a fresh chain is the correct outcome, not an error.
