# DEC-922: A file version chain never crosses a submission or a kind -- including the portal task upload path

src/routes/portal/tasks.tsx:415-424 re-resolves submissionId from the speaker's own DEC-891 choice and then unconditionally sets previousFileId: scope.fileId, with none of the isValidVersionChain guard the organizer path applies at src/routes/files.ts:136. So a speaker who uploads for talk A, then re-uploads the same task naming talk B, chains B's first deliverable onto A's file: insertFile (src/server/repo/files-versions.ts:221-237) labels B's FIRST deliverable 'v2', and resolveTaskFileChainLatest (:77) then serves A's file as this task's deliverable and anchors B's comment thread on A's chain. Rule: the chain rule is ONE predicate for every writer -- chain only when the predecessor's {submissionId, kind} equals the new upload's {submissionId, kind} (null===null for the handout case, which has no submission); otherwise previousFileId is null and a new chain starts at v1. The portal path composes src/domain/files.ts's existing isValidVersionChain semantics rather than inventing a second rule, and it never 400s the speaker for it -- starting a fresh chain is the correct outcome, not an error.

## Amendment (wave 26): a portal re-upload proves its chain through the ROUTE, not the repo — and a chain that cannot continue says so

CNT-04 was closed on organizer-path evidence and re-opened by live judge evidence: three SPEAKER-PORTAL replace attempts produced no v2. Reading src/routes/portal/tasks.tsx:570-576, previousFileId is set only when getReplacesTarget(scope.fileId) matches BOTH submissionId and kind; the deliverableKind===null branch (line 544) forces kind='handout' and submissionId=null, so an assignment whose prior file was recorded with any other kind silently starts a fresh v1 on every upload — three uploads, three v1 chains, and the assignment pointer makes it look like an overwrite. Ruling: the guard stays (a chain must never cross a submission or a kind), but it must be PROVEN at the route level, not the repo level — the closing evidence for this item is a test that drives the real POST /portal/tasks/:assignmentId/upload handler twice and asserts a v1+v2 chain, plus the negative case where the speaker re-chooses a different submission and a fresh v1 is correct. Where the guard legitimately refuses to continue a chain, the redirect must carry that fact rather than looking identical to a successful replace — a silent restart is indistinguishable from data loss, which is why this closed falsely once already.
