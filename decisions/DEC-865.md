# DEC-865: The org user directory is organizer/reviewer only: a speaker portal login is not an org user and cannot be listed, re-passworded, or promoted through /api/v1/users

VERIFIED on main. src/routes/auth.tsx:434-443 (the /claim flow) inserts a schema.user row with role='speaker', the contact's orgId and contactId attached — that is a speaker's own portal login. src/server/repo/users.ts:37-38 listOrgUsers builds its WHERE as `role ? and(orgId, role) : eq(orgId)`, so GET /api/v1/users with no ?role= enumerates those portal logins; getOrgUserById (users.ts:93-101) filters on id+orgId ONLY, so POST /api/v1/users/:id/reset-password (src/routes/api/users.ts:121-134) mints a working password for a speaker's own portal account, RETURNS it in the response body and deletes that speaker's sessions, and PATCH /api/v1/users/:id (143-167) promotes that same login — contactId still attached — to 'organizer', handing a CFP submitter the org's whole CRM. The route's ALLOWED_ROLES set validates the NEW role and never the TARGET's current one, which is the whole defect: a role you were never shown is still a role you can write. SPEC §6 requires role + object-level checks on every fetch-by-id, and J7 makes speaker scoping absolute. Decision: ONE exported vocabulary — `export const ORG_USER_ROLES = ['organizer','reviewer'] as const` declared in src/server/repo/users.ts and imported by the route, with the route's hand-listed ALLOWED_ROLES deleted (a hand-listed twin of a vocabulary desyncs — field guide). listOrgUsers and countOrgUsers compose ONE shared where-builder so list and total can never disagree, and with no role filter they narrow to inArray(user.role, ORG_USER_ROLES). getOrgUserById returns undefined for any row outside that set, so both mutating routes 404 exactly as they already do for a cross-org id — the response leaks nothing about whether the id exists. Promoting a speaker login to organizer is NOT a stage-1 capability: that login is an artifact of a submission, and an organizer who is also a speaker gets a separate account (the globally-unique user_email_idx already forces a distinct address and answers with a loud 409).
