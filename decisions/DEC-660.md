# DEC-660: One merge-field vocabulary: the per-surface resolvable sets and the 100-recipient cap are declared once in pure core and reach the SPA through a single boundary module

Three hand-maintained copies exist: MERGE_FIELDS (src/mail/render.ts:5, seven fields), COMPOSE_MERGE_FIELDS (app/src/pages/comms/types.ts:6, five), BULK_EMAIL_MERGE_FIELDS (app/src/pages/contacts/types.ts:90, three) -- plus BULK_EMAIL_RECIPIENT_CAP=100 mirroring MAX_COMPOSE_RECIPIENTS=100. Each set encodes a real server fact: which vars that send path actually supplies, so a chip offering anything else is a control whose only outcome is a preflight rejection (the DEC-608 rule). Hand-copied vocabularies drift, and these are the vocabulary that decides whether an email to a real speaker renders. DEC-002 made pure core node/cf-free precisely so a browser bundle could share it; exactly ONE app-side module crosses the boundary so the blast radius on the bundle budget stays measurable.

## Amendment (wave 53): every server-enforced numeric bound the SPA restates is declared once in pure core and crosses through one boundary module

DEC-660 already says the 100-recipient cap "is declared once in pure core and reaches the SPA through a single boundary module" — app/src/lib/merge-fields.ts:13 re-exports MAX_COMPOSE_RECIPIENTS and BulkEmailModal.tsx:7 imports it. ComposeWizard.tsx:35, the very surface the cap is named for, declares `const RECIPIENT_CAP = 100` and prints it in three sentences (:447, :506, :755); a decision that names its own boundary module and is not applied at the biggest consumer is a decision with no code. The rule generalizes: a bound the server ENFORCES and the client STATES (or disables a control against) has one declaration in src/domain/**, and app/ reads it through a named crossing — otherwise the client's stated boundary and the server's enforced one drift silently and the user meets a 400 the UI promised was safe. Scan-locked so the next copy fails at the test, not at the gate.
