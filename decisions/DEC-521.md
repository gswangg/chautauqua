# DEC-521: The acceptance write path inserts task_assignment rows set-based and carries an explicit per-request write-burst bound, refused before the first write

`src/server/repo/submissions/status.ts:156-163` issues one sequential `db.insert(schema.taskAssignment)` per planned (contact, title) pair. `src/routes/api/submissions.ts:364-379` accepts up to `parseBoundedIdArray`'s default 1000 ids (`src/server/http.ts:63`), so a single bulk accept at the stated 2k-submission scale target can issue roughly 5,000-10,000 serial D1 statements in one request -- while every sibling bulk path already bounds itself by name: `MAX_AUTO_SCHEDULE_PLACEMENTS` (`the former src/server/repo/agenda.ts:442 (now split across src/server/repo/agenda/)`, which also demonstrates the chunked multi-row insert at :509-511) and `MAX_IMPORT_WRITE_STATEMENTS` (`src/server/repo/contacts/import.ts:59`). This is the last unbounded write burst in the product and it sits on the single most-clicked producer action (J5 bulk accept). Decision: (a) the per-pair loop becomes rows built in memory plus chunked multi-row `values(rows.slice(...))` inserts at `ID_CHUNK_SIZE`, mirroring agenda.ts exactly (DEC-492: set-based beats per-row); (b) a named `MAX_ACCEPTANCE_TASK_ASSIGNMENTS` bound is checked against the planned pair count and, when exceeded, throws `ApiError('invalid', ...)` naming the cap -- NOT a silent slice. Auto-schedule may silently overflow because J9 warns-never-blocks and surfaces the unplaced count; a dropped onboarding assignment is invisible and would show up months later as a speaker who was never asked for their hotel form. (c) The check runs before any write, which DEC-079's planning-before-commit ordering already guarantees leaves every firing submission un-accepted, so a refusal is atomic and a retry in smaller batches is clean.
