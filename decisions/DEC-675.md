# DEC-675: An import speaks the product's OWN closed vocabularies, and an imported participant is RECORDED, not PUBLISHED

The Sessionboard importer passes file cells straight into columns the rest of the product treats as closed vocabularies. src/server/repo/import/sessionboard.ts:354 writes `plan.values.status ?? "pending"` into submission.status, so a Sessionboard export saying "Accepted"/"Confirmed"/"Declined" lands a value that every status filter, the pipeline, and visibleSessionConditions()'s `status='accepted'` silently disagree with; :258 writes `role: v.role ?? "speaker"` bypassing domain/participant-roles.ts's PARTICIPANT_ROLE_OPTIONS so participantRoleLabel() renders an unlabelled role; :259 and :279 bind `Number.parseInt(v.order, 10)`, i.e. NaN, for any non-numeric order cell. Worst, :260-261 writes `visible: true` with `inviteStatus: "none"` — exactly visibleParticipantConditions() (src/server/repo/public/gates.ts:36-42) — so an organizer's import instantly publishes every imported name and email onto /e/<slug>/speakers for any accepted+approved session. That is the same gate-bypass DEC-656 closed on the speaker side, while the organizer's own add-speaker path deliberately writes invite_status='invited' precisely so it is not publicly visible; an importer must not be the one door that skips the gate. Per DEC-613 the planner is the ONE path dry run and real run share, so vocabulary validation belongs in src/domain/sessionboard.ts (pure core) where the dry run NAMES the offending row and value before anything is written — never as a silent coercion in the writer.
