# DEC-158: CNT-11 session content history: submission_revision post-edit snapshots appended by both the admin PATCH path and the portal-edit locked-field sync; restore re-applies a snapshot through the same path

CNT-S3 steps 7-9 require a history panel with two timestamped entries attributed to the editing organizer and a restore that removes only the later edit. Design: `submission_revision` (id, submission_id, editor_user_id nullable, editor_name text snapshot, title, description, created_at) where each successful title/description change appends a row snapshotting the POST-edit state — 'restore the version prior to the second edit' is then a direct application of the first entry's snapshot. Appends happen in exactly two write paths that already sync submission.title/description: the organizer PATCH /submissions/:id handler and src/server/repo/portal-edit.ts's locked-field sync (editor_name = the speaker's contact name), and only when the values actually change. POST /submissions/:id/revisions/:revisionId/restore (organizer-only) applies the snapshot through the same update path so the restore itself lands in history attributed to the restorer. GET /submissions/:id/revisions returns the standard list envelope newest-first. Never sends email; no schema change to submission itself.

## Amendment (wave 59): content history must contain the version before the first edit, and Restore never silently no-ops

VERIFIED on main: src/server/repo/revisions.ts:28 documents appendSubmissionRevision as snapshotting the POST-edit state, and both writers (src/routes/api/submissions.ts:442-450, src/server/repo/portal-edit.ts:318) append only after the change. Two consequences neither was written down: (1) the content a submission was SUBMITTED with is never stored anywhere, so the first edit destroys it irrecoverably and 'History' cannot restore the one version a producer most wants back; (2) the newest revision always equals the current row, so Restore on it is a guaranteed no-op that returns 200 and reports success — which is exactly the externally-filed 'History Restore has no visible effect' defect, and with a single edit it is the ONLY restore the UI offers. A control that changes nothing and says nothing is broken whichever half is at fault. RULING: (a) a BASELINE revision is written on the first content-changing edit, capturing the PRE-edit title/description at the submission's own createdAt, attributed to the stated value `AS_SUBMITTED_EDITOR` ("As submitted") — a stated value, never a fabricated person; it is written only when the submission has zero revisions, so it costs one count on the first edit and nothing thereafter. (b) listSubmissionHistory never renders the baseline as its own 'Edited by' line — it attaches to the existing `submitted` entry, and EVERY history entry gains `revisionId: string | null` so the timeline says which entries are restorable instead of the SPA inferring it from `kind === 'edited'`. (c) POST .../revisions/:revisionId/restore REFUSES loudly when the revision's title+description already equal the current content ('This version is identical to what is there now — nothing to restore.') rather than returning an unchanged 200. (d) the rendered history timestamp carries seconds, so two edits inside one minute are distinguishable rows rather than two identical-looking ones Restore cannot be aimed at.

## Amendment (wave 78): seconds precision is a property of the SURFACE CLASS — successive events on one object — not of the one page that asked for it

formatDateTimeWithSeconds (app/src/lib/dates.ts:111-117) was minted at wave 59 with its population stated in its own doc comment: 'surfaces where two events can land inside the same minute (e.g. a submission's edit history)'. It has exactly ONE reader, SubmissionDetailPage.tsx:1812. The declared population has at least two more members, both of which render one object's own version chain with minute granularity: app/src/pages/content/VersionList.tsx:127 (the organizer's deliverable version history — the CNT judge's 'v1/v2 identical timestamps' finding, docs/eval-findings.md freeze-lane item 9 and P3 item 22) and src/routes/portal/tasks/views.tsx:64 (the speaker portal's DEC-605 task-file version history, in the event's own timezone through formatEventDateTime). Ruling: a list whose rows are SUCCESSIVE STATES OF ONE OBJECT renders seconds, in whichever grammar home that runtime already uses — app/src/lib/dates.ts for the SPA, src/lib/event-time.ts for SSR (which gains formatEventDateTimeWithSeconds, keeping the DEC-408 zone abbreviation and the DEC-918 date order). A list of DIFFERENT objects (files library, recent sends, token rows) keeps the minute grammar: there, two rows sharing a minute are not ambiguous.
