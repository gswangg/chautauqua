# DEC-009: Status pipeline semantics and idempotent acceptance side effects

Producers may set any of the five statuses from any other (Sessionboard's pill allows it; canonical flow is pending → queues → final). Two hard invariants enforced in the domain layer, unit-tested directly: (1) status changes NEVER send email — no mailer reference is reachable from the status-change path; (2) the first transition into 'accepted' fires J6 auto-creation exactly once, guarded by submission.accepted_at being null (idempotent on retries and re-accepts). Acceptance planning is a pure function returning descriptors of records to create: speaker participant/portal access confirmation plus DEFAULT_ONBOARDING_TASKS constant = [hotel stay requirement form (kind 'form', required), flight reimbursement form (kind 'form', required), finalize talk description ('general'), finalize bio + headshot ('file_request'), announce participation ('general')] — the two must-have forms per swyx clarifications. Un-accepting does not delete created records.

## Amendment (wave 59): the canonical "Finalize bio + headshot" onboarding task is PROFILE-backed, not deliverable-backed

DEC-009's canonical set (src/domain/acceptance.ts:18-24) declares "Finalize bio + headshot" with kind 'file_request'. A file_request assignment uploads a SUBMISSION deliverable whose kind must be one of FILE_KINDS = presentation|poster|handout|recording (src/domain/files.ts:11) — there is no headshot kind there, and the real headshot path is a different one entirely (validateHeadshotUpload, 8 MB, png/jpg/jpeg/webp, writing contact.headshot_url, which is what the public speakers/gallery surfaces read). So the one task whose name promises a bio and a headshot cannot produce either: the speaker uploads a mis-typed session file, the assignment flips to complete, the J6 dashboard says the speaker is done, and the public programme still has no photo and no bio. SPEC J6 lists this task as a must-have and J7 requires portal bio/headshot edits to appear on the producer's record instantly — the two are currently unconnected. RULING: the task becomes kind 'general' with a portal card that links to /portal/profile, and saving the portal profile completes it — set-based, idempotent, only when the contact ends that save with BOTH a non-empty bio AND a headshot present; completion is terminal (later clearing a field does not reopen it, mirroring the accepted_at 'stamp once' rule). The title is matched through ONE exported constant, never a duplicated string literal — legitimate because migration 0032 makes (event_id, title) unique and DEC-111 already keys form tasks by exact title.
