# DEC-979: A task assignment and a pipeline entry are JOIN rows, not documents: contact delete cascades them (and the dialog names the cascade); only rows that would lose a document keep refusing

DELETE /contacts/:id (src/routes/api/contacts/crud.ts:293-347) refuses whenever listContactReferenceRows finds ANY task_assignment or pipeline_entry, and tells the organiser to "remove them from those sessions and tasks first" — but the product has no way to remove either: there is no DELETE for a task assignment (src/routes/tasks.ts exposes only PATCH /task-assignments/:id) and no DELETE for a pipeline entry (src/routes/api/pipeline.ts has GET/POST/PATCH/notes only). Combined with DEC-921, which deliberately KEEPS assignments when the submission that put the contact on the roster is deleted (src/server/repo/submission-delete.ts:266-277), deleting a speaker's only session makes that speaker permanently undeletable: an irreversible refusal whose instructions name an action that does not exist. A task_assignment's whole identity is the pair (task, contact) — its content lives elsewhere (the file is owned by the submission, the response is a form answer) and its existence is a derived expansion of the accepted-speaker roster (DEC-746/DEC-932); a pipeline_entry + its activity is relationship history about that one person, which the merge path already carries rather than treats as an independent document (DEC-282). Both therefore cascade with the contact, chunked and set-based, and the delete confirmation states the cascade before it happens. The refusal classes that remain are the ones where something else would lose its meaning: a participant row (a submission would lose an author, removable from the submission editor) and a login (removable in Settings > People). A refusal may only name work the organiser can actually do.

## Amendment (wave 42): `email_log.contact_id` is an optional index key, never an identity-bearing FK, so `deleteContact` leaving it dangling is deliberate, not a defect

task-w42-c triaged a review-lens claim that `deleteContact` (src/server/repo/contacts/crud.ts:285-302) never repoints or clears `email_log.contact_id` for the deleted contact's rows, unlike the merge path (`mergeOnePair`, src/server/repo/contacts/merge.ts:602-603, which repoints it as one of the seven CONTACT_FK_TABLES). The column is nullable (`text("contact_id")`, src/db/schema/email.ts:31 — no `.notNull()`), and DEC-006 already establishes why: DevSinkMailer "writes one email_log row per recipient with full rendered content inline" — subject, body_text, body_html, ics_text, and (load-bearing here) `to_email` are all snapshotted at send time, so an email_log row's displayed recipient identity is `to_email`, never a live join back to `contact`. Enumerated every reader of `schema.emailLog.contactId` under src/server/repo/** and src/routes/**: `repo/email.ts`'s `emailLogConditions`/`SELECTED_COLUMNS` only use it as an optional caller-supplied filter/passthrough column (never joined to `contact` for display — the rendered recipient is always `to_email`); `repo/contacts/history.ts` filters by the CURRENTLY-VIEWED live contact's own id, so a different contact's deletion can't affect it; `repo/submissions/history.ts:74`'s `INNER JOIN emailLog.contactId = participant.contactId` is provably unreachable for a deleted contact, because this same DEC's refusal-class rule keeps a participant row a hard refusal (deleteContact cannot run while any `participant` row still points at that contact), so no `email_log` row can ever dangle against a `contactId` that also still has a matching `participant` row. No reader path breaks, drops rows unexpectedly, or renders an unresolvable recipient. Ruling: `email_log.contact_id` is retained ONLY as a best-effort filter/index convenience once a contact still exists (e.g. "show this contact's emails"); once the contact is gone the row's own inline fields remain the complete and correct record, and `deleteContact` leaving `contact_id` dangling (rather than nulling or blocking on it) is deliberate, matching how `email_log` is documented and read everywhere else in the codebase. If a future feature ever joins `email_log` to `contact` for display (rather than filtering by a live contact's id), that feature — not `deleteContact` — must handle the missing-contact case, e.g. with a `leftJoin` and a "deleted contact" fallback label.
