# DEC-948: A rate limit is an atomic counter in D1, never a read-modify-write against KV

checkAndIncrementScopedLimit (src/lib/rate-limit.ts:58-63) does `get` → compare → `put`, and peek/increment (DEC-180's split) do the same across two awaits. KV is an eventually-consistent, edge-cached store with no compare-and-set, so N concurrent public CFP submits or login attempts all read count=0, all pass the cap, and all write 1 — the cap is enforced only against a strictly serial attacker. The unit tests pass because their in-memory fake is strongly consistent and single-threaded, which is precisely how a nominally-met requirement stays unmet: SPEC §6 asks for rate limits on auth and public submission and what ships is an advisory counter. The house rule is already written down — atomic SQL beats read-then-write — and D1 is bound on every one of these requests. Rule: the counter moves to D1. A new table `rate_limit(key text primary key, count integer not null, expires_at integer not null)` with an index on expires_at; migrations/0030_rate_limit.sql plus the drizzle table. A new src/server/repo/rate-limit.ts exports the SAME four names the callers already use — peekScopedLimit, incrementScopedLimit, resetScopedLimit, checkAndIncrementScopedLimit — with `db: Db` as the first argument in place of `kv: KVStore`, so the call sites change by one argument and one import. The increment is ONE statement, `insert … values(key,1,expires) on conflict(key) do update set count = rate_limit.count + 1 returning count`, and the decision is made on the RETURNED count, so N concurrent callers get N distinct counts and exactly one of them is the one that crosses the cap. Expired rows are pruned by a bounded set-based `delete from rate_limit where expires_at <= ?` issued alongside the write, never by a scan or a per-key sweep. The pure key builders (boundRateLimitId DEC-457, scopedRateLimitKey, requestIpFromHeaders DEC-072) stay in src/lib/rate-limit.ts and are imported by the repo; the four KV-taking counter functions are DELETED, not left as a shim. DEC-180's semantics are unchanged: login peeks before verifying, increments only on a confirmed failure, and clears the per-identity budget on success.

## Amendment (wave 49)

A serial per-row write is a SCANNED class, not a per-wave rediscovery. Waves 46, 47 and 48 each independently found a different loop issuing one D1 write per iteration after the read half had already been batched ("BATCHING LANDS ON THE READ NOT THE WRITE", twice). Finding instance N+1 by hand each wave is the failure. DEC-948 already establishes the principle for the rate limiter (one atomic statement, never read-then-write); generalise it into a ledgered scan so the class cannot recur silently: every `for`/`while` under src/routes/** or src/server/repo/** whose body awaits `db.insert|db.update|db.delete` must EITHER iterate a chunk helper (chunkIds/chunkRowsForInsert) OR appear in the test's ledger with a one-line reason. Both directions fail: an unlisted offender fails, AND a ledger line that no longer matches any site fails with an explicit "delete this line" message — a hand-listed manifest that cannot desync (the shape wave 48 used for contact-referencing columns).

## Amendment (wave 19): a scan's root is ALL of src unless it names its exclusions and enforces that the naming stays complete

Wave 18 caught two D1 chunk scans measuring two directories someone remembered. test/serial-write-scan.test.ts has the same defect and was not in that wave's scope: SCAN_DIRS = ["src/routes", "src/server/repo"], so src/server/auth-session.ts, src/server/context.ts, src/server/scheduled.ts, src/sync/**, src/domain/**, src/auth/**, src/mail/** and src/lib/** have never been in frame for the serial-per-row-write class, and the test's own title honestly advertises the narrow root. The durable fix is not "add the directories someone remembers this time": it is to walk all of src with an EXPLICIT excluded-roots list where each entry states its reason, plus an assertion that every top-level entry under src/ is either scanned or excluded-with-a-reason — so the next directory added to src cannot silently fall out of the guard's claim. Comments are stripped before matching: a DEC citation in a JSDoc is not a call site.


## Amendment (wave 27): an auth budget is check-and-increment-then-reset, never peek-then-verify-then-increment

DEC-948 exists to forbid read-then-write limiters, but /login and /account/password still peek (read-only), run PBKDF2, and only then increment -- so N concurrent attempts all read the same pre-increment count and all reach the 100k-iteration derivation. DEC-180's real requirement is that a SUCCESS must not consume the budget, and that is preserved by the reverse order: increment atomically first (checkAndIncrementScopedLimit), and resetScopedLimit the per-identity bucket on success. The per-IP bucket (max 100) is a source budget and stays consumed by successes. peekScopedLimit keeps no auth call site after this.

## Amendment (wave 62): a write's echo comes from the write — `.returning()`, never a second SELECT of the row just written

updateAssignmentStatus (src/server/repo/tasks/crud.ts:472-490) issues an UPDATE and then a full SELECT of the same row to build its response — two round trips on the highest-frequency organizer write in the product (task check-off, ~140ms, the last unclaimed P1-perf item), and an echo that can report a concurrent writer's value rather than this call's. This is the mirror of the read-then-write DEC-948 already forbids, and the repo has the established remedy in five places (rate-limit.ts:80, files-content-status.ts:133, participants.ts:126, profile.ts:240, recusal.ts:54). RULING: any repo write whose only follow-up read is the row it just wrote uses `.returning()` on the SAME statement; an empty returning array IS the not-found case and keeps the existing fail-loud throw verbatim. No route contract, response shape or error message changes.
