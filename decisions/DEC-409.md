# DEC-409: The 2px olive focus ring is declared in both stylesheet roots, and no rule may remove an outline

The mandate is explicit — "Focus: 2px olive outline, 2px offset" — and the accessibility section rests the AA claim partly on it. app/src/styles.css:82-85 has it; `grep -rn focus-visible src/` returns nothing, so every server-rendered surface (the five public event pages, /submit/:slug, /portal and its five sub-routes, /login, /account/password, /docs/api, /dev/mailbox) falls back to whatever the browser draws — which on the oat/olive palette is neither the designed treatment nor reliably visible. The public CFP form is a keyboard-navigated form filled by strangers with no account; it is the last surface that should be guessing. The rule goes in THEME_CSS beside the a:hover rule (outside the 700px block, so it applies at every width), and a conformance guard in the same shape as test/phone-wrap-conformance.test.ts asserts both roots declare it and that no scanned stylesheet contains `outline: none` or `outline: 0` — the only way this regresses is someone silencing the ring, so that is the thing the test watches. app/src/styles.css and src/views/theme.ts remain ONE lane (DEC-368/372/404); styles.css needs no edit, but the lane owns it so nothing else touches it this wave.

## Amendment (wave 35): the focus ring and its sibling interaction states are proven by MEASUREMENT in the render sweep, not by a stylesheet source scan

DEC-409 rules that the 2px olive focus ring is declared in both stylesheet roots and that no rule may remove an outline — and it is enforced today by reading CSS text. The mandate's standing rule, added after a falsified closure, is that items close on measured or runtime evidence only: a source read proves intent, not behaviour, and the settings cascade defeat (an unscoped `.chq-settings-panel > div` silently beating four intended rules at higher specificity) is the same failure in CSS form — every source scan passed while nothing rendered differently. The render-sweep gate already measures live computed values in CI for the font floor and the type roles, so the machinery exists. RULING: the three deterministically measurable B8 states join it — focus (outline width/style/color/offset against DEC-409 and DESIGN-RULINGS §B8), hover (row background #EFEBDF with no layout shift, measured as an unchanged element box), and disabled (#8E8A7A on #DDD8C8) — as pure evaluators plus a Playwright driver, following the existing evaluate*/format*/all*Passed trio shape. A measured deviation is fixed at the shared token or class, never by loosening the expectation.

## Amendment (wave 25): an interaction-state row that never resolves is a failing instrument, and focus must be measured the way a keyboard user creates it

Two advisory rows are unusable as evidence. The `cfp-primary-focus` row measured `.chq-cfp-step-next` as outline-style:none, yet src/views/theme.ts:170 declares `:focus-visible { outline: 2px solid var(--chq-brand); outline-offset: 2px; }`, --chq-brand IS #4E5C31 (theme.ts:55 — exactly the expected value), and the submit page inlines THEME_CSS before CFP_CSS (src/routes/public/submit-views.tsx:47-69): the probe focuses programmatically, which does not satisfy :focus-visible for a <button> in Chromium, so it measured a state no user ever sees. The `review-anonymize-disabled` row reports 'selector never resolved' although `.chq-review-field-disabled` is real markup rendered when planHasSubmittedReview (app/src/pages/review/PlanEditor.tsx:1337-1345). RULING: a focus expectation is measured after keyboard-induced focus, never script .focus() alone; and an instrument-blocked row is either re-pinned to a route/state where its selector resolves or deleted with its reason inline — it never stands as a permanent advisory. If the ring is still absent after the probe is corrected, THAT is a product defect and gets recorded, not patched blind.
