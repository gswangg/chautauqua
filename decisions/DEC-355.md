# DEC-355: Bulk acceptance planning becomes set-based: a bulk status change issues O(ids/90) + O(distinct task titles) statements, never O(ids) x O(tasks); DEC-079's plan-before-commit ordering is preserved

DEC-079 specified "firing rows handled individually (planning, then update with accepted_at=now)" for retry-exactly-once, and that ordering is right. Its cost was never examined at SPEC §0 scale. src/server/repo/submissions/status.ts:284-308 loops per firing row, each iteration running ensureOnboardingTasks (:129-149 a participant SELECT plus an existing-titles SELECT) plus up to five getOrCreateTask SELECT/INSERT pairs (:68-101, each possibly creating a backing form per DEC-111) plus its own UPDATE. Accepting 500 submissions — mid-range for SPEC §0's 500-5,000 and well under parseBoundedIdArray's 1,000 default — is roughly 6,000 sequential D1 statements in one request, against SPEC §7's "writes p95 < 100 ms" and SPEC §0's "every list view, bulk action, and query must be designed for the top of these ranges." DEC-333's conjunctive test is met: cost scales with the id set and it is observable on local D1 (scripts/walkthrough/scale.ts:265 already bulk-accepts >100 ids). Rule: collect the firing rows first, then ONE chunked participant SELECT across all firing submissionIds, ONE chunked existing-(contact,title) SELECT over the deduped active contacts, ONE planAcceptance call over that deduped set, getOrCreateTask once per distinct title, the task_assignment INSERTs, and only then ONE chunked UPDATE setting status/acceptedAt/updatedAt over the firing ids. Planning still precedes every commit, so a throw leaves zero rows accepted and a retry re-plans idempotently — strictly safer than today's partial-accept window. Per-assignment INSERTs may stay one statement each (they are already proportional to distinct new (contact,title) pairs, and a multi-row INSERT is not required). The DEC-133 full-set guard, the DEC-009 no-mailer invariant and the DEC-278 single-contact entry point are untouched, and the resulting task/form/task_assignment rows must be identical — any existing test whose assertions have to change is evidence the change went too far (DEC-346's rule).
