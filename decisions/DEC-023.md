# DEC-023: Onboarding grid API, task CRUD, and due-date reminder cron

J6's grid UI and API ship in parallel tasks, and reminders must be schedule-driven, never decision-driven (SPEC §2.4). Grid: GET /api/v1/events/:eventId/onboarding -> { tasks: [{ id, kind, title, dueDate, required }], rows: [{ contact: { id, name, email, company, hasAccount }, cells: [{ taskId, assignmentId, status, completedAt, fileId, lastRemindedAt }] }] } covering every contact with at least one assignment in the event, built from joined queries (no N+1). Task CRUD (organizer + csrfJson): POST /api/v1/events/:eventId/tasks { kind, title, description?, dueDate?, required, formId?, assignToAllAccepted?: boolean }; PATCH/DELETE /api/v1/tasks/:id; POST /api/v1/tasks/:id/assign { contactIds }. Assignment status: PATCH /api/v1/task-assignments/:id { status: 'pending'|'complete' } sets completedAt/completedBy(acting user); allowed for organizers, and for speakers on their own assignments (the portal wires this in a later wave). Bulk remind: POST /api/v1/events/:eventId/onboarding/remind { taskIds? } sends ONE email per contact listing their outstanding tasks via {task_list}/{due_date} merge fields, stamps last_reminded_at, returns { sent }. Cron: pure planner src/domain/reminders.ts planReminders({ assignments, now }) selects incomplete assignments that are overdue or due within 72h whose lastRemindedAt is null or older than 24h, grouped per contact; src/index.ts scheduled() calls an exported runDueReminders(env) that sends via the DEC-006 mailer and stamps last_reminded_at. Acceptance-time auto-creation stays with the DEC-009/DEC-016 status endpoint — this API never creates the default task set itself.

## Amendment (wave 48): the reminder fan-out's WRITE half is set-based too — last_reminded_at is stamped once after the send loop, never once per recipient inside it

src/server/repo/tasks/reminders.ts:223-229 stamps `last_reminded_at` with a chunked UPDATE issued INSIDE the per-recipient send loop. Wave 46 batched this same fan-out's READ half (`resolvePortalLinks` at :184, see DEC-530's wave-46 amendment) and left the write half behind, so a capped reminder batch still pays one sequential D1 UPDATE per successfully-emailed recipient, interleaved with the mail sends. The invariant is the one the read half already obeys: the loop contains no I/O. Ruling: accumulate the assignment ids of every recipient whose email send succeeds, and issue ONE chunked UPDATE after the loop completes, stamping the same shared `now` timestamp for all of them. This preserves every existing semantic — a failed send still stamps nothing for that recipient, `sent` still counts recipients accurately, and the timestamp value is unchanged from today's per-recipient stamp.
