# DEC-023: Onboarding grid API, task CRUD, and due-date reminder cron

J6's grid UI and API ship in parallel tasks, and reminders must be schedule-driven, never decision-driven (SPEC §2.4). Grid: GET /api/v1/events/:eventId/onboarding -> { tasks: [{ id, kind, title, dueDate, required }], rows: [{ contact: { id, name, email, company, hasAccount }, cells: [{ taskId, assignmentId, status, completedAt, fileId, lastRemindedAt }] }] } covering every contact with at least one assignment in the event, built from joined queries (no N+1). Task CRUD (organizer + csrfJson): POST /api/v1/events/:eventId/tasks { kind, title, description?, dueDate?, required, formId?, assignToAllAccepted?: boolean }; PATCH/DELETE /api/v1/tasks/:id; POST /api/v1/tasks/:id/assign { contactIds }. Assignment status: PATCH /api/v1/task-assignments/:id { status: 'pending'|'complete' } sets completedAt/completedBy(acting user); allowed for organizers, and for speakers on their own assignments (the portal wires this in a later wave). Bulk remind: POST /api/v1/events/:eventId/onboarding/remind { taskIds? } sends ONE email per contact listing their outstanding tasks via {task_list}/{due_date} merge fields, stamps last_reminded_at, returns { sent }. Cron: pure planner src/domain/reminders.ts planReminders({ assignments, now }) selects incomplete assignments that are overdue or due within 72h whose lastRemindedAt is null or older than 24h, grouped per contact; src/index.ts scheduled() calls an exported runDueReminders(env) that sends via the DEC-006 mailer and stamps last_reminded_at. Acceptance-time auto-creation stays with the DEC-009/DEC-016 status endpoint — this API never creates the default task set itself.

## Amendment (wave 48): the reminder fan-out's WRITE half is set-based too — last_reminded_at is stamped once after the send loop, never once per recipient inside it

src/server/repo/tasks/reminders.ts:223-229 stamps `last_reminded_at` with a chunked UPDATE issued INSIDE the per-recipient send loop. Wave 46 batched this same fan-out's READ half (`resolvePortalLinks` at :184, see DEC-530's wave-46 amendment) and left the write half behind, so a capped reminder batch still pays one sequential D1 UPDATE per successfully-emailed recipient, interleaved with the mail sends. The invariant is the one the read half already obeys: the loop contains no I/O. Ruling: accumulate the assignment ids of every recipient whose email send succeeds, and issue ONE chunked UPDATE after the loop completes, stamping the same shared `now` timestamp for all of them. This preserves every existing semantic — a failed send still stamps nothing for that recipient, `sent` still counts recipients accurately, and the timestamp value is unchanged from today's per-recipient stamp.

## Amendment (wave 58): an automatic reminder has a TERMINAL condition — the cron's window is [due − 72h, due + 7d] and never past the owning event's local end; manual remind-now is unchanged

Verified on main: src/domain/reminders.ts:77 gates only on `a.dueDate <= now + DUE_WINDOW_MS` — no lower bound, no terminal state. Combined with onboardingTaskDueDate = eventStart − N days (src/domain/acceptance.ts:53, unclamped) and a */15 cron (wrangler.jsonc:40), any never-completed optional task emails its owner every 24h FOREVER, past the event, indefinitely. That violates SPEC §2.4 "Communications are deliberate." ## Amendment (wave 61): the cron reminder gate takes the event's timezone; a day-label due date is expanded through dayLabelEndInstant before it is compared to any instant

src/domain/reminders.ts:93/95 is the LAST reader in the product that compares a raw day-label `dueDate` (UTC-midnight epoch, DEC-522) against instants: `now > a.dueDate + REMINDER_OVERDUE_TAIL_MS` and `a.dueDate <= now + DUE_WINDOW_MS`. Its own line 59 states the contract verbatim ("dueDate is a calendar day (DEC-522), not an instant") and then breaks it two lines above. Wave 58/60 fixed all five DISPLAY readers via overdueDayCutoff/isAssignmentOverdue, which take a timeZone; the cron planner never got the parameter, so for America/Los_Angeles the 72h due window is really 88h and the 7-day terminal tail expires ~16h early, and the cron's notion of past-due disagrees with every screen. The rule: PlanRemindersInput carries `timeZone: string` and isReminderDue expands `a.dueDate` through dayLabelEndInstant(a.dueDate, timeZone) for BOTH comparisons. sendDueRemindersForEvent already has `eventTimezone` in hand and simply passes it. The SQL pre-filter in listDueReminderContactIds stays a COARSE SUPERSET (its own doc-comment says so) and is widened by one day on each side, because a lexical/ms bound on a raw day label can no longer be tight once the authoritative gate is zone-expanded — a superset that is too wide is correct, one that is too narrow silently drops a due reminder.

## Amendment (wave 47): a reminder dedupe stamp is a CLAIM, taken before the send, not a receipt written after it

`src/server/repo/tasks/reminders.ts:416-459` sends the whole batch in a loop and only then writes `lastRemindedAt` in one chunked UPDATE (`:454-459`). Two overlapping cron ticks (`src/server/scheduled.ts`, `src/routes/tasks.ts:665-698`) both read the same outstanding set through `isReminderDue` (`src/domain/reminders.ts:114-115`) and both send; a crash between the loop and the UPDATE re-sends the whole batch on the next tick. RULING: the DEC-023 dedupe window is enforced by a CONDITIONAL claim UPDATE that runs BEFORE any mail, returning the assignment ids it actually won; only claimed ids are emailed. The claim predicate is a parameter, not a constant, because `remindNow` is an explicit organizer action that deliberately ignores the dedupe window (DEC-319) — cron passes a cutoff, remindNow passes null (still stamping first, so it is idempotent under retry without being gated). A send failure RELEASES the claim back to its pre-claim value so today's retry-next-tick semantics survive; at-most-once is not an acceptable silent downgrade. Per-(assignment,day) uniqueness was rejected as the mechanism: it would need a new table and a migration to express something a conditional UPDATE ... RETURNING already expresses atomically on D1.

## Amendment (wave 82): a loud invariant is evaluated BEFORE the computation it guards

`src/server/repo/tasks/reminders.ts:807` calls `zonedMinutesToUtc(eventEndDate, 24*60, eventTimezone)` and only then, at `:809`, throws `no event timezone resolved for eventId ...`. An event row with an empty timezone (or empty end_date) therefore never reaches the named error — it dies inside `Intl.DateTimeFormat` with an opaque `RangeError`, which `runDueReminders` folds into `failedEventIds`, and that event's speakers stop getting due-date reminders with nothing diagnosable in the envelope. A guard placed after its subject is not a guard; the fail-loudly principle is about the MESSAGE reaching the operator, not about something throwing. Both preconditions (timezone, end date) are checked, by name, before the first computation that consumes them.

Ruling: the pure planner gains two terminal conditions — (1) REMINDER_OVERDUE_TAIL_MS = 7 days after the effective due date, so an ignored task stops chasing after a week of chasing; (2) the owning event's local end instant (zonedMinutesToUtc(endDate, 1440, timezone)), so a finished event never reminds anyone of anything. No new column, no migration: both facts are already readable. planManualReminders (the organizer's explicit "remind now") deliberately keeps overriding every window — it is a decision, not a schedule. The cron's event enumeration also gains a COARSE SQL pre-filter on event.end_date so a decade of dead events isn't re-scanned every 15 minutes; that pre-filter must be a strict SUPERSET of what the planner accepts (2-day slack for any timezone), and the planner stays the single authoritative gate — never two gates that can disagree.

## Amendment (wave 9, sha 3323a7b7): the reminder path's manual half takes no timezone — delete the dead parameters and the two silent `?? ""` fallbacks that feed them

Verified on main: `buildReminderMessage`'s second parameter is admitted unused in its own comment (`src/server/repo/tasks/reminders.ts:345-348` — `dueDate` is a DEC-522 calendar day, so `formatTaskLines` needs no zone); `planManualReminders` (`src/domain/reminders.ts:174-204`) accepts `PlanRemindersInput` but never reads `input.timeZone`; and `remindNow` (`:578`) and `previewRemindNow` (`:649`) each compute `outstanding[0]?.timezone ?? ""` for the sole purpose of feeding those two dead parameters. Only the cron path really consumes the value, and it alone carries the fail-loud guard the wave-58 amendment installed (`:807`). A parameter every caller must compute and nothing reads is the same lie as an unread setting (DEC-851/DEC-988), and the `?? ""` fallbacks are exactly the silent-empty shape that made the cron path need a named error in the first place. Ruling: the manual planner gets its own input type without `timeZone`, `buildReminderMessage` loses the parameter, the two dead resolutions go, and the cron path's guard + `zonedMinutesToUtc` are left untouched.
