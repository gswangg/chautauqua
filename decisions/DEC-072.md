# DEC-072: Rate limits keyed by identity, not only by IP: login = per-email 20/15min + per-IP flood guard 100/15min; public submit = per-IP 60/hour

The current limiter keys only on IP with a constant 'unknown' fallback and trusts the first x-forwarded-for hop (src/lib/rate-limit.ts:43-49), so one NAT/localhost collapses all users into one bucket — 20 logins/15min bricks the spec's 5-15 concurrent users and local eval runs — while an attacker rotates XFF to bypass. Fix: login checks two scopes — 'login-user' keyed on trimmed lowercase email (20/15min, the spoof-proof anti-brute-force budget that protects the account regardless of source) and 'login-ip' (100/15min flood guard, where 'unknown'/shared IPs are acceptable because the identity key carries correctness). Public submit stays per-IP (attacker-chosen emails would only multiply budget) but the cap rises 10→60/hour so a shared office IP cannot brick J2 while floods still throttle. Claim route unchanged (tokens are unguessable single-use). XFF spoofability is documented; stage 2 sits behind Cloudflare where cf-connecting-ip is authoritative.

## Amendment (wave 10): the one unauthenticated write endpoint keys its limiter on IDENTITY as well as IP

src/lib/rate-limit.ts:43-55 states the rule in its own doc comment: x-forwarded-for is client-controllable and trivially spoofable, cf-connecting-ip is only authoritative behind Cloudflare's edge, and 'callers that need real correctness MUST also key a scoped limiter by a stable identity value'. POST /login obeys it with two independent budgets, login-user + login-ip (src/routes/auth.tsx:324-333). The public CFP submit — the ONLY unauthenticated endpoint in the product that writes contacts, submissions and R2 objects and then sends mail — does not: src/routes/public/submit.tsx:339-344 checks scope 'submit' keyed on `ip` alone, where `ip` falls back through x-forwarded-for to the literal 'unknown' (rate-limit.ts:56-62). A rotating header defeats it entirely. The IP check must STAY where it is (before parseBody, deliberately, so its 429 page honestly shows an empty answer set). RULING: a SECOND scoped budget, keyed on the normalised submitted email, runs after validation succeeds and before the first write — submit.tsx computes `email` at line 479, immediately above findContactByEmail at 486, which is exactly the seam. Scope 'submit-email'. Its 429 re-renders SubmitPage with the submitter's parsed answers and track selection intact, unlike the pre-parse IP path. Neither budget is a substitute for the other: IP catches one source hammering many identities, identity catches one address hammering from many spoofed sources.
