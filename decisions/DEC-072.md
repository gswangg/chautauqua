# DEC-072: Rate limits keyed by identity, not only by IP: login = per-email 20/15min + per-IP flood guard 100/15min; public submit = per-IP 60/hour

The current limiter keys only on IP with a constant 'unknown' fallback and trusts the first x-forwarded-for hop (src/lib/rate-limit.ts:43-49), so one NAT/localhost collapses all users into one bucket — 20 logins/15min bricks the spec's 5-15 concurrent users and local eval runs — while an attacker rotates XFF to bypass. Fix: login checks two scopes — 'login-user' keyed on trimmed lowercase email (20/15min, the spoof-proof anti-brute-force budget that protects the account regardless of source) and 'login-ip' (100/15min flood guard, where 'unknown'/shared IPs are acceptable because the identity key carries correctness). Public submit stays per-IP (attacker-chosen emails would only multiply budget) but the cap rises 10→60/hour so a shared office IP cannot brick J2 while floods still throttle. Claim route unchanged (tokens are unguessable single-use). XFF spoofability is documented; stage 2 sits behind Cloudflare where cf-connecting-ip is authoritative.

## Amendment (wave 10): the one unauthenticated write endpoint keys its limiter on IDENTITY as well as IP

src/lib/rate-limit.ts:43-55 states the rule in its own doc comment: x-forwarded-for is client-controllable and trivially spoofable, cf-connecting-ip is only authoritative behind Cloudflare's edge, and 'callers that need real correctness MUST also key a scoped limiter by a stable identity value'. POST /login obeys it with two independent budgets, login-user + login-ip (src/routes/auth.tsx:324-333). The public CFP submit — the ONLY unauthenticated endpoint in the product that writes contacts, submissions and R2 objects and then sends mail — does not: src/routes/public/submit.tsx:339-344 checks scope 'submit' keyed on `ip` alone, where `ip` falls back through x-forwarded-for to the literal 'unknown' (rate-limit.ts:56-62). A rotating header defeats it entirely. The IP check must STAY where it is (before parseBody, deliberately, so its 429 page honestly shows an empty answer set). RULING: a SECOND scoped budget, keyed on the normalised submitted email, runs after validation succeeds and before the first write — submit.tsx computes `email` at line 479, immediately above findContactByEmail at 486, which is exactly the seam. Scope 'submit-email'. Its 429 re-renders SubmitPage with the submitter's parsed answers and track selection intact, unlike the pre-parse IP path. Neither budget is a substitute for the other: IP catches one source hammering many identities, identity catches one address hammering from many spoofed sources.

## Amendment (wave 54): the per-identity login budget is keyed on (email, IP) — an unauthenticated stranger must never be able to lock a producer out of their own event

Verified on main: src/routes/auth-login.tsx:91 spends the `login-user` budget keyed on the bare email at ADMISSION, before the password is checked, and refunds it (:158) only after a confirmed success; AUTH_RATE_LIMIT_MAX=20 per 900s (src/routes/auth-helpers.ts:16-17). So twenty wrong-password POSTs per fifteen minutes against a known organizer address — a wholly unauthenticated act, on an address printed on the CFP page — hold POST /login at 429 for that account forever, and there is no unlock path: a password reset does not clear the bucket, because login is refused before any credential is read. DEC-072 chose per-email keying to stop credential stuffing and explicitly rejected per-IP-only keying; it did not consider that a per-victim key is a per-victim weapon. Both goals survive if the key names BOTH parties: the attacker can only spend the budget they share with the victim. RULING: the identity bucket's key is `email|ip` through one exported builder (never a second hand-assembled key string), max and window unchanged at 20/900s; the per-IP flood guard stays at 100/900s; consume-then-refund and the DEC-948 atomic checkAndIncrement stay exactly as they are, because the derivation-cost bound they protect is still enforced by both buckets. The IP is the existing requestIpFromHeaders (src/lib/rate-limit.ts:56), which prefers the edge-set cf-connecting-ip — trustworthy in production, and an attacker who can rotate it is already inside the per-IP guard's threat model rather than this one's.

## Amendment (wave 62): save-draft takes the same two-budget shape as final submit — a per-email budget beside the per-IP one

src/lib/rate-limit.ts:43-55 states the rule in its own doc-comment: x-forwarded-for is client-controllable, cf-connecting-ip is only authoritative behind the edge, and therefore "callers that need real correctness MUST also key a scoped limiter by a stable identity value (such as the submitted account email) rather than relying on IP alone." The final-submit handler obeys it (src/routes/public/submit.tsx:545, scope "submit-email", max 10, with a comment saying it exists to close "the spoofed-x-forwarded-for gap"). The save-draft handler (submit.tsx:249) never got its half — it is per-IP only — and it is the path that MINTS a new draft token whenever the cookie is absent (submit.tsx:300) and writes a fresh KV entry with src/lib/draft.ts's 30-day TTL. A rotating header therefore buys unbounded month-lived KV entries on the one path whose sibling was hardened for exactly this reason. THE RULE: the pre-parse per-IP `draft` budget is unchanged; after the answers are extracted and the per-field caps pass — i.e. before the FIRST write of any kind, so the refusal can re-render the submitter's typed answers exactly as the submit-email refusal does — the normalized speaker-email answer, when present and non-empty, consumes scope "draft-email" (windowSeconds 3600, max 30: a draft is saved repeatedly, so the cap is looser than submit's 10 but finite). A draft with no email typed yet is metered by IP alone, as today. Both budgets are consumed through ONE helper in this module so the two paths cannot drift, and the two scope names stay distinct so saving drafts never burns the final-submit budget.


## Amendment (wave 66): login carries THREE budgets — the bare-email account budget returns beside the (email|ip) pair budget, because a spoofable header must never buy unlimited guesses

Verified on main: src/lib/rate-limit.ts:43-55 states the rule in its own doc-comment — x-forwarded-for is client-controllable, cf-connecting-ip is authoritative only behind the edge (i.e. never in stage 1), and "callers that need real correctness (e.g. login) MUST also key a scoped limiter by a stable identity value (such as the submitted account email) rather than relying on IP alone." Today POST /login has NO bucket that satisfies that sentence: loginIdentityKey (src/routes/auth-helpers.ts:29-31) keys `${email}|${ip}` and the flood guard (src/routes/auth-login.tsx:122) keys bare `ip`. Both keys are functions of a header the client chooses, so rotating x-forwarded-for per request gives unbounded password guesses against a known organizer address. /forgot proves the shape is available and safe: auth-reset.tsx:98 keys its per-account bucket on the bare normalizedEmail. The wave-54 amendment removed the bare-email key to stop a stranger locking a producer out "with no unlock path" — but the buckets window is 900s, so the worst case was always a bounded delay, never a permanent lock, and the amendment traded a 15-minute availability risk for a total loss of brute-force protection. RULING: three budgets, spent in this order through ONE exported key builder each, never a hand-assembled key string: (1) `login-account`, keyed on the bare normalised email via a new exported `loginAccountKey(email)`, window AUTH_RATE_LIMIT_WINDOW_SECONDS, max AUTH_ACCOUNT_RATE_LIMIT_MAX = 50 — deliberately looser than the pair budget so an honest owner mistyping cannot reach it, while an attacker rotating the header is capped at 50 guesses per 15 minutes against one address instead of infinity; (2) `login-user` keyed on loginIdentityKey(email, ip), 20/900s, unchanged; (3) `login-ip` keyed on ip, 100/900s, unchanged. DEC-948s atomic checkAndIncrement and DEC-180s consume-then-refund discipline extend unchanged: every bucket already spent in THIS request is refunded before a later buckets 429 (a request that never reached verification must not spend any accounts budget), and a confirmed success resets `login-account` and `login-user` and refunds `login-ip`. The 429 copy is the existing RATE_LIMIT_ERROR for all three — which bucket fired is never disclosed (DEC-004 enumeration discipline). Related, filed NOT taken: GET /claim/:token has no budget while its POST sibling does; the token is 256-bit and single-use, so that oracle is not practically exploitable and stays out of scope.

## Amendment (wave 38): the login account budget is a FAILURE budget — a request that might be the owner is never refused before verification; the correct password is the unlock path

Waves 54 and 66 flip-flopped on the same key (`decisions/DEC-072.md:9-11` vs `:18-20`): wave 54 removed the bare-email key because "a per-victim key is a per-victim weapon"; wave 66 restored it because email|ip and bare-ip are both functions of a client-chosen header, leaving no spoof-proof bucket. Both are right, and the oscillation will continue as long as the account budget's exhaustion is a PRE-VERIFICATION denial: verified on main, `src/routes/auth-login.tsx:120-139` spends `login-account` (bare email, max 50) FIRST and 429s everyone, so 50 anonymous POSTs against a known address — the seeded demo organizer's, printed on the CFP page — hold the real owner at 429 from every IP, renewably, with no unlock path (a reset does not clear the bucket because login is refused before any credential is read). Note the cap is also weak in the direction it was added for: 50 guesses/15min is ~4,800/day against one address. RULING, settling the oscillation rather than swinging it again: the bare-email key STAYS (it is the only spoof-proof key, satisfying `src/lib/rate-limit.ts:52-55`'s own doc-comment) and is still checked-and-incremented ATOMICALLY up front (DEC-948 — the read-then-write race stays closed), but exhaustion no longer short-circuits: it sets a local flag, the request proceeds through the unchanged `login-user` (email|ip, 20) and `login-ip` (100) HARD pre-derivation denials and the single PBKDF2 derivation, and only a FAILED verification is refused (429 + the existing RATE_LIMIT_BAND copy — which bucket fired is still never disclosed). A CORRECT password is admitted and resets the buckets exactly as today (DEC-180). Existing refund discipline is unchanged: a request denied by a later bucket must not leave the account bucket advanced. Residual, stated: a header-rotating attacker regains unbounded guesses against one address, throttled only by the 100k-iteration KDF and by whatever edge the deployment sits behind — the same residual the pair bucket already carries, and a strictly better trade than a stranger being able to make a producer's own event unadministrable. Internal precedent for the shape: `POST /account/password` already spends a budget at admission and clears it the instant the CURRENT password verifies (`src/routes/account.tsx:202-221`) — "a valid credential never counts toward the failure budget." Stage 2 behind Cloudflare (authoritative cf-connecting-ip) may restore a hard pre-derivation denial; stage 1 may not.

## Amendment (wave 58): an IDENTITY budget is refunded when the operation fails for a reason the caller cannot fix; an IP budget is a failure budget and is not

Verified: `src/routes/public/submit-post.tsx:285` spends the atomic per-email budget, then the R2 fan-out rethrows at :380 and the DB write phase rethrows at :426 — neither returns the unit. Ten transient failures lock a legitimate speaker out for an hour behind 'Too many submissions from ...'. The login door already refunds on exactly this reasoning (`auth-login.tsx:213`, DEC-180) and `refundScopedLimit` (`rate-limit.ts:89-101`) is the atomic instrument for it, so the two doors currently disagree. Ruling: the rule splits by KEY, not by route. An IDENTITY-keyed budget (`submit-email`, `draft-email`) is refunded when the failure is server-side; an IP-keyed flood guard (`submit`, `draft`, `login-ip`, `forgot-ip`) is a FAILURE budget and is NOT refunded — DEC-949's 'unknown IP is one bucket for everyone' means an IP bucket must charge for failures or it stops being a guard. Because a refund must land in the SAME window bucket as the spend, `emailBudgetOk` stops calling `Date.now()` internally (`submit-guards.ts:20`) and takes `now` explicitly; `refundEmailBudget(db, scope, email, now)` sits beside it. Every spend site is classified into one of two named lists by an enumerating scan; an unlisted scope fails the scan.

## Amendment (wave 67): the IP-budget property is stated ONCE at the limiter and machine-checked — three call sites currently restate a property the function does not have

`src/lib/rate-limit.ts:56-62` returns `cf-connecting-ip` when present, else the first hop of a client-supplied `x-forwarded-for` VERBATIM, else "unknown". Its own doc comment (:47-55) gets this right. But three callers justify their unrefunded-budget design on the opposite claim — that `requestIpFromHeaders` "collapses every untrustworthy/absent header to the single bucket 'unknown'" — and mis-cite DEC-949 (the one-live-claim-grant rule, which has nothing to do with IP buckets): `src/routes/public/submit-post.tsx:127-133`, `src/routes/public/submit-draft.tsx:55-58` and `src/routes/auth-claim.tsx:47-50`. Only `src/routes/auth-helpers.ts:50-54` states it accurately. This is DEC-018's rule applied to a sibling module: a comment claiming another file's behaviour is a claim about the tree, and here it is false. RULING: no behaviour change — DEC-072 already classifies IP as a best-effort, non-identity signal whose correctness burden is carried by a SECOND budget keyed on a stable identity (submit-post's "submit-email", login's email|ip gate), and stage 1 invents no trusted-proxy config. What changes is that the property is stated once, in rate-limit.ts's doc comment, with an explicit branch table; call sites cite it instead of restating it; and a unit test pins all three branches so the property is machine-checked rather than comment-checked. auth-claim.tsx is owned by a wave-66 branch and is explicitly out of scope — the amendment names it as the one remaining site.
