# DEC-566: Reviewer scope is ONE predicate, and completion is only ever counted inside the assigned set

src/server/repo/review/submissions.ts:256-265 (`isSubmissionInReviewerScope`, per-submission branch) returns true after only confirming the submission is in plan.eventId — it never intersects `plan.filters.trackIds`, unlike the unrestricted branch (:234-250), the track branch (:267-285) and `resolveAssignments`, though its own docstring at :129-136 claims the semantics 'match resolveAssignments exactly'. So a per-submission-assigned reviewer can GET /api/v1/review/submissions/:id and PUT an evaluation (src/routes/review/reviewer.ts:150, :194) on a submission that never appears in their queue (resolveReviewerSubmissions DOES intersect at :180-194) and never appears in /results (buildResults reads listPlanFilteredSubmissions, which filters by track). That orphan evaluation then inflates `completed` in BOTH /progress (src/routes/review/plans.ts:313-330) and /remind (:413-426), because each counts `completedByReviewer.get(userId).size` with no reference to the reviewer's assigned set — so /progress can render completed > assigned, and `if (completed >= assigned.length) continue` at :424 SKIPS a genuinely lagging reviewer. The same arithmetic bites without any scope bug at all: a reviewer who evaluates a submission and is then recused still counts as completed while `assignedExcludingRecused` drops it from the denominator. Decision, two halves of one rule: (a) all three branches of isSubmissionInReviewerScope end in the SAME plan-filter check — hoist the `submission_track` × `plan.filters.trackIds` match into one local helper called by every branch, so scope is one predicate with one exit; (b) /progress and /remind compute `completed` as the size of the intersection of the reviewer's completed submission ids with the ids of `assignedExcludingRecused(...)`, never the raw set size. Invariant this establishes: completed <= assigned, always, on both surfaces.
