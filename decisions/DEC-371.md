# DEC-371: SSR surfaces share one inlined THEME_CSS string in src/views/theme.ts; per-event branding recolours only .chq-brandable

The portal, public surfaces, CFP form, login, account, root and dev mailbox are Hono JSX with no bundler, and today each carries its own ad-hoc <style> block (public/shell.tsx BaseStyles, portal/shared.tsx, public/submit.tsx, auth.tsx, root.tsx, docs.tsx, dev/mailbox.tsx) — seven copies that would drift instantly under a redesign. One module, src/views/theme.ts, exports `THEME_CSS: string` (the DEC-367 tokens, @font-face pair, reset, and the SSR half of the shared component classes) and `ThemeStyles()` returning <style>{THEME_CSS}</style>; every SSR shell inlines it, so a public page stays one request and keeps the <150ms uncached SSR budget with no cache-busting problem. Two constraints: the string must survive hono/jsx text escaping (no quoted attribute selectors — the existing DEC-253 comment in shell.tsx explains why input[type=search] must stay unquoted), and per-event branding (event.brandingJson accentColor, portal_settings accent) no longer overrides the palette: it sets --chq-brandable-accent, which may only recolour the event logo lockup and the public surface's brandable accents, never the olive brand token, button tiers, or text colours. Keeping the accent scoped is what stops a customer's magenta from breaking WCAG AA across the product.

## Amendment (wave 43)

VERIFIED OPEN, now closed: six regex copies of the hex-colour grammar had drifted apart —
src/routes/api/validators.ts accepted '#abc' and '#aabbcc'; src/routes/public/shell.tsx's
validAccent and src/routes/portal/shared.tsx's safeAccent accepted only 6-digit; src/routes/
public/query.ts's parseAccent accepted either with or without a leading '#'; src/routes/
public/cards.tsx's TrackChips and app/src/pages/settings/formState.ts carried further copies.
Consequence: an accent saved as '#abc' passed the API's validator and was then silently
discarded by every reader with a stricter pattern, repainting the brand-default olive — the
reported "accent colour is a no-op" defect. Fix: `src/domain/color.ts` (pure core) is now the
ONE definition site — `normalizeHexColor` ('#' optional, 3 or 6 hex digits, expands 3->6,
returns lowercase '#rrggbb' or null) and `isValidHexColor` (`normalizeHexColor(raw) !== null`).
Every former regex site now imports from there instead of hand-rolling its own pattern. The two
write paths that accept an accent colour — PATCH /api/v1/events branding.accentColor and PUT
portal-settings accentColor — now store `normalizeHexColor`'s output, so a value that reaches
storage is already in the one canonical form and no reader can ever disagree with the writer
that accepted it.

## Amendment (wave 5): the public CFP form column is 732 inside the 820 reading measure

docs/design/README.md §Spacing says "forms sit at 660-760px within the reading measure"; frame 10--14's YOUR TALK rule pixel-measures 732 at 1600. The app renders 663 -- inside the band but not the drawn column, which shifts every left edge and narrows the 2-up pairs. Fixing the number at 732 (not 820, not intrinsic) makes the CFP form's measure statable and testable, and keeps it distinct from the 820 page measure that contains it. This does not touch the admin CFP builder, which is a separate container.
