# DEC-060: Persona verification is modular: scripts/walkthrough/<area>.ts standalone runnables; verify-and-fix tasks repair only their named files

SPEC §9 makes persona walkthroughs the real acceptance bar, and wave 8 executes them. Running one monolithic script from five parallel workers would make scripts/walkthrough.ts (DEC-053, branch task-w7-e still queued at planning time) a five-way merge collision. Decide: each verification area gets its own standalone runnable — scripts/walkthrough/producer.ts, review.ts, speaker.ts, public.ts, data.ts — invoked as `npx tsx scripts/walkthrough/<area>.ts --url http://localhost:8787`, using the same conventions as DEC-053 (cookie jar per persona, form login carrying the chq_csrf cookie value, 'x-chq-csrf: 1' header on JSON mutations, hard exit(1) with a named failing check — fail loudly, no soft warnings). Area tasks never edit scripts/walkthrough.ts or package.json (orchestrator wiring is a later single-owner change). Fix rule: a verification task repairs defects only inside its task-listed files; defects found outside that surface are documented in the commit message body for the next planner, never patched cross-area — this keeps five parallel workers off each other's files.

## Amendment (wave 44): no walkthrough module hand-copies a product constant — it imports it, or derives it from the response it just read

scripts/walkthrough/scale.ts:44 hard-codes `const ONBOARDING_TASK_COUNT = 5; // DEFAULT_ONBOARDING_TASKS in src/domain/acceptance.ts` and asserts strict equality against the onboarding grid's per-row `cells.length`. Two independent drift sources: DEFAULT_ONBOARDING_TASKS (src/domain/acceptance.ts:25-37) can grow, and `cells` are per ASSIGNMENT, not per default template (src/server/repo/tasks/grid.ts:320-360) — so a seed or an organizer that adds one more event task makes the assertion wrong without anything in the product being wrong. This is the field guide's hand-enumeration shape applied to the harness itself. Ruling: a walkthrough module either imports the constant from src/ (scripts are tooling, DEC-002 pure-core rules do not bind them) or derives the expectation from the payload's own `tasks[]`; a literal mirroring a src/ constant with an explanatory comment is a drift bug and gets deleted.

## Amendment (findings wave 16): two runtime harness lanes never share a port or a D1, and every log names the port and the sha it measured

docs/verification-log/task-w21-e-perf-smoke-stage1.md records a perf run that silently measured a SIBLING worktree's dev server (node_modules path from another worktree in the trace), fixed only by pinning --port 8799 — and task-w14-g-walkthrough-module-runs.md pinned the same port for the same reason. With two runtime lanes in one wave that collision is a certainty, not a risk. Ruling: wave 16 pins walkthrough to 8871, perf-smoke to 8873 and the render sweep to 8875; each lane runs `npm run db:migrate` + its own seed inside its own worktree before measuring; and each verification log opens with the port, the worktree path and the `git rev-parse HEAD` it measured, so a future wave can tell a real measurement from an inherited one.
