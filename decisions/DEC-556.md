# DEC-556: The two join tables whose uniqueness three modules assume get real UNIQUE indexes; their inserts become atomic, and merge keeps only the dedupe a constraint cannot make

the former src/db/schema.ts (now split across src/db/schema/) declares eleven uniqueIndexes. `participant(submission_id, contact_id)` and `task_assignment(task_id, contact_id)` are not among them — yet three separate modules implement that uniqueness in JS and one of them believes the database is enforcing it. inviteParticipant (repo/participants.ts:74-79) SELECTs then INSERTs, returning DUPLICATE_PARTICIPANT; createTaskAssignments (repo/tasks/crud.ts:99-108) and planAndPersistOnboardingTasks (repo/submissions/status.ts:147-214) each load existing pairs then insert the complement; and mergeContacts (repo/contacts/merge.ts:134-183) deletes shared rows before repointing, its own comment saying it does so "rather than repointing it into a UNIQUE-violating dupe" — a constraint that does not exist. So the invariant is stated four times and enforced zero times. Two concurrent POSTs to /api/v1/submissions/:id/participants (an optimistic-UI double-click) silently create two participant rows for one contact: the speaker renders twice on the public session page, twice in the .ics ATTENDEE list, twice in every export and roster, and inviteParticipant's own max(order)+1 read hands both rows the same order. Two overlapping bulk-accepts do the same to task_assignment, and a duplicated assignment is permanently un-closable — completing one leaves the other pending, so J6's "who still owes me what?" grid is wrong forever. This is the wave-35 rule (a uniqueIndex is a CONTRACT) applied in the missing direction: the contract was never written down. Decision: (a) migration 0019 adds `participant_submission_id_contact_id_idx` and `task_assignment_task_id_contact_id_idx` as CREATE UNIQUE INDEX, declared in schema.ts with the same names; the migration first deletes pre-existing duplicates, keeping the lowest rowid for participant and preferring any 'complete' row for task_assignment (mirroring merge.ts's rule that completion is never lost). (b) inviteParticipant becomes ONE INSERT ... ON CONFLICT DO NOTHING RETURNING over the schema's own column objects, with its pre-check SELECT deleted and `order` computed by a SQL max(order)+1 subquery in the insert values (precedent: submissionSeqSubquery); DUPLICATE_PARTICIPANT is derived from an empty .returning(). (c) the two task_assignment insert paths add .onConflictDoNothing() — their existence pre-reads STAY, because they are what bounds the write burst per DEC-521, but the race is now closed by the database. (d) mergeContacts's dedupe stays exactly as-is: it chooses WHICH row survives, which a constraint cannot do; only its comment's claim is now true. (e) the regression bar is the constraint and the atomicity: migration-parity gains an assertion that every schema `uniqueIndex` is created by a `CREATE UNIQUE INDEX` (today it only checks the name exists), and a fake-db harness asserts inviteParticipant issues zero selects against participant before its single insert.

## Amendment (wave 55): the uniqueIndex contract is three-way -- ON CONFLICT target, drizzle schema, and an applied migration must all agree, scanned

Wave 54 proved the expensive half of this contract is invisible: task(event_id,title) was declared in the drizzle schema AND written into migrations/0032, and getOrCreateTask's onConflictDoNothing still 500'd every accept for six waves, because the migration aborted on its first statement (CREATE TEMP TABLE, forbidden under D1's authorizer) so the index existed in no database. The dialect scan wave 54 added catches that failure mode; nothing catches the adjacent ones -- a uniqueIndex hand-added to src/db/schema/** with no migration at all, a migration creating an index on a different column order than the schema declares, or an ON CONFLICT target tuple with no unique index behind it anywhere. All three produce the same corpse: a runtime D1_ERROR on a write path, discovered by a user. Ruling: three-way parity becomes a scan enumerable from source with an EMPTY exemption ledger rather than a per-wave rediscovery -- for every uniqueIndex declared in the schema, an equivalent CREATE UNIQUE INDEX must exist in an appliable migration with the same column order, and for every ON CONFLICT target tuple in repo code, a matching uniqueIndex must exist in the schema. Per the two-directional rule, an index present in migrations but not declared in the schema fails just as loudly as the reverse.
