# DEC-248: Task-file serve population drops the 'handout'-only predicate — any kind, submissionId-null, assignment-referenced (DEC-240 conformance; amends DEC-065)

DEC-240 made task uploads carry task.deliverable_kind (scripts/seed.ts:953-967 sets 'presentation' on every seeded file_request task) and link the uploader's submission when one resolves. getTaskFileScope (src/server/repo/files.ts:254) still requires kind==='handout' AND submissionId===null, so an UNLINKED non-handout task upload — any assignee without a submission in the event — is served to NOBODY: the organizer OnboardingGrid paperclip (app/src/pages/speakers/OnboardingGrid.tsx:230, href /files/<fileId>) 404s. New population rule: a file with submissionId null that task_assignment.file_id references, kind unrestricted. Submission-linked task uploads remain population 1 (getFileScope handles organizer/participant/reviewer) — the three serve populations stay disjoint via the submissionId-null gate; canAccessTaskFile's organizer-org-match / assignment-contact / uploader logic is unchanged. The speaker's own portal download is unaffected (dedicated DEC-244 route); this fixes the organizer-facing surface.

## Amendment (wave 10): a task-assignment file is reachable through a STORED LINK on the file row, not through whichever pointer the writer happened to use

Verified on main: the portal form-task handler (src/routes/portal/tasks.tsx:397-411) writes each uploaded file with `submissionId: null` and stores only its id inside `answers[field.id]` -> `task_assignment.response_json`. getTaskFileScope (src/server/repo/files-authz.ts:287-298) resolves the population by reverse-joining `task_assignment.file_id`, which this path never writes, so GET /files/:fileId (src/routes/files.ts:618-621) 404s for organizer AND speaker alike, and the organizer's response view renders the raw id as text (src/server/repo/tasks/response-detail.ts:71 answerToString(String(fileId))). These bytes can never be read by anyone. This is a WRITER WITH NO READER — the mirror of the guide's standing lesson — and it hits a named must-have: the default 'Flight reimbursement form' ships a `file` field 'Receipt or booking confirmation' (src/domain/acceptance.ts:117). `task_assignment.file_id` is singular and already means 'this file_request's completion file', so it cannot carry a form with two file fields. RULING: the link lives on the `file` row. `file` gains a nullable `task_assignment_id` (migration + drizzle declaration, both sides — test/schema-migration-parity.scan.test.ts enforces the pair) with an index; the form path sets it; getTaskFileScope resolves the population as (referenced by task_assignment.file_id) OR (file.task_assignment_id set), one indexed lookup either way, never a JSON LIKE scan and never authz-by-parsing-the-r2-key. canAccessTaskFile is unchanged — the same organizer-or-assigned-speaker-or-uploader rule already covers both halves. The response detail carries `file: {id, filename}` for file-kind fields, resolved in ONE batched select over the answer ids, never a query per row.

## Amendment (wave 70): the file's own link wins; the reverse link is the fallback, not a coin flip

`getTaskFileScope` (repo/files-authz.ts:326-341) resolves the authorizing assignment with `or(taskAssignment.fileId = fileId, taskAssignment.id = file.taskAssignmentId)` + `.limit(1)` and no ORDER BY — and the arbitrarily-chosen row's `assignmentContactId` is exactly what `canAccessTaskFile` (:365-368) gates the speaker branch on. Nothing in the schema prevents assignment B from pointing `fileId` at a file whose own `taskAssignmentId` names assignment A; when both links resolve, SQLite — not the code — decides which speaker may download. The function's own doc comment asserts "Either link resolves the same assignment"; that claim is false, and an authz answer must be a function of the data, never of physical row order. RULING: precedence is ruled, not left to the query planner — the file's own `task_assignment_id` wins (the file declares its owner); the reverse `fileId` link resolves only when the file declares none. The doc comment is corrected to state the precedence rule, not the false equivalence.

## Amendment (wave 78): every task-assignment upload writes the file's OWN task_assignment_id; the reverse task_assignment.file_id link is legacy-only

getTaskFileScope (src/server/repo/files-authz.ts:334-395) resolves a task file through two ordered links: the file's own task_assignment_id, then task_assignment.file_id. Only the kind='form' path writes the first (src/routes/portal/tasks.tsx:422); the plain /tasks/:id/upload path (:602-613) writes neither, and task_assignment.file_id only ever names the CHAIN HEAD. So every superseded version of a task handout resolves NEITHER link and 404s on GET /files/:fileId for the organizer, contradicting SPEC.md:302 ('previous_file_id version chains; history complete and downloadable'). Ruling: the stored link on the file row is the identity of a task upload, written at insert time by EVERY writer, on every version. The reverse file_id lookup survives only as a fallback for rows written before this wave; its doc comment must stop claiming the upload path never sets the column, because that claim becomes false. A comment claiming a sibling's behaviour is a claim about the tree (DEC-018 w58).
