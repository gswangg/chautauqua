# DEC-486: projectFieldForAnswers in src/forms/types.ts is the single projection from a stored form_field row to the render/validate FormFieldDef

DEC-475 diagnosed the asymmetry: src/server/repo/submit.ts:89 re-keys a locked field's id to its short name while :97 passes rule through unmapped, and src/server/repo/portal-edit.ts:110/118 repeats it verbatim. Repairing two call sites leaves the same drift available to the third one somebody writes next year. The repair must make the asymmetry unrepresentable: one exported function that maps `id` and `rule.fieldId` in the same expression, so a future edit either maps both or neither. It belongs in src/forms/types.ts because that module is pure-core (DEC-002) and already owns lockedFieldId/lockedFieldName, and because both callers are repo modules that must not import each other. The builder path deliberately does NOT use it — src/server/repo/forms.ts toFieldRow keeps the raw '<formId>:title' PK because src/forms/builder.ts validateRuleReference:58-62 matches rule targets against those raw ids, and app/src/pages/forms/logic.ts offers them unchanged. Write path raw, render/validate path projected, one function marking the boundary.
