# DEC-817: A field accepts exactly the value its own placeholder shows

VERIFIED the embed builder's Accent color input (app/src/pages/settings/EmbedsPanel.tsx:289) placeholders `#4E5C31` and drops what you type straight into the embed URL's ?accent=, where parseAccent (src/routes/public/query.ts:74) requires 3- or 6-digit hex WITHOUT '#' and returns null for anything else — so copying the placeholder produces an embed with no accent and no error anywhere. DEC-793 settled this rule for the composer; this is the same rule one field over, and the general lesson is that a builder's parameter set and the live route's parsers are ONE contract that must be checked by enumeration, not by reading two files. Decision: parseAccent tolerates one optional leading '#' and still normalizes to '#rrggbb' (the value remains validated and never interpolated raw — DEC-374 untouched), and a parity test enumerates EVERY parameter the builder can emit against the parser the live route runs, so a future builder field the route ignores fails a test instead of a visitor.

## Amendment (findings wave 13): the admin SPA and its routes are ONE contract, graded executably — every key the SPA sends is a key some route parses

DEC-817 made the embed builder and the live public route one contract by enumerating every parameter the builder can emit from the builder's own constant arrays and round-tripping each through the parser the live route runs. The admin SPA has the same seam and no such grader, and it has now failed twice in the same file (DEC-900 amendment above): two controls that POST/PATCH a key no route reads, shipped, reviewed and swept past for waves, because nothing anywhere compares the two sides. Both defects are a one-line grep apart from being impossible. RULING: the parity is executable and lives in test/, derived from the SPA's own source rather than a hand-written list — every literal-object body passed to apiPost/apiPatch/apiPut under app/src/ contributes its top-level keys, each request path is resolved to the route module that serves it, and every key must appear in that module. Unresolvable paths fail loudly (a path the resolver cannot map is a gap in the grader, not a pass), and the shape is a SCAN with no allowlist for known-open keys — an allowlist would be the cap nobody is told about.

LANDED (task w13-e): test/spa-mutation-contract.scan.test.ts walks app/src/**/*.{ts,tsx} (excluding *.test.ts(x), which exercise the api client against synthetic paths no route serves), extracts every apiPost/apiPatch/apiPut call site whose second argument is a literal object, resolves each call's request path through an explicit path-prefix -> route-module map declared in the test, and asserts every top-level key (spread and computed-key entries are skipped with a citing comment, not suppressed) appears as a token in the resolved module's source. Every path in the current SPA resolves (the map is total over the live population); the two DEC-900 defects (task w13-a) are green.

OPEN FINDING surfaced by the scan, NOT suppressed and NOT fixed by this task (out of a one-file scope; needs its own design call): PeopleRolesPanel.tsx's "Invite" form (app/src/pages/settings/PeopleRolesPanel.tsx:113) POSTs `firstName`/`lastName` to POST /api/v1/users — src/routes/api/users.ts never reads either key, and the `user` table (src/db/schema/org.ts) has no name column at all (id/orgId/email/passwordHash/role/contactId only), so the values are not merely unparsed, they have no possible destination today. Two live options, neither decidable by a worker: (a) give org-user accounts a name (schema migration + repo + route + welcome-email copy), or (b) the SPA's Invite form should stop collecting fields the account model can never hold. This is the same class of bug DEC-900 and this DEC's own opening paragraph name (a field the client sends that no route parses) — surfaced here for the first time by the new scan, distinct from the two defects that motivated it. test/spa-mutation-contract.scan.test.ts is deliberately left asserting the honest (currently failing) result for this one pair of keys rather than allowlisting it away, per this amendment's own "no allowlist for known-open keys" ruling; a follow-up task should either wire the fields through or delete them from the form, then this scan goes green with no further changes.

## Amendment (wave 53): A DECLARED TARGET IS PART OF THE CONTRACT — every path the UI declares resolves against the REAL route table, on all three surfaces, through ONE resolver

The user-filed prod P1 (Remove co-presenter: "No route matches DELETE /api/v1/submissions/:id/participants/:pid") happened because DEC-817's scan reads only `apiPost|apiPatch|apiPut` and resolves paths through a HAND-WRITTEN `ROUTE_MODULE_MAP` (spa-mutation-contract.scan.test.ts:429-503) — a hand-listed population, which the wave-52 DEC-180 ruling already named as not a population. Three surfaces declare a server target and none of them is checked for existence: (1) every `api*` helper call in app/src, ALL verbs including apiGet/apiList/apiDelete/apiUpload/apiPostBlob; (2) server-rendered `<form action>`/`formaction` and internal `href` literals under src/routes; (3) render-test `mockApi({'METHOD /api/v1/path': ...})` keys — the very mocks that made the missing route invisible (app/src/test-utils/mockApi.ts:23-36, ~1500 keys across 61 files). RULING: resolution is ONE function, `resolveRegisteredRoute(method: string, clientPath: string): RegisteredRoute | undefined`, exported from `test/helpers/registered-routes.ts` beside `enumerateRegisteredRoutes()`. Semantics, fixed here so three lanes can implement it identically: upper-case the method; strip `?...`/`#...` from clientPath; replace every `${...}` span with `:param`; compare segment-wise against every same-method registration where a registered `:name` segment matches any one client segment, a registered `*` (or trailing `/*`) matches all remaining segments, and every other segment must match exactly; first match wins; undefined when none. `ROUTE_MODULE_MAP` is DELETED — the module a key is checked against is the resolved registration's own `file` plus its one-level relative imports. An unresolved target FAILS the scan naming file:line; it is never allow-listed away, and where an endpoint genuinely must be built later it is recorded in a named `UNBUILT_ENDPOINTS` array with file:line and a written reason, asserted EQUAL to the unresolved set so it can never grow silently.


## Amendment (wave 57) — a call the SPA/route contract scan cannot resolve is a LEDGER ENTRY, never a silent drop

test/spa-mutation-contract.scan.test.ts is the scan built after the user-filed prod P1 ("No route matches DELETE /api/v1/submissions/:id/participants/:pid"). It is careful about what it cannot see — its header enumerates five blind spots, and spread/computed-key BODY entries are collected into a `skipped` array that a dedicated test prints and floors above zero. But its PATH handling is not held to the same standard: line 396 does `if (pathArg[0] !== '"' && ... ) continue;` — a call whose first argument is not a string/template literal is dropped with no record at all, and normalizePath:327 silently erases a `${...}` span not preceded by `/`. The dropped calls are precisely the class the P1 came from: a UI control whose endpoint may not exist. The population is zero today (every api* call site in app/src passes a literal), which is exactly when a tripwire is cheap to install and honest to pin. RULED: the scan records every unresolvable-path call as `skippedPaths` with file:line and the raw argument text, prints them, and asserts the set equals a written array — empty today, growable only with a written reason. FAIL-BLIND IS NOT FAIL-LOUD applies to a grader's own blind spots, not just to product code.
