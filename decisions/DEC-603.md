# DEC-603: A send is a batch even when it has one recipient: history groups by COALESCE(batch_id, id), minted once per fan-out

Comms history is a flat per-recipient list, so one 40-recipient send reads as 40 unrelated events and the design's batch drill-in has nothing to drill into. The group key must be a column, not a heuristic over (subject, sentAt) — rendered subjects differ per recipient once merge fields resolve. A nullable batch_id alone would silently drop every historical and single-recipient row out of a grouped query (the NULL-in-a-set-predicate trap), so the key is COALESCE(batch_id, id): every row belongs to exactly one batch, and a solo send is a batch of one. The id is minted by the caller that fans out, once per call, never per recipient.

## Amendment (findings wave 8): a paged grain gets a pager — Comms History pages its batch list instead of printing a total it cannot reach

DEC-603 defined ?groupBy=batch as its own grain on GET /api/v1/events/:eventId/email-log. That route pages like every other list route (src/routes/api/email-log.ts:34-35, clampPage/clampPerPage, default 50 per page) and returns the DEC-013 envelope {items, total, page, perPage}. The History tab requests it with no page and no perPage (app/src/pages/comms/HistoryTab.tsx:59-62), renders whatever page 1 returned, and then prints '{total} total' at :126 — so on any event with more than 50 send batches the organizer is told a number and given no way to reach it, and the send log silently ends at the fiftieth batch. This is the inverse of the standing shape 'unbounded surface never paged': a paged surface rendered without its pager, which reads as a complete list. The vendored frame draws the pager it needs (docs/design/Chautauqua Comms.dc.html:671-672, 'Showing 1-4 of 57'), and SPEC §2's volume-first principle asks every admin list for exactly this. RULING: History owns a page, sends page/perPage explicitly, and renders the SAME .chq-pager markup and paginationSummary() helper the compose step-1 pager already uses — 'Showing X-Y of N' plus Previous/Next disabled at the bounds — replacing the bare total line. The page resets to 1 whenever the search query changes, since a page number means nothing against a different result set. No server change: the endpoint already answers correctly and has since DEC-603.

## Amendment (wave 18): History gets its own head and the Export CSV door onto the export that already exists

The email-log CSV export is BUILT and honours History's own filters (src/routes/api/exports.ts:120-147, kind="email-log", contactId/status/q/batchId/since, with a truncation refusal that tells the caller to narrow with those very filters) — and no surface in the SPA links to it; the only export anchor in app/src is settings' showflow.csv. Meanwhile the History tab opens onto a bare toolbar search (HistoryTab.tsx:84-100) with no head and no count, while the frame draws History as its own page with a title, a "N sends · M in the last 7 days" line and an Export CSV control (docs/design/Chautauqua Comms.dc.html:616-620, 338-339). A capability with no door is not shipped. RULE: History mirrors the Templates head exactly (breadcrumb + title + count line, one right-flushed action) and the action is a plain cookie-authed <a href> onto the existing export, carrying the tab's live q and nothing the tab does not actually filter by.

## Amendment (wave 56): the History tab is the drawn desktop frame — column heads, template chips backed by a real server-side filter, right-flushed search, Compose as the head's primary

docs/design/Chautauqua Comms.dc.html:613-677 draws the History screen completely and app/src/pages/comms/HistoryTab.tsx builds three quarters of it. Measured deltas at this runtime: the head stacks breadcrumb/h1/count and ships Export CSV alone, where the frame sets h1 and the count line on one baseline with Export CSV (secondary) plus Compose (primary) right-flushed at :619-622; there is no chips row at all, where the frame draws an 'All sends' active pill plus one pill per template inside a row bounded by hairlines top and bottom with the search box pushed right (margin-left:auto, min-width 230px) at :625-631; and RecentSends renders the frame's exact five-column grid (app/src/pages/comms/RecentSends.tsx:280-298, [when][subject][N sent][template][Open]) with NO column-head row, where the frame draws WHEN/SUBJECT/RECIPIENTS/TEMPLATE over a 2px ink rule at :634-636. RULING on the two questions two lanes could otherwise each answer differently. (1) The chips FILTER SERVER-SIDE. `templateId` becomes a real query parameter on GET /api/v1/events/:eventId/email-log at BOTH grains, pushed into SQL through the shared `emailLogConditions` (src/server/repo/email.ts:154-174) and `batchWhere`, so the flat list, the batch grain and the J12 email-log CSV export — which reuses that same predicate precisely so 'one predicate, two surfaces' holds — can never disagree about which rows match. It is expressible at batch grain (listEmailBatches already projects templateId at :309), so DEC-905's 'name the parameter batch grain cannot express' refusal does not apply and must not be copied here. (2) The chip POPULATION is derived, never hand-listed: 'All sends' plus one chip per template in the `templatesById` map Comms.tsx already fetches and passes to both mounts — the frame's 'Acceptance / Decline / Reminders' are that event's own template names, not a vocabulary. A chip whose template has no sends lands in the EXISTING filtered-empty state; that is honest, and hard-coding three names would be the hand-listed population this swarm keeps ruling against. (3) Column heads are a `columnHeads` prop on RecentSends, default off — the frame draws heads under History (where the page h1 already says what the table is) and no heads under Compose's 'Recent sends' section; when on, the component emits the head row and suppresses its own section head so the History page never states its subject twice.
