# DEC-027: Bearer API tokens: chq_ prefix + sha256 lookup in sessionLoader, CSRF-exempt, cookie-only minting; export endpoints per entity

J12 requires the same /api/v1 the SPA uses to work with bearer tokens. Token plaintext: 'chq_' + 40 lowercase base32 chars from crypto.getRandomValues, shown exactly once at creation; stored as sha256 hex in api_token.token_hash with token_prefix = first 12 plaintext chars for display (DEC-025 table). sessionLoader (src/server/middleware.ts) gains: when no session cookie resolves and Authorization: Bearer chq_... is present, hash and look up api_token, set auth { userId: created_by_user_id, role: 'organizer', orgId, viaBearer: true } (AuthInfo in src/server/env.ts gains optional viaBearer) and best-effort stamp last_used_at. csrfJson passes when auth.viaBearer — CSRF protects cookie sessions only; bearer clients cannot be cross-site-forged. Token management is cookie-session-only (viaBearer -> 'forbidden'; tokens must not mint tokens): GET /api/v1/tokens (no secrets, shows prefix + lastUsedAt), POST /api/v1/tokens { name } -> { token } once, DELETE /api/v1/tokens/:id. Exports: GET /api/v1/events/:eventId/export/:kind?format=csv|json (default csv), kinds submissions | speakers | evaluations | agenda | email-log, organizer-only, Content-Disposition attachment, CSV via src/lib/csv.ts's toCsv (that module moved to src/domain/csv.ts per the DEC-011 wave-65 amendment). Fixed columns — submissions: ref,title,status,contentStatus,tracks,speakers,speakerEmails,createdAt; speakers: firstName,lastName,email,company,title,acceptedSessions,visible; evaluations: planName,ref,title,reviewer,round,scoresJson,comment,submittedAt; agenda: day,start,end,room,ref,title,speakers,tracks; email-log: sentAt,toEmail,subject,status,templateId. JSON format returns the same records as an array. This endpoint set (not the plan-results CSV from DEC-018) is the canonical exports surface.

## Amendment (wave 50)

DEC-027's export surface builds the entire table in the isolate: buildExport (src/server/repo/exports/index.ts:40) returns every row, toCsv joins them into one string, and format=json hands the whole record array to c.json. There is no LIMIT anywhere under src/server/repo/exports/* -- the only .limit in the directory is common.ts:12's .limit(1) event lookup -- and exportContacts (contacts.ts:50) documents the omission outright: the same list predicate "minus the page window". Contacts are org-scoped across every event the org has ever run. SPEC §0 sizes the target at 500-5,000 submissions per event with multiple events per year sharing one speaker network, and SPEC §7 names an oversized payload a bug, not a tuning opportunity; today the failure mode is an unexplained isolate death, which is the opposite of failing loudly. Rule, modelled on DEC-353's archive cap: the bound lives on the QUERY, not on a check after the rows are in memory -- every export kind selects at most EXPORT_MAX_ROWS + 1 rows, and the route refuses with ApiError('invalid', ...) naming the cap and the filter to narrow with (submissions and contacts already honour the list's own filter per DEC-649/DEC-671, so "narrow and retry" is a real action, not a dead end). Under the cap the bytes are identical to today. EXPORT_MAX_ROWS is one exported named constant with its own test, never a literal at a callsite.

## Amendment (wave 41): an export kind whose cap refusal names no narrowing is a dead end — email-log and evaluations honour their own surfaces' filters

DEC-649 (submissions export honours the list's q/status/trackId) and DEC-671 (contacts export honours the directory's q/segmentId/rules) already established that an export is the SAME query as its surface, and src/routes/api/exports.ts:126-134 already only offers a `narrow and retry` hint to those two kinds. The other kinds got the bare cap sentence. At SPEC volumes (J5 logs every message PER RECIPIENT; J4 is reviews x submissions x rounds) email-log and evaluations are the two kinds that actually cross EXPORT_MAX_ROWS=20000 on a real event, and neither has any narrowing at all — so the refusal is advice the caller cannot act on (the same shape wave 38 closed on the reminder cron) and J12 'the data stays theirs' fails for exactly the biggest customer. Ruling: an unfiltered kind that can cross the cap must gain its own surface's filter, reusing that surface's existing predicate (listEmailLog) rather than restating it, and every refusal must name the parameters that would make it succeed. Kinds bounded by event size (speakers, agenda, showflow) keep the plain message.

## Amendment (wave 47): the token list projection carries createdAt, and a never-used token is marked

DESIGN-RULINGS §B10 gives the API-token screen its anatomy: 'named rows with their prefix, created and last-used dates, per-row Revoke, and the two facts a token screen must state before you act — the secret is shown once at creation, and revoking is immediate and irreversible. A never-used token is marked in bold caps, since an unused live credential is usually one somebody forgot to delete.' Verified on main: GET /api/v1/tokens (src/routes/api/tokens.ts:37-48) selects id/name/tokenPrefix/lastUsedAt only — createdAt exists on the row and is written at mint (:86-95) but never leaves the server — and ApiTokensPanel.tsx says so in its own header comment ('The GET /tokens response has no createdAt field ... adding "created" would be a new API shape, which this task is scoped to avoid'), so the panel renders Name / Token / Last used / Revoke and prints a plain 'Never' where the ruling wants a mark. A reader cannot render a column its endpoint does not send. Ruling: each item in the GET /api/v1/tokens response gains `createdAt: number` (epoch ms, same shape as lastUsedAt; every other key unchanged, no change to POST or DELETE, and no other endpoint grows a date). The panel's EDIT view renders Name / Token prefix / Created / Last used / Revoke; a row with lastUsedAt === null renders the uppercase micro-label 'NEVER USED' in the Last-used cell instead of the word 'Never'; and the two standing facts are stated once above the table ('The token is shown once, when you create it.' and 'Revoking takes effect immediately and cannot be undone.') rather than only inside the create-reveal box and the confirm dialog, which a reader sees only after acting. The read-only summary row (readOnly=true) keeps name + last used and grows no column — B10 gives the anatomy to the edit view, and DEC-785's summary/edit split stands.

## Amendment (wave 38): a route that mints, resets or elevates an org-user login credential is COOKIE-SESSION-ONLY — bearer containment is a property of the whole credential surface, not of tokens.ts

Verified on main: `csrfJson` is bearer-exempt by design (`src/server/middleware.ts:267-272`), and `src/routes/api/users.ts` guards its three mutations with `requireOrganizer, csrfJson` only — no cookie-session assertion. So a leaked read-oriented bearer token can (1) `POST /api/v1/users` with `role:"organizer"` and receive the one-time password in the response body (`users.ts:87-129`), and (2) `POST /api/v1/users/:id/reset-password` against ANY org user and receive the new plaintext (`users.ts:138-159`), and (3) `PATCH /api/v1/users/:id` to promote an account it controls. Each yields a durable, cookie-loginable organizer identity, which can then mint tokens — defeating DEC-027's own contract (`src/server/env.ts:45-49`: bearer requests "can never mint new tokens themselves") transitively while satisfying it literally. `src/routes/api/tokens.ts:23-28` already has the correct guard but keeps it private to that file, which is exactly why the sibling surface never got it. RULING: one exported middleware `requireCookieSession` in `src/server/middleware.ts` is the ONE assembler of this refusal (`unauthorized`/"Login required" when unauthenticated; `forbidden`/"This action requires a signed-in session, not an API token" when `auth.viaBearer`); tokens.ts's private helper is DELETED and its call sites moved to the middleware chain (no compatibility shim); the three users.ts mutations gain it. Scope boundary, recorded so it reads as measured rather than missed: `GET /api/v1/users` stays bearer-reachable (a read, not a credential); portal claim-link minting stays bearer-reachable (a LESSER privilege than the bearer's own organizer role, so not an escalation); `POST /account/password` (`src/routes/account.tsx:171-216`) is bearer-reachable but requires the CURRENT password, which a bearer client does not have — checked, not a hole. The claim gets a DERIVED POPULATION with a negative control (DEC-099), never a hand-listed allowlist.

## Amendment (wave 51): the bearer-token population is bounded, and the bound is visible where tokens are minted

`POST /api/v1/tokens` (src/routes/api/tokens.ts:64-94) mints without any per-org bound, while every sibling mint door in the product carries one (MAX_COMPOSE_RECIPIENTS, MAX_FIELD_OPTIONS, MAX_PARTICIPANTS_PER_SUBMISSION, DEC-422's saved-view cap). A credential table that grows without limit is the one population where 'A UNIVERSAL NEEDS A POPULATION' bites hardest: every live token is a standing bearer grant that bypasses CSRF by design. RULING: MAX_API_TOKENS_PER_ORG = 25, enforced by one org-scoped count BEFORE minting, refused as a 409 with `overCapCountMessage` (never a silent no-op), and — per DEC-468's rule that a cap the UI cannot see LIES, the same rule DEC-484 was written from — the list envelope reports the ceiling so ApiTokensPanel can state 'N of 25' beside the create control. Adjudicated NOT part of this scope and not re-filed: `lastUsedAt` is already stamped off the critical path (src/server/middleware.ts:193-216), and the list is already paged and org-scoped.

## Amendment (wave 70): the guard becomes a scanned population, and password rotation joins it

`requireCookieSession` (middleware.ts:263-272) declares itself "the ONE assembler of that refusal", placed "immediately after requireOrganizer" on "every credential-bearing route" — but only `api/tokens.ts` and `api/users.ts` actually carry it. `POST /account/password` (routes/account.tsx:171) guards with `requireAuthOr302` + `csrfForm` only; `sessionLoader` accepts `Authorization: Bearer chq_...` (middleware.ts:234-241) and `csrfForm`/`csrfJson` are trivially satisfied by a non-browser client, so a leaked API token reaches password rotation and, on success, is handed a real browser session cookie (account.tsx:270-272) while every genuine session for that user is revoked. A guard named in a comment is not a policy; a policy is a scanned population. RULING: the guard is required on every authenticated principal ROTATING a credential — `POST /account/password` gains `requireCookieSession` immediately after `requireAuthOr302`. The three unauthenticated MINT doors (auth-login, auth-claim, auth-reset) stay exempt, as a closed three-member list with a written reason (they run with no `c.var.auth` at all, so the guard's own refusal is unreachable there). Enforcement is a scan keyed on the credential PRIMITIVES — `hashPassword`, `issueSessionRevokingAll`, `buildSessionCookie` — never on the guard's own name, so a future credential-rotation route cannot silently skip the guard just by not mentioning it.

## Amendment (wave 82): an export's filter vocabulary is DERIVED from the list's, never hand-listed

`src/server/repo/exports/email-log.ts:4-8` asserts in its own header that "a filtered export and the identical filter through GET .../email-log always agree on which rows match", then declares `EmailLogExportParams` (`:24-30`) as a hand-list of five names while `emailLogConditions` (`src/server/repo/email.ts:161,169`) takes six — `templateId` is the missing one, the list route spends it (`src/routes/api/email-log.ts:53-57,101`), and `src/routes/api/exports.ts:146` never reads it. Every other unrecognised value on that route 400s, so this is the one silently-dropped filter: an organiser exporting one template's log gets the whole event's. The rule: the export's params type is a `Pick<EmailLogListParams, ...>` of the list's own filter keys (the same type `filterParams` at `:35` already builds), so adding a seventh filter to the list makes the export fail to compile rather than fail to filter. A hand-list is not a population (DEC-180 lineage).

## Amendment (wave 18): A claim-token mint IS a credential mint: every route that reaches createClaimToken carries requireCookieSession

DEC-027 wave-38 closed the bearer-token escalation on account creation, password reset/reissue, role change and API tokens, and `src/server/middleware.ts` states the rule in one sentence: a bearer-authenticated organizer must never mint credentials for itself or others, and because `csrfJson` deliberately exempts bearer clients, a missing session check is a full escalation rather than a CSRF gap. A `/claim/<token>` link IS an interactive login credential — `src/auth/claim.ts`'s `createClaimToken` writes a 30-day KV record that logs its bearer in — yet four routes reach it with `requireOrganizer, csrfJson` and no `requireCookieSession`: `src/routes/comms/portal-invites.ts` and `src/routes/content-notes.ts` call `resolvePortalLinks(..., true)` directly, and `src/routes/comms/send.ts` and `src/routes/api/contacts/bulk-email.ts` reach the same mint through `applyMintedPortalLinks`. Both credential scans miss all four because `createClaimToken(`, `resolvePortalLinks(` and `applyMintedPortalLinks(` appear in neither `CAPABILITY_MARKERS` nor `CREDENTIAL_PRIMITIVES` — the scan's own PREMISE, not its count, is what was wrong. Combined with the equally session-free `PATCH /api/v1/contacts/:id` email write, a bearer token can repoint a speaker's address and have a working login mailed to it. RULED: `requireCookieSession` goes immediately after the role guard on all four minting routes, and `CREDENTIAL_PRIMITIVES` names the two portal-link mint entry points so the population is derived from the tree rather than hand-listed. Explicitly NOT ruled here: the contacts PATCH itself stays bearer-reachable — editing a CRM field is ordinary API work, and guarding the mint alone breaks the chain. The three non-minting `resolvePortalLinks(..., false)` call sites (compose-core preview links, both reminder paths) are untouched: they hand out `PREVIEW_CLAIM_TOKEN`, not a credential.

## Amendment (wave 20): mintPortalLinks( is the ONE named mint entry point, and createClaimToken( widens the whole-tree scan to the public CFP door

The wave-18 amendment closed portal-invites.ts, content-notes.ts, send.ts and bulk-email.ts on `requireCookieSession`, but left both minting call sites reading `resolvePortalLinks(..., true)` — a bare trailing `true` a reader (or the wave-70 `credential-route-cookie-session.scan.test.ts` population, which classifies a mint by parsing that argument list rather than by name) has to interpret rather than read. `src/server/repo/portal-link.ts` gains `export async function mintPortalLinks(` as a thin named delegate to the existing `resolvePortalLinks(..., true)` path — ONE implementation, never a second copy of the body (DEC-613) — and `src/routes/comms/portal-invites.ts` and `src/routes/content-notes.ts` now call it instead of passing a bare `true`. The `false` (preview / no-mint) call sites in `src/routes/comms/compose-core.ts` and `src/routes/api/contacts/bulk-email.ts` stay on `resolvePortalLinks` unchanged.

Separately, `test/credential-route-cookie-session.scan.test.ts`'s whole-tree `CREDENTIAL_PRIMITIVES` population (the wave-70 section) never carried `createClaimToken(` itself — only the wave-38 section's `api/**`-scoped `CAPABILITY_MARKERS` did — so a route outside `src/routes/api/**` that calls `createClaimToken(` directly was invisible to the whole-tree scan. `src/routes/public/submit-post.tsx` (`import { createClaimToken, ... } from "../../auth/claim";` then `const claimToken = await createClaimToken(claimKv, { contactId, eventId: event.id });`) is exactly this route: the public CFP submit door, registered with no role guard and no `c.var.auth` at all, minting the submitter's own claim token on their own just-created submission. RULED: `CREDENTIAL_PRIMITIVES` gains `mintPortalLinks(` and `createClaimToken(` (alongside the existing `applyMintedPortalLinks(`), and the scan's own offender list — forced red once and read before writing the exemption, per DEC-180's "a hand-listed population is not a population" — named exactly the one file predicted: `src/routes/public/submit-post.tsx`. `UNAUTHENTICATED_DOORS` (`test/credential-route-cookie-session.scan.test.ts`) gains it as a FOURTH entry, with the same no-session justification the existing three carry: it runs with no `c.var.auth`, so `requireCookieSession`'s own refusal is unreachable there. The exemption list is now four entries, still closed, still requiring a written reason per member.
