# DEC-941: An irreversible delete in the SPA goes through ConfirmDialog with a BODY, and the exemptions are a NAMED list

Five delete call sites fire on click with nothing between the pointer and the row: saved views (ViewTabs.tsx:218), API tokens (ApiTokensPanel.tsx:80 — an unrecoverable revoke whose own copy says the token is never shown again), portal resources (ResourcesPanel.tsx:143 — deletes the stored file), email templates (TemplatesTab.tsx:76) and a plan's reviewer (PlanEditor.tsx:654 — drops that reviewer's whole queue). Contacts, segments, saved embeds, file versions and submissions all already route through ConfirmDialog, so this is not a missing capability, it is five places that forgot. DEC-631 made ConfirmDialog the one contract and DEC-886/DEC-929 made a body that NAMES what goes the house grammar; nothing enforces either. Rule: every `apiDelete(` in app/src is gated by a ConfirmDialog with `destructive` set and a `body` that names the row by its own handle and states the consequence in prose ("Any script or embed still using this token stops working."), never a bare title. Deletes that RESTORE rather than destroy — the recusal-undo DELETEs in ReviewerQueue.tsx and Scorecard.tsx — are exempt by NAME in an explicit allow-list inside the scan test, never by silent omission. A scan test enumerates the modules containing `apiDelete(` and requires each to import ConfirmDialog unless it is on that list, so the sixth one cannot ship unguarded.

## Amendment (wave 56): a scan that literal-matches a call spelling is not a population — a generic-parameterised call is the same call, and an exemption list carries structural reasons only

VERIFIED at this plan's runtime. app/src/delete-confirm.scan.test.ts:45 gates on `source.includes('apiDelete(')`, so `apiDelete<T>(` is invisible to it. Two call sites exploit that hole today and neither module imports ConfirmDialog: app/src/pages/submissions/SubmissionDetailPage.tsx:704 `await apiDelete<{ deleted: number }>(...)` (Remove co-presenter — irreversible destroy of a participant row) and app/src/pages/Agenda.tsx:208 `await apiDelete<RefreshedConflictsSummary>(...)` (Unschedule — the slot placement is gone, the toast at :210 offers no undo). Same defect class as the prod P1 DEC-817's wave-53 amendment closed (a hand-written map / a literal match standing in for a derived population) and as DEC-989's className-literal blindness ruled below. RULING: the matcher is `\bapiDelete\b\s*(?:<[^>]*>)?\s*\(` and the test carries a NEGATIVE CONTROL proving the generic and whitespace spellings are seen — a scan whose blindness is not itself asserted is not evidence. Second half: ALLOWED_UNGUARDED currently carries 'pages/settings/TracksRoomsPanel.tsx' with the reason 'an unmerged wave-24 branch owns its track/room delete path' — a wave-scoped scheduling note parked in an exclusion list, exactly what app/src/page-measure.test.ts:211-221 already forbids for NAMED_EXEMPTIONS ('an exclusion list is a promise about the thing's nature, never a parking space, and its reason can expire'). That reason expired; deleteTrack/deleteRoom (TracksRoomsPanel.tsx:256,329) are irreversible and get the dialog. ALLOWED_UNGUARDED ends this wave holding exactly the two restore-not-destroy recusal-undo modules, and its reasons are structural.

## Amendment (wave 58): a confirm's WEIGHT is decided by reversibility, and the irreversible weight types the name

Verified: `app/src/components/ConfirmDialog.tsx` has exactly ONE weight — title/body/confirmLabel/cancelLabel/pending/confirmDisabled, no type-to-confirm. DESIGN-RULINGS:342-349 rules two weights, chosen by reversibility rather than by how alarming the action sounds. Ruling: add `weight?: 'reversible' | 'irreversible'` (default reversible) and `confirmPhrase?: string`; under the irreversible weight the primary stays disabled until the typed value equals `confirmPhrase` after trim, compared case-insensitively — a name typed in the wrong case is still a deliberate act, a name mistyped is not. FAIL LOUDLY: `weight='irreversible'` with a missing or empty `confirmPhrase` throws rather than silently degrading to the reversible weight. The primary label must carry the verb; 'Confirm'/'OK'/'Yes'/'Continue' are banned by an enumerating scan over every `<ConfirmDialog` call site. The irreversible population on THIS tree is exactly two callers — the portal-resource delete (`ResourcesPanel.tsx:373-380`) and the contact merge (`MergePage.tsx`); the ruling's third named site, event delete, has NO control in the SPA (verified: no `apiDelete` against `/events/:id` anywhere under `app/src`), and that absence is RECORDED in the component doc rather than designed for.

## Amendment (wave 60): a confirm dialog whose state is never armed is a dead control, and the scan must say so

Verified on main at b214b999: app/src/pages/submissions/ViewTabs.tsx declares `pendingDelete` (:218), renders a full ConfirmDialog gated on it (:311-320) and implements confirmDeleteView() with the real apiDelete (:245-261) — but grep of setPendingDelete across app/src shows the ONLY two call sites in that file pass `null` (:254, :318). No saved view can ever be deleted; DELETE /api/v1/views/:id and its dialog are unreachable code that every existing test and the DEC-941 delete-confirm scan both pass. DEC-941 previously ruled that an irreversible delete must be CONFIRMED; this amendment adds the converse, because the two failure modes are symmetric and only one was ever asserted: a delete with no confirm ships unguarded, a confirm with no arming ships unusable. RULING: (1) every saved-view row carries a delete affordance that sets pendingDelete to that view; (2) the DEC-941 scan grows a DEAD-CONFIRM check — for every file that renders `<ConfirmDialog` gated on a `pendingX &&`/`pendingX ?` expression, that file must contain at least one `setPendingX(` call whose argument is not the literal `null` — with a negative-control fixture proving the matcher flags a null-only file, per the DEC-989/DEC-941 wave-56 doctrine that a scan whose blindness is not itself asserted is not evidence.


## Amendment (wave 61): a state flip whose blast radius is a public URL is confirmed at the reversible weight

DEC-941's wave-58 amendment gave ConfirmDialog two weights and its wave-60 lane is wiring the saved-view delete. One control still flips a PUBLIC surface off with no confirm at all: SavedEmbedsPanel.tsx:211-213's 'Turn off', which stops /embed/e/<id> serving on somebody else's website. The V11 ruling's own test for the reversible weight is 'reversible, but the consequence is not obvious from the label' — an embed toggle in a settings list is exactly that. Ruling: 'Turn off' opens the shared ConfirmDialog at the DEFAULT reversible weight (no type-the-name — nothing is destroyed), with a body that names the blast radius from real data (the permalink stops serving; the saved recipe, its name and its code survive; Turn on puts it back) and a verb-carrying primary 'Turn it off'. 'Turn on' stays unconfirmed: turning a page back on is not a consequence anyone needs warning about. The DEC-941 scan itself is wave-60's file and must not be edited here — a render test proving the dialog OPENS and that no PATCH fires before the primary is pressed is this lane's evidence.

## Amendment (wave 68): a destructive confirm's primary names its object; a bare verb is banned and the ban is scanned

The v11 confirm frames spell the primary as verb-plus-object ('Turn it off', 'Delete it', 'Add it') and nine of the SPA's own dialogs already do it right ('Delete plan', 'Delete resource', 'Remove break', 'Remove participant', 'Unschedule session', 'Close the call now', 'Merge contacts', 'Advance round', 'Turn it off'). Nine others pass a bare 'Delete'/'Remove' — SegmentsPanel:164, ContactDrawer:817, VersionList:173, ViewTabs:323, TemplatesTab:332, SavedEmbedsPanel:310, PlanEditor:2420, OnboardingGrid:1150, TracksRoomsPanel:803 — so the same word sits on the button that destroys a saved view, an email template, a segment, a whole contact, a speaker's uploaded file version and a live embed. The blast radius belongs in the button, not only in the title. Bare members of {Delete, Remove, Confirm, OK, Yes, Save, Continue} are banned as a confirmLabel, pinned by a source scan in the delete-confirm.scan.test.ts idiom so the next dialog cannot reintroduce one; a computed label is RECORDED as skipped with its expression, never silently passed. app/src/pages/forms/** is exempt BY NAME this wave because unmerged branch task-w66-i is rewriting FieldModal's delete affordance.
