## Amendment — USER RULING 2026-08-16: two-tier docs vocabulary (UI labels for on-screen things, monospace for machine literals, schema identifiers banned), two inline spans in the element library, and dash discipline

The docs rendered as unformatted prose and leaked schema identifiers into it — the user's example: "Triage moves it into accept_queue or decline_queue". `accept_queue` is internal vocabulary the UI never shows (the visible labels are 'Accept queue' / 'Move to accept queue', app/src/pages/submissions/BulkActionBar.tsx and the STATUS_LABELS map in app/src/pages/submissions/types.ts). This is DEC-650's original subject arriving on a new surface: an id in the docs is an internal handle leaking, same as an id in the UI. RULING, three parts:

**Tier 1 — UI vocabulary gets the UI's words, formatted as UI.** When docs prose references something the reader sees on screen (a status, tab, button, field, chip), it uses the LABEL the UI displays — sentence case, verified against the actual app components before writing — never the schema identifier. When the reference is to the literal control or label as a thing to find on screen ('check **Recuse me from this one**'), it is marked bold. Statuses in flowing prose are concepts, not literals: "the accept queue", unformatted. A reference LIST may carry one bold UI-label token per item ("**Pending** — the submission arrived...").

**Tier 2 — machine-literal text gets monospace.** Text the reader types, pastes, or reads as an exact literal string — URLs and paths (`/dev/mailbox`), commands (`db:migrate`), file names and extensions (`.ics`), env vars (`PUBLIC_BASE_URL`), merge-field placeholders (`{missing_field}`) — is an inline code span. Ordinary domain nouns (submission, track, segment, portal) are NEVER monospaced; that over-application is explicitly banned.

**The element library grows exactly two INLINE spans, not a tenth block.** Article prose stays plain strings; `docsInlineSegments` in src/routes/docs-site.tsx parses exactly two spans — `` `code` `` → `<code>` and `**bold**` → `<strong>` — applied to prose text, list items, standfirsts, figure captions and search snippets, never to headings or code blocks. Escape-safe by construction: an unpaired or empty marker renders as-is, spans never nest. Styling in src/routes/docs-site.css.ts scopes inline `code` to the prose-bearing contexts (mono stack, 0.9em, `--chq-surface-sunk`, 2px 4px, 3px radius — quiet, not a highlighter); `strong` needs nothing beyond browser weight. Unit-tested in test/docs-inline-markup.test.ts.

**Dash discipline (same ruling, same day).** The articles overused em dashes (70 across the nine). In flowing prose an em dash must EARN its place — a genuine pivot or emphatic aside — with a budget of at most about one per paragraph and most paragraphs carrying none; the rest were rewritten with commas, colons, parentheses, or sentence splits, whichever read most naturally. The "term — definition" separator in reference lists is a structural convention and stays; en dashes in ranges stay. The relaxed STE writing-rules scan (test/docs-ste.scan.test.ts) and the DEC-518 truth pins bind over the rewritten prose unchanged.
