# DEC-478: ONE import row cap; two constants named MAX_IMPORT_ROWS with different values make the 400 message a lie

src/routes/api/contacts/import.ts:24 declares MAX_IMPORT_ROWS = 10_000 (DEC-417, route layer) and src/server/repo/contacts/import.ts:30 declares MAX_IMPORT_ROWS = 2_000 (DEC-356, repo layer). A 3,000-row file passes the route's check, is told nothing, then fails in the repo with a different message; a producer reading the route's own 400 ('Max 10000 rows') is being told something untrue about the system they are using. Only one of these can be the contract. The repo's 2,000 is the enforced number and the defensible one -- each row still costs its own D1 statement in a serial loop (src/server/repo/contacts/import.ts:87-111), so the cap is a real per-request write-burst bound, not decoration -- so the route imports it rather than re-declaring it. No compatibility shim, no second name: delete the duplicate.

## Amendment (wave 62): the import caps are declared where the file is chosen, and the ONE row cap moves to pure core

DEC-478 already forbids two constants named MAX_IMPORT_ROWS. There is exactly one (src/server/repo/contacts/import.ts:47) — but it lives in a drizzle-importing repo module, so the SPA cannot import it, which is the same shape w59-e closed for MAX_SEGMENT_RULES and MAX_IMPORT_CSV_BYTES (both now in src/domain/contacts.ts:21,25 and both read by the SPA, e.g. FilterRulesPanel.tsx:20). The consequence is live: app/src/pages/contacts/ImportWizard.tsx states NEITHER cap — not the 2,000 rows, not the 5 MB — so an organizer pastes a 5,000-row export, walks the whole match-the-columns ritual, and learns the limit only from a 400 at the end (`csvText must have at most 2000 data rows`, src/routes/api/import.ts:78). A cap the file-chooser never mentions is a cap disclosed by failure. THE RULE: MAX_IMPORT_ROWS moves verbatim (with its doc-comment) to src/domain/contacts.ts beside MAX_IMPORT_CSV_BYTES; src/server/repo/contacts/import.ts imports it from there and keeps its existing re-export so no call site changes meaning — still exactly one declaration, which is what DEC-478 actually protects. ImportWizard prints both caps as a quiet caption on the choose-file step and REFUSES an over-cap file before the mapping step, in the error-vocabulary grammar that counts the overage and offers the way out ("2,143 rows — 143 over the 2,000-row limit. Split the file and import each part."), keeping the chosen file addressable rather than dumping the organizer back to an empty screen.

## Amendment (wave 47): an import column mapping is INJECTIVE — two CSV columns may not target one field

`mapImportRow` (`src/domain/contacts-parts/import.ts:44-101`) walks the header left to right and assigns `result.email`/`result.company`/`customFields[key]` by plain assignment, so a mapping with two columns pointed at the same destination silently keeps the RIGHTMOST value and discards the other — a data-loss default in the one operation whose whole purpose is fidelity, and invisible in the preview because the preview runs the same fold. Last-write-wins is exactly the silent fallback the house rule forbids. RULING: a new pure-core `validateImportMapping(mapping): void` in the same module throws `ApiError('invalid', ..., { mapping: <message naming the duplicated target and both columns> })` when the non-empty values of the mapping object are not distinct (custom.<key> compared by full target string). It is called at the single server door (`src/routes/api/contacts/import.ts:71-74`) before any parse or write, and — following this DEC's own wave-62 precedent, which moved MAX_IMPORT_ROWS into pure core precisely so the wizard could disclose the constraint where the choice is made — the same function backs an inline refusal in the mapping step of `app/src/pages/contacts/ImportWizard.tsx`. Refuse, never truncate and never coerce; the operator re-points one of the two columns.
