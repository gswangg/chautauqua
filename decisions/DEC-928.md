# DEC-928: The deliverable kind an organizer picks IS the file-kind enumeration -- imported, ordered, exhaustive

src/routes/tasks.ts derives its DELIVERABLE_KINDS from FILE_KINDS with the comment 'so a new file kind can never desync the task deliverableKind vocabulary from the upload vocabulary' -- and then launders the validated value through `deliverableKind as CreateTaskInput['deliverableKind']` into src/server/repo/tasks/crud.ts's hand-typed 'presentation' | 'poster' | 'handout', while app/src/pages/speakers/types.ts hand-lists the same three a third time. DEC-879 added 'recording' to FILE_KINDS with its own video mime map and 250 MB cap, so the server accepts a recording deliverable that no organizer can ever request: the New-task picker cannot offer it, and the cast is what hides the missing fourth value. Rule: one enumeration reaches every layer. crud.ts's DeliverableKind IS FileKind (import type from src/domain/files) and the cast at the call site goes; app/src/pages/speakers/types.ts re-exports FILE_KINDS from src/domain/files (the SPA already imports that module in content/UploadZone.tsx, so this is precedent, not a new dependency); the picker renders options in FILE_KINDS order and defaults to FILE_KINDS[0] ('presentation'), which also settles the recorded default-mismatch nit; and both label maps -- the task picker's and app/src/pages/content/types.ts's -- become Record<FileKind, string>, so a fifth kind fails to compile instead of rendering a blank option. A parity test asserts the SPA's list equals FILE_KINDS member-for-member, in order.
