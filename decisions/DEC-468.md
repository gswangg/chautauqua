# DEC-468: A server cap the UI cannot see is a new "falls through the cracks" defect: a truncated admin list must report its true total and offer the rest

DEC-461(a) chose a 200 default precisely so "no admin screen that renders every row today loses rows the day this lands" — but that reasoning holds only for lists that stay under 200, and DEC-460 itself named /api/v1/pipeline as the list that "grows with every contact ever pushed into the pipeline across every event in an org's lifetime." app/src/pages/contacts/PipelineBoard.tsx:33 does `setEntries(res.items)` and line 63 renders `{entries.length} people`, so at 500 pipeline entries the board now silently shows 200 and captions them "200 people" — a cap that lies about its own size is worse than an unbounded read, because the producer has no way to know a person is missing. The same shape sits in app/src/pages/review/PlanEditor.tsx:196, where a reviewer picker built from /users?role=reviewer would omit reviewers past 200 with no notice. Rule: wherever a bounded list is rendered, the count shown to the user comes from the envelope's `total`, never from `items.length`, and `items.length < total` must produce a visible affordance (a "load more" that appends the next page, or at minimum an explicit "showing first N of M" note). Design stays frozen: existing .chq-* classes and tokens only, no new deps, no new palette.
