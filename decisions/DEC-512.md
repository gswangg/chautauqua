# DEC-512: Every participant READ declares its invite-status audience; the list of reads that legitimately span all four statuses IS the enumeration, and it is a test

The same defect has now been fixed in six separate places across five waves (DEC-283 on assignToAllAccepted, DEC-317 on compose recipients, DEC-974/DEC-981 on the Airtable and roster queries, DEC-983 on the Content library's lead speaker) and is STILL open in two more: src/server/repo/overview.ts's placed-session participant read (a DECLINED co-presenter still raises a speaker clash on the Overview) and its fetchLeadSpeakers (a declined co-presenter can be the lead-speaker NAME on a worklist), plus contacts/stats.ts's speakerCount KPI. Forty-three files read schema.participant; thirteen mention an invite predicate. Fixing three more sites by hand buys one wave of quiet and guarantees a seventh recurrence, because nothing in the code records which of the thirty silent reads MEANT to span every status. So the rule becomes: a participant read is one of three audiences -- ACTIVE (inviteStatus in ACTIVE_INVITE_STATUSES: the people who actually hold this slot), PORTAL-VISIBLE (PORTAL_VISIBLE_INVITE_STATUSES), or EVERY (writes, deletes, exports, audit trails) -- and choosing EVERY is a written act, not a silence. A scan test enumerates every file containing a participant read, and the set that declares no audience must equal a hard-coded map from path to a one-line reason; a file that gains a predicate, or disappears, fails the scan as a stale exemption (DEC-985: an exclusion list is never a parking space). ENUMERATE, never sample -- the same shape that closed the LIKE-escaping and epoch-validation classes.

Note for the scribe/operator: DEC-512 was the single remaining gap in the three-digit id space (001-999 are otherwise all taken); the next new decision needs a four-digit id and a matching edit to decisions/README.md's "three digits" rule.
