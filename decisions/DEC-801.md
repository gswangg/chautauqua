# DEC-801: A task cannot be late before it was assigned: an assignment's effective due date

VERIFIED src/server/repo/submissions/status.ts:189 — planAndPersistOnboardingTasks derives ONE shared due date per task title from the event start (DEC-520) and then attaches every new contact to it, so a speaker added today inherits a date that may already be past. The CRM grader measured the consequence: one add-to-event click created 5 assignments, 3 of them BORN OVERDUE, and the nav badge went 9 -> 12 LATE. Nothing is wrong with the task's date — it is right for everyone who had it in time — so the fix is not to mutate the shared task and not to suppress lateness forever. Decision: a pure src/domain/task-due.ts owns the rule `effectiveAssignmentDueDate(taskDueDate, assignmentCreatedAt)` = taskDueDate when the task was already due-dated at or after the assignment was created, else assignmentCreatedAt + ASSIGNED_LATE_GRACE_DAYS (7). Every surface that judges lateness reads that ONE function — the server's overdue count, the Speakers grid cell, and the reminder rows — so the badge, the cell and the email can never disagree. A late-added speaker gets a real deadline they can still meet, and stays chaseable a week later; the rule is data-free and clock-free apart from its arguments, so it is testable in isolation.

## Amendment (wave 58): overdue is a CALENDAR-DAY verdict in the owning event's timezone — effectiveAssignmentDueDate gains a timezone, and all five readers go through it

Verified at the file on main: src/server/repo/tasks/crud.ts:186 and src/server/repo/tasks/grid.ts:133 both compare `effectiveDueDate < ${now}` against a raw task.due_date; app/src/pages/speakers/overdue.ts:17 does `effectiveDueDate < now`; src/routes/portal/index.tsx:133 does `effectiveDue < now`. task.due_date is a DAY LABEL (UTC midnight of the intended calendar day) — src/domain/reminders.ts:59 says so verbatim, citing DEC-522 — so every one of those comparisons flips at UTC midnight. For an America/Los_Angeles event a task due 1 Mar reads OVERDUE from 16:00 on 28 Feb: the chip, the counter, the ?overdueOnly= filter, the Overview 'N days late' rows and the speaker's own portal all lie by a day, on the exact screen SPEC J6 exists to answer ('who still owes me what?'). DEC-801 already rules that ONE function owns lateness; it is missing its timezone argument. RULING: (a) src/lib/timezone.ts gains `dayLabelOfInstant(instantMs, timeZone)` — the UTC-midnight day label of the calendar date `instantMs` falls on in that zone, the inverse of dayLabelStartInstant, with the same fail-loudly range guards as its neighbours; (b) src/domain/task-due.ts gains the ONE verdict `isAssignmentOverdue(taskDueDate, assignmentCreatedAt, now, timeZone)`: null due date is never overdue; when taskDueDate >= assignmentCreatedAt the verdict is `now > dayLabelEndInstant(taskDueDate, timeZone)` (a day label ends at event-local midnight); otherwise the DEC-801 grace branch is a real INSTANT and stays `now > assignmentCreatedAt + GRACE_MS`; (c) its SQL twin compares the day-label branch against `overdueDayCutoff(now, timeZone)` = dayLabelOfInstant, keeping the grace branch against `now` — one CASE expression, still set-based; (d) every reader takes the owning event's IANA timezone, which means the onboarding-grid envelope carries `timezone` (a reader cannot apply a rule its endpoint does not send). Explicitly NOT in scope: src/domain/reminders.ts's DUE_WINDOW_MS 72h pre-window and REMINDER_OVERDUE_TAIL_MS 7d tail — those are deliberately-early instant windows, not overdue verdicts, and a sub-day skew on a 72h/7d boundary changes nothing a user reads.
