# DEC-813: Every write that makes a participant ACTIVE creates their onboarding tasks

DEC-278 says acceptance fires the J6 auto-creation exactly once, idempotently. Two of the three write paths honour it — POST /submissions/:id/participants (src/routes/api/submissions.ts:443-446) and the portal accept (src/routes/portal/index.tsx:598-603) — but PATCH /submissions/:id/participants/:participantId (submissions.ts:499) writes inviteStatus='accepted' and stops. That PATCH is exactly what the Speakers grid's own status control calls (OnboardingGrid.toggleInviteStatus, app/src/pages/speakers/OnboardingGrid.tsx:231), so one click on the who-owes-what grid produces a publicly visible speaker with zero onboarding tasks who then never appears on that grid. Decision: the PATCH ensures tasks under exactly the sibling's guard — submission status 'accepted' AND isActiveParticipant(new status) — using the participant row the handler already reads back, so the invariant is 'any transition INTO an active invite status on an accepted submission ensures tasks', stated with the imported predicate rather than a restated one. ensureOnboardingTasks is already idempotent, so a repeat PATCH writes nothing.
