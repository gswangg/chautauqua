# DEC-579: CFP track selection stays multi-select; the defect is the label, not the control

The fidelity report calls the CFP's track checkboxes "a functional bug — single-track data model" and asks for radios. Rejected on the evidence: SPEC J1/J2 say the producer "sets one or more tracks on the form" and the speaker "picks track(s)", submission_track is a join table, and both src/routes/public/submit-views.tsx and src/routes/portal/edit.tsx already post a repeating trackIds field that the server reads as a set. Swapping in radios would silently truncate any existing multi-track submission the first time its owner edited it — turning a cosmetic finding into the fourth data-loss path of the round. What is actually wrong is the singular legend "Track *" over a multi-select, so the fix is copy: "Tracks *" with "Choose all that apply". No task this wave; this rides the public-CFP redesign so a later worker does not implement the report literally.
