# DEC-547: makeMailer selects the dev sink ONLY in dev mode; every other configuration must present an EMAIL binding or throw

src/server/context.ts:50-60 reads `if (env?.EMAIL && !isDevMode(env)) {...} return new DevSinkMailer(log)` — so an environment with no EMAIL binding and DEV_MODE unset silently falls through to the dev sink. Every send then writes an email_log row with status 'sent', compose/send answers {sent: N, failed: []}, and nothing leaves the building — while /dev/mailbox 404s, so the mail is not even inspectable. This is the exact silent-fallback shape the house rule forbids, and the two adjacent lines already do it right (MAIL_FROM_EMAIL missing throws at :53; pubcache.ts:140,164 throws on a missing KV binding). DEC-450 set the precedent that a stage-2-wired adapter's code correctness is stage-1 work. Decision: (a) the branch inverts to lead with the predicate — `if (isDevMode(env)) return new DevSinkMailer(log)` — so the dev sink is reachable by exactly one deliberate condition and never by omission. (b) Outside dev mode a missing EMAIL binding throws an Error naming both DEV_MODE and EMAIL, alongside the existing MAIL_FROM_EMAIL throw. (c) The `env?` parameter becomes REQUIRED: all seven call sites already pass it (routes/tasks.ts:452,481, api/users.ts:94, comms.ts:448, api/contacts/bulk-email.ts:151, review/plans.ts:394, public/submit.tsx:770), and an optional env is what let `undefined` mean "dev sink". (d) Stage-1 behavior is unchanged by construction: .dev.vars sets DEV_MODE=1, so `npm run dev` with zero secrets still gets the sink. The regression bar is the throw: no EMAIL + DEV_MODE unset/'0'/'true' throws; no EMAIL + DEV_MODE='1' returns DevSinkMailer.

## Amendment (wave 43): mail dispatch is a BOUNDARY, not a bootstrap — makeMailer never throws

src/server/context.ts:63-64 throws when RESEND_API_KEY/MAIL_FROM_EMAIL are absent in non-dev, so EVERY send path (CFP confirm, decision notices, bulk email, reminders, remind-laggards, note replies) 500s before its loop — after the enclosing mutation already persisted. That is the opposite of failing loudly: the user sees 'Internal server error' on a submission that saved, and retries into duplicates, while zero email_log rows are written so the send is not even auditable. Amendment: makeMailer returns an UnconfiguredMailer (src/mail/unconfigured.ts) whose send() writes the email_log row (provider 'none', status 'failed', reason 'mail provider not configured') and then throws MailNotConfiguredError, which every send site already catches per recipient. Missing config stays loud through the read surface (DEC-996 amendment), never through a 500 on a user action. DevSinkMailer behaviour in dev is unchanged.

## Amendment (wave 18): makeMailer never throws, so nothing may catch it — the remind endpoint's swallow is deleted

DEC-547's wave-43 amendment made makeMailer NEVER throw (src/server/context.ts:70-92 returns UnconfiguredMailer, which fails from *send* inside callers' per-recipient try). Two comments still assert the opposite and one of them justifies a live catch: src/routes/tasks.ts:491-515 wraps BOTH makeMailer and the entire `await remindNow(...)` call, so any genuine bug inside the reminder pipeline is converted into `200 {sent: 0, failed: [{email: "*"}], skipped: 0, remaining: 0}` — a fail-loudly violation (SPEC §2.6) that no test exercises because the only test proving it mocks makeMailer into throwing, a fiction. src/routes/tasks.ts:566-571 repeats the false premise in a comment (its per-event try is still correct, for send failures). RULING: the endpoint calls makeMailer + remindNow unguarded; the config-failure case keeps its 200 {sent, failed} envelope because UnconfiguredMailer.send already lands in remindNow's own per-recipient boundary, and a thrown bug becomes a real 500. The `email: "*"` sentinel dies with it: a failure is reported per recipient or not at all.

## Amendment (wave 62): everything that can throw runs BEFORE the first durable write; after it, only per-recipient failures, inside the envelope

src/routes/content-notes.ts:110 durably writes content_status='changes_requested' (which drops the session off every public surface), and only then calls resolveBaseUrl(c) at :118 — which throws by design when PUBLIC_BASE_URL is unset outside dev (src/server/origin.ts:123-127) — and resolvePortalLinks at :137, which can throw on KV failure. DEC-547's wave-43 amendment already put the mailer construction inside the per-recipient guard; it stopped one step short. The organizer sees a failed request for a change that is already applied, and the load test flagged PUBLIC_BASE_URL as load-bearing on deployed origins. RULING: pure config resolution (resolveBaseUrl and any env read) hoists ABOVE the first durable write, so the loud refusal happens before anything is committed. IO that itself has side effects — notably any minting resolvePortalLinks does — stays below the write (DEC-397 forbids minting for a note that may not commit) but runs inside the failure envelope, so its failure reports {sent: 0, failed: [...], recipients: N} at 200 rather than a 500 behind an applied unpublish. Fail-loud is preserved in both halves: the throw still happens, it just happens where nothing is half-done.
