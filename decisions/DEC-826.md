# DEC-826: The effective due date is the date every surface SHOWS, not merely the one the server selects on

VERIFIED DEC-801's rule is half adopted. overdueAssignmentConditions (src/server/repo/tasks/crud.ts:119-128) applies the effective date in SQL, so the overdue SET is right everywhere — but the Overview's own rows still carry the raw task date (src/server/repo/overview.ts:161,179) and buildOverdueTaskRows derives 'N days late' from it (overview/aggregate.ts:59), so a row the effective predicate selected because it went late two days ago can be captioned '42 days late'. Worse, the speaker's portal — the one person who has to meet the deadline — renders `Due {task.dueDate}` and computes overdue as `t.dueDate < now` (src/routes/portal/index.tsx:121,133 and portal/tasks.tsx:213,343), so a speaker added last week is told they are already late for a date that passed before they existed, while the organiser's grid and the reminder email say otherwise. Decision: every surface that PRINTS a due date or a lateness figure computes it through effectiveAssignmentDueDate, which means the assignment's createdAt travels with the row: the portal task projection returns it, the Overview overdue rows return it, and the number is derived where the row is built (server-side on both surfaces) so no client can re-derive it differently. One rule, one arithmetic, three surfaces that cannot drift.
