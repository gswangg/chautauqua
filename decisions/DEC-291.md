# DEC-291: Form-task responses are organizer-readable through one read-only assignment-scoped endpoint, entered from the Speakers onboarding grid; travel/logistics data lives in those responses, never in a new schema column

docs/clarifications.md (which overrides everything) names 'hotel stay requirement form' and 'flight reimbursement form' as MUST-HAVE onboarding tasks, and src/domain/acceptance.ts:14-63 implements them with real field specs (hotel yes/no, check-in/out, special requests; flight yes/no, departure airport...). The speaker fills them at /portal/tasks/:id/form and src/server/repo/portal.ts:448 saveTaskFormResponse persists response_json — but NOTHING organizer-side reads it: getOnboardingGrid's GridCell (src/server/repo/tasks.ts:93-98) exposes only status/completedAt/fileId, and grep for responseJson finds no admin surface. Collecting a producer's must-have logistics data and giving the producer no way to read it is the defect. Fix: `GET /api/v1/task-assignments/:id/response`, requireOrganizer + the existing getAssignmentOwnership org-scope check (404 on a foreign org, never 403-with-existence-leak, matching the review-IDOR house rule), returning `{ assignmentId, taskTitle, contact: {id,name,email}, status, completedAt, fields: [{label, value}] }` where fields are built by joining the stored AnswerMap (keyed by form_field.id — src/forms/types.ts:36) against listFields(db, task.formId) IN FIELD ORDER, with unanswered fields rendered as an empty value rather than dropped. The grid's `tasks[]` entries gain `kind` (one line, cheaper than a per-cell flag) so the UI offers 'View response' only on form-kind columns. This is also the honest answer to SPK-15: travel/logistics data is the hotel/flight responses plus DEC-292's contact field — we do NOT add a `travel` column to the former src/db/schema.ts (now split across src/db/schema/) (that would need a hand-authored migration and the migration-parity tripwire for a field the rubric explicitly says a generic custom field satisfies).
