# DEC-335: listSubmissions is always ONE paginated SQL statement: q/trackId become correlated EXISTS predicates, the id-materialization and its JS fallback are deleted, and every sort carries a deterministic tiebreaker

src/server/repo/submissions/list.ts materializes candidate ids for q (:96-119) and trackId (:121-134) and then, above ID_CHUNK_SIZE matches, fetches EVERY matching row in ceil(n/90) sequential D1 round trips and sorts/slices in JS on every page request (:150-163). J3 is 'triage hundreds of submissions without drowning ... a table built for volume' and SPEC §7 mandates server pagination; the current shape makes page 1 and page 40 cost the same as the whole event. Both predicates are exactly expressible in SQL: q = lower(title) LIKE ? OR EXISTS(participant JOIN contact correlated on submission.id with lower(first||' '||last) LIKE ?), trackId = submission.track_id = ? OR EXISTS(submission_track correlated). With those in the WHERE, total is one COUNT(*) and the page is one ORDER BY ... LIMIT ... OFFSET — no inArray over request-scale ids at all, which satisfies DEC-078/DEC-104 by construction rather than by exemption. LIKE patterns must escape \ % _ with an explicit ESCAPE clause (the old superset-then-narrow shape hid unescaped wildcards behind a JS pass that is now gone). Every ORDER BY appends submission.seq as a tiebreaker so OFFSET pagination is deterministic when created_at/title tie — the seed creates rows in one batch, so this is not hypothetical. sortSubmissionRows, its barrel re-export in src/server/repo/submissions.ts and its tests are deleted with the branch they served.
