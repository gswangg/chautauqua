# DEC-825: The content worklist's chips are the three questions an organiser asks, each counted by its own predicate

VERIFIED app/src/pages/content/SessionList.tsx:5-17 renders four uncounted pills and its own comment flags the drift: the mock collapses changes_requested+pending into one 'Needs a decision' pill, and the build 'still renders four pills rather than the mock's three — flagged as a follow-up, not silently faked'. Two chips that answer one question are one chip with a count, and an uncounted chip makes the organiser click to find out whether it is worth clicking. The API already answers the collapsed predicate — ContentApp.tsx:98 requests contentStatus='changes_requested,pending' for the header figure — so nothing new is needed server-side. Decision: the strip is exactly 'Needs a decision · N' (pending ∪ changes_requested), 'Approved · N', 'All accepted sessions · N', in that order; each chip's COUNT is fetched with the SAME contentStatus predicate its own tab filters by (one predicate over one set, the field guide's standing rule), so the number on a chip and the rows behind it can never disagree; and ?tab= stays the URL state with the new vocabulary, with no back-compatibility alias for the retired tab names.

## Amendment (wave 38): content approval is a bulk action on the worklist, set-based and cache-purging

content_status defaults to 'pending' (src/db/schema/submissions.ts:25) while the public gate demands 'approved' (src/server/repo/public/gates.ts:26), and the only writer is single-id POST /api/v1/submissions/:id/content-status. At SPEC §0 scale (500-5,000 submissions, 200-800 speakers) the entire J10 surface stays empty until a producer clicks approve once per session; SPEC §2 principle 2 requires bulk actions on every table that assumes thousands of rows, and the sibling status pipeline already has one (POST /events/:eventId/submissions/status). Ruling: a bulk content-status route with the same shape as its status sibling — bounded ids (DEC-182), atomic preflight naming unknown ids (DEC-019), set-based chunked write (DEC-355 precedent), event-ownership checked — plus row selection on the Content worklist. It is publish-affecting, so the route joins PUBLIC_AFFECTING in src/server/pubcache.ts exactly as its single-id sibling did (DEC-627).

## Amendment (wave 72): bulk approval stays; the worklist's title row does not carry it

Gate-4 flagged the select-all column plus a filled `Approve N ready` primary as unframed, and asked for a ruling rather than a silent drop. The two halves are not the same thing. The filled primary renders whenever ANY row is unapproved (ContentApp.tsx:355) — no selection required — which makes an event-wide write the most prominent element on a scanning surface, and that is what the frame is objecting to. The selection column is different: it only ever arms a bulk bar that itself renders solely when a selection exists, which is already the conditional-and-quiet grammar. Ruling: capability wins, prominence loses. The selection column and the selection bulk bar (with its filled primary — it appears only in answer to a deliberate selection) are kept exactly as they are; `Approve N ready` leaves the title row and becomes a section action on the worklist's own rule, the house link-on-the-rule treatment, keeping its ConfirmDialog and its page-scoped set unchanged. Separately, the worklist's status vocabulary inverts its emphasis to match the frame: `Re-uploaded` is bold ink (something changed and needs you), `Not reviewed` is muted (nothing has happened yet) — weight carries the state, never colour (DEC-367/DEC-730).

## Amendment (wave 12) — standing ruling on the mandate's 'DEC NEEDED: worklist select-all + Approve N ready': KEEP the capability; the relocation already shipped

The mandate asks a capability question (keep bulk approve on the content worklist and restyle it quieter, or drop it for frame purity). Ruling: KEEP — a frame 'extra' is a capability, and eval bulk-approve is a real producer job; frame purity never justifies deleting a write path. Verified on main: ContentApp.tsx already moved 'Approve N ready' off the title row onto the worklist's own section rule (link-on-the-rule treatment, conditional on notApprovedIds.length > 0) with its confirm dialog intact. No task is issued; this decision exists so the clause is not re-litigated or silently dropped at a later gate.

## Amendment (wave 25)

**The content worklist has ONE approve verb and ONE scope, in a bar below the filters**

Ruling A1 settles the DEC-needed item the mandate flagged: two olive primaries whose scopes differ (eligible-on-page vs ticked) leave a user unable to tell which one they are pressing. The section-rule "Approve N ready" action and its confirm dialog are DELETED; the bulk bar is the only approve control, and it moves inside the worklist to sit BELOW the tab chipstrip and directly ABOVE the table header, because a selection bar must be adjacent to its selection and because the filter governs the bar, not the reverse. The bar's other verbs (Ask for changes, Reset to pending) go — those already live per-row on the deliverable detail. Re-uploaded rows arrive pre-ticked (a re-upload answers changes you specified, so you already hold the context); never-reviewed rows never do, because a file nobody has opened is exactly the batch that needs friction. Select-all renders the partial mark when the page selection is partial — a checked select-all over a partial selection asserts something false.

## Amendment — USER RULING 2026-08-16: the Re-uploaded pre-tick is retired; idle bulk bars render a capability hint

Selection state must assert user intent. The wave-25 pre-tick (SessionList's seeded useEffect that selected every Re-uploaded row on fetch) put rows into the selection without a gesture, so a bulk write could act on rows the producer never touched. It is DELETED — selection now only ever comes from user gestures. The one-gesture affordance it provided moves into the idle bulk bar as an explicit action: when the current page holds N Re-uploaded rows (same predicate, worklistStatusLabel(...) === 'Re-uploaded'), the idle bar's hint reads "N re-uploads are waiting for re-review — Select them", where "Select them" (.chq-bulkbar-hint-action, house link register) sets the selection to exactly those ids; with none, the generic capability hint shows instead. More generally, the always-mounted bulk bars (submissions, contacts, content worklist) no longer reserve their idle space invisibly: idle is a real quiet state — same box height as the armed bar (the hint line copies .chq-btn's vertical metrics; guarded in test/design-system.test.ts), no fill, no aria-hidden — carrying one muted .chq-bulkbar-hint line that names what selection unlocks on that surface. The armed state is unchanged.
