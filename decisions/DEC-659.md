# DEC-659: A scope row carries its own LABEL from the server: GET /api/v1/plans/:id/reviewers emits trackName and submissionRef/submissionTitle beside the ids, and the plan editor never prints a ULID

app/src/pages/review/PlanEditor.tsx:744 renders 'Track <ULID>' / 'Submission <ULID>' and :742 falls back to the raw userId when an email is missing -- internal handles the organizer never chose and cannot read, the same defect DEC-650 names for the CFP builder's conditions, in a file that decision does not own. The fix belongs on the server for the same reason DEC-265 put contact name/email on the participant response: an optimistically appended row must render identically to a reloaded one, and the SPA has no way to resolve a submission id it never listed. Resolution is one batched lookup per page over the distinct track/submission ids, never per row. A track or submission that no longer exists says so in words.

## Amendment (wave 55): the label contract belongs to the WRITE response too, not only the list mapper

POST /plans/:id/reviewers returns the raw plan_reviewer record (src/routes/review/plans-reviewers.ts:114-116 single form, :61-70 DEC-924 array form) with none of the name fields the GET mapper computes, and PlanEditor pushes that response straight into its rendered list (app/src/pages/review/PlanEditor.tsx:752, :817), whose label expression at :1442-1450 falls through to 'Track (removed)' / 'Submission (removed)' whenever the name is absent -- so a reviewer assigned seconds ago is labelled as pointing at a deleted record until the page reloads. This is the same TWO READERS OF ONE STORED ID defect the base decision fixed for the read path: the id VALIDATES on the write path but only the read path ANSWERS what it names. Ruling: the POST 201 carries the identical trackName/submissionRef/submissionTitle fields the GET mapper computes, derived from the same getTrackNamesByIds/getSubmissionLabelsByIds batched helpers, so an optimistic client insert and a reload render byte-identical labels.
