# DEC-866: A portal co-presenter is shown under the name the speaker typed; a CRM identity matched from a supplied email is never echoed back

VERIFIED. src/server/repo/portal-edit.ts:449 resolves the speaker-supplied co-presenter email against the WHOLE org directory via findContactByEmail and then discards the submitted first/last name; getPortalParticipants (portal-edit.ts:363-391) inner-joins contact and returns `${firstName} ${lastName}` — so the speaker types 'Bob Smith <ceo@bigcorp.com>', reloads /portal/submissions/:id/edit, and the org's real record ('Jane Doe') is rendered back at them. That is an org-directory read oracle on a speaker surface, against SPEC J7 'only their own content, ever'. The link itself stays: email is this product's contact identity (DEC-454) and creating a shadow duplicate to avoid an echo would corrupt the directory the CRM graders call flawless — the LEAK is the echo, not the join. Decision: participant gains a nullable `name_at_time` column (migrations/0027_participant_name_at_time.sql), joining DEC-258's existing titleAtTime/orgAtTime snapshot family and read by the SAME rule: addCoPresenter writes the SUBMITTED first/last on BOTH branches (matched contact and freshly created), getPortalParticipants selects it and renders `nameAtTime` when present, falling back to the live contact name for rows this path did not create (the original submitter, organizer invites). The echoed EMAIL stays as-is — it is the submitter's own input, normalized. DEC-604's rule that this path never writes to an existing contact is untouched, and remains asserted by the existing fake db that throws on db.update().
