# DEC-461: One uniform mechanism for DEC-460: optional repo page param + sibling count fn + deterministic ORDER BY; internal non-HTTP callers stay unbounded

Four lanes implement DEC-460 in parallel and must not invent four shapes. (a) Route layer parses with clampPage/clampPerPage from src/lib/pagination.ts, except that these previously-unpaginated endpoints pass a default perPage of MAX_PER_PAGE (200) rather than 50 — the clamp max is unchanged, but no admin screen that renders every row today loses rows the day this lands, since the SPA has no paging UI for them. (b) The repo keeps ONE function per list, gaining an optional trailing `page?: { limit: number; offset: number }` parameter; absent means today's unbounded behavior, because several of these helpers have internal non-HTTP callers that legitimately need every row — the agenda needs every track, and src/server/repo/files-authz.ts:153 calls listPlansForEvent inside reviewerCanAccessSubmissionFile, where a paged read would silently weaken a security check. Never a duplicate "...Page" function, never a mandatory limit. (c) `total` comes from a sibling count* function over the same WHERE, never from items.length. (d) Every newly-paged list needs a deterministic ORDER BY with a unique tiebreak (…, id asc), because LIMIT/OFFSET over an unordered SELECT returns arbitrary pages — listEventsForOrg and listSegmentsForOrg have no ORDER BY at all today and listResourcesForEvent sorts in JS after loading everything. (e) SQL LIMIT/OFFSET is the required mechanism; the single blessed exception is a list assembled in JS from an already-bounded id set, which may clamp with a slice provided `total` still reports the true count.

## Amendment (wave 22): a read whose only consumer is [0] takes a page of one

src/routes/api/users.ts:92 calls `listEventsForOrg(c.var.db, auth.orgId)` with no page argument -- the repo's `page` is optional (src/server/repo/events.ts:71) -- and then reads only `orgEvents[0]` to anchor the welcome email's NOT NULL `email_log.event_id`. That materialises every event row in the org on a WRITE path, which is exactly the unbounded read DEC-461 exists to forbid and which SPEC section 7's budgets do not cover. The repo already orders `desc(startDate), asc(id)`, so a `{ limit: 1, offset: 0 }` page returns the identical anchor row deterministically. Ruling: pass the page. The rule generalises -- when the only consumer of a list read is its first element, the read declares limit 1 rather than trusting the caller's subscript to bound it.

## Amendment (wave 78): a read a route paginates in JS must be bounded at the SQL edge

Every JS-side page slice in this tree sits on a scan that refuses past a named ceiling — MAX_PLAN_SUBMISSION_SCAN, MAX_FILE_LIBRARY_SCAN, MAX_CONTACT_DIRECTORY_SCAN, MAX_AGENDA_SCAN, MAX_REVIEWER_SCOPE_ROWS — with exactly one exception: listSubmissionFiles (src/server/repo/files-versions-read.ts:58-93) issues no LIMIT at all and GET /api/v1/submissions/:id/files materialises the whole result then slices it in JS (src/routes/files.ts:275-278). SPEC.md §7 requires server pagination on admin lists, and this repo's own rule is refuse-rather-than-truncate. Ruling: the ceiling belongs with the READ, not with the route — declare MAX_SUBMISSION_FILE_SCAN = 1000 (far above any real version history, far below MAX_FILE_LIBRARY_SCAN so the more specific guard fires first), limit(MAX+1), and throw a loud ApiError naming the cap. And the rule is a POPULATION, not this one function: a scan pairs each JS pagination site with the repo function that produced the array and fails if that function's body has no bound.
