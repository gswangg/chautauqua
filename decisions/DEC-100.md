# DEC-100: Submission seq is allocated atomically: single INSERT with a scalar subquery (SELECT COALESCE(MAX(seq),0)+1 ... WHERE event_id=?) via one shared helper; SELECT-then-INSERT allocation is deleted

Two duplicate implementations (nextSubmissionSeq in src/server/repo/submit.ts:151 and nextSeq in src/server/repo/submissions/create.ts:16) do a non-atomic SELECT MAX then INSERT against the unique index submission_event_id_seq_idx; two deadline-burst public submitters collide and the loser's fully-filled form dies with an unhandled UNIQUE 500 — exactly the SPEC §0 500-5,000-submission burst case. SQLite/D1 executes each statement atomically under a single writer, so embedding the seq as a scalar subquery inside the INSERT itself eliminates the race with no transaction machinery. One shared fragment helper lives in src/server/repo/submissions/seq.ts and is used by all three insert sites (public submit createSubmission, manual createSubmission, cloneSubmission); both old helpers are deleted with no compat shims (house rule). Callers needing the allocated seq read it back by id after the insert.

## Amendment (wave 52): a coverage cap is not an identity — read-then-write caps stay, atomicity is owed to identity and uniqueness invariants only

Recorded to stop a churn cycle I can see coming, since three separate house rules ('MINTING IS IO', 'atomic SQL > read-then-write', 'a uniqueIndex is a CONTRACT') read as if they condemn every count-then-insert in the tree. They do not. Verified this wave: src/routes/review/reviewer.ts:452-457 counts submitted evaluations and then upserts (maxEvaluations); src/server/repo/participants.ts:104 and src/server/repo/portal-edit.ts:486 count participants against MAX_PARTICIPANTS_PER_SUBMISSION; src/routes/api/breaks.ts:175 counts breaks; src/routes/api/forms.ts:171 counts form fields. All four are read-then-write, and under concurrency each can admit exactly one extra row. RULING: that is not a defect. The distinction is what the race can corrupt. A seq (DEC-100), a version number (DEC-818/migrations/0043) or a join-table pair (migrations/0019) is an IDENTITY — a race there produces two rows claiming to be the same thing, which no later read can disentangle, so those get atomic SQL or a uniqueIndex. A coverage cap is an editorial preference whose worst outcome is one extra review or one extra co-presenter, fully visible and fully reversible in the UI that shows the list. schema.evaluation already carries uniqueIndex(planId, submissionId, reviewerId, round), so the identity half is closed. Do not re-file the cap race for any of the four sites; do not 'harden' them into conditional INSERT...SELECT statements that every drizzle-chain fake in test/ would then have to model.
