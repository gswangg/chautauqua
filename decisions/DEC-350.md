# DEC-350: The J5 compose recipient picker becomes server-paged and searchable with an explicit total; its silent 200-row truncation is a stage-1 defect

app/src/pages/comms/ComposeWizard.tsx:42 issues exactly ONE request — page 1, perPage 200 — and renders `submissions` with no page control, no search box and no total. At SPEC §0's scale targets (500–5,000 submissions/event, 200–800 speakers) a producer physically cannot select a decided record ranked 201st or later, and nothing on screen says so. That is precisely the "demos well with 10 rows and dies at 2,000" pattern SPEC §2.2 forbids, and it is worse than a perf bug because it silently removes data from the producer's field of view, violating SPEC §2.6 fail-loudly. The server side is already correct and needs no change: listSubmissions is one paginated statement whose `q` predicate covers title + speaker name (DEC-335) and whose DEC-013 envelope carries `total`. Binding contract, SPA-only: perPage = 50; `page` and `q` are component state; the query string is built with the existing buildSubmissionsQuery (app/src/pages/submissions/filters.ts) so the wire contract stays single-sourced; the picker renders "Showing X–Y of N" and prev/next buttons disabled at the ends, mirroring the OnboardingGrid idiom DEC-340 established; changing the status checkboxes or the search text resets page to 1; and selectedIds SURVIVES paging, filtering and searching, matching the submissions table's cross-page selection semantics (app/src/pages/submissions/selection.ts). The DEC-019 100-recipient cap stays server-side on the expanded recipient list with its existing banner. Explicitly forbidden: filtering or sorting the fetched page in the client — that is the exact defect DEC-341 and DEC-345 removed elsewhere.
