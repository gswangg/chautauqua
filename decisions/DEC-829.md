# DEC-829: The Speakers roster lists every participant of an accepted submission; ACTIVE is the predicate for expansion and access, never for LISTING

VERIFIED the two halves of one screen contradict each other. GridFilters.tsx:65-75 renders a filter pill for all four INVITE_STATUSES, while src/server/repo/tasks/grid.ts:171 bases every row on acceptedSpeakerExistsForContact — which requires inviteStatus in ACTIVE_INVITE_STATUSES ('none','accepted') — and grid.ts:175-179 says so in its own comment: 'a filter value outside none/accepted correctly yields zero rows'. So two of the four pills can only ever return an empty grid, and an organiser who sets someone to Invited watches the row vanish on reload: the dying-on-reload control the field guide already names. Decision: the roster is the EVENT'S ROSTER — the grid's base row predicate becomes rosterParticipantExistsForContact(eventId) (participant of an ACCEPTED submission in this event, ANY invite status), and the three per-row scalar subqueries (participantId/submissionId/inviteStatus, grid.ts:209-211) resolve over the same widened set so a row and its control can never disagree. ACTIVE_INVITE_STATUSES keeps its exact meaning everywhere else and is NOT widened: listAcceptedContactIds (task expansion), overdueAssignmentConditions (a declined speaker is not chased), public visibility (DEC-274), comms audiences, files-authz and the portal write gate (DEC-317) are untouched. This deliberately amends DEC-754's 'the roster it lists and the set createTask expands over are one set': listing and expanding are different questions, and a row with no cells is the honest way to say 'this person owes nothing yet'. The grid's `speakers` count is that surface's own predicate — the roster total.

## Amendment (wave 59): invite-active is the CHASE set, and every reminder query must compose it — not just the ones that already did

DEC-829's own prose enumerates its consumers: "Every other consumer of 'who gets a task assignment / chase / public-visible slot' (listAcceptedContactIds, overdueAssignmentConditions, files-library's headshot branch, comms audiences, public/portal access) keeps composing acceptedSpeakerConditions unchanged." Verified at file:line, every named consumer honours it EXCEPT the chase itself: src/server/repo/tasks/reminders.ts:55 `listOutstandingForEvent` joins task_assignment -> task -> event -> contact with no participant predicate, and :137 `listRemindableContactIds` groups over task+assignment alone. Consequence: a speaker who DECLINES their session invite (participant.invite_status='declined') keeps every onboarding assignment created while they were active, so the */15 cron and the organizer's "remind everyone outstanding" keep emailing a person who declined — while `overdueAssignmentConditions` (crud.ts:146, composing acceptedSpeakerExistsForContact) correctly reports them as owing nothing. Two sibling readers of one question; per the house rule the younger/stricter one is right. RULING: the chase set is exactly the task-expansion set — ACTIVE_INVITE_STATUSES ('none','accepted') on an accepted submission of the event, expressed as ONE exported correlated-EXISTS predicate composed by both reminder queries, so preview, send and the overdue count are the same arithmetic fact. A contact active on any accepted submission of the event stays chaseable even if they declined a different one. The cron's event-level enumeration is deliberately left as a superset filter (wave 58 lane a owns it); the per-event queries are the authoritative gate.

## Amendment (wave 61): a Remind control renders only where something is outstanding, and a zero-recipient reminder preview says why instead of showing an empty list under a header

DEC-829 already rules that a declined-only roster row offers no per-row remind action 'instead of a live control nothing will act on' (OnboardingGrid.tsx:889-903). The same reasoning was never extended to the other way a remind is guaranteed to send nothing: the speaker has no incomplete assignment. Both surfaces render the control regardless — OnboardingGrid.tsx:901/980 for any non-declined row, SpeakerDetailPage.tsx:297 unconditionally in the header plus 'Remind this task' on COMPLETED task rows — while the design handoff states the rule verbatim: 'Each row with something outstanding carries a quiet Remind <first name> link; rows that are fully complete carry nothing, by the same conditional-and-quiet rule as the Response link.' Clicking it opens RemindPreviewModal with drafts=[], skipped=0, remaining=0, which renders 'Review reminders / 0 recipients', an EMPTY <ul>, no draft and a disabled Send — headers over nothing, the one shape B7 forbids outright, and a refusal that names nothing. The dialog's zero-state must say which of the three reasons applies from the envelope it already receives (all reminded within the hour when skipped>0; otherwise nothing outstanding / not being chased), and hide the recipient list chrome rather than print an empty one.

## Amendment (wave 29): the onboarding grid's row set is driven by the event-scoped roster join, never a full scan of `contact`

`getOnboardingGrid` issues three statements shaped `from contact where <correlated EXISTS over participant JOIN submission>` — the COUNT (src/server/repo/tasks/grid.ts:240-244), the page (`:248-262`), and `speakersCount` (`:390-393`) — via `rosterParticipantExistsForContact` (src/server/repo/tasks/crud.ts:109-111). The outer relation is the ORG's entire contact directory, so cost scales with the directory rather than with the event's roster. Measured at `ceda66f2` (docs/verification-log.md:3750-3759): 116.1ms adjusted at 800 contacts (default profile) rising to 995.7ms at 6,000 contacts (aie), also breaching the 150ms raw ceiling — an ~8.6x rise against an ~7.5x contact-count rise, versus the 50ms `read` class budget (scripts/perf-smoke-lib.ts:9,19; SPEC §7 via DEC-338/DEC-309). RULING: the driving relation for the grid's row set is `participant ⋈ submission` scoped by `submission.event_id`, with `contact` joined by id purely for name/company/ordering. Identical rows, identical ordering (`lower(last_name) asc, lower(first_name) asc, contact.id asc`), identical JSON envelope — cost proportional to the roster. `rosterParticipantExistsForContact` remains for callers that genuinely start from a contact row; this ruling binds the grid only. A COUNT or an ORDER BY is not a licence to make the org directory the driving table.

## Amendment (wave 32): a list route hydrates DISPLAY-ONLY columns for the rows it EMITS, never for the population it ranks

DEC-829's wave-29 amendment fixed the driving relation (count over the reviewer's own scope, not the plan's). The remaining overrun is a different shape: `/plans/:id/results` and `/review/plans/:id/queue` both compute a ranked population of up to MAX_PLAN_SUBMISSION_SCAN rows and then hydrate every one of them with columns that only the RENDERED rows need. Verified at the tip: `sortValueForColumn` (src/domain/evaluation/results.ts:62-79) reads only ref/title/average/count/perCriterion/perDropdown — never speakers, trackNames, status or recusals — yet buildResults (shared.ts:456-460) issues `listSpeakerNamesForSubmissions` and `listTrackNamesForSubmissions` over ALL ~2000 plan submissions before any slice. Same on the queue: format/audienceLevel/identities (reviewer.ts:166-182) are display fields fetched over the whole scope, then 200 rows at most are emitted. At ~90 ids per chunkIds batch this is ~23 statements per reader that should be 1. RULING: split every paged list route into a RANK phase (population-wide, only the fields ordering/filtering/counting actually read) and a HYDRATE phase (called with an already-sliced id set; the CSV/export path passes the full set explicitly). `total` and any FULL-population counter (unscoredTotal) keep being computed before the slice. This is a structural rule, not a tuning knob: it is what makes the 50ms read budget reachable without touching DEC-440.

## Amendment (wave 33): a per-id loop is not a batch — concurrency hides latency, it does not reduce statement count

DEC-829's wave-32 amendment split ranking from hydration on the two paged review readers. The same file carries a shape that amendment does not cover: `src/routes/review/reviewer.ts:68`, the reviewer branch of `GET /api/v1/review/plans` — the reviewer's LANDING screen — resolves its page with `Promise.all(pagedIds.map((id) => repo.getPlanById(db, id)))`, i.e. one full SELECT+JOIN per id, up to MAX_PER_PAGE=200 statements for one view. It reads as fixed because it is wrapped in Promise.all, which is exactly the trap: concurrency hides the latency of an N+1 without removing the N. RULING: a route that already holds a page's id set resolves it with ONE chunked `IN (...)` read per `chunkIds` batch (`src/lib/chunk.ts`, ID_CHUNK_SIZE=90, DEC-078), never one statement per id, even inside Promise.all. Input-order preservation and missing-id skipping are the batch reader's job, not the caller's. This binds every list route that starts from an already-bounded id list under the DEC-461(e) blessed JS-slice.

## Amendment (wave 59): a roster is a population, not a projection of its tasks — and a success line links to the event it just changed

VERIFIED on main: src/server/repo/tasks/grid.ts:200-202 returns `{tasks: [], rows: [], total: 0, counts: emptyCounts}` the moment the event has zero task rows — so every accepted speaker on an event that has not yet been given onboarding tasks is invisible on /admin/speakers, even though the rest of the function already handles the empty case correctly (the cell query is guarded by `taskIds.length > 0` at :360, and `speakersCount` at :414-419 is derived from rosterParticipantConditions alone, never from task_assignment). This is the root cause of the externally-filed CRM major 'Add to an event confirmed the speaker was added, then /admin/speakers in that event does not show him': the push worked, the grid refused to answer. RULING: the Speakers grid is the event's ROSTER with task columns attached, never a task matrix — the zero-task early return is deleted, an event with no tasks lists every roster participant with `tasks: []` and zero cells, and `counts.speakers` keeps counting the roster it already counts. Second half of the same user-visible outcome: a success line that offers a link must link to the thing it just changed — AddToEventModal's 'View in Speakers' carries `?eventId=<the event just chosen>` (the resolution order DEC-024/useCurrentEvent.ts:56 already honours), never the page's ambient current event, so the organiser lands on the roster that now holds the person instead of a different event's roster.

## Amendment (wave 39): an id-scoped narrowing that spans more than ONE chunk is a fan-out, not a narrowing — issue the single scoped aggregate instead

DEC-078 sets ID_CHUNK_SIZE=90. DEC-829's "the driving relation is the already-scoped set, never a wider table" is right for a track-scoped reviewer holding a handful of ids, but I verified both hot review reads now pass ~2000 ids into `chunkIds`, i.e. ~23 SQL statements per request: (i) `src/routes/review/reviewer.ts:189` calls `countEvaluationsBySubmission(db, planId, round, scopedIds)` where `scopedIds` is the whole scope for an unrestricted reviewer (perf-seed joins every reviewer to every plan), while the SAME function's unscoped branch is "exactly one D1 round trip regardless of caller slice size" and its own docstring already blesses the whole-round map as leaking nothing (`src/server/repo/review/evaluations.ts:159-187` — the queue reads it only via `.get(id)` over its own scoped set); (ii) `listPlanFilteredSubmissions` (`src/server/repo/review/submissions.ts:58-107`) hydrates trackIds "via chunkIds batches over submission_track" for the same ~2000-row matched set. Both are SPEC §7's named N+1 bug class. RULING: when an optional id-scoped narrowing would span more than one chunk, issue the single plan/event-scoped query once instead of N chunked ones; when a hydration set IS the matched set, join it in the same WHERE that produced the match rather than feeding the match's ids back in as an `inArray`. The loud caps (MAX_PLAN_SUBMISSION_SCAN + 1 / MAX_PLAN_EVALUATION_SCAN + 1) and the existing 2-arg contracts are preserved unchanged; this decision is mine and not each lane's, so the two review-perf lanes cannot answer it differently.

## Amendment (wave 74): the plan-results CSV population is already bounded by the plan scan cap — no second EXPORT_MAX_ROWS guard is added

A review lens filed `GET /api/v1/plans/:id/results` as loading the plan's entire submission + evaluation population on every request, and the `?format=csv` path as hydrating every ranked row with no cap, "unlike the sibling export's `EXPORT_MAX_ROWS` refusal at `src/routes/api/exports.ts:178`". Re-derived this wave: ranking the WHOLE population before paging is DEC-345's explicit ruling (paging without moving the sort first mis-ranks everything past page one), so the read is a requirement, not an oversight; and both reads already refuse loudly rather than truncate — `listPlanFilteredSubmissions` at `MAX_PLAN_SUBMISSION_SCAN` (`review/submissions.ts:22`) and `listEvaluationScoresForPlan` at `MAX_PLAN_EVALUATION_SCAN` (`review/evaluations.ts:20`). `MAX_PLAN_SUBMISSION_SCAN` and `EXPORT_MAX_ROWS` (`exports/table.ts:24`) are BOTH 20000, so adding the sibling's guard here would be a refusal that can never fire ahead of the scan refusal already in place — a no-op with a name, which this codebase forbids. RULING: DO-NOT-CHASE. If a future wave wants the CSV bounded tighter than the scan cap, it must change the NUMBER deliberately and say why, not add a redundant guard.
