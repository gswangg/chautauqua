# DEC-829: The Speakers roster lists every participant of an accepted submission; ACTIVE is the predicate for expansion and access, never for LISTING

VERIFIED the two halves of one screen contradict each other. GridFilters.tsx:65-75 renders a filter pill for all four INVITE_STATUSES, while src/server/repo/tasks/grid.ts:171 bases every row on acceptedSpeakerExistsForContact — which requires inviteStatus in ACTIVE_INVITE_STATUSES ('none','accepted') — and grid.ts:175-179 says so in its own comment: 'a filter value outside none/accepted correctly yields zero rows'. So two of the four pills can only ever return an empty grid, and an organiser who sets someone to Invited watches the row vanish on reload: the dying-on-reload control the field guide already names. Decision: the roster is the EVENT'S ROSTER — the grid's base row predicate becomes rosterParticipantExistsForContact(eventId) (participant of an ACCEPTED submission in this event, ANY invite status), and the three per-row scalar subqueries (participantId/submissionId/inviteStatus, grid.ts:209-211) resolve over the same widened set so a row and its control can never disagree. ACTIVE_INVITE_STATUSES keeps its exact meaning everywhere else and is NOT widened: listAcceptedContactIds (task expansion), overdueAssignmentConditions (a declined speaker is not chased), public visibility (DEC-274), comms audiences, files-authz and the portal write gate (DEC-317) are untouched. This deliberately amends DEC-754's 'the roster it lists and the set createTask expands over are one set': listing and expanding are different questions, and a row with no cells is the honest way to say 'this person owes nothing yet'. The grid's `speakers` count is that surface's own predicate — the roster total.

## Amendment (wave 59): invite-active is the CHASE set, and every reminder query must compose it — not just the ones that already did

DEC-829's own prose enumerates its consumers: "Every other consumer of 'who gets a task assignment / chase / public-visible slot' (listAcceptedContactIds, overdueAssignmentConditions, files-library's headshot branch, comms audiences, public/portal access) keeps composing acceptedSpeakerConditions unchanged." Verified at file:line, every named consumer honours it EXCEPT the chase itself: src/server/repo/tasks/reminders.ts:55 `listOutstandingForEvent` joins task_assignment -> task -> event -> contact with no participant predicate, and :137 `listRemindableContactIds` groups over task+assignment alone. Consequence: a speaker who DECLINES their session invite (participant.invite_status='declined') keeps every onboarding assignment created while they were active, so the */15 cron and the organizer's "remind everyone outstanding" keep emailing a person who declined — while `overdueAssignmentConditions` (crud.ts:146, composing acceptedSpeakerExistsForContact) correctly reports them as owing nothing. Two sibling readers of one question; per the house rule the younger/stricter one is right. RULING: the chase set is exactly the task-expansion set — ACTIVE_INVITE_STATUSES ('none','accepted') on an accepted submission of the event, expressed as ONE exported correlated-EXISTS predicate composed by both reminder queries, so preview, send and the overdue count are the same arithmetic fact. A contact active on any accepted submission of the event stays chaseable even if they declined a different one. The cron's event-level enumeration is deliberately left as a superset filter (wave 58 lane a owns it); the per-event queries are the authoritative gate.

## Amendment (wave 61): a Remind control renders only where something is outstanding, and a zero-recipient reminder preview says why instead of showing an empty list under a header

DEC-829 already rules that a declined-only roster row offers no per-row remind action 'instead of a live control nothing will act on' (OnboardingGrid.tsx:889-903). The same reasoning was never extended to the other way a remind is guaranteed to send nothing: the speaker has no incomplete assignment. Both surfaces render the control regardless — OnboardingGrid.tsx:901/980 for any non-declined row, SpeakerDetailPage.tsx:297 unconditionally in the header plus 'Remind this task' on COMPLETED task rows — while the design handoff states the rule verbatim: 'Each row with something outstanding carries a quiet Remind <first name> link; rows that are fully complete carry nothing, by the same conditional-and-quiet rule as the Response link.' Clicking it opens RemindPreviewModal with drafts=[], skipped=0, remaining=0, which renders 'Review reminders / 0 recipients', an EMPTY <ul>, no draft and a disabled Send — headers over nothing, the one shape B7 forbids outright, and a refusal that names nothing. The dialog's zero-state must say which of the three reasons applies from the envelope it already receives (all reminded within the hour when skipped>0; otherwise nothing outstanding / not being chased), and hide the recipient list chrome rather than print an empty one.

## Amendment (wave 29): the onboarding grid's row set is driven by the event-scoped roster join, never a full scan of `contact`

`getOnboardingGrid` issues three statements shaped `from contact where <correlated EXISTS over participant JOIN submission>` — the COUNT (src/server/repo/tasks/grid.ts:240-244), the page (`:248-262`), and `speakersCount` (`:390-393`) — via `rosterParticipantExistsForContact` (src/server/repo/tasks/crud.ts:109-111). The outer relation is the ORG's entire contact directory, so cost scales with the directory rather than with the event's roster. Measured at `ceda66f2` (docs/verification-log.md:3750-3759): 116.1ms adjusted at 800 contacts (default profile) rising to 995.7ms at 6,000 contacts (aie), also breaching the 150ms raw ceiling — an ~8.6x rise against an ~7.5x contact-count rise, versus the 50ms `read` class budget (scripts/perf-smoke-lib.ts:9,19; SPEC §7 via DEC-338/DEC-309). RULING: the driving relation for the grid's row set is `participant ⋈ submission` scoped by `submission.event_id`, with `contact` joined by id purely for name/company/ordering. Identical rows, identical ordering (`lower(last_name) asc, lower(first_name) asc, contact.id asc`), identical JSON envelope — cost proportional to the roster. `rosterParticipantExistsForContact` remains for callers that genuinely start from a contact row; this ruling binds the grid only. A COUNT or an ORDER BY is not a licence to make the org directory the driving table.
