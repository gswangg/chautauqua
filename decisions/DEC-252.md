# DEC-252: Local-first absolute-link origins: resolveBaseUrl precedence + relative same-origin hrefs

The prior campaign's exit battery (docs/verification-log/task-w4-b-walkthrough.md) proved the only red in the tree: under local `wrangler dev`, the `routes`/`custom_domain: chautauqua.cc` entry in wrangler.jsonc (human stage-2 commit, which stays) makes `new URL(c.req.url).origin` resolve to the LIVE production host, so speaker claim/portal links generated in dev point at the deployed site and the walkthrough's claim GET is answered by production with a 410. That breaks SPEC §0's hard stage-1 rule (fresh checkout + npm ci + one dev command = fully working app, zero external dependency). Fix in app code, never by editing deploy config: a single helper `resolveBaseUrl()` in src/server/origin.ts becomes the ONLY source of absolute link bases, with precedence (1) `env.PUBLIC_BASE_URL` when non-empty — must parse as an absolute http(s) URL, trailing slash stripped, otherwise THROW (fail loudly); (2) when `env.DEV_MODE === "1"`, the first loopback origin (localhost/127.0.0.1/[::1]) among [request URL origin, `Origin` header, `Referer` origin] — header sniffing is dev-only and loopback-only so it can never poison links in production (an attacker-supplied Origin must never end up in a mailed claim token link); (3) the request URL origin. Additionally, same-origin links rendered into HTML are RELATIVE (`/claim/<token>`, `/login`) so on-page flows never depend on origin inference at all; only email bodies use resolveBaseUrl. Verification tooling must never fetch an off-origin URL scraped from a page: gates resolve relative hrefs against their own base and FAIL LOUDLY on an off-origin absolute href rather than silently hitting production. wrangler.jsonc's routes/custom_domain, send_email binding and real resource ids stay untouched (stage-2 wiring is out of scope).

## Amendment (wave 18): outside dev, a user-facing absolute link needs a CONFIGURED base — resolveBaseUrl never guesses from the request's Host

resolveBaseUrl (src/server/origin.ts:112-119) falls back to `new URL(c.req.url).origin` — i.e. the request's Host — when PUBLIC_BASE_URL is unset, in NON-dev deployments, on paths that mint credentials into emails: the unauthenticated public CFP (src/routes/public/submit.tsx:632-640 builds /claim/<token> from it), comms sends, content notes, reminders. Its own twin resolveBaseUrlForCron (src/server/origin.ts:129-135) refuses to guess and throws for exactly this reason; the two disagree and the guessing branch is the attacker-reachable one. wrangler.jsonc already sets PUBLIC_BASE_URL in `vars`, so requiring it costs the real deployment nothing and turns a silent link-poisoning path into a loud misconfiguration. RULING: when PUBLIC_BASE_URL is unset and DEV_MODE !== "1", resolveBaseUrl throws with the same actionable message shape as its cron twin. Dev behaviour (loopback sniffing, request-origin fallback under DEV_MODE=1) is untouched. A test that exercises a mailed-link route must state a base URL in its env — that is the honest fixture, not a bug in the rule.
