# DEC-595: The publish result counts through the public visibility gate, never through placement

POST /events/:eventId/agenda/publish returns { published: payload.placed.length } and the SPA prints 'Schedule live — N sessions public.' A placed session that is not content-approved never reaches the public agenda, so the number is wrong in exactly the case an organiser most needs to know about (re-verification measured 5 claimed vs 4 rendered). The endpoint must compute the public count with the same predicate src/server/repo/public/gates.ts uses and return { placed, public, heldBack }; the toast names all three, so the gap becomes information instead of a discrepancy the user discovers on the public page.

## Amendment (wave 67): the publish receipt names the withheld sessions, because a count is information the organizer cannot act on

DEC-595 already ruled that publish must count through the public visibility gate and report `{placed, public, heldBack}` (`src/routes/agenda.ts:158-163`), and the SPA prints "N held back: content not approved." as a transient toast (`app/src/pages/Agenda.tsx:280`). That closed the discrepancy but not the mandate item (P3 #19), which asks for the LIST. A number an organizer cannot resolve to rows is a dead end: they must now go hunting for which of 19 placed sessions are unapproved. RULING: the response carries `heldBackSessions: {submissionId, title}[]` derived from the SAME gate `countPubliclyVisible` uses — one predicate, never a second copy (the gate lives in `src/server/repo/public/gates.ts` and the count already routes through it) — and the client renders the names as links into `/content/:submissionId` rather than only a toast. The list is bounded by the placed set the agenda payload already loads, so no new unbounded surface is created; `heldBack === 0` renders nothing new.
