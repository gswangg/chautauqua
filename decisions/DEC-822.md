# DEC-822: A saved embed saves the recipe, not just the name — and turning one off is an intentional blank, not a broken page

VERIFIED DEC-785 landed the skeleton and stopped one step short of the point: SavedEmbedsPanel.tsx:49 posts `{name, surface, format: 'iframe', options: {}}` and PATCH /embeds/:id (src/routes/api/embeds.ts:88-109) accepts only `name` and `enabled`, so no saved embed can ever carry a track, day, limit, field set or accent — every knob in EmbedsPanel remains stateless and is lost on reload. A saved embed whose filters cannot be saved is a bookmark with a name on it. docs/design/README.md:276-285 states the whole reason for saving: editing the filters later updates every page the snippet is pasted on. Decision: the builder is the EDITOR of one saved embed — it carries a Name field, heads itself 'Editing · <name>' when opened at ?embed=<id>, and its primary action writes the FULL current parameter set (surface, format, and every knob) through POST/PATCH, with Copy demoted to secondary; the list row states the recipe it stores ('Sessions · iframe · AI Engineering · 6 fields') beside its On/Off pill, under the caption 'Turning one off breaks it wherever it is pasted'. DESIGN OVERRIDES DEC-785 on the disabled case: /embed/e/:id for a DISABLED embed returns an empty 200 (an intentional blank inside someone else's iframe), while an unknown id keeps the designed 404 — a page the organiser switched off must not shout 'not found' on a customer's website.

## Amendment (findings wave 11): saved embeds take a per-EVENT creation cap, not a per-organiser one

Saved views, plan criteria, plan rounds, breaks, contact custom fields, segment rules, form fields and participants all declare a cap in src/domain/ and enforce it server-side at creation. Saved embeds are the one organiser-writable collection with none — countEmbeds exists but only feeds the list's pagination total. An embed is live HTML on somebody else's site, so an unbounded table behind it is the least defensible place to leave the gap. The scoping differs from saved views deliberately, and the constant's doc comment must say so: a saved view has an owner and a shared flag, so its cap counts the caller's own rows; an embed has no per-organiser ownership at all — it is a published artifact of the event — so the cap is event-wide by construction, not by oversight. The constant lives in a new embeds module under src/domain/ rather than alongside MAX_SAVED_VIEWS_PER_EVENT, because that file is owned by an in-flight branch and because the two caps mean different things.

## Amendment (wave 59, REVERSES the empty body but NOT the 200): a switched-off embed says it is switched off

This amendment partially REVERSES DEC-822's original ruling that a disabled embed returns an empty 200 body. VERIFIED on main: src/routes/public/saved-embed.tsx:62 is `if (!embed.enabled) return c.html("")`. DEC-822 was right that a page the organiser switched off must not shout 'not found' on a customer's website — that is why the status stays 200 and the cache headers set by setCacheHeaders(c) are kept. It was wrong that the honest expression of 'off' is zero bytes: inside someone else's iframe, white nothing is indistinguishable from a broken snippet, a failed deploy, or a CSP block, and the customer's only move is to file a bug against the wrong system. RULING: a disabled saved embed returns 200 with a MINIMAL body in the public visual language — one quiet line, 'This embed has been turned off.', and nothing else. No event name, no surface name, no link back (the response must leak nothing about an embed the organiser has withdrawn, and must not need an event lookup to render). Status, cache headers and the unknown-id 404 are all unchanged.
