# DEC-890: Templates is a page with a header and rows that say what each template is for and when it was last actually sent

The v5 Comms frame renders Templates as a breadcrumb + H1 + top-right 'New template' over rows carrying the name, a one-line description, a 'Last used <date>' meta, and per-row Duplicate and 'Use in a send'. The build renders a bare list with an inline editor. 'Last used' is not a stored column and must not become one: email_log already carries template_id with its own index (src/db/schema/email.ts:30,53), so the list endpoint computes it as ONE grouped MAX(sent_at) GROUP BY template_id over the event's log — never a query per row (the standing 'a per-row count re-scanning per row is N scans' rule) — and a template no send has ever named reads 'Not used yet' rather than a blank. 'Use in a send' is a link into the composer with the template preselected (?tab=compose&template=<id>), which is a starting point exactly as DEC-846 requires: prefill only, and the composer still posts its own subject/body.

## Amendment (wave 4): a template's NAME is the editor's eyebrow, one template is always selected, and the row says what it is FOR

DEC-890 already ruled that a row says what a template is for and when it was last sent; the rows print the subject line instead, the editor opens blank with a generic 'EDIT TEMPLATE' eyebrow and a NAME input the frame does not have. Ruling: the row's first line is purpose copy and the subject is secondary; opening Templates preselects the first template so the right pane is never an empty box; the editor's eyebrow IS the template name with Duplicate beside it, which makes the NAME input redundant (rename lives on the eyebrow); the footer is Save + Use in a send. The page measure landed in wave 1 and must not move.

## Amendment (wave 3): the Name column prints the name the organizer typed; the derived purpose is meta

app/src/pages/comms/TemplatesTab.tsx:222 renders `derivePurpose(t)` as the row's first line under a `<th>Name</th>` header, with `t.subject` beneath — so `email_template.name`, the one field the organizer types and the only handle they can search or say out loud, is never displayed anywhere in the list. The wave-4 amendment that promoted purpose copy was right that a bare filename-ish name is a weak first line; it was wrong to spend the NAME column on a keyword classifier's guess. A derived label is a reading aid; it is not the record. RULING: line one is `t.name` verbatim; the derived purpose and the subject are the muted second line. `derivePurpose` stays (it is genuinely useful meta) but never occupies a column whose header promises the stored value. The general shape: A COLUMN HEADER IS A PROMISE ABOUT WHICH FIELD IS UNDER IT.

## Amendment (wave 18): Templates rows carry no verbs — the editor panel owns every action, including Delete

The desktop frame (docs/design/Chautauqua Comms.dc.html:238-246) draws each saved-template row as `1fr auto`: name + detail left, usage caption right, NO actions; the verbs live in the editor panel (:249-272 — Duplicate in the section head, Save primary, "Use in a send" secondary). The build puts four controls in every row (TemplatesTab.tsx:232-247), and the fleet measured the consequence: Delete is unreachable because the editor panel overlaps the cluster. This is the same disease DESIGN-RULINGS item 12 rules against (twelve controls in a row whose job is labelling), and the fix is subtractive. RULE: the row's one control is its name, which selects the template into the editor; Delete moves into the editor's action row as a tertiary link in muted ink (never a bordered button — DESIGN-RULINGS items 3 and 20), shown only for a saved template, still gated by the existing confirm dialog.
