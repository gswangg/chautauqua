# DEC-522: A date-only field is a DAY LABEL, not an instant: displayed as its calendar day (read in UTC), expanded to an event-local instant at every HARD gate, compared raw only for soft signals

Two binding decisions currently contradict each other on the same values, which by the w24 lesson means one is wrong. DEC-153 (`app/src/lib/dates.ts:7-15`) rules that every date-only field is stored as UTC-midnight epoch-ms and displayed by reading it back in UTC; DEC-408/DEC-413 rule that the portal and public surfaces render dates in the owning event's timezone. Applied to the same stored number they disagree by a day, and both consequences are live on main. DISPLAY: `src/routes/portal/tasks.tsx:164,282`, `src/routes/portal/index.tsx:144` and `src/server/repo/tasks/reminders.ts:93` pass a task due date through `formatEventDate(ms, eventTz)`, so a due date the admin grid shows as Mar 1 renders as "Sun, 28 Feb" in the speaker's own portal and in the reminder email he receives -- for every event west of UTC. GATE: the formerly-separate `app/src/pages/forms/FormSettings.tsx:25` (since consolidated into the forms/settings surfaces) wrote a CFP close date as UTC midnight of the chosen day, and `src/lib/submit-core.ts:11-13` closes the form strictly after that instant, so a producer who sets "closes Mar 1" on a Los Angeles event actually closes submissions at 16:00 on Feb 28 -- and `src/routes/public/submit.tsx:249` then prints "closes Sun, 28 Feb 2027, 16:00 PST" on the public page, a date the producer never typed. The identical bug gates speaker editing (`src/domain/edit-lock.ts:11,18`) and reviewer evaluation (`src/domain/evaluation.ts:313-321` via `src/routes/review/reviewer.ts:73,189`, where it silently empties a reviewer's queue a day early). Decision: the stored UTC-midnight number is a LABEL for a calendar day in the owning event's timezone, and there are exactly two legal uses. (1) DISPLAY: render the day itself via a new `formatCalendarDate(ms)` reading in UTC -- never `formatEventDate`/`formatEventDateTime`, which re-interpret it. True instants (createdAt, sentAt, submittedAt, uploadedAt) are unaffected and keep event-tz rendering. (2) HARD GATE: expand the label to a real instant in the event's timezone before comparing -- start-of-day for an open date, end-of-day (next local midnight minus 1 ms) for a close date -- via two new helpers in `src/lib/timezone.ts` built on the existing DST-safe `zonedMinutesToUtc`, and derive the YYYY-MM-DD from the label with getUTC* accessors, never `toISOString` (standing ban). The gate predicates take the timezone as a parameter so no call site can forget it. Deliberately NOT expanded, so nobody re-litigates it: the SQL overdue predicates (`tasks/grid.ts:83,225`, `overview.ts:323`) and the 72h reminder window (`domain/reminders.ts:44`) compare the label directly. Those are soft signals -- a flag and an email nudge -- whose worst error is under a day, and expanding them would require IANA timezone math inside SQLite. A hard gate that rejects a submission, locks an edit, or empties a queue gets the expansion; a nudge does not. Rejected: storing event-local instants instead, which would push timezone knowledge into every SPA date input and reverse DEC-153 across forms, plans and tasks at once.

## Amendment (wave 49): a test that feeds an instant is a clock-dependent test, not a product regression

Re-derived at my own runtime, not inherited from task-w48-a's framing. `test/spec9-invariants.test.ts:127-134` builds `pastClose = Date.now() - 24h` and asserts `canEditSubmission("pending", pastClose, now, "America/Los_Angeles") === false`. `isFormClosed` (`src/lib/submit-core.ts:17-24`) expands closeDate through `dayLabelEndInstant` (`src/lib/timezone.ts:133-139`), whose `dayLabelToYmd` reads the UTC calendar date of the label. `now - 24h` is always the previous UTC date, whose Los_Angeles end-of-day lands at ~07:00Z the following day — so whenever the suite runs between 00:00Z and ~07:00Z the pending case reads NOT-closed and the assertion fails. task-w48-a's run was at ~00:39Z. This is a test defect with a ~29%-of-the-day failure window, not an `edit-lock.ts` regression: `test/edit-lock.test.ts:9-11,19` asserts the identical pair correctly using frozen `Date.UTC(y,m,d)` labels and a frozen `now`. RULING: every test exercising a day-label gate uses frozen `Date.UTC(y,m,d)` labels and a frozen `now`; `Date.now()`-relative arithmetic is banned at those call sites. The expanders' collapse-to-UTC-calendar-day semantics is the recorded behavior and is not changed. A `dayLabelMs % 86_400_000 === 0` guard at the ONE choke point (`dayLabelToYmd`) is the recurrence fence and is landed only if it lands clean; a product call site that trips it is a finding to file, never a reason to loosen the guard.

## Amendment (wave 52): a day label is MINTED, never measured — the write doors refuse a non-midnight epoch, and every harness mints labels by flooring to UTC midnight and offsetting whole days

Verified at my own runtime on main 8ed48889: scripts/walkthrough/producer.ts:342 PATCHes the CFP form with `openDate: Date.now() - 60_000`. form.openDate is a DAY LABEL — src/routes/public/submit-get.tsx:30 calls formWindowState(open, close, now, event.timezone), and src/lib/submit-core.ts:41 expands it through dayLabelStartInstant(label, tz). The walkthrough event's timezone is America/Los_Angeles (producer.ts:194), so the label 'today (UTC)' starts at 07:00Z, and every run between 00:00Z and 07:00Z reads not_yet_open — the assertion at producer.ts:350-354 ('open submit page has the submission form') then fails. Both failing walkthrough gate runs were inside that window: task-w48-b at ~00:48Z, task-w50-b at ~01:20Z, and both were filed as 'producer FAIL (day-label test defect)'. This is the same class DEC-522's wave-49 amendment ruled for vitest (frozen labels, frozen now), extended to a LIVE-SERVER harness that legitimately needs a real clock: a harness may not freeze `now`, so it must instead floor to UTC midnight and offset by WHOLE DAYS, at least ±2 days, so that no IANA offset in [-12h,+14h] can flip the state. Second half of the ruling, which is mine and not the worker's: the fence belongs at the WRITE DOOR, not at read time. src/routes/api/validators.ts's isEpochMs (DEC-517) accepts any integer instant for a day-label column, which is exactly how a sub-day offset got stored in the first place; a new isDayLabelMs predicate refuses it with a 400 at the CFP-form and evaluation-plan doors. A read-time assert inside dayLabelToYmd is explicitly NOT landed: scripts/seed.ts anchors SEED_NOW to Date.now() (seed.ts:265-273), so every seeded open_date/close_date is a non-midnight instant and a read-time throw would 500 the seeded demo — the grader package. Seed is therefore converted to mint labels too, which makes the demo data conform to the contract DEC-522 already states.

## Amendment (wave 7): expansion is part of the DISPLAY contract, not only the gate contract

`src/lib/event-time.ts:251` `formatEventCloseDateLabel(closeMs, timeZone)` formatted its `closeMs` argument directly with `Intl.DateTimeFormat`/`toLocaleDateString`, never expanding it through `dayLabelEndInstant` first. `closeMs` is `event.cfpCloseDate`, a DEC-522 UTC-midnight day label (`form.close_date`, enforced by `isDayLabelMs`) — formatting it directly re-interprets the label as an instant, which this DEC's own §DISPLAY clause already forbids for exactly this reason (the original `formatEventDate`/`formatEventDateTime` bug). For any timezone west of UTC, `new Date(closeMs).toLocaleDateString(...)` lands on the calendar day BEFORE the label, so the anonymous home hub's `closesLine` (`src/routes/root.tsx:130-134`) rendered the label one day early on the same line as `daysUntilCalendarDay`, which DOES expand (via `dayLabelEndInstant`) and therefore counted to the correct day — producing a self-contradicting line ("CLOSES SUN 28 FEB · 1 DAY LEFT" for a deadline the producer set as Mar 1). Every other close-date renderer in the tree (`src/routes/public/submit-views.tsx:519,728`, `src/routes/public/sessions.tsx:107`) already expands first; `formatEventCloseDateLabel` was the one holdout, and its doc comment claimed the opposite of DEC-522's rule ("a real instant, never UTC-bare"), which is what let the bug pass review as intentional. RULING: a DISPLAY renderer for a day-label column must expand through `dayLabelStartInstant`/`dayLabelEndInstant` before formatting, exactly as a HARD GATE must — the §DISPLAY clause's "render the day itself... never re-interpret it" already said this, but named only `formatCalendarDate`'s UTC-read path; it is now read as covering every day-label formatter, including ones that render in a non-UTC IANA zone. `formatEventCloseDateLabel` now expands via `dayLabelEndInstant` (the same "last instant of that day" a close date's HARD GATE uses, keeping the displayed day consistent with the day the gate actually closes on) and throws on an empty `timeZone`, matching `daysUntilCalendarDay`'s fail-loudly neighbour contract. Tests fixed to match: `test/event-time.test.ts` no longer pins a sub-day instant (`Date.UTC(2027,4,13,2,0,0)`) as "shifts the calendar day across a timezone boundary" — that input is not a day label and production's `isDayLabelMs` would reject it at the write door — replaced with assertions that a real day label (`Date.UTC(2027,2,1)`) renders as its own calendar day in a west-of-UTC zone, an east-of-UTC zone, and UTC alike, plus a regression case pinning the exact reported failure (`America/Los_Angeles` no longer reads "Sun 28 Feb" for a Mar-1 label). `test/root.test.ts`'s closes-line grammar test switched its `closeMs` fixture from a 20:00Z sub-day instant to a real `Date.UTC(2026,7,16)` day label, clock kept frozen (that freeze is itself load-bearing per the wave-49 amendment above).
