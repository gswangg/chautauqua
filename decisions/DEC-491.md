# DEC-491: The CSV import's per-row write cost is measured, and the row cap is stated in terms of it

src/server/repo/contacts/import.ts:29-31 declares that "applyImportRows below issues one D1 statement per row (see the createContact/patchContact calls in the loop)" and derives the 2000-row cap from that claim. At this sha the create branch issues 2 statements (insert + createContact's trailing findContactById, src/server/repo/contacts/crud.ts:74-91) and the update branch up to 4 (contact UPDATE + up to two backfillNullAttribution UPDATEs at src/server/repo/attribution.ts:37,44 + patchContact's trailing findContactById), so the declared 2000-row cap actually authorizes a burst of up to ~8000 statements. DEC-481: a comment inside src/ is narration too, and DEC-485 makes the import cap the write-burst bound -- a bound stated in the wrong unit is not a bound. Decision: the import loop stops calling the two verification re-reads it never uses (it needs only the contact id, which it already mints), IMPORT_MAX_STATEMENTS_PER_ROW is declared next to MAX_IMPORT_ROWS with the statements enumerated branch by branch, MAX_IMPORT_WRITE_STATEMENTS = MAX_IMPORT_ROWS * IMPORT_MAX_STATEMENTS_PER_ROW is written down where the cap is declared, and a statement-counting Db double asserts the worst-case row shape hits exactly that number. MAX_IMPORT_ROWS stays 2000: J11 imports a whole speaker network, and the honest fix is to state the burst, not to shrink the product.
