# DEC-894: Every headshot path runs the same gate; WEBP is not exempt, and the organizer's path thumbnails too

src/lib/image-dims.ts:108-116 sniffs PNG and JPEG only, and both call sites (src/routes/portal/profile.tsx:352, src/routes/api/contacts/crud.ts:331) therefore skip the dimension gate entirely for image/webp -- which both accept lists allow -- so an arbitrarily large WEBP is stored at full size behind a size cap alone. And DEC-059's 'thumbnailed at upload' is a client-side canvas downscale that exists in exactly one place, the portal's inline script (profile.tsx:55-109); the organizer's Contacts drawer posts the original bytes untouched. SPEC section 7 says headshots are thumbnailed at upload -- a property of the artefact, not of one route. Rule: readImageDims learns the WEBP RIFF container (VP8 / VP8L / VP8X) and stays the ONE dimension reader; the gate runs for every accepted content type on both upload paths; and the Contacts drawer performs the same 512px longest-edge downscale before it POSTs, so the sentence is true of every door a headshot can come through. Serving is already immutable for the public case (profile.tsx:417-432) and is not touched. The drawer additionally prints the stored file's filename and upload date beside the image: an uploaded file with no metadata reads as decoration, not as a record.

## Amendment (wave 53): the shared .chq-file control is bounded by its container, never by the UA's intrinsic width

app/src/styles.css:1416 gives `.chq-file` a font, colour, `min-height` and `display:inline-flex` but no width bound at all, so an `input[type=file]` falls back to the user agent's intrinsic width. Inside the contacts drawer's value column that measures wider than the viewport (right edge 1477 against 1440; 38px of internal drawer overflow) — the last surviving gate-2 BROKEN. A control that four different panels reuse (ContactDrawer, ImportWizard, SessionboardImportPanel, ResourcesPanel, UploadZone) must fit whatever column it is dropped into: `max-width: 100%` plus `box-sizing: border-box` on the control and its `::file-selector-button`. The earlier hard-coded `width: 284px` is already gone; removing a bad width without adding a bound left the control unguarded, which is why the finding survived three gates.
