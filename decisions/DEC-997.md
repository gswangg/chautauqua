# DEC-997: DEC-417's caps are a property of the COLUMN, not of the admin API: every public and portal HTML-form field passes the same four named caps

DEC-417 introduced four named caps (NAME 200, TEXT 2000, LONG_TEXT 20000, RICH_TEXT 100000) in src/forms/validate.ts and enumerated "every admin JSON mutation route" in one commit — but the HTML-form surfaces were never in that enumeration, and the gap shows: src/routes/portal/profile.tsx:315-323 bounds firstName/lastName/title/company/links/bio, while addCoPresenter (src/server/repo/portal-edit.ts:442-450) trims first/last and writes them straight into participant.name_at_time and a new contact row with no cap at all. The unbounded value reaches D1, fails with `string or blob too big`, and surfaces as a generic 500 from an unauthenticated-adjacent surface — the exact DoS-and-fail-quietly pair DEC-417 exists to prevent. An enumeration that names one of two families is a promise half kept, so the caps are restated as a property of the column: every non-admin mutation path that writes a free-text column applies the same named cap the admin API applies to that column, the failure is a 400 naming the field, and the guard is a test that exercises each such route with an oversized value rather than a spot check on the one that was noticed.
