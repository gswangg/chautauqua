# DEC-694: A scope parameter goes on the send AND its preview, identically; a response viewer has one action over values that round-trip

The v4 design README's normative "Speakers grid — interaction rules" requires per-person "Remind ‹name›" links, which requires optional `contactIds` on BOTH POST /api/v1/events/:eventId/onboarding/remind (src/routes/tasks.ts:444) and its /remind/preview sibling (:464). Verified: neither accepts it today — both parse only `taskIds` via parseBoundedIdArray. A preview whose scope differs from the send it previews is a lie by construction (DEC-441 built the preview precisely so the organizer can see what will go out), so the parameter is added to both with identical parsing, identical scoping and the same {sent, skipped, remaining} shape, keeping the dedupe window and cap. Second, app/src/pages/speakers/ResponseModal.tsx:35-49 still offers the two-action DEC-599 flow ("Mark complete" / "Ask for more"); v4 specifies exactly ONE action, "Reopen this task", because an organizer reading a completed response has exactly one thing to decide. Third, the response viewer maps `answerToString(answers[f.id])` (src/server/repo/tasks/response-detail.ts:69-72) over the form's field defs, and the field-guide's own lockedFieldName precedent shows field ids arrive in two shapes in this codebase — so the round trip must be proved by a test that saves through the portal path and reads back non-empty values, not asserted by inspection.

## Amendment (wave 53): a remind control that names or counts its recipients must pass contactIds

DEC-694 added the optional `contactIds` scope to POST /events/:id/onboarding/remind and its preview so a per-person chase addresses exactly that person; OnboardingGrid.tsx:490/518 and SpeakerDetailPage.tsx:162/187 both use it. Overview.tsx:336 does not: the row that prints one speaker's name sends {taskIds:[row.taskId]} alone, which mails EVERY contact who still owes that task, and the section action "Remind all three" counts displayed ROWS while sending by task id. OverdueTaskRow already carries `contactId` (app/src/pages/overview/types.ts:16) — a field parsed into the type and never read at the call site. Ruling: any remind affordance whose label names a person or states a number must pass the contactIds it named; bare taskIds is reserved for the whole-event case, and a section label counts the DISTINCT contacts it will actually mail.
