# DEC-551: Every route that streams stored user content sets X-Content-Type-Options: nosniff

SPEC §6 promises "no user-content served with HTML content types", and src/domain/files.ts keeps that promise on the write side: validateUpload FORCES a served content type from an extension allowlist that contains no HTML type and no SVG. The read side then leaves the promise unenforced in the browser — src/routes/files.ts:409 and :299 and src/routes/portal/profile.tsx:433 all set Content-Type (and, for non-images, an attachment disposition) but never X-Content-Type-Options, so nothing tells a sniffing client to honor the declared type. The headshot route is the sharpest case: it is unauthenticated (it feeds the public speaker gallery) and serves inline, from the app's own origin, bytes a speaker chose. nosniff is the one header that makes the forced content type binding rather than advisory. Decision: every route that returns bytes read from R2 — the file download, the bulk ZIP archive, and the headshot serve — sets `X-Content-Type-Options: nosniff` alongside its Content-Type, and a test enumerates src/routes/** for handlers that stream a FileStore/R2 body and asserts each one carries the header, so the fourth such route cannot land without it. Deliberately NOT in scope, so it is not re-raised: a Content-Security-Policy on these responses (they are never HTML documents) and any change to the allowlist or the image/attachment disposition split, both of which are correct as they stand.
