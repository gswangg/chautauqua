# DEC-844: Narrowing an event's window never blocks — but it names every session it unschedules, at the moment of the write

VERIFIED: PATCH /api/v1/events/:eventId (src/routes/api/events.ts:299ff) validates ISO format and start<=end and nothing else; src/server/repo/agenda.ts:379 and src/server/repo/public/gates.ts:65 then reclassify any schedule_slot outside the new window as unscheduled, so it silently vanishes from the public agenda, agenda.ics and schedule.ics while the row still sits in D1. The slot-WRITE path already honours SPEC §2.3's warn-never-block rule (agenda.ts:75); the event-window path does not warn at all. Decision: the PATCH still applies (never blocks — the organiser may be fixing a typo'd year), and its response carries the consequence: {..event, unscheduledByWindow: {count, sessions: [{submissionId, ref, title, day}] capped at 20}} computed by one new repo helper beside the existing window logic in src/server/repo/agenda.ts. The Settings event form renders that as a persistent, non-dismissable notice naming the count and the refs with a link to the agenda. Same family as DEC-802/DEC-829: a write that un-publishes somebody says so where the choice is made, rather than leaving the organiser to discover it on their own public site.

## Amendment (wave 54): the outside-window slot query is bounded in SQL, and its predicate has one truth in two encodings

listSlotsOutsideWindow (src/server/repo/agenda.ts:460-472) SELECTs every accepted session's schedule_slot row for the event with no LIMIT, then filters in JS and `.slice(0, limit)`s — on every PATCH /api/v1/events/:eventId (src/routes/api/events.ts). That is the exact unbounded-scan/JS-slice shape DEC-418/DEC-461 ban, against SPEC section 7's writes-p95 < 100ms at the 2,000-submission target. isDayWithinEventRange (agenda.ts:63) is a pure lexical comparison on zero-padded ISO days, so it IS expressible in SQL. Rule: a SQL condition twin lives immediately beside the JS predicate; the count comes from one COUNT query and the named rows from one LIMITed query; and a test walks a day/start/end matrix asserting the two encodings agree on every cell, so the pair can never drift the way a hand-copied WHERE clause would.

## Amendment (wave 54): fixed — SQL twin exported, listSlotsOutsideWindow rewritten to COUNT+LIMIT

`dayOutsideEventRangeCondition(startDate, endDate)` now lives immediately beside `isDayWithinEventRange` in src/server/repo/agenda.ts, returning `or(lt(scheduleSlot.day, startDate), gt(scheduleSlot.day, endDate))` — the SQL encoding of that predicate's negation. `listSlotsOutsideWindow` composes it into the shared WHERE (eventId + status='accepted' + the new condition) for two queries: one `count(*)` and one row query ordered by `submissionId asc` with `.limit(limit)`; the JS `.filter(...)` and `.slice(0, limit)` are gone. Response shape and ordering are unchanged. Verified by test/agenda-day-outside-window.test.ts (a day/start/end matrix, including exact boundaries and non-zero-padded adjacent-sorting strings, structurally evaluating the drizzle condition tree and asserting agreement with `!isDayWithinEventRange`) and a repo-level assembly test added to test/agenda-repo.test.ts (3 slots, 1 outside → count 1 with that named row, and the row query's `.limit()` call is captured and asserted). test/events-api.test.ts's DEC-844 route tests were updated to feed the fake db pre-filtered "outside" rows for the COUNT and LIMIT queries (previously it fed all rows and relied on the deleted JS filter).
