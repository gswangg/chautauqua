# DEC-844: Narrowing an event's window never blocks — but it names every session it unschedules, at the moment of the write

VERIFIED: PATCH /api/v1/events/:eventId (src/routes/api/events.ts:299ff) validates ISO format and start<=end and nothing else; the former src/server/repo/agenda.ts:379 (now split across src/server/repo/agenda/) and src/server/repo/public/gates.ts:65 then reclassify any schedule_slot outside the new window as unscheduled, so it silently vanishes from the public agenda, agenda.ics and schedule.ics while the row still sits in D1. The slot-WRITE path already honours SPEC §2.3's warn-never-block rule (agenda.ts:75); the event-window path does not warn at all. Decision: the PATCH still applies (never blocks — the organiser may be fixing a typo'd year), and its response carries the consequence: {..event, unscheduledByWindow: {count, sessions: [{submissionId, ref, title, day}] capped at 20}} computed by one new repo helper beside the existing window logic in the former src/server/repo/agenda.ts (now split across src/server/repo/agenda/). The Settings event form renders that as a persistent, non-dismissable notice naming the count and the refs with a link to the agenda. Same family as DEC-802/DEC-829: a write that un-publishes somebody says so where the choice is made, rather than leaving the organiser to discover it on their own public site.

## Amendment (wave 54): the outside-window slot query is bounded in SQL, and its predicate has one truth in two encodings

listSlotsOutsideWindow (the former src/server/repo/agenda.ts:460-472 (now split across src/server/repo/agenda/)) SELECTs every accepted session's schedule_slot row for the event with no LIMIT, then filters in JS and `.slice(0, limit)`s — on every PATCH /api/v1/events/:eventId (src/routes/api/events.ts). That is the exact unbounded-scan/JS-slice shape DEC-418/DEC-461 ban, against SPEC section 7's writes-p95 < 100ms at the 2,000-submission target. isDayWithinEventRange (agenda.ts:63) is a pure lexical comparison on zero-padded ISO days, so it IS expressible in SQL. Rule: a SQL condition twin lives immediately beside the JS predicate; the count comes from one COUNT query and the named rows from one LIMITed query; and a test walks a day/start/end matrix asserting the two encodings agree on every cell, so the pair can never drift the way a hand-copied WHERE clause would.

## Amendment (wave 54): fixed — SQL twin exported, listSlotsOutsideWindow rewritten to COUNT+LIMIT

`dayOutsideEventRangeCondition(startDate, endDate)` now lives immediately beside `isDayWithinEventRange` in the former src/server/repo/agenda.ts (now split across src/server/repo/agenda/), returning `or(lt(scheduleSlot.day, startDate), gt(scheduleSlot.day, endDate))` — the SQL encoding of that predicate's negation. `listSlotsOutsideWindow` composes it into the shared WHERE (eventId + status='accepted' + the new condition) for two queries: one `count(*)` and one row query ordered by `submissionId asc` with `.limit(limit)`; the JS `.filter(...)` and `.slice(0, limit)` are gone. Response shape and ordering are unchanged. Verified by test/agenda-day-outside-window.test.ts (a day/start/end matrix, including exact boundaries and non-zero-padded adjacent-sorting strings, structurally evaluating the drizzle condition tree and asserting agreement with `!isDayWithinEventRange`) and a repo-level assembly test added to test/agenda-repo.test.ts (3 slots, 1 outside → count 1 with that named row, and the row query's `.limit()` call is captured and asserted). test/events-api.test.ts's DEC-844 route tests were updated to feed the fake db pre-filtered "outside" rows for the COUNT and LIMIT queries (previously it fed all rows and relied on the deleted JS filter).

## Amendment (wave 68): the narrowed-window report names every day-scoped thing it orphans, breaks included

DEC-844's premise, live at src/routes/api/events.ts:370-375, is that narrowing an event's date window never blocks the write but NAMES every placed session it unschedules (listSlotsOutsideWindow -> `unscheduledByWindow`, surfaced by app/src/pages/settings/EventSettingsPanel.tsx:82/131). Breaks (src/server/repo/breaks.ts, wave 63) are day-scoped placements of exactly the same kind and were never added to that report. Today: an organiser narrows the dates, getPublicBreaksByDay (src/server/repo/public/agenda.ts:317) silently drops every break outside the new [startDate,endDate], so lunch vanishes from the public agenda and the printable programme -- while GET /events/:id/breaks still lists it and the organiser is told nothing. Create-time validation (isDayWithinEventRange in src/routes/api/breaks.ts:105) cannot cover this: the range moves after the fact. So PATCH /events/:eventId returns `breaksOutsideWindow` beside `unscheduledByWindow`, computed after the update against the NEW window, count in SQL plus at most 20 named rows, and Settings names both in its one notice. The write still never blocks and never deletes: the rows survive, they just stop rendering, and the organiser learns that from the app rather than from a visitor. This decision also retires the false boundary in src/server/repo/breaks.ts's own header ("never wired into agenda conflict detection, auto-schedule, or export machinery") -- wave 66 wired breaks into autoSchedule/nextFreeSlot (DEC-010 amendment), the run-of-show export, and the overview's placement suggestions. A boundary comment that lies is worse than no comment, because the next worker trusts it.
