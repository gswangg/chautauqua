# DEC-336: Contact directory search/sort/paging happens in SQL; DEC-266's AND-tokens x OR-columns semantics move from the pure predicate into the WHERE, and matchesContactQuery is deleted

src/server/repo/contacts/crud.ts:148 selects EVERY contact row in the org (all columns, including notes and custom_fields_json) on every /api/v1/contacts request, then filters, sorts and slices in JS. J11's directory is explicitly cross-event ('multiple events per year sharing one speaker network'), so this grows without bound while the page stays 50 rows. DEC-266 chose a superset SQL prefilter plus an in-memory exact pass; the exact predicate — AND across tokens, OR across firstName/lastName/email/coalesce(company,'') — is directly expressible as and(...tokens.map(t => or(4 LIKE terms))) with an ESCAPE clause, so the superset is unnecessary. DEC-266's SEMANTICS are preserved verbatim (the 'Priya Raman' case it was created for must still match, and a query whose tokens split across two different contacts must still match neither); only its mechanism is superseded. Consequences: q + sort + page become one COUNT(*) plus one ORDER BY/LIMIT/OFFSET query (name -> lower(last_name), lower(first_name), id; recent -> updated_at desc, id); matchesContactQuery loses its only caller and is deleted with its tests (house rule); tokenizeContactQuery stays. The segmentId/rules path keeps today's in-memory evaluation because SegmentRule supports custom.* JSON fields, but it now rides the same exact SQL q predicate, and that residual whole-directory load is documented at the call site as the one known exception, to be revisited only if measured over budget.
