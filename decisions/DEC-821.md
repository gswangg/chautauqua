# DEC-821: Pipeline fit is two nullable columns, set when someone is enrolled and editable after, ranking only within a stage

VERIFIED src/server/repo/pipeline.ts:20-38 — pipeline_entry is {id, orgId, contactId, stage, createdAt, updatedAt} and enrollContact(db, orgId, contactId, stage, actor) takes nothing else; there is no fit_score anywhere in src/. docs/design/README.md:268-272 is explicit about why it matters: stage says how far along someone is, fit says how much you want them, and two people can sit in `contacted` for six weeks with opposite worth in chasing. Decision: migration 0026 adds `fit_score` (integer, nullable) and `rationale` (text, nullable) to pipeline_entry — the numbers 0025 (DEC-818) and 0026 are hereby reserved so two in-flight waves cannot mint the same migration index. Fit is OPTIONAL and its absence is a visible state, never an implied low score: an unrated card renders a dashed 'Unrated' rather than nothing, because absence read as a zero is the failure this feature exists to prevent. The score is validated server-side as an integer 1-5 or null (loud field error, never coerced), the rationale is a bounded one-liner, and fit orders cards WITHIN a stage column only — it never reorders or crosses stages, since stage is the fact the board is about. Enrolling still writes a move activity and still sends no email (DEC-157 untouched).

## Amendment (wave 40): a picker over an org-scale collection is a server-side search, never page 1 of the directory in a select

DEC-821 owns the pipeline enroll dialog. Its contact chooser (app/src/pages/contacts/PipelineBoard.tsx:504-508, 555-568) loads `/contacts?perPage=200` once and renders every returned row as an <option>. At SPEC's stated scale (200-800 speakers per event, "multiple events per year sharing one speaker network") the directory passes 200 quickly, and from then on the dialog can enroll only the alphabetically-first 200 contacts, silently: no search, no pager, no statement of the bound — the person you are sourcing is simply not in the list. The repo already owns the correct idiom for exactly this problem one page over: the add-co-presenter chooser searches server-side (`/contacts?q=`, app/src/pages/submissions/SubmissionDetailPage.tsx:591-607) instead of downloading a page of the directory. RULING: the enroll chooser becomes that same search — a query the server answers, results rendered from the envelope, already-enrolled contacts filtered out — and when the server's `total` exceeds the rows returned, the dialog says so in one line rather than presenting a page as the whole. No new predicate, no second contacts-search definition; the enroll POST body and the "no email is sent" footnote are untouched.
