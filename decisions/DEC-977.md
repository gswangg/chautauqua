# DEC-977: A contact's Labels export the way they render — the empty tags column is retired

src/server/repo/exports/contacts.ts:37 emits "" for its seventh column on every row, with a module comment declaring 'There is no tags concept anywhere in the contact data model … every cell is "" until a tags feature exists'. That reason expired: DEC-738/DEC-726 settled that a contact's Labels ARE its customFields and put the one formatter in src/domain/contact-labels.ts (contactLabels), which the directory column, the drawer row and the merge screen all read, and docs/design/README.md:247-256 makes the same call ('Labels are custom fields, not a tags column … one keyed format everywhere'), with the mock's own sample data reading 'role speaker · year 2027'. So the CRM's export — a J11/J12 deliverable and the only way a customer gets their data back out — is the one reader that drops a field the import can write (mapImportRow's custom.<key> targets), making the round trip lossy in one direction only. Rule: the export's seventh column is named `labels` (the product's vocabulary; DEC-597's `tags` naming went with the empty-column rationale and is not kept as a compatibility shim) and carries contactLabels(customFields).join(' · '); both branches of exportContacts supply customFields — the filtered branch from ContactRow.customFields, the unfiltered query by projecting and parsing custom_fields_json — and the module header stops asserting a gap that no longer exists.
