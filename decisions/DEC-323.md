# DEC-323: `/e/:slug/schedule.ics` with no `ids` publishes the whole agenda through the shared agendaIcsEvents mapper; the ids filter never runs against an empty selection

Confirmed on main at src/routes/public/index.tsx:197-214: line 197 correctly branches (`ids.length > 0 ? getPublicAgendaByIds(...) : getPublicAgenda(...)`), but line 200 then builds the VEVENT list with `ids.filter((id) => agendaById.has(id)).map(...)` — filtering the empty `ids` array. So the bare URL hydrates the entire agenda and throws it away, returning `200 OK` with a valid but EMPTY VCALENDAR (task-w13-b-c3-walkthrough.md OPEN ITEM 3: 12 accepted+approved+scheduled sessions, 0 VEVENTs). That is the worst of both worlds — full query cost, silent empty result, no error. Decide it publishes the whole agenda rather than an honest empty calendar, for three reasons: (a) the branch at :197 already pays for and clearly intends the whole-agenda payload; (b) an empty .ics from a URL a human typed or bookmarked is an invisible failure, the exact class the house fail-loudly rule forbids, whereas an empty 400 would be hostile to a legitimate 'give me everything' request; (c) /e/:slug/agenda.ics (EMB-15, DEC-289) already proves the whole-agenda payload is a supported public artifact, and src/routes/public/feeds.ts:53 agendaIcsEvents is byte-for-byte the same mapping schedule.ics duplicates inline, so both feeds emit identical UID/SEQUENCE per session and a calendar client that imported an itinerary UPDATES rather than duplicates. The inline mapping at :200-214 is therefore deleted in favour of agendaIcsEvents — the drift risk between two copies of one mapping is itself a latent defect. DEC-310's 'never hydrate the whole agenda' still governs the ids path, which keeps getPublicAgendaByIds. Content-Disposition filename is unchanged.
