# DEC-697: A response you did not create may have IMMUTABLE headers: every decorating middleware goes through one clone-on-failure helper, proved against a frozen-header response

Mandate item 28 is STILL LIVE on main: src/server/framing.ts:35-36 and src/server/middleware.ts:283 both call c.res.headers.set() after await next(), and workerd's ASSETS-served responses carry immutable headers, so every authenticated /admin asset load 500s with "Can't modify immutable headers". Logged-out requests redirect before reaching the middleware, which is why shallow checks pass — the same reason it shipped. test/framing-headers.test.ts enumerates paths but every one of them is served by an in-test c.text() handler whose headers are mutable, so the test can never see the bug: the enumeration is honest and the FIXTURE is wrong. The rule: no middleware mutates a response it did not construct; it calls one helper that attempts the mutation and, on failure, rebuilds `new Response(res.body, res)` and assigns that back. The proof is a test that stamps headers over a response whose Headers throw on set (DEC-687's lesson: prove by executing the real shape, not by reading the TS), and a source scan forbids `c.res.headers.set(` outside the helper so a fourth decorator can't reintroduce it.
