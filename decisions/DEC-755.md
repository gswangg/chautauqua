# DEC-755: Every control in a creation dialog reaches the store: New submission persists Track and Format, and a contact is matched by (org, lower(email))

Verified: NewSubmissionModal.tsx holds trackIds and format state, but submit() sends neither (line 68), CreateSubmissionBody (src/routes/api/submissions.ts:106) declares only title/description/contact, and createSubmission takes only those three. So both selectors are decoration — the CNT grader's "Session format dropped on create" is the visible half; the Track half silently reproduces exactly the failure DEC-598 fixed for PATCH (a track-less submission falls out of track-scoped reviewer assignment, the public track filter and the agenda). DEC-750 keeps Track and Format in the frame on the grounds that chrome fidelity never removes a capability; this decision makes the capability real rather than promised. Track validation is PATCH's rule verbatim (ids must belong to THIS event, unknown ids are a 400 with a fields entry, never a silent drop) and the write reuses PATCH's repo path so the track columns keep ONE writer (DEC-717). Format has no submission column — it is an answer on SESSION_FORMAT_FIELD_ID (src/forms/types.ts:61), which is how every read surface already hydrates it — so create writes a submission_answer against that imported id, never a literal, and PATCH accepts it too so a missing format is fixable afterwards. Separately, findOrCreateContact in submissions/create.ts:55 compares email with a case-SENSITIVE eq while the public CFP path compares lower()=lower(); that asymmetry mints the duplicate contact records the graders keep tripping over. Contact identity within an org is (orgId, lower(email)) on every find-or-create path.

## Amendment (wave 43): POST /api/v1/contacts is find-or-REFUSE, never mint-a-duplicate

DEC-755 fixed contact identity as (orgId, lower(email)) on every find-or-create path — public CFP submit, portal co-presenter, sessionboard import and submissions/create.ts:findOrCreateContact all honour it. src/routes/api/contacts/crud.ts:137 does not: it calls createContact unconditionally, so the manual Add-speaker/Add-contact path mints a second row for an address the org already holds. That single hole explains a chain of downstream 'defects' filed as separate findings: three Priya Raman rows, returning-speakers KPI stuck at 0, assign-to-all tasks landing on the no-account twin, and the agenda conflict engine missing a speaker double-booking (it keys on contactId, and one person under two ids can never clash with themself). A silent find-and-return would be a silent merge of two different people's names, so the rule is REFUSE: 409 conflict naming the existing contact, with the modal offering to open that record. Merging remains the explicit Duplicates-tab action.

## Amendment (wave 44): a duplicate PAIR is produced by the NAME rule, never by a duplicate email — the harness pins the 409 instead of contradicting it

DEC-755 made POST /api/v1/contacts find-or-REFUSE: a matching (orgId, lower(email)) is a 409 naming the existing contact (src/routes/api/contacts/crud.ts:151-163). scripts/walkthrough/data.ts:264-273 still mints a same-email contact and asserts 201, so J11 can never pass and the CI walkthrough job is red for a second, independent reason. The product still produces duplicate pairs — findDuplicateGroups (src/domain/contacts.ts:107-127) groups by normalized firstName+lastName, sub-grouped by company with a blank company acting as a wildcard (DEC-143), and surfaces the whole name bucket as reason 'name' when companies differ (DEC-800). Ruling: the harness builds its pair the way the product allows — same firstName/lastName as the history-bearing seeded contact, a FRESH unique email, company omitted — and additionally asserts that re-POSTing the seeded contact's exact email returns 409 with fields.email. The duplicate-merge coverage is preserved and the create-side contract becomes pinned rather than assumed.

## Amendment (findings wave 10): the default CFP ships a usable Format and Audience level select, both optional, and format is clearable

Once createDefaultForm mints the role-tagged fields (DEC-592 amendment) it must decide their content, and that is a design question, not a worker question. OPTIONS — session_format: ['Keynote (45 min)','Talk (30 min)','Lightning talk (10 min)','Workshop (90 min)','Panel (45 min)']; audience_level: ['Beginner','Intermediate','Advanced']. The '(N min)' suffix is LOAD-BEARING, not decoration: parseFormatDurationMin reads it (src/server/repo/agenda/rows.ts:201-246) and it is what makes auto-schedule produce true durations on a fresh event. These are product defaults chosen here, not fixture values copied from docs/fixtures/sample-data.json (which product code must never reference). REQUIRED: both false on the default form — a brand-new event must not impose a required question the organiser never wrote, and an optional field keeps every existing 'create a form, then create a submission' path valid without test churn. The seeded demo event may keep its own required setting; the seed is a configured event, not the default. CLEARABLE: because the field is optional, PATCH /api/v1/submissions/:id {format: null} must DELETE the answer rather than 400 'format must be a non-empty string' — a select the organiser can set but never unset is a one-way door. LOCKED: false for both (organisers may rename, reorder, or remove them).

## Amendment (findings wave 13): a RETIRED symbol may not survive in prose — a comment naming a deleted identifier is a false citation, and the mandate's own triage runs on citations

The wave-10/w10-b conversion deleted SESSION_FORMAT_FIELD_ID and AUDIENCE_LEVEL_FIELD_ID (src/forms/types.ts:19-20 says so explicitly) but left them standing in comments across at least src/routes/public/cards.tsx:57, src/routes/review/reviewer.ts:311, src/server/repo/overview/types.ts:122, app/src/pages/review/types.ts:216-221, migrations/0038_form_field_role.sql:4-9 and four test files — and left src/server/repo/form-roles.ts:1-6 asserting the exact opposite of current main ('Those literals still stand this wave -- no read site is converted here'). This is not cosmetic: this round a review lens re-derived a closed defect ('format only ever works on the seeded demo event') straight from those comments, and the standing triage rule is that a file:line citation proves intent. A comment that cites a symbol nobody can resolve is a citation that cannot be checked. RULING: every reference to a retired symbol is rewritten in the surviving vocabulary (role, answerFieldRoleCondition, getEventFieldIdByRole, getFieldOptionsByRole), and the retirement is enforced by an executable scan with an explicit BANNED list — a fixed, named set of retired identifiers that may not appear anywhere under src/, app/src/, test/, migrations/ or scripts/, in code or prose. A banned-list scan, not a heuristic: the guard must be exactly as narrow as the claim it protects.

## Amendment (wave 6, sha d4584747): a dead binding is a false citation the compiler can catch — noUnusedLocals is on in both projects

DEC-755 already carries the findings-wave-13 ruling that "a RETIRED symbol may not survive in prose — a comment naming a deleted identifier is a false citation". A dead IMPORT is the same lie in code, and neither `tsconfig.json` nor `app/tsconfig.json` sets `noUnusedLocals`, so it compiles in silence. That is how `src/routes/agenda.ts:23`'s `roomBelongsToEvent` import survived after the route moved to `getRoomEventId` — and that dead import was the visible symptom of a duplicated cross-event ownership predicate (since given one owner at `src/server/repo/agenda/rows.ts:47`, cited from `src/routes/api/embeds.ts:31-34`). Ruling: `noUnusedLocals: true` is set in both `tsconfig.json` and `app/tsconfig.json`, and the dead import at `agenda.ts:23` is removed as part of landing it. `noUnusedParameters` is deliberately NOT included, because it forces `_`-prefix churn across handler signatures and is a separate question.
