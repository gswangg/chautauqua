# DEC-755: Every control in a creation dialog reaches the store: New submission persists Track and Format, and a contact is matched by (org, lower(email))

Verified: NewSubmissionModal.tsx holds trackIds and format state, but submit() sends neither (line 68), CreateSubmissionBody (src/routes/api/submissions.ts:106) declares only title/description/contact, and createSubmission takes only those three. So both selectors are decoration — the CNT grader's "Session format dropped on create" is the visible half; the Track half silently reproduces exactly the failure DEC-598 fixed for PATCH (a track-less submission falls out of track-scoped reviewer assignment, the public track filter and the agenda). DEC-750 keeps Track and Format in the frame on the grounds that chrome fidelity never removes a capability; this decision makes the capability real rather than promised. Track validation is PATCH's rule verbatim (ids must belong to THIS event, unknown ids are a 400 with a fields entry, never a silent drop) and the write reuses PATCH's repo path so the track columns keep ONE writer (DEC-717). Format has no submission column — it is an answer on SESSION_FORMAT_FIELD_ID (src/forms/types.ts:61), which is how every read surface already hydrates it — so create writes a submission_answer against that imported id, never a literal, and PATCH accepts it too so a missing format is fixable afterwards. Separately, findOrCreateContact in submissions/create.ts:55 compares email with a case-SENSITIVE eq while the public CFP path compares lower()=lower(); that asymmetry mints the duplicate contact records the graders keep tripping over. Contact identity within an org is (orgId, lower(email)) on every find-or-create path.
