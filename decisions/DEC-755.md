# DEC-755: Every control in a creation dialog reaches the store: New submission persists Track and Format, and a contact is matched by (org, lower(email))

Verified: NewSubmissionModal.tsx holds trackIds and format state, but submit() sends neither (line 68), CreateSubmissionBody (src/routes/api/submissions.ts:106) declares only title/description/contact, and createSubmission takes only those three. So both selectors are decoration — the CNT grader's "Session format dropped on create" is the visible half; the Track half silently reproduces exactly the failure DEC-598 fixed for PATCH (a track-less submission falls out of track-scoped reviewer assignment, the public track filter and the agenda). DEC-750 keeps Track and Format in the frame on the grounds that chrome fidelity never removes a capability; this decision makes the capability real rather than promised. Track validation is PATCH's rule verbatim (ids must belong to THIS event, unknown ids are a 400 with a fields entry, never a silent drop) and the write reuses PATCH's repo path so the track columns keep ONE writer (DEC-717). Format has no submission column — it is an answer on SESSION_FORMAT_FIELD_ID (src/forms/types.ts:61), which is how every read surface already hydrates it — so create writes a submission_answer against that imported id, never a literal, and PATCH accepts it too so a missing format is fixable afterwards. Separately, findOrCreateContact in submissions/create.ts:55 compares email with a case-SENSITIVE eq while the public CFP path compares lower()=lower(); that asymmetry mints the duplicate contact records the graders keep tripping over. Contact identity within an org is (orgId, lower(email)) on every find-or-create path.

## Amendment (wave 43): POST /api/v1/contacts is find-or-REFUSE, never mint-a-duplicate

DEC-755 fixed contact identity as (orgId, lower(email)) on every find-or-create path — public CFP submit, portal co-presenter, sessionboard import and submissions/create.ts:findOrCreateContact all honour it. src/routes/api/contacts/crud.ts:137 does not: it calls createContact unconditionally, so the manual Add-speaker/Add-contact path mints a second row for an address the org already holds. That single hole explains a chain of downstream 'defects' filed as separate findings: three Priya Raman rows, returning-speakers KPI stuck at 0, assign-to-all tasks landing on the no-account twin, and the agenda conflict engine missing a speaker double-booking (it keys on contactId, and one person under two ids can never clash with themself). A silent find-and-return would be a silent merge of two different people's names, so the rule is REFUSE: 409 conflict naming the existing contact, with the modal offering to open that record. Merging remains the explicit Duplicates-tab action.

## Amendment (wave 44): a duplicate PAIR is produced by the NAME rule, never by a duplicate email — the harness pins the 409 instead of contradicting it

DEC-755 made POST /api/v1/contacts find-or-REFUSE: a matching (orgId, lower(email)) is a 409 naming the existing contact (src/routes/api/contacts/crud.ts:151-163). scripts/walkthrough/data.ts:264-273 still mints a same-email contact and asserts 201, so J11 can never pass and the CI walkthrough job is red for a second, independent reason. The product still produces duplicate pairs — findDuplicateGroups (src/domain/contacts.ts:107-127) groups by normalized firstName+lastName, sub-grouped by company with a blank company acting as a wildcard (DEC-143), and surfaces the whole name bucket as reason 'name' when companies differ (DEC-800). Ruling: the harness builds its pair the way the product allows — same firstName/lastName as the history-bearing seeded contact, a FRESH unique email, company omitted — and additionally asserts that re-POSTing the seeded contact's exact email returns 409 with fields.email. The duplicate-merge coverage is preserved and the create-side contract becomes pinned rather than assumed.
