# DEC-292: Contact custom fields are edited as key/value rows with a reserved `travel_logistics` key surfaced as a labeled 'Travel & logistics' textarea; duplicate keys are a loud validation error, never a silent overwrite

app/src/pages/contacts/ContactDrawer.tsx:157-165 exposes custom fields as a raw JSON textarea whose contents go through JSON.parse on save. The buyers are 'not technical at all; they are event production professionals' (docs/clarifications.md) and SPEC §2.1 is 'legible over configurable' — a JSON blob is the wrong affordance for that user, and it is also why SPK-15's scenario text ('enter "Arrival May 11, aisle seat; dietary: Vegetarian" and save') fails today: typed as prose it is invalid JSON and the save errors. Decision: customFields stays exactly the same wire type (Record<string,string>, PATCH /contacts/:id unchanged, no schema change), but the editor becomes (a) one labeled 'Travel & logistics' textarea bound to the RESERVED key `travel_logistics`, rendered first, and (b) a key/value row editor for every other key with Add field / Remove row. Serialization rules, fixed here so the pure module and the drawer agree: keys are trimmed; a row with a blank key AND blank value is dropped; a blank key with a non-blank value is a validation error (never silently discarded data); two rows with the same trimmed key is a validation error that disables save (never last-wins, because last-wins silently destroys the other value); `travel_logistics` is omitted from the row list and rejected as a hand-typed key with a message pointing at the labeled field. The parse/serialize pair lives in a pure module with its own unit tests so the rules are testable without a DOM.
