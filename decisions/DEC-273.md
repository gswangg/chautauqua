# DEC-273: 'unreviewed -> approve/maybe/deny' is a reviewer RECOMMENDATION expressed as a scorecard criterion, never a sixth submission-status literal; the seeded demo says the customer's words

docs/clarifications.md (highest precedence) names 'unreviewed -> approve/maybe/deny' as the minimum review workflow. The shipped pipeline is pending -> accept_queue|decline_queue -> accepted|declined (src/domain/status.ts:5-18), which covers unreviewed/approve/deny but has no home for 'maybe'. Adding a status literal at the end of the campaign would touch the triage board, bulk-status routes, filters, exports, overview counts and the public visibility rules -- the highest-regression change available for the smallest semantic gain, exactly what DEC-260 exists to prevent. The correct reading is that approve/maybe/deny is the REVIEWER's opinion axis, and the product already has a first-class, configurable home for it: dropdown criteria on the evaluation plan, which DEC-241 renders as per-option distribution + modal columns in results and exports to CSV. What is actually missing is that the demo data never says those words: scripts/seed.ts:809 seeds the third criterion as 'Session length fit' with Too short/Just right/Too long. Stage 1 therefore reseeds that one criterion as 'Recommendation' with options Approve/Maybe/Deny -- no schema change, no new code path, three lines of seed data -- so the non-technical event producers who evaluate this see their own vocabulary in the reviewer scorecard and in the aggregated results. This is a narrow, seed-only amendment to DEC-261's freeze on product commits, justified because clarifications.md outranks everything and the change carries no runtime code risk (scripts/walkthrough/review.ts creates its own plan and is untouched).
