# DEC-663: A CSV import is PLANNED before it is applied: one dry run names, per row, what it will do, which stored non-blank fields it will replace, and which existing contact it may duplicate under a different address -- and the organizer's per-line skips bind the real run

Two confirmed data paths converge here. (1) src/server/repo/contacts/import.ts dedupes strictly by normalized email, so re-importing the same person under a second address silently creates a duplicate while the summary reads "Created 1, updated 2, skipped 0" -- the org already owns a name+company duplicate rule (findDuplicateGroups, src/domain/contacts.ts:76, DEC-143) that the import path simply never consults. (2) resolveImportUpsert (src/server/repo/contacts/query.ts:109-114) writes any non-blank incoming bio/title/company straight over a curated stored value with no warning (mandate Tier 0 #5's third data-loss path). Both are the same defect: the organizer is asked to commit before being shown the consequence. The contract is fixed here so the server and the wizard can be built in parallel: POST /api/v1/contacts/import accepts `dryRun?: boolean` and `skipLines?: number[]`; with dryRun:true it performs NO writes and returns { rows: Array<{ line, email, action: 'create'|'update'|'skip', reason?, contactId?, overwrites?: Array<{ field, from, to }>, possibleDuplicates?: Array<{ contactId, name, email, company }> }>, created, updated, skipped } where those three counts are INTENT; on a real run the counts stay what they are today -- counted AFTER commit -- and every line in skipLines appears in `skipped` with an explicit reason. A field is an `overwrite` only when the incoming value is non-blank, the stored value is non-blank, and they differ after trim (a blank cell remains ABSENT DATA, unchanged). Duplicate candidates use the SAME normalization findDuplicateGroups uses and are restricted to contacts whose normalized email differs from the row's; they are fetched in the same chunked pre-pass style applyImportRows already uses for emails, never a whole-org scan.


## Amendment (wave 40)

**An import that recognises a header must map it, and a disabled primary must name its blocker**

Verified on main: app/src/pages/contacts/csv.ts:261 lists company synonyms as company/organization/organisation/employer — `org`, the header the frame maps and the fixtures use, is absent, so it auto-maps to (ignore) and both preview rows print Company '—' with no warning. That is DEC-663's own promise broken at the step it exists for: a dry run that names what it will do must not silently drop a column it could have recognised. Second half, same screen: ImportWizard.tsx:190 disables 'Preview N rows' solely because the batch's session-title field is empty, with no required marker on that field and no inline reason at the button — an opaque dead end. RULING: `org` (with `orgname`/`companyname`) joins the company synonyms, and a disabled primary in this product always renders the reason it is disabled next to itself, naming the field that blocks it. Silent recognition failure and silent blocking are the same defect wearing different clothes.

## Amendment (wave 61): the import dry run must model its own within-file email collapse

applyImportRows seeds `byEmail` from the DB and then writes each newly minted id back into it (import.ts:309), so the second file row carrying an email that first appeared earlier in the SAME file resolves to `update` against the row just created -- within-file duplicates collapse onto one contact. planImportRows (import.ts:417-421) builds `byEmail` from the DB only and never feeds its own planned creates back in, so both rows plan as `create`. A file with the same address twice therefore promises "2 created" and delivers "1 created, 1 updated", and the second row shows no overwrite warning for values it will in fact write over the first. DEC-663's whole premise is that the plan is the organizer's contract with the run; a plan that models a different collapse rule than the run is the run lying in advance. RULING: the plan carries planned creates forward in its own lookup, exactly as the apply loop does. The collapsing row plans as `action:'update'` with NO contactId (none exists yet) and a fixed reason naming the cause; the review table renders that reason where it already renders per-row action detail. created/updated/skipped from the plan must equal what the same file produces on apply.

## Amendment (wave 27): the import review step leads with two counts and states its irreversibility

DEC-663 already delivers the per-row plan, the field-level overwrites and the binding per-line skips. Ruling B5 adds what the step must SAY: the heading is two counts ('205 new / 9 updated'), because the dedupe outcome is the whole point of the step and one number hides it; each overwrite renders as struck old value then new value so the loss is visible before it happens; and the commit carries 'A bulk import cannot be undone.' A count without a diff asks the organiser to trust a number.
