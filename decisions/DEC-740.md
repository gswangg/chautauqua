# DEC-740: The sign-in page names the event and shows both public doors; the password minimum is 12, stated at the field and enforced by one constant

docs/design/Chautauqua Account.dc.html is unambiguous and none of it is built: the card reads "Sign in to DevFlow Conf 2027", and under a rule sits "NO ACCOUNT?" with two links — "Submit a talk ›" and "Browse the sessions ›". The CSS for that block (.chq-auth-footer / .chq-auth-footer-links in src/routes/auth.css.ts) has existed unused since the redesign; DEC-716 recorded a narrower version (CFP only) and never landed. The design pack is authoritative over DEC-716: both doors render, each suppressed when its destination does not exist (no open CFP → no "Submit a talk"; no published programme → no "Browse the sessions"), which keeps the conditional-and-quiet rule. The event name shows when the deployment has exactly one event, otherwise the generic subtitle stands. Separately, the pack's password field reads "At least 12 characters" while both forms carry minlength=8 and the route rejects below 8 — the number must be one exported constant used by the route, both inputs' minlength and the placeholder, so the field cannot promise what the route does not enforce. Tests asserting 8 are wrong and change.

## Amendment: the password policy has a MAXIMUM, enforced at one chokepoint (hash throws, verify refuses) (wave 2)

DEC-740 records "the password minimum is 12, stated at the field and enforced by one constant" and nothing else. Verified on main: no path bounds a caller-supplied password. src/auth/password.ts runs PBKDF2 at 100k iterations over whatever string arrives, from six call sites (api/users.ts x2, auth-login.tsx, auth-claim.tsx, account.tsx x2, auth-reset.tsx), including the ANONYMOUS /login surface whose rate limiter counts failures only (DEC-180) -- so a multi-megabyte password can be posted repeatedly at no cost to the attacker. Ruling: MAX_PASSWORD_LENGTH = 128 lives in src/domain/auth-copy.ts beside MIN_PASSWORD_LENGTH, and the bound is enforced INSIDE src/auth/password.ts so a future caller cannot forget it. The two directions differ on purpose: hashPassword THROWS (a write path must never truncate or silently accept a credential), verifyPassword RETURNS FALSE without hashing (an anonymous verify path must refuse, never 500). User-facing forms pre-check with copy in the existing minimum's register and declare a real maxlength, so the refusal is disclosed before submit. Consequence accepted and to be stated in the code: an existing password longer than the ceiling becomes unusable, and the reset flow is the way out.
