# DEC-699: Waitlisted is a HOLD, not a decision: a sixth submission status, never public, never 'decided', speaker-facing as "Under review"

src/domain/status.ts:5-18 carries exactly five literals and no waitlist, yet docs/design v4 ships WAITLISTED as a first-class filter chip (Submissions frame line 563), a bulk/queue action (line 97), a phone triage action (line 270), an Overview triage action (Overview frame line 108) and a Comms template (Comms frame line 366); SPEC.md:292 says "pending → accept_queue | decline_queue → accepted | declined (+ custom)", so a sixth literal is the spec's own extension point, and submission.status is plain text (schema.ts:198) so no migration is involved. Semantics, decided here so no task re-decides them: waitlisted is NOT decided (isDecided stays false — no acceptance planning, no accepted_at, never public, never on the agenda), it is not awaiting triage either, and speaker-facing surfaces keep the DEC-003 rule that internal queue states never leak, so src/server/repo/portal.ts's exhaustive switch maps it to the same "Under review" the queues use. The hazard that comes with any new enum member is NEGATIVE predicates: every `status != 'declined'`-shaped filter silently acquires a new member, so each one is re-read against the new vocabulary rather than assumed.
