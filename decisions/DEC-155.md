## Amendment (wave 34): the agenda payload's independent reads issue as one wave, and a drag never waits on a read it does not consume

J9 is the screen SPEC §7 singles out for high-frequency actions, and it is the deepest unowned waterfall in the app. GET /api/v1/events/:eventId/agenda serializes getEventInfo -> roomRows (payload.ts:36) -> trackRows (:42) -> loadAcceptedSessions (:48), and loadAcceptedSessions itself serializes its submission read then THREE further independent batch readers (rows.ts:82,100,115,153); getConflictsAndSummary serializes slotRows, its batch loop, roomRows (:283) and totalAcceptedRows (:289). PUT /submissions/:id/slot serializes ownership -> roomBelongsToEvent -> getEventInfo -> upsertSlot -> getConflictsAndSummary; DELETE serializes four. RULE: after the authz gate has resolved (getSubmissionOwnership / the event org-id check — A PARALLEL WAVE MAY NEVER OUTRUN ITS OWN AUTHZ GATE), every READ that does not consume another read's result joins one Promise.all wave. Every WRITE keeps its exact current position and order (upsertSlot before getConflictsAndSummary; unscheduleSlot before it; bumpIcsSequences unchanged) — no write is ever parallelized with another write or with the read that observes it. A chunked loop over one id list counts as ONE read and stays as it is. Where two reads in the same wave can each throw a user-facing ApiError (roomBelongsToEvent's 'invalid' vs getEventInfo's 'not_found'), the wave uses Promise.allSettled and re-throws in the ORIGINAL SOURCE ORDER, so the message a caller sees for a doubly-bad request is byte-identical to today's.

## Amendment (wave 61): the slot PUT's authz statement carries the event window, and the room check reads the ROOM's own event

PUT /api/v1/submissions/:id/slot still pays four sequential waves on every agenda drag/tap (~450ms measured): getSubmissionOwnership, then {roomBelongsToEvent, getEventInfo}, then upsertSlot, then getConflictsAndSummary. Two of those links are artificial. (1) getEventInfo is only ever called with ownership.eventId, and submission->event is one join: the ownership gate and the date-window read are ONE statement (LEFT JOIN, so 'submission missing' and 'event missing' stay distinguishable refusals rather than collapsing into one 404). (2) roomBelongsToEvent(db, roomId, eventId) takes eventId as an argument purely to compare it in SQL — resolving the room's OWN eventId and comparing in JS removes the dependency on ownership entirely, so the room check issues in the SAME wave as the context read instead of after it. Net: three waves instead of four, with the refusal ladder (submission 404 -> org 404 -> not-accepted 400 -> invalid-slot 400 -> room 400 -> event 404 -> day-range 400) byte-identical, including the existing test that the room error wins over event-not-found when a request is doubly wrong.

## Amendment (wave 68): a write phase is a wave too — PATCH /submissions/:id issues its independent writes together

Waves 60/61 collapsed this handler's READ waterfall into one settleInDeclarationOrder wave (src/routes/api/submissions.ts:405-466) and stopped there. The write phase below it (:486-541) is still seven sequential awaits — updateSubmissionFields, ensureBaselineRevision, appendSubmissionRevision, bumpIcsSequences, replaceSubmissionTracks, applyRoleAnswer(format), applyRoleAnswer(audienceLevel) — followed by getSubmissionDetail. On D1 over the wire each await is a 10-30ms round trip, which is what the mandate's measured ~533ms per description save is made of (docs/eval-findings.md P1-PERF). Only ONE pair is genuinely ordered: ensureBaselineRevision must stamp revision #1 before appendSubmissionRevision appends #2. The rest observe none of each other's results and touch disjoint columns/tables, so they issue as one wave; the detail read observes ALL of them and stays last, alone. The refusal semantics are untouched: the two 'field id missing after validation passed' Errors are evaluated before the wave is issued, and settleInDeclarationOrder (not Promise.all) keeps rejection order equal to source order. This is a shape change, not a semantics change — the NO-REGRESSION RULE binds, and the before/after measurement is the operator's perf env, so no lane may claim a measured closure.
