# DEC-746: A task is created FOR the accepted roster — creation always expands, and task kinds are named for what the speaker does (Upload / Form / Acknowledge)

The SPK grader's P2: New Task with "Assign to all accepted speakers" unchecked creates a permanently unassigned task with no recovery UI. The design answers it by omission — docs/design/Chautauqua Speakers.dc.html:184-216 shows the modal captioned "Applies to every accepted speaker" / "Created for all 12 accepted speakers" with fields Task, Due date, Kind, Required only: there is no checkbox because a task that applies to nobody is not a state the product offers. So `assignToAllAccepted` is deleted from the request body, from CreateTaskInput and from the modal (no compat shim, house rule), and createTask always expands through listAcceptedContactIds — the DEC-283/DEC-278 active-invite gate and the DEC-528 write cap are unchanged, only the flag goes. Separately the stored kinds general/file_request/form are internal words; the mock's segmented control names the speaker's action — Upload (file_request), Form (form), Acknowledge (general), in that order — so the label map lives in one exported function and the grid, modal and portal cannot drift.

## Amendment (wave 26): a task carries INSTRUCTIONS, and the speaker reads them where they do the work

CNT-01: the eval judge looked for instruction text on New-task and found none; verified on main — app/src/pages/speakers/TaskModal.tsx has Task/Due date/Kind/Form/Deliverable kind/Required and no free-text field, and schema/tasks.ts has no such column. A task title is an imperative, not a brief; 'Submit your slides' cannot say 16:9, under 20 MB, no video. Ruling: one nullable `instructions` TEXT column on `task` (never on task_assignment — the instruction is a property of the task, identical for every assignee), capped server-side at 2,000 characters using the DEC-124 long-answer cap grammar, editable in BOTH create and edit modes of TaskModal (unlike kind/formId/deliverableKind, instructions are safe to change after creation because they orphan nothing), and rendered on the speaker's own task row in the portal — not behind a disclosure, since a brief nobody opens is a brief nobody read.

## Amendment (wave 59, REVERSES 'creation always expands'): a task may be created for an explicit non-empty subset of the roster

This amendment REVERSES DEC-746's original ruling that "createTask always expands through listAcceptedContactIds." VERIFIED on main: src/server/repo/tasks/crud.ts:326-329 always expands to every accepted contact and app/src/pages/speakers/TaskModal.tsx:158 always subtitles 'Created for all N accepted speakers' — an organiser who needs one person to send one thing must create a task for the whole roster and then let 22 people see a chore that is not theirs. What DEC-746 actually forbade was a task that applies to NOBODY (an unassigned task with no recovery UI); a task that applies to SOME named people was never the question it answered. RULING: `POST /api/v1/events/:eventId/tasks` accepts an OPTIONAL `contactIds: string[]`. Absent means every accepted speaker, exactly as today (the default is unchanged and stays the modal's default). Present must be a non-empty array of ids that all pass filterRosterContactIds for this event — an empty array, a non-array, or an id that is not on this event's roster is refused with `fields.contactIds` naming the count that did not resolve, never silently narrowed and never silently widened. DEC-283/DEC-278's active-invite gate and DEC-528's write cap are untouched. The modal stops claiming 'all N' when a subset is chosen. The picker's population is the event roster fetched from the grid's own endpoint at page 1, perPage 200 (MAX_PER_PAGE, src/lib/pagination.ts:10); an event whose roster exceeds that states the ceiling and offers only 'Everyone accepted' — a refusal, never a truncated list presented as the whole population.

## Amendment (wave 77): a task's AUDIENCE is a property of the task, and DEC-932's acceptance back-fill ranges over the everyone-tasks only

VERIFIED at main c4d32612, both halves. (a) The UI offers the choice: app/src/pages/speakers/TaskModal.tsx:116 carries `audienceMode` ('everyone' | 'subset'), :374 renders "Everyone accepted (N)", :176 POSTs `contactIds` only for the subset case, and src/routes/tasks.ts:305-335 (DEC-746 wave-59) resolves those ids and assigns exactly them. (b) The schema cannot hold the choice: src/db/schema/tasks.ts has no audience column, so src/server/repo/submissions/status.ts:313 selects EVERY task row for the event and back-fills it onto EVERY newly-active contact, with its own comment at :303 declaring that as DEC-932's rule ("activation BACK-FILLS, it never snapshots"). Both the organizer accept path and the portal invite-accept path (src/routes/portal/index.tsx:695) run through it. So a task an organizer deliberately targeted at three speakers silently becomes universal at the next acceptance, and there is no unassign endpoint to repair it. Two decisions with opposite behaviour on one table; the younger, more specific one (DEC-746, a user's explicit choice) wins over the older blanket rule. RULING: `task.audience` is a real, defaulted column ('everyone' | 'targeted'), named once as TASK_AUDIENCES/DEFAULT_TASK_AUDIENCE in src/domain/task-kinds.ts beside TASK_KINDS; create-with-contactIds stamps 'targeted', create-without stamps the default; the back-fill's driving select filters to audience = DEFAULT_TASK_AUDIENCE, and the MAX_TASK_ASSIGNMENT_WRITES refusal message derives its per-contact row count from that FILTERED set so the number it tells the producer stays true. POST /tasks/:id/assign does NOT change audience — it only adds people, and widening a targeted task by side effect would be the same silent override one layer up. No unassign endpoint this wave: the defect is that a targeted task does not STAY targeted, and inventing a destructive repair path is a separate design question. DEC-932 keeps its meaning verbatim for everyone-tasks, which is every task it was written about.
