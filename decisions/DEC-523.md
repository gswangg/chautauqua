# DEC-523: portal-config's `/events/*` middleware is the exact wildcard events.ts documents as forbidden, and role gates are locked by an order-INDEPENDENT composition test

`src/routes/api/events.ts:56-59` states the rule in the codebase's own words -- 'a "/events/*" wildcard here would ALSO match the bare "/events" path ... re-introducing the exact reviewer lockout this task fixes' -- and lists its nested routes explicitly instead. `src/routes/api/portal-config.ts:37` then registers exactly `portalConfigRoutes.use("/events/*", requireOrganizer)`, whose composed pattern `/api/v1/events/*` matches the bare `/api/v1/events` list route that DEC-141 deliberately leaves reviewer-reachable (`events.ts:51-54`). It is inert today for one reason only: `src/index.ts:42-43` mounts `eventsRoutes` before `portalConfigRoutes`, and Hono composes matched handlers in registration order, so the already-registered list handler answers before the later middleware ever runs. Swapping two adjacent lines in index.ts -- an alphabetization, a lint autofix, a new sub-app inserted between them -- silently 403s every reviewer's event list, and no existing test catches it: `test/api-route-composition.test.ts:66-68` and `test/w10-verify-no-blanket-wildcard.test.ts:67-75` both replicate index.ts's current order and both probe `/api/v1/me`, never the bare events list. A gate whose correctness depends on mount order is not a gate. Decision: portal-config lists its own two path shapes (`/events/:eventId/portal-settings`, `/events/:eventId/resources`) and its `/resources/*` wildcard likewise becomes the explicit `:resourceId` shape, so no sub-app under /api/v1 owns a wildcard that can reach a sibling's collection route; and the regression is locked by a test that composes the sub-apps in the ADVERSARIAL order (portalConfigRoutes mounted first) and asserts a reviewer still gets 200 on `/api/v1/events` -- the invariant is order-independence, so the test must be the one thing index.ts is not.
