# DEC-024: SPA shared modules for wave 3: useCurrentEvent, useMe, api.ts as sole wire

Five wave-3 SPA tasks each need the current event and the caller's role; without one contract each would invent its own. app/src/lib/useCurrentEvent.ts exports useCurrentEvent(): { eventId: string | null, loading: boolean, error?: string } — resolution order: ?eventId URL param -> localStorage 'chq.currentEventId' (same key w2-f's stand-in uses) -> fetch GET /api/v1/events and take items[0].id, persisting it; errors surface loudly, no silent null. app/src/lib/useMe.ts exports useMe(): { me: { userId, email, role, orgId, contactId? } | null, loading } via GET /api/v1/me. Any wave-3 SPA task that finds either file missing on its branch creates it exactly to this contract (declared overlap; the merge train dedupes identical intents). All SPA API traffic goes through app/src/lib/api.ts (apiGet/apiList/apiPost/apiPatch/apiDelete, landed) — pages never call fetch() directly; the one extension allowed is an appended apiUpload(path, formData) helper (sets x-chq-csrf, credentials include, no manual content-type) owned by the Content SPA task for multipart uploads. The submissions-local useCurrentEventId.ts hook stays untouched until a cleanup wave. App.tsx role gating (reviewers see only Review, land on /review) is owned by the Review SPA task.

## Amendment (wave 19): the 401 door is ONE policy in ONE reader — app/src/lib/api.ts — and 403 is never a door

The wave-14 amendment established the policy "a 401 sends the caller to the login door" but implemented it in exactly one place: app/src/lib/useMe.ts:41. Every other endpoint in the SPA goes through request()/apiUpload()/apiPostBlob(), which turn a 401 into a generic ApiError that pages render as inline red text — so an organizer whose session expires mid-session sits on a page reading "Unauthorized" with no exit, on every screen, forever. A policy that lives in one hook is not a policy. It moves into api.ts's three wire paths, guarded by a module-level once-flag so N concurrent 401s assign /login exactly once, and the typed ApiError is STILL thrown so callers' catch/finally run (nothing silently resolves). 403 explicitly does NOT redirect: a signed-in user lacking a grant has a valid session, and bouncing them to /login would state something false about it. useMe keeps setMe(null) and drops its own assign() — a second reader of one policy is how the two drift.

## Amendment (wave 51): 'which event am I on' has one reader, one fetch, and a stored id is not an answer until /events confirms it

Two components answer this question and disagree by construction. eventSwitcherState.resolveCurrentEvent already knows a stored id may match nothing and falls back to items[0] -- but only for the switcher's own display, and it never writes the correction back. useCurrentEvent returns the localStorage/URL id verbatim and fetches /events ONLY when there is no stored id. So a chq.currentEventId left behind by a previous session (different persona, different org, or a deleted event) makes the header show event A while every page requests event B: 403/404 on every screen, with no self-heal short of devtools. Rule: /events is fetched ONCE per page through a single in-flight promise cache exported from app/src/lib/useCurrentEvent.ts (EventSwitcher consumes it instead of its own apiList('/events'), preserving SPEC §7's 'one round trip per view'); the pure helper in eventSwitcherState.ts is the ONE place that decides whether a stored id survives; the corrected id is persisted in exactly one place, the hook. The reconcile FAILS SOFT -- a failed or absent /events response leaves the stored id untouched, because a network blip must not evict a valid selection -- while the no-stored-id path stays loud as today.
