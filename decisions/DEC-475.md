# DEC-475: A conditional rule's fieldId is re-keyed exactly like the field's own id, or the rule is silently dead

src/server/repo/submit.ts:89 maps every form_field row's id through lockedFieldName (so answers are keyed 'title'/'description'/'email'), but line 97 passes rule through JSON.parse UNMAPPED. src/server/repo/portal-edit.ts:110/118 repeats the same asymmetry. Meanwhile src/server/repo/forms.ts:31-45 hands the builder the raw locked PK ('<formId>:title'), app/src/pages/forms/logic.ts:81-85 offers locked fields as rule targets, and src/forms/builder.ts:59 validates the rule against that raw id -- so the write path is legal and the read path is broken. Result: src/forms/visibility.ts:11 reads answers['<formId>:description'] === undefined forever, making the dependent field permanently invisible under 'eq' (and permanently visible under 'ne'), and validateAnswers silently drops it even when required. Silent-dead-rule is the worst failure mode this house allows: J1/CFP-03 breaks with no error anywhere. The fix is symmetry, not a new concept -- one shared normalizer applied to id and rule.fieldId in the same expression, so the two can never drift again. The builder API keeps raw PKs on purpose (validateRuleReference matches against them); only the render/validate projection normalizes.
