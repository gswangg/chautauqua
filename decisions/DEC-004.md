# DEC-004: Auth: PBKDF2 format, session tokens, cookies, CSRF

Password hash stored as literal format 'pbkdf2$v1$600000$<salt-b64url>$<hash-b64url>' — PBKDF2-SHA256, 600000 iterations, 16-byte random salt, 32-byte derived key, compared constant-time. Any code that hashes (login, seed) produces this exact format, so parallel implementations interoperate. Sessions: 32-byte random token, b64url, sent in HttpOnly cookie 'chq_session' (SameSite=Lax, Path=/, Secure only when request proto is https so local dev works); DB stores SHA-256 hex of the token in auth_session.token_hash, 30-day expiry, token rotated on every login. CSRF: JSON mutations under /api/v1 require header 'x-chq-csrf: 1' (custom-header check); plain HTML form posts (public CFP, portal) use a double-submit cookie 'chq_csrf'. Roles: user.role in ('organizer','reviewer','speaker'); speaker users link to their person via user.contact_id. Password auth, no magic links (eval agent has no inbox).

## Amendment (2026-08-11, stage-2 deploy)

Production workerd caps PBKDF2 at 100,000 iterations (NotSupportedError above
that); local dev does not enforce the cap, so the original 600k choice passed
every local gate and failed only on the deployed Worker (login 500). ITERATIONS
is now 100_000 — the runtime maximum. The hash format self-describes its
iteration count, so verify() is unchanged; seeded/stored hashes were
regenerated at 100k.

## Amendment (wave 58): a login attempt for an unknown email pays the SAME PBKDF2 cost as a known one — no branch may short-circuit before the KDF

src/routes/auth.tsx:353 is `if (!user || !(await verifyPassword(...)))`: JS short-circuits, so an unknown email skips 100k PBKDF2 iterations while a known email pays them. Responses are otherwise byte-identical and the rate limiter does not mask the difference, so any unauthenticated caller has a wall-clock account-enumeration oracle against a product whose whole CRM is people's email addresses. SPEC §6 asks for constant-time compares; a constant-time compare inside verifyPassword is worthless if the caller decides whether to call it. Ruling: src/auth/password.ts exports one checked-in, well-formed DUMMY_PASSWORD_HASH that no real password can match, and every credential-checking caller derives against `user?.passwordHash ?? DUMMY_PASSWORD_HASH` so exactly one derivation runs on both branches. The guard test asserts the CALL COUNT (spying crypto.subtle.deriveBits), never wall-clock timing — a timing assertion is flaky and would be the wrong invariant to freeze.


## Amendment (wave 27): the reset request never branches on whether the email exists

POST /forgot must render one identical response for a known and an unknown address -- 'If that address has an account, a reset link is on its way.' -- and must do the same amount of visible work either way (no extra redirect, no different status). This is the same oracle-closing discipline DEC-004 already applies to /login's single 'Invalid email or password' message and to the dummy-hash timing equalisation. The budget is the DEC-180 failures-only shape, keyed on the SUBMITTED email, incremented on every request (there is no 'failure' to condition on when the response cannot reveal one) via the atomic counter of DEC-948.

## Amendment (wave 44): enumeration-safety at POST /forgot binds the RESPONSE PATH's work, not just the response bytes — branch-dependent IO moves off it

DEC-004's wave-27 amendment already rules that /forgot 'must do the same amount of visible work either way', and its wave-58 amendment closed exactly this oracle at /login by forcing one PBKDF2 derivation on both branches. /forgot still violates its own rule: the known-address branch awaits createResetToken (a KV write), listEventsForOrg (a D1 read) and mailer.send (an HTTP call to the mail provider in production) before rendering CheckEmailPage, while the unknown branch pays one SHA-256 (src/routes/auth-reset.tsx:120-176). The response bytes are identical; the wall clock is not, by hundreds of milliseconds against a product whose entire CRM is people's email addresses. Ruling: every branch-dependent side effect moves into ONE deferred block scheduled through executionCtxOf(c)'s waitUntil when an ExecutionContext exists and awaited inline when it does not — the exact fallback shape servePublicGet uses (src/server/pubcache.ts:136-148), so existing direct-call tests keep observing the mint. Both branches then return after identical response-path work: the two rate-limit upserts plus one user lookup. Per the wave-58 precedent the guard asserts OPERATION COUNTS at response time, never wall-clock timing. DEC-180's consume-always/never-refund budget is untouched.

## Amendment (wave 22): the clear-cookie is the set-cookie's mirror, attribute for attribute

src/auth/cookies.ts:18-30 `buildSessionCookie` appends `Secure` when the request is https; :32-41 `clearSessionCookie` takes no options and emits `chq_session=; HttpOnly; SameSite=Lax; Path=/; Max-Age=0` with no `Secure` -- so signing out over TLS sets a non-Secure cookie on a name that was minted Secure. It happens to clear today because browsers match cookies on name/path/domain, but the pair being asymmetric is the defect: RFC 6265bis's Leave-Secure-Cookies-Alone rule makes the asymmetry load-bearing the moment any non-secure origin is in play, and the sibling builders (buildCsrfCookie, buildDraftCookie) both already take the flag. Ruling: `clearSessionCookie(options: SessionCookieOptions)` mirrors buildSessionCookie's attribute list exactly, differing only in the empty value and `Max-Age=0`; the one caller (src/routes/auth-login.tsx:242) passes `isSecureRequest(c.req.url)`. No defaulted parameter -- a default would let a future caller silently reintroduce the asymmetry, and this repo does not ship back-compat shims.

## Amendment (wave 55): one record, two views is an enumeration — every field the speaker portal writes must have a producer-side reader

SPEC J7 promises 'Speakers edit bio/social links/headshot and the changes appear on the producer's record instantly (one record, two views)'. Today that is kept by construction and by memory: the portal writes onto the shared `contact`/`submission` rows, and the admin readers happen to select the same columns. Nothing fails when a portal-written column gains no admin reader — the speaker sees their edit, the producer never does, and neither side errors. The counter-rule already exists for the deliberate cases: `title_at_time`/`org_at_time` are frozen at submission on purpose and must stay exempt in writing. RULING: enumerate the columns the portal profile/edit doors write and require each to be named by a producer-side reader or exempted with a written reason; fix rather than exempt.
