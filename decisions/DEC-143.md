# DEC-143: Duplicate detection surfaces same-normalized-name contacts even across distinct emails when normalized company also matches (or one side is blank); import stays an email-keyed upsert; merging stays a human act

src/domain/contacts.ts:82-86 suppresses any name-match group containing two different non-empty emails — which hides precisely the real-world duplicate (same person, work vs personal email) and the seeded test vector (two Priya Ramans, same company, different emails). New rule: within a normalized-name bucket, sub-group by normalized company treating blank company as wildcard; any sub-group of >=2 surfaces as a duplicate group regardless of email diversity. Surfacing is safe because merge remains an explicit organizer action (deliberate-actions principle) — the guard's job moves from hiding candidates to the human review step. CSV import keeps matching strictly by normalized email (update on match, create otherwise): silently merging different-email rows at import time would destroy data; the duplicates tab is where cross-email dupes get resolved. The import-reports-success-but-row-missing defect is a bug to reproduce at the route level and fix, not a design change.
