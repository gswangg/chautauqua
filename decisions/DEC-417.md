# DEC-417: One shared parseBoundedText caps every admin mutation's free-text field; oversized input is a 400, never a D1 SQLITE_TOOBIG 500

PATCH /api/v1/submissions/:id accepts an unbounded `title` (src/routes/api/submissions.ts:155-159); the write reaches D1, fails with `D1_ERROR: string or blob too big`, and the shared handler (src/server/http.ts:90-93) turns it into a generic `internal` 500 after seconds of payload buffering -- an authenticated-but-unthrottled DoS and a fail-loudly violation, since the client is told 'internal' rather than which field was too long. The public /submit path already caps answers via src/forms/validate.ts:8-9, so the gap is inconsistency, not intent. Sprinkling per-route length checks is the DEC-402/DEC-406 incomplete-coverage failure mode, so instead: ONE helper (parseBoundedText) sitting next to parseBoundedIdArray in src/server/http.ts, FOUR named caps living beside the existing two in src/forms/validate.ts (NAME 200, TEXT 2000, LONG_TEXT 20000, RICH_TEXT 100000) so the admin API and the public form agree on what 'too long' means, and ONE enumerated pass over every admin JSON mutation route in a single commit. The contacts CSV import is bounded in its own units (a csvText byte cap and a data-row cap, checked before parseCsv/applyImportRows) because an unbounded csvText is the same hole in different clothes.

## Amendment (wave 46): the request-input bound is ENUMERATED from source with a reasoned allowlist, not sampled one-route-per-file

test/field-length-limits.test.ts walks ONE over-cap request per route FILE. That is a sample, and the field guide's own rule is that rows are graded from enumeration, never a sample — and the sample missed five live free-text writes that reach D1 unbounded: src/routes/api/pipeline.ts:276 (note body -> repo.addNote), :213 (decline reason), src/routes/api/contacts/crud.ts:444 (add-to-event title -> submission.title), :132 (create-with-event sessionTitle -> submission.title) and src/routes/api/contacts/import.ts:94 (import batch sessionTitle -> submission.title). Every one of them surfaces an oversized payload as a D1 500 rather than the named field error its siblings produce. Decision: (a) the five get the bound their sibling endpoints already apply — MAX_LONG_TEXT_LENGTH for the pipeline note body, MAX_TEXT_LENGTH for the decline reason, MAX_NAME_LENGTH for all three title fields, each raised as ApiError("invalid", ..., { <field>: "Max N" }); (b) the sample becomes a scan, in the DEC-628 shape that already works in this repo — enumerate every hand-rolled `typeof body.<name> !== "string"` required-check under src/routes and fail loudly, naming file:line, unless the same handler applies a length bound OR the field appears in a named { file, field, reason } allowlist (ids, enums, and byte-capped payloads belong there, with the reason stated, never as silence).

## Amendment (wave 46): landed

The five writes named above now carry the bound named for each: src/routes/api/pipeline.ts:281 (note body, MAX_LONG_TEXT_LENGTH), :213-216 (decline reason, MAX_TEXT_LENGTH), src/routes/api/contacts/crud.ts:447-450 (add-to-event title, MAX_NAME_LENGTH), :132-137 (create-with-event sessionTitle, MAX_NAME_LENGTH) and src/routes/api/contacts/import.ts:94-100 (import batch sessionTitle, MAX_NAME_LENGTH), each raised as `ApiError("invalid", "Validation failed", { <field>: "Max <N>" })`. test/field-length-limits.test.ts now also carries the enumerating scan described in (b) above, with the ids/enums/byte-capped fields on a reasoned `UNBOUNDED_STRING_FIELDS` allowlist rather than silently skipped.

## Amendment (wave 31): the read side gets the same bound as the write side — list FILTER strings are capped in the parser, never at the D1 bind

DEC-417 closed unbounded free text on every admin MUTATION; the read side was never swept. parseListQuery (src/server/repo/submissions/query.ts:137) and parseContactListQuery (src/server/repo/contacts/query.ts:30-33) are trim-or-null with no cap on `q`, `trackId` or `segmentId`, and both are reused by the export routes (src/routes/api/exports.ts:96/111), so a megabyte query string reaches a D1 LIKE bind and surfaces as a generic `internal` 500 — the exact shape DEC-417 named, in the other direction. Ruling: one new pure module src/lib/query-bounds.ts declares MAX_SEARCH_QUERY_LENGTH = 200 (a search box is a name-sized input, matching MAX_NAME_LENGTH's order) and MAX_FILTER_ID_LENGTH = 64 (id-sized, matching parseBoundedIdArray's per-id cap); over-cap is a 400 naming the field, never a silent truncation, because a truncated query answers a different question. The repo parsers keep throwing plain Errors (the layering rule stands — repo modules do not import ApiError/hono) and EVERY call site converts, including the two that currently do not: src/routes/api/contacts/crud.ts:73 and src/routes/api/exports.ts:111, where a throw is presently a 500. Same read-side rule covers ?rules= (src/routes/api/contacts/segments.ts:67), which bounds neither the rule COUNT nor each rule's `value`: cap the set at MAX_SEGMENT_RULES = 20 declared in that file and bound each value with the existing MAX_NAME_LENGTH from src/forms/validate.ts — deliberately NOT the new module, so the rules fix and the parser fix stay independently landable.

## Amendment (wave 63): the control that types a capped field DECLARES the cap — every free-text input/textarea in the settings register carries maxLength from the same pure-core constant its route enforces, locked by a source scan

DEC-417 put every admin mutation's free-text cap on the server; waves 58 and 61 taught three SPA components and the portal's SSR profile inputs to declare theirs. The settings register never got the lesson: `maxLength` appears exactly 7 times in the entire SPA (SubmissionDetailPage, TaskModal, CommentThread, PipelineBoard, PlanEditor) and ZERO times across the nine panels under app/src/pages/settings/, which render 32 chq-input/chq-textarea controls whose values the routes cap (src/routes/api/events.ts:223 location at MAX_TEXT_LENGTH, :96 names at MAX_NAME_LENGTH, portal-config.ts, forms.ts, embeds.ts, tokens.ts, views.ts, segments.ts). A producer pastes a 300-character event name into a control that accepts it silently, then gets a server refusal that is the first mention of any limit — the cap is documentation, not an affordance. One exemption is principled and must be stated rather than implied: SessionboardImportPanel's paste textarea is bounded in BYTES via MAX_IMPORT_CSV_BYTES, not characters (the reason string test/field-length-limits.test.ts:625 already uses), so a character maxLength would be a second, disagreeing cap. A source scan over the directory keeps the sixth panel from being the one nobody enumerated.

## Amendment (wave 68): "a text control declares the cap its route enforces" binds EVERY app/src/pages directory, not just settings — and the constant is imported, never typed

w63-e proved the rule with a derived-population scan whose population is app/src/pages/settings/** — a directory someone typed. Verified on main: `maxLength` occurs 40x in app/src and ~35 of those are inside that one directory, while ~65 `chq-input`/`chq-textarea` controls across contacts/speakers/review/comms/submissions/content/forms/agenda declare nothing though their routes cap them (ContactDrawer 8, RosterPanel 7, BreaksPanel 8, NewContactModal 5, FieldModal 5, PlanEditor 14, NewSubmissionModal 4, ComposeWizard/TemplatesTab 6, Scorecard 2, ...). The producer types past the server's limit and gets a 400 after filling the form — the exact failure the v9 error standard's "count against limits" rule exists to prevent. Ruling: one scan, population re-derived from app/src/pages/** at test time; every offender takes `maxLength={CONSTANT}` imported from the module that owns the cap (src/forms/validate.ts, src/lib/query-bounds.ts MAX_SEARCH_QUERY_LENGTH for search boxes, src/domain/*), or an EXEMPTIONS row with a principled reason (read-only copy-fallback echo, a value no capping route reads, a closed grammar such as hex colour, a non-text type). Where two caps are plausible, choose the LOOSER — a control must never invent a cap tighter than its server's. Hand-typed numbers are forbidden by the same scan.

## Amendment (w1): a cap belongs to the COLUMN, so every writer enforces it — including the bulk importers

Verified at the file: mapImportRow (src/domain/contacts.ts:713-760) assigns the raw CSV cell to email/firstName/lastName/company/title/phone/bio and to custom.<key> with no length check of any kind; applyImportRows and the Sessionboard planSessionboardRows do the same. Both import routes bound only BYTES and ROWS. Meanwhile every hand-typed editor of those same columns caps at MAX_NAME_LENGTH=200 (api/contacts/crud.ts, portal-edit.ts:474-476, portal/profile.tsx) or MAX_LONG_TEXT_LENGTH. So an import mints contacts whose own drawer refuses to re-save them, 500 rows at a time, and the producer discovers it one contact at a time. Count the writers of the column, not the validators of the form. Ruling: the importers validate per field against the identical constant, refuse the ROW rather than truncating (fail loudly), and surface the refusal at PLAN time with the offending target named, so the dry-run Review step can offer the V9 partial action ('import the 205 good rows') instead of failing the batch at apply time.

## Amendment: a per-item check guarded by a typeof must REFUSE the wrong type, never skip it (wave 2)

src/routes/api/contacts/crud.ts validates customFields with `if (typeof value === 'string') checkLen(...)` on both the create and patch branches. A number, array, or object value skips validation entirely, is then cast `as Record<string,string>`, JSON-stringified into custom_fields_json, and read back by src/domain/contact-labels.ts's contactLabels as if it were a string. That is a silent accept dressed as a bounds check -- the house's fail-loudly rule inverted -- and it is the same shape as the field-guide's PARSE RESULT DISCARDED != PARSED. Ruling: a typeof guard in front of a validation call is a refusal branch, not a skip branch; the non-string case gets its own field error in the same shape the drawer's err.fields reader already consumes.

## Amendment (findings wave 14): a validator that accumulates a fields map may not call a helper that throws — accumulate-or-throw is chosen once per validator, not once per field

validateBreakWrite (src/routes/api/breaks.ts:107-164) accumulates every problem into `fields` for a single 400 raised at :180 (POST) and :202 (PATCH) — except two branches: :132 parseBoundedText(body.label) and :137 parseBoundedOptionalText(body.location), which throw immediately from src/server/http.ts:131-141. So a break write with a bad `day` PLUS a blank `label` reports only `label`, silently discards the already-set fields.day, and never runs the per-field startMin/durationMin checks or the DEC-022 wave-66 cross-field midnight check at :159 — the organiser fixes one field, resubmits, and is refused again on a different field the server already knew about. RULING: src/server/http.ts grows COLLECTING siblings alongside the throwing ones — collectBoundedText(value, field, opts, fields) and collectBoundedOptionalText(value, field, opts, fields) — which write the IDENTICAL message (same overCapFieldMessage/'Required'/'Invalid' vocabulary) into the caller's fields map and return a fallback value instead of throwing. The throwing forms stay unchanged for the many single-field callers (views.ts, embeds.ts, exports.ts, email-log.ts, segments.ts): this adds a second door, it does not migrate anyone. validateBreakWrite is the one caller converted.

## Amendment (wave 14): landed

src/server/http.ts factors the shared bounded-text check (the 'must be a
string' / 'Required' / over-cap message vocabulary) into one internal
`checkBoundedText` helper, consumed by both parseBoundedText/
parseBoundedOptionalText (unchanged signatures and behaviour) and the two
new collecting exports, `collectBoundedText` and
`collectBoundedOptionalText`, which write into a caller-supplied `fields`
map and return a safe fallback instead of throwing. src/routes/api/breaks.ts's
validateBreakWrite now calls the collecting forms at its label (:132) and
location (:137) sites, so a break write with a bad `day`, a blank `label`,
an out-of-bounds `startMin`, and a durationMin that overruns midnight now
reports all four fields in one 400, and the DEC-022 (wave 66) resolved-value
cross-field midnight check still runs even when label/location are also
invalid. test/schedule-breaks.test.ts covers both: a POST accumulating all
four problems, and a PATCH proving the cross-field check fires against the
resolved (stored + patched) values even when label is independently invalid.
