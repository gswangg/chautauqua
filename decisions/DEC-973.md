# DEC-973: A hidden trigger hides its dependents structurally — the transitive fixed point marks, it does not delete the answer

DEC-532 implements 'hidden trigger ⇒ dependent hidden' by copying the answer map and DELETING every hidden field's answer (src/forms/visibility.ts:45-46), then re-evaluating. That is only correct for kinds whose absence canonicalizes to undefined. Checkbox is deliberately not one of them: DEC-867/DEC-681 canonicalize an absent checkbox to `false` — 'an unchecked box is a real value, not an absence' (src/forms/rule-match.ts:36) — which is right for a visible trigger and wrong for a hidden one. So a field ruled {op:'ne', value:true} or {op:'eq', value:false} on a checkbox trigger that is ITSELF hidden stays visible AND required, and the browser twin agrees on the same wrong answer: src/views/form-render.tsx:215 passes `undefined` into the identical canonicalizer. The public submit POST validates against this predicate, so a submitter can be blocked by a required field they cannot see. The fix belongs to the fixed point, not the canonicalizer: RULE_MATCH_CASES' `checkbox / undefined / ne true → true` row is correct for a genuinely unanswered visible box and stays. Rule: resolveHiddenFieldIds hides a field whose rule names an already-hidden field directly (same branch shape as the missing-target case), the effectiveAnswers copy-and-delete step is removed entirely, and the inline browser twin's computeHidden takes the identical early branch in the same commit — one behaviour, two implementations, one test table.
