# DEC-840: The distribute wire contract: the cap is a parameter of this run, echoed back, and the shortfall is part of the answer

DEC-824 settled that distribution owes the work it could NOT do; its code never landed either (app/src/pages/review/PlanEditor.tsx:364-398 still GETs a capless preview and POSTs an empty body, and the dialog reports only per-reviewer totals). Pinning the shape here so the route half and the editor half can be built in parallel. Contract: GET /plans/:id/assignments/distribute/preview?cap=<n> and POST /plans/:id/assignments/distribute with body {cap?: number|null} — cap optional, positive integer, loud 400 otherwise — and the preview ECHOES the cap it used so the apply sends byte-identically what the organiser saw. Both return {cap: number|null, totalAssigned: number, items: {submissionId, userId}[], perReviewer: {userId, name, trackName: string|null, before: number, after: number, added: number, eligible: boolean, reason: 'cap_reached'|'wrong_track'|null}[], shortfall: {submissionId, ref, title, needed: number, reason: 'cap_reached'|'no_eligible_reviewer'}[]}. Reviewers the run cannot use are LISTED with eligible:false and their reason rather than omitted, because an absent name reads as an oversight; a non-empty shortfall renders as a sentence naming the constraint and the track. The action is renamed 'Distribute the unassigned' — it fills the unassigned pool, it does not level existing load — and nothing is written before the explicit confirm (DEC-786 unchanged).

## Amendment (wave 51): the distribute confirm shows the run, not a sentence about it

GET /plans/:id/assignments/distribute/preview already returns everything design frame 03 asks for -- per-reviewer name, trackName, before, after, added, eligible and a closed-vocabulary reason, plus the cap the run used, totalAssigned and the per-submission shortfall -- and the confirm dialog collapses all of it into one <ul> of interpolated strings ('Name — 6 → 8 talks' / 'Name — unchanged · wrong track'). The organizer cannot see how many talks are in play, how many reviews the plan needs at N each, how many reviewers are participating, or what stays unstaffed, and the cap input clips its own placeholder. Rule: the dialog renders the frame's anatomy -- a cap row 'CAP PER REVIEWER [n] talks each', a summary line 'N talks · M reviews needed at K each · R reviewers', a three-column table (name | track | 'before → after talks' or 'unchanged · <reason>'), a primary naming its count ('Assign these N'), and the leftover line -- every figure DERIVED from the existing DistributePreview payload plus the plan's own reviews-per-talk field. No new endpoint and no new server field: a payload that already carries the answer must not be summarised into ambiguity.
