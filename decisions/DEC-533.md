# DEC-533: Conflict detection is bucketed by (day, room) and (day, speaker) and computed ONCE per payload -- autoSchedule already proved the index; findConflicts is the same invariant done the slow way

`findConflicts` (src/domain/schedule.ts:42-73) is a naive double loop over every pair of placed sessions, and inside each intersecting pair it does an O(s^2) `filter`/`includes` over the two speaker lists. `scheduleSummary` (:78-87) then calls `findConflicts` AGAIN purely to take `.length`. The callers make it worse: `the former src/server/repo/agenda.ts:314-315 (now split across src/server/repo/agenda/)` computes it twice per agenda load and `:350-351` twice more after EVERY drag-drop slot write, and `src/server/repo/overview.ts:143,483` computes it twice more on the producer's first screen. At the SPEC.md scale target of 200-800 accepted sessions that is up to 320,000 pair comparisons per pass and over a million per drag -- against SPEC section 7's p95 < 100 ms write budget on the surface SPEC calls "the most fluid artifact of an event". The same module already contains the correct structure: `autoSchedule`'s DEC-130 occupancy index keys `${day}|${roomId}` and `${day}|${contactId}` and never re-scans the trial set. Two implementations of one invariant means one is wrong, and it is the one that compares every pair. Decision: (a) `findConflicts` keeps its EXACT signature and must return a byte-identical array -- same pairs, same order, same `detail` strings -- because callers render `submissionIds` order and `overview.ts:181` builds rows from it; the guard is a randomized differential test against a naive reference implementation written inline in the test file, not a hand-written expectation list. (b) Internally it buckets by day first, then indexes by roomId and by contactId within the day, comparing only same-bucket candidates, and emits in ascending (i, j) original-index order with room_overlap before speaker_overlap per pair. (c) `scheduleSummary` gains an optional third parameter `conflicts?: Conflict[]` so a caller that already has them does not pay a second pass, defaulting to today's behavior; agenda.ts's two call sites pass the already-computed array. overview.ts's calls are deliberately left alone -- they become cheap by construction and are not worth widening this task's blast radius.
