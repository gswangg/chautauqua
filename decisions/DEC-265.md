# DEC-265: Participant API responses carry the contact's name and email server-side: an optimistically appended row must render identically to a reloaded one

Confirmed in the tree at src/server/repo/participants.ts:35-42/84 - ParticipantRow is {id, contactId, role, order, visible, inviteStatus} with an explicit comment that name/email are omitted 'which callers can join in separately' - while the SPA contract type SubmissionDetailParticipant (src/server/repo/submissions/detail.ts:10-19, mirrored in app/src/pages/submissions/types.ts) requires name and email, and SubmissionDetailPage.tsx:237 appends the raw POST response straight into detail.participants. Result: a co-presenter shows blank Name/Email until the next page load. This is exactly the DEC-239/DEC-246 class of defect (server shape vs SPA contract KEY mismatch that no render sweep catches). Decision: the SERVER fills name and email - not the client patching them in from the contact-search result it happens to hold - because /api/v1 is dogfooded by the SPA but also consumed directly (DEC-027 bearer tokens), and a REST row missing the human-readable fields is wrong for every non-SPA consumer. Formatting must match detail.ts exactly: `${firstName} ${lastName}`.trim(). The invite route already fetches the contact for org-scoping (findContactForOrg), so this costs no extra query on the write path; the PATCH path joins contact in getParticipantRow. The locking test is reload-equivalence: the object returned by POST deep-equals the same participant as returned by the submission-detail read.
