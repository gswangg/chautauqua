# DEC-914: A back link names the route it LANDS on, and the portal has one back-link grammar

src/routes/portal/profile.tsx:142 renders `<a href="/portal">← Back to My Submissions</a>` — the label promises the submissions list and the href delivers the portal home. Two lines away, src/routes/portal/index.tsx:480 writes '← Your portal' for the same destination and :422 writes '← Back to My Submissions' for /portal/submissions, so the product has three strings for two routes and one of them is false. The field guide already states the rule that was violated ('a link is the route it LANDS on'), which means the fix is not to retype the string on profile.tsx — a hand-written label per page will drift again the next time a route moves. Rule: shared.tsx exports ONE PortalBackLink taking the destination path and resolving its label from a single table (/portal → 'Your portal', /portal/submissions → 'Your submissions', /portal/tasks → 'Your tasks'), rendered as '‹ <label>'. No portal page writes a back-link string. Same pass: profile.tsx's page heading is an <h2> on a page with no <h1> — the portal's heading level follows the page, not the visual size.

## Amendment (wave 16): a server-rendered href is scanned against the route table, the same way an in-app target already is

DEC-914 gave the portal a back-link table because a link must name the route it lands on, and DEC-837's scan enforces that for every react-router target in app/src. Neither reaches src/routes/**/*.tsx -- the public, portal, auth, account and docs surfaces build hrefs as string/template literals with no guard at all, and the field guide already records this exact bug class twice ('GUESSABLE URL 404 IS DEAD END', 'LINK LABEL RIGHT, HREF A ROUTER PATTERN NOT A ROUTE'). The SSR side is where a dead link costs most: an anonymous visitor has no nav memory to recover with. Every literal internal href emitted by an SSR surface must resolve to a route pattern registered in that same tree (path params matched by shape), or be allowlisted with a reason (external, mailto, in-page anchor).

Landed (wave 16, task w16-d): test/ssr-link-targets-scan.test.ts. Route table is derived, not hand-listed -- it reuses test/docs-route-coverage.test.ts's DEC-518 technique (parse every literal `app.route("<prefix>", <identifier>)` call out of src/index.ts's own source, resolve the identifier through that file's imports, dynamically import the real sub-app, mount it into a throwaway Hono app at the exact prefix) and reads the resulting app's own `app.routes` table -- this automatically picks up the SURFACES for-loop in src/routes/public/index.tsx (each surface registers a concrete `.get()` at import time) and the admin SPA's `/admin` + `/admin/*` shell mounts (src/routes/root.tsx) with no special-casing. hrefs are collected from every `href="..."`, `href='...'`, `href={\`...\`}` in src/routes/**/*.tsx; a template literal's static prefix up to the first `${` is matched against registered patterns by leading-segment shape (a href like `/e/${slug}/sessions` only has to match a pattern that continues past `/e/` -- it can't see the rest). Two non-obvious allowlist entries, both with reasons in the test file: an interpolation whose static prefix is empty (`href={\`${basePath}...\`}` -- nothing left to check), and src/routes/public/submit.tsx:657's mailer HTML body, which nests a literal `href="${safeClaimUrl}"` HTML-attribute string inside an outer JS template literal (not JSX) -- the double-quote regex sees it as a plain string with no static path text, and safeClaimUrl is already an absolute built URL, not a route pattern. No dead SSR hrefs were found; every literal href already resolved to a registered route.

## Amendment (wave 17): a scan's ROOT is part of its claim — the SSR link guard covers every server-rendered .tsx, and a form's action is a route too

test/ssr-link-targets-scan.test.ts (landed w16-e) scans only src/routes/**/*.tsx and only the `href` attribute. Two consequences, both verified on main: (1) src/server/not-found.tsx is OUTSIDE the root — that is the exact file whose ORGANIZER_NOT_FOUND_LINKS pointed at bare /overview and /submissions, the bug this guard was written to make impossible; src/views/form-render.tsx is likewise outside. (2) ~20 literal `action=`/`formaction=` targets across portal, auth, account and public submit are unchecked, and a dead form action costs more than a dead link because it loses the data the visitor already typed. The guard must derive its roots (walk src/, take .tsx, drop *.test.tsx) rather than name one directory, and must resolve actions against the registered route table for the FORM'S METHOD, not the GET table.
