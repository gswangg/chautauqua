# DEC-465: One `listPerPage` in src/lib/pagination.ts replaces five per-route copies of DEC-461(a)'s rule; three call sites never implemented that rule at all

DEC-461(a) said "route default perPage 200" and four lanes implemented it four ways. In the tree right now there are five local helpers with identical bodies — `perPageWithDefault200` (src/routes/api/views.ts:26, src/routes/api/tokens.ts:25, src/routes/comms/templates.ts), `resolvePerPage` (src/routes/review/plans.ts:49, src/routes/review/reviewer.ts:36) — plus `clampConfigPerPage` exported from src/routes/api/events.ts:47 and imported by another ROUTE file (src/routes/api/portal-config.ts), a layering inversion. Worse, three endpoints wrote `clampPerPage(c.req.query("perPage") ?? 200)` (src/routes/api/pipeline.ts:67, src/routes/api/users.ts:52, src/routes/api/contacts/segments.ts:98), which handles ABSENT correctly and INVALID wrongly: `?perPage=abc` falls through clampPerPage to DEFAULT_PER_PAGE=50, so /api/v1/users returns 50 rows where /api/v1/tokens returns 200 for byte-identical input, and test/admin-list-bounds-config.test.ts already asserts the 200 answer. The rule is one function, in the pure core, exported verbatim as: `export function listPerPage(raw: string | number | null | undefined): number { if (raw === undefined || raw === null || raw === "") return MAX_PER_PAGE; const n = typeof raw === "number" ? raw : Number(raw); if (!Number.isFinite(n) || !Number.isInteger(n) || n < 1) return MAX_PER_PAGE; return Math.min(n, MAX_PER_PAGE); }` — absent OR invalid resolves to MAX_PER_PAGE, an explicit valid value clamps to [1, MAX_PER_PAGE]. Every local copy is deleted; no route file imports another route file for pagination. src/routes/tasks.ts's onboarding-grid clamp (DEFAULT_GRID_PER_PAGE=50) is a deliberately different contract for a grid that has always paged, and stays.
