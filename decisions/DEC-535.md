# DEC-535: The J4 bulk reviewer nudge carries a named per-request bound, the same way its J6 sibling does; the reviewer-side dedupe window is deliberately deferred, not forgotten

`POST /api/v1/plans/:id/remind` (src/routes/review/plans.ts:382-442) loops every reviewer on the plan and sends one email each, with no cap, no ordering, and no `remaining` in its response. Its sibling -- the J6 "remind everyone outstanding" button -- has had exactly those since DEC-319: `MAX_REMINDER_BATCH = 100`, `capReminderGroups` sorting by id first so a second click advances to the next slice instead of repeating the first, and `remaining` returned so the organizer knows to click again. SPEC principle 4 says sends are "templated, previewed per-recipient, capped, and logged"; this one is not capped, and an organizer who clicks twice re-emails every laggard with nothing recorded. Decision: (a) the generic capping rule moves into ONE function -- `src/domain/reminders.ts` gains `capById<T>(items, idOf, max): { items, remaining }` and `capReminderGroups` becomes a thin delegate, so there is not a second implementation of "sort, slice, report the remainder"; (b) `MAX_REVIEWER_REMINDER_BATCH = 100` is declared next to `MAX_REMINDER_BATCH` in the same pure module, matching DEC-019's 100-recipient compose cap; (c) the handler sorts laggards by `userId` ascending, caps, and returns `{ reminded, sent, failed, remaining }`. (d) EXPLICITLY NOT DONE, so it is not re-raised as a miss: a reviewer-side dedupe window equivalent to `MANUAL_DEDUPE_WINDOW_MS`. plan_reviewer has no `last_reminded_at` column, that is a migration, and a cap alone already removes the unbounded burst; the dedupe is a stage-1-optional refinement whose absence is now documented rather than accidental.
